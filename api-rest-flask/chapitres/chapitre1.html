Chapitre 1 — API Web & le protocole HTTP

Module 1 ≈ 2 h 30 de travail Accès libre
Mise en situation

Dans les architectures logicielles actuelles, les applications frontend (React, Vue, mobile) et les micro-services doivent échanger des données de façon standardisée et découplée. Le protocole HTTP et le format JSON constituent le socle universel de cet échange moderne.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. comprendre le modèle d’échange client-serveur sur le Web ;
  2. analyser la structure d’une requête et d’une réponse HTTP ;
  3. différencier les verbes HTTP fondamentaux (GET, POST, PUT, DELETE) ;
  4. maîtriser le rôle des en-têtes Content-Type et Accept pour la négociation de contenu ;
  5. manipuler les types de données fondamentaux du format JSON.

1. L’architecture client-serveur et les API Web

Une API (Application Programming Interface) définit un contrat formel permettant à deux programmes informatiques distincts de communiquer et d’échanger des données. Dans le contexte web, une API Web expose des points d’entrée (endpoints) accessibles via le protocole HTTP sur le réseau.

Le modèle repose sur une stricte séparation des responsabilités :

  • Le Client : initie les demandes (navigateur web, application mobile, script serveur, outil cURL).
  • Le Serveur : reçoit les requêtes, traite la logique métier, interroge la base de données et renvoie une réponse structurée.
L’API comme menu de restaurant

Le client est le client assis à table, le serveur est la cuisine, et l’API est le menu : le client commande un plat précis selon les règles du menu sans avoir besoin de savoir comment les cuisiniers préparent les ingrédients en cuisine.

2. Anatomie d’une requête et d’une réponse HTTP

Le protocole HTTP (Hypertext Transfer Protocol) est un protocole de la couche application fonctionnant en mode requête/réponse textuel ou binaire.

Une requête HTTP comprend quatre composantes clés :

  1. La ligne de requête : méthode (ex. GET), chemin d’accès (ex. /api/v1/articles) et version du protocole (ex. HTTP/1.1).
  2. Les en-têtes (Headers) : métadonnées sous forme de paires clé-valeur (ex. Host, User-Agent, Content-Type).
  3. Une ligne vide : séparateur obligatoire entre les métadonnées et le corps.
  4. Le corps (Body) : données transmises lors de mutations (JSON, formulaire), absent dans la plupart des requêtes GET.
POST /api/v1/utilisateurs HTTP/1.1
Host: api.monsite.fr
Content-Type: application/json
Accept: application/json

{
  "nom": "Camille",
  "email": "camille@domaine.fr"
}
Format de la réponse HTTP

La réponse envoyée par le serveur respecte une symétrie rigoureuse :

HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 42,
  "nom": "Camille",
  "email": "camille@domaine.fr"
}

3. En-têtes HTTP et négociation de contenu

Les en-têtes HTTP permettent au client et au serveur de négocier les caractéristiques de leur échange.

En-têteÉmetteurRôle
Content-TypeClient ou ServeurIndique le format des données incluses dans le corps (ex. application/json).
AcceptClientIndique les formats de données acceptés en retour (ex. application/json).
AuthorizationClientTransmet les identifiants ou jetons d’authentification (ex. Bearer <token>).
Piège fréquent : Oublier le Content-Type

Si vous envoyez un corps JSON lors d’une requête POST sans préciser Content-Type: application/json, la plupart des frameworks comme Flask ignoreront le parsing JSON automatique et request.get_json() renverra None.

4. Le format JSON (JavaScript Object Notation)

JSON s’est imposé comme le format universel d’échange de données sur le web, remplaçant largement XML grâce à sa légèreté et sa facilité d’intégration dans tous les langages.

Un document JSON ne peut contenir que six types de valeurs :

  • Objet : collection non ordonnée de paires "clé": valeur délimitée par { }.
  • Tableau : liste ordonnée de valeurs délimitée par [ ].
  • Chaîne : texte encadré obligatoirement de guillemets doubles "...".
  • Nombre : entier ou flottant (ex. 42, 3.14).
  • Booléen : true ou false (en minuscules strictes).
  • Nul : null (absence de valeur).

Exercice 1 — Ligne de requête HTTP

Python Niveau 1 — Acquisition

Objectif : Décomposer une ligne de requête HTTP brute en méthode, chemin et version.

Une requête HTTP débute par une ligne contenant trois éléments séparés par des espaces : la méthode (ex: GET), la cible / chemin (ex: /api/v1/users) et la version du protocole (ex: HTTP/1.1).

Lit la ligne sur l’entrée standard et affiche les trois valeurs sous la forme suivante :
Methode: <methode>
Chemin: <chemin>
Version: <version>

Entrée du programme
GET /api/v1/users HTTP/1.1
Sortie attendue
Methode: GET
Chemin: /api/v1/users
Version: HTTP/1.1

Requête GET classique sur la collection users.

Deux indices, rédigés en mots
  1. Utilisez la méthode ligne.split() pour séparer les éléments sur les espaces.
  2. Affichez chaque valeur sur une ligne dédiée avec le préfixe demandé.

Exercice 2 — Extraction de la Query String

Python Niveau 2 — Application

Objectif : Analyser une URL et extraire ses paramètres d’URL ordonnés alphabétiquement.

Dans une API REST, la Query String permet de filtrer, paginer ou trier une collection. Elle débute après le caractère ? et se compose de paires clé=valeur séparées par &.

Lit une URL complète sur l’entrée standard. Extrayez les paramètres et affichez chaque paire sous la forme cle=valeur, triée par ordre alphabétique de la clé. Si l’URL ne contient aucun paramètre, affiche Aucun parametre.

Entrée du programme
https://api.site.fr/v1/articles?limit=10&page=2&sort=desc
Sortie attendue
limit=10
page=2
sort=desc

Trois paramètres déjà dans l’ordre alphabétique.

Trois indices, rédigés en mots
  1. urlparse(url).query renvoie la chaîne de paramètres brute.
  2. parse_qsl(query) renvoie une liste de couples (cle, valeur).
  3. Triez la liste avec sorted(..., key=lambda x: x[0]) avant d’afficher chaque paire.

Exercice 3 — Validation des en-têtes HTTP JSON

Python Niveau 3 — Raisonnement

Objectif : Vérifier la compatibilité JSON des en-têtes Content-Type et Accept.

Une API REST moderne dialogue couramment au format JSON. Dans les en-têtes HTTP reçus, le client indique le format envoyé via Content-Type et le format attendu via Accept.

Lit l’ensemble des lignes d’en-têtes HTTP sur l’entrée standard jusqu’à EOF. Chaque ligne est au format Nom-Entete: Valeur.

Vérifiez si application/json est présent soit dans Content-Type soit dans Accept (en ignorant la casse).
Si oui, affichez JSON supporte.
Sinon, affichez Format non supporte.

Entrée du programme
Host: api.exemple.com
Content-Type: application/json
User-Agent: curl/8.4.0
Sortie attendue
JSON supporte

Content-Type indique du JSON.

Deux indices, rédigés en mots
  1. Sépare le nom de l’en-tête et sa valeur sur le premier caractère deux-points (header.split(":", 1)).
  2. Convertissez les noms et valeurs en minuscules (.lower()) pour une comparaison robuste.

6. QCM — niveau examen

Une API Web repose principalement sur quel protocole de communication ?

HTTP (et sa variante chiffrée HTTPS) est le protocole de transport fondamental des API Web.

Quelle partie d’une requête HTTP contient les données envoyées lors d’un POST ?

Le corps de la requête transporte la charge utile (payload) envoyée au serveur.

Quel en-tête informe le serveur que les données soumises sont au format JSON ?

Content-Type décrit le format des données contenues dans le corps de la requête.

En syntaxe JSON stricte, les clés d’un objet doivent obligatoirement être…

La spécification RFC 8259 impose des guillemets doubles pour toutes les clés JSON.

Quel en-tête le client transmet-il pour indiquer le format attendu en réponse ?

Accept permet la négociation de contenu pour spécifier le format de réponse désiré.

Que contient la toute première ligne d’une requête HTTP standard ?

Exemple : GET /api/v1/users HTTP/1.1.

Lequel de ces types de données est invalide en JSON standard ?

JSON est un format de données pur ; il ne peut pas sérialiser de code exécutable ou de fonctions.

Dans une URL, où se situe la query string ?

La query string commence immédiatement après le caractère ? dans l’URL.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Oublier l’en-tête Content-Type: application/json lors de requêtes POST ou PUT.
  • Utiliser des guillemets simples (') dans un payload JSON (invalide selon la norme RFC).
  • Transmettre des données sensibles (mots de passe, tokens) en clair dans la query string d’une URL.
  • Confondre le rôle de Content-Type (données envoyées) et d’Accept (données souhaitées en retour).
  • Supposer que toutes les requêtes HTTP possèdent un corps (les requêtes GET n’en ont généralement pas).

8. Méthodologie de résolution

Analyser une requête HTTP pour une API REST
  1. Identifier la méthode : déterminer l’action demandée (GET, POST, PUT, DELETE).
  2. Examiner l’URI : vérifier la ressource ciblée et extraire les paramètres de chemin ou de requête.
  3. Contrôler les en-têtes : vérifier Content-Type, Accept et les jetons d’autorisation.
  4. Parser le corps : désérialiser la charge utile JSON reçue en structure de données interne.
  5. Formater la réponse : produire le corps JSON attendu et fixer les en-têtes appropriés.

9. Révision active

Résumé essentiel
  • Une API Web définit un contrat formel de communication client-serveur sur le réseau.
  • HTTP structure l’échange en requêtes (méthode, chemin, en-têtes, corps) et réponses (statut, en-têtes, corps).
  • L’en-tête Content-Type indique le format de la charge utile transmise (ex. application/json).
  • L’en-tête Accept permet la négociation du format de réponse souhaité par le client.
  • JSON est le standard de sérialisation léger, strict et universel des architectures REST.

Checklist de maîtrise

  • Je comprends l’architecture client-serveur d’une API Web.
  • Je sais décomposer les éléments constitutifs d’une requête HTTP.
  • Je connais la différence entre Content-Type et Accept.
  • Je sais formater un document JSON valide sans erreur de syntaxe.
  • Je sais extraire et lire les paramètres passés dans une query string.
