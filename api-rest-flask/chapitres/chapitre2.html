Chapitre 2 — Architecture REST & modélisation des ressources

Module 2 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Concevoir une API sans règles directrices produit des routes chaotiques (ex. /creerUtilisateur, /delete_item?id=5) difficiles à maintenir et à consommer. L’architecture REST standardise l’organisation autour de ressources identifiées par des URI stables et manipulées par les verbes natifs du protocole HTTP.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. assimiler les contraintes fondatrices du style architectural REST ;
  2. comprendre le principe fondamental du Stateless (sans état) ;
  3. modéliser des URI canoniques basées sur des noms pluriels et hiérarchiques ;
  4. associer chaque verbe HTTP (GET, POST, PUT, PATCH, DELETE) à son usage canonique ;
  5. distinguer les notions clés de sécurité (safe) et d’idempotence des opérations.

1. Les fondements de l’architecture REST

L’acronyme REST (Representational State Transfer) désigne un style architectural théorisé en 2000 par Roy Fielding dans sa thèse de doctorat. REST ne constitue pas un protocole ou une norme fermée, mais un ensemble de contraintes architecturales guidant la conception d’API distribuées.

Les 6 contraintes majeures de REST sont :

  1. Architecture Client-Serveur : séparation stricte de l’interface utilisateur et de la logique de persistance.
  2. Sans état (Stateless) : chaque requête du client doit contenir toutes les informations nécessaires à son traitement par le serveur. Aucune session de contexte client n’est conservée sur le serveur entre deux appels.
  3. Mise en cache (Cacheable) : les réponses doivent explicitement se déclarer cachables ou non pour réduire la latence.
  4. Interface uniforme : identification standardisée des ressources par URI, manipulation par représentations, messages auto-descriptifs et hypermédias (HATEOAS).
  5. Système en couches (Layered System) : le client ne sait pas s’il communique avec le serveur final, un reverse proxy ou un répartiteur de charge.
  6. Code à la demande (optionnel) : exécution de scripts côté client (ex. JavaScript).
Stateless : Pourquoi aucune session serveur ?

Le principe du Stateless garantit une excellente scalabilité horizontale : n’importe quel nœud d’un cluster de serveurs peut traiter n’importe quelle requête client, à condition que le client transmette son jeton d’authentification à chaque fois.

2. Conception d’URI canoniques pour les ressources

Dans une API RESTful, une ressource représente une entité métier du système (un utilisateur, un article, une facture). L’identification s’effectue à l’aide d’une URI (Uniform Resource Identifier).

Règles d’or de nommage des URI REST :

  • Utiliser des noms, jamais des verbes : /articles et non /getArticles.
  • Privilégier le pluriel pour les collections : /utilisateurs pour la collection, /utilisateurs/42 pour un élément.
  • Minuscules et tirets : privilégier le kebab-case (ex. /centres-interet) et bannir les majuscules ou underscores.
  • Hiérarchie logique d’imbrication : pour une sous-ressource dépendante : /auteurs/7/livres ou /commandes/12/lignes/3.
Anti-pattern : Le verbe dans l’URI

Évitez à tout prix les URI contenant des actions comme /api/ajouterUtilisateur ou /api/supprimerArticle?id=12. En REST, l’URI désigne la ressource (le quoi) et le verbe HTTP exprime l’action (le comment).

3. Verbes HTTP et matrice CRUD

L’interface uniforme REST mappe directement les opérations fondamentales de manipulation de données (CRUD) sur les méthodes standard du protocole HTTP :

GET/articlesLister la collection200 OK
GET/articles/42Consulter une ressource individuelle200 OK
POST/articlesCréer une nouvelle ressource201 Created
PUT/articles/42Remplacement complet d’une ressource200 OK
PATCH/articles/42Modification partielle d’attributs200 OK

4. Sécurité et Idempotence des opérations

Deux propriétés fondamentales régissent le comportement prédictible des méthodes HTTP :

  • Méthode sûre (Safe) : n’altère aucunement l’état du serveur (aucune écriture ou modification en base). Seuls GET, HEAD et OPTIONS sont réputés sûrs.
  • Méthode idempotente : exécuter la requête une seule fois ou 100 fois consécutives produit exactement le même état final sur le serveur. GET, PUT et DELETE sont idempotents. En revanche, POST n’est pas idempotent (répéter la requête crée 100 ressources dupliquées).
PUT vs PATCH : La nuance essentielle

PUT exige de fournir l’intégralité de la ressource : les champs omis sont souvent écrasés ou réinitialisés à leur valeur par défaut. PATCH ne transmet que les champs à modifier sans altérer les autres propriétés existantes.

Exercice 1 — Normalisation d’un chemin REST

Python Niveau 1 — Acquisition

Objectif : Formater et nettoyer un chemin d’accès REST en supprimant les doublons de slashes et les majuscules.

Une bonne pratique de conception REST consiste à utiliser des chemins en minuscules, sans slashes superflus, et sans slash final (sauf pour la racine /).

Lit une chaîne de chemin sur l’entrée standard. Nettoie la chaîne :
1. Convertis en minuscules.
2. Remplacer les séquences de slashes multiples par un slash unique.
3. Retirer le slash final s’il y en a un et que le chemin ne se réduit pas à /.
4. S’assurer que le chemin commence bien par un slash /.
Affiche le chemin normalisé.

Entrée du programme
/API//V1/Students//
Sortie attendue
/api/v1/students

Slashes multiples et majuscules nettoyés.

Deux indices, rédigés en mots
  1. Tu peux découper la chaîne avec .split("/") et filtrer les segments non vides avec [s for s in ... if s].
  2. Reconstitue le chemin avec "/" + "/".join(segments).

Exercice 3 — Structure d’URI : Collection vs Ressource

Python Niveau 3 — Raisonnement

Objectif : Identifier si une URI REST cible une collection ou une ressource spécifique.

Une URI REST bien conçue suit une hiérarchie alternant nom de collection (au pluriel) et identifiant unique. Si le dernier segment est un identifiant (numérique), l’URI cible une ressource individuelle ; si le dernier segment est un nom, l’URI cible une collection.

Lit une URI sur l’entrée standard (ex: /api/clients/42 ou /api/clients/42/commandes).
- Si le dernier segment est un entier (identifiant) : affiche Type: ressource | Cible: <nom_collection> | ID: <id>.
- Si le dernier segment est textuel : affiche Type: collection | Cible: <nom_collection>.
Ignore les préfixes éventuels comme /api ou /v1 pour trouver la collection ciblée.

Entrée du programme
/utilisateurs/42
Sortie attendue
Type: ressource | Cible: utilisateurs | ID: 42

Cible l’utilisateur 42.

Deux indices, rédigés en mots
  1. Découpe l’URI en segments non vides avec [s for s in uri.split("/") if s].
  2. Vérifie si le dernier segment est composé uniquement de chiffres avec segment.isdigit().

6. QCM — niveau examen

Qui a théorisé l’architecture REST en l’an 2000 ?

Roy Fielding a présenté les principes fondamentaux de REST dans sa thèse doctorale.

Que signifie la contrainte Stateless dans une API REST ?

Chaque requête doit être auto-suffisante et fournir toutes les informations nécessaires à son traitement.

Quelle URI respecte le mieux les conventions de nommage REST ?

Les URI REST utilisent des noms au pluriel et séparent l’identifiant par un slash.

Quel verbe HTTP est utilisé pour remplacer intégralement une ressource ?

PUT remplace l’intégralité de la ressource ciblée par la nouvelle représentation.

Une méthode HTTP est dite idempotente si…

L’idempotence garantit qu’une répétition d’appels identiques ne modifie pas l’état du serveur au-delà du premier.

Lequel de ces verbes HTTP n’est PAS idempotent ?

Exécuter plusieurs requêtes POST identiques entraîne des créations multiples successives.

Quelle méthode HTTP modifie partiellement certains attributs d’une ressource ?

PATCH est conçu spécifiquement pour les modifications différentielles ou partielles.

Pour lister les commandes passées par l’utilisateur 7, quelle URI est la plus RESTful ?

La hiérarchie /utilisateurs/7/commandes exprime élégamment la relation parent-enfant.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Insérer des verbes d’action dans l’URI (ex. /modifierArticle au lieu de PUT /articles/1).
  • Conserver des sessions utilisateur côté serveur (session cookie d’état) dans une API qui se veut RESTful.
  • Utiliser le verbe GET pour effectuer une mutation ou une suppression (non-respect de la sécurité HTTP).
  • Confondre PUT (remplacement intégral) et PATCH (mise à jour partielle d’attributs).
  • Employer des noms au singulier de manière incohérente (/client puis /articles).

8. Méthodologie de résolution

Modéliser une ressource et ses points d’accès REST
  1. Identifier les entités métier : repérer les concepts clés du domaine (utilisateurs, commandes, produits).
  2. Fixer l’URI de base : choisir un substantif au pluriel en minuscules (ex. /produits).
  3. Structurer les relations : concevoir les sous-ressources imbriquées pour les dépendances fortes.
  4. Mapper les verbes HTTP : associer GET, POST, PUT, PATCH et DELETE aux besoins de l’application.
  5. Valider l’idempotence : s’assurer que les méthodes sûres et idempotentes respectent leur contrat.

9. Révision active

Résumé essentiel
  • REST est un style architectural fondé sur le découplage client-serveur et l’absence d’état (Stateless).
  • Les URI identifient des ressources au moyen de substantifs au pluriel, sans verbes d’action.
  • Les verbes HTTP (GET, POST, PUT, PATCH, DELETE) expriment les opérations de manipulation.
  • Une opération sûre ne modifie pas le serveur ; une opération idempotente peut être rejouée sans effet cumulé.
  • PUT remplace la ressource en totalité, tandis que PATCH applique une mise à jour partielle.
