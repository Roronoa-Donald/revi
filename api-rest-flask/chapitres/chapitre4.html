Chapitre 4 — Codes d’état HTTP & réponses JSON

Module 4 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Renvoyer systématiquement un code 200 OK avec un message {"erreur": "introuvable"} est une mauvaise pratique courante qui induit en erreur les bibliothèques clientes (Axios, Fetch, cURL). Une API RESTful utilise les codes d’état HTTP natifs pour signaler sans ambiguïté le succès ou la nature de l’échec.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. maîtriser la signification des grandes familles de codes HTTP (2xx, 3xx, 4xx, 5xx) ;
  2. choisir le code de statut précis pour chaque scénario REST (200, 201, 204, 400, 404, 409) ;
  3. sérialiser des dictionnaires et listes avec jsonify() et comprendre ses optimisations ;
  4. construire des réponses Flask enrichies sous forme de tuples (body, status, headers) ;
  5. définir un schéma JSON cohérent pour les erreurs et la pagination de collections.

1. Les familles de codes de statut HTTP

Le protocole HTTP classe ses codes de réponse à trois chiffres en cinq catégories distinctes :

  • 1xx (Informationnel) : requête reçue, traitement en cours (ex. 100 Continue).
  • 2xx (Succès) : l’action a été reçue, comprise et acceptée avec succès.
  • 3xx (Redirection) : le client doit effectuer une action supplémentaire pour compléter la requête.
  • 4xx (Erreur du client) : la requête contient une syntaxe erronée ou ne peut pas être honorée (responsabilité du client).
  • 5xx (Erreur du serveur) : le serveur a rencontré une anomalie interne lors du traitement (responsabilité du backend).
À qui la faute ?

Une règle mémotechnique simple pour débugger : si le code commence par 4, c’est le client qui a envoyé une requête invalide, incomplète ou non autorisée. Si le code commence par 5, c’est le serveur qui a planté ou généré une exception non interceptée.

2. Les codes de statut indispensables en REST

Dans une API REST professionnelle, une dizaine de codes couvrent l’immense majorité des besoins :

3. Sérialisation avec jsonify et tuples de réponse Flask

Dans les versions récentes de Flask, retourner un dictionnaire Python (dict) ou une liste le convertit automatiquement en réponse JSON avec le code 200 par défaut.

Cependant, l’utilisation explicite de la fonction jsonify() reste recommandée :

  • Elle configure immédiatement l’en-tête Content-Type: application/json.
  • Elle gère proprement la sérialisation des listes d’objets racines.
from flask import jsonify

@app.route("/utilisateurs/<int:id>")
def obtenir_utilisateur(id):
    user = trouver_utilisateur(id)
    if not user:
        return jsonify({"erreur": "Utilisateur non trouvé"}), 404
    return jsonify(user), 200
Le tuple de réponse Flask

Une fonction vue Flask peut retourner un tuple contenant jusqu’à 3 éléments :

return reponse, code_statut, en_tetes_dict
# Exemple :
return jsonify(article), 201, {"Location": f"/articles/{article['id']}"}

4. Format d’erreur standardisé et pagination

Pour faciliter la tâche des développeurs frontend, une API doit renvoyer un format d’erreur prévisible :

{
  "code": 404,
  "error": "Not Found",
  "message": "La facture 82 n’existe pas dans votre compte."
}

De même, pour les collections volumineuses, l’enveloppe de pagination fournit les repères indispensables :

{
  "total": 150,
  "page": 2,
  "limit": 20,
  "data": [
    {"id": 21, "titre": "Article 21"},
    {"id": 22, "titre": "Article 22"}
  ]
}

201 Created est le statut standard pour signaler une création réussie.

204 No Content est couramment employé après une suppression (DELETE).

404 Not Found indique que la ressource demandée n’existe pas.

409 Conflict signale une violation de contrainte d’intégrité ou d’unicité.

Le 2e élément du tuple Flask définit le code d’état HTTP de la réponse.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Renvoyer un code 200 OK avec un corps contenant {"succes": false, "erreur": "..."}.
  • Renvoyer 200 OK au lieu de 201 Created lors d’une création par POST.
  • Renvoyer du texte brut au lieu de JSON pour les messages d’erreur (incohérence de format).
  • Confondre les codes 401 (non authentifié) et 403 (authentifié mais non autorisé).
  • Oublier d’inclure le code de statut dans le tuple Flask : return jsonify(err) produit un 200 par défaut.

8. Méthodologie de résolution

Construire une réponse REST conforme dans Flask
  1. Déterminer l’issue métier : succès complet, création, suppression ou anomalie.
  2. Sélectionner le code HTTP : 200, 201, 204, 400, 401, 403, 404, 409 ou 500.
  3. Structurer le payload : préparer le dictionnaire de données ou l’objet d’erreur standardisé.
  4. Sérialiser avec jsonify() : envelopper la charge utile pour garantir l’en-tête JSON.
  5. Former le tuple de retour : retourner return jsonify(payload), code_statut.

9. Révision active

Résumé essentiel
  • Les codes HTTP informent immédiatement le client sur le succès ou l’échec d’une opération.
  • Les codes 2xx attestent du succès (200 OK, 201 Created, 204 No Content).
  • Les codes 4xx indiquent une anomalie imputable au client (400, 401, 403, 404, 409).
  • Flask permet de renvoyer un tuple (payload, statut, en-têtes) pour configurer la réponse.
  • Standardiser le format des erreurs JSON et paginer les collections garantit une API professionnelle.

Checklist de maîtrise

  • Je connais la classification des statuts HTTP (2xx, 3xx, 4xx, 5xx).
  • Je sais quand employer 200, 201 et 204.
  • Je fais la distinction précise entre 401 Unauthorized et 403 Forbidden.
  • Je maîtrise l’utilisation de jsonify() et les tuples de retour Flask.
  • Je structure des réponses d’erreur JSON prévisibles et informatives.
