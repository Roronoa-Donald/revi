Examen blanc n°1 : Protocoles Web, Conception REST & Routage Flask

Sujet théorique et pratique : dialogue HTTP, modélisation de ressources et système de routage de Flask.

Exercice 1 /5 : Dialogue HTTP & En-têtes

Énoncé : Décrivez les quatre composantes d’une requête HTTP. Quelle est la différence fondamentale entre l’en-tête Content-Type et l’en-tête Accept ?

Voir le corrigé type
Une requête HTTP se compose de : (1) La ligne de requête (méthode, chemin cible, version du protocole) ; (2) Les en-têtes (métadonnées clé-valeur) ; (3) Une ligne vide séparatrice ; (4) Le corps (body) portant la charge utile. Content-Type indique le format des données envoyées dans le corps (ex. application/json), tandis que Accept indique le format attendu par le client en retour.
Exercice 2 /5 : Principes REST & Nommage d’URI

Énoncé : Rappelez les contraintes du principe Stateless. Donnez trois règles strictes de conception d’URI dans une architecture RESTful.

Voir le corrigé type
Le principe Stateless impose que chaque requête client contienne toutes les informations nécessaires à son traitement ; aucun état de session n’est conservé sur le serveur entre deux appels. Trois règles d’URI : (1) Utiliser des noms et non des verbes (/articles et non /getArticles) ; (2) Employer des pluriels pour les collections (/utilisateurs/42) ; (3) Respecter une hiérarchie logique pour les sous-ressources (/auteurs/7/livres).
Exercice 3 /5 : Sécurité & Idempotence

Énoncé : Définissez une méthode HTTP sûre (safe) et une méthode idempotente. Classez GET, POST, PUT et DELETE dans ces catégories.

Voir le corrigé type
Une méthode sûre ne modifie pas l’état du serveur (lecture seule). Une méthode idempotente produit le même résultat sur le serveur qu’elle soit exécutée une ou plusieurs fois. GET est sûre et idempotente. PUT et DELETE sont idempotents mais non sûrs. POST n’est ni sûr ni idempotent.
Exercice 4 /5 : Routage dynamique dans Flask

Énoncé : Comment déclare-t-on une route acceptant un entier positif dans l’URL avec Flask ? Que se passe-t-il si un client passe une valeur textuelle non numérique ?

Voir le corrigé type
On utilise le convertisseur typé : @app.route("/utilisateurs/<int:id>"). Si la valeur transmise n’est pas convertible en entier (ex. /utilisateurs/abc), Flask rejette immédiatement la requête avec une erreur 404 Not Found sans exécuter la fonction vue.

Examen blanc n°2 : Statuts HTTP, Validation défensive & Architecture

Sujet d’approfondissement : gestion d’erreurs unifiée, prévention des failles et modularité professionnelle.

Exercice 1 /5 : Codes d’état HTTP REST

Énoncé : Associez chaque situation au code d’état HTTP recommandé : (a) Création réussie d’un compte ; (b) Suppression d’un article sans contenu retourné ; (c) Corps JSON sans champ obligatoire ; (d) Jeton JWT absent ou expiré.

Voir le corrigé type
(a) Création réussie : 201 Created (avec en-tête Location). (b) Suppression sans contenu : 204 No Content. (c) Données requises manquantes : 400 Bad Request. (d) Jeton d’authentification absent : 401 Unauthorized.
Exercice 2 /5 : Validation & Mass Assignment

Énoncé : Qu’est-ce que la vulnérabilité de Mass Assignment ? Comment l’empêcher concrètement lors de la réception d’un dictionnaire JSON dans Flask ?

Voir le corrigé type
Le Mass Assignment survient lorsqu’un client injecte des attributs privilégiés (ex. is_admin: true) qui sont enregistrés en base sans contrôle. On s’en protège par une liste blanche (whitelisting) : champs_permis = {"nom", "email"} et on filtre le payload : data = {k: v for k, v in request.get_json().items() if k in champs_permis}.
Exercice 3 /5 : Gestion globale d’erreurs

Énoncé : À quoi sert le décorateur @app.errorhandler() ? Donnez un exemple d’implémentation pour garantir que les erreurs 404 renvoient du JSON.

Voir le corrigé type
@app.errorhandler(404) intercepte toutes les erreurs 404 de l’application pour unifier leur formatage :
@app.errorhandler(404) def introuvable(err): return jsonify({"code": 404, "error": "Not Found", "message": getattr(err, "description", "Introuvable")}), 404.
Exercice 4 /5 : Blueprints & Mise en production

Énoncé : Quel est l’intérêt des Blueprints dans Flask ? Pourquoi ne doit-on jamais exécuter app.run(debug=True) sur un serveur public de production ?

Voir le corrigé type
Les Blueprints découpent l’application en modules fonctionnels indépendants avec factorisation du préfixe d’URL (url_prefix). app.run(debug=True) est strictement interdit en production car le débogueur interactif de Werkzeug permet l’exécution arbitraire de code Python à distance ; on utilise un serveur WSGI dédié tel que Gunicorn.
