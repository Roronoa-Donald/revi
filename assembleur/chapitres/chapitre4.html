Chapitre 4 — Chaîne de Production Logicielle (Assembleur, ELF, Linker & Débogueur)

Module 4 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Un développeur tape la commande gcc -O2 main.c -o programme dans son terminal. En quelques millisecondes, le compilateur a prétraité les macros, généré du code assembleur intermédiaire, assemblé les mnémoniques en opcodes machine binaires dans un fichier objet main.o, puis l’éditeur de liens (ld) a résolu les symboles externes pour produire un exécutable binaire ELF. Que contiennent les sections .text, .data et .bss ? Pourquoi l’éditeur de liens émet-il l’erreur redoutée undefined reference ? Et pourquoi l’alignement mémoire sur 16 octets est-il obligatoire avant tout appel de fonction en x86_64 ?

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. décrire avec exactitude les 4 étapes séquentielles de la chaîne de compilation logicielle ;
  2. expliquer le concept et l’utilité de la compilation croisée (cross-compilation) pour les cibles embarquées ;
  3. détailler la structure interne et le rôle de chaque section d’un binaire ELF (.text, .rodata, .data, .bss) ;
  4. déclarer des données brutes en assembleur NASM avec les directives de taille adaptées (db, dw, dd, dq) ;
  5. calculer les contraintes d’alignement mémoire et le nombre d’octets de padding imposés par la directive ALIGN.

1. Les 4 étapes de la chaîne de compilation (Toolchain)

La transformation d’un code source de haut niveau en un programme binaire exécutable fait intervenir quatre outils logiciels spécialisés travaillant en pipeline :

ÉtapeOutil GNUEntrée → SortieRôle technique exact
1. Préprocesseurcpp.c / .h → .iSupprime les commentaires, remplace les macros (#define) et inclut textuellement les fichiers d’en-tête (#include).
2. Compilateurgcc (cc1).i → .sAnalyse syntaxique, optimisation et traduction du code en instructions assembleur textuelles propres à la cible.
3. Assembleuras / nasm.s → .oTraduit les mnémoniques textuels (MOV, ADD) en opcodes binaires machine et génère un fichier objet relocalisable.
4. Éditeur de liensld.o + .a → ELF / EXEFusionne les sections des fichiers objets, résout les adresses des symboles externes et intègre les bibliothèques système.
Qu’est-ce que la compilation croisée (Cross-Compilation) ?

La compilation croisée consiste à compiler un programme sur une machine hôte puissante (ex. un PC de développement x86_64 sous Linux) pour produire un fichier binaire destiné à être exécuté sur une machine cible d’architecture matérielle totalement différente (ex. une puce ARM Cortex, ou un microcontrôleur AVR ATmega328P). La toolchain utilise alors des outils préfixés : avr-gcc, avr-as, avr-ld et avr-objcopy.

2. Anatomie d’un exécutable ELF & ses sections mémoire

Sous Linux et les systèmes UNIX, le format binaire standard est ELF (Executable and Linkable Format). Le programme est découpé en plusieurs sections indépendantes ayant des droits d’accès matériels distincts (rwx) :

// Structure des 4 sections fondamentales d’un binaire ELF :

1. Section .text (Code exécutable, Droits: r-x) :
   - Contient la séquence des instructions machine lues par le processeur.
   - Mémoire en lecture seule et exécution (protégée contre l’écriture pour interdire l’auto-modification).

2. Section .rodata (Read-Only Data, Droits: r--) :
   - Constantes littérales du programme (chaînes de caractères de printf, tables de sinus, masques constants).

3. Section .data (Initialized Data, Droits: rw-) :
   - Variables globales et statiques explicitement initialisées à une valeur non nulle.
   - Présente physiquement dans le fichier binaire sur le disque.

4. Section .bss (Block Started by Symbol, Droits: rw-) :
   - Variables globales non initialisées (ou initialisées à 0).
   - N’occupe aucun octet sur le disque ! Le noyau Linux se contente d’allouer des pages de zéros en mémoire vive au démarrage.

3. Directives d’allocation NASM & Table des symboles

En assembleur NASM, la section .data alloue et initialise la mémoire à l’aide de directives explicites de largeur binaire :

DirectiveNom completTaille en octetsExemple d’utilisation
dbDefine Byte1 octet (8 bits)msg db "Hello", 0 (chaîne terminée par zéro)
dwDefine Word2 octets (16 bits)compteur dw 1000
ddDefine Double Word4 octets (32 bits)valeur dd 0x12345678
dqDefine Quad Word8 octets (64 bits)grand_nombre dq 1000000000
Le rôle de la table des symboles

Chaque étiquette (label) déclarée dans le code (ex. main: ou msg:) est enregistrée dans la table des symboles du fichier objet avec son nom, sa section d’appartenance, sa portée (locale ou global) et son offset relatif au début de la section.

4. Alignement mémoire & Directive ALIGN

Pour que le bus mémoire puisse lire une donnée en un seul cycle d’horloge, l’adresse de départ de la donnée doit idéalement être un multiple de sa taille :

// Directive ALIGN en assembleur NASM :
ALIGN 4    ; Insère des octets de bourrage (padding) jusqu’au prochain multiple de 4
ALIGN 16   ; Obligatoire en x86_64 ABI pour aligner la pile avant un CALL externe

// Formule du padding nécessaire pour aligner l’adresse A sur N octets :
reste = A % N
padding = (N - reste) % N
nouvelle_adresse = A + padding

Exercice 1 — Décodeur de directives de données NASM (db, dw, dd, dq)

Python Niveau 1 — Acquisition

Objectif : Convertir des directives d’allocation mémoire NASM en séquences d’octets bruts Little-Endian.

Dans la section .data d’un programme NASM, la taille des variables est définie par des directives :

  • db (define byte) : 1 octet (8 bits) ;
  • dw (define word) : 2 octets (16 bits, Little-Endian) ;
  • dd (define double word) : 4 octets (32 bits, Little-Endian) ;
  • dq (define quad word) : 8 octets (64 bits, Little-Endian).

Lit sur l’entrée standard DIRECTIVE;VALEURS où VALEURS est une liste d’entiers décimaux séparés par des virgules. Affiche la taille totale allouée et la séquence d’octets générée :
TAILLE=<nb_octets> OCTETS=<XX XX ...>.

Entrée du programme
dw;10,20
Sortie attendue
TAILLE=4 OCTETS=0A 00 14 00

Deux mots de 16 bits : 10 = 0x000A (0A 00) et 20 = 0x0014 (14 00) -> 4 octets au total.

Deux indices, rédigés en mots
  1. db -> 1 octet, dw -> 2 octets, dd -> 4 octets, dq -> 8 octets.
  2. Pour convertir un entier x en n octets Little-Endian : (x >> (8*i)) & 0xFF pour i de 0 à n-1.
  3. Concatène les octets de toutes les valeurs séparés par un espace.

Exercice 2 — Résolution d’adresses virtuelles de sections ELF

Python Niveau 1 — Acquisition

Objectif : Calculer l’adresse virtuelle absolue d’un symbole dans un exécutable ELF.

Lors de l’étape d’édition de liens (linkage), l’éditeur de liens fusionne les sections des fichiers objets et leur attribue une adresse virtuelle (Virtual Address, VA) en mémoire.

Lit sur l’entrée standard SECTION;BASE_HEX;OFFSET_HEX où :

  • SECTION est le nom de la section (ex. .text, .data, .rodata) ;
  • BASE_HEX est l’adresse virtuelle de base de la section (ex. 0x00401000) ;
  • OFFSET_HEX est le déplacement du symbole dans la section (ex. 0x00000050).

Affiche :
SECTION=<NOM> VA=0x<8 chiffres HEX majuscules> DEC=<valeur>.

Entrée du programme
.text;0x00401000;0x00000050
Sortie attendue
SECTION=.text VA=0x00401050 DEC=4198480

0x00401000 + 0x50 = 0x00401050 dans l’espace mémoire du processus.

Deux indices, rédigés en mots
  1. Convertis BASE_HEX et OFFSET_HEX en entiers avec int(s, 16).
  2. L’adresse virtuelle finale vaut base + offset.
  3. Formate avec f"SECTION={sec} VA=0x{va:08X} DEC={va}".

Exercice 3 — Alignement mémoire & calcul de Padding (Directive ALIGN)

Python Niveau 2 — Application

Objectif : Calculer le nombre d’octets de bourrage (padding) nécessaires pour aligner une variable sur une frontière N octets.

Pour optimiser les accès au bus mémoire et éviter les pénalités de cycle CPU, les processeurs requièrent souvent que les données soient alignées sur des multiples de 2, 4, 8 ou 16 octets.

Lit sur l’entrée standard ADRESSE_HEX;N (où N vaut 2, 4, 8 ou 16). Affiche le nombre d’octets de bourrage ajoutés et la nouvelle adresse alignée :
PADDING=<nb_octets> ALIGNEE=0x<HEX>.

Entrée du programme
0x1003;4
Sortie attendue
PADDING=1 ALIGNEE=0x1004

0x1003 (4099) modulo 4 donne 3. On ajoute 1 octet pour atteindre 4100 (0x1004).

Deux indices, rédigés en mots
  1. Si adr % n == 0, aucun padding n’est requis (padding = 0).
  2. Sinon, padding = n - (adr % n), et la nouvelle adresse vaut adr + padding.
  3. Formate l’adresse avec au moins 4 chiffres : f"0x{alignee:04X}".

6. QCM — niveau examen

Quel outil de la chaîne de compilation transforme le code assembleur textuel (.s) en fichier objet binaire (.o) ?

L’assembleur traduit les mnémoniques (comme MOV, ADD) en opcodes binaires machine.

Pourquoi la section .bss d’un fichier ELF n’occupe-t-elle presque aucun espace sur le disque ?

La section .bss n’enregistre que la taille totale à allouer : les pages de zéros sont fournies à la volée par le système d’exploitation.

Quelle directive NASM permet de réserver et d’initialiser un entier de 64 bits (8 octets) ?

dq = Define Quad Word = 64 bits = 8 octets.

Quelle section d’un binaire ELF contient le code exécutable du programme protégé en lecture et exécution (r-x) ?

La section .text héberge le code machine exécuté par le processeur.

Qu’est-ce qu’une erreur d’édition de liens « undefined reference to main » signifie exactement ?

Cette erreur survient lors de la phase de linkage : le symbole du point d’entrée principal n’a pas été résolu.

À quelle adresse se retrouve une variable située à l’adresse 0x1003 si l’on applique la directive ALIGN 4 ?

0x1003 = 4099. Le multiple de 4 supérieur le plus proche est 4100 = 0x1004 (padding de 1 octet).

Dans quelle section mémoire résident les chaînes de caractères littérales passées à printf("Hello ") ?

Les constantes non modifiables sont logées dans la section .rodata (Read-Only Data).

Quel outil de la toolchain AVR permet d’extraire le code machine binaire d’un fichier ELF pour en faire un fichier .hex flashable ?

avr-objcopy extrait les sections exécutables de l’ELF pour produire le format Intel HEX accepté par les programmateurs de Flash.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Confondre la section .data (variables initialisées occupant de la place sur disque) et .bss (variables nulles allouées en RAM).
  • Oublier le mot-clé global devant une étiquette en NASM, rendant le symbole invisible pour l’éditeur de liens externe.
  • Mélanger les directives de taille : déclarer dw pour un entier 32 bits, ce qui tronque la valeur à 16 bits.
  • Négliger l’alignement de la pile sur 16 octets avant un appel de fonction système en x86_64, provoquant un crash direct.
  • Confondre avr-gcc (le compilateur croisé) et avrdude (l’outil de flashage qui communique physiquement avec la puce via USB).

8. Méthodologie de résolution

Protocole en 4 étapes pour assembler et lier un programme NASM
  1. Écrire le code source assembleur en déclarant explicitement la section .data, la section .text et global _start.
  2. Assembler le code avec NASM en spécifiant le format cible : nasm -f elf64 prog.asm -o prog.o.
  3. Lier les fichiers objets avec ld pour résoudre les adresses virtuelles : ld prog.o -o prog.
  4. Inspecter les sections du binaire généré à l’aide des commandes GNU size prog et objdump -d prog.

9. Révision active

Résumé essentiel
  • La toolchain transforme le code en 4 étapes : préprocesseur (.i), compilateur (.s), assembleur (.o) et linker (ELF).
  • La cross-compilation produit du binaire pour une cible d’architecture différente de la machine hôte.
  • Un binaire ELF isole .text (instructions r-x), .rodata (constantes r--), .data (initialisé rw-) et .bss (non initialisé rw-).
  • Les directives NASM définissent la taille mémoire : db (1o), dw (2o), dd (4o) et dq (8o).
  • La directive ALIGN insère du bourrage pour aligner les données et structures sur des frontières de bus optimales.
