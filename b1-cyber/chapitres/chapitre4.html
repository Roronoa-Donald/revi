Chapitre 4 — Sécurité des systèmes et des applications

Module 4 ≈ 2 h de travail Réservé B1 et plus
Mise en situation

Un serveur web a 46 jours de retard de correctif, un compte applicatif a des droits de côté administrateur, et une page accepte n'importe quelle saisie. Trois failles différentes, une même discipline : permissions justes, correctifs réguliers, entrées filtrées.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. gérer utilisateurs, groupes et permissions d'un système d'exploitation ;
  2. distinguer DAC, MAC, RBAC, ABAC et ACL ;
  3. organiser un cycle de correctifs et justifier sa criticité ;
  4. appliquer les réflexes du développement sécurisé contre injection et XSS.

1. Utilisateurs, groupes, permissions

Un utilisateur est une entité (humaine ou logicielle) identifiée par un nom unique et un identifiant numérique UID ; les groupes (GID) rapprochent des utilisateurs aux besoins similaires ; les permissions — lecture, écriture, exécution — définissent ce que chacun peut faire d'une ressource.

Le modèle POSIX (Linux/Unix) attribue à chaque fichier un propriétaire et un groupe, avec des permissions posées séparément pour le propriétaire, le groupe et les autres. Le cours d'administration Linux en détaille les calculs ; ici, il faut retenir le principe : le droit minimal par ressource, jamais le droit large par commodité.

Les cas d'usage à citer
  • Fichiers sensibles : accès limité aux seuls utilisateurs autorisés (paie, RH).
  • Administration : droits administratifs réservés aux utilisateurs qualifiés.
  • Serveur web multi-utilisateurs : permissions distinctes développeurs, testeurs, administrateurs.
  • Cloud : politiques d'accès granulaires (AWS IAM) plutôt que comptes partagés.

2. Modèles de contrôle d'accès

Cinq modèles structurent les décisions d'accès, et l'examen adore les confondre :

ModèleQui décideExemple
DAC (Discrétionnaire)le propriétaire de la ressourcepermissions POSIX classiques
MAC (Obligatoire)une politique centrale imposée par le systèmeSELinux, AppArmor
RBAC (par rôles)le rôle attribué à l'utilisateurrôle « technicien paie » dans une PME
ABAC (par attributs)des critères dynamiques (heure, lieu, appareil)accès aux heures de bureau seulement
ACL (listes d'accès)une liste explicite d'entrées par ressourceNTFS sous Windows
Mnémotechnique — « propriétaire, politique, rôle, attribut, liste »

DAC = le propriétaire décide ; MAC = la politique impose ; RBAC = le rôle porte les droits ; ABAC = l'attribut (heure, lieu) tranche ; ACL = la liste explicite d'entrées. Cinq mots-clés, cinq modèles, aucune confusion possible.

3. La gestion des correctifs

Un correctif (patch) est une mise à jour publiée par le fournisseur pour corriger une vulnérabilité, un bug ou ajouter une fonction. Ignorer les correctifs expose aux attaques connues : Heartbleed (OpenSSL), Shellshock (Bash), EternalBlue (SMB Windows, moteur de WannaCry) ont tous été corrigés avant d'être massivement exploités — sur les machines non patchées.

Le cycle professionnel : inventorier les produits, suivre les bulletins du fournisseur, qualifier la criticité (CVSS, exposition), tester en environnement de recette, déployer par vagues, vérifier la conformité. Le délai de correction est un indicateur de sécurité à part entière : au-delà de 90 jours sans correctif de sécurité, la situation est critique.

Piège — « on patchera à la prochaine maintenance »

WannaCry a frappé en mai 2017 un correctif publié en mars : 60 jours de retard ont suffi. Le correctif de sécurité ne suit pas le calendrier de maintenance, il le devance — et la conformité RGPD/PCI DSS exige des systèmes tenus à jour.

4. Développement sécurisé et bases de données

Le secure coding part d'un principe : toute entrée est suspecte tant qu'elle n'est pas validée. Les deux attaques de référence :

  • Injection SQL : la saisie Robert');-- se glisse dans une requête construite par concaténation et en détourne le sens. Parade : requêtes paramétrées, et validation des entrées (apostrophes, tirets doubles, chevrons suspects).
  • XSS (cross-site scripting) : un script injecté dans une page s'exécute dans le navigateur d'un autre visiteur. Parade : échapper toute sortie affichée, filtrer les chevrons < et >.

Côté bases de données : contrôle d'accès par comptes nominatifs et privilèges minimaux, chiffrement des données sensibles au repos, sauvegardes testées. Côté tests : le pentesting cherche les failles avant l'attaquant, l'audit vérifie la conformité — le référentiel OWASP tient la liste des risques applicatifs les plus courants.

Mnémotechnique — « valider à l'entrée, échapper à la sortie »

Deux portes pour la même maison : on valide ce qui entre (longueur, format, caractères interdits) et on échappe ce qui sort vers une page (les chevrons deviennent &lt;). Une seule des deux portes oubliée suffit à l'attaque.

5. Exercices de code

Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

En cas d’erreur, le bouton Expliquer mon erreur interroge le tuteur : il décrit ce qui s’est passé et par où chercher, sans jamais écrire de code à votre place — c’est le principe de l’exercice.

Exercice 1 — Guichet des correctifs

Bash Niveau 1 — Acquisition

Objectif : Classer les produits selon l’âge de leur dernier correctif de sécurité.

Le script lit n lignes « produit jours » (jours = nombre de jours depuis le dernier correctif de sécurité). Verdict par ligne produit : statut : dans les temps (45 jours ou moins), hors delai (46 à 90), critique (plus de 90).

Entrée du programme
6
serveur_web 46
base_donnees 12
poste_compta 46
borne_acces 90
messagerie 30
cluster_bdd 3
Sortie attendue
serveur_web : hors delai
base_donnees : dans les temps
poste_compta : hors delai
borne_acces : hors delai
messagerie : dans les temps
cluster_bdd : dans les temps
Deux indices, rédigés en mots
  1. Deux comparaisons numériques suffisent : -le 45 puis -le 90, le reste tombe dans le else.
  2. Le statut est un simple texte : pas besoin de case, un if/elif/else sur $jours suffit.

Exercice 2 — Filtre d’entrées

Bash Niveau 2 — Application

Objectif : Coder le premier réflexe du développement sécurisé : refuser les payloads suspects.

Le script lit n charges utiles (sans espace). Une charge est refusée si elle contient une apostrophe (injection SQL), un chevron < ou > (XSS) ou un double tiret -- (commentaire SQL) : le script affiche alors charge : refuse, sinon charge : accepte. Enfin rapport : a acceptes, b refuses.

Entrée du programme
6
admin'--
<script>alert(1)</script>
Robert');--
alert(1)
Pomme2026
O'Brien
Sortie attendue
admin'-- : refuse
<script>alert(1)</script> : refuse
Robert');-- : refuse
alert(1) : accepte
Pomme2026 : accepte
O'Brien : refuse
rapport : 2 acceptes, 4 refuses
Deux indices, rédigés en mots
  1. Un case sur « $charge » avec des motifs du type *"'"* ou *"--"* sait détecter une sous-chaîne.
  2. Compte acceptés et refusés dans les deux branches du if, et affiche le rapport après la boucle.

Exercice 3 — ACL du serveur de fichiers

Bash Niveau 3 — Raisonnement

Objectif : Simuler une liste de contrôle d’accès : ajouter, retirer, refuser le retrait d’une entrée absente.

Le script gère une ACL vide au départ et lit n lignes « action fichier » : add fichier l’ajoute et affiche add fichier : ok ; remove fichier la retire si présente (remove fichier : ok) ou échoue (remove fichier : introuvable). Enfin bilan : K éléments avec K le nombre d’entrées distinctes restantes — ajouter deux fois le même fichier ne le compte qu’une fois, et un add sur un nom présent est refusé.

Entrée du programme
6
add rapports
add photo_a.png
add rapports
remove photo_a.png
add photo_a.png
remove factures
Sortie attendue
add rapports : ok
add photo_a.png : ok
add rapports : refuse
remove photo_a.png : ok
add photo_a.png : ok
remove factures : introuvable
bilan : 2 éléments
Deux indices, rédigés en mots
  1. Pour savoir si le fichier est présent, balaie le tableau avec ${#noms[@]} et compare chaque case.
  2. Le retrait se fait en reconstruisant le tableau sans la valeur visée, puis noms=("${liste[@]}").

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Confondre DAC et MAC : le propriétaire décide (DAC) n'a rien à voir avec la politique imposée (MAC).
  • Donner les droits admin « pour dépanner » : le moindre privilège n'a pas d'exception durable.
  • Reporter les correctifs de sécurité : 60 jours ont suffi à WannaCry.
  • Construire des requêtes par concaténation : paramétré ou exposé, pas d'entre-deux.
  • Valider l'entrée mais oublier la sortie : la XSS passe par l'affichage non échappé.

8. Méthodologie de résolution

Durcir un système en cinq gestes
  1. Inventorier les comptes et ressources, supprimer les comptes dormants.
  2. Poser les permissions au droit minimal : propriétaire, groupe, autres — puis ACL si besoin.
  3. Choisir le modèle d'accès adapté : RBAC pour l'organisation, MAC pour le sensible.
  4. Planifier les correctifs : inventaire, qualification, test, déploiement par vagues, vérification.
  5. Blind er le code : validation des entrées, requêtes paramétrées, échappement des sorties, OWASP en check-list.
