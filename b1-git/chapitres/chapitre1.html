Chapitre 1 — Créer un dépôt : init, config, status

Module 1 ≈ 2 h de travail Accès libre
Mise en situation

Tu démarres le projet Python gestion_taches du TP : quatre fichiers, un dossier. Sans Git, chaque erreur se paie en copie manuelle « version_finale_v2 ». Avec Git, chaque état du projet s'archive proprement. Ce chapitre installe le réflexe du TP1 : init, config, status — dans cet ordre, toujours.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. expliquer ce qu'est un système de gestion de versions décentralisé ;
  2. créer un dépôt local avec git init et décrire le rôle du dossier .git ;
  3. configurer son identité avec git config (globale ou locale) ;
  4. lire la sortie de git status et citer les trois espaces de Git.

1. Pourquoi versionner

Git est le système de gestion de version décentralisé open source qui facilite les activités GitHub sur votre ordinateur. Décentralisé signifie que chaque machine possède tout l'historique : on peut commité, revenir en arrière, brancher, sans réseau. Le réseau ne sert qu'à la synchronisation entre dépôts.

Les bénéfices concrets du TP : revenir à n'importe quelle version d'un fichier, savoir qui a changé quoi et quand, expérimenter sur une branche sans risquer la version qui marche, collaborer à plusieurs sans s'écraser les fichiers.

Mnémotechnique — « tout l'historique dans la poche »

Un dépôt Git complet vit dans un seul dossier .git : cloner un projet, c'est transporter son passé entier. C'est pourquoi un commit accidentel se rattrape toujours en local — tant qu'il n'est pas poussé.

2. git init : naître au versionnage

Créer un dépôt local tient en trois lignes, exactement les premières du TP1 :

mkdir gestion_taches
cd gestion_taches
git init

La commande git init crée un sous-dossier .git qui contient le dépôt local : tout l'historique, les branches, la configuration propre au projet. Supprimer .git revient à désamorcer le versionnage — les fichiers, eux, restent. On peut aussi créer un dépôt à partir d'un projet existant avec git init nom-du-projet.

L'autre naissance possible : git clone url télécharge un projet et tout son historique de versions, et crée automatiquement le lien vers le dépôt distant.

Deux commandes de création à ne pas confondre

git init part du vide (ou d'un dossier existant) et crée un dépôt local ; git clone part d'un dépôt distant et reconstruit tout : dossier, historique, lien origin. Cloneer, c'est hériter ; initier, c'est fonder.

3. Configurer son identité

Chaque commit porte la signature de son auteur. Sans configuration, Git peut refuser de commiter ou utiliser une identité incorrecte — l'erreur classique du débutant que le TP1 signale en gras. Deux niveaux de configuration :

git config --global user.name "Votre Nom"
git config --global user.email "votre@email.com"

# ou, projet par projet (sans --global) :
git config user.name "Votre Nom"
git config user.email "votre@email.com"

# vérification :
git config --list

La configuration globale vaut pour tous les dépôts de la machine (recommandée en poste personnel) ; la locale ne vaut que pour le dépôt courant et écrase la globale — utile quand un projet professionnel exige une adresse différente.

Piège — le commit sans identité

Premier commit sans user.name ni user.email : refus. Git n'invente pas d'auteur. L'exercice « identité et commits refusés » de l'atelier reproduit ce refus et apprend à le lire avant de chercher ailleurs.

4. git status : les trois espaces

La copie de travail distingue trois espaces : la copie de travail contient les fichiers créés et modifiés par le développeur ; l'index est une zone de transit stockant les fichiers qui seront poussés vers le dépôt ; le dépôt local garde l'historique des versions, repéré par sa tête nommée HEAD.

copie de travail  ──git add──→     index      ──git commit──→   dépôt local (HEAD)
                        ←──git reset HEAD──                    ←──git checkout──

La commande git status liste tous les nouveaux fichiers et les fichiers modifiés à commiter : c'est l'état des lieux permanent. « Untracked » (non suivi) pour un fichier jamais ajouté, « modified » pour un suivi qui a changé depuis l'index, « staged » (indexé) pour un prêt à commiter.

Mnémotechnique — « la table, le plateau, l'armoire »

La table (copie de travail) accueille tout ce qu'on bricole ; le plateau (index) n'embarque que ce qu'on a posé exprès ; l'armoire (dépôt) archive pour de bon. add pose sur le plateau, commit range dans l'armoire, reset repose sur la table.

5. Exercices de code

Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

Exercice 1 — Journal du dépôt

Bash Niveau 1 — Acquisition

Objectif : Rejouer la séquence git init / config / status d’un TP et rendre compte de l’état du dépôt.

Le script lit n opérations : init nom (crée le dépôt et affiche dépôt nom créé), config cle valeur (enregistre la configuration), status. À chaque status il affiche deux lignes : dépôt : NOM (ou dépôt : aucun si pas encore d’init) et config : ok si user.name ET user.email sont posés, config : manquant sinon.

Entrée du programme
4
init gestion_taches
config user.name Alice
status
config user.email a@x.fr
Sortie attendue
dépôt gestion_taches créé
dépôt : gestion_taches
config : manquant
Deux indices, rédigés en mots
  1. Couper l’opération et son argument : read -r op reste lit le premier mot puis tout le reste de la ligne.
  2. Deux drapeaux suffisent pour la config : un pour user.name, un pour user.email.

Exercice 2 — Identité et commits refusés

Bash Niveau 1 — Acquisition

Objectif : Simuler le refus de commit sans identité : le premier piège du TP1.

Le script lit n opérations : config user.name X, config user.email X, ou commit msg. Un commit est accepté seulement si user.name ET user.email sont posés : il affiche alors [main SHA] msg avec SHA le numéro du commit sur quatre chiffres (0001, 0002…). Sinon il affiche erreur : identité manquante.

Entrée du programme
4
config user.name Alice
config user.email a@x.fr
commit init
commit second
Sortie attendue
[main 0001] init
[main 0002] second
Deux indices, rédigés en mots
  1. Un compteur de commits acceptés, initialisé avant la boucle, sert de numéro.
  2. Le formatage sur quatre chiffres : printf "%04d" $numero.

Exercice 3 — git status classé

Bash Niveau 2 — Application

Objectif : Classer les fichiers en non suivis, modifiés ou indexés, comme la sortie de git status.

Le script lit n opérations : cree fichier (fichier non suivi), modifie fichier (valide pour un fichier créé ou indexé ; ignoré sinon), add fichier, ou status. Le status affiche trois lignes : non suivis : K, modifies : K, indexes : K — K étant le nombre de fichiers de chaque catégorie. Un modifie sur un fichier non suivi ou inconnu est ignoré. Un add enlève le fichier des autres catégories et le compte une seule fois.

Entrée du programme
6
cree main.py
cree README.md
add main.py
modifie main.py
status
add README.md
Sortie attendue
non suivis : 1
modifies : 1
indexes : 0

main.py indexé puis modifié repasse en « modifies » ; README.md reste non suivi au status.

Deux indices, rédigés en mots
  1. Trois comptes et trois règles de passage : cree → non suivi, modifie → modifié, add → indexé.
  2. add depuis une autre catégorie doit décrémenter l’ancienne catégorie, sinon les comptes doublent.

6. QCM — niveau examen

Que crée exactement git init ?

git init crée le sous-dossier .git qui abrite tout le dépôt local.

Sans user.name ni user.email configurés, un commit…

C'est l'erreur classique du débutant signalée par le TP1 : configurer avant de commiter.

La configuration --global s'applique…

--global vaut pour tous les dépôts locaux ; sans elle, la configuration ne vaut que pour le dépôt courant.

Quels sont les trois espaces de Git ?

Copie de travail, index (zone de transit) et dépôt local (historique, tête HEAD).

Quelle commande fait un état des lieux permanent ?

git status liste nouveaux fichiers et modifications à commiter.

Un fichier « untracked » est…

Non suivi : présent dans la copie de travail mais jamais passé par git add.

git clone fait quoi, de plus que copier des fichiers ?

Le clone reconstruit l'historique complet et le lien vers le dépôt distant.

Quelle commande vérifie la configuration posée ?

git config --list liste toutes les valeurs de configuration actives.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Committer avant de configurer : refus ou identité fausse — le premier réflexe du TP1 est git config.
  • Confondre init et clone : init fonde, clone hérite d'un historique existant.
  • Supprimer .git pour « nettoyer » : c'est effacer tout l'historique.
  • Croire que status archive : status ne déplace rien, il observe.
  • Confondre les trois espaces : modifier n'est pas indexer, indexer n'est pas commiter.

8. Méthodologie de résolution

Démarrer un dépôt sans faux pas
  1. Créer le dossier et y entrer : mkdir puis cd, comme au TP1.
  2. Initialiser : git init — et vérifier la présence de .git.
  3. Configurer l'identité : user.name et user.email, globale ou locale.
  4. Vérifier : git config --list puis git status.
  5. Se représenter les trois espaces avant chaque déplacement de fichier.

9. Révision active

Résumé essentiel
  • Git est un gestionnaire de versions décentralisé : chaque machine a tout l'historique.
  • git init crée le sous-dossier .git ; git clone reconstruit dépôt et lien origin.
  • user.name et user.email s'imposent avant tout commit (--global pour la machine, local pour le projet).
  • Trois espaces : copie de travail, index, dépôt local (HEAD) ; status les observe sans rien déplacer.
  • add transite vers l'index, commit archive, reset renvoie vers la copie.

Checklist de maîtrise

  • Je décris ce que crée git init et ce que contient .git.
  • Je configure mon identité globale et je la vérifie.
  • Je classe un fichier dans l'un des trois espaces d'après la sortie de git status.
  • Je distingue init et clone avec un cas d'usage chacun.
