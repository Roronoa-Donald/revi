Chapitre 2 — Index et commits : add, reset, commit

Module 2 ≈ 2 h 30 de travail Réservé B1 et plus
Mise en situation

Le projet avance : main.py a changé, utils.py est nouveau, un cache __pycache__ pollue le dossier. Tout n'a pas vocation à partir dans l'historique. Ce chapitre apprend à sélectionner exactement ce qu'on archive — et à écrire des messages de commit qui se relisent.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. ajouter au sélectif avec git add et connaître ses options (-A, ., -u) ;
  2. exclure du suivi avec .gitignore et comprendre sa limite ;
  3. retirer un fichier de l'index avec git reset HEAD et git rm --cached ;
  4. écrire des messages de commit nets et comprendre l'option --amend.

1. git add : sélectionner

git add dépose les fichiers dans l'index. Trois façons de cibler :

git add /chemin/vers/fichier.ext   un fichier précis
git add /chemin/vers/dossier      tout un dossier
git add .                         le dossier courant

Les options sélectionnent selon l'état des fichiers :

OptionNouveauxModifiésDétruits
git add -Aouiouioui
git add .ouiouioui
git add -unonouioui

Règle d'or du vade-mecum : git add ajoute les fichiers tels qu'ils sont au moment de la commande. Une modification ultérieure ne sera pas prise dans l'index sans un nouveau add. En cas de doute, un git status fait l'état des lieux.

Mnémotechnique — « -u = déjà suivis seulement »

L'option -u (update) ne voit que ce que Git connaît déjà : ni nouveaux fichiers, ni dossiers entiers débarqués. Pratique pour indexer proprement des modifications sans ramasser les fichiers de travail en cours.

2. Exclure : .gitignore et sa limite

Le fichier .gitignore contient la liste des fichiers ou dossiers à ne pas inclure lors des git add. La syntaxe utilise des motifs standards :

fichier     # exclure un fichier exact
dossier/    # exclure un dossier
*.pyc       # exclure tous les fichiers finissant par .pyc
*~          # exclure tous les fichiers se terminant par ~

Le TP1 ajoute un .gitignore Python : __pycache__/, *.pyc, venv/. Et une limite essentielle : si un fichier est déjà suivi, l'ajouter au .gitignore ne le retire pas du suivi. La solution est git rm --cached fichier : le fichier sort de l'index et de la liste des suivis, mais reste physiquement sur le disque.

Piège — le .gitignore rétrospectif

Un fichier déjà commité ne disparaît pas de l'historique parce qu'on l'a écrit dans .gitignore. Il faut d'abord git rm --cached (puis commiter) : le .gitignore ne s'applique qu'aux fichiers pas encore suivis. L'exercice « gitignore » de l'atelier fait tester ce filtre sur des adds réels.

Trois rm à distinguer

git rm fichier supprime de la copie de travail ET de l'index ; git rm --cached fichier de l'index seulement (le fichier reste sur disque et devient non suivi) ; /bin/rm fichier de la copie de travail seulement. Et git mv ancien nouveau renomme en préparant le changement pour le commit.

3. Retirer de l'index : reset HEAD

git reset HEAD est l'inverse de git add : il vide l'index. Pour un seul fichier : git reset HEAD /chemin/vers/fichier.ext. Ainsi, pour indexer tout un dossier sauf un fichier :

git add /chemin/vers/dossier
git reset /chemin/vers/dossier/fichier.ext

Différence avec rm --cached : après un reset, le fichier reste suivi — simplement, ses dernières modifications repartent dans la copie de travail. Après un rm --cached, il n'est plus suivi du tout.

4. Committer et renommer l'archive

git commit -m "message" déplace les fichiers de l'index vers le dépôt : une nouvelle ligne dans l'historique, indexée par un SHA-1 et décrite par le message. Le commit archive l'état de l'index, pas la copie de travail.

git log montre l'historique des archivages, avec beaucoup d'options d'affichage. Et pour corriger le dernier commit — changer le message, ou ajouter/retirer des fichiers oubliés :

git commit --amend -m "Mon nouveau message"

Amend crée un nouveau SHA-1 : à ne faire que si le commit n'a pas encore été poussé, sinon les autres collaborateurs subissent le changement d'identifiant.

Piège — le message qui ne raconte rien

« modifications », « fix », « mise à jour » : un message sans verbe ni objet ne sert qu'à polluer git log. La convention de l'atelier : commence par une majuscule, 50 caractères au plus, pas de point final — « Ajout du fichier gitignore pour les caches ».

6. QCM — niveau examen

git add . et git add -A ont en commun de…

Les deux couvrent les trois états ; -u, lui, ignore les nouveaux fichiers.

Que fait git add -u ?

-u (update) ne voit que les fichiers déjà suivis : modifiés et détruits.

Un fichier déjà suivi est ajouté au .gitignore : que se passe-t-il ?

Le .gitignore ne s'applique qu'aux fichiers pas encore suivis.

Que fait git rm --cached fichier ?

--cached sort de l'index et du suivi sans détruire physiquement le fichier.

git reset HEAD fichier fait quoi ?

reset HEAD est l'inverse de git add : le fichier reste suivi.

Que contient un commit ?

Le commit archive ce que l'index contient au moment de la commande.

Quand peut-on commit --amend sans risque ?

Amend change le SHA-1 : les autres collaborateurs subiraient le déplacement d'historique.

Après un commit, l'index est…

Le commit a transféré tout l'index vers le dépôt : l'index se vide.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Add oublié après modification : le commit n'embarque que l'état indexé au moment du add.
  • -u attendu pour les nouveaux fichiers : -u ignore tout ce qui n'est pas déjà suivi.
  • .gitignore rétrospectif : sans git rm --cached, le fichier suivi reste suivi.
  • rm --cached et rm confondus : l'un garde le fichier sur disque, l'autre le détruit.
  • Amend après push : le SHA change, l'historique partagé se casse.

8. Méthodologie de résolution

Composer un commit propre
  1. Faire l'état des lieux : git status avant toute sélection.
  2. Sélectionner précisément : add fichier par fichier, ou add -u pour les suivis.
  3. Filtrer le bruit : .gitignore pour les caches, venv, fichiers temporaires.
  4. Vérifier l'index : git status — seul ce qui est indexé partira.
  5. Committer avec un message utile : majuscule, concis, sans point final.

9. Révision active

Résumé essentiel
  • git add dépose dans l'index : fichier, dossier, . (tout) ; -A prend tout, -u seulement les suivis.
  • L'index reflète l'état au moment du add : toute modification ultérieure demande un nouvel add.
  • .gitignore filtre les adds des fichiers non suivis ; pour un suivi, git rm --cached d'abord.
  • reset HEAD renvoie les modifications de l'index vers la copie de travail, sans dé-suivre.
  • Le commit archive l'index avec un SHA-1 ; amend le réécrit — avant tout push.

Checklist de maîtrise

  • Je choisis la bonne option de add selon ce que je veux indexer.
  • J'écris un .gitignore correct pour un projet Python.
  • Je retire proprement un fichier de l'index (reset) ou du suivi (rm --cached).
  • Je formule des messages de commit lisibles et je sais quand utiliser amend.
