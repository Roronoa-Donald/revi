Chapitre 3 — Historique et annulations : log, reset, revert

Module 3 ≈ 2 h 30 de travail Réservé B1 et plus
Mise en situation

Un commit part trop tôt, une modification casse tout, un message est faux. Git sait revenir en arrière — mais chaque méthode laisse une trace différente. Savoir choisir entre reset et revert, entre soft, mixed et hard, c'est ce qui distingue un utilisateur d'un administrateur de dépôt.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. lire l'historique avec git log et ses formats d'affichage ;
  2. distinguer les trois options de git reset et leurs effets sur les trois espaces ;
  3. annuler un commit avec trace grâce à git revert ;
  4. comparer deux états avec git diff.

1. Lire l'historique

git log montre l'historique des versions pour la branche courante : du plus récent au plus ancien, chaque entrée porte son SHA-1, son auteur, sa date et son message. Quelques formats utiles :

git log                      l'historique complet
git log --oneline            une ligne par commit (SHA abrégé + message)
git log --oneline --graph --all   avec le graphe des branches
git log --follow fichier     l'historique d'un fichier, renommages compris
git show SHA                 le contenu exact d'un commit

C'est le format --oneline que le TP1 utilise pour vérifier la propreté de l'historique : une ligne, un commit, un message qui raconte quelque chose.

Mnémotechnique — « le log lit, le show montre »

log liste les états dans le temps ; show détaille un état : ses modifications de métadonnées et de contenu. Pour inspecter une régression, on log pour trouver le SHA suspect, puis show pour voir exactement ce qu'il a changé.

2. reset : les trois options

git reset ramène les trois espaces vers un état passé. Avec une référence (HEAD~3 = trois commits en arrière), il déplace la tête du dépôt :

OptionDépôt (HEAD)IndexCopie de travail
--softrevientles commits annulés y remontentinchangée
--mixed (défaut)revientvidéles modifications restent
--hardrevientvidéeffacée

Exemples du vade-mecum : git reset --soft HEAD^ (revenir à l'avant-dernier commit), git reset --soft HEAD~3 (trois commits en arrière), git reset --hard SHA (tout effacer après ce commit — les trois espaces deviennent identiques).

Piège — hard ne pardonne pas

reset --hard détruit les modifications de la copie de travail, sans confirmation. C'est l'option la plus utile et la plus dangereuse : en cas de doute, remiser avec git stash (chapitre 6) avant de reset — les modifications restent récupérables.

3. revert : annuler avec trace

Comme reset, git revert revient en arrière — mais il ajoute un commit à l'historique pour signaler cette réversion. Rien ne disparaît : l'erreur et son annulation restent toutes deux visibles.

git revert HEAD^      annule le commit d'avant-dernier par un nouveau commit

Le choix entre les deux : reset quand l'historique n'a pas été partagé (le commit est local et frais), revert quand il a été poussé — les autres collaborateurs conservent un historique cohérent, et l'annulation se propage proprement.

Mnémotechnique — « reset efface, revert écrit l'inverse »

reset réécrit le passé (avant push) ; revert écrit une page de plus : « voici l'annulation de ce commit ». Sur un dépôt partagé, l'historique est un contrat — revert le respecte.

4. comparer : git diff

git diff compare les espaces entre eux. Les variantes du vade-mecum :

git diff                    copie de travail ↔ index
git diff --cached           index ↔ dépôt local
git diff --staged           index ↔ dernier commit
git diff fichier            copie de travail ↔ index, pour un fichier
git diff HEAD^              copie de travail ↔ commit précédent
git diff master..feature1   deux branches

En guise de discipline : avant chaque commit, un git diff --staged relit ce qui part vraiment. C'est le réflexe qui évite les « modifications » comme message de commit.

Ce que diff ne montre pas

diff ne montre que les fichiers modifiés : les fichiers non suivis (jamais ajoutés) n'apparaissent pas. C'est git status qui les liste — les deux commandes se complètent.

Exercice 3 — revert : annuler avec trace

Bash Niveau 3 — Raisonnement

Objectif : Simuler git revert : l’annulation devient un nouveau commit visible dans l’historique.

Le script lit n opérations : commit msg, revert k (annule le k-ième commit le plus récent — k=1 le dernier — en ajoutant un commit Revert: msg ; si l’historique a moins de k commits, affiche inaccessible), ou log (comme au chapitre : du plus récent au plus ancien, SHA msg, SHA a1, a2… par ordre de création).

6. QCM — niveau examen

Quelle commande montre une ligne par commit ?

log --oneline : SHA abrégé + message, du plus récent au plus ancien.

Avec reset --soft, où remontent les commits annulés ?

soft ramène les modifications dans l'index : prêtes à être re-commitées.

Quelle option de reset efface aussi la copie de travail ?

hard aligne les trois espaces sur le commit visé — les modifications locales sont perdues.

Quelle est l'option par défaut de git reset ?

Sans option, reset agit comme --mixed : index vidé, copie conservée.

Que fait git revert ?

revert annule avec trace : l'historique gagne un commit de réversion.

Sur un dépôt partagé, quelle annulation privilégier ?

revert préserve l'historique partagé ; reset réécrirait le passé des autres.

git diff --cached compare…

--cached (comme --staged) montre ce que l'index contient par rapport au dépôt.

Que ne montre pas git diff ?

diff ne voit que le suivi : les non suivis apparaissent dans git status.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • reset --hard par réflexe : les modifications locales disparaissent sans retour.
  • reset sur un dépôt partagé : les autres subissent un historique réécrit.
  • Confondre revert et reset : revert ajoute une trace, reset efface.
  • HEAD~1 et HEAD^ confondus : les deux notent le parent, mais HEAD~n compte n génération.
  • Se fier à diff seul : les fichiers non suivis n'y figurent pas.

8. Méthodologie de résolution

Revenir en arrière proprement
  1. Identifier l'état à rejoindre : SHA, HEAD~n, ou HEAD^.
  2. Se demander qui voit l'historique : seul (reset possible) ou partagé (revert).
  3. Choisir l'option de reset selon ce qu'on garde : soft (index), mixed (copie), hard (rien).
  4. Sécuriser avant hard : stash ou copie de sauvegarde.
  5. Vérifier après : git log puis git status pour l'état des trois espaces.

9. Révision active

Résumé essentiel
  • git log liste les commits du plus récent au plus ancien ; --oneline une ligne par commit.
  • reset déplace HEAD vers le passé : soft (index plein), mixed (défaut, index vide), hard (copie effacée).
  • revert annule en ajoutant un commit de réversion : la méthode des dépôts partagés.
  • git diff compare copie ↔ index (--cached : index ↔ dépôt) ; les non suivis restent dans status.
  • Avant un reset --hard, stash : la récupération reste possible.

Checklist de maîtrise

  • Je lis un git log --oneline et j'identifie le commit cible.
  • Je prédis l'état des trois espaces après chaque option de reset.
  • Je choisis reset ou revert selon que l'historique est partagé ou non.
  • Je compare deux états avec la bonne variante de git diff.
