Chapitre 4 — Branches : isoler, fusionner, supprimer

Module 4 ≈ 2 h 30 de travail Réservé B1 et plus
Mise en situation

Le workflow professionnel du TP3 est formel : interdiction de travailler directement sur main. Chaque fonctionnalité vit sur sa branche, se développe tranquillement, puis fusionne dans main. Ce chapitre fait passer du « je commite tout sur main » au cycle main → feature → merge → main.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. créer une branche et s'y déplacer (branch + checkout, ou checkout -b) ;
  2. lister les branches locales et distantes ;
  3. fusionner une branche dans une autre et reconnaître un fast-forward ;
  4. identifier l'origine d'un conflit et choisir entre annulation et résolution.

1. Créer et basculer

Une branche est un pointeur mobile sur un commit : créer une branche n'écrase rien, cela pose une étiquette. Deux façons, équivalentes :

git branch 15_query_database        # créer
git checkout 15_query_database      # puis se déplacer dessus

git checkout -b 15_query_database   # créer ET se déplacer en une commande

Le TP3 l'utilise : git checkout -b feature-ajout-tache depuis main — la fonctionnalité se développe maintenant hors du fil principal. La vérification : git branch liste les branches locales, la courante marquée d'une étoile.

Mnémotechnique — « -b = branch + basculer »

checkout -b est la contraction du duo branch/checkout : la lettre b fait les deux d'un coup. C'est la forme du workflow professionnel, parce qu'on ne crée presque jamais une branche sans aller travailler dessus aussitôt.

2. Changer de branche proprement

git checkout nom change la branche courante — possible seulement s'il n'y a pas de modification dans la copie de travail (fichier ajouté, modifié ou supprimé). Pour forcer le changement, deux solutions :

SolutionEffet
git checkout -f nomforce ; les fichiers modifiés sont définitivement perdus
git stashremise temporaire ; rien ne se perd (chapitre 6)

Listes utiles : git branch -v pour les branches locales avec leur dernier commit, git branch -r pour les branches distantes. Suppression : git branch -d nom — le TP3 supprime la branche après fusion.

Piège — le checkout qui jette

checkout -f écrase les modifications non commitées, sans demande de confirmation. Avant de forcer un changement de branche, se demander ce que valent les fichiers modifiés : souvent, git stash est la réponse honnête.

3. Fusionner : merge et fast-forward

Fusionner la branche feature dans main :

git checkout main
git merge feature-ajout-tache

Cas attendu du TP3 : le fast-forward. Quand main n'a pas bougé depuis la création de la branche, la fusion avance simplement le pointeur : les commits de la branche deviennent des commits de main comme s'ils y avaient toujours été. Il n'y a plus trace de la branche dans l'historique — impossible de voir quels commits constituaient la fonctionnalité.

L'option --no-ff (no fast-forward) force la création d'un commit de fusion même quand le fast-forward est possible : l'existence de la branche de fonctionnalité reste visible. Un merge en cours s'annule avec git merge --abort.

Mnémotechnique — « ff avance, no-ff grave »

fast-forward : le pointeur glisse, l'historique reste droit, la branche disparaît. no-ff : un commit de fusion grave la fonctionnalité dans l'historique. Choix d'équipe : traçabilité contre simplicité de lecture.

4. Conflits : pourquoi, comment

Le conflit naît quand deux branches modifient la même zone d'un même fichier : Git ne peut pas choisir à votre place. C'est exactement le scénario des TP2 et TP5 : deux développeurs modifient main.py, la fusion s'arrête, le fichier porte des marqueurs :

<<<<<<< HEAD
print("Bienvenue dans le gestionnaire de tâches version finale")
=======
print("Bienvenue dans l'application de gestion des tâches")
>>>>>>> feature-message

Lecture des marqueurs : <<<<<<< HEAD ouvre la version de la branche courante, ======= sépare, >>>>>>> branche ferme la version de la branche fusionnée. La résolution se fait à la main : garder l'une, l'autre, ou les combiner — puis valider :

git add main.py
git commit -m "Résolution du conflit entre A et B"

Pour les fichiers binaires, pas de résolution à la main : choisir entre l'ancienne version (git checkout --ours fichier) et la nouvelle (git checkout --theirs fichier).

Le fil du TP3 en une séquence

checkout main → checkout -b feature-ajout-tache → deux commits atomiques → checkout main → merge feature → push origin main → git log --oneline --graph --all → branch -d feature. Le cycle complet du workflow professionnel.

Exercice 3 — merge et conflit

Bash Niveau 3 — Raisonnement

Objectif : Simuler la fusion de deux branches et détecter le conflit sur fichier commun.

Le script lit n opérations : branch nom + bascule immédiate (comme checkout -b), checkout nom, touch fichier (modifie un fichier sur la branche courante), commit (valide les modifications de la branche courante), ou merge nom. La fusion réussit (fast-forward) si les deux branches n’ont modifié aucun fichier en commun depuis leur séparation ; elle échoue (conflit) si un même fichier a été modifié des deux côtés. La fusion ramène sur la branche cible. Une branche créée hérite des fichiers modifiés non commités ? Non : chaque touch ne concerne que la branche courante.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Travailler directement sur main : l'interdiction n°1 du workflow du TP3.
  • checkout -f par impatience : les modifications non commitées disparaissent.
  • Fast-forward confondu avec fusion propre : ff efface la trace de la branche.
  • Marqueurs de conflit commités : <<<<<<< partis dans l'historique par un add aveugle.
  • Résoudre sans comprendre : choisir un côté au hasard fait perdre un travail.

8. Méthodologie de résolution

Résoudre un conflit sans panique
  1. Reconnaître l'état : merge arrêté, fichier marqué par les chevrons.
  2. Relire les deux versions : HEAD (courante) et la branche fusionnée.
  3. Décider du contenu final : garder, combiner, ou réécrire — jamais au hasard.
  4. Nettoyer les marqueurs : plus aucun chevron dans le fichier.
  5. Valider la résolution : add puis commit dédié au conflit.

9. Révision active

Résumé essentiel
  • checkout -b crée et bascule en une commande ; la courante porte l'étoile dans git branch.
  • Changer de branche exige une copie propre : -f perd les modifications, stash les garde.
  • merge avance par fast-forward quand main n'a pas bougé — sans trace de la branche.
  • --no-ff grave un commit de fusion : l'existence de la fonctionnalité reste lisible.
  • Conflit = même zone, deux versions ; les chevrons se lisent, se résolvent, s'add puis se commitent.

Checklist de maîtrise

  • Je crée une branche de fonctionnalité et je m'y place en une commande.
  • Je fusionne dans main et je reconnais un fast-forward.
  • Je lis des marqueurs de conflit et produis la version combinée.
  • Je supprime une branche après fusion et vérifie le graphe avec log --graph.
