Chapitre 5 — Dépôt distant : clone, push, pull, fetch

Module 5 ≈ 2 h 30 de travail Réservé B1 et plus
Mise en situation

Le TP2 passe en binôme : le dépôt de l'étudiant A part sur GitHub, l'étudiant B clone, et les deux modifient le même fichier. Premier push refusé, premier pull, premier conflit — le cycle complet de la collaboration. Ce chapitre explique ce que chaque commande déplace entre les deux dépôts.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. lier un dépôt local à un dépôt distant avec git remote add origin ;
  2. pousser ses commits avec git push et comprendre un rejet ;
  3. décomposer git pull en fetch + merge et voir ce que chacun met à jour ;
  4. rejouer le scénario du TP2 : deux développeurs, un conflit, une résolution.

1. origin : le lien vers le distant

Le dépôt local se lie au dépôt distant par une adresse. Le TP2 la pose ainsi :

git remote add origin https://github.com/<user>/gestion_taches.git
git branch -M main
git push -u origin main

Le nom origin est purement conventionnel : c'est le nom par défaut du lien vers le dépôt distant, il peut être changé. La vérification : git remote -v liste les liens avec leurs URL. git branch -M main renomme la branche principale en main, et push -u origin main pousse en liant la branche locale à sa jumelle distante.

Mnémotechnique — « origin = l'origine du clonage »

Un dépôt cloné connaît déjà son origin : le clone crée le lien automatiquement. Un dépôt initialisé en local doit se lier à la main avec remote add — c'est l'étape que le TP1 n'a pas, et le TP2 oui.

2. push : envoyer, et se faire refuser

git push envoie tous les commits de la branche locale vers le dépôt distant. Sous une forme complète : git push origin main.

Mais le push a une règle : on ne pousse que si l'on a tout ce que le distant contient. Si un tiers a poussé entre-temps (l'étudiant A dans le TP2), le push est rejeté : le distant refuse qu'on écrive par-dessus des commits que notre local ne connaît pas. La séquence du TP2 est formelle :

git push                    → rejeté (l'autre a poussé)
git pull origin main        → récupère et fusionne
git push                    → accepté
Piège — le push sans pull

Le rejet n'est pas une panne : c'est la protection qui empêche d'écraser le travail des autres. L'exercice « push refusé » de l'atelier rejoue exactement ce scénario et montre que le pull remet tout le monde d'accord.

3. fetch et pull : deux façons de ramener

Les deux commandes écoutent le distant, mais ne vont pas aussi loin l'une que l'autre :

CommandeEffet
git fetch originrécupère tout l'historique du dépôt distant et actualise les références locales — sans fusionner, sans toucher à la copie de travail
git pullfetch puis merge : ramène ET incorpore les modifications dans la branche courante

Un git pull correspond donc exactement à :

git fetch origin
git merge origin/main

La nuance compte : après un fetch, on peut examiner ce qui est arrivé (git log origin/main, git diff) avant de décider de fusionner. Après un pull, la fusion a déjà eu lieu — conflits compris. Pour éviter les dérivations d'historique, le vade-mecum propose aussi un pull avec rebase : git pull --rebase=preserve origin main.

Mnémotechnique — « fetch écoute, pull obéit »

fetch ramène les nouvelles sans toucher à votre travail : il met à jour les références distantes locales (origin/main). pull = fetch + merge : il avance aussi votre branche. En cas de doute, fetch d'abord, on merge ensuite en connaissance de cause.

4. Le scénario complet du TP2

Rejouons le fil du TP2, la scène de conflit la plus fréquente du travail en binôme :

# Étudiant A (propriétaire) : init, commit, push initial
git init ; git add . ; git commit -m "Initialisation du projet"
git remote add origin ...
git branch -M main ; git push -u origin main

# Étudiant B : clone
git clone ...

# Les deux modifient main.py, chacun son côté :
A : add + commit + push          → accepté
B : add + commit + push          → REJETÉ (A a poussé avant)
B : git pull origin main         → CONFLIT sur main.py
# B résout les marqueurs, puis :
B : add + commit + push          → accepté

La leçon : le rejet et le conflit ne sont pas des accidents, ce sont les gardiens de la collaboration. On les rencontre chaque fois que deux personnes modifient la même zone — et la résolution se fait toujours de la même façon : lire les deux versions, décider, add, commit.

Aller plus loin : la distribution des sources

Pour livrer une archive propre de la version courante sans le dossier .git : git archive --format=tar --prefix=dossier/ HEAD | gzip > v1.4.0.tar.gz. L'archive se décompresse dans un dossier nommé, avec tous les fichiers du dépôt.

Exercice 1 — push refusé : repartir du pull

Bash Niveau 2 — Application

Objectif : Rejouer le scénario du TP2 : un push sans pull préalable est rejeté par le dépôt distant.

Le script lit n opérations : commit (commit local), pull (récupère l’état du distant : le compteur local s’aligne sur le plus grand des deux compteurs), push — accepté seulement si le local contient tout le distant, c’est-à-dire si aucun commit distant n’a été « appris » après le dernier pull et qu’il y a au moins un commit local à envoyer. Simplification du TP : le push réussit si aucun autre développeur n’a poussé depuis (drapeau distants incrémenté par chaque pull d’un tiers, opération tierce) ; sinon il affiche rejeté et il faut pull puis recommencer. Après chaque push réussi ou refusé, afficher local : K et distant : K (K = commits du dépôt distant).

distant : 2

Le push affiche l'état, puis l'opération distant le redonne.

Deux indices, rédigés en mots
  1. Le push n’est jamais possible sans pull si un tiers a poussé entre-temps : le drapeau le retient.
  2. Après un push réussi, local et distant sont égaux : le drapeau de fraîcheur repart à zéro.

Exercice 2 — clone et origin

Bash Niveau 2 — Application

Objectif : Simuler clone : le dépôt local démarre avec tout l’historique du distant.

Le script lit n opérations : commit k (k commits poussés sur le dépôt distant par d’autres), clone (crée le local avec tout le distant), ou etat (affiche local : K / distant : K, ou local : aucun si pas de clone). Un commit après clone reste local jusqu’au push (traité au chapitre 6 — ici, les commits d’un tiers s’ajoutent directement au distant).

  1. Un drapeau cloné vaut mieux qu’un test de nil : etat sait quoi répondre.
  2. commit k pendant le clone n’existe pas : k n’arrive qu’avec l’opération commit.

Exercice 3 — fetch puis merge : le vrai pull

Bash Niveau 3 — Raisonnement

Objectif : Décomposer git pull en fetch + merge et montrer ce que chacun met à jour.

Le script lit n opérations : commit (commit local, la copie avance), tierce branche (un tiers pousse k=1 commit sur la branche distante nommée), fetch (copie l’état distant dans les références locales, sans toucher à la branche locale), ou etat. L’état affiche trois lignes : local : K, remote-suivi : K (dernière valeur vue par fetch), distant : K. Après un fetch, remote-suivi rattrape distant ; la branche locale, elle, ne bouge pas.

Deux indices, rédigés en mots
  1. fetch met à jour remote-suivi mais jamais local : c’est toute la différence avec pull.

6. QCM — niveau examen

Le nom origin désigne…

origin est le nom par défaut du lien distant ; il peut être changé.

Quelle commande liste les liens distants ?

remote -v montre les liens et leurs URL ; branch -r liste les branches distantes.

Un push est rejeté quand…

Le distant refuse qu'on écrive par-dessus ce que notre local ne connaît pas : pull d'abord.

Que fait git fetch ?

fetch ramène l'historique distant et met à jour origin/main, sans toucher à la copie.

git pull équivaut à…

pull = fetch + merge : il ramène ET incorpore dans la branche courante.

Après un fetch, la copie de travail est…

fetch ne touche ni à la copie de travail ni à la branche courante.

Que fait git push -u origin main ?

-u (upstream) lie la branche locale à la branche distante pour les push/pull suivants.

Dans le TP2, le conflit survient parce que…

Deux modifications de la même zone : la fusion demande un arbitrage humain.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Pusher sans pull après un rejet : le rejet se lève par un pull, pas par l'insistance.
  • Confondre fetch et pull : l'un écoute, l'autre fusionne déjà.
  • Croire que clone lie origin automatiquement mais pas remote add : le lien se crée dans les deux cas, manuellement ou non.
  • Forcer un push (--force) pour passer : le travail des autres disparaît.
  • Oublier branch -M main : le push vise main, le local s'appelle peut-être master.

8. Méthodologie de résolution

Synchroniser sans écraser personne
  1. Lier correctement : remote add origin + branch -M main + push -u.
  2. Pousser tôt et souvent : moins de divergence, moins de conflits.
  3. Lire un rejet : il signifie « le distant avance, rattrape-le ».
  4. Fetch pour observer, pull pour incorporer : choisir en connaissance de cause.
  5. Résoudre les conflits comme au chapitre 4 : lire, décider, add, commit.

9. Révision active

Résumé essentiel
  • remote add origin lie le local au distant ; remote -v vérifie ; clone crée le lien tout seul.
  • push -u origin main pousse et lie la branche pour les échanges suivants.
  • Un push est rejeté si le distant contient du travail inconnu du local : pull d'abord.
  • fetch actualise les références sans fusionner ; pull = fetch + merge.
  • Rejet et conflit sont les protections de la collaboration : on les résout, jamais on ne les contourne.

Checklist de maîtrise

  • Je lie un dépôt local à un distant et je vérifie avec remote -v.
  • Je prédis l'issue d'un push d'après l'état des deux dépôts.
  • Je décompose pull en fetch + merge et montre ce que chacun change.
  • Je rejoue le scénario A/B du TP2 avec conflit et résolution.
