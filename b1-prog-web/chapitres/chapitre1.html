Chapitre 1 — Le Web : clients, serveurs, URL et HTTP

Module 1 ≈ 2 h 30 de travail Accès libre
Mise en situation

Tu tapes une adresse dans la barre du navigateur et la page apparaît. Entre ces deux instants, il y a un dialogue complet entre deux ordinateurs : une demande précise, une réponse, puis un document qu’il faut interpréter. Quand une page affiche « 404 » ou charge des images cassées, toute la lecture du problème se fait dans ce dialogue. Ce chapitre t’apprend à le voir.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. décrire le rôle du client, du serveur et du protocole HTTP ;
  2. décomposer une URL en protocole, hôte, chemin et paramètres de requête ;
  3. reconnaître les méthodes HTTP et dire lesquelles sont idempotentes ;
  4. interpréter un code de statut par sa famille (1xx à 5xx) ;
  5. situer les responsabilités de HTML, CSS et JavaScript dans une page.

1. Un dialogue entre deux programmes

Le client est le programme qui demande (le navigateur, un script, une application mobile). Le serveur est le programme qui répond, en attendant les demandes sur un port. Entre les deux circule du texte : la requête du client, puis la réponse du serveur. Le protocole qui fixe la forme de ces messages s’appelle HTTP.

Une requête HTTP contient toujours trois choses : une méthode (ce qu’on veut faire), une ressource (le chemin demandé) et des en-têtes (métadonnées : langue, type de contenu accepté, cookies). La réponse contient un code de statut, ses propres en-têtes et un corps — le plus souvent du HTML.

GET /cours/index.html HTTP/1.1        ← la requête du client
Host: campus.exemple.fr
Accept-Language: fr

HTTP/1.1 200 OK                      ← la réponse du serveur
Content-Type: text/html; charset=utf-8

 …
Intuition — le serveur ne devine rien

Un serveur ne « sait » pas ce que tu regardes à l’écran. Il reçoit un chemin et rend un fichier. Si les images ne s’affichent pas, c’est souvent que le navigateur a redemandé une ressource dont l’adresse était fausse : autant de requêtes, autant de réponses.

2. Anatomie d’une URL

Une URL (Uniform Resource Locator) désigne une ressource de façon unique. Elle se lit toujours dans le même ordre :

https://campus.exemple.fr:443/cours/index.html?page=2&tri=asc#section-3
└┬─┘   └───────┬───────┘└┬┘└────────┬────────┘└─────┬─────┘└───┬────┘
protocole      hôte     port     chemin          requête     fragment
ComposanteRôleExemple
protocolela langue du dialoguehttps
hôtequel serveur joindrecampus.exemple.fr
portquel service sur ce serveur (facultatif)443
cheminquelle ressource/cours/index.html
requêtedes paramètres, après le ?page=2&tri=asc
fragmentune ancre dans la page, jamais envoyée au serveur#section-3

Deux points se retiennent : le chemin commence toujours par une barre oblique, même quand tu ne l’écris pas (taper https://exemple.fr demande en réalité /) ; et le fragment reste dans le navigateur — le serveur ne le reçoit jamais.

Piège — paramètres de requête et chemins différents

/notes?page=2 et /notes?page=3 mènent au même chemin : la différence tient dans la requête. Pour un serveur, ce sont deux demandes distinctes de la même ressource. Confondre les deux fait chercher longtemps un fichier qui n’existe pas.

3. Les méthodes HTTP

La méthode dit l’intention. Neuf méthodes existent ; cinq suffisent au quotidien :

MéthodeCe qu’elle demandeIdempotente ?
GETlire une ressource, sans la modifieroui
POSTcréer une ressource, envoyer des donnéesnon
PUTremplacer une ressource par celle envoyéeoui
PATCHmodifier une partie d’une ressourcenon
DELETEsupprimer une ressourceoui

Une méthode est idempotente quand rejouer la même requête laisse le serveur dans le même état que de l’avoir envoyée une fois. Refaire DELETE /notes/12 ne supprime rien de plus ; refaire POST /notes crée une deuxième note. C’est ce qui rend une requête rejouable sans crainte après une coupure réseau — et ce qui oblige à protéger les POST.

Mnémotechnique — « POST pousse, PUT pose »

PUT pose la ressource complète : deux fois la même requête donnent exactement le même résultat. POST pousse quelque chose de neuf dans la collection : chaque envoi ajoute une ligne.

4. Les codes de statut

Le code de statut est un nombre à trois chiffres. Le premier chiffre donne la famille ; les deux suivants précisent le cas. Savoir lire la famille suffit pour diagnostiquer la plupart des problèmes.

FamilleSensExemples
1xxinformation : la demande est en cours de traitement100, 101
2xxsuccès : la demande a abouti200, 201, 204
3xxredirection : voir ailleurs301, 302, 304
4xxerreur du client (la demande est fautive)400, 403, 404, 422
5xxerreur du serveur (la demande était valable)500, 502, 503

La frontière entre 4xx et 5xx est la plus utile à connaître : 404 signifie « cette adresse n’existe pas chez moi », 500 signifie « mon code a planté pendant que je traitais ta demande valable ». Corriger une 404 se fait dans l’adresse ; corriger une 500 se fait dans le serveur.

Piège — confondre 401 et 403

401 Unauthorized veut dire « je ne sais pas qui tu es » : il manque une identification. 403 Forbidden veut dire « je sais qui tu es, et tu n’as pas le droit ». La première invite à se connecter ; la seconde interdit d’insister.

5. HTML, CSS, JavaScript : trois rôles distincts

Une page web est faite de trois langages qui ne se remplacent pas :

  • HTML : la structure et le sens du contenu (un titre, une liste, un paragraphe). Sans HTML, rien à afficher.
  • CSS : la présentation (couleurs, tailles, disposition). Sans CSS, la page reste lisible mais brute.
  • JavaScript : le comportement (réagir à un clic, calculer, modifier la page après son chargement). Sans JavaScript, la page reste consultable mais figée.

    6. Suivre le dialogue dans le navigateur

    Tout ce chapitre se vérifie à l’écran, sans installer quoi que ce soit. Les outils de développement du navigateur (touche F12) contiennent un onglet Réseau qui liste chaque requête, son statut, son type et sa durée.

    Devant une page qui ne s’affiche pas comme prévu, ouvre l’onglet Réseau et recharge. Cherche la première ligne en rouge : c’est presque toujours la cause, et les suivantes n’en sont que la conséquence.

    7. Exercices de code

    Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

    En cas d’erreur, le bouton Expliquer mon erreur interroge le tuteur : il décrit ce qui s’est passé et par où chercher, sans jamais écrire de code à votre place — c’est le principe de l’exercice.

    8. QCM — niveau examen

    Dans le dialogue HTTP, qui envoie la requête ?

    Le client demande la ressource ; le serveur y répond.

    Dans l’URL https://campus.fr/cours/a.html?page=2, que vaut l’hôte ?

    L’hôte suit le protocole et se termine avant la première barre oblique.

    Quel élément du chemin est réellement envoyé au serveur ?

    Le fragment reste dans le navigateur ; les paramètres font partie de la requête.

    Quelle méthode est idempotente ?

    PUT remplace la ressource : la rejouer ne change pas l’état final. POST crée à chaque appel.

    Le serveur renvoie 503. De quelle famille s’agit-il ?

    5xx : la demande était valable mais le serveur n’a pas pu y répondre.

    Quel langage décrit la structure du contenu ?

    HTML structure et donne du sens ; CSS présente ; JavaScript anime.

    9. Erreurs classiques — récapitulatif

    À reconnaître en examen
    • Confondre paramètres de requête et chemin : /notes?page=2 n’est pas un fichier notes?page=2.
    • Croire que le fragment part au serveur : #section ne quitte jamais le navigateur.
    • Attendre d’un GET qu’il modifie quelque chose : il est censé ne rien changer.
    • Chercher une erreur de serveur dans le HTML : une 500 se diagnostique côté serveur.
    • Mettre le <script> en haut de page sans defer : le script cherche des éléments qui n’existent pas encore.

    10. Méthodologie de résolution

    Lire une adresse et une réponse, sans hésiter
    1. Découpe l’URL de gauche à droite : protocole, hôte, port éventuel, chemin, requête, fragment.
    2. Décide de la méthode selon l’intention : lire (GET), créer (POST), remplacer (PUT), modifier (PATCH), supprimer (DELETE).
    3. Prévois le statut attendu du serveur avant de lancer la requête ; compare ensuite.
    4. Lis le premier chiffre d’un code inattendu pour savoir de quel côté chercher.
    5. Ouvre l’onglet Réseau et remonte à la première requête rouge.

    11. Révision active

    Résumé essentiel
    • Le client demande, le serveur répond ; HTTP fixe la forme des messages.
    • Une URL se lit : protocole, hôte, port, chemin, requête, fragment — le fragment ne part pas au serveur.
    • Cinq méthodes suffisent : GET lire, POST créer, PUT remplacer, PATCH modifier, DELETE supprimer.
    • Idempotente = rejouable sans effet supplémentaire : GET, PUT, DELETE le sont ; POST et PATCH non.
    • Le premier chiffre du statut donne la famille : 2xx succès, 3xx redirection, 4xx faute du client, 5xx faute du serveur.
    • HTML structure, CSS présente, JavaScript anime — trois rôles, trois fichiers.

    Checklist de maîtrise

    • Je décompose une URL en quatre parties sans me tromper.
    • Je choisis la bonne méthode HTTP pour une intention donnée.
    • Je dis si une méthode est idempotente et j’explique pourquoi.
    • Je classe un code de statut dans sa famille et j’en tire la bonne conclusion.
