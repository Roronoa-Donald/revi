Chapitre 1 — Le Web : clients, serveurs, URL et HTTP

Module 1 ≈ 2 h 30 de travail Accès libre
Mise en situation

Vous tapez une adresse dans la barre du navigateur et la page apparaît. Entre ces deux instants, il y a un dialogue complet entre deux ordinateurs : une demande précise, une réponse, puis un document qu’il faut interpréter. Quand une page affiche « 404 » ou charge des images cassées, toute la lecture du problème se fait dans ce dialogue. Ce chapitre vous apprend à le voir.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. décrire le rôle du client, du serveur et du protocole HTTP ;
  2. décomposer une URL en protocole, hôte, chemin et paramètres de requête ;
  3. reconnaître les méthodes HTTP et dire lesquelles sont idempotentes ;
  4. interpréter un code de statut par sa famille (1xx à 5xx) ;
  5. situer les responsabilités de HTML, CSS et JavaScript dans une page.

1. Un dialogue entre deux programmes

Le client est le programme qui demande (le navigateur, un script, une application mobile). Le serveur est le programme qui répond, en attendant les demandes sur un port. Le protocole HTTP décrit la requête du client et la réponse du serveur ; selon la version, leur représentation sur le réseau peut être textuelle ou binaire.

Une requête indique une méthode et une cible ; des en-têtes apportent éventuellement des métadonnées, et un corps peut transmettre des données. La réponse contient un code de statut et peut avoir des en-têtes et un corps.

GET /cours/index.html HTTP/1.1        ← la requête du client
Host: campus.exemple.fr
Accept-Language: fr

HTTP/1.1 200 OK                      ← la réponse du serveur
Content-Type: text/html; charset=utf-8

<!DOCTYPE html> …
Intuition — le serveur ne devine rien

Un serveur ne « sait » pas ce que vous regardez à l’écran. Il reçoit un chemin et rend un contenu ou un résultat produit par une application. Si les images ne s’affichent pas, vérifiez notamment l’adresse des ressources demandées.

2. Anatomie d’une URL

Une URL (Uniform Resource Locator) désigne une ressource. Voici les composantes possibles d’une adresse HTTPS absolue ; plusieurs peuvent être absentes :

https://campus.exemple.fr:443/cours/index.html?page=2&tri=asc#section-3
└┬─┘   └───────┬───────┘└┬┘└────────┬────────┘└─────┬─────┘└───┬────┘
protocole      hôte     port     chemin          requête     fragment
ComposanteRôleExemple
protocolela langue du dialoguehttps
hôtequel serveur joindrecampus.exemple.fr
portquel service sur ce serveur (facultatif)443
cheminquelle ressource/cours/index.html
requêtedes paramètres, après le ?page=2&tri=asc
fragmentune ancre dans la page, jamais envoyée au serveur#section-3

Deux points se retiennent : le chemin commence toujours par une barre oblique, même quand vous ne l’écrivez pas (taper https://exemple.fr demande en réalité /) ; et le fragment reste dans le navigateur — le serveur ne le reçoit jamais.

Piège — paramètres de requête et chemins différents

/notes?page=2 et /notes?page=3 mènent au même chemin : la différence tient dans la requête. Pour un serveur, ce sont deux demandes distinctes de la même ressource. Confondre les deux fait chercher longtemps un fichier qui n’existe pas.

3. Les méthodes HTTP

La méthode dit l’intention. Neuf méthodes existent ; cinq suffisent au quotidien :

MéthodeCe qu’elle demandeIdempotente ?
GETlire une ressource, sans la modifieroui
POSTsoumettre des données à un traitementnon garanti
PUTremplacer une ressource par celle envoyéeoui
PATCHmodifier une partie d’une ressourcenon garanti
DELETEsupprimer une ressourceoui

Une méthode est idempotente lorsque plusieurs requêtes identiques ont le même effet demandé sur le serveur qu’une seule. Les réponses peuvent différer et des effets auxiliaires, comme les journaux, peuvent subsister. Refaire DELETE /notes/12 ne demande pas une suppression supplémentaire ; un POST de création peut ajouter une deuxième note. POST et PATCH ne garantissent pas cette propriété, même si une opération particulière peut être idempotente. Une reprise automatique doit aussi tenir compte de l’application et de la panne. Les méthodes HEAD, OPTIONS et TRACE sont également définies comme idempotentes : HEAD demande les en-têtes sans le corps, OPTIONS les possibilités de communication, TRACE un diagnostic de la requête reçue.

Mnémotechnique — « POST pousse, PUT pose »

PUT pose la ressource complète : deux fois la même requête donnent le même effet attendu sur la ressource. POST soumet des données à un traitement : selon l’application, il peut notamment créer une nouvelle entrée.

4. Les codes de statut

Le code de statut est un nombre à trois chiffres. Le premier chiffre donne la famille ; les deux suivants précisent le cas. Savoir lire la famille suffit pour diagnostiquer la plupart des problèmes.

FamilleSensExemples
1xxinformation : la demande est en cours de traitement100, 101
2xxsuccès : la demande a abouti200, 201, 204
3xxredirection : voir ailleurs301, 302, 304
4xxréponse de la famille erreur client400, 403, 404, 422
5xxréponse de la famille erreur serveur500, 502, 503

La frontière entre 4xx et 5xx est la plus utile à connaître : 404 indique que le serveur ne trouve pas de représentation disponible ou ne souhaite pas en révéler l’existence. 500 signale une situation inattendue côté serveur. Le code oriente le diagnostic mais ne prouve ni la cause exacte ni la validité de la demande.

Piège — confondre 401 et 403

401 Unauthorized indique que la requête n’a pas de justificatifs d’authentification valides. 403 Forbidden indique un refus d’autoriser la requête ; cela ne prouve pas que l’identité du client soit connue.

5. HTML, CSS, JavaScript : trois rôles distincts

Une page web est faite de trois langages qui ne se remplacent pas :

  • HTML : la structure et le sens du contenu (un titre, une liste, un paragraphe). Sans HTML, rien à afficher.
  • CSS : la présentation (couleurs, tailles, disposition). Sans CSS, la page reste lisible mais brute.
  • JavaScript : le comportement (réagir à un clic, calculer, modifier la page après son chargement). Sans JavaScript, la page reste consultable mais figée.
<!DOCTYPE html>
<html lang="fr">
<head>
  <meta charset="UTF-8">
  <title>Mes notes</title>
  <link rel="stylesheet" href="styles.css">   ← CSS
</head>
<body>
  <h1>Mes notes</h1>                          ← HTML
  <ul id="notes"></ul>
  <script src="app.js" defer></script>        ← JavaScript
</body>
</html>
Le navigateur lit la page dans l’ordre

Le serveur envoie le HTML en premier ; le navigateur le construit de haut en bas. Le CSS est appliqué dès qu’il est lu, et le JavaScript s’exécute quand il arrive — sauf s’il porte l’attribut defer, qui le fait attendre la fin de l’analyse du document. D’où la règle : un script qui manipule la page se place en fin de body ou avec defer.

6. Suivre le dialogue dans le navigateur

Tout ce chapitre se vérifie à l’écran, sans installer quoi que ce soit. Les outils de développement du navigateur (touche F12) contiennent un onglet Réseau qui liste chaque requête, son statut, son type et sa durée.

Ce que vous observezCe que cela signifie
une ligne rouge en 404aucune représentation disponible n’est déclarée pour cette demande
une ligne en 500le serveur a échoué pendant le traitement
une ligne en 304la ressource n’a pas changé : le navigateur réutilise sa copie
une ressource en « (blocked) »une règle de sécurité ou une extension l’a refusée
Réflexe de débogage

Devant une page qui ne s’affiche pas comme prévu, ouvre l’onglet Réseau et recharge. Cherche la première ligne en rouge : c’est presque toujours la cause, et les suivantes n’en sont que la conséquence.

8. QCM — niveau examen

Dans le dialogue HTTP, qui envoie la requête ?

Le client demande la ressource ; le serveur y répond.

Dans l’URL https://campus.fr/cours/a.html?page=2, que vaut l’hôte ?

L’hôte suit le protocole et se termine avant la première barre oblique.

Pour une URL HTTP, quelle composante est incluse dans la cible transmise au serveur ?

La requête fait partie de la cible HTTP ; le fragment n’y est pas inclus.

Quelle méthode est définie comme idempotente par HTTP ?

PUT est défini comme idempotent. POST et PATCH ne le garantissent pas, même si une opération précise peut l’être.

Le serveur renvoie 503. De quelle famille s’agit-il ?

503 appartient à la famille 5xx ; ce code ne prouve pas à lui seul que la demande était valide.

Quel langage décrit la structure du contenu ?

HTML structure et donne du sens ; CSS présente ; JavaScript anime.

9. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Confondre paramètres de requête et chemin : /notes?page=2 n’est pas un fichier notes?page=2.
  • Croire que le fragment part au serveur : #section ne quitte jamais le navigateur.
  • Attendre d’un GET qu’il modifie quelque chose : il est censé ne rien changer.
  • Chercher une erreur de serveur dans le HTML : une 500 se diagnostique côté serveur.
  • Mettre le <script> en haut de page sans defer : le script cherche des éléments qui n’existent pas encore.

10. Méthodologie de résolution

Lire une adresse et une réponse, sans hésiter
  1. Découpez l’URL de gauche à droite : protocole, hôte, port éventuel, chemin, requête, fragment.
  2. Décide de la méthode selon l’intention : lire (GET), créer (POST), remplacer (PUT), modifier (PATCH), supprimer (DELETE).
  3. Prévois le statut attendu du serveur avant de lancer la requête ; compare ensuite.
  4. Lisez le premier chiffre d’un code inattendu pour savoir de quel côté chercher.
  5. Ouvrez l’onglet Réseau et remonte à la première requête rouge.

11. Révision active

Résumé essentiel
  • Le client demande, le serveur répond ; HTTP fixe la forme des messages.
  • Une URL se lit : protocole, hôte, port, chemin, requête, fragment — le fragment ne part pas au serveur.
  • Cinq méthodes suffisent : GET lire, POST créer, PUT remplacer, PATCH modifier, DELETE supprimer.
  • Idempotence : les requêtes identiques ont le même effet demandé ; GET, PUT et DELETE le sont par définition, contrairement à POST et PATCH qui ne le garantissent pas.
  • Le premier chiffre du statut donne la famille : 2xx succès, 3xx redirection, 4xx erreur client, 5xx erreur serveur.
  • HTML structure, CSS présente, JavaScript anime — trois rôles, trois fichiers.

Checklist de maîtrise

  • Je décompose une URL en quatre parties sans me tromper.
  • Je choisis la bonne méthode HTTP pour une intention donnée.
  • Je dis si une méthode est idempotente et j’explique pourquoi.
  • Je classe un code de statut dans sa famille et j’en tire la bonne conclusion.
