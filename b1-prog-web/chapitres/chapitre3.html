Chapitre 3 — Formulaires, validation et sécurité des entrées

Module 3 ≈ 3 h de travail Réservé B1 et plus
Mise en situation

Un formulaire est la seule porte d’entrée du site : ce qui vient de l’utilisateur est, par définition, imprévisible. Le navigateur peut aider à filtrer, mais il ne protège rien : n’importe qui peut envoyer ce qu’il veut, avec ou sans navigateur. Écrire un formulaire, c’est donc écrire deux fois la même règle — une fois pour aider l’utilisateur, une fois pour se protéger.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. construire un formulaire HTML complet et correctement étiqueté ;
  2. choisir le type de champ adapté à la donnée attendue ;
  3. utiliser la validation native du navigateur sans en dépendre ;
  4. échapper une entrée utilisateur avant de l’insérer dans une page ;
  5. expliquer pourquoi la validation serveur reste indispensable.

1. Un formulaire, c’est une requête préparée

Un formulaire décrit ce qui sera envoyé au serveur : où (action), comment (method) et quoi (chaque champ qui porte un attribut name). Sans name, un champ est visible mais jamais transmis.

Avec method="post", les données voyagent dans le corps de la requête. Avec method="get", elles se retrouvent dans l’URL, visibles et conservées dans l’historique du navigateur : acceptable pour une recherche, à proscrire pour un mot de passe.

Piège — GET pour une action qui modifie

Un formulaire de suppression en GET se déclenche par un simple rechargement d’URL. Une action qui change l’état du serveur s’envoie toujours en POST.

2. Les types de champs

Le type d’un input dit au navigateur ce qu’il attend : il adapte le clavier sur téléphone et propose un contrôle adapté. Ce n’est pas une protection, c’est une aide.

Pour les listes de choix, on utilise select avec option, ou textarea pour un texte long. Attention : textarea n’est pas un input, sa valeur est écrite entre les balises, pas dans un attribut value.

Mnémotechnique — « un name, une valeur »

Le couple qui compte pour le serveur est toujours name=valeur. Le id, lui, sert au navigateur : il relie l’étiquette au champ et permet au CSS et au JavaScript de le cibler.

3. Étiquettes et accessibilité

Chaque champ doit avoir une étiquette. Deux façons de la relier, la première étant préférable : l’attribut for qui désigne l’id du champ, ou l’imbrication du champ dans l’étiquette.

Un placeholder disparaît dès la première frappe et n’est pas toujours lu par les lecteurs d’écran : c’est une aide, jamais une étiquette. Pour un groupe de cases à cocher, on encadre l’ensemble avec <fieldset> et <legend>.

Le clic qui va au bon champ

Quand label for="mail" désigne input id="mail", cliquer sur le texte place le curseur dans le champ. C’est un gain de confort réel sur téléphone, et le signe que la relation entre étiquette et champ est correcte.

4. La validation côté client

HTML fournit des règles déclaratives : required (champ obligatoire), min et max (bornes numériques), minlength et maxlength (longueur), pattern (expression régulière), type (forme attendue). Le navigateur bloque l’envoi et affiche un message s’il n’est pas satisfait.

Deux limites, décisives : un utilisateur peut désactiver la validation du navigateur, et n’importe quel programme peut envoyer une requête POST sans passer par la page. La validation côté client est un service rendu à l’utilisateur ; la validation côté serveur est la seule qui protège le système.

Piège — la validation en JavaScript n’est pas une protection

Désactiver le JavaScript du navigateur, ou envoyer directement la requête avec curl, contourne toutes les règles écrites dans la page. La même vérification doit exister sur le serveur, sans exception.

5. Insérer une entrée utilisateur sans danger

Le navigateur interprète comme du HTML tout ce qu’on lui donne à afficher. Si une chaîne saisie par un visiteur est insérée telle quelle dans la page, son contenu devient du code : c’est le mécanisme de l’injection HTML, et de la faille XSS qui en découle.

// dangereux : la saisie devient du balisage
zone.innerHTML = commentaire;

// sûr : la saisie reste du texte
zone.textContent = commentaire;

// si le HTML est indispensable, on échappe d’abord les caractères sensibles
function echapper(texte) {
  return texte
    .replace(/&/g, "&")
    .replace(//g, ">")
    .replace(/"/g, """)
    .replace(/'/g, "'");
}

L’ordre des remplacements n’est pas neutre : on commence toujours par le &, sinon les entités déjà créées seraient ré-échappées et afficheraient &amp;lt; au lieu de &lt;.

Mnémotechnique — texte ou balisage ?

textContent traite ce qu’on lui donne comme du texte ; innerHTML comme du balisage. Pour une donnée venue d’un utilisateur, la réponse est toujours textContent.

6. Progression d’un formulaire bien conçu

Un formulaire utilisable se construit dans un ordre stable : structure, étiquettes, types, validation, puis messages d’erreur.

  1. Action et méthode : où vont les données et comment elles voyagent.
  2. Étiquettes : un label relié à chaque champ, un fieldset par groupe de choix.
  3. Types et contraintes : le bon type, les bornes, required.
  4. Validation serveur : les mêmes règles, réécrites côté serveur, sans exception.
  5. Messages : explicites et proches du champ, jamais un simple « erreur ».
MessageCe qu’il apporte au visiteur
« Note attendue entre 0 et 20. »la règle et la borne
« Cette note vaut 25. »la valeur reçue, à corriger
« Erreur de saisie. »rien : le visiteur ne sait pas quoi corriger
La règle des deux validations

Écris la règle une fois pour l’utilisateur (HTML, messages clairs) et une fois pour le système (serveur, refus silencieux). Si tu ne dois en garder qu’une, garde celle du serveur : elle est la seule que personne ne peut contourner.

7. Exercices de code

Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

En cas d’erreur, le bouton Expliquer mon erreur interroge le tuteur : il décrit ce qui s’est passé et par où chercher, sans jamais écrire de code à votre place — c’est le principe de l’exercice.

Exercice 1 — Valider une adresse électronique

JavaScript Niveau 2 — Application

Objectif : Écrire une validation explicite plutôt que de se reposer sur le navigateur.

Le programme reçoit une adresse électronique sur une seule ligne. Elle est valide si elle contient exactement un @, si la partie avant est non vide, si la partie après contient un point qui n’est ni le premier ni le dernier caractère, et si elle ne contient aucun espace. Affichez valide ou invalide.

Entrée du programme
etudiant.b1@campus.fr
Sortie attendue
valide

Un seul @, domaine avec un point, pas d’espace.

Deux indices, rédigés en mots
  1. Compte les @ avec split("@"): le tableau obtenu ne doit contenir que deux éléments.
  2. Pour la partie domaine : elle doit contenir un point, et ni commencer ni finir par ce point.

Exercice 2 — Force d’un mot de passe

JavaScript Niveau 3 — Raisonnement

Objectif : Compter des critères, puis traduire un score en conseil lisible.

Le programme reçoit un mot de passe sur une seule ligne. Comptez cinq critères : au moins 8 caractères ; au moins une majuscule ; au moins une minuscule ; au moins un chiffre ; au moins un caractère qui n’est ni lettre ni chiffre. Affichez score conseil où le conseil vaut faible (score ≤ 2), moyen (3 ou 4) ou fort (5).

Entrée du programme
B1-secret!
Sortie attendue
5 fort

Longueur, majuscule, minuscule, chiffre et symbole.

Deux indices, rédigés en mots
  1. Trois expressions régulières (majuscule, minuscule, chiffre) suffisent ; le caractère spécial s’obtient par différence.
  2. Les critères vrais valent 1 et les faux 0 : la somme donne directement le score.

Exercice 3 — Échapper du HTML

JavaScript Niveau 3 — Raisonnement

Objectif : Neutraliser un texte saisi par l’utilisateur avant de l’insérer dans une page.

Le programme reçoit un texte saisi par un visiteur, sur une seule ligne. Affichez ce texte après échappement : & devient &amp;, < devient &lt;, > devient &gt;, " devient &quot; et ' devient &#39;.

Entrée du programme
5 < 10 & "ok"
Sortie attendue
5 &lt; 10 &amp; &quot;ok&quot;

Chaque caractère sensible est remplacé.

Deux indices, rédigés en mots
  1. L’ordre des remplacements n’est pas neutre : commence impérativement par le & , sinon tu ré-échapperas les entités créées.
  2. replace() avec une expression régulière globale — le drapeau g — remplace toutes les occurrences, pas seulement la première.

8. QCM — niveau examen

Quel attribut rend un champ effectivement transmis au serveur ?

Le couple name/valeur est ce qui voyage dans la requête ; sans name, le champ est ignoré.

Quel type de champ pour une note sur 20 bornée ?

type="number" avec min et max donne un contrôle adapté et des bornes.

Pourquoi un placeholder ne remplace-t-il pas un label ?

Le texte d’aide doit rester visible et associé au champ : c’est le rôle du label.

Que fait la validation HTML côté client ?

Elle est contournable : elle rend service au visiteur, mais ne protège rien.

Comment insérer un commentaire d’utilisateur sans risque ?

textContent traite la valeur comme du texte ; innerHTML l’interpréterait comme du HTML.

Quel remplacement doit être fait en premier lors de l’échappement ?

Commencer par & évite de ré-échapper les entités créées par les remplacements suivants.

9. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Champ sans name : il s’affiche, mais rien n’arrive au serveur.
  • Formulaire de modification en GET : l’action se rejoue à chaque rechargement.
  • Placeholder utilisé comme étiquette : l’information disparaît à la première frappe.
  • Validation uniquement en JavaScript : désactiver le script contourne tout.
  • Insérer une saisie avec innerHTML : la donnée devient du code exécutable.

10. Méthodologie de résolution

Construire et sécuriser un formulaire
  1. Fixez action et méthode avant d’ajouter le premier champ.
  2. Étiquetez chaque champ avec un label relié par for/id.
  3. Choisissez le bon type et ajoutez les contraintes natives (bornes, longueur, motif).
  4. Réécrivez les mêmes règles côté serveur : c’est la seule validation qui compte.
  5. Échappez à l’affichage toute donnée venue de l’extérieur, ou affichez-la en texte.

11. Révision active

Résumé essentiel
  • Un formulaire est une requête préparée : action pour la destination, method pour le transport.
  • Seul un champ porteur d’un name est transmis ; l’id sert au navigateur.
  • Le type du champ adapte le clavier et les contrôles : email, number, date, password, checkbox, radio.
  • Chaque champ a une étiquette reliée par for ; le placeholder n’en est pas une.
  • La validation HTML aide l’utilisateur ; la validation serveur est la seule qui protège.
  • Une donnée utilisateur s’affiche en texte (textContent) ou après échappement des caractères sensibles.

Checklist de maîtrise

  • Je construis un formulaire complet, étiquettes et contraintes comprises.
  • Je choisis le type de champ adapté à chaque donnée.
  • J’explique pourquoi la validation côté client ne suffit pas.
  • J’échappe une entrée utilisateur avant de l’insérer dans une page.
