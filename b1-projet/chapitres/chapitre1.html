Chapitre 1 — Cadrage du projet

Module 1 ≈ 1 h 30 de travail Accès libre
Mise en situation

Tout projet informatique réussi commence bien avant d’écrire la première ligne de code : il naît d’un besoin métier concret. Ici, un commerçant gère son inventaire sur des carnets papier ou des classeurs Excel fragiles : les ruptures de stock sont fréquentes et les erreurs de saisie quotidiennes. Le projet tutoré consiste à concevoir et livrer une application robuste de gestion de stock. Pour réussir, l’ingénieur doit cadrer le besoin, choisir une architecture en couches claire (interface graphique, logique métier, persistance en base) et préparer un environnement de développement reproductible.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. cadrer le besoin fonctionnel d’une application de gestion de stock ;
  2. comprendre l’architecture en couches : Interface (Tkinter) ↔ Logique (Python) ↔ Base de données (PostgreSQL) ;
  3. relier chaque objectif pédagogique à son concept informatique (POO, CRUD, exceptions, persistance) ;
  4. vérifier les prérequis et configurer un environnement reproductible (requirements.txt, README.md).

1. Présentation, besoin métier et objectifs

Le projet tutoré met en pratique l’ensemble des compétences acquises en première année à travers un cas d’entreprise réaliste : automatiser la gestion d’un stock de produits. Pour y parvenir, l’application s’articule autour d’une architecture découplée en trois responsabilités fondamentales :

  • L’interface graphique (IHM) : réalisée avec la bibliothèque native Tkinter, elle offre des formulaires de saisie et des tableaux visuels conviviaux pour l’utilisateur final ;
  • La logique métier orientée objet : codée en Python (classes Database et ApplicationGestionStock), elle valide les règles de gestion (prix positifs, quantités entières) ;
  • La persistance fiable des données : déléguée au SGBD relationnel PostgreSQL, pour garantir que les données restent intactes même après extinction de l’ordinateur.

Les opérations fondamentales à implémenter constituent le cycle CRUD universel : Create (ajouter un produit), Read (consulter la liste), Update (modifier un prix ou une quantité), Delete (retirer une référence). Le cours met un accent particulier sur la gestion robuste des exceptions (erreurs de connexion SQL, saisie de texte à la place d’un nombre) et la modularité du code.

Pourquoi cette architecture en couches ?

Séparer l’affichage (Tkinter) de la base de données (PostgreSQL) permet une maintenance aisée : si demain l’entreprise décide de remplacer la fenêtre de bureau par une application Web ou mobile, toute la logique de base de données et les règles de stock restent 100 % réutilisables sans modification.

Mnémotechnique — « Une classe pour l’écran, une classe pour la base »

Deux classes, deux mondes : Database parle SQL via le pilote psycopg2 ; ApplicationGestionStock parle à l’utilisateur via Tkinter. Le fichier main.py les initialise et orchestre leur rencontre.

2. Installer l'environnement

Vérifier Python : python3 --version — sinon sudo apt install python3 python3-pip. PostgreSQL : sudo apt install postgresql postgresql-contrib puis sudo service postgresql start. Tkinter : sudo apt install python3-tk — vérifiable avec python3 -m tkinter. Configuration de la base : sudo -u postgres psql, ALTER USER postgres WITH PASSWORD 'postgres', puis CREATE DATABASE gestion_stock.

La dépendance Python tient en une ligne dans requirements.txt : psycopg2-binary==2.9.9, installée par pip install -r requirements.txt. Un requirements.txt versionné, c'est un projet que n'importe qui peut installer.

Confusions d'examen
  • psycopg2 est le PONT Python-PostgreSQL ; Tkinter ne parle pas SQL.
  • La version minimale est 3.7 : 3.6 refuse, 3.10 passe.
  • La base se nomme gestion_stock : créer la base AVANT de lancer l'application.
  • Le README fait partie du livrable : un projet sans documentation est incomplet.

3. La structure du projet

Quatre fichiers, quatre rôles : main.py — l'interface principale (fenêtre, formulaire, tableau) ; database.py — la classe Database qui encapsule toute la gestion PostgreSQL ; requirements.txt — les dépendances ; README.md — la documentation. Cette séparation n'est pas décorative : on peut changer d'interface sans toucher à la base, et tester la base sans ouvrir la fenêtre.

Vérifier dans l’atelier
  • Le classeur des compétences : interface → tkinter, connexion → postgres, operations → crud, classes → poo.
  • Le testeur de prérequis : version -ge 37, tkinter et psql = oui — trois conditions en ET.
  • La structure : main → interface, database → database, requirements → deps, readme → doc.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Coder l'interface et le SQL dans le même fichier : séparer main.py et database.py.
  • Oublier d'installer python3-tk : l'import tkinter échoue.
  • Lancer l'application avant de créer la base gestion_stock.
  • Omettre requirements.txt : le projet ne s'installe plus ailleurs.
