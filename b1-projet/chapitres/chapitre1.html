Chapitre 1 — Cadrage du projet

Mise en situation

Tout projet informatique réussi commence bien avant d’écrire la première ligne de code : il naît d’un besoin métier concret. Ici, un commerçant gère son inventaire sur des carnets papier ou des classeurs Excel fragiles : les ruptures de stock sont fréquentes et les erreurs de saisie quotidiennes. Le projet tutoré consiste à concevoir et livrer une application robuste de gestion de stock. Pour réussir, l’ingénieur doit cadrer le besoin, choisir une architecture en couches claire (interface graphique, logique métier, persistance en base) et préparer un environnement de développement reproductible.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. cadrer le besoin fonctionnel d’une application de gestion de stock ;
  2. comprendre l’architecture en couches : Interface (Tkinter) <-> Logique (Python) <-> Base de données (PostgreSQL) ;
  3. relier chaque objectif pédagogique à son concept informatique (POO, CRUD, exceptions, persistance) ;
  4. vérifier les prérequis et configurer un environnement reproductible (requirements.txt, README.md).

1. Présentation, besoin métier et objectifs

Le projet tutoré met en pratique l’ensemble des compétences acquises en première année à travers un cas d’entreprise réaliste : automatiser la gestion d’un stock de produits. Pour y parvenir, l’application s’articule autour d’une architecture découplée en trois responsabilités fondamentales :

  • L’interface graphique (IHM) : réalisée avec la bibliothèque native Tkinter, elle offre des formulaires de saisie et des tableaux visuels conviviaux pour l’utilisateur final ;
  • La logique métier orientée objet : codée en Python (classes Database et ApplicationGestionStock), elle valide les règles de gestion (prix positifs, quantités entières) ;
  • La persistance fiable des données : déléguée au SGBD relationnel PostgreSQL, pour garantir que les données restent intactes même après extinction de l’ordinateur.

Les opérations fondamentales à implémenter constituent le cycle CRUD universel : Create (ajouter un produit), Read (consulter la liste), Update (modifier un prix ou une quantité), Delete (retirer une référence). Le cours met un accent particulier sur la gestion robuste des exceptions (erreurs de connexion SQL, saisie de texte à la place d’un nombre) et la modularité du code.

Pourquoi cette architecture en couches ?

Séparer l’affichage (Tkinter) de la base de données (PostgreSQL) permet une maintenance aisée : si demain l’entreprise décide de remplacer la fenêtre de bureau par une application Web ou mobile, toute la logique de base de données et les règles de stock restent 100 % réutilisables sans modification.

Mnémotechnique — « Une classe pour l’écran, une classe pour la base »

Deux classes, deux mondes : Database parle SQL via le pilote psycopg2 ; ApplicationGestionStock parle à l’utilisateur via Tkinter. Le fichier main.py les initialise et orchestre leur rencontre.

2. Installer l'environnement

Vérifier Python : python3 --version — sinon sudo apt install python3 python3-pip. PostgreSQL : sudo apt install postgresql postgresql-contrib puis sudo service postgresql start. Tkinter : sudo apt install python3-tk — vérifiable avec python3 -m tkinter. Configuration de la base : sudo -u postgres psql, ALTER USER postgres WITH PASSWORD 'postgres', puis CREATE DATABASE gestion_stock.

La dépendance Python tient en une ligne dans requirements.txt : psycopg2-binary==2.9.9, installée par pip install -r requirements.txt. Un requirements.txt versionné, c'est un projet que n'importe qui peut installer.

Confusions d'examen
  • psycopg2 est le PONT Python-PostgreSQL ; Tkinter ne parle pas SQL.
  • La version minimale est 3.7 : 3.6 refuse, 3.10 passe.
  • La base se nomme gestion_stock : créer la base AVANT de lancer l'application.
  • Le README fait partie du livrable : un projet sans documentation est incomplet.

3. La structure du projet

Quatre fichiers, quatre rôles : main.py — l'interface principale (fenêtre, formulaire, tableau) ; database.py — la classe Database qui encapsule toute la gestion PostgreSQL ; requirements.txt — les dépendances ; README.md — la documentation. Cette séparation n'est pas décorative : on peut changer d'interface sans toucher à la base, et tester la base sans ouvrir la fenêtre.

Vérifier dans l’atelier
  • Le classeur des compétences : interface → tkinter, connexion → postgres, operations → crud, classes → poo.
  • Le testeur de prérequis : version -ge 37, tkinter et psql = oui — trois conditions en ET.
  • La structure : main → interface, database → database, requirements → deps, readme → doc.

4. Du cahier des charges au planning

Avant le code, le cahier des charges fixe ce que l’application doit faire, et ce qu’elle ne fera pas. Pour la gestion de stock, il tient en quelques lignes :

  • Périmètre : un seul utilisateur, une seule boutique, une base PostgreSQL locale ;
  • Fonctions : ajouter, lister, modifier, supprimer un produit (CRUD), enregistrer un mouvement de stock, signaler les produits sous le seuil, exporter en CSV ;
  • Contraintes : Python 3.7+, Tkinter, psycopg2, prix exacts à deux décimales ;
  • Critères d’acceptation : chaque fonction se démontre en moins de trente secondes, sans erreur non traitée.

On découpe ensuite en petites tâches ordonnées : base de données, module database.py, écran Tkinter, logique de stock, export, livraison. Chaque tâche se termine par une démonstration qui prouve qu’elle fonctionne.

5. Versionner le projet avec Git

Un projet livrable est un projet versionné. Git garde l’historique, permet de revenir en arrière et rend le travail à plusieurs possible. Séquence minimale :

git init
git add main.py database.py requirements.txt README.md
git commit -m "Structure initiale du projet"
git switch -c fonction-export-csv
# ... travail, tests, puis :
git commit -am "Ajout de l'export CSV"
git switch main
git merge fonction-export-csv

Un fichier .gitignore exclut ce qui ne se versionne pas : __pycache__/, les environnements virtuels et surtout les mots de passe. Un message de commit décrit pourquoi le changement existe, à l’impératif ou au passé, mais de façon cohérente.

Exercice 1 — Le cahier des charges de la librairie Sésame

Étude de cas Formative Niveau 1 — Acquisition

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Cadrer le besoin d'un client : lire un cahier des charges simplifié, délimiter le périmètre et retenir les critères de succès.

Énoncé. Mme Adjovi tient la librairie-papeterie Sésame, rue du Commerce à Lomé. Elle note encore tout dans un cahier : les ruptures de stylos sont fréquentes, les erreurs de saisie aussi. Elle confie le problème à une petite équipe : Inès, cheffe de projet, et Kofi, développeur. Première étape du projet : le cadrage. Inès rencontre Mme Adjovi, observe le comptoir et rédige le cahier des charges simplifié :

Fonction demandéeDans le périmètre ?
Enregistrer les produits (nom, catégorie, quantité, prix)Oui
Suivre les entrées et les sorties de stockOui
Signaler les produits qui passent sous un seuil d'alerteOui
Gérer la paie des employés de la librairieNon
Vendre les livres sur InternetNon

Utilisatrices prévues : Mme Adjovi et sa vendeuse, deux personnes qui ne sont pas expertes en informatique. Inès et Mme Adjovi conviennent aussi de trois critères de succès : saisir un produit en moins d'une minute ; signaler toute rupture avant l'ouverture du magasin ; conserver les données même après une coupure de courant.

  1. Combien de fonctions du tableau sont dans le périmètre du projet ?
  2. Combien de personnes utiliseront l'application au quotidien ?
  3. La gestion de la paie fait-elle partie du projet ? Répondez par oui ou non.
  4. Quel outil Mme Adjovi utilise-t-elle aujourd'hui pour suivre son stock ? Répondez en un seul mot.
  5. Combien de critères de succès Inès et Mme Adjovi ont-elles convenus ?
  6. Quel critère de succès répond à une coupure de courant : la rapidité, la persistance des données ou les alertes ?
Cas d’exemple
M. Diallo tient la boulangerie « Le Fournil ». Il gère ses ventes de mémoire.
Cahier des charges : encaisser les ventes (oui), suivre les invendus (oui),
livrer à domicile (non). Utilisateurs : M. Diallo et son apprenti.
Critères de succès : encaisser une vente en moins de trente secondes ;
savoir chaque soir combien de baguettes restent.

1) Fonctions dans le périmètre : 2 (encaisser, suivre les invendus).
2) Utilisateurs au quotidien : 2 (M. Diallo et son apprenti).
3) La livraison à domicile est hors périmètre : non.
4) Outil actuel : la mémoire de M. Diallo — il ne note rien.
Trois indices, rédigés en mots
  1. Le périmètre d'un projet est la liste des fonctions que l'équipe s'engage à livrer : repérez les lignes marquées Oui.
  2. Les utilisateurs sont ceux qui manipuleront l'application chaque jour ; les critères de succès sont les promesses mesurables du cadrage.
  3. Pour la question 4, relisez la première phrase de l'énoncé ; pour la question 6, demandez-vous ce qui protège les données quand le courant s'arrête.

Exercice 2 — Les postes prêts pour le développement

Étude de cas Formative Niveau 1 — Acquisition

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Vérifier les prérequis d'un poste de développement (Python 3.7+, Tkinter, PostgreSQL) machine par machine.

Énoncé. Avant d'écrire la moindre ligne de code, Kofi vérifie les machines qui feront tourner le projet. Les prérequis du tutoriel sont stricts : Python 3.7 ou supérieur, Tkinter installé, PostgreSQL installé — les trois conditions ensemble. Voici l'état des postes :

PostePythonTkinterPostgreSQL
Comptoir de la librairie3.8ouioui
Arrière-boutique3.6ouioui
Portable d'Inès3.10ouinon

  1. Combien de postes satisfont les trois prérequis à la fois ?
  2. Quelle est la version minimale de Python exigée par le tutoriel ? (format 3.7)
  3. Le poste de l'arrière-boutique peut-il lancer le projet ? Répondez par oui ou non.
  4. Le portable d'Inès peut-il lancer le projet ? Répondez par oui ou non.
  5. Quel nom porte la base de données que l'équipe doit créer ? (un seul mot, avec un tiret bas)
Cas d’exemple
Un fablab prépare un projet qui exige Python 3.8 ou plus, Flask et MySQL.
- poste A : Python 3.9, Flask oui, MySQL oui
- poste B : Python 3.8, Flask non, MySQL oui
- poste C : Python 3.12, Flask oui, MySQL oui

1) Postes prêts : A et C, soit 2 postes sur 3.
2) Le poste B refuse : il manque Flask.
3) Version minimale exigée : 3.8 — un prérequis manquant disqualifie le poste.
Trois indices, rédigés en mots
  1. Un poste est prêt seulement si les trois prérequis sont vrais en même temps : la version de Python, Tkinter, PostgreSQL.
  2. Comparez chaque version de Python à l'exigence minimale de l'énoncé : en dessous, le poste refuse ; la branche 2.7 est hors sujet.
  3. Pour la dernière question, le nom de la base du tutoriel s'écrit en un seul « mot », avec un tiret bas, sans espace.

Exercice 3 — Quatre fichiers, quatre rôles

Étude de cas Formative Niveau 2 — Application

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Associer chaque fichier du projet (main.py, database.py, requirements.txt, README.md) à son rôle et nommer les couches de l'architecture.

Énoncé. Inès fixe la structure du projet avant la première ligne de code. L'application s'articule en trois couches : l'interface graphique (Tkinter), la logique métier (Python) et la base de données (PostgreSQL). Quatre fichiers, quatre rôles :

FichierRôle
main.pyl'interface principale : fenêtre, formulaire, tableau des produits
database.pyla classe Database : toute la gestion PostgreSQL, tout le SQL
requirements.txtla liste des dépendances à installer (psycopg2-binary)
README.mdla documentation du projet

Le projet doit notamment permettre les quatre opérations CRUD sur les produits, et la séparation des fichiers doit permettre de changer d'écran sans toucher au SQL.

  1. Dans quel fichier vit la classe Database ?
  2. Quel fichier liste les dépendances à installer avec pip ?
  3. Quelle couche de l'architecture affiche les fenêtres et reçoit les clics ? (un seul mot)
  4. Que signifie la lettre C de CRUD ? (un mot anglais)
  5. Quel SGBD relationnel assure la persistance des données ?
  6. Peut-on changer l'interface sans modifier le fichier du SQL ? Répondez par oui ou non.
Cas d’exemple
Une épicerie commande une petite application. Structure retenue :
- ecran.py : la fenêtre de saisie des articles
- bdd.py : la classe qui parle à SQLite
- besoins.txt : la liste des paquets à installer
- notice.md : le mode d'emploi

1) La classe de la base vit dans bdd.py.
2) Les dépendances sont dans besoins.txt.
3) La couche qui affiche : l'interface.
4) Le SGBD : SQLite.
Trois indices, rédigés en mots
  1. Chaque fichier a un seul métier : l'écran, le SQL, les dépendances, la documentation — dans cet ordre du tableau.
  2. Les trois couches se lisent de l'utilisateur vers la machine : ce qu'on voit, ce qui décide, ce qui conserve.
  3. CRUD est l'acronyme de quatre opérations ; chaque lettre ouvre un verbe anglais qui correspond à une requête SQL précise.

8. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Coder l'interface et le SQL dans le même fichier : séparer main.py et database.py.
  • Oublier d'installer python3-tk : l'import tkinter échoue.
  • Lancer l'application avant de créer la base gestion_stock.
  • Omettre requirements.txt : le projet ne s'installe plus ailleurs.

9. Méthodologie de résolution

Méthode — démarrer le projet en trois gestes
  1. Vérifier : python3 --version, python3 -m tkinter, service postgresql status.
  2. Installer : python3-pip, postgresql-contrib, psycopg2-binary ; créer la base gestion_stock.
  3. Poser la structure : main.py, database.py, requirements.txt, README.md.
