Chapitre 2 — La base de données

Module 2 ≈ 2 h de travail Réservé B1 et plus
Mise en situation

La classe Database est le pont vers PostgreSQL : elle se connecte, crée la table produits si elle n'existe pas, et offre quatre méthodes CRUD. Chaque méthode vit dans un try/except — parce qu'un serveur éteint, un mot de passe faux ou une requête maladroite ne demandent qu'à arriver.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. décrire la table produits : id SERIAL, nom et categorie VARCHAR, quantite INTEGER, prix DECIMAL(10,2) ;
  2. expliquer la connexion : psycopg2.connect, cursor, gestion des erreurs par try/except ;
  3. utiliser CREATE TABLE IF NOT EXISTS et comprendre commit ;
  4. relier chaque opération CRUD à sa requête : INSERT, SELECT, UPDATE, DELETE ;
  5. fermer proprement : cursor.close, connection.close.

1. La table produits

Cinq colonnes : id — identifiant unique, clé primaire auto-incrémentée (SERIAL PRIMARY KEY) ; nom — VARCHAR(100) NOT NULL ; categorie — VARCHAR(50) ; quantite — INTEGER NOT NULL ; prix — DECIMAL(10,2) NOT NULL. Le CREATE TABLE IF NOT EXISTS rend le premier lancement idempotent : la table ne se recrée pas à chaque démarrage.

\n

Pourquoi DECIMAL et non FLOAT pour le prix : DECIMAL(10,2) stocke exactement deux décimales — 2500.50 reste 2500.50, sans arrondi binaire. La précision monétaire n'est pas négociable.

\n
Mnémotechnique — « SERIAL compte, VARCHAR écrit, INTEGER compte en stock, DECIMAL coûte »

Cinq colonnes, cinq types : la grille attendue à l'examen.

2. Connexion et gestion des erreurs

La méthode connecter() appelle psycopg2.connect(host, database, user, password), récupère un cursor, affiche le succès et renvoie True ; en cas d'Error, elle affiche le problème et renvoie False. Ce pattern try/except recommence dans chaque méthode : le programme ne plante jamais, il rapporte.

\n

Après toute écriture (INSERT, UPDATE, DELETE), la méthode appelle self.connection.commit() : sans commit, PostgreSQL annule la modification à la déconnexion. La deconnecter() ferme le cursor puis la connexion — dans cet ordre.

\n
Confusions d'examen
    \n
  • SELECT lit : fetchall ; INSERT/UPDATE/DELETE écrivent : commit.
    • \n
  • Sans commit, la modification est perdue à la fermeture : piège classique.
    • \n
  • Le try/except renvoie False : l'application continue, elle ne s'arrête pas.
    • \n
  • CREATE TABLE IF NOT EXISTS : le second lancement ne duplique rien.
    • \n

3. Les quatre requêtes CRUD

Create — INSERT INTO produits (nom, categorie, quantite, prix) VALUES (%s, %s, %s, %s) avec les valeurs passées en paramètre ; Read — SELECT * FROM produits ORDER BY id puis fetchall() ; Update — UPDATE produits SET nom=%s, categorie=%s, quantite=%s, prix=%s WHERE id=%s ; Delete — DELETE FROM produits WHERE id=%s.

\n

Les %s sont des requêtes paramétrées : psycopg2 échappe les valeurs. Concaténer du SQL à la main ouvre la porte à l'injection — le paramétrage n'est pas une option, c'est la seule façon.

\n
Vérifier en Bash
    \n
  • Le schéma : id → serial, nom/categorie → varchar, quantite → integer, prix → decimal.
    • \n
  • La connexion : serveur/mdp/base dans l'ordre, sortie au premier ko.
    • \n
  • Le cycle CRUD : create→insert, read→select, update→update, delete→delete.
    • \n

Exercice 2 — Connexion PostgreSQL : oui ou non ?

Bash Niveau 2 — Application

Objectif : Décider si la connexion peut s'établir et réagir comme la méthode connecter().

La méthode connecter() du tutoriel tente la connexion et renvoie True en cas de succès, False en cas d'échec (exception Error). Le script lit n lignes « service etat » : service est un code parmi serveur, mdp, base — etat vaut ok ou ko. Si les trois services sont ok, il affiche connexion reussie ; dès qu'un service est ko, il affiche erreur : service et s'arrête (comme le try/except qui renvoie False au premier problème).

Entrée du programme
serveur ok
mdp ok
base ok
Sortie attendue
connexion reussie
Deux indices, rédigés en mots
  1. Dès que etat vaut ko : echo "erreur : $service" puis exit 0.
  2. Si la boucle se termine sans défaut, afficher le verdict de succès.

Exercice 3 — L'ordre des opérations SQL

Bash Niveau 3 — Raisonnement

Objectif : Remettre chaque ordre CRUD devant sa requête SQL et valider l'ordre du cycle.

Le script lit 4 lignes « operation sql » dans l'ordre du cycle : le script doit vérifier que l'étape 1 est create (requête attendue insert), l'étape 2 read (select), l'étape 3 update (update) et l'étape 4 delete (delete). Pour chaque ligne il affiche etape N : OK quand l'opération ET sa requête sont justes, sinon etape N : NON, puis etapes correctes : X/4.

Entrée du programme
create insert
read select
update update
delete delete
Sortie attendue
etape 1 : OK
etape 2 : OK
etape 3 : OK
etape 4 : OK
etapes correctes : 4/4
Deux indices, rédigés en mots
  1. Un case sur le numéro : 1 → create/insert, 2 → read/select, 3 → update/update, 4 → delete/delete.
  2. Les deux conditions doivent être vraies en même temps : operation ET sql.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Concaténer les valeurs dans le SQL : requêtes paramétrées obligatoires.
  • Oublier commit après INSERT : la ligne n'est pas vraiment écrite.
  • Mettre FLOAT pour le prix : DECIMAL(10,2) est exact, FLOAT arrondit.
  • Supprimer sans WHERE : la table entière disparaît.

7. Méthodologie de résolution

Méthode — écrire une méthode Database en trois gestes
  1. Ouvrir un try : exécuter la requête paramétrée avec le cursor.
  2. Commit si écriture, fetchall si lecture ; renvoyer le résultat ou True.
  3. Except Error : afficher le problème, renvoyer False ou [] — jamais de crash.

8. Révision active

Résumé essentiel

Les 8 notions à connaître absolument

  1. SERIAL : entier auto-incrémenté de PostgreSQL.
  2. DECIMAL(10,2) : décimal exact à deux décimales.
  3. cursor : objet qui exécute les requêtes et lit les résultats.
  4. commit : validation des écritures sur la connexion.
  5. fetchall : récupère toutes les lignes d'un SELECT.
  6. Requête paramétrée : %s passés séparément, échappés par psycopg2.
  7. CREATE TABLE IF NOT EXISTS : création idempotente.
  8. Error (psycopg2) : exception attrapée par chaque try/except.
