Chapitre 3 — L'interface Tkinter

Mise en situation

La fenêtre est le visage du projet : un écran de connexion vers PostgreSQL, puis l'écran principal avec formulaire d'ajout, boutons d'action et tableau des produits. Le tutoriel construit cet enchaînement widget par widget — et protège chaque saisie avant qu'elle n'atteigne la base.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. décrire l'architecture : interface de connexion, puis interface principale ;
  2. nommer les widgets : Label, Entry, Button, Frame, LabelFrame, Treeview, Scrollbar ;
  3. placer avec pack et grid, lier la sélection du Treeview avec bind ;
  4. choisir la bonne messagebox : showinfo, showwarning, showerror, askyesno ;
  5. valider les champs avant tout appel à la base (nom, quantite, prix).

1. Prérequis intégré : Initiation progressive à l’interface graphique Tkinter

Niveau 1 — Intuition : Fenêtre principale, composants (Widgets) et événements (Callbacks)

La bibliothèque standard tkinter (et son sous-module stylisé ttk) permet de créer une interface de bureau en quatre étapes simples :

  1. Fenêtre racine : fenetre = tk.Tk() crée la fenêtre et fenetre.mainloop() lance la boucle d’écoute des clics ;
  2. Widgets de base : tk.Label affiche un texte fixe, tk.Entry crée un champ de saisie (lu avec .get()), et tk.Button(..., command=fonction) déclenche une fonction Python au clic (callback) ;
  3. Placement : .pack() empile les éléments verticalement ou horizontalement, tandis que .grid(row=..., column=...) les aligne dans un tableau ;
  4. Tableau de données : ttk.Treeview(fenetre, columns=(...), show="headings") affiche la liste des articles du stock sous forme de table multi-colonnes.

2. Deux écrans, une fenêtre

L'application ApplicationGestionStock s'ouvre sur l'interface de connexion : champs host, database, user, password préremplis, bouton « Se connecter ». Si db.connecter() réussit, la méthode crée la table, détruit le frame de connexion (destroy()) et affiche l'interface principale : formulaire d'ajout/modification, boutons Ajouter / Modifier / Supprimer, tableau des produits. En cas d'échec : messagebox.showerror et on reste sur l'écran de connexion.

La fenêtre se termine proprement : root.protocol("WM_DELETE_WINDOW", fermer_application) appelle db.deconnecter() avant root.destroy() — la base est fermée avant l'écran.

Mnémotechnique — « d'abord la porte, ensuite la salle »

Écran 1 : se connecter. Écran 2 : travailler. La fenêtre ne détruit jamais l'écran actif avant d'avoir bâti le suivant.

3. Widgets, layout et tableau

Les widgets : Label (texte), Entry (saisie), Button (action avec command=), Frame et LabelFrame (cadres titrés), ttk.Treeview (tableau multi-colonnes), Scrollbar (ascenseur relié par yscrollcommand). Le layout : pack empile, grid place en lignes/colonnes avec sticky et padx/pady.

Le Treeview définit ses colonnes (« ID », « Nom », « Catégorie », « Quantité », « Prix »), leurs en-têtes (heading) et largeurs ; le clic sur une ligne déclenche selectionner_produit via bind("<ButtonRelease-1>", …), qui remplit le formulaire. actualiser_tableau() efface le tableau puis le recharge depuis obtenir_tous_produits() : la base reste la source unique de vérité.

Confusions d'examen
  • pack empile, grid place en grille : les deux ne se mélangent pas dans un même conteneur.
  • command= appelle la méthode du bouton : pas de parenthèses, la référence suffit.
  • Le Treeview n'est pas la base : il se recharge depuis fetchall à chaque changement.
  • bind relie un événement souris à une méthode : c'est le clic qui remplit le formulaire.

4. Validation et boîtes de dialogue

Avant tout appel à la base, ajouter_produit() vérifie : champs obligatoires non vides (nom, quantite, prix) sinon showwarning ; puis int(quantite) et float(prix) dans un try — une ValueError provoque showerror « Quantité et prix doivent être des nombres ». La validation vivant dans l'interface, la base ne reçoit jamais de donnée absurde.

Les quatre boîtes de dialogue : showinfo — succès (« Produit ajouté avec succès ») ; showwarning — champs manquants ou sélection absente ; showerror — échec de connexion, conversion impossible ; askyesno — confirmation avant suppression (« Voulez-vous vraiment supprimer… ? »), la suppression n'a lieu que si l'utilisateur répond oui.

Vérifier dans l’atelier
  • Les familles : entry/label/button/treeview → widget, pack/grid → layout, messagebox → boite.
  • La validation : nom refuse le vide, quantite et prix testent nombre positif.
  • Les dialogues : succès → showinfo, attention → showwarning, échec → showerror, suppression → askyesno.

5. Séparer modèle, vue et contrôleur

Le projet applique, sans le dire, le principe MVC : le modèle est database.py (accès aux données), la vue est l’interface Tkinter (widgets), le contrôleur est l’ensemble des fonctions appelées par les boutons, qui valident la saisie puis délèguent au modèle. Un écran ne contient jamais de SQL.

# Modèle (database.py)
def ajouter(self, nom, categorie, quantite, prix):
    self.cursor.execute(
        "INSERT INTO produits (nom, categorie, quantite, prix) VALUES (%s, %s, %s, %s)",
        (nom, categorie, quantite, prix))
    self.conn.commit()

# Contrôleur (main.py), appelé par le bouton
def on_ajouter(self):
    nom = self.champ_nom.get().strip()
    if not nom:
        messagebox.showwarning("Saisie", "Le nom est obligatoire")
        return
    self.db.ajouter(nom, self.champ_cat.get(), int(self.champ_qte.get()), self.champ_prix.get())
    self.rafraichir_tableau()

Les valeurs passent toujours par les paramètres %s de psycopg2, jamais par concaténation : c’est la protection contre l’injection SQL. En PHP, le même rôle est tenu par les requêtes préparées de PDO ; la règle est identique quel que soit le langage.

Exercice 1 — Les widgets de l'écran principal

Étude de cas Formative Niveau 1 — Acquisition

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Nommer les widgets Tkinter d'une maquette d'écran : Label, Entry, Button, Listbox, Treeview.

Énoncé. Troisième étape : l'interface. Kofi dessine sur papier l'écran principal de l'application, puis le décrit à Inès :

Zone de l'écranÉlément affiché
Ligne 1texte « Nom du produit », puis une zone pour taper le nom
Ligne 2texte « Catégorie », puis une zone pour taper la catégorie
Ligne 3texte « Quantité », puis une zone pour taper la quantité
Ligne 4texte « Prix », puis une zone pour taper le prix
En bas du formulaireun bouton « Ajouter » qui déclenche l'ajout au clic
Centre de la fenêtrele tableau des produits en cinq colonnes (ID, Nom, Catégorie, Quantité, Prix)

Rappel des widgets du cours : Label (texte fixe), Entry (saisie d'une ligne), Button (bouton d'action), Listbox (liste simple, une colonne), ttk.Treeview (tableau multi-colonnes).

  1. Quel widget crée la zone où la vendeuse tape le nom du produit ? (un mot anglais)
  2. Quel widget affiche le texte fixe « Nom du produit » ? (un mot anglais)
  3. Quel widget déclenche l'ajout quand on clique dessus ? (un mot anglais)
  4. Quel widget ttk affiche le tableau des produits en cinq colonnes ? (un mot anglais)
  5. Quel widget simple affiche une liste à une colonne, sans prix ni quantités ? (un mot anglais)
  6. Quelle méthode lit le contenu tapé dans un Entry ? (un seul mot, sans parenthèses)
Cas d’exemple
L'épicerie d'à côté ouvre son application par un écran de connexion :
texte « Identifiant » + une zone de saisie ;
texte « Mot de passe » + une zone de saisie ;
un bouton « Se connecter » ;
une liste des trois dernières caisses clôturées.

1) Les zones de saisie : des Entry (2).
2) Les textes : des Label.
3) Le bouton : un Button.
4) La liste des caisses : une Listbox.
5) Le contenu d'un Entry se lit avec get().
Trois indices, rédigés en mots
  1. Un widget, un métier : afficher un texte, saisir une ligne, déclencher une action, présenter une liste ou un tableau.
  2. Le tableau des produits dépasse une simple colonne : le widget prévu par le cours vient du module ttk.
  3. Le contenu tapé dans un champ de saisie ne se lit pas par magie : une méthode très courte du widget le rend.

Exercice 2 — La grille du formulaire

Étude de cas Formative Niveau 2 — Application

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Placer des widgets avec grid (row, column), relier une action avec command et nommer le callback.

Énoncé. Pour aligner proprement le formulaire, Kofi choisit le gestionnaire grid : chaque widget occupe une cellule repérée par row (ligne) et column (colonne). Il interdit formellement de mélanger pack et grid dans un même conteneur. Maquette exacte du formulaire :

Colonne 0Colonne 1

Ligne 1Label « Catégorie »Entry categorie
Ligne 2Label « Quantité »Entry quantite
Ligne 3Label « Prix »Entry prix
Ligne 4(vide)Button « Ajouter »

Le bouton est câblé par Button(..., command=ajouter_produit) : on passe la référence de la fonction, sans parenthèses.

  1. Quel gestionnaire de placement organise les widgets en lignes et colonnes ? (un mot anglais)
  2. Dans quelle colonne se trouvent les quatre Entry ? (un nombre)
  3. Sur quelle ligne (row) se trouve le bouton « Ajouter » ? (un nombre)
  4. Peut-on mélanger pack et grid dans un même conteneur ? Répondez par oui ou non.
  5. Quel paramètre du Button désigne la fonction appelée au clic ? (un mot anglais)
  6. Comment appelle-t-on la fonction exécutée en réponse à un événement comme un clic ? (un mot anglais)
Cas d’exemple
Écran de connexion d'une épicerie, en grille :
ligne 0 : Label « Identifiant » / Entry identifiant
ligne 1 : Label « Mot de passe » / Entry motdepasse
ligne 2 : (vide) / Button « Entrer »

1) Gestionnaire : grid.
2) Les Entry sont en colonne 1.
3) Le bouton est en ligne 2.
4) Le bouton appelle sa fonction via command= ; la fonction déclenchée est le callback.
Trois indices, rédigés en mots
  1. La grille se lit comme un tableau : les lignes et les colonnes commencent à zéro, et la maquette les numérote.
  2. Deux gestionnaires de placement existent : celui qui empile et celui qui aligne en cellules ; ils ne partagent pas un conteneur.
  3. Le paramètre du bouton reçoit la référence de la fonction, sans parenthèses ; la fonction déclenchée par l'événement porte un nom anglais précis.

Exercice 3 — Protéger les saisies de la vendeuse

Étude de cas Formative Niveau 3 — Raisonnement

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Choisir la bonne boîte de dialogue (showinfo, showwarning, showerror, askyesno) et prévoir l'exception d'une conversion ratée.

Énoncé. Mme Adjovi tape vite et se trompe parfois. Avant tout appel à la base, l'application valide les champs : obligatoires non vides, puis conversion de la quantité en entier et du prix en nombre, dans un try. Kofi rédige les scénarios de tests et choisit la boîte de dialogue adaptée à chaque situation :

N°Situation testéeBoîte attendue
1La vendeuse valide le formulaire sans avoir tapé le nom?
2Elle tape « douze » dans le champ quantité : la conversion échoue?
3Le produit est enregistré dans la base?
4Elle demande la suppression d'un produit sélectionné?
5La connexion à PostgreSQL échoue au démarrage?

Rappel : showinfo (information de succès), showwarning (attention, on peut corriger), showerror (échec), askyesno (question oui/non).

  1. Quelle boîte convient à la situation 1 ? (un mot anglais)
  2. Quelle boîte convient à la situation 2 ? (un mot anglais)
  3. Quelle boîte annonce le succès de la situation 3 ? (un mot anglais)
  4. Quelle boîte pose la question oui/non de la situation 4 ? (un mot anglais)
  5. Quelle exception Python lève la conversion du texte « douze » en entier ? (un mot anglais)
  6. La validation des champs a-t-elle lieu avant ou après l'appel à la base ? (un mot)
Cas d’exemple
L'application de l'épicerie affiche ses messages :
1) prix laissé vide à l'enregistrement : showwarning (avertissement, on peut corriger) ;
2) prix « abc » : la conversion échoue, ValueError, showerror ;
3) article enregistré : showinfo ;
4) suppression demandée : askyesno.

1) Champ vide : showwarning.
2) Conversion ratée : ValueError + showerror.
3) Suppression : confirmation par askyesno.
Trois indices, rédigés en mots
  1. Classez chaque situation : information, avertissement (on peut corriger), erreur (l'opération échoue), confirmation.
  2. La conversion d'un texte en nombre peut échouer : Python lève alors une exception dédiée aux valeurs inattendues.
  3. La règle du cours : la base ne doit jamais recevoir une donnée absurde — le garde-fou se place donc en amont de l'appel.

8. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Appeler la base sans validation : des quantités textuelles finissent en base.
  • Utiliser showinfo pour un échec de connexion : c'est showerror.
  • Laisser le formulaire rempli après une opération : effacer_champs() existe.
  • Oublier d'actualiser le tableau après un ajout : l'écran ment.

9. Méthodologie de résolution

Méthode — câbler une action en trois gestes
  1. Récupérer les champs et valider : vides refusés, nombres convertis dans un try.
  2. Appeler la méthode Database correspondante dans un if : succès ou messagebox.
  3. Effacer les champs et actualiser le tableau : l'écran reflète la base.

10. Révision active

Résumé essentiel
  • Deux écrans : connexion (destroy après succès), puis interface principale.
  • Widgets : Label, Entry, Button, Frame, Treeview, Scrollbar ; pack et grid.
  • Boîtes : showinfo (succès), showwarning (attention), showerror (échec), askyesno (confirmation).
  • Validation : champs non vides, int/float dans un try — la base reçoit du propre.

Checklist de maîtrise

  • Je décris l'enchaînement des deux écrans.
  • Je nomme chaque widget et son rôle.
  • Je choisis la bonne messagebox pour une situation.
  • Je valide les champs avant l'appel à la base.

Les 8 notions à connaître absolument

  1. Entry : champ de saisie d'une ligne.
  2. Treeview : tableau ttk multi-colonnes avec sélection.
  3. pack / grid : les deux gestionnaires de mise en page.
  4. bind : relier un événement souris/clavier à une méthode.
  5. messagebox : showinfo, showwarning, showerror, askyesno.
  6. command= : référence de la méthode déclenchée par un Button.
  7. effacer_champs : nettoyage du formulaire après opération.
  8. WM_DELETE_WINDOW : protocole de fermeture propre.
