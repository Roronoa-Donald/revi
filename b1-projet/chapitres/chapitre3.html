Chapitre 3 — L'interface Tkinter

Module 3 ≈ 2 h de travail Réservé B1 et plus
Mise en situation

La fenêtre est le visage du projet : un écran de connexion vers PostgreSQL, puis l'écran principal avec formulaire d'ajout, boutons d'action et tableau des produits. Le tutoriel construit cet enchaînement widget par widget — et protège chaque saisie avant qu'elle n'atteigne la base.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. décrire l'architecture : interface de connexion, puis interface principale ;
  2. nommer les widgets : Label, Entry, Button, Frame, LabelFrame, Treeview, Scrollbar ;
  3. placer avec pack et grid, lier la sélection du Treeview avec bind ;
  4. choisir la bonne messagebox : showinfo, showwarning, showerror, askyesno ;
  5. valider les champs avant tout appel à la base (nom, quantite, prix).

1. Prérequis intégré : Initiation progressive à l’interface graphique Tkinter

Niveau 1 — Intuition : Fenêtre principale, composants (Widgets) et événements (Callbacks)

La bibliothèque standard tkinter (et son sous-module stylisé ttk) permet de créer une interface de bureau en quatre étapes simples :

  1. Fenêtre racine : fenetre = tk.Tk() crée la fenêtre et fenetre.mainloop() lance la boucle d’écoute des clics ;
  2. Widgets de base : tk.Label affiche un texte fixe, tk.Entry crée un champ de saisie (lu avec .get()), et tk.Button(..., command=fonction) déclenche une fonction Python au clic (callback) ;
  3. Placement : .pack() empile les éléments verticalement ou horizontalement, tandis que .grid(row=..., column=...) les aligne dans un tableau ;
  4. Tableau de données : ttk.Treeview(fenetre, columns=(...), show="headings") affiche la liste des articles du stock sous forme de table multi-colonnes.

2. Deux écrans, une fenêtre

L'application ApplicationGestionStock s'ouvre sur l'interface de connexion : champs host, database, user, password préremplis, bouton « Se connecter ». Si db.connecter() réussit, la méthode crée la table, détruit le frame de connexion (destroy()) et affiche l'interface principale : formulaire d'ajout/modification, boutons Ajouter / Modifier / Supprimer, tableau des produits. En cas d'échec : messagebox.showerror et on reste sur l'écran de connexion.

La fenêtre se termine proprement : root.protocol("WM_DELETE_WINDOW", fermer_application) appelle db.deconnecter() avant root.destroy() — la base est fermée avant l'écran.

Mnémotechnique — « d'abord la porte, ensuite la salle »

Écran 1 : se connecter. Écran 2 : travailler. La fenêtre ne détruit jamais l'écran actif avant d'avoir bâti le suivant.

3. Widgets, layout et tableau

Les widgets : Label (texte), Entry (saisie), Button (action avec command=), Frame et LabelFrame (cadres titrés), ttk.Treeview (tableau multi-colonnes), Scrollbar (ascenseur relié par yscrollcommand). Le layout : pack empile, grid place en lignes/colonnes avec sticky et padx/pady.

Le Treeview définit ses colonnes (« ID », « Nom », « Catégorie », « Quantité », « Prix »), leurs en-têtes (heading) et largeurs ; le clic sur une ligne déclenche selectionner_produit via bind("<ButtonRelease-1>", …), qui remplit le formulaire. actualiser_tableau() efface le tableau puis le recharge depuis obtenir_tous_produits() : la base reste la source unique de vérité.

Confusions d'examen
  • pack empile, grid place en grille : les deux ne se mélangent pas dans un même conteneur.
  • command= appelle la méthode du bouton : pas de parenthèses, la référence suffit.
  • Le Treeview n'est pas la base : il se recharge depuis fetchall à chaque changement.
  • bind relie un événement souris à une méthode : c'est le clic qui remplit le formulaire.

4. Validation et boîtes de dialogue

Avant tout appel à la base, ajouter_produit() vérifie : champs obligatoires non vides (nom, quantite, prix) sinon showwarning ; puis int(quantite) et float(prix) dans un try — une ValueError provoque showerror « Quantité et prix doivent être des nombres ». La validation vivant dans l'interface, la base ne reçoit jamais de donnée absurde.

Les quatre boîtes de dialogue : showinfo — succès (« Produit ajouté avec succès ») ; showwarning — champs manquants ou sélection absente ; showerror — échec de connexion, conversion impossible ; askyesno — confirmation avant suppression (« Voulez-vous vraiment supprimer… ? »), la suppression n'a lieu que si l'utilisateur répond oui.

Vérifier dans l’atelier
  • Les familles : entry/label/button/treeview → widget, pack/grid → layout, messagebox → boite.
  • La validation : nom refuse le vide, quantite et prix testent nombre positif.
  • Les dialogues : succès → showinfo, attention → showwarning, échec → showerror, suppression → askyesno.

Exercice 2 — Validation des champs de saisie

Étude de cas Niveau 2 — Application

Objectif : Appliquer la validation du formulaire avant tout appel à la base.

La méthode ajouter_produit() du tutoriel refuse l'insertion si un champ obligatoire est vide, puis convertit quantite en int et prix en float. Analysez chaque ligne proposée « champ valeur » : champ est un code parmi nom, quantite, prix — valeur est le contenu saisi (un seul mot ; - = vide). Règles : nom non vide ; quantite nombre entier positif ; prix nombre positif. Pour chaque ligne il Indiquez champ : OK si la règle est respectée, sinon champ : REFUSE, puis valides : X/n.

Cas d’exemple
3
nom clavier
quantite 5
prix -
Résolution attendue
nom : OK
quantite : OK
prix : REFUSE
valides : 2/3
Deux indices, rédigés en mots
  1. Un case sur le champ : nom refuse seulement -, quantite/prix testent -gt 0 apres un test numerique.
  2. Le bilan sort une seule fois, après la boucle.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Appeler la base sans validation : des quantités textuelles finissent en base.
  • Utiliser showinfo pour un échec de connexion : c'est showerror.
  • Laisser le formulaire rempli après une opération : effacer_champs() existe.
  • Oublier d'actualiser le tableau après un ajout : l'écran ment.

8. Méthodologie de résolution

Méthode — câbler une action en trois gestes
  1. Récupérer les champs et valider : vides refusés, nombres convertis dans un try.
  2. Appeler la méthode Database correspondante dans un if : succès ou messagebox.
  3. Effacer les champs et actualiser le tableau : l'écran reflète la base.

9. Révision active

Résumé essentiel
  • Deux écrans : connexion (destroy après succès), puis interface principale.
  • Widgets : Label, Entry, Button, Frame, Treeview, Scrollbar ; pack et grid.
  • Boîtes : showinfo (succès), showwarning (attention), showerror (échec), askyesno (confirmation).
  • Validation : champs non vides, int/float dans un try — la base reçoit du propre.

Checklist de maîtrise

  • Je décris l'enchaînement des deux écrans.
  • Je nomme chaque widget et son rôle.
  • Je choisis la bonne messagebox pour une situation.
  • Je valide les champs avant l'appel à la base.

Les 8 notions à connaître absolument

  1. Entry : champ de saisie d'une ligne.
  2. Treeview : tableau ttk multi-colonnes avec sélection.
  3. pack / grid : les deux gestionnaires de mise en page.
  4. bind : relier un événement souris/clavier à une méthode.
  5. messagebox : showinfo, showwarning, showerror, askyesno.
  6. command= : référence de la méthode déclenchée par un Button.
  7. effacer_champs : nettoyage du formulaire après opération.
  8. WM_DELETE_WINDOW : protocole de fermeture propre.
