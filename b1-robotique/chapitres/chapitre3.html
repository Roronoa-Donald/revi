Chapitre 3 — Conditions et fonctions

Mise en situation

Le robot doit distinguer : ce capteur est-il activé ? Ce relevé dépasse-t-il le seuil ? Cette valeur est-elle acceptable ? La décision se code avec des conditions — et dès qu’une décision mérite d’être réutilisée, elle sort du programme principal pour devenir une fonction qui renvoie True ou False. Le TP du club demandait une fonction is_even : c’est exactement ce chapitre.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. écrire une fonction de test qui renvoie un booléen sans rien afficher ;
  2. compter les deux branches d’une condition sur une série ;
  3. implémenter un test de primalité qui s’arrête à la racine carrée ;
  4. classer des relevés par seuil strict et compter les alertes.

1. Une fonction qui répond vrai ou faux

Une fonction de test a un contrat précis : recevoir une valeur, renvoyer un booléen, ne rien afficher. C’est le programme qui décide quoi faire de la réponse.

RÈGLE DE DÉCISION EstPair(x) :
  Si (x MOD 2 = 0) Alors VRAI Sinon FAUX

Exemples :
  EstPair(4) → VRAI
  EstPair(7) → FAUX

La comparaison x % 2 == 0 est déjà un booléen : pas besoin d’écrire if ... : return True else: return False. Un return direct est plus court et dit la même chose.

Piège — la fonction qui bavarde

Une fonction de test qui print son verdict est à moitié inutilisable : on ne peut ni compter avec, ni la recombiner. Une fonction calcule et renvoie ; l’affichage appartient au programme principal. Cette séparation est ce qui permet de tester une fonction toute seule.

2. Compter les deux branches

Sur une série, la condition s’applique valeur par valeur, et les deux issues se comptent.

pairs = impairs = 0
for x in valeurs:
    if est_pair(x):
        pairs += 1
    else:
        impairs += 1

Chaque passage incrémente un seul compteur : la somme des deux vaut forcément n à la sortie. C’est un contrôle gratuit — si pairs + impairs ne vaut pas n, le programme a un bug ailleurs.

Mnémotechnique — « Un test, deux destins »

Dans un if / else, exactement une branche s’exécute par passage. Si un compteur double ou saute, c’est que le test n’est pas exclusif : relire l’opérateur de comparaison avant de soupçonner la boucle.

3. Tester la primalité

Un nombre premier possède exactement deux diviseurs : 1 et lui-même. 0 et 1 ne sont donc pas premiers. Tester tous les diviseurs jusqu’à x serait du gaspillage : il suffit d’aller jusqu’à la racine carrée de x.

ALGORITHME TestPrimalite(x) :
  Si x < 2 Alors Retourner FAUX
  Pour d de 2 jusqu'à √x faire :
    Si (x MOD d = 0) Alors Retourner FAUX
  Retourner VRAI

Pourquoi s’arrêter à la racine ? Si x = a × b avec a ≤ b, alors a ≤ √x. Un diviseur au-delà de la racine en entraîne donc un plus petit déjà testé. Pour 97, on essaie 2 à 9 au lieu de 2 à 96.

Attention aux cas de bord

0, 1 et les nombres négatifs tombent dans le premier test x < 2. Sans lui, la boucle while ne tournerait pas mais renverrait True pour 1 — un résultat faux. Les cas de bord se traitent d’abord, explicitement.

4. Classer des relevés par seuil

Le capteur de distance du TP déclenche une alerte sous 10 cm. Le classement par seuil est la décision la plus fréquente en robotique.

if d < seuil:      alerte
else:              tout va bien

Strictement inférieur se traduit par < : une distance égale au seuil n’alerte pas. Avec un <=, la frontière changerait de camp — et les tests le remarquent, car ils incluent toujours le cas de la valeur exactement au seuil.

Trois états avec elif
if t > 30:
    etat = "ALERTE CHALEUR"
elif t < 15:
    etat = "ALERTE FROID"
else:
    etat = "normale"

Les trois branches sont mutuellement exclusives : le premier test vrai gagne, les autres ne sont même pas évalués. L’ordre des tests fait partie de la logique.

5. Études de cas & applications pratiques

Ces trois études de cas se réalisent directement dans la page. Complétez chaque grille d’analyse à partir des données du cas, puis lancez la validation pour vérifier vos réponses critère par critère.

La validation compare vos réponses aux attendus des cas affichés ; elle ne vérifie pas votre capacité à traiter toutes les situations.

Exercice 1 — Les allées paires du robot d'inventaire

Étude de cas Formative Niveau 1 — Acquisition

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Appliquer une fonction de test de parité à une série et compter chacune des deux branches.

Énoncé. Dans l'entrepôt, seules les allées de numéro pair sont équipées de lecteurs de codes-barres : le robot d'inventaire ne les descend que si sa fonction de test répond vrai. La règle de décision du club s'écrit :

RÈGLE DE DÉCISION EstPair(x) :
  Si (x MOD 2 = 0) Alors VRAI Sinon FAUX

La tournée du jour passe par les allées numéro : 12 — 7 — 30 — 15 — 8 — 21 — 4.

  1. Que renvoie une fonction de test : un booléen, un texte ou un nombre ?
  2. Que vaut EstPair(12) : vrai ou faux ?
  3. Combien d'allées paires compte la tournée ?
  4. Combien d'allées impaires ?
  5. Contrôle du cours : paires + impaires = ?
  6. Que vaut EstPair(0) : vrai ou faux ?

Répondez aux questions 2 et 6 par vrai ou faux, et à la question 1 par un seul mot.

Cas d’exemple
Tournée courte de trois allées : 9, 14, 5.

1) EstPair(14) vaut vrai (14 = 2 × 7).
2) 1 allée paire : 14.
3) 2 allées impaires : 9 et 5.
4) Contrôle : 1 + 2 = 3, l'effectif de la tournée.
Trois indices, rédigés en mots
  1. Une fonction de test reçoit une valeur, renvoie vrai ou faux et n'affiche rien : c'est le programme principal qui décide quoi faire de la réponse.
  2. x MOD 2 vaut 0 exactement pour les nombres pairs : classez chaque numéro d'allée dans une des deux catégories, sans en oublier.
  3. Contrôle final : la somme des deux comptes doit redonner l'effectif de la tournée ; et pour zéro, le reste de la division par 2 est nul.

Exercice 2 — Les caisses à numéro premier du bras

Étude de cas Formative Niveau 2 — Application

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Appliquer le test de primalité avec arrêt à la racine carrée et traiter les cas de bord 0 et 1.

Énoncé. Le bras robotisé de l'atelier emballe des caisses. Une caisse dont le numéro est un nombre premier part seule sur la palette des références uniques. La règle du club s'écrit :

ALGORITHME TestPrimalite(x) :
  Si x < 2 Alors Retourner FAUX
  Pour d de 2 jusqu'à √x :
    Si (x MOD d = 0) Alors Retourner FAUX
  Retourner VRAI

Les quatre numéros du jour sont : 23, 27, 31 et 1.

  1. La caisse 23 part-elle seule sur la palette des références uniques (oui ou non) ?
  2. La caisse 27 part-elle seule (oui ou non) ?
  3. Pour x = 31, jusqu'à quel diviseur d suffit-il de tester ?
  4. Combien de diviseurs sont testés au total pour conclure que 31 est premier (d de 2 à 5) ?
  5. La caisse 1 part-elle seule (oui ou non) ?
  6. Quel est le premier diviseur trouvé pour 27 ?

Répondez par oui ou non aux questions 1, 2 et 5, et par des nombres aux autres.

Cas d’exemple
Caisses numérotées 19 et 15.

1) √19 est entre 4 et 5 : on teste d = 2, 3, 4 — aucun ne divise 19, elle est première.
2) 15 est divisible par 3 dès le deuxième essai : elle n'est pas première.
3) Pour x = 19, d va de 2 à 4 : 3 diviseurs testés.
Trois indices, rédigés en mots
  1. Un nombre premier possède exactement deux diviseurs : 1 et lui-même ; les nombres inférieurs à 2 sont exclus d'entrée par le premier test.
  2. On cherche un diviseur d de 2 jusqu'à la racine carrée de x : pour x = 31, la racine est entre 5 et 6, donc d s'arrête à 5.
  3. Pour 27, essayez les petits diviseurs dans l'ordre : dès qu'un reste de division est nul, le test répond faux ; pour 31, aucun des diviseurs testés ne divise.

Exercice 3 — Le freinage anti-collision de l'aspirateur

Étude de cas Formative Niveau 3 — Raisonnement

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Appliquer un seuil strict à des relevés de capteur, compter les alertes et enchaîner une règle à trois états.

Énoncé. Le robot aspirateur freine dès que son capteur de distance annonce un obstacle à moins de 10 cm (seuil strict, comme sur le TP du club). La décision s'écrit :

Si d < 10 Alors freiner
Sinon poursuivre

Relevés du capteur pendant la traversée du salon (en cm) : 12 — 10 — 8 — 25 — 10 — 7 — 14.

La même carte surveille aussi le local des batteries avec une sonde d'humidité à trois états :

Si h > 65 Alors "ALERTE HUMIDITE"
Sinon Si h < 35 Alors "ALERTE SEC"
Sinon "normale"
  1. Le capteur lit 8 : le robot freine-t-il (oui ou non) ?
  2. Le capteur lit exactement 10 : freine-t-il (oui ou non) ?
  3. Combien de relevés de la série déclenchent le freinage ?
  4. Quel symbole traduit « strictement inférieur » (écrivez < ou <=) ?
  5. La sonde du local des batteries lit h = 25 : quel état affiche-t-elle ?

Répondez par oui ou non aux questions 1 et 2, et par le nom exact de l'état à la question 5.

Cas d’exemple
Seuil de freinage réglé à 15 cm ; relevés : 20 — 15 — 9 — 12.

1) 9 et 12 sont strictement sous 15 : 2 freinages.
2) 15 exactement ne freine pas (seuil strict).
3) Symbole du test : <.
4) Sonde à trois états (mêmes seuils) pour h = 14 : ALERTE SEC, car 14 est sous 35 sans dépasser 65.
Trois indices, rédigés en mots
  1. Le seuil de distance est strict : seul un relevé strictement inférieur à la limite déclenche le freinage ; le relevé exactement égal passe.
  2. Classez chaque relevé de la série en « strictement sous 10 » ou « 10 et plus », puis comptez la branche freinage.
  3. Dans une chaîne Si / Sinon Si / Sinon, le premier test vrai gagne : comparez la valeur d'humidité aux deux seuils, dans l'ordre d'écriture.

6. QCM — niveau examen

Que doit faire une fonction de test ?

Elle renvoie True ou False ; l’affichage appartient au programme.

Que vaut est_pair(0) avec return x % 2 == 0 ?

0 % 2 vaut 0, donc 0 == 0 est True : zéro est pair.

Pourquoi tester la primalité jusqu’à √x seulement ?

Si x = a × b avec a ≤ b, alors a ≤ √x : suffisant pour trouver un diviseur.

Que vaut est_premier(1) ?

1 n’a qu’un seul diviseur : il n’est pas premier, le test x < 2 le renvoie en False.

d = seuil avec le test d < seuil : y a-t-il alerte ?

Strictement inférieur : la valeur égale au seuil n’alerte pas.

Dans une chaîne if / elif / else, combien de branches s’exécutent ?

Le premier test vrai gagne ; les suivants sont ignorés.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Fonction qui affiche au lieu de renvoyer : impossible de compter avec son résultat.
  • if ... : return True, else : return False : verbeux, mais surtout signe qu’on n’a pas vu que la comparaison est déjà un booléen.
  • est_premier(1) mal géré : sans le test x < 2, 1 sortirait « premier ».
  • <= au lieu de < : la valeur au seuil change de camp et le compte d’alertes glisse.
  • elif transformé en if séparés : un relevé peut alors être classé deux fois.

8. Méthodologie de résolution

Décider puis compter
  1. Isoler le critère dans une fonction de test qui renvoie un booléen.
  2. Traiter les cas de bord au début de la fonction (0, 1, négatifs).
  3. Comparer au seuil avec le bon opérateur : strict ou large, l’énoncé le dit.
  4. Compter chaque branche avec un compteur dédié initialisé avant la boucle.
  5. Contrôler que la somme des comptes redonne l’effectif total.

9. Révision active

Résumé essentiel
  • Une fonction de test renvoie un booléen et n’affiche rien ; le programme principal décide.
  • La comparaison est déjà un booléen : return x % 2 == 0 suffit.
  • Premiers : x ≥ 2 et aucun diviseur jusqu’à √x ; 0 et 1 sont exclus d’entrée.
  • Strict ou large au seuil : la frontière change de camp, les tests la vérifient toujours.
  • if / elif / else : une seule branche par passage, la première vraie gagne.

Checklist de maîtrise

  • J’écris une fonction de test qui renvoie True ou False sans afficher.
  • Je gère les cas de bord avant la boucle de test.
  • Je classe des relevés par seuil strict et je compte chaque catégorie.
  • Je vérifie que mes comptes additionnés redonnent le total.
