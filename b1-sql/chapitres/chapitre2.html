Chapitre 2 — Types de données et création de tables

Module 2 ≈ 2 h 30 de travail Réservé B1 et plus
Mise en situation

La base du parc auto ne se remplit pas à la main : on la décrit d’abord. Chaque colonne reçoit un type — un entier, une chaîne, une date — et ce choix engage tout : la place en mémoire, les comparaisons possibles, les erreurs évitées. Avec un prix stocké en texte, les conversions et les comparaisons dépendent du SGBD ; dans SQLite, une moyenne peut convertir le texte de façon inattendue.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. choisir le type adapté pour une colonne : numérique, chaîne, temporel ;
  2. distinguer CHAR et VARCHAR et savoir quand préférer l’un ;
  3. écrire une instruction CREATE TABLE complète avec clés ;
  4. insérer des lignes avec INSERT et comprendre le rôle de NULL.

1. Les types numériques

Pour les entiers, MySQL propose une gamme de tailles croissantes :

TypePlage (signé)Usage typique
TINYINT−128 à 127un âge, un petit compteur
SMALLINT≈ −32 700 à 32 700une année, une quantité
MEDIUMINT≈ −8,4 M à 8,4 Mun identifiant interne
INT≈ −2,1 Md à 2,1 Mdun prix en francs, un kilométrage
BIGINT≈ ±9,2 × 10¹⁸des identifiants mondiaux, des horodatages

Deux précisions du support MySQL : la notation INT(x) ne change pas la plage de valeurs ; elle indiquait une largeur d’affichage. Cette largeur et ZEROFILL sont dépréciés dans les versions récentes de MySQL. Pour les décimaux, on utilise DECIMAL(p, s) — précision p, s décimales — pour l’argent, et FLOAT/DOUBLE pour les mesures scientifiques.

Piège — l’argent et les dialectes

Les nombres flottants peuvent produire des arrondis. Dans MySQL, DECIMAL sert aux valeurs décimales exactes. SQLite traite DECIMAL avec une affinité numérique et ne garantit pas ce calcul décimal exact. Dans notre parc, pxachat est un entier en francs : INTEGER.

2. CHAR et VARCHAR

En MySQL, les chaînes de longueur fixe ou variable s’écrivent avec un paramètre de taille :

StockéCHAR(5)VARCHAR(5)
« OK »« OK    » (complété d’espaces)« OK » (tel quel)
Stockagecomplété jusqu’à 5 caractèrescontenu + 1 ou 2 octets de longueur

CHAR(x) réserve toujours x caractères et complète les plus courts d’espaces : il convient quand la longueur est constante — un code de marque sur trois lettres, un code postal. VARCHAR(x) stocke jusqu’à x caractères, sans remplissage : c’est le choix par défaut pour un nom, une adresse, un immatriculé.

Dans SQLite, CHAR et VARCHAR ont une affinité texte : la longueur entre parenthèses n’est pas une limite imposée par le type. Notre schéma utilise TEXT.

Le support cite aussi les grands textes (TEXT) et les binaires (BLOB) pour les contenus longs — un commentaire, une image stockée en base.

Mnémotechnique — « Fixe = CHAR, variable = VARCHAR »

En MySQL, un code de pays à trois lettres naît et meurt à trois lettres : CHAR(3). Un nom de famille va de une lettre à vingt : VARCHAR(20). Se tromper ne casse rien, mais gaspille — et un CHAR qui complète d’espaces surprend les comparaisons.

3. Les types temporels

Cinq types pour le temps en MySQL :

TypeContenuFormat littéral
DATEune date'AAAA-MM-JJ'
TIMEune heure'HH:MM:SS'
DATETIMEdate et heure'AAAA-MM-JJ HH:MM:SS'
TIMESTAMPdate et heure (fuseau géré)idem DATETIME
YEARune année'AAAA' ou AAAA

Le format littéral n’est pas décoratif : dans le parc, la date du 21 novembre 2014 s’écrit '2014-11-21'. La chaîne '21/11/2014' est valide comme texte SQL, mais ne respecte pas le format choisi pour les dates de ce parc.

SQLite n’a pas de type de stockage spécifique aux dates. Dans notre parc, datecirc est un texte au format AAAA-MM-JJ, ou NULL si la date est inconnue. C’est une convention des données du parc : le type TEXT seul ne valide pas la date. Avec ce format homogène, on peut comparer : SELECT immat FROM Voiture WHERE datecirc < '2015-01-01';

4. CREATE TABLE et INSERT

La description d’une table passe par CREATE TABLE : chaque colonne reçoit un nom, un type, et des contraintes optionnelles (NOT NULL, PRIMARY KEY).

Voici le schéma exact du simulateur SQLite ; les tables existent déjà dans l’atelier. La première instruction active les clés étrangères pour cette connexion :

PRAGMA foreign_keys = ON;
CREATE TABLE Marque (
  codemarque TEXT NOT NULL PRIMARY KEY,
  nommarque  TEXT NOT NULL UNIQUE,
  paysmarque TEXT NOT NULL,
  UNIQUE (codemarque, nommarque)
);
CREATE TABLE Voiture (
  immat     TEXT NOT NULL PRIMARY KEY,
  marque    TEXT NOT NULL,
  codemarque TEXT NOT NULL,
  moteur    TEXT NOT NULL,
  datecirc  TEXT,
  km        INTEGER NOT NULL,
  pxachat   INTEGER NOT NULL,
  nbreplace INTEGER NOT NULL,
  FOREIGN KEY (codemarque, marque) REFERENCES Marque (codemarque, nommarque)
);
CREATE TABLE Equipement (
  codeequipement TEXT NOT NULL PRIMARY KEY,
  nomequipement TEXT NOT NULL UNIQUE,
  prix INTEGER DEFAULT 0
);
CREATE TABLE VoitureEquipement (
  immat TEXT NOT NULL,
  codeequipement TEXT NOT NULL,
  PRIMARY KEY (immat, codeequipement),
  FOREIGN KEY (immat) REFERENCES Voiture (immat) ON DELETE CASCADE,
  FOREIGN KEY (codeequipement) REFERENCES Equipement (codeequipement) ON DELETE CASCADE
);

immat et codemarque sont des clés primaires non nulles. La clé étrangère composée assure que le code et le nom de chaque voiture désignent ensemble une marque existante. Seule datecirc peut manquer dans Voiture. Les tables Equipement et VoitureEquipement ajoutent des données fictives pour les jointures du chapitre 4. Dans Equipement, un prix omis vaut 0 par défaut ; un prix explicitement inconnu peut être NULL.

Les lignes arrivent par INSERT INTO. Ajoutez d’abord deux marques fictives, puis une voiture dont la date est inconnue :

INSERT INTO Marque (codemarque, nommarque, paysmarque) VALUES
('TES', 'EXEMPLE', 'TOGO'),
('ABC', 'ATELIER', 'BENIN');
INSERT INTO Voiture (immat, marque, codemarque, moteur, datecirc, km, pxachat, nbreplace)
VALUES ('TG-0001-TEST', 'EXEMPLE', 'TES', 'ELECTRIQUE', NULL, 0, 12000000, 5);
SELECT immat, datecirc FROM Voiture WHERE immat = 'TG-0001-TEST';

Résultat : TG-0001-TEST | NULL. Réinitialisez le simulateur avant de recommencer pour éviter les clés déjà présentes. Une colonne omise reçoit son DEFAULT, sinon NULL ; si une contrainte NOT NULL est violée, l’insertion échoue. Une clé INTEGER PRIMARY KEY omise dans une table ordinaire peut recevoir un entier généré par SQLite.

Le simulateur du cours

La page atelier — simulateur SQL charge ce schéma et les données du parc. SQLite et MySQL partagent de nombreuses syntaxes, mais leurs règles diffèrent notamment pour les types, les agrégats et l’administration.

5. Ajouter une colonne avant de s’exercer

ALTER TABLE … ADD COLUMN ajoute une colonne à une table existante. Dans une copie du parc, ajoutez provisoirement une garantie par défaut de 12 mois aux équipements :

ALTER TABLE Equipement ADD COLUMN garantie_mois INTEGER DEFAULT 12;
SELECT codeequipement, garantie_mois FROM Equipement WHERE codeequipement = 'AIR';

Résultat : AIR | 12. La ligne existante reçoit cette valeur par défaut lors de sa lecture. Réinitialisez le simulateur pour retrouver le schéma de référence. Dans l’exercice, une version antérieure d’Equipement ne possède pas encore la colonne prix : vous l’ajouterez avec sa valeur par défaut. Au chapitre 6, vous étudierez d’autres évolutions de structure et leurs limites selon le SGBD.

7. QCM — niveau examen

En MySQL, quel type convient à un prix avec des centimes ?

MySQL propose DECIMAL pour les décimaux exacts ; un flottant peut arrondir et VARCHAR est du texte.

En MySQL, INT(2) limite-t-il la valeur à deux chiffres ?

INT(x) ne change pas la capacité de stockage ; la largeur concerne un affichage éventuel avec ZEROFILL.

En MySQL, quel type à longueur fixe choisir pour un code de 3 caractères ?

CHAR(3) est le type fixe ; VARCHAR est variable et TEXT ne précise pas cette longueur.

Dans le parc SQLite, quelle chaîne représente le 21 novembre 2014 ?

Le parc choisit le format texte année, mois, jour : AAAA-MM-JJ.

En SQLite, que peut recevoir une colonne ordinaire omise dans INSERT ?

Un DEFAULT fournit la valeur ; sinon c’est NULL, sauf si une contrainte comme NOT NULL interdit l’insertion. Une INTEGER PRIMARY KEY ordinaire peut être générée.

Que fait IF NOT EXISTS dans CREATE TABLE ?

L’instruction devient sans effet (et sans erreur) si la table existe déjà.

8. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Argent en FLOAT/DOUBLE : arrondis invisibles qui faussent totaux et moyennes.
  • Dates en format local : '21/11/2014' est une chaîne SQL valide, mais pas une date au format du parc.
  • CHAR confondu avec VARCHAR : les espaces de complément surprennent les comparaisons.
  • Clé primaire oubliée : deux voitures avec la même immatriculation deviennent possibles.
  • INSERT sans colonnes nommées : tout repose sur l’ordre des colonnes, fragile au moindre changement.

9. Méthodologie de résolution

Déclarer une table proprement
  1. Lister les colonnes et leur contenu réel (est-ce un nombre, un texte, une date ?).
  2. Choisir les types selon le SGBD : DECIMAL exact en MySQL, INTEGER pour les francs entiers du parc SQLite.
  3. Poser la clé primaire et les contraintes NOT NULL indispensables.
  4. Insérer des lignes de test en nommant toujours les colonnes.
  5. Vérifier avec SELECT * que la structure et les NULL sont conformes.

10. Révision active

Résumé essentiel
  • En MySQL, les entiers vont de TINYINT à BIGINT ; INT(x) ne change pas leur plage.
  • En MySQL, DECIMAL convient à l’argent ; dans le parc SQLite, les francs entiers sont en INTEGER.
  • En MySQL, CHAR est fixe et VARCHAR variable ; SQLite applique une affinité texte sans imposer leur longueur.
  • Dans le parc SQLite, les dates sont du texte au format 'AAAA-MM-JJ' ; en MySQL, DATETIME ajoute l’heure.
  • CREATE TABLE décrit colonnes, types et clés ; INSERT nomme les colonnes renseignées.

Checklist de maîtrise

  • Je distingue CHAR et VARCHAR avec un exemple de chaque.
  • J’écris un CREATE TABLE complet avec clé primaire.
  • J’insère des lignes en nommant les colonnes et je prévois les NULL.
