Chapitre 6 — Modifier les données et gérer les droits

Module 6 ≈ 2 h 30 de travail Réservé B1 et plus
Mise en situation

Le parc évolue : une voiture change de moteur, une autre est vendue, une colonne kilométrage doit être ajoutée. Et surtout, le club recrute : un gestionnaire qui peut consulter mais pas effacer, un admin qui hérite de tout. Un SGBD digne de ce nom ne se contente pas de lire : il modifie sous contrôle et répartit les droits.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. modifier des lignes avec UPDATE et les supprimer avec DELETE, toujours avec WHERE ;
  2. faire évoluer une structure avec ALTER TABLE ;
  3. créer des utilisateurs et leur accorder des privilèges gradués ;
  4. comprendre le rôle du privilège GRANT OPTION et de REVOKE.

1. UPDATE : modifier sous condition

La syntaxe porte trois informations : quelle table, quelles colonnes changent, quelles lignes :

\n
UPDATE nom_table
SET colonne1 = valeur1, colonne2 = valeur2
WHERE condition;

-- le support normalise les codes de marque :
UPDATE Voiture SET codemarque = 'TOY' WHERE marque = 'TOYOTA';
UPDATE Voiture SET codemarque = 'BMW' WHERE marque = 'BMW';
\n

Le WHERE n’est pas décoratif : c’est lui qui limite la modification aux lignes visées. Le support le rappelle en marge de ses exemples — et le SGBD se protège un peu : en mode par défaut prudent, un UPDATE sans WHERE est rejeté ou demande confirmation.

\n
Piège — le UPDATE sans WHERE

UPDATE Voiture SET moteur = 'DIESEL'; sans WHERE s’applique à toutes les lignes : 23 voitures passées au diesel en une requête. Toute modification sérieuse se teste d’abord par le SELECT équivalent — si le SELECT ramène les bonnes lignes, l’UPDATE avec le même WHERE les modifiera.

2. DELETE et ALTER

La suppression suit le même principe : une table, une condition.

\n
DELETE FROM Voiture WHERE immat = 'TG-7854-Z';
DELETE FROM Voiture;        -- VIDE TOUTE LA TABLE, ligne par ligne
\n

Le DELETE sans WHERE ne supprime pas la table : il la vide. La structure reste ; seule la commande DROP TABLE fait disparaître la table elle-même.

\n

La structure évolue par ALTER TABLE :

\n
ALTER TABLE Voiture ADD COLUMN comment VARCHAR(100);
ALTER TABLE Marque DROP COLUMN paysmarque;   -- l’opération du support avant normalisation
ALTER TABLE Voiture MODIFY COLUMN km BIGINT;
\n

Ajouter, supprimer, changer un type : ALTER est la commande d’évolution du schéma — elle s’accompagne d’une réflexion sur les données existantes, qui doivent rester cohérentes avec la nouvelle structure.

3. Utilisateurs : CREATE USER et l’hôte

On ne se connecte pas « à MySQL » en général : on s’y connecte en tant qu’un utilisateur, défini par un login et un hôte — l’adresse depuis laquelle la connexion est autorisée :

\n
CREATE USER 'login'@'hote' [IDENTIFIED BY 'mot_de_passe'];
DROP   USER 'login'@'hote';

CREATE USER 'delegueITB1'@'localhost' IDENTIFIED BY 'wincrafts@Big';
CREATE USER 'profside'@'192.168.66.9' IDENTIFIED BY 'vivinve3';
\n

Le joker % élargit l’hôte :

\n
Utilisateur déclaréConnexion autorisée depuis
'leader'@'192.168.66.%'toute IP commençant par 192.168.66.
'youssoufa'@'%.camer.net'n’importe quel hôte du domaine camer.net
'yeslows'@'%'n’importe quel hôte (équivalent à 'yeslows')
\n

Les guillemets entourent indépendamment login et hôte — jamais l’ensemble 'login@hote'. Sans précision d’hôte, c’est l’équivalent de % : tous les hôtes.

\n
Mnémotechnique — « login@hôte : deux clés, une porte »

Le login dit qui entre, l’hôte dit d’où. Le même login peut exister en plusieurs exemplaires aux privilèges différents selon l’hôte — deux clés distinctes pour deux portes distinctes.

4. Privilèges : GRANT et REVOKE

Un utilisateur créé n’a aucun privilège : il peut à peine se connecter. Un privilège est l’autorisation d’effectuer une action sur un objet, accordée par GRANT et retirée par REVOKE :

\n
-- tous les droits sur une base :
GRANT ALL PRIVILEGES ON parc_auto.* TO 'IT_B1'@'localhost';

-- consultation seule :
GRANT SELECT ON parc_auto.* TO 'delegueITB1'@'localhost';

-- écriture limitée à une table :
GRANT SELECT, INSERT, UPDATE ON parc_auto.Voiture TO 'gestionnaire'@'localhost';

-- retirer :
REVOKE UPDATE ON parc_auto.Voiture FROM 'gestionnaire'@'localhost';
\n

Les privilèges s’appliquent à plusieurs niveaux : global (*.*), base (parc_auto.*), table (parc_auto.Voiture), voire colonne. Parmi les privilèges particuliers : ALL (tous, s’emploie seul), USAGE (aucun droit, toujours global) et GRANT OPTION.

\n
GRANT SELECT, UPDATE ON parc_auto.*
TO 'admincdp'@'localhost'
WITH GRANT OPTION;
\n

GRANT OPTION autorise son détenteur à transmettre les privilèges qu’il possède à d’autres utilisateurs — il n’est pas compris dans ALL, et un utilisateur ne peut jamais accorder plus qu’il ne possède. C’est la règle de sécurité du support : la délégation se contrôle, sinon chaque utilisateur pourrait créer sa hiérarchie de droits.

\n
Piège — ALL et GRANT OPTION ensemble

GRANT ALL, GRANT OPTION ON … est refusé : ALL s’emploie seul. Pour donner tout et le droit de transmettre, la forme est GRANT ALL PRIVILEGES ON … TO … WITH GRANT OPTION. La distinction est tombée en QCM du support.

5. Exercices de code

Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

En cas d’erreur, le bouton Expliquer mon erreur interroge le tuteur : il décrit ce qui s’est passé et par où chercher, sans jamais écrire de code à votre place — c’est le principe de l’exercice.

Exercice 1 — UPDATE, DELETE ou GRANT ?

Bash Niveau 1 — Acquisition

Objectif : Associer chaque opération de fin de cours à sa famille.

Le script lit n lignes « operation famille » : famille est un code parmi maj, suppression, structure ou droits. Familles du chapitre : UPDATE → maj ; DELETE → suppression ; ALTER TABLE → structure ; GRANT et REVOKE → droits. Pour chaque ligne il affiche operation : OK ou operation : ERREUR, puis corrects : X/n.

Entrée du programme
3
update maj
delete suppression
grant droits
Sortie attendue
update : OK
delete : OK
grant : OK
corrects : 3/3
Deux indices, rédigés en mots
  1. Un case sur l’opération : update → maj, delete → suppression, alter → structure, grant/revoke → droits.
  2. Le bilan sort une seule fois, après la boucle.

Exercice 2 — UPDATE ciblé : condition WHERE obligatoire

Bash Niveau 2 — Application

Objectif : Appliquer une hausse de prix uniquement aux voitures du moteur demandé.

Le script lit d’abord n lignes « immat moteur prix » (la table), puis une ligne moteur hausse — hausse en pourcentage entier. Il rejoue UPDATE Voiture SET pxachat = pxachat * (100 + hausse) / 100 WHERE moteur = moteur : pour chaque voiture du moteur demandé il affiche immat : ancien -> nouveau (prix recalculé, arrondi à l’entier inférieur), pour les autres immat : inchangé, puis lignes modifiees : X — le nombre que renverrait l’UPDATE.

Entrée du programme
3
TG-0001-AA DIESEL 20000000
TG-0002-AA ESSENCE 10000000
TG-0003-AA DIESEL 15000000
DIESEL 10
Sortie attendue
TG-0001-AA : 20000000 -> 22000000
TG-0002-AA : inchangé
TG-0003-AA : 15000000 -> 16500000
lignes modifiees : 2
Deux indices, rédigés en mots
  1. Nouveau prix : $(( prix * (100 + hausse) / 100 )) — la division entière tronque, c’est l’arrondi demandé.
  2. Le compteur ne progresse que pour les lignes réellement modifiées : c’est le « X rows affected ».

Exercice 3 — Le journal d’administration : audit de session

Bash Niveau 3 — Raisonnement

Objectif : Vérifier les autorisations avant chaque opération, comme GRANT/REVOKE le décident.

Le script lit n lignes « role operation » : role est un code parmi admin, ecriture ou lecture ; operation est un code parmi select, insert, update, delete ou grant. Droits du cours : admin peut tout ; ecriture peut select, insert, update et delete ; lecture ne peut que select ; personne d’autre ne peut grant. Pour chaque ligne il affiche role/operation : autorise ou role/operation : refuse, puis autorisations : X/n.

Entrée du programme
3
admin grant
lecture select
ecriture delete
Sortie attendue
admin/grant : autorise
lecture/select : autorise
ecriture/delete : autorise
autorisations : 3/3
Deux indices, rédigés en mots
  1. Un case sur le rôle qui fixe la liste des opérations permises : admin → toutes, ecriture → les quatre CRUD, lecture → select.
  2. grant est refusé à tout le monde sauf admin ; le bilan sort après la boucle.

6. QCM — niveau examen

Que fait UPDATE sans clause WHERE ?

Sans condition, la modification s’applique à toute la table.

DELETE FROM Voiture; (sans WHERE)…

La structure reste ; seule DROP TABLE supprime la table.

Quelle commande ajoute une colonne à une table existante ?

ALTER TABLE fait évoluer la structure.

Un utilisateur créé avec CREATE USER, avant tout GRANT, peut…

Aucun privilège : ni données ni création d’objets.

'leader'@'192.168.66.%' signifie…

% élargit l’hôte ; ici tout le réseau 192.168.66.x.

GRANT OPTION permet de…

C’est le droit de déléguer — jamais inclus dans ALL.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • UPDATE ou DELETE sans WHERE : toute la table est touchée — tester par le SELECT équivalent d’abord.
  • DROP TABLE confondu avec DELETE : l’un efface la structure, l’autre les lignes.
  • 'login@hote' quoté en un seul bloc : login et hôte se quotent séparément.
  • GRANT ALL, GRANT OPTION : syntaxe refusée — la clause est WITH GRANT OPTION.
  • Accorder plus qu’on possède : impossible ; un utilisateur transmet au maximum ses propres droits.

8. Méthodologie de résolution

Modifier ou déléguer sans casse
  1. Écrire le SELECT équivalent avant tout UPDATE/DELETE : les lignes ramenées sont celles qui seront touchées.
  2. Modifier les données (UPDATE/DELETE) sans confondre avec la structure (ALTER/DROP).
  3. Créer l’utilisateur avec son couple login@hôte exact.
  4. Accorder le minimum nécessaire : SELECT pour consulter, pas ALL par confort.
  5. Documenter les délégations : chaque WITH GRANT OPTION est une décision, pas un réflexe.

9. Révision active

Résumé essentiel
  • UPDATE … SET … WHERE modifie ; DELETE FROM … WHERE supprime ; sans WHERE, c’est toute la table.
  • ALTER TABLE fait évoluer la structure ; DROP TABLE la supprime ; DELETE la vide seulement.
  • Un utilisateur = login@hôte ; le joker % élargit l’hôte ; guillemets séparés sur chaque partie.
  • GRANT accorde, REVOKE retire ; niveaux global, base, table, colonne ; un utilisateur créé n’a aucun droit.
  • GRANT OPTION autorise la transmission des privilèges propres ; ALL s’emploie seul, avec WITH GRANT OPTION.

Checklist de maîtrise

  • Je teste chaque modification par le SELECT équivalent avant de l’exécuter.
  • Je distingue DELETE, DROP TABLE et TRUNCATE sur une table.
  • Je crée un utilisateur login@hôte et je lui accorde le minimum.
  • J’explique GRANT OPTION et sa syntaxe exacte avec ALL.
