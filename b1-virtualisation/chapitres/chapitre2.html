Chapitre 2 — La virtualisation et le partage des ressources

Mise en situation

La colère du serveur est franchie : « Faire le travail de plusieurs serveurs ? C’est de la folie ! » Les machines virtuelles répondent calmement : « On va se partager votre mémoire, votre processeur et même votre disque dur. Et on ne prendra chacun que ce dont on a besoin. » Ce chapitre prend la promesse au mot : allouer sans dépasser, partager sans violer.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. expliquer la proposition de l’ingénieur : plusieurs machines, un seul serveur physique ;
  2. citer les ressources partagées de l’histoire : mémoire, processeur, disque ;
  3. allouer des ressources demandées sans dépasser la capacité restante ;
  4. retenir l’ordre exact de la conversation de l’histoire.
  5. distinguer un hyperviseur de type 1 (bare metal) d’un hyperviseur de type 2 (hébergé) et citer un exemple de chaque ;
  6. expliquer le rôle des extensions processeur Intel VT-x et AMD-V et savoir les activer dans le BIOS/UEFI.

1. L’idée : faire croire au serveur

La proposition de l’ingénieur tient en une phrase : « faire croire au serveur qu’il héberge plusieurs machines… alors qu’en réalité, ce sont juste des machines virtuelles qui partagent ses ressources ! »

Chaque machine virtuelle se comporte comme un ordinateur complet — son propre système, ses propres applications — mais tout cela n’est qu’un partage organisé du matériel physique du serveur hôte.

La définition à retenir

La virtualisation, c’est faire tourner plusieurs machines indépendantes sur un seul matériel physique, en partageant ses ressources. Le serveur ne travaille pas plus : il travaille mieux.

2. Hyperviseur de type 1 et de type 2

Dans l’histoire, l’ingénieur installe « une couche logicielle » qui fabrique les machines virtuelles : c’est l’hyperviseur. Selon l’endroit où il se place, on en distingue deux familles.

CritèreType 1 (bare metal)Type 2 (hébergé)
Où s’installe-t-il ?Directement sur le matériel, à la place d’un système classiqueComme une application, au-dessus d’un système (Windows, Linux, macOS)
Chemin d’un accès disqueVM → hyperviseur → matérielVM → hyperviseur → système hôte → matériel
ExemplesVMware ESXi, Microsoft Hyper-V, KVM (Linux), XenOracle VirtualBox, VMware Workstation / Player, Parallels
Usage typiqueSalle serveur, production, consolidationPoste d’étude, laboratoire, tests d’un développeur
PerformanceMeilleure : une seule couche entre la VM et le matérielUn peu moindre : le système hôte s’intercale

Le serveur fainéant de l’histoire est un cas de type 1 : on veut que la machine physique serve uniquement à faire tourner des VM. Le laboratoire de ce cours (chapitre 6) utilise au contraire un type 2, VirtualBox, parce qu’il s’installe sur votre ordinateur personnel sans le réinstaller.

La frontière n’est pas toujours nette : KVM est un module du noyau Linux (le système devient hyperviseur) et Hyper-V fait tourner le Windows « parent » lui-même comme une VM privilégiée. Pour le cours, retenez la règle pratique : si l’on installe l’hyperviseur sur un système déjà utilisé au quotidien, c’est un type 2 ; si la machine est dédiée à la virtualisation, c’est un type 1.

Mnémo : 1 = sous, 2 = sur

Type 1 : l’hyperviseur est sous tous les systèmes, au contact du matériel. Type 2 : il est sur un système, comme n’importe quel logiciel.

3. Ce qui se partage

Les VM de l’histoire sont précises : « on va se partager votre mémoire, votre processeur et même votre disque dur ».

RessourcePartage
Mémoire (RAM)répartie entre les VM selon leurs besoins déclarés
Processeurtemps de calcul partagé entre toutes les machines
Disqueespace de stockage découpé entre les VM

Certaines ressources peuvent rester dédiées (une carte réseau réservée à une VM, par exemple) : le partage est une règle par défaut, pas un dogme.

Mémoire, processeur, disque

Les trois ressources de la promesse — dans cet ordre dans l’histoire : mémoire, processeur, disque. C’est le vocabulaire des exercices d’allocation du chapitre.

4. VT-x et AMD-V : l’aide du processeur

Faire croire à un système qu’il possède toute la machine serait lent si l’hyperviseur devait tout traduire en logiciel. Les fabricants de processeurs ont donc ajouté des instructions dédiées : Intel VT-x (Intel Virtualization Technology) et AMD-V (AMD Virtualization, aussi appelée SVM). Elles laissent le système invité exécuter ses instructions directement sur le processeur, sous le contrôle de l’hyperviseur.

Ces extensions sont présentes sur la quasi-totalité des processeurs récents, mais elles peuvent être désactivées dans le BIOS/UEFI. Sans elles, les hyperviseurs modernes refusent de démarrer des VM 64 bits ou les font tourner très lentement.

Comment vérifier ?

# Linux : un nombre different de 0 signifie que vmx (Intel) ou svm (AMD) est actif
grep -E -c '(vmx|svm)' /proc/cpuinfo
lscpu | grep -i virtualization

# Windows : Gestionnaire des taches, onglet Performance, ligne « Virtualisation »
# ou, dans une console : systeminfo | find "Hyper-V"
Piège — « VT-x n’est pas disponible »

Ce message n’annonce presque jamais un processeur trop ancien : il signale le plus souvent une option désactivée dans le BIOS/UEFI (Intel Virtualization Technology, SVM Mode), ou un autre hyperviseur déjà actif sur le poste (Hyper-V sous Windows). Vérifiez ces deux points avant d’accuser le matériel.

5. « On ne prendra que ce dont on a besoin »

La seconde moitié de la promesse est une règle d’allocation : chaque VM demande ce dont elle a besoin, et le total des demandes ne dépasse pas la capacité du serveur. Allouer, c’est donc un contrôle à deux conditions : la mémoire demandée tient-elle dans le reste disponible ? le disque demandé tient-il dans le reste disponible ? Si oui, la VM est allouée et les restes diminuent ; si non, elle est refusée — et rien n’est consommé.

Exemple du cours : un serveur de 64 Go de RAM et 500 Go de disque. La VM web (16 Go, 50 Go) passe ; la VM base (32 Go, 200 Go) passe ; la VM test (32 Go, 400 Go) est refusée — il ne reste que 16 Go et 250 Go. Le refus n’est pas un échec : c’est la promesse tenue.

Piège — allouer avant de contrôler

Une ressource refusée ne doit jamais être décomptée. Contrôler d’abord (les deux conditions en même temps), allouer ensuite. Sinon le serveur promet ce qu’il n’a plus.

6. La conversation, dans l’ordre

L’histoire suit un déroulé exact — que les exercices rejouent étape par étape :

  1. l’ingénieur propose l’idée de la virtualisation ;
  2. le serveur se réveille en sursaut et refuse (« C’est de la folie ! ») ;
  3. les machines virtuelles proposent le partage des ressources ;
  4. le serveur accepte — le récit le dit « rentabilisé à 100 % », image à distinguer d’une mesure.
Les exercices de ce chapitre

Classer les ressources partagées, allouer les demandes sans dépasser la capacité, rejouer la conversation dans l’ordre. Trois scripts qui transforment la fable en règles programmables.

Exercice 1 — L'idée de l'ingénieur et les deux familles d'hyperviseurs

Étude de cas Formative Niveau 1 — Acquisition

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Nommer l'hyperviseur, citer les trois ressources partagées et distinguer hyperviseur de type 1 et de type 2.

Énoncé. Un jour, un ingénieur IT a une idée : faire croire à M. Fainéant qu'il héberge plusieurs machines, alors qu'en réalité ce sont des machines virtuelles (VM) qui partagent ses ressources. Les VM ambitieuses promettent : « On va se partager votre mémoire, votre processeur et même votre disque dur. Et on ne prendra chacun que ce dont on a besoin. » Pour tenir la promesse, l'ingénieur installe la couche logicielle qui crée et fait tourner les VM : l'hyperviseur. Il explique au responsable informatique qu'il existe deux familles : les hyperviseurs de type 1 (dits « bare-metal » : ESXi, Proxmox VE, KVM), installés directement sur le matériel sans système d'exploitation hôte, et les hyperviseurs de type 2 (dits « hébergés » : VirtualBox, VMware Workstation), installés au-dessus d'un système d'exploitation hôte.

  1. Comment s'appelle la couche logicielle qui crée et fait tourner les machines virtuelles sur le serveur physique ? (un mot)
  2. Quelle est la première ressource partagée citée par les VM dans leur promesse ?
  3. Quelle est la deuxième ressource partagée de la promesse ?
  4. Quelle est la troisième ressource partagée (« et même votre... ») ?
  5. Un hyperviseur de type 1 s'installe-t-il directement sur le matériel, sans système d'exploitation hôte ? (oui ou non)
  6. VirtualBox s'installe sur un PC déjà doté de Windows : de quel type d'hyperviseur s'agit-il ? (répondez par le chiffre seul : 1 ou 2)
Cas d’exemple
Un technicien veut s'exercer chez lui : sur son portable Windows, il installe VirtualBox et y crée deux VM. Au bureau, le serveur ESXi, lui, tourne seul sur sa machine, sans Windows ni Linux dessous.

1) La couche qui crée les VM s'appelle l'hyperviseur.
2) VirtualBox est installé au-dessus de Windows : hyperviseur de type 2.
3) ESXi tourne directement sur le matériel : hyperviseur de type 1.
4) Les VM de son labo partagent la mémoire, le processeur et le disque du portable.
Trois indices, rédigés en mots
  1. Dans l'histoire, la couche qui sépare le matériel des VM porte un nom précis : c'est elle qui « fait croire » au serveur qu'il héberge plusieurs machines.
  2. La promesse des VM cite les ressources dans un ordre exact : relisez la citation de l'énoncé, entre la mémoire et le disque dur.
  3. Le type 1 (bare-metal : ESXi, Proxmox VE, KVM) se pose sur le matériel nu ; le type 2 (hébergé : VirtualBox, VMware Workstation) a besoin d'un système d'exploitation hôte.

Exercice 2 — « On ne prendra que ce dont on a besoin »

Étude de cas Formative Niveau 2 — Application

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Appliquer la règle d'allocation : contrôler mémoire ET disque avant d'allouer, refuser sans rien consommer.

Énoncé. La promesse devient règle d'allocation : chaque VM demande ce dont elle a besoin, et une demande n'est acceptée que si la mémoire ET le disque demandés tiennent tous les deux dans les capacités restantes du serveur. Une VM refusée ne consomme rien. M. Fainéant offre 32 Go de RAM et 800 Go de disque. Les VM ambitieuses se présentent dans l'ordre :

VMRAM demandéeDisque demandé
vm-web8 Go200 Go
vm-base16 Go300 Go
vm-test12 Go200 Go
vm-fichiers8 Go150 Go
  1. Après l'allocation de vm-web et de vm-base, combien de RAM reste-t-il, en Go ?
  2. La VM vm-test (12 Go, 200 Go) est-elle acceptée ? (oui ou non)
  3. Quelle ressource lui manque-t-il : la mémoire ou le disque ? (un mot)
  4. La VM vm-fichiers (8 Go, 150 Go) est-elle acceptée ? (oui ou non)
  5. Après l'allocation de vm-fichiers, combien de disque reste-t-il, en Go ?
  6. La VM refusée a-t-elle consommé des ressources ? (oui ou non)
Cas d’exemple
Un serveur de recette offre 16 Go de RAM et 400 Go de disque. Demandes dans l'ordre :
vm-a (4 Go, 100 Go) — vm-b (8 Go, 200 Go) — vm-c (6 Go, 50 Go).

1) vm-a acceptée : restes 12 Go et 300 Go.
2) vm-b acceptée : restes 4 Go et 100 Go.
3) vm-c : il reste 4 Go de RAM, elle en demande 6 : refusée pour la mémoire (le disque, lui, tenait).
4) vm-c ne consomme rien : les restes restent 4 Go et 100 Go.
Trois indices, rédigés en mots
  1. Suivez les allocations dans l'ordre : décomptez la RAM et le disque de chaque VM acceptée, jamais celles des VM refusées.
  2. Pour chaque demande, comparez les DEUX restes en même temps : il suffit qu'une seule ressource manque pour que la VM soit refusée.
  3. Après chaque allocation acceptée, recalculez les deux restes ; comparez-y la demande suivante : une seule ressource qui dépasse suffit à refuser.

Exercice 3 — La conversation et le premier partage

Étude de cas Formative Niveau 3 — Raisonnement

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Rejouer la conversation de l'histoire dans l'ordre et dimensionner le premier partage de M. Fainéant (RAM et vCPU).

Énoncé. L'histoire se joue en quatre temps : l'ingénieur propose l'idée de la virtualisation ; M. Fainéant se réveille en sursaut et se met en colère (« Faire le travail de plusieurs serveurs ? C'est de la folie ! ») ; les machines virtuelles répondent en proposant le partage des ressources ; le serveur accepte enfin. Pour sceller l'accord, les trois premières VM ambitieuses s'installent sur M. Fainéant, qui dispose de 16 Go de RAM, de 8 cœurs de processeur et de 500 Go de disque. Chaque VM demande 4 Go de RAM, 2 vCPU et 100 Go de disque.

  1. Qui a l'idée de la virtualisation dans l'histoire ? (répondez par le métier du personnage, un mot)
  2. Quelle est la réaction immédiate de M. Fainéant quand il entend l'idée ? (un mot)
  3. Qui propose de partager la mémoire, le processeur et le disque ? (réponse courte)
  4. Quelle quantité totale de RAM les trois VM demandent-elles, en Go ?
  5. Combien de RAM reste-t-il à M. Fainéant après les trois VM, en Go ?
  6. Combien de cœurs restent disponibles, si chaque VM reçoit 2 vCPU ?
Cas d’exemple
Même scène sur un serveur de secours plus petit : 8 Go de RAM, 4 cœurs.
Deux VM s'y installent, chacune avec 3 Go de RAM et 1 vCPU.

1) L'ingénieur propose l'idée, le serveur se met en colère, les VM proposent le partage, le serveur accepte.
2) RAM totale demandée : 2 x 3 = 6 Go.
3) RAM restante : 8 - 6 = 2 Go.
4) vCPU utilisés : 2 x 1 = 2 ; cœurs restants : 4 - 2 = 2.
Trois indices, rédigés en mots
  1. La conversation suit un ordre exact : celui qui propose l'idée n'est pas celui qui propose le partage, et le serveur passe par la colère avant l'acceptation.
  2. Pour la RAM : multipliez la demande d'une VM par le nombre de VM, puis soustrayez ce total de la capacité de M. Fainéant.
  3. Même raisonnement pour les cœurs : chaque VM consomme des vCPU pris sur les cœurs physiques ; ce qui n'est pas pris reste disponible.

8. QCM — niveau examen

La virtualisation permet de…

Plusieurs machines indépendantes, un seul serveur physique, des ressources partagées.

Les ressources partagées de l’histoire sont…

La promesse des VM : « votre mémoire, votre processeur et même votre disque dur ».

La règle d’allocation des VM est…

« On ne prendra chacun que ce dont on a besoin » — et le total tient dans la capacité.

Une VM refusée…

Contrôler d’abord, allouer ensuite : le refus ne touche pas aux restes.

La première réaction du serveur est…

Il se réveille en sursaut et refuse, avant d’accepter à l’étape 4.

Qui propose le partage des ressources ?

Les VM, très enthousiastes, répondent au serveur fâché.

64 Go, 500 Go : web (16/50) puis base (32/200) laissent…

64−16−32 = 16 Go ; 500−50−200 = 250 Go — la VM test (32/400) sera refusée.

Le partage est…

Certaines ressources peuvent rester dédiées à une VM : le partage reste la règle par défaut.

Quel hyperviseur est de type 2 (hébergé) ?

VirtualBox est une application qui s’installe sur un système existant : c’est le modèle du type 2. ESXi et Xen se placent directement sur le matériel (type 1).

À quoi servent Intel VT-x et AMD-V ?

Ces extensions du processeur permettent à l’hyperviseur de faire tourner le système invité à vitesse quasi native, sans tout émuler en logiciel.

9. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Décompter les ressources d’une VM refusée : le contrôle précède l’allocation.
  • Ne contrôler que la mémoire et oublier le disque : les deux conditions sont simultanées.
  • Mémoriser la conversation dans le désordre : idée, colère, partage, acceptation.
  • Croire que tout se partage : certaines ressources peuvent rester dédiées.

10. Méthodologie de résolution

Allouer comme les VM de l’histoire
  1. Fixer la capacité du serveur : RAM et disque, une seule fois.
  2. Pour chaque demande : vérifier les DEUX restes, puis allouer ou refuser sans toucher aux réserves.
  3. Reporter les restes après chaque allocation : c’est le bilan de fin.

11. Révision active

Résumé essentiel
  • La virtualisation = plusieurs machines indépendantes sur un seul matériel, ressources partagées.
  • Mémoire, processeur, disque : les trois ressources de la promesse.
  • On n’alloue que si la demande tient dans les restes — sinon refus sans consommation.
  • La conversation a un ordre : idée, colère, partage, acceptation.

Checklist de maîtrise

  • Je définis la virtualisation en une phrase d’histoire.
  • Je cite les trois ressources partagées sans regarder.
  • Je calcule les restes après chaque allocation (RAM et disque).
  • Je rejoue la conversation dans l’ordre exact.

Les 11 notions à connaître absolument

  1. machine virtuelle
  2. serveur hôte
  3. ressources partagées
  4. mémoire (RAM)
  5. processeur
  6. stockage (disque)
  7. allocation
  8. capacité restante
  9. Hyperviseur de type 1 : logiciel installé directement sur le matériel (ESXi, Hyper-V, KVM, Xen).
  10. Hyperviseur de type 2 : application installée sur un système existant (VirtualBox, VMware Workstation).
  11. VT-x / AMD-V : extensions du processeur qui permettent d’exécuter une VM à vitesse quasi native.
