Chapitre 3 — Les services virtualisés de l’histoire

Module 3 ≈ 2 h de travail Réservé B1 et plus
Mise en situation

La fin de l’histoire donne l’inventaire : le serveur « hébergeait maintenant une base de données, un site web, un pare-feu virtuel et même un serveur de test. Et pour une fois, il ne s’ennuyait plus ! » Quatre services très différents vivent désormais ensemble. Ce chapitre apprend à inventorier ce qui tourne et à surveiller la charge de chacun.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. citer les quatre services virtualisés et leur rôle ;
  2. classer chaque service dans sa catégorie : données, publication, protection, recette ;
  3. dresser l’inventaire des VM par type de service, dans l’ordre d’apparition ;
  4. mesurer la charge par service et repérer celui qui porte le plus.

1. Quatre services, quatre rôles

L’histoire virtualise quatre services, chacun avec un rôle distinct :

ServiceRôle
Base de donnéesles données de l’entreprise, centralisées
Site webla publication vers les utilisateurs et le monde
Pare-feu virtuella protection du reste du parc
Serveur de testla recette : essayer sans casser la production

Le serveur de test mérite une pause : avant la virtualisation, il fallait une machine physique pour tester ; maintenant, une VM s’allume, essuie les plâtres, s’éteint. C’est l’un des grands bénéfices du partage.

Le même serveur, quatre métiers

Données, publication, protection, recette : quatre fonctions qui n’avaient auparavant droit qu’à quatre machines physiques. Le matériel est unique, les métiers sont multiples.

2. L’inventaire des VM

Gérer un parc, c’est d’abord savoir ce qui tourne. L’inventaire compte les VM par type de service, dans l’ordre de première apparition : « base : 2 vm », « site : 1 vm »… Cet ordre d’apparition est celui du fichier d’inventaire, pas un tri alphabétique — c’est l’ordre dans lequel le parc a grandi.

Un inventaire qui dit aussi les fermes : cinq VM « site » derrière un même site web, trois VM « base » en redondance. Le nombre par service est le premier indicateur de la forme du parc.

L’inventaire en trois gestes

Lire chaque VM et son service, compter par service (ordre d’apparition), rapporter le nombre de services distincts. Trois gestes qui se programment en Bash au chapitre.

3. La charge de chaque service

« On ne prendra chacun que ce dont on a besoin » suppose de mesurer ce qu’on prend. La charge se cumule par service : chaque VM déclare son pourcentage de processeur, le service additionne ses VM. Au-delà de 70 % cumulés, un service entre en zone « à surveiller » — pas encore en panne, mais la marge s’amincit.

Le service « le plus chargé » se repère avec une règle stricte : un service ne devient champion que si sa charge dépasse strictement le maximum connu. À égalité, le premier arrivé garde la couronne — comme dans l’histoire, où chacun ne prend que son dû.

Piège — le test non strict du maximum

Si deux services atteignent 70 %, le premier rencontré doit rester « le plus chargé ». Un test « supérieur ou égal » couronnerait le second à tort : le maximum se met à jour en strictement supérieur.

4. Ce que l’inventaire révèle

L’inventaire et la charge préparent le dimensionnement du chapitre 4 : un service dont la charge cumulée grimpe aura besoin d’une VM supplémentaire ; un service à 5 % pourrait partager mieux. Le parc devient un objet que l’on lit, pas une collection de machines que l’on subit.

Les exercices de ce chapitre

Classer les quatre services de l’histoire, dresser l’inventaire par service dans l’ordre d’apparition, calculer la charge par service avec le maximum strict et le seuil des 70 %.

5. Exercices de code

Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

En cas d’erreur, le bouton Expliquer mon erreur interroge le tuteur : il décrit ce qui s’est passé et par où chercher, sans jamais écrire de code à votre place — c’est le principe de l’exercice.

Exercice 1 — Les services de l’histoire

Bash Niveau 1 — Acquisition

Objectif : Valider les quatre services virtualisés : base, site, pare-feu, test.

L’histoire se termine : le serveur « hébergeait maintenant une base de données, un site web, un pare-feu virtuel et même un serveur de test ». Le script lit n lignes « service categorie » : categorie est un code parmi donnees (base de données), publication (site web), protection (pare-feu) ou recette (serveur de test). Pour chaque ligne il affiche service : OK ou service : ERREUR, puis correctes : X/n.

Entrée du programme
3
base donnees
site publication
pare-feu protection
Sortie attendue
base : OK
site : OK
pare-feu : OK
correctes : 3/3
Deux indices, rédigés en mots
  1. Un case sur le service : base → donnees, site → publication, pare-feu → protection, test → recette.
  2. Le bilan sort une seule fois, après la boucle.

Exercice 2 — Une machine par service : l’inventaire

Bash Niveau 2 — Application

Objectif : Dresser l’inventaire des VM par type de service et compter les catégories.

Le script lit n lignes « vm service » puis affiche chaque ligne vm : service. Ensuite, pour chaque service dans l’ordre de première apparition, il affiche service : X vm, et enfin services : Y — l’inventaire de ce que le serveur héberge maintenant, comme à la fin de l’histoire.

Entrée du programme
3
vm-bd base
vm-web site
vm-bd2 base
Sortie attendue
vm-bd : base
vm-web : site
vm-bd2 : base
base : 2 vm
site : 1 vm
services : 2
Deux indices, rédigés en mots
  1. Nouveau service : [ -z "${compte[$service]+x}" ] → ordre[$g]=$service et g=$((g+1)).
  2. Les bilans sortent après la boucle, dans l’ordre du tableau ordre, puis g.

Exercice 3 — La charge de chaque service

Bash Niveau 3 — Raisonnement

Objectif : Calculer la charge par service et repérer celui qui consomme le plus.

Le script lit n lignes « vm service charge » (charge en % CPU), puis affiche pour chaque service dans l’ordre de première apparition service : X% de charge (somme des charges), puis service le plus charge : NOM (Y%) — le premier atteignant le maximum gagne, comme au support « on ne prendra chacun que ce dont on a besoin » : au-delà de 70 % cumulés, le service est service : X% de charge (a surveiller).

Entrée du programme
4
vm1 base 40
vm2 site 30
vm3 base 20
vm4 test 5
Sortie attendue
base : 60% de charge
site : 30% de charge
test : 5% de charge
service le plus charge : base (60%)
Deux indices, rédigés en mots
  1. Somme par service dans un tableau ; nouveau service → enregistrer l’ordre (g).
  2. Maximum au sens strict : charge > max → max=charge, max_nom=service (le premier atteignant le max gagne).

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Confondre les rôles : la base porte les données, le site publie, le pare-feu protège, le test recette.
  • Trier l’inventaire alphabétiquement au lieu de respecter l’ordre d’apparition.
  • Utiliser un test non strict pour le maximum : le premier arrivé doit gagner à égalité.
  • Oublier le seuil des 70 % : un service cumulé au-delà entre en zone à surveiller.

8. Méthodologie de résolution

Lire son parc
  1. Inventorier : chaque VM avec son service, comptage dans l’ordre d’apparition.
  2. Charger : additionner les déclarations de chaque service, repérer les dépassements de 70 %.
  3. Rapporter : le service le plus chargé, au maximum strict, est celui qu’on regarde en premier.

9. Révision active

Résumé essentiel
  • Quatre services dans l’histoire : base, site web, pare-feu virtuel, serveur de test.
  • Données, publication, protection, recette : quatre rôles, un seul serveur.
  • L’inventaire compte les VM par service, dans l’ordre de première apparition.
  • La charge se cumule par service ; au-delà de 70 % on surveille, le maximum se prend au sens strict.

Checklist de maîtrise

  • Je cite les quatre services et leur catégorie sans note.
  • Je produis un inventaire par service dans l’ordre d’apparition.
  • Je calcule la charge cumulée et j’applique le seuil des 70 %.
  • Je trouve le service le plus chargé avec le test strict.

10. Test de maîtrise

Comment t'auto-évaluer

Le QCM ci-dessus est un test de maîtrise. Lis ton pourcentage :

< 50 % — relis l’inventaire de fin d’histoire et refais le comptage.
50–69 % — rejoue l’exercice d’inventaire jusqu’au sans-faute.
70–89 % — solide : analyse la charge d’un parc fictif de 6 VM.
≥ 95 % — maîtrise : passe au dimensionnement et à la rentabilisation.
