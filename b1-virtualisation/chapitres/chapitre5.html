Chapitre 5 — Les risques de la surcharge

Module 5 ≈ 2 h de travail Réservé B1 et plus
Mise en situation

L’histoire pose elle-même la question finale : « Que se passerait-il si trop de machines ambitieuses étaient créées sur un seul serveur ? » La promesse du partage a une limite : la capacité. Ce chapitre apprend à la respecter, à reconnaître les symptômes de la surcharge et à réagir avant la panne.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. formuler les trois questions techniques de l’histoire : concept, avantages, risques ;
  2. appliquer le seuil de saturation : une VM refusée plutôt qu’un serveur noyé ;
  3. détecter les symptômes de surcharge : CPU, RAM, temps de réponse ;
  4. conseiller l’action de secours : déplacer une VM.

1. Les trois questions techniques de l’histoire

L’histoire n’est pas seulement un conte : elle pose trois questions techniques exactes.

  • Quel concept est illustré ? La mutualisation : plusieurs VM sur un même serveur physique, ressources partagées.
  • Quels avantages ? La rentabilisation à 100 %, moins de machines physiques, moins d’électricité — tout le chapitre 4.
  • Quels risques si trop de VM ? La surcharge : mémoire épuisée, processeur saturé, temps de réponse qui s’effondrent pour tout le monde.
Le revers de la promesse

« On ne prendra chacun que ce dont on a besoin » suppose que le total des besoins tient dans la capacité. Si chacun prend son besoin mais que les besoins s’additionnent trop, le serveur promet plus qu’il n’a : c’est la surcharge.

2. Le seuil de saturation

La défense est simple : ne jamais dépasser la capacité. Chaque VM demande sa charge ; si la charge totale reste dans la capacité, elle est hébergée ; sinon elle est refusée — et sa charge n’est pas comptée. Un refus vaut mieux qu’une saturation : on cherche un autre hôte, on ne noie pas celui-ci.

Cas limite à connaître : le serveur plein. Quand la charge totale atteint exactement la capacité, il reste hébergeable — mais plus rien ne pourra s’ajouter. C’est un état à surveiller, pas encore une panne.

Piège — tester après avoir ajouté

Le contrôle se fait avant l’ajout : si total + charge dépasse la capacité, refuser. Ajouter puis retirer, c’est promettre puis décevoir — le chemin de la panne.

3. Les symptômes de la surcharge

Un serveur surchargé prévient avant de tomber. Trois symptômes, dans l’ordre de détection :

  • CPU au-delà de 90 % : le processeur n’a plus de marge ;
  • RAM au-delà de 90 % : la mémoire promise aux VM menace de manquer ;
  • temps de réponse au-delà de 500 ms : les utilisateurs le sentent déjà.

Un symptôme : la cause est identifiée. Plusieurs symptômes à la fois : cas « multiple » — le serveur est entrain de saturer globalement, la priorité monte.

90, 90, 500

CPU à 90 %, RAM à 90 %, réponses à 500 ms : les trois seuils d’alerte. Au-delà d’un seul, le serveur est en surcharge ; l’action est la même dans tous les cas.

4. L’action de secours : déplacer une VM

Que faire quand la surcharge est détectée ? La réponse du cours tient en quatre mots : déplacer une VM. C’est le privilège de la virtualisation : une machine qui tourne sur un serveur noyé peut rejoindre un hôte qui dort — un autre fainéant à réveiller. Le service continue, l’utilisateur ne voit rien, le serveur respire.

C’est aussi la réponse à la dernière question de réflexion de l’histoire : « comment être efficace mais pas surchargé ? » — en équilibrant : chaque hôte chargé mais aucun noyé, chaque VM prête à déménager.

Les exercices de ce chapitre

Classer les trois questions techniques, respecter le seuil de saturation (avec le cas du serveur plein), détecter les symptômes au seuil 90/90/500 et émettre l’action de déplacement.

Exercice 2 — Le seuil de saturation du serveur

Bash Niveau 2 — Application

Objectif : Surveiller la charge totale et refuser les VM quand le serveur menace de saturer.

La dernière question de l’histoire : « que se passerait-il si trop de machines virtuelles étaient créées sur un seul serveur ? ». Le script lit une ligne capacite (100 par défaut si la ligne vaut -), puis n lignes « vm charge ». La charge totale s’accumule : si elle reste <= capacité, la VM est vm : hebergee ; si elle la dépasse, vm : refusee (saturation) et la charge n’est pas ajoutée. À la fin : charge : X/capacite et hebergees : Y/n — et si X atteint exactement la capacité, une dernière ligne serveur plein.

Entrée du programme
-
3
vm1 40
vm2 40
vm3 30
Sortie attendue
vm1 : hebergee
vm2 : hebergee
vm3 : refusee (saturation)
charge : 80/100
hebergees : 2/3
Deux indices, rédigés en mots
  1. Tester avant d’ajouter : si total + charge <= capacite → hebergee et total augmente, sinon refusee.
  2. Après la boucle : total -eq capacite → afficher « serveur plein ».

Exercice 3 — Les symptômes de la surcharge

Bash Niveau 3 — Raisonnement

Objectif : Détecter les symptômes de surcharge et conseiller l’action du support.

Le script lit n lignes « serveur cpu ram reponses » : cpu et ram en %, reponses = temps de réponse en ms des services hébergés. Symptômes : cpu > 90 OU ram > 90 OU reponses > 500 → le serveur est serveur : surcharge (symptome) avec symptome = cpu, ram, reponses ou multiple (dans cet ordre de détection) ; l’action conseillée est alors serveur : action = deplacer une VM. Sinon serveur : sain. Enfin surcharges : X/n et deplacements : X.

Entrée du programme
3
a 95 50 100
b 60 95 200
c 50 50 600
Sortie attendue
a : surcharge (cpu)
a : action = deplacer une VM
b : surcharge (ram)
b : action = deplacer une VM
c : surcharge (reponses)
c : action = deplacer une VM
surcharges : 3/3
deplacements : 3
Deux indices, rédigés en mots
  1. Compter les symptômes : c=0 ; cpu -gt 90 → c+1 et nom cpu ; ram -gt 90 → idem ; reponses -gt 500 → idem.
  2. c = 0 → sain ; c = 1 → le nom du symptôme ; c >= 2 → multiple ; dans tous les cas de surcharge, action = deplacer une VM.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Ajouter la charge avant de tester : le contrôle précède toujours l’ajout.
  • Confondre « plein » et « saturé » : le plein est l’égalité exacte, il reste fonctionnel.
  • Négliger un symptôme unique : un seul dépassement de seuil fait déjà une surcharge.
  • Charger les hôtes à 100 % systématiquement : aucune marge, aucun déplacement possible.

8. Méthodologie de résolution

Surveiller sans noyer
  1. Fixer la capacité et refuser toute VM qui la ferait dépasser.
  2. Surveiller les trois seuils : CPU 90, RAM 90, réponses 500 — un seul suffit à alerter.
  3. Réagir par déplacement de VM vers un hôte moins chargé, jamais par accumulation.

9. Révision active

Résumé essentiel
  • Trois questions techniques : concept (mutualisation), avantages (rentabilisation), risques (surcharge).
  • Le seuil de saturation se respecte : VM refusée plutôt que serveur noyé ; égalité exacte = serveur plein.
  • Les symptômes : CPU et RAM au-delà de 90 %, réponses au-delà de 500 ms — plusieurs à la fois = multiple.
  • L’action de secours est le déplacement de VM : le privilège de la virtualisation.

Checklist de maîtrise

  • Je formule les trois questions techniques et leurs réponses.
  • J’applique le contrôle avant l’ajout et je reconnais le serveur plein.
  • Je détecte les symptômes dans l’ordre et je nomme le cas multiple.
  • Je conseille le déplacement de VM comme action de secours.
