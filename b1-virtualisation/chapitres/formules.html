Mémo Virtualisation

Les règles de l’histoire sur une page, dans l’ordre du cours. À garder ouvert pendant les exercices et l’atelier.

Le constat : le serveur fainéant

histoire : 1 serveur puissant, 1 systeme, 1 service

  80% du temps a ne rien faire, electricite pour rien



nombres du constat : 48 min (80% d une heure) /

  2 services (seuil du faineant) / 80% du cout

heure perdue : inactif >= 48 min

faineant : moins de 2 services hébergés

energie : W * heures / 1000 = kWh ; x prix = facture

Un constat chiffré convainc ; une impression ne convainc personne.

La virtualisation : le partage

idee de l ingenieur : plusieurs machines sur un seul

  serveur physique, ressources partagées



ressources partagées : mémoire / processeur / disque

regle des VM : « on ne prendra chacun que ce dont on

  a besoin »

allocation : controler les DEUX restes (ram + disque)

  avant d allouer ; refusee = rien n est consommé

conversation : idee → colere → partage → acceptation

Contrôler d’abord, allouer ensuite : la promesse se tient par le calcul.

Les services virtualisés

4 services de la fin de l histoire :

  base de donnees → donnees

  site web        → publication

  pare-feu        → protection

  serveur de test → recette



inventaire : comptage par service, ordre d apparition

charge : somme des charges des VM du service

  au-dela de 70% cumules → a surveiller

maximum : mise a jour en STRICTEMENT superieur

  (a egalite, le premier arrivé garde le titre)

Un parc se lit : inventaire d’abord, charge ensuite.

Rentabilisation et consolidation

reveil d un serveur : avant < 30% ET apres >= 80%

  sinon : en progres (apres > avant) / insuffisant



nb de VM : PLAFOND de (cout total / cout d une VM)

  = division entiere + 1 si reste non nul

economie : cout parc physique - cout parc virtualise

placement : premier hote suffisant, ordre du fichier

  VM sans place = rien n est décompté

hote a 0 restant = rentabilise a 100%

2,5 VM font 3 : le plafond, pas l’arrondi au plus proche.

Surcharge et vigilance

regle anti-saturation : controler AVANT d ajouter

  total + charge > capacite → refusee (saturation)

serveur plein : total == capacite exactement



symptomes (dans l ordre) : cpu > 90% / ram > 90% /

  reponses > 500 ms ; plusieurs a la fois = multiple

action de secours : deplacer une VM vers un hote

  moins chargé (le privilège de la virtualisation)

Un refus vaut mieux qu’une saturation : on déménage, on ne noie pas.

L’argumentaire final

pitch en 4 etapes (l ordre de l histoire) :

  1 constat → gaspillage

  2 idee     → virtualisation

  3 preuve   → rentabilisation

  4 verdict  → parc plein



bilan avant/apres : reveilles + moyenne avant +

  moyenne apres (divisions entieres)

plan de reveil : v = virtualisable / e = econome

  (< 30%) / s = sûr (sauvegardes) ; premiere lettre

  manquante = prochaine action

verdict : plan pret / a ajuster (charge > 200) /

  impossible (un serveur bloque)

La morale de l’histoire : « il se plaignait quand même un peu » — la vigilance ne s’arrête jamais.

Erreurs fréquentes à éviter

  • Confondre puissance (W) et énergie (kWh) dans la facture.
  • Décompter les ressources d’une VM refusée : le contrôle précède l’allocation.
  • Trier l’inventaire alphabétiquement au lieu de l’ordre d’apparition.
  • Maximum non strict : à égalité, le premier arrivé doit gagner.
  • Arrondir 2,5 VM à 2 : c’est le plafond qui fait foi.
  • Tester la saturation après l’ajout : toujours avant.
  • Négliger un symptôme unique : un seul dépassement fait déjà une surcharge.
  • Annoncer le verdict avant le constat dans le pitch.
  • Dire « à étudier » sans la lettre manquante du plan v/e/s.
  • Oublier la charge des VM dans le plan final.
