Chapitre 1

🗃️ Le modèle relationnel

Relations, attributs, tuples, clés primaires et étrangères — les fondations des bases de données.

Objectifs du chapitre

  • Comprendre le rôle d'un SGBD et le modèle relationnel
  • Maîtriser le vocabulaire R.A.T.D. (Relation, Attribut, Tuple, Domaine)
  • Identifier clés primaires et clés étrangères

Pourquoi les bases de données ?

🔧 Analogie AutoBot : Imagine un bibliothécaire qui gère des milliers de livres. Sans système, retrouver un livre prendrait des heures. Une base de données, c'est le catalogue organisé qui permet de retrouver n'importe quel livre en secondes !

Avant les bases de données, on stockait les informations dans des fichiers plats (texte, CSV…). Problèmes :

  • Redondance : mêmes données copiées partout
  • Incohérence : une modification oubliée dans un fichier
  • Pas de sécurité : tout le monde accède à tout
  • Difficile à interroger : pas de langage standard
💡 Solution : Le Système de Gestion de Base de Données (SGBD) — un logiciel spécialisé qui organise, stocke, interroge et protège les données. Exemples : MySQL, PostgreSQL, Oracle, SQL Server, SQLite.

Le modèle relationnel

Inventé par Edgar F. Codd en 1970, le modèle relationnel organise les données sous forme de tables (appelées relations).

🧠 Mnémonique R.A.T.D.

Relation — Attribut — Tuple — Domaine

Les 4 concepts fondamentaux du modèle relationnel.

📋 Vocabulaire clé

Terme techniqueÉquivalent courantExemple
RelationTableETUDIANTS
AttributColonnenom, prenom, age
TupleLigne / Enregistrement(1, "Ali", "Ben", 20)
DomaineType de valeursINTEGER, VARCHAR, DATE
SchémaStructure de la tableETUDIANTS(id, nom, prenom, age)
🔧 Analogie : Une relation = un classeur Excel. Les colonnes = les en-têtes (attributs). Chaque ligne = un enregistrement (tuple). Le type de données attendu dans chaque colonne = le domaine.

Notation d'un schéma

On note un schéma relationnel ainsi :

Schéma relationnel
ETUDIANTS(id, nom, prenom, date_naissance, email)
COURS(code_cours, intitule, credits)
INSCRIPTIONS(#id_etudiant, #code_cours, note)

🔑 Conventions

  • Souligné = clé primaire
  • # = clé étrangère (référence vers une autre table)
  • NOM EN MAJUSCULES = nom de la relation
  • Attributs entre parenthèses, séparés par des virgules

La clé primaire (PK)

🧠 Mnémonique U.N.I.

Unique — Non-null — Immuable

Les 3 propriétés d'une clé primaire.

La clé primaire est l'attribut (ou combinaison d'attributs) qui identifie de manière unique chaque tuple.

🔧 Analogie : La clé primaire, c'est comme ton numéro de sécurité sociale — chaque personne en a un et un seul, et deux personnes ne partagent jamais le même.

Propriétés de la clé primaire

PropriétéSignificationExemple violation
UniquePas de doublon dans la colonneDeux étudiants avec id=1 → ❌
Non-nullJamais videUn étudiant sans id → ❌
ImmuableNe change pas après créationModifier l'id d'un étudiant → ❌
💡 Clé candidate vs clé primaire : Plusieurs colonnes pourraient servir de clé (email, numéro étudiant) — ce sont les clés candidates. On en choisit UNE comme clé primaire.

Types de clés primaires

  • Simple : un seul attribut → ETUDIANTS(id, nom, …)
  • Composée : plusieurs attributs → INSCRIPTIONS(id_etudiant, code_cours, note)
  • Artificielle : auto-générée (ex: SERIAL, AUTO_INCREMENT) quand aucun attribut naturel ne convient

La clé étrangère (FK)

La clé étrangère crée un lien entre deux tables. Elle référence la clé primaire d'une autre table.

🔧 Analogie : Imagine un ticket de cinéma. Le numéro de salle sur ton ticket (clé étrangère) pointe vers une salle précise dans le cinéma (clé primaire de la table SALLES). Le ticket n'invente pas de salle — il référence une salle existante.
Exemple FK
ETUDIANTS(id, nom, prenom)
NOTES(id_note, #id_etudiant, matiere, valeur)
       │                │
       │                └── clé étrangère → ETUDIANTS.id
       └── clé primaire
⚠️ Intégrité référentielle : On ne peut PAS insérer un id_etudiant dans NOTES qui n'existe pas dans ETUDIANTS. Le SGBD bloque l'opération.

Règles de suppression (ON DELETE)

ActionComportement
RESTRICTInterdit de supprimer si des FK pointent
CASCADESupprime aussi les lignes filles
SET NULLMet NULL dans les FK concernées
SET DEFAULTRemet la valeur par défaut

Types de relations

🧠 Mnémonique 1:1 / 1:N / M:N

1:1 = Personne ↔ Passeport | 1:N = Professeur → Cours | M:N = Étudiants ↔ Cours

Les 3 types de relations

TypeSignificationImplémentation
1:1Un enregistrement lié à un seulFK UNIQUE dans l'une des deux tables
1:NUn enregistrement lié à plusieursFK dans la table côté N
M:NPlusieurs liés à plusieursTable de jonction (table pivot)
Relation M:N avec table de jonction
ETUDIANTS(id_etu, nom, prenom)
COURS(id_cours, intitule, credits)
INSCRIPTIONS(#id_etu, #id_cours, date_inscription, note)
              └───────────────── table de jonction
💡 Astuce : Une relation M:N se décompose TOUJOURS en deux relations 1:N via une table de jonction. C'est la raison d'être d'INSCRIPTIONS !

Domaines et types de données

Chaque attribut a un domaine = l'ensemble des valeurs autorisées.

Types SQL courants

TypeDescriptionExemple
INTEGERNombre entier42, -5, 0
FLOAT / REALNombre décimal3.14, -0.5
VARCHAR(n)Texte variable (max n car.)'Ali', 'SQL'
CHAR(n)Texte fixe (n car.)'FR', 'US'
DATEDate (AAAA-MM-JJ)'2025-01-15'
BOOLEANVrai/FauxTRUE, FALSE

⚠️ NULL : NULL ≠ 0 ≠ '' ≠ 'NULL'. NULL signifie « valeur inconnue ou absente ». Toute opération avec NULL donne NULL (sauf IS NULL).

Exercices guidés

Identifier clé primaire et étrangère

Énoncé : On a les tables suivantes :

ETUDIANT(NumEtu, Nom, Prenom, DateNaissance)
INSCRIPTION(NumEtu, CodeModule, Annee, Note)

Question : Identifier les clés primaires et étrangères.

Étape 1 — Clés primaires
ETUDIANT : NumEtu est la clé primaire
  → Identifie de manière unique chaque étudiant

INSCRIPTION : (NumEtu, CodeModule, Annee) est la clé primaire
  → Un étudiant peut s'inscrire à plusieurs modules sur différentes années
  → Il faut les 3 attributs pour identifier une inscription unique
Étape 2 — Clés étrangères
INSCRIPTION.NumEtu → ETUDIANT.NumEtu
  → C'est une clé étrangère : elle référence la clé primaire d'ETUDIANT
  → Garantit qu'on ne peut pas inscrire un étudiant inexistant
Vérification des propriétés
✓ Unicité de la clé primaire d'ETUDIANT
✓ Intégrité référentielle entre INSCRIPTION et ETUDIANT
✓ Pas de redondance dans ETUDIANT

Passage du schéma conceptuel au schéma relationnel

Énoncé : Traduire en relationnel : Un CLIENT passe des COMMANDES contenant des PRODUITS.

Étape 1 — Identifier les entités
CLIENT(IdClient, Nom, Ville)
PRODUIT(IdProd, Libelle, Prix)
Étape 2 — Traduire l'association 1:N (Client → Commande)
COMMANDE(NumCmd, DateCmd, IdClient#)
  → La clé étrangère IdClient# migre côté "N"
  → Un client peut avoir plusieurs commandes
Étape 3 — Traduire l'association N:M (Commande ↔ Produit)
LIGNE_COMMANDE(NumCmd#, IdProd#, Quantite)
  → Table de jonction avec clé primaire composite
  → Deux clés étrangères : NumCmd# et IdProd#
Schéma final
CLIENT(IdClient, Nom, Ville)
COMMANDE(NumCmd, DateCmd, IdClient#)
PRODUIT(IdProd, Libelle, Prix)
LIGNE_COMMANDE(NumCmd#, IdProd#, Quantite)
