Chapitre 5

🧹 La Normalisation

1NF → 2NF → 3NF → BCNF — éliminer la redondance et les anomalies.

Objectifs du chapitre

  • Construire un MCD avec entités, associations et cardinalités
  • Identifier les identifiants et les cardinalités (0,n / 1,1 / etc.)
  • Appliquer les règles de passage MCD → MLD

Pourquoi normaliser ?

🔧 Analogie AutoBot : Imagine un placard en bazar où les chaussettes sont mélangées avec les chemises. Normaliser = ranger le placard : chaque tiroir a un rôle précis, rien n'est en double, et on retrouve tout facilement.

Sans normalisation, une base de données souffre de 3 types d'anomalies :

Les 3 anomalies

AnomalieProblèmeExemple
InsertionImpossible d'ajouter sans données inutilesAjouter un cours sans étudiant inscrit
Mise à jourIncohérence si on oublie une copieChanger l'adresse d'un client dans 1 ligne sur 5
SuppressionPerte de données non voulueSupprimer le dernier étudiant d'un cours supprime aussi le cours
🧠 Mnémonique I.M.S.

Insertion — Mise à jour — Suppression

Les 3 anomalies que la normalisation élimine.

Dépendances fonctionnelles (DF)

Une dépendance fonctionnelle A → B signifie : si on connaît A, on connaît B de manière unique.

🔧 Analogie : Connaître le numéro de sécurité sociale → connaître le nom, prénom, date de naissance. Le numéro détermine les autres infos.
Exemples de DF
id_etudiant → nom, prenom, email     (l'id détermine tout)
email → id_etudiant                   (email unique aussi)
(id_etu, id_cours) → note             (clé composée → note)
ville → code_postal  ❌ FAUX !        (une ville peut avoir plusieurs CP)

Types de DF

TypeDéfinitionExemple
DF élémentaireAucun sous-ensemble de A ne détermine B(id_etu, id_cours) → note ✓
DF partielleUn sous-ensemble de la clé suffitid_etu → nom (ne dépend pas de id_cours) ⚠️
DF transitiveA → B → C (indirect)id → ville → region ⚠️

Première forme normale (1NF)

🧠 Règle 1NF : A.U.P.

Atomique — Unique (pas de répétition) — PK définie

1NF = chaque cellule contient une valeur atomique (indivisible). Pas de listes, pas de groupes répétitifs.

Avant 1NF ❌
| id | nom    | telephones           |
|----|--------|----------------------|
| 1  | Ali    | 0601, 0602, 0603     |  ← liste = PAS atomique !
| 2  | Marie  | 0701                 |
Après 1NF ✅
PERSONNES(id, nom)
TELEPHONES(id_tel, #id_personne, numero)

| id_tel | id_personne | numero |
|--------|-------------|--------|
| 1      | 1           | 0601   |
| 2      | 1           | 0602   |
| 3      | 1           | 0603   |
| 4      | 2           | 0701   |
💡 Test 1NF : « Y a-t-il des virgules, des listes ou des ensembles dans une cellule ? » → Si oui, pas en 1NF !

Deuxième forme normale (2NF)

2NF = 1NF + pas de dépendance partielle. Tous les attributs non-clé dépendent de la clé ENTIÈRE (pas d'un sous-ensemble).

🔧 Analogie : Si la clé est un verrou à 2 clés, chaque information dans le tiroir doit nécessiter les DEUX clés pour être retrouvée. Si une info n'a besoin que d'UNE clé, elle est mal rangée.
Avant 2NF ❌ (DF partielle)
INSCRIPTIONS(id_etu, id_cours, note, nom_etu, intitule_cours)
                                        │          │
                                        └── dépend seulement de id_etu
                                                   └── dépend seulement de id_cours
Après 2NF ✅ (décomposition)
ETUDIANTS(id_etu, nom_etu)
COURS(id_cours, intitule_cours)
INSCRIPTIONS(#id_etu, #id_cours, note)
⚠️ Quand s'applique 2NF ? Uniquement sur les tables avec une clé composée. Si la clé primaire est simple (un seul attribut), la table est déjà en 2NF (si elle est en 1NF).

Troisième forme normale (3NF)

3NF = 2NF + pas de dépendance transitive. Aucun attribut non-clé ne détermine un autre attribut non-clé.

🧠 Résumé 3NF « La clé, toute la clé, rien que la clé »

Chaque attribut non-clé dépend :
• de la clé (1NF) → valeurs atomiques
• de toute la clé (2NF) → pas de DF partielle
• de rien que la clé (3NF) → pas de DF transitive

Avant 3NF ❌ (DF transitive)
ETUDIANTS(id, nom, ville, region)
    id → ville → region     ← transitive !
    (la region dépend de ville, pas directement de id)
Après 3NF ✅
ETUDIANTS(id, nom, #ville)
VILLES(ville, region)

Forme normale de Boyce-Codd (BCNF)

BCNF = version plus stricte de 3NF. Règle : tout déterminant (côté gauche d'une DF) doit être une clé candidate.

🔧 Analogie : En 3NF, on dit « les non-clés ne déterminent pas d'autres non-clés ». En BCNF, on va plus loin : « SEULES les clés candidates ont le droit de déterminer quoi que ce soit ».

Hiérarchie des formes normales

FormeRègle ajoutéeÉlimine
1NFValeurs atomiques + PKGroupes répétitifs
2NF+ Pas de DF partiellesDépendances partielles
3NF+ Pas de DF transitivesDépendances transitives
BCNF+ Tout déterminant est clé candidateCas résiduels rares
💡 En pratique : 3NF suffit dans 95% des cas. BCNF est un bonus pour les puristes. L'examen teste surtout 1NF → 2NF → 3NF.

Méthode pas à pas

🔧 Procédure de normalisation

  1. Identifier les DF : lister toutes les dépendances fonctionnelles
  2. Vérifier 1NF : valeurs atomiques ? PK définie ?
  3. Vérifier 2NF : DF partielles ? (seulement si clé composée)
  4. Vérifier 3NF : DF transitives ?
  5. Décomposer : créer de nouvelles tables pour chaque violation
  6. Vérifier : les FK relient correctement les tables décomposées

Exercices guidés

Normaliser une table pas à pas (1NF → 2NF → 3NF)

Table de départ (non normalisée) :

COMMANDE(NumCmd, DateCmd, NomClient, VilleClient,
         Produit1, Qte1, Produit2, Qte2)
Étape 1 — Passage en 1NF (atomicité)

Problème : attributs répétitifs (Produit1/Qte1, Produit2/Qte2).

COMMANDE_1NF(NumCmd, DateCmd, NomClient, VilleClient,
             IdProd, Qte)
-- Chaque produit = une ligne distincte
-- Clé primaire : (NumCmd, IdProd)
Étape 2 — Passage en 2NF (dépendances totales)

Problème : NomClient et VilleClient dépendent de NumCmd seulement (pas de IdProd).

COMMANDE_2NF(NumCmd, DateCmd, NomClient, VilleClient)
DETAIL_CMD(NumCmd#, IdProd, Qte)
-- NomClient ne dépend que de NumCmd → déplacé
Étape 3 — Passage en 3NF (pas de dépendance transitive)

Problème : VilleClient dépend de NomClient (transitif via NumCmd).

COMMANDE_3NF(NumCmd, DateCmd, NomClient#)
CLIENT(NomClient, VilleClient)
DETAIL_CMD(NumCmd#, IdProd, Qte)

✓ 3NF atteinte : chaque attribut non-clé dépend
  directement et uniquement de la clé primaire.

Identifier les dépendances fonctionnelles

Table : EMPLOYE(NumEmp, Nom, NumDept, NomDept, NomChef)

Lister les dépendances fonctionnelles (DF)
NumEmp → Nom          (chaque n° identifie un nom)
NumEmp → NumDept      (chaque employé a un département)
NumDept → NomDept     (chaque n° de dept a un nom)
NumDept → NomChef     (chaque dept a un chef)

Dépendance transitive détectée :
  NumEmp → NumDept → NomDept
  NumEmp → NumDept → NomChef
Décomposition en 3NF
EMPLOYE_3NF(NumEmp, Nom, NumDept#)
DEPARTEMENT(NumDept, NomDept, NomChef)

✓ Plus de dépendance transitive
✓ Mise à jour du chef = 1 seule ligne à modifier
