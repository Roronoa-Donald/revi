Le modèle Entité-Relation (E-R)

🔧 Analogie AutoBot : Le schéma E-R est le plan d'architecte avant de construire la maison (la base de données). On dessine les pièces (entités), les portes entre elles (relations) et les règles de la maison (contraintes).
🧠 Mnémonique E.A.R.

Entité — Attribut — Relation

Les 3 composants d'un schéma E-R.

Composants du schéma E-R

ComposantReprésentationExemple
EntitéRectangleETUDIANT, COURS, PROFESSEUR
AttributOvale relié à l'entiténom, prenom, age
Attribut cléOvale soulignéid
RelationLosangeINSCRIT, ENSEIGNE
CardinalitéNombres sur les liens1..N, 0..*, 1..1
Exemple schéma E-R (texte)
┌──────────────┐         ┌──────────────┐
│   ETUDIANT   │         │    COURS     │
│──────────────│         │──────────────│
│ id_etu       │   M:N   │ id_cours     │
│ nom          │◄─INSCRIT─►│ intitule     │
│ prenom       │         │ credits      │
│ age          │         │              │
└──────────────┘         └──────────────┘
      La relation INSCRIT a un attribut : note

Les cardinalités

La cardinalité indique combien d'instances d'une entité participent à une relation.

Notation des cardinalités

NotationSignificationExemple
1..1Exactement unUn passeport → UN citoyen
0..1Zéro ou unUn étudiant → 0 ou 1 stage
1..NUn à plusieursUn dept → 1 à N employés
0..N ou *Zéro à plusieursUn étudiant → 0 à N cours
💡 Comment lire : Lisez TOUJOURS la cardinalité dans le sens de chaque entité :
« Un ETUDIANT peut être inscrit à 0..N cours. Un COURS peut avoir 0..N étudiants inscrits. » → c'est du M:N.

Passage E-R → Schéma relationnel

🧠 Règles de conversion E-R → Relationnel

Entité → Table | Attribut → Colonne | Clé E-R → PK

Règles selon la cardinalité

CardinalitéTransformation
1:1FK dans l'une des deux tables (ou fusionner)
1:NFK dans la table côté N (le « plusieurs »)
M:NCréer une table de jonction avec les PK des deux entités
Exemple complet
E-R :
  PROFESSEUR (1) ───ENSEIGNE──── (N) COURS
  ETUDIANT   (M) ───INSCRIT───── (N) COURS  [attribut: note]

Relationnel :
  PROFESSEURS(id_prof, nom, prenom, specialite)
  COURS(id_cours, intitule, credits, #id_prof)      ← FK côté N
  ETUDIANTS(id_etu, nom, prenom, date_naissance)
  INSCRIPTIONS(#id_etu, #id_cours, note)             ← table de jonction M:N
💡 Astuce pour M:N : La table de jonction a une clé composée des PK des deux entités. Elle peut avoir des attributs propres (ici : note, date_inscription…).

Contraintes d'intégrité

🧠 Mnémonique E.R.D.U.

Entité — Référentielle — Domaine — Utilisateur

Les 4 types de contraintes d'intégrité.

Les 4 contraintes

ContrainteRègleSQL
EntitéChaque table a une PK unique et non-nullPRIMARY KEY
RéférentielleToute FK pointe vers une PK existanteREFERENCES table(pk)
DomaineLes valeurs respectent le type et les contraintesCHECK, NOT NULL, types
UtilisateurRègles métier spécifiquesCHECK, TRIGGER
SQL — Toutes les contraintes ensemble
CREATE TABLE inscriptions (
    id_etu   INTEGER NOT NULL,
    id_cours INTEGER NOT NULL,
    note     DECIMAL(4,2) CHECK (note >= 0 AND note <= 20),
    date_insc DATE DEFAULT CURRENT_DATE,
    
    PRIMARY KEY (id_etu, id_cours),                -- contrainte d'entité
    FOREIGN KEY (id_etu) REFERENCES etudiants(id)  -- contrainte référentielle
        ON DELETE CASCADE,
    FOREIGN KEY (id_cours) REFERENCES cours(id)
        ON DELETE RESTRICT
);

-- Contrainte utilisateur (métier)
ALTER TABLE inscriptions 
ADD CONSTRAINT chk_date 
CHECK (date_insc >= '2020-01-01');

Pièges classiques à l'examen

⚠️ Piège n°1 — Les 4 contraintes (E.R.D.U.) : Ne confondez pas : Entité (clé primaire unique), Référentielle (clé étrangère valide), Domaine (valeurs autorisées), Utilisateur (règles métier). Chacune a un rôle différent !
⚠️ Piège n°2 — ON DELETE CASCADE : Si vous supprimez un enregistrement parent avec CASCADE, tous les enfants référencés sont supprimés aussi ! Utilisez RESTRICT ou SET NULL si vous voulez empêcher la suppression en cascade.
⚠️ Piège n°3 — Clé naturelle vs surrogate : Utiliser un numéro de sécurité sociale ou un email comme clé primaire est risqué (ils peuvent changer !). Préférez une clé artificielle auto-incrémentée (surrogate key).

Exercices guidés

Concevoir un schéma avec contraintes d'intégrité

Énoncé : Concevoir le schéma SQL pour une bibliothèque : LIVRE, ADHERENT, EMPRUNT.

Étape 1 — Créer les tables avec contraintes
CREATE TABLE ADHERENT (
    id_adh   INT PRIMARY KEY,
    nom      VARCHAR(50) NOT NULL,
    email    VARCHAR(100) UNIQUE,          -- Contrainte d'unicité
    date_ins DATE DEFAULT CURRENT_DATE
);

CREATE TABLE LIVRE (
    isbn     VARCHAR(13) PRIMARY KEY,
    titre    VARCHAR(100) NOT NULL,
    auteur   VARCHAR(50),
    dispo    BOOLEAN DEFAULT TRUE
);

CREATE TABLE EMPRUNT (
    id_emp   INT PRIMARY KEY AUTO_INCREMENT,
    id_adh   INT NOT NULL,
    isbn     VARCHAR(13) NOT NULL,
    date_emp DATE NOT NULL,
    date_ret DATE,
    FOREIGN KEY (id_adh) REFERENCES ADHERENT(id_adh)
        ON DELETE RESTRICT,                -- Empêche suppression si emprunts
    FOREIGN KEY (isbn) REFERENCES LIVRE(isbn)
        ON UPDATE CASCADE,                 -- Met à jour si ISBN change
    CHECK (date_ret IS NULL OR date_ret >= date_emp)
        -- La date de retour ne peut précéder l'emprunt
);
Étape 2 — Tester les contraintes
-- ✓ Insertion valide :
INSERT INTO EMPRUNT VALUES (1, 101, '978-2-01-000001', '2024-01-15', NULL);

-- ✗ Violation d'intégrité référentielle :
INSERT INTO EMPRUNT VALUES (2, 999, '978-2-01-000001', '2024-01-20', NULL);
-- ERREUR : id_adh 999 n'existe pas dans ADHERENT

-- ✗ Violation du CHECK :
INSERT INTO EMPRUNT VALUES (3, 101, '978-2-01-000001', '2024-01-15', '2024-01-10');
-- ERREUR : date_ret (10 jan) < date_emp (15 jan)
