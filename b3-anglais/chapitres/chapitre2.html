Chapitre 2 — Maîtrise de la Documentation Technique & Spécifications d’API

Module 2 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Lors de l’intégration d’un nouveau service de paiement (Stripe), d’une passerelle SMS (Twilio) ou d’un microservice interne développé par une équipe basée à l’étranger, l’ingénieur doit être capable de lire, comprendre et auditer une documentation technique rédigée intégralement en anglais sans recourir à des outils de traduction approximatifs. Une mécompréhension des verbes normatifs d’une RFC (confondre SHOULD et MUST) ou l’ignorance des codes de statut HTTP expose l’architecture à des failles de sécurité majeures, des pertes de transactions ou des blocages d’intégration.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. décortiquer la structure normalisée d’une documentation d’API REST (endpoints, paramètres d’URI, en-têtes Bearer et payloads JSON) ;
  2. interpréter les codes de statut HTTP standard (200, 201, 204, 400, 401, 403, 404, 500, 502, 503) et leurs implications opérationnelles ;
  3. auditer et classifier les clauses contractuelles d’une spécification technique selon les mots-clés normatifs de la RFC 2119 ;
  4. concevoir un fichier README.md technique conforme aux standards de l’industrie (prérequis, installation, configuration d’environnement et dépannage) ;
  5. développer en Python 3 des linters d’OpenAPI, des analyseurs de conformité RFC 2119 et des générateurs de sommaires Markdown avec ancres.

1. Anatomie d’une Spécification d’API REST & Standards OpenAPI

Une documentation d’API de niveau industriel (OpenAPI / Swagger) formalise le contrat d’échange entre le fournisseur de service et les développeurs intégrateurs :

Les Verbes d’Action HTTP & Idempotence

  • GET (Read) : récupération de ressources sans effet de bord. Sûr et idempotent.
  • POST (Create) : création d’une nouvelle ressource ou déclenchement d’un traitement. Non idempotent (deux appels créent deux ressources distinctes).
  • PUT (Replace) : remplacement intégral d’une ressource existante à l’URI spécifiée. Idempotent.
  • PATCH (Update) : modification partielle des attributs d’une ressource existante. Généralement non idempotent.
  • DELETE (Remove) : suppression définitive de la ressource. Idempotent.

Codes de Statut HTTP et Gestion des Erreurs

  • 2xx Success : 200 OK (succès avec contenu), 201 Created (ressource créée), 204 No Content (succès sans corps renvoyé, typique sur DELETE).
  • 4xx Client Error : 400 Bad Request (syntaxe JSON invalide), 401 Unauthorized (token manquant ou invalide), 403 Forbidden (droits insuffisants), 404 Not Found.
  • 5xx Server Error : 500 Internal Server Error (exception non gérée), 502 Bad Gateway (serveur amont injoignable), 503 Service Unavailable (surcharge temporaire), 504 Gateway Timeout.

2. La Norme RFC 2119 : Mots-clés Normatifs d’Exigence Technique

Rédigée par Scott Bradner en 1997 pour l’IETF, la norme RFC 2119 élimine toute subjectivité dans la rédaction des spécifications logicielles et protocolaires :

Mot-clé NormatifDegré d’ObligationConséquence pour l’Ingénieur
MUST / REQUIRED / SHALLExigence absolue (P1)Le système n’est pas interopérable ou non conforme s’il ne respecte pas cette directive. Aucun compromis toléré.
MUST NOT / SHALL NOTInterdiction absolue (P1)Comportement formellement prohibé. L’implémentation de ce comportement invalide la certification.
SHOULD / RECOMMENDEDForte recommandation (P2)Des raisons valables peuvent exister dans des circonstances particulières pour ne pas l’appliquer, mais le choix doit être motivé et documenté.
SHOULD NOT / NOT RECOMMENDEDPratique déconseillée (P2)Comportement indésirable qui doit être évité sauf justification technique explicite.
MAY / OPTIONALOption purement facultative (P3)L’implémenteur peut librement choisir d’inclure ou non l’élément sans compromettre l’interopérabilité générale.

3. Conception d’un README.md Professionnel : Clarté & Reproductibilité

Le fichier README.md constitue la vitrine technique et le premier point de contact avec un référentiel de code. Un bon README permet à un nouvel ingénieur d’exécuter le projet en moins de 5 minutes :

Les Six Sections Obligatoires d’un README

  1. Project Title & One-line Pitch : intitulé clair et énoncé de valeur immédiat (rôle du composant dans l’architecture).
  2. Prerequisites & Dependencies : versions exactes du runtime (Node 20, Python 3.11), outils requis (Docker, Make) et services tiers.
  3. Quickstart / Installation : commandes en bloc de code copiables directement (npm install, pip install -r requirements.txt).
  4. Configuration / Environment Variables : tableau exhaustif des variables d’environnement avec valeurs par défaut et caractère obligatoire.
  5. Running Tests : commande pour exécuter la suite de tests automatisée (npm test, pytest).
  6. Troubleshooting & FAQ : recensement des erreurs d’installation courantes et procédures de contournement.

JWT_SECRETString(Required)Clé cryptographique de signature des tokens de session.

Exercice 1 — Analyseur et auditeur de conformité RFC 2119

Étude de cas Niveau 1 — Acquisition

Objectif : Analyser les mots-clés normatifs d’une spécification technique en anglais (RFC 2119) pour déterminer le niveau d’exigence contractuel.

La norme RFC 2119 définit avec rigueur les mots-clés indiquant les exigences impératives, recommandées ou optionnelles dans les standards de l'Internet.
Pour chaque cas d’application des clauses techniques au format :
RFC_CLAUSE id=<ID> text=<clause en anglais>.

Règles d'évaluation (recherche de mots entiers, insensible à la casse) :
- Si le texte contient MUST NOT ou SHALL NOT :
LEVEL=ABSOLUTE_PROHIBITION | PRIORITY=P1_CRITICAL
- Sinon, si le texte contient MUST, REQUIRED ou SHALL :
LEVEL=ABSOLUTE_REQUIREMENT | PRIORITY=P1_CRITICAL
- Sinon, si le texte contient SHOULD NOT ou NOT RECOMMENDED :
LEVEL=DEPRECATED_PRACTICE | PRIORITY=P2_RECOMMENDED
- Sinon, si le texte contient SHOULD ou RECOMMENDED :
LEVEL=BEST_PRACTICE | PRIORITY=P2_RECOMMENDED
- Sinon, si le texte contient MAY ou OPTIONAL :
LEVEL=OPTIONAL_FEATURE | PRIORITY=P3_OPTIONAL
- Dans les autres cas :
LEVEL=INFORMATIONAL | PRIORITY=P4_INFO

Afficher :
RFC_AUDIT: <ID> -> LEVEL=<LEVEL> | PRIORITY=<PRIORITY>

Cas d’exemple
RFC_CLAUSE id=REQ-101 text=The client MUST validate the TLS certificate chain before sending data.
Résolution attendue
RFC_AUDIT: REQ-101 -> LEVEL=ABSOLUTE_REQUIREMENT | PRIORITY=P1_CRITICAL

Le mot-clé MUST impose une exigence absolue de niveau P1.

Deux indices, rédigés en mots
  1. Traiter les négations ("MUST NOT", "SHALL NOT", "SHOULD NOT") avant les affirmations simples.
  2. Utiliser re.search avec \b pour ne pas confondre "may" dans un autre mot comme "maybe".

Exercice 2 — Linter de documentation d’endpoints REST & OpenAPI

Étude de cas Niveau 2 — Application

Objectif : Vérifier la validité et la complétude de la documentation d’une route d’API REST (méthode HTTP, format de chemin, authentification et codes de retour).

Dans la documentation d'API (type Swagger/OpenAPI ou Stripe/Twilio), chaque endpoint doit respecter des conventions strictes.
Pour chaque cas d’application des définitions d'endpoints au format :
API_ENDPOINT method=<METHOD> path=<PATH> auth=<true|false> status_codes=<c1,c2,...>.

Règles de validation :
1. Méthode HTTP : doit appartenir à GET, POST, PUT, DELETE, PATCH. Si invalide : ajouter INVALID_METHOD.
2. Chemin (URI) : doit débuter par / et ne contenir que des caractères alphanumériques, tirets, underscores, slashes et accolades de variables d'URL ({id}). Si invalide : ajouter INVALID_PATH_FORMAT.
3. Succès : la liste des codes doit comporter au moins un code de succès (200, 201 ou 204). Si absent : ajouter MISSING_SUCCESS_STATUS.
4. Authentification : si auth=true, la liste doit contenir au moins un code d'erreur d'authentification ou d'autorisation (401 ou 403). Si absent : ajouter MISSING_AUTH_ERROR_CODE.

Afficher :
- Si aucune anomalie :
ENDPOINT_STATUS: <METHOD> <PATH> -> VALID
- Si des anomalies sont détectées :
ENDPOINT_STATUS: <METHOD> <PATH> -> INVALID | ISSUES=<issue1,issue2,...> (anomalies triées par ordre alphabétique).

Cas d’exemple
API_ENDPOINT method=GET path=/api/v1/users auth=true status_codes=200,401,500
Résolution attendue
ENDPOINT_STATUS: GET /api/v1/users -> VALID

Méthode GET valide, chemin conforme, code 200 présent et code 401 présent pour auth=true.

Deux indices, rédigés en mots
  1. Valider le format du chemin avec une expression régulière : ^/[a-zA-Z0-9/_{}-]+$
  2. Trier la liste des anomalies avec sorted() avant de la joindre avec une virgule.

Exercice 3 — Générateur de sommaire technique Markdown et slugification

Étude de cas Niveau 3 — Raisonnement

Objectif : Analyser une documentation technique en Markdown, extraire les titres h1, h2, h3 et générer une table des matières indentée avec ancres de liens conformes.

Une documentation technique de qualité professionnelle (fichier README.md ou spécification d'architecture) comporte une table des matières (Table of Contents) structurée permettant une navigation rapide.
Pour chaque cas d’application des lignes d'un document Markdown.

Règles d'extraction et de formatage :
- Les lignes de titres commencent par # (h1), ## (h2) ou ### (h3). Ignorer les autres lignes.
- Pour chaque titre, nettoyer les espaces superflus et construire un slug d'ancre :
* Convertir le texte du titre en minuscules.
* Remplacer tout caractère qui n'est ni une lettre minuscule, ni un chiffre par un tiret -.
* Réduire les tirets consécutifs à un seul tiret.
* Supprimer les tirets au début et à la fin du slug.
- Formatage de la table des matières :
* Titre h1 : - [<Titre>](#<slug>)
* Titre h2 : - [<Titre>](#<slug>) (2 espaces d'indentation)
* Titre h3 : - [<Titre>](#<slug>) (4 espaces d'indentation)

Afficher :
TABLE_OF_CONTENTS_START
<lignes du sommaire>
TABLE_OF_CONTENTS_END | COUNT=<nombre_de_titres>

Cas d’exemple
# Introduction to Cloud API
## Getting Started
### Installation Guide
Résolution attendue
TABLE_OF_CONTENTS_START
- [Introduction to Cloud API](#introduction-to-cloud-api)
  - [Getting Started](#getting-started)
    - [Installation Guide](#installation-guide)
TABLE_OF_CONTENTS_END | COUNT=3

Génération de la table des matières avec trois niveaux d'indentation et slugs conformes.

Deux indices, rédigés en mots
  1. Calculer le niveau de titre selon le nombre de dièses consécutifs (1, 2 ou 3).
  2. Construire le slug avec re.sub(r"[^a-z0-9]+", "-", texte.lower()).strip("-").

5. QCM — niveau examen

Dans la norme RFC 2119, que signifie la directive « The server MUST NOT log bearer tokens » ?

« MUST NOT » désigne une interdiction absolue et impérative dans la norme RFC 2119.

Quel code de statut HTTP indique que le client est authentifié mais ne possède pas les permissions nécessaires pour accéder à la ressource demandée ?

Le code 401 signale une absence d’authentification valide, tandis que 403 Forbidden indique que l’identité est connue mais que les droits sont insuffisants.

Que garantit la propriété d’idempotence d’une méthode HTTP comme PUT ou DELETE ?

Une opération est dite idempotente si la répéter plusieurs fois avec les mêmes paramètres aboutit au même état final sur le serveur.

Dans la documentation d’une API REST, quelle est la méthode HTTP recommandée pour créer une nouvelle commande d’achat ?

POST est la méthode standard pour créer de nouvelles ressources dont l’identifiant n’est pas encore déterminé par le client.

Quelle est la différence entre les mots-clés RFC 2119 « MUST » et « SHOULD » ?

MUST impose une obligation absolue. SHOULD tolère des exceptions motivées et documentées par les ingénieurs.

Quel code de retour HTTP est le plus approprié lorsqu’une ressource est supprimée avec succès et qu’aucun corps de réponse n’est renvoyé ?

Le code HTTP 204 No Content confirme le succès du traitement tout en spécifiant qu’aucun corps de réponse n’est transmis.

Dans un fichier README.md de qualité professionnelle, quelle section doit obligatoirement détailler les versions de Node.js, Python ou Docker nécessaires ?

La section Prerequisites énumère l’ensemble des dépendances matérielles et logicielles requises pour exécuter le projet.

Que signale un code d’erreur HTTP 502 Bad Gateway reçu par un navigateur ?

Le code 502 Bad Gateway survient lorsqu’un reverse proxy (ex: Nginx, Traefik) ne parvient pas à obtenir une réponse valide du microservice applicatif amont.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Confondre SHOULD (recommandation avec dérogation permise) et MUST (obligation absolue incontournable).
  • Oublier de documenter les codes d’erreur 401/403 sur un endpoint sécurisé par token Bearer.
  • Fournir un README sans préciser les versions exactes des runtimes (ex. Node.js ou Python requis).
  • Utiliser PUT pour une modification partielle d’attributs au lieu de PATCH.

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Vérifier chaque clause de spécification technique en repérant les mots-clés RFC 2119 pour distinguer obligations absolues et recommandations.
  2. Contrôler la présence d’au moins un code 2xx et des codes 401/403 pour tout endpoint protégé dans la documentation OpenAPI.
  3. Structurer tout fichier README selon les 6 sections standard pour garantir une reproduction en moins de cinq minutes.
  4. Documenter systématiquement l’idempotence des méthodes HTTP exposées pour guider les intégrateurs sur la politique de retry.
  5. Générer automatiquement une table des matières Markdown avec slugs valides pour faciliter la navigation dans les longs documents techniques.

8. Révision active

Résumé essentiel
  • Les spécifications OpenAPI formalisent les contrats d’API : verbes HTTP, URI, en-têtes et statuts 2xx/4xx/5xx.
  • La norme RFC 2119 élimine l’ambiguïté avec MUST (obligatoire), SHOULD (recommandé) et MAY (optionnel).
  • La différence entre 401 (non authentifié) et 403 (non autorisé) est cruciale dans la gestion des permissions.
  • Un README.md professionnel fournit prérequis, installation, variables d’environnement et guide de dépannage.
  • L’idempotence (GET, PUT, DELETE) permet de répéter une requête en cas d’échec réseau sans effet de bord imprévu.

Checklist de maîtrise

  • Ai-je audité les clauses MUST vs SHOULD dans mes spécifications d’interface ?
  • Mes routes d’API protégées documentent-elles les statuts 401 et 403 ?
  • Mon README contient-il un tableau complet des variables d’environnement avec valeurs par défaut ?
  • Les commandes d’installation et d’exécution des tests sont-elles directement copiables ?
  • Les ancres de ma table des matières Markdown renvoient-elles vers des slugs valides ?

Les 8 notions à connaître absolument

  1. Spécification OpenAPI & Swagger
  2. Verbes HTTP (GET, POST, PUT, DELETE, PATCH)
  3. Codes de statut HTTP (2xx, 4xx, 5xx)
  4. Idempotence des requêtes réseau
  5. Norme RFC 2119 (MUST, SHOULD, MAY)
  6. Structure canonique d’un README.md
  7. Matrice de variables d’environnement
  8. Slugification et ancres Markdown
