Examens Blancs & Épreuves Corrigées — Anglais B3

Deux épreuves complètes d’anglais technique et professionnel conformes aux exigences académiques et aux évaluations en milieu professionnel de niveau Bachelor 3 : documentation d’API, gestion d’incidents, animation d’équipe agile, SLA et soutenance technique.

Épreuve 1 : Contrôle Continu (CC) — Durée 1 h 30 (Barème sur 20 points)

Sujet du Contrôle Continu — Terminologie, Documentation d’API & Communication d’Incident

Partie 1 : Précision Terminologique & Acronymes Critiques (6 points)

  1. Définissez avec précision en anglais la différence entre un glitch, un bug, une vulnerability et un exploit. Donnez un exemple concret pour chacun. (3 pts)
  2. Explicitez la différence entre les acronymes IaaS, PaaS et SaaS selon le modèle de responsabilité partagée. Quelle couche spécifique de la pile est gérée par le client en PaaS mais par le fournisseur en SaaS ? (3 pts)

Partie 2 : Analyse de Spécification Technique & RFC 2119 (7 points)

  1. Soit la clause suivante issue d’un projet de microservices : "The authentication gateway SHOULD NOT store raw bearer tokens in plaintext; it MUST hash incoming API keys before persistence and it MAY cache validation decisions for up to sixty seconds." Identifiez les trois mots-clés RFC 2119, indiquez leur niveau d’obligation contractuel et traduisez cette exigence pour l’équipe de développement. (4 pts)
  2. Citez les 4 composantes fondamentales d’un endpoint REST documenté selon les standards OpenAPI. Pourquoi l’absence d’un code de retour 401 ou 403 sur un endpoint sécurisé constitue-t-elle une anomalie critique de documentation ? (3 pts)

Partie 3 : Rédaction Professionnelle & Diagnostic d’Email Malade (7 points)

  1. Diagnostiquez les trois défauts majeurs de l’email suivant :
    Subject: hey
    Yo, the database stuff is broken, fix it asap cause we gonna lose money. thx
    Réécrivez cet email sous une forme professionnelle, précise et actionnable à destination du Tech Lead d’infrastructure. (4 pts)
  2. Quelles sont les six sections obligatoires d’un rapport de bug (Bug Report) professionnel pour qu’il soit immédiatement qualifié par l’équipe de développement sans demande d’informations complémentaires ? (3 pts)
Corrigé type & Barème détaillé du Contrôle Continu

Corrigé Partie 1 (6 points)

  • Glitch vs Bug vs Vulnerability vs Exploit (3 pts) : 1. Glitch : un dysfonctionnement temporaire ou éphémère ne perturbant pas durablement le système (ex. un saut d’affichage d’un pixel ou un micro-délai de rafraîchissement d’UI). 2. Bug : une erreur reproductible dans le code source causant un comportement inattendu ou erroné (ex. une exception de division par zéro lors du calcul du panier). 3. Vulnerability : une faille ou faiblesse de sécurité dans la conception ou le code pouvant être compromise (ex. une absence de validation des entrées menant à une injection SQL). 4. Exploit : un code, script ou payload malveillant tirant activement parti d’une vulnérabilité pour compromettre le système (ex. un script automatisé exploitant la CVE Log4j pour exécuter du code à distance).
  • Modèle de responsabilité partagée (3 pts) : En IaaS, le fournisseur gère le matériel et la virtualisation, le client gère l’OS, le runtime et l’application. En PaaS, le fournisseur gère en plus l’OS et le runtime (ex. Node.js/Python), le client gère le code applicatif et les données. En SaaS, le fournisseur gère l’ensemble de la pile applicative. La couche spécifique gérée par le client en PaaS et par le fournisseur en SaaS est l’application elle-même (son code source, son déploiement et sa maintenance applicative).

Corrigé Partie 2 (7 points)

  • Analyse RFC 2119 (4 pts) : 1. SHOULD NOT : pratique fortement déconseillée (P2 — Recommended) ; stocker les tokens en clair est proscrit sauf contrainte technique absolue dûment documentée. 2. MUST : exigence absolue et impérative (P1 — Critical) ; le hachage des clés d’API avant stockage en base est une obligation contractuelle non négociable. 3. MAY : fonctionnalité purement optionnelle (P3 — Optional) ; la passerelle a le droit mais non l’obligation de mettre en cache les décisions d’authentification pour une durée maximale de 60 secondes.
  • Documentation OpenAPI d’endpoints REST (3 pts) : Les 4 composantes sont : la méthode HTTP (GET, POST, etc.), l’URI de chemin (/api/v1/...), les paramètres d’en-tête ou de payload (dont auth Bearer), et les codes de statut HTTP de retour. L’absence de codes 401 (Unauthorized) ou 403 (Forbidden) sur un endpoint sécurisé est critique car elle empêche les intégrateurs tiers d’implémenter correctement la gestion des échecs d’authentification et de renouvellement de token.

Corrigé Partie 3 (7 points)

  • Diagnostic et réécriture de l’email malade (4 pts) : Défauts : 1. Sujet vague et non professionnel ("hey" ne donne aucun contexte ni composant) ; 2. Salutation et clôture relâchées ("Yo", "thx") ; 3. Corps imprécis contenant de l’argot ("stuff", "broken", "asap", "gonna"). Version professionnelle corrigée :
    Subject: PROD: Database Connection Pool Outage on Payments Cluster
    Hi Peter,
    We are currently observing high connection timeout rates on the PostgreSQL payments replica in production. This is causing HTTP 500 errors on the checkout service for approximately 25% of active users. Could the infrastructure team please inspect connection limits and scale up pool capacity? Thank you, Best regards, Alex.
  • Les 6 sections d’un Bug Report (3 pts) : 1. Title (intitulé précis et descriptif) ; 2. Environment (OS, navigateur, version, commit) ; 3. Steps to Reproduce (étapes numérotées 1, 2, 3...) ; 4. Expected Behavior ; 5. Actual Behavior ; 6. Severity / Priority (Critical, Major, Minor, Trivial).

Épreuve 2 : Examen Terminal (ET) — Durée 2 h 00 (Barème sur 20 points)

Sujet de l’Examen Terminal — Agilité, Métriques SLA, Support Utilisateur & Soutenance

Partie 1 : Animation Agile & Négociation de SLA (6 points)

  1. Rédigez en anglais l’intervention typique d’un ingénieur Cloud lors d’un Daily Standup meeting, en respectant les trois rubriques standard (Yesterday, Today, Blockers). Intégrez une demande polie d’aide sur un problème de réseau virtuel. (3 pts)
  2. Un contrat de service international garantit une disponibilité de 99.95 % sur un mois de 30 jours (43 200 minutes). Calculez le downtime maximal autorisé en minutes. Si le service enregistre une coupure réelle cumulée de 65 minutes et que la pénalité contractuelle est de 400 $ par heure entamée d’excédent, déterminez le montant exact de la pénalité financière due. (3 pts)

Partie 2 : Support Technique & Post-Mortem Blameless (7 points)

  1. Traduisez le message d’erreur technique suivant en une explication bienveillante et orientée utilisateur final (Support Client) : "Fatal Error 502: Bad Gateway. Connection pool to upstream microservice exhausted after socket timeout." Quels sont les 3 principes d’empathie à respecter ? (3 pts)
  2. Expliquez pourquoi les géants de la tech (Google, AWS, Netflix) imposent des Blameless Post-Mortems. Appliquez la méthode des 5 Pourquoi (5-Whys) à un incident de certificat SSL expiré pour remonter de la panne initiale jusqu’au défaut d’architecture systémique sans jamais incriminer d’individu. (4 pts)

Partie 3 : Présentation Technique & Méthode STAR (7 points)

  1. Dans le cadre d’une présentation technique internationale de 5 minutes, citez et illustrez par une phrase en anglais les 4 phases de balisage verbal (Signposting) : Starting, Outlining, Transition, et Concluding/Q&A. (3 pts)
  2. En entretien d’embauche technique pour un poste d’ingénieur DevOps international, formulez une réponse modèle selon la structure STAR (Situation, Task, Action, Result) décrivant comment vous avez accéléré un pipeline CI/CD en incluant un résultat quantifié. (4 pts)
Corrigé type & Barème détaillé de l’Examen Terminal

Corrigé Partie 1 (6 points)

  • Intervention de Daily Standup (3 pts) :
    "Yesterday, I finished automating the staging Kubernetes cluster provisioning using Terraform. Today, I plan to deploy the ingress controller and configure TLS termination. As for blockers, I am currently stuck on cross-VPC peering routing tables; could someone from the networking team pair with me for fifteen minutes after the standup? Thanks."
  • Calcul de SLA et pénalités (3 pts) :
    Temps total $= 30 \times 24 \times 60 = 43\,200$ minutes. Downtime autorisé $= 43\,200 \times (100 - 99.95) / 100 = 43\,200 \times 0.0005 = 21.60$ minutes. Excédent de downtime $= 65 - 21.60 = 43.40$ minutes. Heures entamées pénalisables $= \lceil 43.40 / 60 \rceil = 1$ heure. Pénalité financière $= 1 \times 400 = 400$ USD.

Corrigé Partie 2 (7 points)

  • Traduction de message d’erreur support (3 pts) :
    Message utilisateur bienveillant : "Our payment service is temporarily unavailable due to high demand. No charges have been made to your payment card. Please wait a few moments and refresh the page, or try again shortly." Les 3 principes d’empathie sont : 1. Rassurer l’usager (aucune perte d’argent ni de données) ; 2. Éviter tout jargon technique (pas de socket, gateway ou microservice) ; 3. Fournir une consigne d’action claire (patienter et rafraîchir).
  • Post-Mortem Blameless et 5 Pourquoi (4 pts) :
    Le principe blameless stipule que blâmer un ingénieur masque les vulnérabilités de l’infrastructure et crée une culture de la dissimulation. Exemple des 5 Pourquoi : 1. Pourquoi l’accès web a-t-il échoué ? Le certificat TLS a expiré. 2. Pourquoi le certificat a-t-il expiré sans alerte ? Le renouvellement manuel programmé sur l’agenda n’a pas été réalisé. 3. Pourquoi le renouvellement était-il manuel ? Aucune autorité automatisée (ACME / Let’s Encrypt) n’était branchée sur le proxy inverse. 4. Pourquoi l’outil ACME n’était-il pas déployé ? La configuration du reverse proxy n’était pas gérée sous forme d’Infrastructure as Code (IaC). 5. Cause racine systémique : L’infrastructure de certificats manquait d’automatisation déclarative et d’une surveillance synthétique des dates d’expiration. Action corrective : Déployer Cert-Manager avec renouvellement automatique et alertes Prometheus à J-30.

Corrigé Partie 3 (7 points)

  • Balisage verbal en présentation (3 pts) :
    1. Starting : "Today, I would like to present our distributed database observability platform."
    2. Outlining : "I have divided my presentation into three main sections: the latency bottleneck, our caching architecture, and benchmark results."
    3. Transition : "Moving on to our caching layer, let’s examine how Redis was integrated into the query pipeline."
    4. Concluding & Q&A : "To sum up, this architecture reduced p99 latency by 55%. Thank you for your attention, I would now be glad to take any questions."
  • Réponse modèle STAR d’entretien (4 pts) :
    S : "At my previous internship, our continuous integration test suite took forty-five minutes to run on every pull request, causing major deployment bottlenecks."
    T : "My mission was to cut pipeline execution time by at least 50% to accelerate feedback loops for a team of twenty engineers."
    A : "I analyzed test execution traces, identified unparallelized database seed scripts, configured Docker layer caching on GitHub Actions self-hosted runners, and split unit tests across four parallel workers."
    R : "As a result, build and test duration dropped from 45 minutes to 11 minutes (a 75% speedup), saving approximately thirty engineering hours per week and preventing merge queue congestions."
