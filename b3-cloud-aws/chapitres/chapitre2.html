Chapitre 2 — Sécurité des Identités IAM, Politiques JSON & Gouvernance Multi-Comptes

Module 2 ≈ 2 h 45 Réservé B3 et plus
Mise en situation

À la suite d'un audit de cybersécurité interne, votre direction vous confie le durcissement intégral de la gestion des identités et des accès sur le tenant AWS de l'entreprise. Vous devez éradiquer les clés d'accès statiques en déployant des rôles IAM temporaires, modéliser des politiques d'autorisation JSON respectant le principe du moindre privilège, et instaurer une gouvernance multi-comptes centralisée avec AWS Organizations et des Service Control Policies (SCPs) infranchissables.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. Maîtriser les entités IAM : Utilisateurs, Groupes, Rôles temporaires (Instance Profiles, STS AssumeRole) et politiques basées sur l'identité vs sur la ressource.
  2. Rédiger et auditer des politiques d'autorisation IAM JSON (Version, Statement, Effect, Action, Resource, Condition).
  3. Comprendre et appliquer l'algorithme d'évaluation strict d'AWS (Default Deny, Explicit Allow, primauté absolue de l'Explicit Deny).
  4. Mettre en œuvre la gouvernance multi-comptes avec AWS Organizations et les Service Control Policies (SCPs) pour imposer des garde-fous organisationnels.

1. Les Fondements d'AWS IAM : Utilisateurs, Groupes & Rôles

AWS Identity and Access Management (IAM) est le service mondial gratuit permettant de contrôler de manière sécurisée les accès aux ressources AWS :

Utilisateurs IAM (Users)

Identité persistante attribuée à une personne ou un système spécifique nécessitant un accès console (mot de passe + MFA) ou programmatique (Access Key ID et Secret Access Key).

Bonne pratique : ne jamais créer d'utilisateurs IAM avec des accès administrateurs pour des services automatisés.

Groupes IAM (Groups)

Regroupement logique d'utilisateurs (ex: Developpeurs, Auditeurs-Securite) simplifiant l'application collective de politiques d'autorisation.

Un groupe ne peut pas contenir d'autres groupes et ne possède pas d'identifiants propres.

Rôles IAM (Roles)

Identité sans identifiant permanent, endossable temporairement par des entités de confiance (instances EC2 via Instance Profile, fonctions Lambda, utilisateurs fédérés).

Génère des jetons éphémères via AWS Security Token Service (STS) valides de 15 minutes à 12 heures, éliminant les fuites de clés statiques.

2. Structure & Syntaxe des Politiques d'Autorisation JSON

Toute autorisation dans AWS est déclarée sous forme d'un document JSON normalisé :

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3ReadOnlyProduction",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::data-prod-2026",
        "arn:aws:s3:::data-prod-2026/*"
      ],
      "Condition": {
        "Bool": { "aws:MultiFactorAuthPresent": "true" }
      }
    }
  ]
}
  • Version : toujours spécifier "2012-10-17" (la version moderne supportant les variables de stratégie et conditions).
  • Effect : obligatoirement Allow ou Deny.
  • Action : liste des opérations API ciblées (supporte les caractères génériques ex: ec2:Describe*).
  • Resource : liste des ARN sur lesquels s'appliquent les actions.
  • Condition : bloc facultatif restreignant l'autorisation (ex: présence du MFA, plage d'adresses IP source aws:SourceIp, date/heure).

3. Moteur d'Évaluation des Politiques : La Règle d'Or d'AWS

Lorsqu'un utilisateur ou un service émet un appel d'API, le moteur IAM évalue l'ensemble des politiques selon un ordre invariable :

Logique de Décision IAM

  1. 1. Refus par défaut (Default Deny) : toute action est interdite a priori.
  2. 2. Recherche d'un Explicit Deny : si n'importe quelle politique applicable (politique d'identité, SCP, politique de ressource) stipule Deny sur l'action, la décision est immédiatement et irrévocablement DENY.
  3. 3. Recherche d'un Explicit Allow : si aucun Deny n'est trouvé et qu'au moins une politique stipule Allow, la décision devient ALLOW.
  4. 4. Refus implicite : en l'absence de déclaration Allow applicable, la décision finale reste DENY.

Politiques d'Identité vs Politiques de Ressource

  • Identity-based policies : attachées aux utilisateurs, groupes ou rôles (gérées par AWS ou par le client).
  • Resource-based policies : attachées directement aux ressources (ex: Bucket Policy S3, politique de clé KMS, politique de file SQS). Elles comportent un champ obligatoire Principal définissant QUI a le droit d'agir.

4. Cycle de Vie des Clés d'Accès & Sécurité des Identifiants

Les clés d'accès permanentes (Access Key ID / Secret Access Key) constituent le vecteur d'attaque le plus fréquemment ciblé par les cybercriminels :

  • Format officiel : les clés IAM permanentes débutent par AKIA et comportent 20 caractères alphanumériques majuscules. Les clés temporaires STS commencent par ASIA.
  • Seuil de rotation maximal : les standards industriels (CIS AWS Foundations Benchmark) exigent une rotation tous les 90 jours au maximum.
  • Privilégier les Instance Profiles : une instance EC2 ou un conteneur ECS ne doit JAMAIS contenir de clés d'accès écrites sur disque. Le rattachement d'un rôle IAM fournit automatiquement des identifiants temporaires renouvelés via le service de métadonnées d'instance (IMDSv2).

5. Gouvernance Multi-Comptes : AWS Organizations & SCPs

Dans les architectures d'entreprise, l'isolation des charges de travail impose une stratégie multi-comptes (comptes distincts pour la Sécurité, le Réseau, la Préproduction et la Production) :

AWS Organizations

Permet de consolider la facturation (Consolidated Billing) et de structurer les comptes membres en une arborescence d'Unités Organisationnelles (OUs - Organizational Units).

Le compte de gestion (Management Account) administre la hiérarchie et applique les stratégies globales.

Service Control Policies (SCPs)

Les SCPs définissent les permissions maximales autorisées (garde-fous) pour les comptes d'une OU ou d'un compte individuel :

  • Une SCP ne confère jamais de droit, elle limite la portée des autorisations que les administrateurs locaux peuvent accorder.
  • Pour qu'une action soit possible dans un compte membre, elle doit être explicitement autorisée à CHAQUE niveau de l'arbre hiérarchique, et interdite à AUCUN niveau.
  • Exemple : interdire la désactivation du chiffrement ou l'utilisation d'une région non approuvée (ex: interdire les régions hors Europe).

Exercice 1 — Moteur d'Évaluation de Politiques IAM JSON (Deny / Allow / Default Deny)

Python Niveau 1 — Acquisition

Objectif : Implémenter l'algorithme d'évaluation officiel des politiques d'autorisation IAM d'AWS.

Dans AWS IAM, chaque requête API est évaluée selon un ordre strict :

1. Default Deny : Par défaut, toute requête est refusée.
2. Explicit Deny prioritaire : Si au moins une déclaration applicable comporte Effect: Deny, la décision finale est DENY, quoi qu'il arrive.
3. Explicit Allow : Si aucune déclaration ne refuse la requête et qu'au moins une déclaration comporte Effect: Allow, la décision est ALLOW.
4. Refus implicite : Si aucune déclaration ne s'applique, la décision finale reste DENY.

Les actions supportent le préfixe avec joker (ex: s3:Get* correspond à s3:GetObject, s3:GetBucketLocation ; * correspond à tout).

Format d'entrée STDIN :
ACTION=<action_demandée> STATEMENTS=<Effect:Action_pattern;Effect:Action_pattern;...>

Sortie : IAM_EVAL: action=<act> decision=<ALLOW|DENY> reason=<EXPLICIT_DENY|EXPLICIT_ALLOW|DEFAULT_DENY>.

Entrée du programme
ACTION=s3:GetObject STATEMENTS=Allow:s3:Get*;Deny:s3:PutObject
Sortie attendue
IAM_EVAL: action=s3:GetObject decision=ALLOW reason=EXPLICIT_ALLOW

Exercice 2 — Auditeur de Clés d'Accès IAM & Détecteur d'Inactivité / Rotation

Python Niveau 2 — Application

Objectif : Auditer le rapport d'identifiants IAM (Credential Report) et identifier les clés compromises, inactives ou périmées.

Les bonnes pratiques de sécurité AWS exigent une rotation régulière des clés d'accès programmatiques (Access Keys) :

Règles d'audit d'une clé :
1. Format valide : Une clé d'accès IAM permanente commence obligatoirement par le préfixe AKIA et comporte exactement 20 caractères alphanumériques majuscules.
Si ce n'est pas le cas -> ALERT_MALFORMED_KEY.
2. Statut inactif : Si STATUS=Inactive -> NOTICE_KEY_INACTIVE (ne pose pas de risque immédiat mais doit être supprimée).
3. Périmètre d'âge (Rotation) :
- Si STATUS=Active et AGE_DAYS > 90 -> ALERT_ROTATION_REQUIRED (dépassement du seuil de 90 jours préconisé par AWS).
- Si STATUS=Active et AGE_DAYS <= 90 -> KEY_COMPLIANT.

Entrée STDIN : KEY_AUDIT USER=<username> KEY_ID=<key> STATUS=<Active|Inactive> AGE_DAYS=<n>.
Sortie : AUDIT: user=<u> key=<k> status=<s> age_days=<n> verdict=<VERDICT>.

Entrée du programme
KEY_AUDIT USER=dev-alice KEY_ID=AKIAIOSFODNN7EXAMPLE STATUS=Active AGE_DAYS=45
Sortie attendue
AUDIT: user=dev-alice key=AKIAIOSFODNN7EXAMPLE status=Active age_days=45 verdict=KEY_COMPLIANT

Exercice 3 — Évaluateur de Politiques de Contrôle des Services AWS Organizations (SCP)

Python Niveau 2 — Application

Objectif : Vérifier si une action est autorisée à travers l'arborescence hiérarchique d'unités organisationnelles (OUs) avec des SCPs.

Les Service Control Policies (SCPs) dans AWS Organizations définissent les garde-fous maximaux pour les comptes membres :

Règles d'évaluation des SCPs :
1. Les SCPs ne confèrent pas de droits, elles définissent une limite supérieure de permissions.
2. Pour qu'une action soit autorisée sur un compte cible :
- Aucun niveau de l'arborescence (du Root jusqu'au compte) ne doit comporter de Deny explicite sur l'action.
- CHAQUE niveau traversé (Root, OUs intermédiaires, Compte) doit explicitement comporter un Allow sur l'action (politique FullAWSAccess par défaut).
3. Si un seul niveau bloque l'action (absence d'Allow ou présence d'un Deny), l'action est interdite (BLOCKED).

Entrée STDIN :
SCP_CHECK ACTION=<action> HIERARCHY=<Niveau1:Allow/Deny;Niveau2:Allow/Deny;...>.

Sortie : Si autorisée : SCP_RESULT: action=<act> status=ALLOWED.
Si bloquée : SCP_RESULT: action=<act> status=BLOCKED blocked_by=<Niveau> reason=<EXPLICIT_DENY|NO_ALLOW_FOUND>.

Entrée du programme
SCP_CHECK ACTION=ec2:StopInstances HIERARCHY=Root:Allow;CoreOU:Allow;Account:Allow
Sortie attendue
SCP_RESULT: action=ec2:StopInstances status=ALLOWED

7. QCM — niveau examen

Que se passe-t-il si un utilisateur IAM fait l'objet d'une politique avec « Effect: Allow » sur s3:* et d'une autre politique avec « Effect: Deny » sur s3:DeleteBucket ?

L'Explicit Deny est prioritaire absolu sur tout Allow. L'utilisateur conserve le droit d'exécuter toutes les actions S3 (GetObject, PutObject...) SAUF DeleteBucket qui est refusée.

Quel mécanisme AWS permet à une application exécutée sur une instance EC2 d'accéder à S3 sans stocker de clés d'accès en dur sur le serveur ?

L'Instance Profile transmet un rôle IAM à la VM EC2. Le SDK Boto3/AWS CLI interroge alors automatiquement le service de métadonnées (IMDS) pour obtenir des clés temporaires renouvelées en continu.

Quel préfixe identifie de manière univoque une clé d'accès IAM permanente dans AWS ?

AKIA désigne une clé d'accès permanente pour utilisateur IAM. Les clés temporaires fournies par STS commencent par ASIA, les rôles par AROA et les utilisateurs par AIDA.

Selon les recommandations officielles d'AWS et le benchmark CIS, quelle est la fréquence maximale de rotation des clés d'accès ?

Le benchmark CIS AWS Foundations exige une rotation d'au moins tous les 90 jours pour toute clé d'accès IAM permanente afin de minimiser le risque de compromission.

Quel est le rôle exact d'une Service Control Policy (SCP) dans AWS Organizations ?

Une SCP ne donne aucun droit direct. Elle agit comme un filtre supérieur interdisant formellement certaines actions ou limitant le périmètre d'action possible des administrateurs du compte.

Quelle version de document de stratégie doit être impérativement déclarée dans le champ « Version » d'une politique JSON moderne ?

La valeur officielle standard est strictement « 2012-10-17 ». L'ancienne version « 2008-10-17 » ne supporte pas les conditions avancées ni les variables de stratégie.

Quelle est la différence fondamentale entre une Identity-based policy et une Resource-based policy ?

Une Resource-based policy (comme une Bucket Policy S3) est attachée à la ressource elle-même et doit impérativement spécifier « Principal » pour désigner QUI a le droit d'y accéder.

Si aucune politique applicable ne mentionne une action donnée, quelle décision est prise par le moteur IAM ?

Dans AWS IAM, la sécurité repose sur le modèle de fermeture par défaut : toute action qui n'est pas explicitement autorisée est systématiquement refusée (Default Deny).

8. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Créer des clés d'accès AccessKeyId permanentes pour des applications s'exécutant sur des instances EC2 au lieu d'utiliser un Instance Profile.
  • Supposer qu'une SCP avec Effect: Allow confère des droits directs à un utilisateur : la SCP n'est qu'un filtre supérieur, il faut aussi une politique IAM d'identité.
  • Oublier de spécifier l'ARN de la ressource dans une politique IAM en utilisant Resource: "*", ce qui expose inutilement toutes les ressources du compte.
  • Négliger la politique de confiance (Trust Policy) d'un rôle IAM, sans laquelle aucune entité ne peut endosser le rôle.

9. Méthodologie de résolution

Méthodologie de Cadrage des Droits & IAM Hardening
  1. Inventaire des besoins et application stricte du principe du moindre privilège (PoLP) : spécifier des actions API et des ARN de ressources granulaires sans jamais utiliser d'étoile générique (*:*).
  2. Déploiement systématique de rôles IAM temporaires pour les charges de calcul : bannir les Access Keys sur les VMs EC2, les conteneurs et les lambdas au profit d'Instance Profiles.
  3. Activation obligatoire du Multi-Factor Authentication (MFA) : exiger un token TOTP ou une clé FIDO2 matérielle pour tout utilisateur console et protéger les actions sensibles via des conditions JSON (aws:MultiFactorAuthPresent).
  4. Mise en place de garde-fous centralisés avec les SCPs : bloquer l'accès aux régions non utilisées, interdire la suppression des logs CloudTrail et verrouiller les buckets de sauvegarde.

10. Révision active

Résumé essentiel
  • AWS IAM gère les identités (Utilisateurs, Groupes, Rôles temporaires STS) et les politiques d'autorisation JSON à l'échelle mondiale sans frais supplémentaires.
  • Les rôles IAM éliminent les risques de fuite de clés statiques en fournissant des identifiants éphémères renouvelés automatiquement.
  • Le moteur d'évaluation IAM applique le Default Deny, donne une priorité absolue et immuable à tout Explicit Deny, puis vérifie la présence d'un Explicit Allow.
  • Les clés d'accès statiques AKIA doivent faire l'objet d'une rotation obligatoire tous les 90 jours maximum selon le CIS Benchmark.
  • AWS Organizations et les Service Control Policies (SCPs) imposent des limites supérieures de permissions infranchissables sur l'ensemble des comptes d'entreprise.

Checklist de maîtrise

  • Savez-vous expliquer la différence entre un utilisateur IAM et un rôle IAM temporaire ?
  • Connaissez-vous les 5 blocs fondamentaux d'une déclaration de politique JSON (Version, Statement, Effect, Action, Resource, Condition) ?
  • Pouvez-vous prédire sans erreur l'issue d'une requête en présence de politiques contradictoires Allow et Deny ?
  • Savez-vous pourquoi les SCPs dans AWS Organizations ne confèrent aucun droit direct mais définissent des garde-fous ?
  • Avez-vous compris le mécanisme de jetons STS et l'intérêt d'un Instance Profile sur une instance EC2 ?

Les 8 notions à connaître absolument

  1. Rôle IAM : Identité sans mot de passe permanent, endossable temporairement par des services ou utilisateurs via AWS STS.
  2. Instance Profile : Conteneur permettant de transmettre un rôle IAM à une machine virtuelle Amazon EC2 sans identifiants écrits sur disque.
  3. AWS STS : Security Token Service : service générant des jetons d'accès temporaires signés d'une durée de vie limitée.
  4. Explicit Deny : Déclaration Effect: Deny l'emportant de façon irrévocable sur toute autre autorisation dans le moteur IAM.
  5. Service Control Policy (SCP) : Politique d'AWS Organizations définissant les limites maximales de permissions pour une organisation ou une OU.
  6. Moindre Privilège : Principe de sécurité consistant à n'accorder que les permissions strictement nécessaires à l'accomplissement d'une tâche.
  7. IMDSv2 : Instance Metadata Service version 2 : API locale (169.254.169.254) sécurisée par jeton de session contre les failles SSRF.
  8. Credential Report : Rapport téléchargeable d'audit listant l'état, l'âge et l'utilisation des identifiants et clés de tous les utilisateurs du compte.
