Chapitre 3 — Calcul & Conteneurs — EC2, EBS, ELB, Auto Scaling & Fargate

Module 3 ≈ 2 h 45 Réservé B3 et plus
Mise en situation

Votre entreprise prépare le lancement d'une nouvelle plateforme applicative à fort trafic. Vous devez concevoir une architecture de calcul hautement disponible et élastique : dimensionner les instances Amazon EC2 avec la stratégie d'achat optimale (Reserved + Spot), configurer des volumes EBS gp3 performants, déployer un Application Load Balancer (ALB) répartissant le trafic sur plusieurs zones de disponibilité, et automatiser l'élasticité via un Auto Scaling Group.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. Identifier et sélectionner les familles d'instances Amazon EC2 et optimiser les coûts via les modèles d'achat (On-Demand, Reserved, Savings Plans, Spot).
  2. Dimensionner et administrer les volumes de stockage bloc Amazon EBS (gp3, io2), gérer les snapshots incrémentaux et le chiffrement.
  3. Déployer et configurer les répartiteurs de charge Elastic Load Balancing (ALB, NLB) avec leurs Target Groups et contrôles de santé.
  4. Configurer un Auto Scaling Group (ASG) avec Launch Template et politiques de Target Tracking pour garantir une haute disponibilité Multi-AZ équilibrée.

1. Amazon EC2 : Familles de Calcul & Modèles d'Achat

Amazon Elastic Compute Cloud (EC2) fournit une capacité de calcul redimensionnable dans le cloud sous forme de machines virtuelles sécurisées :

Les Familles d'Instances EC2

  • Usage général (General Purpose - T4g, M6i) : équilibre idéal entre calcul, mémoire et réseau pour les serveurs web et microservices.
  • Optimisées pour le calcul (Compute - C6i, C7g) : forte puissance CPU pour le traitement batch, l'encodage vidéo et le calcul scientifique.
  • Optimisées pour la mémoire (Memory - R6i, X2gd) : volumétrie RAM élevée pour les bases de données en mémoire (Redis, SAP HANA).
  • Optimisées pour le stockage (Storage - I3en, D3) : disques NVMe locaux ultra-rapides pour les entrepôts de données et clusters Elasticsearch.

Les 4 Modèles d'Achat d'Instances

  • À la demande (On-Demand) : flexibilité totale, facturation à la seconde sans engagement. Idéal pour le développement et charges imprévisibles.
  • Instances Réservées & Savings Plans : engagement de 1 ou 3 ans en échange d'une réduction jusqu'à 72%. Optimal pour la charge socle continue.
  • Instances Spot : surplus de capacité AWS vendu jusqu'à 90% moins cher, mais interruptible avec un préavis de 2 minutes si AWS réclame la capacité.
  • Hôtes Dédiés (Dedicated Hosts) : serveur physique complet dédié pour conformité réglementaire ou licences logicielles complexes (BYOL).

2. Stockage Bloc Amazon EBS (Elastic Block Store) & Snapshots

Amazon EBS fournit des volumes de stockage bloc persistants rattachables aux instances EC2 au sein d'une même Availability Zone :

Types de Volumes SSD & Métriques Clés

  • General Purpose SSD (gp3) : volume par défaut moderne. Offre 3 000 IOPS et 125 MB/s de base inclus sans frais, modulables jusqu'à 16 000 IOPS et 1 000 MB/s indépendamment de la taille de stockage.
  • Provisioned IOPS SSD (io2 Block Express) : performance extrême jusqu'à 256 000 IOPS et 4 000 MB/s avec une durabilité de 99.999% pour bases de données critiques.
  • Throughput Optimized HDD (st1) / Cold HDD (sc1) : stockage magnétique économique pour les charges séquentielles volumineuses (Big Data, logs).

Snapshots Incrémentaux & Chiffrement KMS

  • Snapshots incrémentaux : sauvegardes point-in-time stockées de manière redondante dans Amazon S3. Seuls les blocs modifiés depuis le dernier snapshot sont sauvegardés et facturés.
  • Chiffrement au repos : activable en un clic via AWS KMS (AES-256). Les données du volume, les I/O en transit vers l'instance et tous les snapshots dérivés sont automatiquement chiffrés sans impact sur les performances.

3. Elastic Load Balancing (ELB) : ALB, NLB & Health Checks

Elastic Load Balancing distribue automatiquement le trafic entrant sur plusieurs cibles (instances EC2, conteneurs, adresses IP) réparties sur plusieurs AZs :

Application Load Balancer (ALB)

Opère au niveau de la couche 7 (HTTP/HTTPS) du modèle OSI.

Routage intelligent basé sur le chemin d'URL (/api/* vs /images/*), les en-têtes HTTP, les cookies et les méthodes de requête. Supporte WebSockets et gère la terminaison SSL/TLS avec certificats AWS ACM gratuits.

Network Load Balancer (NLB)

Opère au niveau de la couche 4 (TCP/UDP/TLS).

Ultra-haute performance capable de traiter des millions de requêtes par seconde avec une latence ultra-faible (< 1 ms). Fournit une adresse IP statique ou Elastic IP par Availability Zone.

Target Groups & Health Checks

Les cibles sont regroupées dans des Target Groups.

L'équilibreur de charge sonde régulièrement chaque instance (Health Checks). Si une instance ne répond pas (ex: code HTTP 500 ou timeout), le trafic est immédiatement dérouté vers les instances saines restantes.

4. Auto Scaling Groups (ASG) & Équilibre Multi-AZ

Un Auto Scaling Group (ASG) ajuste automatiquement la taille de la flotte d'instances pour répondre aux variations de charge tout en garantissant la résilience :

Paramètres de Capacité & Launch Templates

  • Capacité minimale (Min) : nombre d'instances plancher garantissant le service même en creux de trafic.
  • Capacité souhaitée (Desired) : nombre d'instances actives en régime nominal.
  • Capacité maximale (Max) : plafond d'instances pour borner les coûts en cas de pic ou d'attaque.
  • Launch Template : modèle de lancement moderne définissant l'AMI, le type d'instance, le Security Group, l'Instance Profile et le script de démarrage (User Data).

Politiques d'Échelle & Répartition Multi-AZ

  • Target Tracking Scaling : ajuste dynamiquement le nombre d'instances pour maintenir une métrique cible (ex: maintenir l'utilisation CPU globale à 50%).
  • Step Scaling & Simple Scaling : réagit par paliers en cas d'alerte CloudWatch.
  • Équilibrage Multi-AZ : l'ASG distribue toujours les nouvelles instances dans la zone qui en compte le moins, garantissant une répartition géographique homogène.

5. Conteneurs Managés : Amazon ECS, EKS & AWS Fargate

Pour exécuter des applications conteneurisées Docker sans administrer manuellement de serveurs virtuels :

Amazon ECS

Service d'orchestration de conteneurs hautement performant natif AWS, simple et profondément intégré avec IAM, VPC et CloudWatch.

Amazon EKS

Service Kubernetes entièrement managé certifié conforme, garantissant la portabilité des charges de travail conteneurisées avec l'écosystème open-source K8s.

AWS Fargate (Serverless)

Moteur d'exécution serverless pour ECS et EKS. Vous définissez le CPU et la RAM de la tâche conteneur, AWS alloue l'infrastructure sous-jacente sans aucune VM à gérer ni patcher.

Exercice 1 — Optimiseur de Coûts & Stratégie d'Achat EC2 (On-Demand, Reserved, Spot)

Étude de cas Niveau 1 — Acquisition

Objectif : Calculer le coût total et l'économie réalisée en panachant les modèles d'achat d'instances EC2 pour une charge avec pic.

Une architecture cloud moderne optimise ses coûts en combinant plusieurs modèles d'achat EC2 :

1. Charge de base stable (Baseline) :
Tourne 100% du temps. Elle bénéficie d'instances réservées (Reserved Instances) ou d'un Savings Plan offrant un rabais contractuel (ex: 40%).
Cout_baseline = Baseline_instances * Heures * Taux_OnDemand * (1.0 - Rabais_Reserved / 100).

2. Pic variable (Spike) :
Charge additionnelle tolérante aux pannes couverte par des instances Spot avec un rabais agressif (ex: 70%).
Cout_spike = Spike_instances * Heures * Taux_OnDemand * (1.0 - Rabais_Spot / 100).

3. Scénario de référence 100% On-Demand :
Cout_ref = (Baseline_instances + Spike_instances) * Heures * Taux_OnDemand.

Données du cas :
EC2_COST BASELINE=<n> SPIKE=<n> HOURS=<h> RATE=<$/h> SPOT_DISC=<pct> RES_DISC=<pct>.

Résultat d’analyse attendu :
BUDGET: baseline_cost=<b:.2f>$ spike_cost=<s:.2f>$ total_cost=<t:.2f>$ savings_pct=<p:.2f>%.

Cas d’exemple
EC2_COST BASELINE=4 SPIKE=6 HOURS=720 RATE=0.10 SPOT_DISC=70 RES_DISC=40
Résolution attendue
BUDGET: baseline_cost=172.80$ spike_cost=129.60$ total_cost=302.40$ savings_pct=58.00%

Exercice 2 — Dimensionneur de Volumes de Stockage EBS (gp3 vs io2 Block Express)

Étude de cas Niveau 2 — Application

Objectif : Valider et calculer les paramètres d'un volume EBS en respectant les plafonds et ratios officiels d'AWS.

Amazon Elastic Block Store (EBS) propose différents types de volumes SSD :

1. gp3 (General Purpose SSD) :
- Taille : 1 GiB à 16 384 GiB.
- Base incluse gratuite : 3 000 IOPS et 125 MB/s de débit.
- Maximum provisionnable : 16 000 IOPS et 1 000 MB/s.
- Règle de cohérence : le ratio max est de 500 IOPS par GiB.

2. io2 Block Express (Provisioned IOPS SSD) :
- Taille : 4 GiB à 65 536 GiB.
- Maximum provisionnable : 256 000 IOPS et 4 000 MB/s.
- Règle de cohérence : le ratio max est de 1 000 IOPS par GiB.

Données du cas :
EBS_CHECK TYPE=<gp3|io2> SIZE_GIB=<n> IOPS=<n> MBPS=<n>.

Résultat d’analyse attendu :
Si conforme : EBS_VERDICT: type=<t> size=<s>GiB iops=<i> mbps=<m> status=VALID.
Si non conforme : EBS_VERDICT: type=<t> size=<s>GiB status=INVALID reason=<BAD_SIZE|EXCEEDED_IOPS|EXCEEDED_MBPS|RATIO_IOPS_EXCEEDED>.

Cas d’exemple
EBS_CHECK TYPE=gp3 SIZE_GIB=100 IOPS=3000 MBPS=125
Résolution attendue
EBS_VERDICT: type=gp3 size=100GiB iops=3000 mbps=125 status=VALID

Exercice 3 — Simulateur d'Auto Scaling Group & Répartition Équilibrée Multi-AZ

Étude de cas Niveau 3 — Raisonnement

Objectif : Simuler l'algorithme de répartition équilibrée d'un Auto Scaling Group lors d'un événement de mise à l'échelle (Scale Out ou Scale In).

Un Auto Scaling Group (ASG) garantit que les instances sont toujours réparties le plus équitablement possible entre les Availability Zones (AZs) configurées :

Algorithme de répartition :
1. Scale Out (Ajout d'instances) :
À chaque nouvelle instance à ajouter, l'ASG sélectionne la zone qui possède actuellement le moins d'instances. En cas d'égalité, il choisit la première zone par ordre alphabétique.
2. Scale In (Suppression d'instances) :
À chaque instance à supprimer, l'ASG sélectionne la zone qui possède le plus d'instances. En cas d'égalité, il choisit la première zone par ordre alphabétique.
3. Bornes Min/Max : La capacité cible (Desired) ne peut pas descendre sous MIN ni dépasser MAX (tronquer si nécessaire).

Données du cas :
ASG_DISTRIB ZONES=<az1:count,az2:count,...> TARGET=<n> MIN=<min> MAX=<max>.

Résultat d’analyse attendu :
ASG_PLAN: target=<t> current=<c> delta=<+n|-n|0> final_distribution=<az1:count,az2:count,...>.

Cas d’exemple
ASG_DISTRIB ZONES=eu-west-3a:1,eu-west-3b:1,eu-west-3c:1 TARGET=6 MIN=2 MAX=10
Résolution attendue
ASG_PLAN: target=6 current=3 delta=+3 final_distribution=eu-west-3a:2,eu-west-3b:2,eu-west-3c:2

7. QCM — niveau examen

Quel modèle d'achat EC2 permet d'obtenir jusqu'à 90% de réduction par rapport au tarif On-Demand, sous réserve d'accepter des interruptions potentielles avec 2 minutes de préavis ?

Les instances Spot exploitent le surplus de capacité matérielle inutilisée d'AWS avec jusqu'à 90% de rabais, mais AWS peut les réclamer avec un préavis d'interruption de 2 minutes.

Quelle caractéristique technique distingue les volumes EBS gp3 par rapport aux anciens volumes gp2 ?

Contrairement à gp2 dont les performances dépendaient strictement du nombre de Go alloués, gp3 permet de provisionner les IOPS et le débit indépendamment de la capacité de stockage.

À quelle couche du modèle OSI l'Application Load Balancer (ALB) opère-t-il pour inspecter les requêtes HTTP/HTTPS ?

L'Application Load Balancer opère au niveau de la couche 7 (Application), ce qui lui permet d'inspecter les en-têtes HTTP, les URLs, les cookies et d'effectuer des redirections intelligentes.

Comment un Auto Scaling Group réagit-il lors d'un événement de Scale Out pour maintenir une haute disponibilité optimale ?

Pour garantir la tolérance aux pannes, l'Auto Scaling Group veille à toujours équilibrer la flotte en allouant les nouvelles instances dans la zone de disponibilité la moins chargée.

Quel service d'orchestration AWS permet d'exécuter des conteneurs Docker sans avoir à gérer, dimensionner ni patcher de machines virtuelles EC2 sous-jacentes ?

AWS Fargate est une technologie de calcul serverless pour conteneurs (utilisable avec ECS et EKS) qui abstrait totalement l'infrastructure et les serveurs sous-jacents.

Quelle métrique un volume EBS gp3 inclut-il gratuitement de base, sans frais additionnels ?

Tout volume EBS gp3 inclut gratuitement 3 000 IOPS et 125 MB/s de débit de base, quelle que soit sa taille en GiB.

Qu'advient-il d'une instance EC2 membre d'un Auto Scaling Group qui échoue de manière répétée aux sondes de santé (Health Checks) de son Load Balancer ?

L'ASG intègre l'auto-healing : dès qu'une instance est déclarée Unhealthy par le Load Balancer, il la termine et en instancie une nouvelle pour préserver la capacité désirée.

Pourquoi les snapshots Amazon EBS sont-ils qualifiés d'incrémentaux ?

Les snapshots EBS sont incrémentaux : seule la différence (les blocs modifiés depuis la sauvegarde précédente) est stockée dans S3, ce qui réduit considérablement les coûts et le temps de sauvegarde.

8. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Tenter de rattacher un volume EBS à une instance EC2 située dans une Availability Zone différente (EBS est lié à une seule AZ, sauf réplication via snapshot).
  • Utiliser des instances Spot pour des bases de données d'état critiques non répliquées qui ne peuvent pas tolérer une interruption abrupte.
  • Oublier de configurer des Health Checks réalistes sur le Load Balancer, entraînant le maintien en ligne d'instances défaillantes.
  • Utiliser les anciennes Launch Configurations dépréciées au lieu des Launch Templates modernes recommandés par AWS.

9. Méthodologie de résolution

Démarche de Dimensionnement & Résilience de Calcul
  1. Analyse du profil de charge : séparer la charge socle continue (à couvrir par des Savings Plans / Reserved Instances) des variations de trafic imprévisibles (gérées par l'Auto Scaling).
  2. Création d'un Launch Template standardisé : configurer l'AMI durcie, le Security Group minimal, le rattachement d'Instance Profile IAM et le script User Data automatisant l'installation.
  3. Mise en place de l'équilibreur de charge ALB multi-AZ : déclarer au minimum deux sous-réseaux publics dans des zones distinctes et paramétrer des sondes de santé HTTP précises.
  4. Configuration de l'Auto Scaling Group : attacher le Target Group de l'ALB, fixer les capacités Min/Desired/Max et activer une politique de mise à l'échelle Target Tracking (CPU à 50%).

10. Révision active

Résumé essentiel
  • Amazon EC2 propose des familles d'instances adaptées (General Purpose, Compute, Memory, Storage) et des modèles d'achat permettant d'optimiser jusqu'à 90% des coûts (Reserved, Spot).
  • Amazon EBS fournit du stockage bloc persistant hautement disponible au sein d'une AZ, avec les volumes gp3 (performances modulables) et des snapshots incrémentaux vers S3.
  • L'Application Load Balancer (ALB) opère en couche 7 (HTTP/HTTPS, routage d'URL, SSL), tandis que le Network Load Balancer (NLB) traite des millions de requêtes en couche 4 à latence ultra-faible.
  • L'Auto Scaling Group (ASG) ajuste automatiquement le nombre d'instances entre les bornes Min et Max, tout en assurant une répartition rigoureusement équilibrée entre les Availability Zones.
  • AWS Fargate élimine la gestion de serveurs physiques en fournissant un moteur de calcul serverless pour conteneurs Docker sous Amazon ECS et EKS.

Checklist de maîtrise

  • Savez-vous choisir le modèle d'achat EC2 le plus économique selon la nature et la prévisibilité d'une charge ?
  • Comprenez-vous le fonctionnement des volumes EBS gp3 et le rôle des snapshots incrémentaux ?
  • Distinguez-vous parfaitement les cas d'usage d'un Application Load Balancer (ALB) par rapport à un Network Load Balancer (NLB) ?
  • Savez-vous comment un Auto Scaling Group réagit lors d'un événement de mise à l'échelle pour maintenir l'équilibre Multi-AZ ?
  • Pouvez-vous expliquer le concept de serverless containers apporté par AWS Fargate ?

Les 8 notions à connaître absolument

  1. Amazon EC2 : Elastic Compute Cloud : service de machines virtuelles sécurisées et redimensionnables dans le cloud AWS.
  2. Spot Instance : Instance EC2 achetée avec jusqu'à 90% de remise sur le surplus de capacité AWS, interruptible avec 2 minutes de préavis.
  3. Amazon EBS : Elastic Block Store : volumes de stockage bloc montables sur une instance EC2 dans la même zone de disponibilité.
  4. Volume gp3 : Volume SSD standard offrant 3 000 IOPS et 125 MB/s inclus sans surcoût, extensibles indépendamment de la taille.
  5. ALB (Application Load Balancer) : Répartiteur de charge couche 7 supportant le routage avancé basé sur le chemin d'URL, les cookies et WebSockets.
  6. Auto Scaling Group (ASG) : Groupe d'instances EC2 ajustant automatiquement sa capacité pour maintenir la disponibilité et l'équilibre zonal.
  7. Target Tracking : Politique d'auto-scaling maintenant une métrique cible (ex: utilisation CPU moyenne à 50%) en ajustant la flotte.
  8. AWS Fargate : Moteur de calcul serverless exécutant des conteneurs Docker (ECS/EKS) sans provisionner ni administrer de serveurs EC2.
