Chapitre 4 — Réseau Avancé — Amazon VPC, Sous-réseaux, Routage & Pare-feux (SG / NACL)

Module 4 ≈ 2 h 45 Réservé B3 et plus
Mise en situation

Dans le cadre du déploiement d'une architecture cloud d'entreprise sécurisée, vous devez concevoir l'infrastructure réseau Amazon Virtual Private Cloud (VPC). Votre mission comprend le découpage d'un bloc CIDR /16 en sous-réseaux publics, applicatifs et bases de données répartis sur plusieurs zones de disponibilité, la configuration des tables de routage avec passerelles Internet et NAT managées, et le durcissement périmétrique en combinant Security Groups avec état et Network ACLs sans état.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. Concevoir et découper un plan d'adressage Amazon VPC en sous-réseaux multi-AZ en maîtrisant les 5 adresses IP réservées par sous-réseau.
  2. Configurer les tables de routage et différencier l'Internet Gateway (sous-réseaux publics) de la NAT Gateway (sous-réseaux privés).
  3. Maîtriser et simuler le filtrage combiné des Security Groups (stateful) et des Network ACLs (stateless, règles numérotées et ports éphémères).
  4. Identifier les solutions d'interconnexion réseau avancées : VPC Peering, AWS Transit Gateway, VPC Endpoints et Direct Connect.

1. Amazon VPC : Blocs CIDR & Sous-réseaux Multi-AZ

Amazon Virtual Private Cloud (VPC) est votre réseau virtuel privé isolé au sein du cloud AWS, logiquement équivalent à un réseau d'entreprise traditionnel :

Plages d'Adresses CIDR (RFC 1918)

  • Un VPC est associé à un ou plusieurs blocs d'adresses IPv4 privés (ex: 10.0.0.0/16 offrant 65 536 adresses).
  • Le masque autorisé par AWS est compris strictement entre /16 (le plus grand) et /28 (le plus petit : 16 adresses).
  • Un VPC est une ressource régionale ; les sous-réseaux découpés au sein du VPC sont quant à eux strictement confinés à une Availability Zone unique.

Les 5 Adresses IP Réservées par Sous-Réseau

Dans chaque sous-réseau AWS, 5 adresses IP ne peuvent JAMAIS être attribuées à des instances :

  • .0 : adresse réseau du sous-réseau.
  • .1 : routeur VPC par défaut (passerelle locale).
  • .2 : serveur DNS Amazon (Route 53 Resolver / AmazonProvidedDNS).
  • .3 : réservé par AWS pour extension future.
  • Dernière IP (ex: .255 pour /24) : adresse de diffusion (broadcast).

2. Routage VPC : Internet Gateway, NAT Gateway & Tables de Routage

Le trafic au sein d'un VPC est guidé par des tables de routage associées à chaque sous-réseau :

Tables de Routage (Route Tables)

Chaque table contient une route locale implicite (ex: 10.0.0.0/16 → local) permettant la communication privée entre tous les sous-réseaux du VPC.

Pour joindre l'extérieur, une route par défaut 0.0.0.0/0 est ajoutée vers une cible réseau spécifique.

Internet Gateway (IGW)

Passerelle redondante et managée hautement disponible attachée au VPC.

Un sous-réseau dont la table de routage pointe 0.0.0.0/0 → igw-xxxx est qualifié de sous-réseau public. Ses instances ayant une IP publique peuvent échanger directement avec Internet.

NAT Gateway Managée

Déployée obligatoirement dans un sous-réseau public avec une Elastic IP.

Permet aux instances de sous-réseaux privés (route 0.0.0.0/0 → nat-xxxx) d'initier des connexions sortantes vers Internet (téléchargement de paquets, APIs) tout en bloquant toute intrusion entrante.

3. Sécurité Réseau : Security Groups (Stateful) vs Network ACLs (Stateless)

La défense en profondeur au sein d'un VPC combine deux lignes de filtrage distinctes :

Security Groups (SG) — Première Ligne (Instance)

  • Opère au niveau de l'interface réseau élastique (ENI) de l'instance.
  • Avec état (Stateful) : si une connexion entrante est autorisée, le paquet retour sortant est automatiquement accepté, quel que soit le port éphémère.
  • Par défaut en entrée : tout est bloqué (Deny implicite). On ne peut ajouter que des règles d'autorisation (Allow).
  • Toutes les règles sont évaluées globalement.
  • Supporte le référencement d'autres Security Groups comme source.

Network ACLs (NACL) — Seconde Ligne (Sous-Réseau)

  • Opère au niveau de la frontière du sous-réseau (Subnet boundary).
  • Sans état (Stateless) : chaque paquet entrant et sortant est examiné isolément. Le trafic réponse doit obligatoirement être permis explicitement par les règles sortantes (ports éphémères 1024-65535).
  • Règles numérotées (1 à 32766) évaluées dans l'ordre croissant : la première règle correspondante s'applique immédiatement. Règle finale * par défaut en Deny.
  • Prend en charge les règles Allow et Deny explicites (idéal pour bloquer une IP attaquante spécifique).

4. Interconnexion & Passerelles Privées : Peering, Transit Gateway & Endpoints

Pour interconnecter plusieurs VPCs et raccorder le réseau sur site (On-Premises) :

VPC Peering

Connexion privée point-à-point entre deux VPCs sans passerelle ni passer par Internet public.

Attention : le peering est strictement non-transitif (si A est connecté à B et B à C, A ne peut pas communiquer avec C sans lien direct A-C).

AWS Transit Gateway

Hub de routage réseau centralisé en topologie en étoile (Hub-and-Spoke).

Permet d'interconnecter des milliers de VPCs et des réseaux sur site avec routage transitif simplifié et tables de routage partagées.

VPC Endpoints (PrivateLink)

Accès privé aux services AWS (S3, DynamoDB, SQS) sans sortir sur Internet ni traverser de NAT Gateway.

Deux types : Gateway Endpoints (gratuits, pour S3 et DynamoDB via tables de routage) et Interface Endpoints (cartes ENI privées via AWS PrivateLink).

Exercice 1 — Calculateur de Sous-réseaux CIDR & Adresses Réservées AWS

Python Niveau 1 — Acquisition

Objectif : Calculer la plage d'adresses d'un sous-réseau VPC, les 5 adresses IP réservées par AWS et le nombre d'adresses assignables.

Dans tout sous-réseau d'un Amazon Virtual Private Cloud (VPC), AWS réserve obligatoirement 5 adresses IP :

1. .0 : Adresse réseau.
2. .1 : Passerelle du routeur VPC par défaut.
3. .2 : Serveur DNS fourni par Amazon (AmazonProvidedDNS / Route 53 Resolver).
4. .3 : Réservé par AWS pour extension future.
5. Dernière adresse (ex: .255 pour un /24) : Adresse de diffusion (broadcast réseau).

Formule :
- Total d'adresses brutes : 2 ** (32 - masque).
- Adresses IP réellement utilisables pour des instances : Total - 5.

Entrée STDIN : VPC_SUBNET CIDR=<ip/masque> (ex: 10.0.1.0/24).
Sortie : SUBNET_CALC: total_ips=<t> usable_ips=<u> net_ip=<net> router_ip=<r> dns_ip=<d> broadcast_ip=<b>.

Entrée du programme
VPC_SUBNET CIDR=10.0.1.0/24
Sortie attendue
SUBNET_CALC: total_ips=256 usable_ips=251 net_ip=10.0.1.0 router_ip=10.0.1.1 dns_ip=10.0.1.2 broadcast_ip=10.0.1.255

Exercice 2 — Auditeur de Tables de Routage VPC (Public vs Privé vs Isolé)

Python Niveau 2 — Application

Objectif : Qualifier un sous-réseau VPC selon la destination de sa route par défaut 0.0.0.0/0.

Dans Amazon VPC, la typologie d'un sous-réseau dépend de sa Route Table :

1. PUBLIC :
Comporte une route par défaut 0.0.0.0/0 pointant directement vers une passerelle Internet igw-<id>.
Les instances avec IP publique peuvent communiquer directement avec Internet.

2. PRIVATE :
Comporte une route par défaut 0.0.0.0/0 pointant vers une passerelle NAT managée nat-<id> ou une instance NAT.
Les instances peuvent initier des connexions sortantes (ex: téléchargement de patchs) mais sont inaccessibles depuis l'extérieur.

3. ISOLATED :
Aucune route vers 0.0.0.0/0. Le trafic est strictement confiné au VPC local ou à des passerelles d'extrémités privées (VPC Endpoints vpce-<id> ou Peering pcx-<id>).

Entrée STDIN :
ROUTE_AUDIT SUBNET=<id> ROUTES=<dest1->target1;dest2->target2;...>.

Sortie : ROUTE_VERDICT: subnet=<id> type=<PUBLIC|PRIVATE|ISOLATED> default_target=<target|NONE>.

Entrée du programme
ROUTE_AUDIT SUBNET=subnet-0a1b2c3d ROUTES=10.0.0.0/16->local;0.0.0.0/0->igw-11223344
Sortie attendue
ROUTE_VERDICT: subnet=subnet-0a1b2c3d type=PUBLIC default_target=igw-11223344

Exercice 3 — Simulateur de Pare-feu : Security Group (Stateful) vs Network ACL (Stateless)

Python Niveau 3 — Raisonnement

Objectif : Évaluer le filtrage d'un flux entrant ou d'un retour sortant en combinant Security Groups et Network ACLs.

La sécurité réseau AWS repose sur deux couches complémentaires :

1. Security Group (Avec état / Stateful) :
- S'applique au niveau de l'interface réseau élastique (ENI) de l'instance.
- Tout trafic retour d'un flux entrant autorisé est automatiquement accepté, quelles que soient les règles sortantes.
- Par défaut en entrée : DENY.

2. Network ACL (Sans état / Stateless) :
- S'applique au niveau du sous-réseau.
- Règles numérotées (1..32766) évaluées par ordre croissant : la première règle correspondante s'applique (ALLOW ou DENY).
- Règle par défaut * (fin de liste) : DENY.
- Sans état : Pour qu'un paquet retour d'une connexion TCP puisse sortir, la NACL doit comporter une règle sortante autorisant les ports éphémères (ex: 1024-65535).

Entrée STDIN :
FLOW_CHECK DIRECTION=<INBOUND|RETURN_OUTBOUND> PORT=<n> SG_IN=<ports_allow> NACL_RULES=<num:Effect:port_or_range;...>.

Sortie : FLOW_VERDICT: dir=<d> port=<p> sg=<ALLOW|DENY> nacl=<ALLOW|DENY> final=<ALLOW|DENY>.

Entrée du programme
FLOW_CHECK DIRECTION=INBOUND PORT=443 SG_IN=80,443 NACL_RULES=100:Allow:443;200:Deny:All;*:Deny:All
Sortie attendue
FLOW_VERDICT: dir=INBOUND port=443 sg=ALLOW nacl=ALLOW final=ALLOW

6. QCM — niveau examen

Combien d'adresses IP utilisables pour des instances sont disponibles dans un sous-réseau AWS de masque /24 (256 adresses au total) ?

AWS réserve obligatoirement 5 adresses IP dans chaque sous-réseau (.0 réseau, .1 routeur VPC, .2 DNS, .3 réservé futur, .255 broadcast). Il reste donc 256 - 5 = 251 adresses utilisables.

Dans quel type de sous-réseau une NAT Gateway doit-elle obligatoirement être déployée pour permettre aux serveurs privés de joindre Internet ?

Une NAT Gateway doit obligatoirement résider dans un sous-réseau public associé à une Elastic IP pour pouvoir relayer les flux vers l'Internet Gateway du VPC.

Pourquoi n'est-il PAS nécessaire d'autoriser explicitement les ports clients en sortie dans un Security Group lorsqu'un flux entrant HTTP (port 80) est accepté ?

Les Security Groups sont Stateful : ils mémorisent l'état des flux établis. Si le flux entrant est autorisé, le paquet retour vers le client est automatiquement permis.

Comment les règles d'une Network ACL (NACL) sont-elles évaluées par AWS lorsqu'un paquet arrive à la frontière d'un sous-réseau ?

Les NACLs évaluent les règles dans l'ordre strictement croissant de leur numéro. Dès qu'une règle correspond au trafic (Allow ou Deny), la décision est prise et l'évaluation s'arrête.

Pourquoi le VPC Peering classique entre VPC A, VPC B et VPC C ne permet-il pas à A de communiquer avec C si seuls les peerings A-B et B-C sont configurés ?

Le peering VPC ne supporte pas le routage transitif. Pour que A et C communiquent, il faut soit créer un peering direct A-C, soit utiliser une AWS Transit Gateway.

Quelle adresse IP est automatiquement affectée au résolveur DNS AmazonProvidedDNS dans le sous-réseau 10.0.5.0/24 ?

Dans tout sous-réseau AWS, l'adresse réseau + 2 (.2) est systématiquement réservée pour le serveur DNS interne fourni par Amazon (Route 53 Resolver).

Quel service d'interconnexion physique dédiée permet de relier un centre de données sur site à un VPC AWS avec une bande passante garantie de 1 à 100 Gbps ?

AWS Direct Connect établit une liaison réseau en fibre dédiée privée entre les locaux d'une entreprise et AWS, contournant entièrement l'Internet public pour garantir performance et sécurité.

Quelle est la taille minimale (le plus petit sous-réseau) autorisée par AWS lors de la création d'un sous-réseau VPC ?

Le plus petit bloc CIDR autorisé par AWS pour un sous-réseau est /28 (16 adresses au total, dont 11 assignables à des interfaces après déduction des 5 IPs réservées).

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Oublier de soustraire les 5 adresses IP réservées lors du calcul de dimensionnement des sous-réseaux VPC.
  • Déployer une NAT Gateway dans un sous-réseau privé : elle ne pourra jamais communiquer avec l'Internet public sans Internet Gateway dans son sous-réseau.
  • Bloquer les ports éphémères sortants (1024-65535) dans une Network ACL, provoquant le blocage complet des réponses aux requêtes web des clients.
  • Tenter d'utiliser un VPC Peering pour faire du routage transitif entre trois VPCs sans établir de liens de peering directs pour chaque paire.

8. Méthodologie de résolution

Méthodologie de Conception d'un VPC d'Entreprise
  1. Dimensionnement du bloc CIDR : sélectionner une plage privée RFC 1918 (ex: 10.0.0.0/16) qui ne chevauche pas les réseaux sur site de l'entreprise.
  2. Architecture 3-tiers multi-AZ : découper le VPC en sous-réseaux Publics (ALB), Privés Applicatifs (instances EC2) et Privés Données (bases de données RDS) répartis sur au moins 2 AZs distinctes.
  3. Isolation du routage : déployer des passerelles NAT Gateway redondées dans les sous-réseaux publics et n'associer de passerelle Internet qu'aux sous-réseaux hébergeant des répartiteurs publics.
  4. Chaining des Security Groups : autoriser le trafic HTTP sur l'ALB depuis Internet (0.0.0.0/0), autoriser le trafic sur les instances uniquement depuis le groupe de l'ALB, et autoriser la base de données uniquement depuis le groupe applicatif.

9. Révision active

Résumé essentiel
  • Amazon VPC fournit un réseau virtuel isolé au sein d'une région AWS, découpé en sous-réseaux confinés à une Availability Zone unique.
  • AWS réserve obligatoirement 5 adresses IP dans chaque sous-réseau (.0 réseau, .1 routeur, .2 DNS AWS, .3 futur, .255 broadcast).
  • Un sous-réseau public achemine son trafic 0.0.0.0/0 vers une Internet Gateway, tandis qu'un sous-réseau privé utilise une NAT Gateway pour ses flux sortants.
  • Les Security Groups sont avec état (stateful) au niveau de l'instance ; les Network ACLs sont sans état (stateless) avec règles numérotées au niveau du sous-réseau.
  • AWS Transit Gateway simplifie l'interconnexion complexe de multiples VPCs et sites distants en surmontant la non-transitivité du VPC Peering classique.

Checklist de maîtrise

  • Savez-vous calculer le nombre exact d'adresses assignables dans un sous-réseau /24 ou /28 en tenant compte des 5 IPs réservées AWS ?
  • Comprenez-vous pourquoi une NAT Gateway doit obligatoirement être déployée dans un sous-réseau public pour fonctionner ?
  • Savez-vous expliquer la différence de comportement entre un Security Group stateful et une Network ACL stateless sur le trafic retour ?
  • Pouvez-vous justifier l'intérêt du chaining de Security Groups par rapport à l'utilisation d'adresses IP statiques ?
  • Connaissez-vous la distinction entre un Gateway Endpoint (S3/DynamoDB) et un Interface Endpoint PrivateLink ?

Les 8 notions à connaître absolument

  1. Amazon VPC : Virtual Private Cloud : réseau virtuel isolé régional personnalisable dans le cloud AWS.
  2. Adresses Réservées AWS : Les 5 premières et dernière adresses de tout sous-réseau (.0, .1, .2, .3, .255) réservées pour l'infrastructure interne.
  3. Internet Gateway (IGW) : Composant managé hautement disponible permettant la communication directe entre un VPC et l'Internet public.
  4. NAT Gateway : Passerelle de translation d'adresses permettant aux instances privées d'accéder à Internet sans être joignables de l'extérieur.
  5. Security Group : Pare-feu virtuel avec état (stateful) filtrant le trafic au niveau des interfaces réseau élastiques des instances.
  6. Network ACL (NACL) : Pare-feu sans état (stateless) évaluant des règles numérotées par ordre croissant à la frontière du sous-réseau.
  7. Ports Éphémères : Plage de ports clients (1024-65535) obligatoirement autorisée en sortie dans les NACLs pour recevoir les réponses TCP.
  8. Transit Gateway : Hub de routage réseau centralisé en étoile reliant des milliers de VPCs et des réseaux sur site avec transitivité.
