Chapitre 6 — Serverless, Observabilité, Supervision & Automatisation (Lambda, CloudWatch, SQS, SNS)

Module 6 ≈ 2 h 45 Réservé B3 et plus
Mise en situation

Pour achever la modernisation du système d'information de votre entreprise, vous devez concevoir une architecture pilotée par les événements (Event-Driven) hautement scalable et découplée. Vous allez orchestrer des fonctions serverless AWS Lambda connectées à des files d'attente Amazon SQS protégées par Dead-Letter Queue, diffuser des notifications multi-abonnés via Amazon SNS, centraliser les métriques et alertes critiques sous Amazon CloudWatch, et auditer l'activité avec AWS CloudTrail.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. Maîtriser le fonctionnement et la tarification à l'usage d'AWS Lambda (exécution pilotée par événements, mémoire, durée max de 15 min, cold start).
  2. Concevoir des architectures asynchrones découplées et tolérantes aux pannes avec Amazon SQS (Standard, FIFO, Dead-Letter Queue) et Amazon SNS (Pub/Sub fan-out).
  3. Superviser les charges de travail avec Amazon CloudWatch (métriques, logs, alarmes composites) et tracer l'activité API avec AWS CloudTrail.
  4. Automatiser le déploiement d'infrastructures cloud via l'Infrastructure as Code (IaC) avec AWS CloudFormation et le Cloud Development Kit (CDK).

1. AWS Lambda & l'Architecture Serverless Événementielle

AWS Lambda est le service de calcul serverless phare d'AWS permettant d'exécuter du code sans provisionner ni administrer de serveurs :

Principes de Fonctionnement

  • Piloté par les événements (Event-driven) : déclenché automatiquement par des sources d'événements (dépose de fichier dans S3, requête HTTP via API Gateway, message SQS, modification de table DynamoDB).
  • Scalabilité instantanée : passe automatiquement de 0 à des milliers d'exécutions concurrentes en quelques fractions de seconde.
  • Durée maximale d'exécution : 15 minutes (900 secondes) au maximum par invocation.
  • Allocation proportionnelle : la puissance CPU et la bande passante réseau sont allouées proportionnellement à la quantité de mémoire RAM configurée (de 128 MB à 10 240 MB).

Cold Start & Provisioned Concurrency

  • Cold Start (Démarrage à froid) : latence initiale lors de la création d'un nouvel environnement d'exécution (initialisation du runtime Python/Node/Java et chargement du code).
  • Provisioned Concurrency : préchauffe un nombre défini d'environnements d'exécution pour garantir une latence de démarrage à deux chiffres en millisecondes pour les APIs critiques.
  • Facturation à la milliseconde : coût basé uniquement sur le nombre d'invocations et la consommation de calcul en Go-secondes (GB-seconds).

2. Découplage Asynchrone : Amazon SQS & Amazon SNS

Pour éviter les pannes en cascade et absorber les pics de charge, les composants applicatifs doivent être découplés de manière asynchrone :

Amazon SQS (Simple Queue Service) — Modèle Pull

  • File d'attente de messages distribuée hautement disponible. Les consommateurs interrogent la file (Pull).
  • Files Standard : débit quasi illimité, garantie de distribution au moins une fois (at-least-once), ordre des messages non garanti.
  • Files FIFO (First-In-First-Out) : ordre de distribution strictement préservé, traitement unique sans doublon (exactly-once), débit limité à 300 msg/s (ou 3 000 avec batching).
  • Dead-Letter Queue (DLQ) : file de rebut isolant automatiquement les messages toxiques ayant échoué après un nombre maximal de tentatives (MaxReceiveCount) pour analyse ultérieure.

Amazon SNS (Simple Notification Service) — Modèle Push

  • Service de messagerie Pub/Sub (Publication / Abonnement) basé sur des sujets (Topics).
  • Lorsqu'un message est publié sur un Topic, SNS le pousse (Push) instantanément à tous les abonnés enregistrés.
  • Abonnés hétérogènes : files SQS, fonctions Lambda, adresses e-mail, numéros SMS, webhooks HTTP/S.
  • Fan-out Pattern : un événement unique publié dans SNS est dupliqué vers plusieurs files SQS distinctes pour être traité en parallèle par différents services métiers.

3. Observabilité & Surveillance : Amazon CloudWatch

Amazon CloudWatch est la suite centralisée de supervision des ressources et applications hébergées sur AWS et sur site :

CloudWatch Metrics

Collecte des séries temporelles de performances générées automatiquement par tous les services AWS (CPUUtilization, NetworkIn, DiskReadBytes, Invocations Lambda, SQS ApproximateNumberOfMessagesVisible).

Résolution standard de 1 minute ou détaillée de 1 seconde.

CloudWatch Logs

Centralisation, indexation et analyse en temps réel des journaux applicatifs et système (fichiers logs d'OS via CloudWatch Agent, sorties stdout/stderr des Lambdas, logs d'accès VPC Flow Logs).

CloudWatch Alarms

Déclenche automatiquement des actions lorsque des seuils définis sont dépassés sur N périodes consécutives.

Actions possibles : envoi d'une notification SNS, déclenchement d'une politique d'auto-scaling EC2, ou redémarrage/arrêt automatique d'une VM défaillante.

4. Traçabilité & Audit des Accès : AWS CloudTrail

Alors que CloudWatch surveille les performances et l'état des ressources, AWS CloudTrail surveille les actions et les personnes :

  • Historique complet des appels API : enregistre chaque interaction avec la plateforme AWS (actions émises via la Console, l'AWS CLI, les SDKs ou les services automatisés).
  • Métadonnées d'audit détaillées : consigne QUI a fait la demande (utilisateur IAM, rôle STS), QUAND (horodatage précis UTC), DEPUIS OÙ (adresse IP source), QUEL SERVICE a été appelé et QUELLE A ÉTÉ la réponse (succès ou code d'erreur AccessDenied).
  • Intégrité et sécurité : activation recommandée sur toutes les régions (multi-region trail), chiffrement des journaux avec AWS KMS et validation d'intégrité cryptographique des fichiers de log (Digest files) pour empêcher toute altération malveillante.

5. Infrastructure as Code (IaC) : CloudFormation & AWS CDK

L'automatisation déclarative d'infrastructures élimine les erreurs humaines et garantit la reproductibilité des environnements :

AWS CloudFormation

  • Définit l'infrastructure sous forme de templates déclaratifs au format JSON ou YAML.
  • Regroupe les ressources dans une pile (Stack) gérée comme une unité atomique (création, mise à jour, suppression ordonnée).
  • Détection des dérives (Drift Detection) pour identifier les modifications manuelles effectuées hors template.

AWS Cloud Development Kit (CDK)

  • Framework de développement logiciel permettant de modéliser l'infrastructure avec des langages de programmation modernes (Python, TypeScript, Java, C#).
  • Compile le code impératif en templates CloudFormation déclaratifs tout en fournissant des composants de haut niveau (Constructs) intégrant les meilleures pratiques de sécurité.

Exercice 1 — Calculateur de Coûts Serverless AWS Lambda (Go-secondes & Requêtes)

Étude de cas Niveau 1 — Acquisition

Objectif : Calculer la facture mensuelle d'une fonction AWS Lambda selon sa mémoire allouée, sa durée d'exécution et le nombre d'invocations.

Le modèle de tarification d'AWS Lambda repose sur deux axes :

1. Coût des requêtes : 0.20 $ par million de requêtes (soit 0.0000002 $ par requête).
2. Coût de calcul (Go-secondes) :
La mémoire (ex: 512 MB) est convertie en Go : Go = Memory_MB / 1024.0.
La durée en ms est convertie en secondes : Secondes = Duration_MS / 1000.0.
Go_Secondes = Requetes * Go * Secondes.
Tarif unitaire de calcul : 0.0000166667 $ par Go-seconde (architecture x86).

3. AWS Free Tier (Optionnel) :
Si FREE_TIER=YES, déduire chaque mois :
- 1 000 000 de requêtes gratuites (minimum facturé 0).
- 400 000 Go-secondes gratuites (minimum facturé 0).

Entrée STDIN :
LAMBDA_COST REQS=<n> DURATION_MS=<ms> MEM_MB=<mb> FREE_TIER=<YES|NO>.

Sortie :
LAMBDA_BILL: gb_seconds=<gbs:.2f> req_cost=<rc:.4f>$ compute_cost=<cc:.4f>$ total_cost=<tot:.2f>$.

Cas d’exemple
LAMBDA_COST REQS=5000000 DURATION_MS=200 MEM_MB=512 FREE_TIER=NO
Résolution attendue
LAMBDA_BILL: gb_seconds=500000.00 req_cost=1.0000$ compute_cost=8.3334$ total_cost=9.33$

Exercice 2 — Analyseur de Métriques & Détecteur d'Alarmes Amazon CloudWatch

Étude de cas Niveau 2 — Application

Objectif : Évaluer l'état d'une alarme CloudWatch (OK, ALARM, INSUFFICIENT_DATA) selon la règle des N points de données consécutifs.

Une alarme Amazon CloudWatch surveille une métrique (ex: CPUUtilization) :

Règles d'évaluation :
1. OPERATOR :
- GREATER_EQUAL : un point est en infraction si valeur >= THRESHOLD.
- LESS_EQUAL : un point est en infraction si valeur <= THRESHOLD.
2. PERIODS : Nombre de points consécutifs récents nécessaires pour déclencher l'alarme.
3. États de l'alarme :
- Si le nombre de points disponibles est inférieur à PERIODS -> INSUFFICIENT_DATA.
- Si les PERIODS derniers points sont TOUS en infraction -> ALARM.
- Sinon -> OK.

Entrée STDIN :
CW_ALARM METRIC=<nom> THRESHOLD=<t> OP=<GREATER_EQUAL|LESS_EQUAL> PERIODS=<n> POINTS=<p1,p2,...>.

Sortie : ALARM_VERDICT: metric=<nom> state=<OK|ALARM|INSUFFICIENT_DATA> evaluated_points=<pts>.

Cas d’exemple
CW_ALARM METRIC=CPUUtilization THRESHOLD=80.0 OP=GREATER_EQUAL PERIODS=3 POINTS=45.0,78.0,85.0,88.0,92.0
Résolution attendue
ALARM_VERDICT: metric=CPUUtilization state=ALARM evaluated_points=85.0,88.0,92.0

Exercice 3 — Simulateur de File d'Attente Amazon SQS & Dead-Letter Queue (DLQ)

Étude de cas Niveau 3 — Raisonnement

Objectif : Simuler le traitement de messages SQS et l'isolation des messages en échec vers une Dead-Letter Queue (DLQ).

Amazon SQS permet de découpler les architectures asynchrones et gère les pannes avec une Dead-Letter Queue (DLQ) :

Règles de cycle de vie d'un message :
1. Chaque message possède un identifiant id, un compteur de tentatives receive_count et un statut de tentative de traitement SUCCESS ou ERROR.
2. Si le traitement est SUCCESS : le message est traité avec succès et supprimé de la file (PROCESSED).
3. Si le traitement est ERROR : le compteur receive_count est incrémenté de 1.
- Si le nouveau receive_count >= MAX_RECEIVES : le message est transféré vers la Dead-Letter Queue (SENT_TO_DLQ).
- Sinon : le message reste dans la file principale pour une nouvelle tentative (RETRY_IN_FLIGHT).

Entrée STDIN :
SQS_PROCESS MAX_RECEIVES=<n> MSGS=<id:rec_count:status;...>.

Sortie :
SQS_SUMMARY: processed=<p> retry_in_flight=<r> dlq_count=<d> dlq_ids=<id1,id2,...|NONE>.

Cas d’exemple
SQS_PROCESS MAX_RECEIVES=3 MSGS=m1:1:SUCCESS;m2:1:ERROR;m3:2:ERROR
Résolution attendue
SQS_SUMMARY: processed=1 retry_in_flight=1 dlq_count=1 dlq_ids=m3

7. QCM — niveau examen

Quelle est la durée maximale d'exécution (timeout limite) autorisée pour une fonction AWS Lambda avant interruption forcée ?

Une fonction AWS Lambda peut s'exécuter pendant une durée maximale de 15 minutes (900 secondes). Au-delà, l'exécution est interrompue et il convient d'employer AWS Batch, ECS ou EC2.

Dans Amazon SQS, quel mécanisme permet d'isoler automatiquement les messages ayant échoué à être traités après N tentatives infructueuses ?

Une Dead-Letter Queue (DLQ) reçoit automatiquement les messages dont le compteur ReceiveCount atteint ou dépasse le seuil MaxReceiveCount configuré, isolant ainsi les messages toxiques.

Quelle est la différence fondamentale entre Amazon CloudWatch et AWS CloudTrail ?

CloudWatch monitore l'état opérationnel et les métriques des ressources (CPU, mémoire, requêtes). CloudTrail est un outil d'audit de gouvernance qui trace l'identité de l'appelant et chaque requête API.

Quel patron d'architecture permet de dupliquer un message unique vers plusieurs files d'attente SQS traitées en parallèle par différents services ?

Le pattern Fan-out consiste à publier un message sur un topic Amazon SNS, auquel sont abonnées plusieurs files SQS distinctes. SNS duplique et pousse le message vers chaque file en parallèle.

Comment la puissance de calcul CPU et la bande passante réseau sont-elles allouées à une fonction AWS Lambda ?

Dans AWS Lambda, l'unique curseur de performance est la mémoire RAM (128 MB à 10 GB). AWS alloue automatiquement la puissance CPU et le réseau de façon strictement proportionnelle à la RAM allouée.

Quelle caractéristique technique distingue formellement une file Amazon SQS FIFO d'une file SQS Standard ?

Les files SQS FIFO (First-In-First-Out) garantissent que les messages sont remis strictement dans l'ordre de leur émission et éliminent les doublons (exactly-once processing).

Dans AWS CloudFormation, quel mécanisme permet d'inspecter les modifications qui seront apportées à l'infrastructure avant de les appliquer réellement ?

Les Change Sets permettent de prévisualiser l'impact d'une mise à jour de template CloudFormation (ressources créées, modifiées ou supprimées avec ou sans interruption) avant validation.

Quel paramètre d'une file Amazon SQS définit la durée pendant laquelle un message retiré par un consommateur reste invisible pour les autres consommateurs ?

Le VisibilityTimeout définit la fenêtre de temps pendant laquelle un message en cours de traitement est masqué pour éviter que d'autres consommateurs ne le traitent en parallèle.

8. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Tenter d'exécuter des traitements batch continus dépassant 15 minutes dans AWS Lambda au lieu d'utiliser AWS Batch ou des instances EC2.
  • Oublier de configurer une Dead-Letter Queue sur une file SQS, provoquant le blocage de consommateurs par des messages corrompus réexécutés indéfiniment.
  • Confondre CloudWatch (monitoring des performances et métriques) avec CloudTrail (journalisation d'audit des appels API de sécurité).
  • Modifier manuellement des ressources déployées par CloudFormation dans la console, ce qui crée des dérives d'état (Stack Drift).

9. Méthodologie de résolution

Démarche d’Ingénierie Serverless & Observabilité
  1. Conception découplée Event-Driven : utiliser Amazon SNS pour diffuser les événements métiers à plusieurs consommateurs, et intercaler des files Amazon SQS devant chaque worker pour amortir la charge.
  2. Sécurisation des files avec Dead-Letter Queue : fixer un MaxReceiveCount (ex: 3 tentatives) pour isoler les messages malformés et éviter les boucles d'échec infinies.
  3. Optimisation des coûts et de la latence Lambda : dimensionner la mémoire RAM pour trouver le compromis optimal durée/coût, et réserver de la Provisioned Concurrency uniquement sur les chemins critiques utilisateurs.
  4. Surveillance proactive et audit d'infrastructure : configurer des alarmes CloudWatch sur les taux d'erreur HTTP 5xx et la taille des files SQS, et activer un trail CloudTrail global consigné dans un bucket S3 verrouillé.

10. Révision active

Résumé essentiel
  • AWS Lambda exécute du code piloté par événements avec montée en charge instantanée, sans gestion de serveurs, avec une durée maximale de 15 minutes et facturation aux Go-secondes.
  • Amazon SQS offre des files d'attente fiables (Standard ou FIFO) avec isolation des messages toxiques via Dead-Letter Queue (DLQ).
  • Amazon SNS permet de diffuser des notifications en temps réel selon le patron Pub/Sub et d'alimenter plusieurs files SQS en parallèle (Fan-out).
  • Amazon CloudWatch centralise les métriques de performances, les logs applicatifs et déclenche des alarmes sur franchissement de seuils.
  • AWS CloudTrail audite l'intégralité des appels d'API (qui, quand, où, quelle action), et AWS CloudFormation automatise le déploiement de piles déclaratives complètes.

Checklist de maîtrise

  • Connaissez-vous la durée maximale d'exécution autorisée pour une fonction AWS Lambda (15 minutes) ?
  • Savez-vous comment fonctionne une Dead-Letter Queue (DLQ) dans Amazon SQS et quel paramètre déclenche le transfert ?
  • Distinguez-vous parfaitement le rôle d'Amazon CloudWatch (métriques et performances) de celui d'AWS CloudTrail (audit des appels d'API) ?
  • Pouvez-vous expliquer le patron d'architecture Fan-out combinant Amazon SNS et plusieurs files Amazon SQS ?
  • Comprenez-vous le fonctionnement des piles (Stacks) et la détection de dérive dans AWS CloudFormation ?

Les 8 notions à connaître absolument

  1. AWS Lambda : Service de calcul serverless exécutant du code en réponse à des événements avec facturation à la milliseconde.
  2. Cold Start : Temps d'initialisation du conteneur et du runtime lors de la première invocation d'une fonction serverless.
  3. Amazon SQS : Simple Queue Service : files d'attente managées de messages permettant de découpler des architectures distribuées.
  4. Dead-Letter Queue (DLQ) : File de rebut SQS recevant les messages ayant dépassé le nombre maximal de tentatives de traitement infructueuses.
  5. Amazon SNS : Simple Notification Service : service de messagerie Pub/Sub envoyant des notifications en mode push à de multiples abonnés.
  6. Fan-out Pattern : Patron d'architecture publiant un message dans un topic SNS qui le duplique vers plusieurs files SQS en parallèle.
  7. Amazon CloudWatch : Plateforme centralisée de surveillance collectant métriques, logs et pilotant des alarmes opérationnelles.
  8. AWS CloudTrail : Service d'audit et de traçabilité consignant l'historique complet de tous les appels API émis sur un compte AWS.
