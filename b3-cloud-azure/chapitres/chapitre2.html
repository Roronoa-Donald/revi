Chapitre 2 — Identité Microsoft Entra ID (Azure AD), RBAC & Gouvernance

Module 2 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans un environnement d'entreprise hébergeant des données financières et des infrastructures critiques, accorder des droits trop larges (ex: rôle Owner ou Contributor généralisé) expose l'organisation à des destructions accidentelles et des compromissions massives. En tant qu'administrateur Cloud Azure, vous devez appliquer le principe du moindre privilège (Least Privilege) via Azure RBAC, automatiser l'authentification applicative sans mot de passe avec les Managed Identities, imposer des garde-fous de conformité avec Azure Policy et protéger les secrets et certificats dans un Azure Key Vault sécurisé par Soft-Delete et Purge Protection.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. maîtriser le modèle d'identité Microsoft Entra ID (ex-Azure Active Directory) et les Managed Identities ;
  2. concevoir et évaluer des attributions de rôles Azure RBAC selon le principe du moindre privilège ;
  3. comprendre la structure JSON d'un rôle RBAC (Actions, NotActions, DataActions, NotDataActions et AssignableScopes) ;
  4. définir et assigner des règles de gouvernance Azure Policy avec effets Audit et Deny ;
  5. sécuriser les secrets, clés et certificats d'entreprise dans Azure Key Vault avec Soft-Delete et Purge Protection ;
  6. analyser et résoudre méthodologiquement des évaluateurs de permissions RBAC, des moteurs de conformité Policy et des auditeurs de secrets Key Vault.

1. Identité Moderne avec Microsoft Entra ID & Managed Identities

Microsoft Entra ID (anciennement Azure Active Directory) est le service d'annuaire et de gestion des identités dans le Cloud. Contrairement à Active Directory Domain Services (AD DS) traditionnel basé sur Kerberos et NTLM, Entra ID repose sur des protocoles modernes web et Cloud (OAuth 2.0, OpenID Connect, SAML 2.0) :

Objets d'Identité Fondamentaux

  • Utilisateurs & Groupes : comptes membres du tenant ou invités externes (B2B) regroupés de manière statique ou dynamique (par attributs de département ou titre).
  • Service Principals (Principaux de service) : identité attribuée à une application tierce ou un pipeline CI/CD (GitHub Actions, Azure DevOps) pour interagir de façon autonome avec l'API Azure.
  • Rôle de sécurité : l'authentification multifacteur (MFA) et les stratégies d'accès conditionnel (Conditional Access) protègent les accès à risque selon la localisation, l'état de conformité du terminal et le risque utilisateur.

Managed Identities (Identités Managées)

  • Zéro secret dans le code : élimine le besoin pour les développeurs d'écrire des identifiants ou mots de passe dans les fichiers de configuration de leurs VMs ou Web Apps.
  • System-Assigned : identité liée au cycle de vie de la ressource Azure. Si la VM est supprimée, son identité dans Entra ID est automatiquement révoquée.
  • User-Assigned : ressource Azure indépendante pouvant être partagée entre plusieurs machines ou conteneurs pour mutualiser des permissions identiques.

2. Contrôle d'Accès Granulaire Azure RBAC (Role-Based Access Control)

Azure RBAC détermine les autorisations accordées à une identité (Security Principal) sur un périmètre donné (Scope). Une attribution de rôle combine obligatoirement trois éléments : Qui (Principal), Quoi (Role Definition) et Où (Scope) :

Composant du Rôle RBACRôle et SyntaxeExemple Concret
Actions (Plan de contrôle)Liste des opérations administratives autorisées via ARM (création, modification, lecture, redémarrage).Microsoft.Compute/virtualMachines/restart/action
NotActionsOpérations expressément exclues de la liste précédente (effet de soustraction de droits).Microsoft.Compute/virtualMachines/delete
DataActions (Plan de données)Opérations sur les données applicatives internes de la ressource (lecture de blobs, requêtes Cosmos DB).Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read
NotDataActionsExclusions appliquées aux opérations de données internes.Microsoft.Storage/storageAccounts/blobServices/containers/blobs/delete
AssignableScopesPérimètres où le rôle peut être attribué (abonnements, groupes de gestion)./subscriptions/1111-2222-3333

Règle d'or de l'évaluation Azure : Une opération est autorisée si et seulement si elle correspond à au moins un pattern dans Actions ET ne correspond à AUCUN pattern dans NotActions.

3. Gouvernance avec Azure Policy, Resource Locks & Azure Key Vault

Au-delà des droits utilisateurs individuels, l'organisation d'entreprise doit garantir la conformité globale et la protection de ses actifs cryptographiques :

Azure Policy & Resource Locks

  • Azure Policy : moteur de règles déclaratives évaluant les propriétés des ressources créées. Effet Deny pour bloquer une création non conforme (ex: région interdite) ou Audit pour signaler les écarts dans un tableau de bord.
  • Resource Locks (Verrous) :
    - CanNotDelete : lecture et modification autorisées, mais suppression interdite.
    - ReadOnly : consultation uniquement, toute modification ou suppression est rejetée (même par le propriétaire Owner).

Sécurité Azure Key Vault

  • Gestion centralisée : stockage hermétique des clés de chiffrement (HSM FIPS 140-2), mots de passe applicatifs (Secrets) et certificats TLS/SSL.
  • Soft-Delete (Suppression réversible) : les secrets supprimés sont conservés dans une corbeille protégée pendant 7 à 90 jours au lieu d'être détruits immédiatement.
  • Purge Protection : empêche même l'administrateur de forcer la purge définitive avant l'expiration de la période de rétention (défense absolue contre les rançongiciels).

Exercice 1 — Évaluateur de permissions Azure RBAC

Étude de cas Niveau 1 — Acquisition

Objectif : Analyser une définition de rôle Azure RBAC et déterminer si des opérations administratives sont autorisées ou refusées.

Azure RBAC (Role-Based Access Control) applique une logique d'autorisation stricte : une action est autorisée si elle correspond à au moins une directive dans Actions (supportant le caractère générique *) et ne correspond à aucune directive dans NotActions.

Rôles Azure prédéfinis pris en charge :
- Owner :
- Actions : ["*"]
- NotActions : []
- Contributor :
- Actions : ["*"]
- NotActions : ["Microsoft.Authorization/*/Delete", "Microsoft.Authorization/*/Write", "Microsoft.Resources/subscriptions/resourceGroups/delete"]
- Reader :
- Actions : ["*/read"]
- NotActions : []
- VM_Operator :
- Actions : ["Microsoft.Compute/virtualMachines/start/*", "Microsoft.Compute/virtualMachines/restart/*", "Microsoft.Compute/virtualMachines/read"]
- NotActions : ["Microsoft.Compute/virtualMachines/delete"]

Format d'entrée :
La première ligne définit le rôle assigné :
ROLE <nom_du_role>
Les lignes suivantes soumettent des opérations ARM à tester :
CHECK_ACTION <action_path>

Pour chaque action :
- Si l'action est autorisée : ACTION <action_path> -> ALLOWED
- Si l'action est refusée : ACTION <action_path> -> DENIED
- Si le rôle est inconnu au départ, afficher : ROLE_ERROR: Unknown role '<nom_du_role>' et arrêter.

Cas d’exemple
ROLE VM_Operator
CHECK_ACTION Microsoft.Compute/virtualMachines/restart/action
CHECK_ACTION Microsoft.Compute/virtualMachines/delete
Résolution attendue
ACTION Microsoft.Compute/virtualMachines/restart/action -> ALLOWED
ACTION Microsoft.Compute/virtualMachines/delete -> DENIED

Le rôle VM_Operator autorise le redémarrage mais refuse la suppression.

Deux indices, rédigés en mots
  1. Le module Python `fnmatch` permet d'évaluer simplement les règles avec wildcards `*`.
  2. Penser à convertir en minuscules pour garantir l'insensibilité à la casse.

Exercice 2 — Auditeur de conformité Azure Policy

Étude de cas Niveau 2 — Application

Objectif : Auditer un ensemble de ressources Cloud Azure contre des règles de gouvernance déclaratives et détecter les non-conformités.

Azure Policy permet d'imposer des normes de gouvernance organisationnelle au niveau des abonnements et groupes de ressources.

Règles de conformité définies pour l'organisation :
1. allowedLocations : la localisation géographique (location) doit obligatoirement être l'une des suivantes : ["westeurope", "northeurope", "francecentral"].
Violation : DENY: Invalid location '<loc>'
2. requireTags : la ressource doit obligatoirement inclure les deux tags Environment et CostCenter.
Pour chaque tag manquant : AUDIT: Missing required tag '<nom_tag>'
3. disallowedSKUs : les SKUs surdimensionnées ou hors catalogue ne sont pas autorisées : ["Standard_M128ms", "Standard_G5"].
Violation : DENY: Disallowed SKU '<sku>'

Format d'entrée : chaque ligne déclare une ressource sous la forme :
RESOURCE id=<id> type=<type> location=<loc> sku=<sku> tags=<k1:v1,k2:v2> (si aucun tag : tags=none).

Format de sortie attendu pour chaque ressource :
- Si aucune violation :
AUDIT id=<id> STATUS=COMPLIANT
- Si des violations existent :
AUDIT id=<id> STATUS=NON_COMPLIANT issues=[<issue1>; <issue2>] (dans l'ordre de détection : location, SKU, puis tags manquants).

Cas d’exemple
RESOURCE id=vm-web-01 type=Microsoft.Compute/virtualMachines location=westeurope sku=Standard_D4s_v5 tags=Environment:prod,CostCenter:IT-401
Résolution attendue
AUDIT id=vm-web-01 STATUS=COMPLIANT

Ressource entièrement conforme aux règles de localisation, SKU et tags.

Deux indices, rédigés en mots
  1. Extraire chaque champ clé=valeur de la ligne de déclaration.
  2. Construire la liste des anomalies dans l'ordre prescrit avant d'émettre le diagnostic.

Exercice 3 — Analyseur de sécurité Azure Key Vault & Expiration de secrets

Étude de cas Niveau 3 — Raisonnement

Objectif : Auditer les paramètres de sécurité d’un coffre-fort Azure Key Vault et évaluer l’état d’expiration de ses secrets et certificats.

Azure Key Vault centralise la gestion des clés cryptographiques, secrets et certificats. La sécurisation du coffre exige l'activation de la suppression réversible (Soft-Delete) et de la protection contre la purge (Purge Protection).

Format d'entrée :
Ligne 1 : Configuration du coffre :
VAULT name=<nom> soft_delete=<enabled|disabled> purge_protection=<enabled|disabled> auth_mode=<rbac|access_policies> current_day=<int>
Lignes suivantes : Déclaration des secrets :
SECRET name=<nom> expires_at=<int> (si pas de date d'expiration : expires_at=0).

Règles d'audit du coffre (VAULT) :
- Si soft_delete != enabled : relever CRITICAL: Soft-delete disabled
- Si purge_protection != enabled : relever WARNING: Purge protection disabled
- Mode d'autorisation : afficher AUTH=<auth_mode.upper()>
Afficher :
VAULT_SECURITY name=<nom> AUTH=<AUTH> ISSUES=[<issues>] (ou ISSUES=[NONE] si aucune anomalie).

Règles d'audit des secrets (SECRET) :
- Si expires_at == 0 : SECRET <nom> -> STATUS=NO_EXPIRY_RISK
- Si expires_at <= current_day : SECRET <nom> -> STATUS=EXPIRED
- Si 0 < (expires_at - current_day) <= 30 : SECRET <nom> -> STATUS=EXPIRING_SOON (days_left=<N>)
- Sinon : SECRET <nom> -> STATUS=VALID (days_left=<N>)

Cas d’exemple
VAULT name=kv-prod-we soft_delete=enabled purge_protection=enabled auth_mode=rbac current_day=100
SECRET name=db-password expires_at=125
SECRET name=api-key expires_at=0
Résolution attendue
VAULT_SECURITY name=kv-prod-we AUTH=RBAC ISSUES=[NONE]
SECRET db-password -> STATUS=EXPIRING_SOON (days_left=25)
SECRET api-key -> STATUS=NO_EXPIRY_RISK

Coffre sécurisé, secret expirant dans 25 jours et secret sans date d'expiration relevé.

Deux indices, rédigés en mots
  1. Parser la ligne VAULT pour récupérer current_day et les indicateurs de sécurité.
  2. Comparer expires_at à current_day pour chaque secret selon les 4 cas prescrits.

5. QCM — niveau examen

Quel est l'avantage principal d'utiliser une Managed Identity (Identité Managée) pour une machine virtuelle Azure accédant à une base de données ?

Une Managed Identity permet à la VM de demander un jeton d'accès Entra ID directement à la plateforme Azure locale sans qu'aucun secret ni mot de passe ne soit inscrit dans le code applicatif.

Dans une définition de rôle Azure RBAC, comment s'articulent les directives Actions et NotActions ?

Dans Azure RBAC, une opération est validée si elle correspond à au moins un élément d'Actions et ne correspond à AUCUN élément de NotActions (soustraction stricte de privilèges).

Quel rôle prédéfini (Built-in Role) permet de créer et modifier toutes les ressources Azure sans pouvoir gérer les attributions de droits RBAC à d'autres utilisateurs ?

Le rôle Contributor possède Actions: ["*"] avec NotActions excluant les modifications d'autorisations RBAC (Microsoft.Authorization/*).

Quel effet Azure Policy devez-vous employer pour empêcher immédiatement le déploiement d'une machine virtuelle si sa localisation n'est pas dans la liste autorisée ?

L'effet Deny bloque la requête de déploiement au niveau d'ARM et retourne un message d'erreur explicite à l'utilisateur avant même que la ressource ne soit créée.

Quel verrou de ressource (Resource Lock) permet aux utilisateurs de lire et modifier les données d'une ressource mais interdit rigoureusement sa suppression ?

Le verrou CanNotDelete protège la ressource contre toute suppression accidentelle tout en autorisant les modifications de configuration et les mises à jour.

Que se passe-t-il si un utilisateur tente de modifier la configuration d'une ressource protégée par un verrou ReadOnly ?

Un verrou ReadOnly équivaut à restreindre l'accès à des droits de pure lecture (Reader) pour tous les utilisateurs, interdisant toute modification ou suppression.

Dans Azure Key Vault, quel est le rôle de la fonctionnalité Soft-Delete ?

Soft-Delete empêche la perte définitive immédiate en plaçant les objets supprimés dans une corbeille protégée pendant une durée de 7 à 90 jours (par défaut 90 jours).

Quelle mesure de sécurité Key Vault empêche un attaquant disposant des droits administrateurs de purger immédiatement un secret placé en Soft-Delete ?

Purge Protection verrouille l'objet en corbeille jusqu'à la fin de la période de rétention Soft-Delete, empêchant toute destruction prématurée même par un compte administrateur.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Attribuer le rôle Contributor à une équipe de développement au niveau de l'abonnement complet au lieu de restreindre les droits à leur Resource Group de dev/test.
  • Confondre Azure RBAC (qui gère l'autorisation des utilisateurs sur ARM) et Azure Policy (qui contrôle la configuration et les propriétés des ressources).
  • Oublier qu'un verrou de ressource ReadOnly empêche également le démarrage et l'arrêt d'une machine virtuelle car cette action met à jour le statut dans ARM.
  • Désactiver la Purge Protection sur un Azure Key Vault de production : un compte administrateur compromis pourrait détruire irréversiblement les clés de chiffrement de l'entreprise.

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Remplacement des comptes nominatifs par des Managed Identities : activer une Managed Identity System-Assigned sur chaque serveur ou conteneur pour éliminer définitivement les clés d'accès en dur dans le code.
  2. Définition des attributions RBAC au périmètre le plus restreint : n'assigner jamais de droits au niveau de l'abonnement quand un groupe de ressources suffit, et préférer des rôles d'exploitation dédiés (ex. Virtual Machine User Login).
  3. Déploiement d'Azure Policy pour la gouvernance territoriale et les tags : créer une initiative de politiques imposant la localisation westeurope/francecentral et la présence obligatoire des tags CostCenter et Environment.
  4. Chiffrement et verrouillage des ressources de production : placer un verrou CanNotDelete sur les passerelles réseau et bases de données, et centraliser tous les mots de passe de production dans un Key Vault avec Purge Protection activée.

8. Révision active

Résumé essentiel
  • Microsoft Entra ID centralise les identités Cloud et offre les Managed Identities pour une authentification automatique sans mot de passe.
  • Azure RBAC applique le contrôle d'accès granulaire combinant un Principal, une Définition de rôle et un Périmètre (Scope).
  • La structure d'un rôle RBAC repose sur Actions (autorisations) et NotActions (exclusions soustractives), évaluées avec wildcards.
  • Azure Policy impose des contraintes de conformité aux ressources (ex: restriction géographique, tags obligatoires) avec les effets Deny et Audit.
  • Azure Key Vault protège les secrets contre les rançongiciels grâce aux mécanismes combinés de Soft-Delete et Purge Protection.

Checklist de maîtrise

  • Savez-vous différencier une Managed Identity System-Assigned d'une identité User-Assigned ?
  • Pouvez-vous expliquer pourquoi une action présente dans NotActions est systématiquement refusée même si Actions contient * ?
  • Connaissez-vous la différence entre un verrou CanNotDelete et un verrou ReadOnly ?
  • Savez-vous rédiger une condition Azure Policy pour bloquer la création de machines hors des régions autorisées ?
  • Comprenez-vous le rôle de la Purge Protection face aux scénarios d'attaque par rançongiciel ?

Les 8 notions à connaître absolument

  1. Managed Identity : Identité gérée automatiquement par Azure dans Entra ID pour une ressource Cloud, permettant de s'authentifier auprès d'autres services sans stocker de secret.
  2. RBAC (Role-Based Access Control) : Modèle d'autorisation fondé sur des rôles découpés en Actions et NotActions assignés à un niveau de scope précis.
  3. Scope (Périmètre) : Niveau hiérarchique auquel s'applique une attribution de rôle (Management Group, Subscription, Resource Group ou Ressource individuelle).
  4. Azure Policy : Service de gouvernance évaluant la conformité des propriétés des ressources par rapport à des règles d'entreprise déclaratives.
  5. Purge Protection : Fonctionnalité de sécurité imposant la rétention incompressible des objets supprimés dans Key Vault, interdisant toute destruction définitive prématurée.
  6. Microsoft Entra ID centralise les identités Cloud et offre les Managed Identities pour une authentification automatique sans mot de passe.
  7. Azure RBAC applique le contrôle d'accès granulaire combinant un Principal, une Définition de rôle et un Périmètre (Scope).
  8. La structure d'un rôle RBAC repose sur Actions (autorisations) et NotActions (exclusions soustractives), évaluées avec wildcards.
