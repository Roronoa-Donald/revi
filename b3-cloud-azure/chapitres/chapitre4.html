Chapitre 4 — Réseau Virtuel Azure (Azure Virtual Network - VNet & Sécurité)

Module 4 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans une entreprise déployant ses services applicatifs et ses bases de données sur Azure, exposer directement les machines virtuelles à Internet via des adresses IP publiques constitue un risque de sécurité critique. En tant qu'ingénieur réseau Cloud B3, vous devez concevoir un plan d'adressage IP rigoureux en tenant compte des 5 adresses réservées par Azure dans chaque sous-réseau, isoler les flux entrants et sortants grâce aux Network Security Groups (NSG), mettre en place une topologie sécurisée en étoile (Hub-and-Spoke) avec VNet Peering sans chevauchement CIDR, et sécuriser l'administration RDP/SSH grâce à Azure Bastion.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. concevoir et découper un réseau virtuel Azure (VNet) en sous-réseaux logiques étanches ;
  2. maîtriser le rôle précis des 5 adresses IP réservées par Azure dans chaque sous-réseau et calculer les plages utilisables ;
  3. configurer des Network Security Groups (NSG) et évaluer l'ordre de priorité des règles personnalisées et règles par défaut ;
  4. sécuriser l'administration des serveurs Linux/Windows sans adresse IP publique avec Azure Bastion ;
  5. interconnecter des réseaux virtuels via VNet Peering (local et global) et valider la non-collision des plages CIDR ;
  6. développer en Python 3 des calculateurs de sous-réseaux Azure, des moteurs d'évaluation de règles NSG et des validateurs de peering.

1. Fondations SDN : Réseaux Virtuels Azure VNet et Adressage Réservé

Un Azure Virtual Network (VNet) est une représentation logique et isolée de votre réseau privé dans le Cloud. Il permet aux machines virtuelles, conteneurs et bases de données de communiquer de manière sécurisée entre elles et avec l'extérieur :

Structure d'un VNet & Sous-réseaux

  • Espace d'adressage CIDR : défini au niveau du VNet (ex: 10.0.0.0/16 pour 65 536 adresses) selon les plages privées RFC 1918.
  • Segmentation en sous-réseaux : division logique par niveau applicatif (ex: snet-web en 10.0.1.0/24, snet-db en 10.0.2.0/24).
  • Sous-réseaux dédiés Azure : certains services exigent des noms de sous-réseaux réservés stricts (ex: GatewaySubnet pour les passerelles VPN, AzureBastionSubnet pour Bastion, AzureFirewallSubnet pour le pare-feu).

Les 5 Adresses IP Réservées par Azure

  • .0 : Network ID (adresse réseau).
  • .1 : Default Gateway (passerelle par défaut interne au VNet gérée par Azure).
  • .2 : DNS Resolver Primaire (résolveur DNS Azure routé en interne).
  • .3 : DNS Resolver Secondaire (redondance et allocation interne Azure).
  • .<dernière> (ex: .255) : Broadcast (adresse de diffusion non utilisée mais réservée).
  • Conséquence : un sous-réseau en /24 (256 adresses théoriques) n'offre que 251 adresses IP exploitables pour les VMs (de .4 à .254).

2. Sécurité Périmétrique : Network Security Groups (NSG) & Azure Bastion

Le contrôle des flux réseau à l'intérieur du VNet s'opère au niveau de chaque sous-réseau ou interface réseau (NIC) par les Network Security Groups :

3. Interconnexion Réseau d'Entreprise : VNet Peering & Topologie Hub-and-Spoke

Pour interconnecter plusieurs réseaux virtuels au sein d'une même région (VNet Peering local) ou entre régions différentes (Global VNet Peering) :

Principes du VNet Peering

  • Performances natives : le trafic transite directement par le backbone privé de Microsoft sans traverser l'Internet public, offrant la même latence qu'au sein d'un même réseau.
  • Règle de non-chevauchement : deux VNets en peering ne peuvent posséder aucune plage d'adresses IP qui se chevauche (Overlapping CIDRs strictement interdit).
  • Non-transitif par défaut : si le VNet A est appairé au VNet B, et le VNet B au VNet C, le VNet A ne peut pas communiquer avec le VNet C sans passer par une passerelle ou un routeur intermédiaire.

Architecture Hub-and-Spoke

  • VNet Hub (Central) : héberge les services partagés (Azure Firewall, passerelle VPN/ExpressRoute connectée au datacenter on-premise, DNS centralisé).
  • VNets Spokes (Périphériques) : hébergent les environnements applicatifs (Spoke-Prod, Spoke-Dev) appairés exclusivement au Hub.
  • Transit de passerelle : les Spokes activent Use Remote Gateways pour utiliser la passerelle VPN du Hub (qui active Allow Gateway Transit) sans dupliquer les coûts de passerelle.

Exercice 1 — Calculateur d'adressage Azure VNet & Adresses IP réservées

Python Niveau 1 — Acquisition

Objectif : Calculer la plage d’adresses IP d’un sous-réseau Azure en déduisant les 5 adresses réservées par le système SDN d’Azure.

Dans chaque sous-réseau (Subnet) d'un VNet Azure, Microsoft réserve systématiquement 5 adresses IP qui ne peuvent pas être assignées aux machines virtuelles ou ressources clientes :
- .0 : Adresse réseau (Network ID)
- .1 : Passerelle par défaut Azure (Default Gateway)
- .2 : Résolveur DNS Azure primaire
- .3 : Résolveur DNS Azure secondaire
- .<dernière> (ex: .255 pour un /24) : Adresse de diffusion (Broadcast)

Ainsi, la première IP assignable est .4 et la dernière est .<dernière - 1>.
Le nombre d'IPs exploitables est donc Total - 5.

Format d'entrée :
SUBNET name=<nom> cidr=<adresse/préfixe>

Format de sortie attendu :
SUBNET <nom>: TOTAL=<total> USABLE=<usable> RESERVED=5 GATEWAY=<gw_ip> DNS1=<dns1_ip> RANGE=<first_usable>-<last_usable>

Entrée du programme
SUBNET name=snet-web cidr=10.0.1.0/24
Sortie attendue
SUBNET snet-web: TOTAL=256 USABLE=251 RESERVED=5 GATEWAY=10.0.1.1 DNS1=10.0.1.2 RANGE=10.0.1.4-10.0.1.254

Sous-réseau /24 classique avec 251 adresses exploitables.

Deux indices, rédigés en mots
  1. Utiliser le module Python `ipaddress.ip_network(cidr, strict=False)`.
  2. L'IP de passerelle est net.network_address + 1, et la première IP assignable est net.network_address + 4.

Exercice 2 — Moteur d'évaluation de règles de sécurité NSG

Python Niveau 2 — Application

Objectif : Évaluer le traitement d’un paquet réseau entrant par un groupe de sécurité réseau (NSG) selon l’ordre de priorité des règles et les règles par défaut Azure.

Un groupe de sécurité réseau (NSG) filtre le trafic entrant et sortant. Les règles sont traitées par ordre croissant de priorité (de 100 à 4096). La première règle correspondant au paquet s'applique immédiatement.

Règles par défaut Azure (INBOUND) automatiques en fin de chaîne :
- Priorité 65000 : AllowVNetInBound, source=VirtualNetwork, port=*, proto=ANY, action=ALLOW
- Priorité 65001 : AllowAzureLoadBalancerInBound, source=AzureLoadBalancer, port=*, proto=ANY, action=ALLOW
- Priorité 65500 : DenyAllInBound, source=*, port=*, proto=ANY, action=DENY

Format d'entrée :
Déclaration de règles personnalisées :
RULE prio=<int> name=<nom> direction=INBOUND source=<SRC> port=<PORT> proto=<TCP|UDP|ANY> action=<ALLOW|DENY>
Puis paquets à évaluer :
TEST_PACKET source=<SRC> port=<PORT> proto=<TCP|UDP>

Critères de correspondance d'un paquet :
- source : matche si la règle a * ou la même valeur exacte.
- port : matche si la règle a * ou le même numéro de port.
- proto : matche si la règle a ANY ou le même protocole exact.

Format de sortie attendu :
PACKET: matched_rule=<name> (prio=<prio>) -> RESULT=<ALLOW|DENY>

Entrée du programme
RULE prio=100 name=Allow-HTTP direction=INBOUND source=Internet port=80 proto=TCP action=ALLOW
RULE prio=200 name=Deny-SSH direction=INBOUND source=* port=22 proto=TCP action=DENY
TEST_PACKET source=Internet port=80 proto=TCP
TEST_PACKET source=Internet port=22 proto=TCP
Sortie attendue
PACKET: matched_rule=Allow-HTTP (prio=100) -> RESULT=ALLOW
PACKET: matched_rule=Deny-SSH (prio=200) -> RESULT=DENY

Le port 80 est autorisé par la règle 100 et SSH 22 est bloqué par la règle 200.

Deux indices, rédigés en mots
  1. Ajouter les 3 règles par défaut Azure dans la liste des règles avec leurs priorités 65000, 65001 et 65500.
  2. Trier l'ensemble des règles par priorité croissante et trouver la première règle correspondante.

Exercice 3 — Validateur de Peering VNet & Topologie Hub-and-Spoke

Python Niveau 3 — Raisonnement

Objectif : Vérifier la validité de liens d’interconnexion (VNet Peering) en détectant les chevauchements de plages CIDR et les incohérences de passerelles de transit.

L'interconnexion de réseaux virtuels par Peering Azure permet une communication privée à haute performance. Toutefois, Azure refuse catégoriquement l'établissement d'un peering si les plages d'adresses IP se chevauchent, ou si la configuration de passerelle est incohérente.

Format d'entrée :
1. Déclaration des VNets :
VNET id=<nom> cidr=<plage_ip>
2. Demande d'établissement de Peering :
PEERING vnet1=<nom1> vnet2=<nom2> allow_gw_transit=<true|false> use_remote_gw=<true|false>

Règles de validation :
- Si l'un des deux VNets n'a pas été déclaré au préalable :
PEERING_ERROR: Unknown VNet in peering <nom1> <-> <nom2>
- Si les plages CIDR des deux réseaux se chevauchent :
PEERING_FAILED: Overlapping CIDR between <nom1> (<cidr1>) and <nom2> (<cidr2>)
- Si allow_gw_transit=true ET use_remote_gw=true simultanément :
PEERING_FAILED: Incompatible gateway flags on peering <nom1> <-> <nom2>
- Si toutes les conditions sont remplies :
PEERING_SUCCESS: <nom1> <-> <nom2> status=CONNECTED gateway_transit=<ENABLED|DISABLED>
(avec ENABLED si au moins l'un des deux flags est à true, sinon DISABLED).

Entrée du programme
VNET id=vnet-hub cidr=10.0.0.0/16
VNET id=vnet-spoke1 cidr=10.1.0.0/16
PEERING vnet1=vnet-hub vnet2=vnet-spoke1 allow_gw_transit=true use_remote_gw=false
Sortie attendue
PEERING_SUCCESS: vnet-hub <-> vnet-spoke1 status=CONNECTED gateway_transit=ENABLED

Peering valide sans chevauchement avec passerelle de transit activée sur le Hub.

Deux indices, rédigés en mots
  1. Utiliser la méthode net1.overlaps(net2) du module `ipaddress`.
  2. Vérifier que allow_gw_transit et use_remote_gw ne sont pas tous les deux actifs en même temps.

5. QCM — niveau examen

Combien d'adresses IP utilisables pour des machines virtuelles sont disponibles dans un sous-réseau Azure de masque /24 (256 adresses théoriques) ?

Azure réserve systématiquement 5 adresses IP dans chaque sous-réseau (.0, .1, .2, .3 et .255 en /24), ce qui laisse 256 - 5 = 251 adresses IP exploitables.

À quoi sert l'adresse IP finissant par .1 dans chaque sous-réseau Azure ?

L'adresse .1 est réservée par Azure pour faire office de Default Gateway (passerelle de routage par défaut) pour toutes les ressources du sous-réseau.

Comment s'effectue l'évaluation de deux règles contradictoires au sein d'un même Network Security Group (NSG) ?

Les règles NSG sont traitées par ordre strictement croissant de priorité (100 à 4096). La première règle qui correspond aux critères du paquet s'applique et arrête le processus d'évaluation.

Quelle est la priorité de la règle par défaut Inbound d'un NSG qui bloque tout le trafic entrant non explicitement autorisé (DenyAllInBound) ?

La règle par défaut DenyAllInBound possède la priorité 65500, garantissant qu'elle s'applique en toute fin de chaîne si aucune règle personnalisée précédente n'a matché.

Pourquoi Azure Bastion est-il considéré comme une pratique d'excellence pour l'administration de machines virtuelles ?

Azure Bastion établit une session RDP/SSH sécurisée au travers d'une connexion web chiffrée (port 443), éliminant l'exposition des ports 22 et 3389 sur Internet et évitant d'assigner des IPs publiques aux serveurs.

Quelle condition technique stricte est obligatoire pour pouvoir établir un VNet Peering entre deux réseaux virtuels Azure ?

Le peering entre deux réseaux virtuels est strictement impossible si leurs plages d'adresses IP (espaces d'adressage CIDR) se chevauchent, afin d'éviter toute collision de routage.

Dans une architecture Hub-and-Spoke, quel paramètre de peering le VNet Spoke doit-il activer pour acheminer son trafic vers le réseau d'entreprise via la passerelle du Hub ?

Le VNet Spoke active Use Remote Gateways pour transférer ses paquets via la passerelle VPN/ExpressRoute du Hub (sur lequel est activé Allow Gateway Transit).

Quelle est la portée géographique du service Global VNet Peering sous Azure ?

Global VNet Peering permet d'interconnecter des VNets situés dans des régions Azure différentes (ex: France Central et East US) avec un chiffrement matériel natif sur le réseau privé Microsoft.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Oublier les 5 adresses IP réservées lors du dimensionnement d'un petit sous-réseau en /29 (8 adresses théoriques mais seulement 3 adresses utilisables !).
  • Attribuer des priorités trop proches (ex: 100, 101, 102) dans les règles NSG, empêchant l'insertion future de nouvelles règles intermédiaires (préférer 100, 200, 300).
  • Tenter d'apparier en VNet Peering deux réseaux virtuels partageant un même espace d'adressage CIDR : ARM rejette immédiatement la création.
  • Croire que le peering est transitif par défaut : si A est appairé à B et B à C, A ne peut pas communiquer avec C sans passer par une passerelle de routage (NVA/Firewall).

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Élaboration du plan d'adressage IP sans chevauchement : définir des plages CIDR RFC 1918 distinctes pour chaque VNet et dimensionner les sous-réseaux en retranchant les 5 adresses réservées par Azure.
  2. Déploiement des sous-réseaux système obligatoires : allouer GatewaySubnet (/27 minimum) pour les passerelles VPN et AzureBastionSubnet (/26 minimum) pour l'administration sans IP publique.
  3. Configuration de la politique de filtrage NSG par couches : appliquer des règles NSG restrictives par défaut et n'ouvrir que les ports strictement nécessaires avec des priorités basses (100-300).
  4. Établissement des peerings bidirectionnels avec transit de passerelle : créer les liaisons de peering entre le Hub et les Spokes en autorisant le transit de passerelle pour mutualiser l'accès au réseau d'entreprise.

8. Révision active

Résumé essentiel
  • Un Azure VNet isole un réseau virtuel privé ; Azure réserve systématiquement 5 adresses IP (.0, .1, .2, .3, .255) dans chaque sous-réseau.
  • Les sous-réseaux en /24 offrent exactement 251 adresses IP exploitables pour les machines virtuelles.
  • Les Network Security Groups (NSG) filtrent le trafic selon la priorité des règles (100 à 4096), avec les règles par défaut 65000 (Allow VNet) et 65500 (Deny All).
  • Azure Bastion fournit un accès d'administration RDP/SSH sécurisé par navigateur web sans nécessiter d'adresse IP publique sur les serveurs.
  • Le VNet Peering interconnecte des réseaux virtuels privés via le backbone Microsoft sans transiter par Internet, sous condition de non-chevauchement des plages CIDR.

Checklist de maîtrise

  • Savez-vous énumérer les 5 adresses IP réservées par Azure dans n'importe quel sous-réseau ?
  • Combien d'adresses exploitables compte un sous-réseau /26 (64 adresses) sous Azure ?
  • Comprenez-vous pourquoi une règle NSG de priorité 100 prévaut sur une règle de priorité 500 ?
  • Savez-vous pourquoi Azure Bastion élimine le risque d'attaques par force brute sur le port 22 ou 3389 ?
  • Pouvez-vous expliquer pourquoi deux réseaux ayant le même CIDR (ex: 10.0.0.0/16) ne peuvent pas être appairés en VNet Peering ?

Les 8 notions à connaître absolument

  1. Azure Virtual Network (VNet) : Réseau virtuel privé isolé sous Azure permettant la communication sécurisée entre ressources Cloud et sur site.
  2. Adresses IP réservées Azure : Les 5 adresses IP (.0 réseau, .1 passerelle, .2 DNS primaire, .3 DNS secondaire, .dernière broadcast) confisquées par le SDN Azure dans chaque subnet.
  3. Network Security Group (NSG) : Pare-feu de niveau 4 filtrant les paquets réseau par liste de contrôle d'accès (ACL) ordonnée par priorité.
  4. Azure Bastion : Passerelle PaaS managée permettant d'administrer des machines virtuelles en RDP/SSH via le portail web (HTTPS) sans IP publique.
  5. VNet Peering : Interconnexion directe à haute vitesse et faible latence entre deux réseaux virtuels via le réseau fédérateur privé de Microsoft.
