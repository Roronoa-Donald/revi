Chapitre 4 — Réseau Virtuel Azure (Azure Virtual Network - VNet & Sécurité)

Mise en situation

Dans une entreprise déployant ses services applicatifs et ses bases de données sur Azure, exposer directement les machines virtuelles à Internet via des adresses IP publiques constitue un risque de sécurité critique. En tant qu'ingénieur réseau Cloud B3, vous devez concevoir un plan d'adressage IP rigoureux en tenant compte des 5 adresses réservées par Azure dans chaque sous-réseau, isoler les flux entrants et sortants grâce aux Network Security Groups (NSG), mettre en place une topologie sécurisée en étoile (Hub-and-Spoke) avec VNet Peering sans chevauchement CIDR, et sécuriser l'administration RDP/SSH grâce à Azure Bastion.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. concevoir et découper un réseau virtuel Azure (VNet) en sous-réseaux logiques étanches ;
  2. maîtriser le rôle précis des 5 adresses IP réservées par Azure dans chaque sous-réseau et calculer les plages utilisables ;
  3. configurer des Network Security Groups (NSG) et évaluer l'ordre de priorité des règles personnalisées et règles par défaut ;
  4. sécuriser l'administration des serveurs Linux/Windows sans adresse IP publique avec Azure Bastion ;
  5. interconnecter des réseaux virtuels via VNet Peering (local et global) et valider la non-collision des plages CIDR ;
  6. analyser et résoudre méthodologiquement des calculateurs de sous-réseaux Azure, des moteurs d'évaluation de règles NSG et des validateurs de peering.

1. Fondations SDN : Réseaux Virtuels Azure VNet et Adressage Réservé

Un Azure Virtual Network (VNet) est une représentation logique et isolée de votre réseau privé dans le Cloud. Il permet aux machines virtuelles, conteneurs et bases de données de communiquer de manière sécurisée entre elles et avec l'extérieur :

Structure d'un VNet & Sous-réseaux

  • Espace d'adressage CIDR : défini au niveau du VNet (ex: 10.0.0.0/16 pour 65 536 adresses) selon les plages privées RFC 1918.
  • Segmentation en sous-réseaux : division logique par niveau applicatif (ex: snet-web en 10.0.1.0/24, snet-db en 10.0.2.0/24).
  • Sous-réseaux dédiés Azure : certains services exigent des noms de sous-réseaux réservés stricts (ex: GatewaySubnet pour les passerelles VPN, AzureBastionSubnet pour Bastion, AzureFirewallSubnet pour le pare-feu).

Les 5 Adresses IP Réservées par Azure

  • +0 : Network ID (adresse réseau).
  • +1 : Default Gateway (passerelle par défaut gérée par Azure).
  • +2 et +3 : adresses réservées pour la correspondance des adresses Azure DNS dans l'espace du VNet, et non résolveurs primaire et secondaire.
  • Dernière adresse : adresse de diffusion réservée ; Azure ne prend pas en charge le broadcast dans le VNet.
  • Ces décalages partent de l'adresse réseau : pour 10.0.5.16/28, les adresses de correspondance sont 10.0.5.18 et 10.0.5.19. Un /24 offre 256 - 5 = 251 adresses exploitables.
  • Lorsque le DNS fourni par Azure est utilisé, son résolveur est accessible à 168.63.129.16. Un VNet ou une interface peut aussi utiliser un DNS personnalisé ; ne remplacez pas sa configuration par cette adresse. Voir la FAQ réseau Microsoft.

2. Sécurité Périmétrique : Network Security Groups (NSG) & Azure Bastion

Le contrôle des flux réseau à l'intérieur du VNet s'opère au niveau de chaque sous-réseau ou interface réseau (NIC) par les Network Security Groups :

Propriété de la Règle NSGValeurs PossiblesRôle et Fonction
Priority (Priorité)Nombre entier de 100 à 4096Détermine l'ordre d'évaluation. Le nombre le plus faible est évalué en premier. Dès qu'une règle correspond au paquet, son action s'applique immédiatement.
Source / DestinationIP, CIDR, Tag de service (Internet, VirtualNetwork)Délimite l'origine ou la cible du paquet. Le wildcard * correspond à toute source.
Port & ProtocoleNuméro de port (ex: 443, 22), TCP, UDP, ANYSpécifie le port de destination et le protocole de couche 4.
ActionAllow ou DenyAutorise ou rejette le paquet réseau.
Administration Sécurisée avec Azure Bastion

Traditionnellement, l'administration de serveurs distants s'effectuait en attribuant une adresse IP publique à la VM et en ouvrant les ports RDP (3389) ou SSH (22) sur Internet, exposant les machines à des attaques de force brute massives. Azure Bastion résout ce risque :

  • Service PaaS managé déployé dans son sous-réseau dédié AzureBastionSubnet.
  • Permet aux administrateurs de se connecter en RDP/SSH directement depuis le portail Azure dans leur navigateur web via TLS/HTTPS sécurisé (port 443).
  • Les machines virtuelles cibles n'ont besoin d'aucune adresse IP publique et leurs ports 22/3389 restent totalement fermés à Internet.

3. Interconnexion Réseau d'Entreprise : VNet Peering & Topologie Hub-and-Spoke

Pour interconnecter plusieurs réseaux virtuels au sein d'une même région (VNet Peering local) ou entre régions différentes (Global VNet Peering) :

Principes du VNet Peering

  • Performances natives : le trafic transite directement par le backbone privé de Microsoft sans traverser l'Internet public, offrant la même latence qu'au sein d'un même réseau.
  • Règle de non-chevauchement : deux VNets en peering ne peuvent posséder aucune plage d'adresses IP qui se chevauche (Overlapping CIDRs strictement interdit).
  • Non-transitif par défaut : si le VNet A est appairé au VNet B, et le VNet B au VNet C, le VNet A ne peut pas communiquer avec le VNet C sans passer par une passerelle ou un routeur intermédiaire.

Architecture Hub-and-Spoke

  • VNet Hub (Central) : héberge les services partagés (Azure Firewall, passerelle VPN/ExpressRoute connectée au datacenter on-premise, DNS centralisé).
  • VNets Spokes (Périphériques) : hébergent les environnements applicatifs (Spoke-Prod, Spoke-Dev) appairés exclusivement au Hub.
  • Transit de passerelle : les Spokes activent Use Remote Gateways pour utiliser la passerelle VPN du Hub (qui active Allow Gateway Transit) sans dupliquer les coûts de passerelle.

Exercice 1 — Calculateur d'adressage Azure VNet & Adresses IP réservées

Étude de cas Formative Niveau 1 — Acquisition

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Calculer la plage d’adresses IP d’un sous-réseau Azure en déduisant les 5 adresses réservées par le système SDN d’Azure.

Dans chaque sous-réseau IPv4 Azure, les quatre premières adresses et la dernière sont réservées : 5 adresses IP ne peuvent pas être assignées aux ressources clientes. Les décalages partent de l'adresse réseau du sous-réseau :
- +0 : adresse réseau (Network ID)
- +1 : passerelle par défaut Azure
- +2 et +3 : adresses réservées pour la correspondance Azure DNS, et non deux résolveurs
- dernière adresse : réservée ; le broadcast n'est pas pris en charge dans le VNet

Le DNS fourni par Azure utilise 168.63.129.16 ; un DNS personnalisé configuré sur le VNet ou l'interface peut être conservé.
La première IP assignable est l'adresse réseau + 4, la dernière précède l'adresse finale, et le nombre d'IPs exploitables vaut Total - 5.

Format d'entrée :
SUBNET name=<nom> cidr=<adresse/préfixe>

Format de sortie attendu :
SUBNET <nom>: TOTAL=<total> USABLE=<usable> RESERVED=5 GATEWAY=<gw_ip> DNS_MAP_1=<adresse_reseau_plus_2> DNS_MAP_2=<adresse_reseau_plus_3> RANGE=<first_usable>-<last_usable>

Cas d’exemple
SUBNET name=snet-web cidr=10.0.1.0/24
Trois indices, rédigés en mots
  1. Déterminez d’abord l’adresse réseau du CIDR, puis calculez les décalages à partir de cette adresse.
  2. La passerelle est à réseau + 1, les correspondances DNS à + 2 et + 3, et la première adresse assignable à + 4.
  3. Déterminez réseau, broadcast et passerelle Azure (.1), puis soustrayez les 5 IP réservées par Azure (.0, .1, .2, .3 et dernière) pour compter les hôtes utilisables.

Exercice 2 — Le filtrage du portail des Ateliers Norvian

Étude de cas Formative Niveau 2 — Application

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Évaluer des règles de sécurité d'un groupe de sécurité réseau (NSG) selon leur priorité et connaître les règles par défaut.

Énoncé. Ateliers Norvian, PME industrielle, publie son portail fournisseur sur une machine virtuelle protégée par un groupe de sécurité réseau (NSG). Rappel du cours : les règles sont évaluées de la priorité la plus basse à la plus haute (la règle de priorité 100 passe avant celle de priorité 200) ; la première règle qui correspond au paquet détermine l'action.

Règles personnalisées du NSG (trafic entrant) :

PrioritéNomPortSourceAction
100Allow-HTTP80InternetAutoriser
110Allow-HTTPS443InternetAutoriser
200Allow-SSH-Bastion22AzureBastionSubnetAutoriser
1000Deny-All-InboundtousquelconqueRefuser

Le NSG conserve aussi ses règles par défaut : AllowVnetInBound (priorité 65000), AllowAzureLoadBalancerInBound (65001) et DenyAllInbound (65500).

  1. Un paquet TCP arrive d'Internet sur le port 443 : quelle règle s'applique ?
  2. Un paquet TCP arrive d'Internet sur le port 3389 (RDP) : quelle action le NSG applique-t-il ?
  3. Un paquet TCP arrive du sous-réseau AzureBastionSubnet sur le port 22 : est-il autorisé ou refusé ?
  4. Deux règles correspondent à un même paquet, l'une de priorité 100, l'autre de priorité 200 : laquelle est évaluée en premier ?
  5. Quel numéro de priorité porte la règle par défaut DenyAllInbound ?
Cas d’exemple
L'imprimerie Rivoire filtre la machine virtuelle de son site avec un NSG :
- priorité 150 : Allow-HTTPS, port 443, Internet, Autoriser ;
- priorité 400 : Deny-All-Inbound, tous ports, quelconque, Refuser ;
- règles par défaut : AllowVnetInBound (65000), DenyAllInbound (65500).

1) Un paquet Internet sur 443 correspond à Allow-HTTPS (priorité 150) : autorisé.
2) Un paquet Internet sur le port 8080 atteint Deny-All-Inbound (400) : refusé.
3) La priorité 150 est évaluée avant la priorité 400.
4) La règle par défaut DenyAllInbound porte le numéro 65500.
Trois indices, rédigés en mots
  1. Pour chaque paquet, parcourez les règles par priorité croissante et arrêtez-vous à la première qui correspond au port et à la source.
  2. La priorité est un numéro : plus il est petit, plus la règle est évaluée tôt ; 100 passe avant 200, qui passe avant 1000.
  3. 1. Port 443 : cherchez la règle dédiée. 2. Aucune règle d'autorisation ne couvre le port 3389 : la règle de refus générale s'applique. 3. La règle 200 couvre le port 22 depuis le sous-réseau Bastion. 4. Comparez les deux numéros. 5. Relisez les trois règles par défaut.

Exercice 3 — La topologie hub-and-spoke du groupe Palissy

Étude de cas Formative Niveau 3 — Raisonnement

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Concevoir un maillage de peerings entre réseaux virtuels Azure (hub-and-spoke) et vérifier la compatibilité des espaces d'adressage.

Énoncé. Le groupe Palissy, distributeur disposant de quatre sites, déploie une topologie hub-and-spoke :

Réseau virtuelRôleEspace d'adressage
vnet-hubhub (héberge le pare-feu)10.10.0.0/16
vnet-entrepot-estspoke10.20.0.0/16
vnet-entrepot-ouestspoke10.30.0.0/16
vnet-bureauxspoke10.40.0.0/16

Rappels du cours : un peering entre deux réseaux virtuels exige deux liaisons, une configurée dans chaque sens ; un peering est impossible entre deux réseaux dont les espaces d'adressage se chevauchent ; dans une topologie hub-and-spoke, le trafic entre deux spokes traverse le hub, qui le route.

  1. Combien de peerings (liaisons hub-spoke) la topologie établit-elle entre le hub et les trois spokes ?
  2. Chaque peering exige une liaison par sens : combien de liaisons faut-il configurer au total ?
  3. Les espaces 10.10.0.0/16 et 10.20.0.0/16 se chevauchent-ils ?
  4. Par quel réseau virtuel transite le trafic entre vnet-entrepot-est et vnet-entrepot-ouest ?
  5. Un nouveau site souhaite rejoindre la topologie avec l'espace 10.20.0.0/16 : le peering est-il possible ?
Cas d’exemple
Le réseau de cliniques Axelys construit un hub vnet-hub-axelys (10.50.0.0/16) relié à
deux spokes : vnet-imagerie (10.60.0.0/16) et vnet-admin (10.70.0.0/16).

1) La topologie compte 2 peerings hub-spoke.
2) Il faut 2 liaisons par peering, soit 4 liaisons au total.
3) 10.50.0.0/16 et 10.60.0.0/16 ne se chevauchent pas.
4) Le trafic imagerie-admin transite par le hub.
5) Un spoke supplémentaire en 10.60.0.0/16 serait refusé : chevauchement avec vnet-imagerie.
Trois indices, rédigés en mots
  1. Comptez les paires hub-spoke : un peering relie le hub à un spoke, pas les spokes entre eux.
  2. Chaque paire demande deux liaisons : une déclarée depuis chaque réseau virtuel.
  3. 1. Un peering par spoke. 2. Multipliez par deux. 3. Comparez les blocs /16 : le deuxième octet suffit à les distinguer. 4. En hub-and-spoke, les spokes ne se parlent pas directement. 5. Vérifiez si la plage demandée existe déjà dans la topologie.

5. QCM — niveau examen

Combien d'adresses IP utilisables pour des machines virtuelles sont disponibles dans un sous-réseau Azure de masque /24 (256 adresses théoriques) ?

Azure réserve systématiquement 5 adresses IP dans chaque sous-réseau (.0, .1, .2, .3 et .255 en /24), ce qui laisse 256 - 5 = 251 adresses IP exploitables.

À quoi servent les adresses réservées aux décalages +2 et +3 dans un sous-réseau Azure ?

Ces deux adresses servent à la correspondance Azure DNS ; elles ne désignent pas deux résolveurs. Le DNS fourni par Azure utilise 168.63.129.16, sauf configuration DNS personnalisée.

Comment s'effectue l'évaluation de deux règles contradictoires au sein d'un même Network Security Group (NSG) ?

Les règles NSG sont traitées par ordre strictement croissant de priorité (100 à 4096). La première règle qui correspond aux critères du paquet s'applique et arrête le processus d'évaluation.

Quelle est la priorité de la règle par défaut Inbound d'un NSG qui bloque tout le trafic entrant non explicitement autorisé (DenyAllInBound) ?

La règle par défaut DenyAllInBound possède la priorité 65500, garantissant qu'elle s'applique en toute fin de chaîne si aucune règle personnalisée précédente n'a matché.

Pourquoi Azure Bastion est-il considéré comme une pratique d'excellence pour l'administration de machines virtuelles ?

Azure Bastion établit une session RDP/SSH sécurisée au travers d'une connexion web chiffrée (port 443), éliminant l'exposition des ports 22 et 3389 sur Internet et évitant d'assigner des IPs publiques aux serveurs.

Quelle condition technique stricte est obligatoire pour pouvoir établir un VNet Peering entre deux réseaux virtuels Azure ?

Le peering entre deux réseaux virtuels est strictement impossible si leurs plages d'adresses IP (espaces d'adressage CIDR) se chevauchent, afin d'éviter toute collision de routage.

Dans une architecture Hub-and-Spoke, quel paramètre de peering le VNet Spoke doit-il activer pour acheminer son trafic vers le réseau d'entreprise via la passerelle du Hub ?

Le VNet Spoke active Use Remote Gateways pour transférer ses paquets via la passerelle VPN/ExpressRoute du Hub (sur lequel est activé Allow Gateway Transit).

Quelle est la portée géographique du service Global VNet Peering sous Azure ?

Global VNet Peering permet d'interconnecter des VNets situés dans des régions Azure différentes (ex: France Central et East US) avec un chiffrement matériel natif sur le réseau privé Microsoft.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Oublier les 5 adresses IP réservées lors du dimensionnement d'un petit sous-réseau en /29 (8 adresses théoriques mais seulement 3 adresses utilisables !).
  • Attribuer des priorités trop proches (ex: 100, 101, 102) dans les règles NSG, empêchant l'insertion future de nouvelles règles intermédiaires (préférer 100, 200, 300).
  • Tenter d'apparier en VNet Peering deux réseaux virtuels partageant un même espace d'adressage CIDR : ARM rejette immédiatement la création.
  • Croire que le peering est transitif par défaut : si A est appairé à B et B à C, A ne peut pas communiquer avec C sans passer par une passerelle de routage (NVA/Firewall).

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Élaboration du plan d'adressage IP sans chevauchement : définir des plages CIDR RFC 1918 distinctes pour chaque VNet et dimensionner les sous-réseaux en retranchant les 5 adresses réservées par Azure.
  2. Déploiement des sous-réseaux système obligatoires : allouer GatewaySubnet (/27 minimum) pour les passerelles VPN et AzureBastionSubnet (/26 minimum) pour l'administration sans IP publique.
  3. Configuration de la politique de filtrage NSG par couches : appliquer des règles NSG restrictives par défaut et n'ouvrir que les ports strictement nécessaires avec des priorités basses (100-300).
  4. Établissement des peerings bidirectionnels avec transit de passerelle : créer les liaisons de peering entre le Hub et les Spokes en autorisant le transit de passerelle pour mutualiser l'accès au réseau d'entreprise.

8. Révision active

Résumé essentiel
  • Un Azure VNet isole un réseau virtuel privé ; Azure réserve systématiquement 5 adresses IP (.0, .1, .2, .3, .255) dans chaque sous-réseau.
  • Les sous-réseaux en /24 offrent exactement 251 adresses IP exploitables pour les machines virtuelles.
  • Les Network Security Groups (NSG) filtrent le trafic selon la priorité des règles (100 à 4096), avec les règles par défaut 65000 (Allow VNet) et 65500 (Deny All).
  • Azure Bastion fournit un accès d'administration RDP/SSH sécurisé par navigateur web sans nécessiter d'adresse IP publique sur les serveurs.
  • Le VNet Peering interconnecte des réseaux virtuels privés via le backbone Microsoft sans transiter par Internet, sous condition de non-chevauchement des plages CIDR.

Checklist de maîtrise

  • Savez-vous énumérer les 5 adresses IP réservées par Azure dans n'importe quel sous-réseau ?
  • Combien d'adresses exploitables compte un sous-réseau /26 (64 adresses) sous Azure ?
  • Comprenez-vous pourquoi une règle NSG de priorité 100 prévaut sur une règle de priorité 500 ?
  • Savez-vous pourquoi Azure Bastion élimine le risque d'attaques par force brute sur le port 22 ou 3389 ?
  • Pouvez-vous expliquer pourquoi deux réseaux ayant le même CIDR (ex: 10.0.0.0/16) ne peuvent pas être appairés en VNet Peering ?

Les 8 notions à connaître absolument

  1. Azure Virtual Network (VNet) : Réseau virtuel privé isolé sous Azure permettant la communication sécurisée entre ressources Cloud et sur site.
  2. Adresses IP réservées Azure : Les quatre premières adresses d'un sous-réseau (réseau, passerelle, deux adresses de correspondance Azure DNS) et la dernière sont réservées.
  3. Network Security Group (NSG) : Pare-feu de niveau 4 filtrant les paquets réseau par liste de contrôle d'accès (ACL) ordonnée par priorité.
  4. Azure Bastion : Passerelle PaaS managée permettant d'administrer des machines virtuelles en RDP/SSH via le portail web (HTTPS) sans IP publique.
  5. VNet Peering : Interconnexion directe à haute vitesse et faible latence entre deux réseaux virtuels via le réseau fédérateur privé de Microsoft.
  6. Un Azure VNet isole un réseau virtuel privé ; Azure réserve systématiquement 5 adresses IP (.0, .1, .2, .3, .255) dans chaque sous-réseau.
  7. Les sous-réseaux en /24 offrent exactement 251 adresses IP exploitables pour les machines virtuelles.
  8. Les Network Security Groups (NSG) filtrent le trafic selon la priorité des règles (100 à 4096), avec les règles par défaut 65000 (Allow VNet) et 65500 (Deny All).

9. Test de maîtrise

Comment vous auto-évaluer

Le QCM ci-dessus est un test de maîtrise. Lisez votre pourcentage :

< 50 % — Conception de plan d'adressage d'entreprise multi-VNets : Découper des espaces d'adressage 10.x.0.0/16 en sous-réseaux étanches (Front, Métier, Data, DMZ) en intégrant les contraintes des 5 adresses réservées.
50–69 % — Matrice de sécurité NSG et Application Security Groups (ASG) : Structurer des règles de pare-feu applicatif par étiquettes ASG pour sécuriser les flux inter-tiers sans multiplier les règles d'IP manuelles.
70–94 % — Déploiement zéro-exposition avec Azure Bastion et Private Endpoints : Bannir totalement les adresses IP publiques et interconnecter les services PaaS (Azure SQL, Storage) via des points de terminaison privés dans le VNet.
≥ 95 % — Automatisation d'évaluation réseau de manière méthodique : Programmer des calculateurs de sous-réseaux CIDR, des simulateurs d'évaluation de paquets par NSG et des vérificateurs de topologie peering.
