Chapitre 5 — Stockage Azure (Blob, Files, Disques) et Données Managées

Module 5 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans un écosystème d'entreprise produisant quotidiennement des téraoctets de sauvegardes, de logs applicatifs et de données transactionnelles, conserver indéfiniment toutes les données sur des paliers de stockage à coût élevé entraîne une explosion budgétaire. De même, partager des clés maîtresses de compte de stockage avec des applications clientes crée une faille de sécurité majeure. En tant qu'architecte de données Cloud B3, vous devez structurer les comptes de stockage Azure, implémenter une politique de cycle de vie (Lifecycle Management) automatisant le passage vers Cool et Archive, sécuriser les accès par jetons SAS délimités dans le temps, et arbitrer entre Azure SQL Database pour le relationnel ACID et Azure Cosmos DB pour le NoSQL distribué à l'échelle mondiale.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. maîtriser l'architecture des comptes de stockage Azure Storage (Blob, File, Queue, Table) ;
  2. comparer les mécanismes de réplication des données : LRS, ZRS, GRS et GZRS ;
  3. configurer des règles d'optimisation du cycle de vie des données (Hot -> Cool -> Cold -> Archive -> Delete) ;
  4. générer et valider des jetons de signature d'accès partagé (Shared Access Signature - SAS) à privilèges restreints ;
  5. différencier les services de bases de données managées : Azure SQL Database (ACID relationnel) et Azure Cosmos DB (NoSQL distribué mondialement) ;
  6. développer en Python 3 des simulateurs de cycle de vie de stockage, des validateurs de jetons SAS et des sélecteurs d'architecture de données.

1. Comptes de Stockage Azure (Storage Accounts) & Éventail de Services

Un Azure Storage Account (Standard general-purpose v2) est le conteneur fondamental de données d'entreprise sous Azure. Il expose quatre services spécialisés accessibles via des API REST HTTP/HTTPS hautement performantes :

Blob Storage (Objets Non Structurés)

  • Block Blobs : optimisés pour le streaming de médias, les sauvegardes et les data lakes (fichiers jusqu'à 190,7 To par blob).
  • Append Blobs : optimisés pour l'écriture séquentielle de journaux d'audit et de logs en continu.
  • Page Blobs : blocs de 512 octets à accès aléatoire, servant de support physique aux disques durs virtuels VHD des machines virtuelles.

Azure Files, Queues & Tables

  • Azure Files : partages de fichiers réseau managés accessibles via les protocoles standard SMB 3.0 (port 445) et NFS 4.1. Montables nativement sur Windows, Linux et macOS.
  • Azure Queue Storage : file d'attente de messagerie asynchrone pour découpler les composants d'une architecture logicielle (messages jusqu'à 64 Ko).
  • Azure Table Storage : magasin de clés-valeurs NoSQL sans schéma pour jeux de données tabulaires simples et économiques.

2. Paliers d'Accès (Access Tiers), Cycle de Vie & Réplication des Données

3. Sécurité par Jetons SAS & Bases de Données Managées (SQL vs Cosmos DB)

L'exposition sécurisée des données et le choix des moteurs de bases de données constituent deux piliers d'architecture majeurs :

Signatures d'Accès Partagé (SAS Tokens)

  • Principe : URL signée temporaire accordant un accès granulaire sans divulguer la clé maîtresse du compte de stockage.
  • Paramètres clés :
    - sp (Permissions) : r (read), w (write), d (delete), l (list).
    - st / se : date de début et d'expiration stricte.
    - spr=https : impose le protocole HTTPS sécurisé.
  • User Delegation SAS : signée avec une identité Entra ID pour une traçabilité totale des accès dans les logs d'audit.

Azure SQL Database vs Cosmos DB

  • Azure SQL Database : base relationnelle managée (PaaS), compatible T-SQL / SQL Server, transactions ACID complètes, intégrité référentielle et requêtes jointures complexes.
  • Azure Cosmos DB : base NoSQL multi-modèle (document JSON, clé-valeur, graphe Gremlin) avec distribution mondiale à l'échelle de la planète en un clic, latence garantie inférieure à 10 ms et 5 niveaux de consistance (de Strong à Eventual).

Exercice 1 — Simulateur de cycle de vie Azure Blob Storage

Étude de cas Niveau 1 — Acquisition

Objectif : Appliquer des règles de gestion automatique du cycle de vie des données Blob Storage (Hot -> Cool -> Archive -> Delete) et mesurer les économies financières.

Azure Blob Lifecycle Management permet de transférer automatiquement des données froides vers des paliers de stockage moins coûteux ou de les purger.

Tarification de référence mensuelle par Go :
- HOT : 0.0184 USD / Go
- COOL : 0.0100 USD / Go
- ARCHIVE : 0.00099 USD / Go
- DELETED : 0.0000 USD / Go

Format d'entrée :
Ligne 1 : Déclaration de la politique de cycle de vie :
POLICY cool_days=<int> archive_days=<int> delete_days=<int>
Lignes suivantes : Objets blobs à évaluer :
BLOB name=<nom> size_gb=<int> age_days=<int>

Règles de transition (évaluation par ordre de priorité descendante) :
- Si age_days >= delete_days : palier DELETED (coût = 0.0000)
- Sinon si age_days >= archive_days : palier ARCHIVE (coût = size_gb * 0.00099)
- Sinon si age_days >= cool_days : palier COOL (coût = size_gb * 0.0100)
- Sinon : palier HOT (coût = size_gb * 0.0184)

Format de sortie attendu :
Pour chaque blob :
BLOB <nom>: age=<age_days>d TARGET_TIER=<TIER> COST=$<cost:.4f>
À la fin, afficher le récapitulatif comparatif (coût initial si tous en HOT vs coût optimisé) :
TOTAL_HOT=$<total_hot:.2f> TOTAL_OPTIMIZED=$<total_opt:.2f> SAVINGS=<savings_pct:.1f>%

Cas d’exemple
POLICY cool_days=30 archive_days=90 delete_days=365
BLOB name=log-recent.csv size_gb=10 age_days=10
BLOB name=backup-q1.bak size_gb=100 age_days=45
BLOB name=archive-2023.tar size_gb=500 age_days=120
BLOB name=temp-2022.tmp size_gb=50 age_days=400
Résolution attendue
BLOB log-recent.csv: age=10d TARGET_TIER=HOT COST=$0.1840
BLOB backup-q1.bak: age=45d TARGET_TIER=COOL COST=$1.0000
BLOB archive-2023.tar: age=120d TARGET_TIER=ARCHIVE COST=$0.4950
BLOB temp-2022.tmp: age=400d TARGET_TIER=DELETED COST=$0.0000
TOTAL_HOT=$12.14 TOTAL_OPTIMIZED=$1.68 SAVINGS=86.2%

Migration vers Cool, Archive et suppression générant 86.2% d'économies.

Deux indices, rédigés en mots
  1. Vérifier les conditions d'âge dans l'ordre : delete_days, puis archive_days, puis cool_days.
  2. Calculer total_hot = somme(size_gb * 0.0184) pour mesurer le gain du Lifecycle Management.

Exercice 2 — Validateur de requêtes avec jetons SAS

Étude de cas Niveau 2 — Application

Objectif : Valider la conformité d’appels API clients face aux permissions, plages horaires et protocoles imposés par un jeton de signature d’accès partagé (SAS).

Les jetons de signature d'accès partagé (Azure SAS Tokens) délèguent un accès restreint aux ressources de stockage en précisant les permissions accordées, une fenêtre temporelle et un protocole strict.

Format d'entrée :
Ligne 1 : Configuration du jeton SAS :
SAS_CONFIG sp=<perms> st=<int> se=<int> spr=<protocol>
- sp : permissions autorisées (sous-chaîne contenant r, w, d, l)
- st : horodatage début de validité (entier)
- se : horodatage fin de validité (entier)
- spr : protocole imposé (https ou https,http)

Lignes suivantes : Requêtes HTTP clientes :
REQUEST method=<GET|PUT|DELETE|LIST> time=<int> proto=<http|https>

Correspondance des méthodes HTTP avec les permissions SAS :
- GET requiert r
- PUT requiert w
- DELETE requiert d
- LIST requiert l

Ordre strict d'évaluation de la requête :
1. Si spr=https et que la requête utilise proto=http :
REQUEST <method> at <time>: DENIED (reason=PROTOCOL_VIOLATION)
2. Si time < st :
REQUEST <method> at <time>: DENIED (reason=NOT_YET_VALID)
3. Si time > se :
REQUEST <method> at <time>: DENIED (reason=EXPIRED)
4. Si la permission requise n'est pas présente dans sp :
REQUEST <method> at <time>: DENIED (reason=INSUFFICIENT_PERMISSIONS)
5. Si tous les contrôles réussissent :
REQUEST <method> at <time>: ALLOWED

Cas d’exemple
SAS_CONFIG sp=rw st=100 se=200 spr=https
REQUEST method=GET time=150 proto=https
REQUEST method=DELETE time=150 proto=https
Résolution attendue
REQUEST GET at 150: ALLOWED
REQUEST DELETE at 150: DENIED (reason=INSUFFICIENT_PERMISSIONS)

Lecture autorisée mais suppression interdite par le jeton SAS (permissions rw uniquement).

Deux indices, rédigés en mots
  1. Créer un dictionnaire associant chaque méthode HTTP à sa lettre de permission (GET: r, PUT: w, DELETE: d, LIST: l).
  2. Respecter l'ordre prescrit des contrôles d'erreur : protocole, puis anticipé, puis expiré, puis permissions.

Exercice 3 — Sélecteur d'architecture de données Azure

Étude de cas Niveau 3 — Raisonnement

Objectif : Analyser les besoins fonctionnels et recommander le service de stockage ou de base de données managé Azure adéquat.

Azure dispose d'une gamme diversifiée de services de données managés. Le choix dépend du modèle de données (relationnel, NoSQL, fichiers, objets) et des contraintes d'infrastructure.

Matrice de décision Azure :
- Si model=RELATIONAL :
SERVICE=Azure_SQL_Database JUSTIFICATION="Moteur relationnel transactionnel ACID et compatibilité T-SQL"
- Si model=NOSQL_DOCUMENT :
SERVICE=Azure_Cosmos_DB JUSTIFICATION="Base NoSQL multi-modèle distribuée mondialement avec latence garantie < 10ms"
- Si model=FILE_SMB :
SERVICE=Azure_Files JUSTIFICATION="Partage de fichiers partagé natif compatible SMB/NFS sans serveur dédié"
- Si model=UNSTRUCTURED_OBJECTS :
SERVICE=Azure_Blob_Storage JUSTIFICATION="Stockage objet massif hautement scalable avec gestion de cycle de vie et niveaux d'accès"

Format d'entrée :
REQUIREMENT workload=<nom> model=<MODEL>

Format de sortie attendu :
DECISION workload=<nom>: SERVICE=<SERVICE> JUSTIFICATION="<JUSTIFICATION>"
(Si le modèle est inconnu : DECISION workload=<nom>: SERVICE=UNKNOWN JUSTIFICATION="Modèle non supporté").

Cas d’exemple
REQUIREMENT workload=app-erp model=RELATIONAL
REQUIREMENT workload=mobile-cart model=NOSQL_DOCUMENT
Résolution attendue
DECISION workload=app-erp: SERVICE=Azure_SQL_Database JUSTIFICATION="Moteur relationnel transactionnel ACID et compatibilité T-SQL"
DECISION workload=mobile-cart: SERVICE=Azure_Cosmos_DB JUSTIFICATION="Base NoSQL multi-modèle distribuée mondialement avec latence garantie < 10ms"

Sélection d'Azure SQL pour l'ERP et Cosmos DB pour le panier mobile.

Deux indices, rédigés en mots
  1. Associer chaque mot-clé de modèle de données aux caractéristiques techniques du service managé Azure.
  2. Soigner le formatage avec guillemets autour de la justification.

5. QCM — niveau examen

Quel protocole réseau standard Azure Files supporte-t-il nativement pour permettre le montage de lecteurs réseau partagés sur des postes Windows et serveurs Linux ?

Azure Files fournit des partages de fichiers managés dans le Cloud accessibles directement via les protocoles standard SMB 3.0 (port 445) et NFS 4.1.

Quelle est la durée minimale de facturation d'un objet stocké dans le palier Cool (Froid) d'Azure Blob Storage ?

Le palier Cool impose une durée minimale de rétention de 30 jours. Tout fichier supprimé ou déplacé avant ce terme fait l'objet d'une facturation anticipée au prorata des 30 jours.

Quel palier de stockage offre le coût de stockage par Go le plus bas (moins de 0.001 $/Go/mois) mais nécessite une réhydratation de plusieurs heures pour être lu ?

Le palier Archive stocke les données hors ligne au tarif le plus bas (≈ 0.00099 $/Go/mois), mais nécessite un délai de réhydratation de plusieurs heures pour redevenir lisible.

Quel paramètre d'un jeton de signature d'accès partagé (SAS) permet de forcer l'utilisation exclusive du protocole chiffré HTTPS ?

Le paramètre spr (Signed Protocol) configuré à spr=https contraint le client à utiliser uniquement le protocole HTTPS, rejetant toute requête transmise en HTTP non sécurisé.

Dans quelles circonstances devez-vous recommander Azure Cosmos DB plutôt qu'Azure SQL Database ?

Azure Cosmos DB est la base NoSQL par excellence pour les applications web et mobiles modernes distribuées mondialement nécessitant une latence ultra-faible garantie et un schéma JSON flexible.

Quelle est la taille maximale d'un seul Block Blob dans Azure Blob Storage ?

Un Block Blob standard dans Azure Storage peut atteindre jusqu'à environ 190.7 To (50 000 blocs de 4 000 Mo chacun).

Quelle stratégie de réplication garantit la copie synchrone sur 3 zones de disponibilité locales, suivie d'une réplication asynchrone dans la région jumelée ?

GZRS (Geo-Zone-Redundant Storage) combine la haute disponibilité locale sur 3 zones (ZRS) avec la résilience géographique dans la région jumelée (GRS).

Quel service Azure Storage devez-vous utiliser pour créer un système de découplage de tâches et de traitement asynchrone entre microservices ?

Azure Queue Storage permet de stocker d'immenses volumes de messages (jusqu'à 64 Ko par message) pour découpler les microservices et absorber les pics de charge applicatifs.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Passer un blob en palier Archive puis tenter de le lire immédiatement via une requête HTTP directe : Azure retourne une erreur 409 (l'objet doit d'abord être réhydraté).
  • Supprimer un fichier dans le palier Cool au bout de 5 jours : Azure facture la pénalité des 25 jours restants de la durée minimale de rétention de 30 jours.
  • Générer un jeton SAS sans date d'expiration ou avec des droits de suppression complets pour une simple application mobile cliente.
  • Utiliser Azure Blob Storage pour partager des répertoires de travail réseau d'entreprise alors qu'Azure Files est spécialement conçu pour le protocole SMB avec gestion des verrous de fichiers.

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Choix du service de données selon le modèle applicatif : qualifier le modèle entre relationnel transactionnel (Azure SQL), documents NoSQL ultra-rapides (Cosmos DB), partage réseau (Azure Files) ou stockage objet volumineux (Blob Storage).
  2. Définition de la politique de réplication de résilience : sélectionner ZRS pour les données critiques locales, et GRS/GZRS pour les sauvegardes devant survivre à un sinistre régional continental.
  3. Mise en place de règles de cycle de vie FinOps : automatiser la descente progressive des fichiers vers Cool et Archive pour réduire jusqu'à 90% des coûts de stockage des données froides.
  4. Verrouillage des accès par jetons SAS et points de terminaison privés : interdire l'accès public aux comptes de stockage, déployer des Private Endpoints dans le VNet et restreindre les flux clients via des jetons SAS éphémères.

8. Révision active

Résumé essentiel
  • Les comptes de stockage Azure regroupent 4 services majeurs : Blob (objets), Files (partage SMB/NFS), Queues (messages) et Tables (NoSQL simple).
  • Les 4 paliers d'accès Blob (Hot, Cool, Cold, Archive) permettent d'ajuster les coûts selon la fréquence de consultation des fichiers.
  • Le Lifecycle Management déplace automatiquement les données froides vers des paliers économiques selon leur ancienneté sans code.
  • Les signatures d'accès partagé (SAS Tokens) accordent un accès restreint (droits, durée, HTTPS) sans divulguer la clé secrète du compte.
  • Azure SQL Database répond aux besoins relationnels ACID structurés, tandis qu'Azure Cosmos DB gère le NoSQL mondial à latence sub-10ms.

Checklist de maîtrise

  • Savez-vous dans quels cas utiliser Azure Files (SMB/NFS) plutôt qu'un conteneur Azure Blob ?
  • Connaissez-vous les durées minimales de facturation associées aux paliers Cool (30 j), Cold (90 j) et Archive (180 j) ?
  • Pouvez-vous expliquer le phénomène de réhydratation lors de la lecture d'un blob archivé ?
  • Savez-vous composer les paramètres obligatoires d'un jeton SAS sécurisé (sp=r, spr=https, fenêtre temporelle courte) ?
  • Quand devez-vous choisir Azure Cosmos DB plutôt qu'Azure SQL Database ?

Les 8 notions à connaître absolument

  1. Block Blob : Type de blob Azure optimisé pour stocker efficacement d'immenses volumes de données non structurées (fichiers, images, sauvegardes).
  2. Access Tier (Palier d'accès) : Niveau de stockage Blob (Hot, Cool, Cold, Archive) associant un coût de rétention par Go et un coût d'opération de lecture/écriture.
  3. Réhydratation de Blob : Processus asynchrone prenant plusieurs heures pour copier un blob du palier Archive vers un palier en ligne (Hot ou Cool).
  4. Shared Access Signature (SAS) : URI sécurisée intégrant un jeton cryptographique autorisant un accès délégué restreint aux ressources Azure Storage.
  5. Azure Cosmos DB : Base de données NoSQL distribuée mondialement avec latences de lecture et écriture inférieures à 10 millisecondes.
