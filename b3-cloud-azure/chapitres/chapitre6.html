Chapitre 6 — Surveillance, Gestion des Coûts & Automatisation (IaC & KQL)

Module 6 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans un parc de plusieurs centaines de machines virtuelles et microservices dans le Cloud, attendre qu'un utilisateur signale une panne ou découvrir une facture mensuelle imprévue avec 15 000 euros de surcoût révèle un défaut critique de gouvernance. En tant qu'ingénieur DevOps et Cloud B3, vous devez instrumenter la supervision continue avec Azure Monitor, configurer des alertes intelligentes sur seuils CPU et budgétaires, auditer les logs de sécurité et d'application via des requêtes analytiques KQL puissantes dans Log Analytics, améliorer le Secure Score dans Defender for Cloud et industrialiser les déploiements de ressources reproductibles grâce à des gabarits Infrastructure as Code Bicep / ARM.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. maîtriser la collecte télémétrique (métriques, logs d'activité, diagnostics) avec Azure Monitor ;
  2. configurer des règles d'alerte métriques et budgétaires déclenchant des Action Groups (email, SMS, webhooks) ;
  3. interroger efficacement les journaux d'infrastructure avec KQL (Kusto Query Language) : where, project, summarize, order by, take ;
  4. évaluer et renforcer la posture de sécurité de l'entreprise avec Microsoft Defender for Cloud et le Secure Score ;
  5. maîtriser les principes du FinOps, le suivi des budgets Cost Management et les prévisions de dépenses (Forecast) ;
  6. concevoir, valider et ordonnancer des gabarits déclaratifs d'Infrastructure as Code (IaC Bicep et ARM templates) ;
  7. implémenter en Python 3 des moteurs d'exécution KQL, des gestionnaires d'alertes métriques et des linters de gabarits IaC.

1. Observabilité Globale avec Azure Monitor & Règles d'Alerte

Azure Monitor est la plateforme unifiée de collecte, d'analyse et d'action sur la télémétrie de l'ensemble des ressources Azure et sur site :

Les Deux Piliers Télémétriques

  • Métriques (Metrics) : données numériques légères collectées en temps quasi réel (intervalles d'une minute) décrivant l'état instantané des ressources (pourcentage CPU, mémoire disponible, octets réseau, IOPS disque). Idéales pour l'alerte immédiate et l'auto-scaling.
  • Journaux (Logs) : enregistrements textuels structurés ou semi-structurés (événements système, Activity Logs ARM, logs d'authentification Entra ID, Syslog Linux). Stockés et indexés dans Log Analytics.

Règles d'Alerte & Action Groups

  • Condition d'alerte : évaluation d'une métrique (ex: CPU > 80% pendant 5 min) ou d'une requête de log.
  • Sévérités normalisées : de Sev0 (Critique - service interrompu) à Sev4 (Informationnelle / Audit).
  • Action Groups (Groupes d'actions) : définissent la cible de la notification : envoi d'emails, SMS, notifications push, appel de webhooks (Teams/Slack), déclenchement d'une Azure Automation Runbook ou d'une Azure Function pour auto-remédiation.

2. Analyse Avancée des Journaux avec Log Analytics & KQL (Kusto Query Language)

Un Log Analytics Workspace est l'environnement d'ingestion et d'indexation où convergent les journaux de vos serveurs, réseaux et services PaaS. KQL est le langage de requête déclaratif ultra-rapide utilisé pour explorer ces téraoctets de données :

Opérateur KQLRôle et FonctionExemple Concret de Syntaxe
whereFiltre les lignes correspondant à un prédicat logique booléen.AzureActivity | where Status == "Failed" and DurationMs > 1000
projectSélectionne, ordonne ou renomme les colonnes à afficher dans le résultat.| project TimeGenerated, OperationName, Caller, ResourceGroup
summarizeAgrège les lignes par regroupement (fonctions count(), avg(), sum(), dcount()).| summarize FailureCount = count() by OperationName

AzureActivity
| where TimeGenerated >= ago(24h)
| where Status == "Failed"
| summarize TotalErreurs = count() by OperationName, Caller
| order by TotalErreurs desc
| take 5

Cette requête identifie en une fraction de seconde les 5 opérations ayant provoqué le plus grand nombre d'échecs au cours des dernières 24 heures ainsi que les comptes administrateurs ou services à l'origine des requêtes.

3. Microsoft Defender for Cloud, FinOps Budgets & Infrastructure as Code (Bicep)

La maîtrise globale du Cloud conjugue posture de sécurité, contrôle budgétaire et industrialisation du code :

Sécurité : Defender for Cloud & Secure Score

  • Secure Score : note globale sur 100% reflétant la conformité de votre tenant face aux recommandations de sécurité Microsoft et aux standards internationaux (ISO 27001, CIS Benchmark).
  • Recommandations automatisées : chiffrements des disques non activés, ports d'administration ouverts sur Internet, authentification MFA non requise.
  • Protection contre les menaces : alertes en temps réel sur les attaques par force brute RDP/SSH et les comportements suspects de conteneurs ou bases de données.

FinOps & IaC (Bicep / ARM)

  • Azure Cost Management : création de budgets mensuels alertant à 80% (Spend réel) et 100% (Spend prévisionnel Forecast).
  • Bicep : langage déclaratif moderne conçu par Microsoft comme une évolution élégante des templates JSON ARM : syntaxe concise, vérification de types à la compilation, et gestion automatique des dépendances dependsOn.
  • Idempotence : redéployer un template Bicep plusieurs fois produit toujours le même état cible sans créer de doublons.

Exercice 1 — Interpréteur de requêtes Log Analytics KQL

Python Niveau 1 — Acquisition

Objectif : Exécuter un pipeline de requêtes KQL (where, summarize, order by, take) sur un jeu de journaux d’événements Azure.

Le langage KQL (Kusto Query Language) est le standard d'interrogation analytique d'Azure Monitor, Log Analytics et Microsoft Sentinel.

Format d'entrée :
Un flux d'événements Azure au format :
EVENT rg=<rg> op=<operation> status=<Success|Failed> duration_ms=<int>
Suivi d'une instruction KQL sur la dernière ligne :
KQL where status == "<Success|Failed>" | summarize count() by op | order by count_ desc | take <N>

Comportement du moteur KQL :
1. Filtrer les événements où status correspond à la valeur demandée.
2. Agréger les occurrences par op (opération), produisant un champ count_.
3. Trier les résultats par count_ décroissant (en cas d'égalité, tri alphabétique croissant sur op).
4. Conserver les N premières lignes (opérateur take).

Format de sortie attendu :
En-tête : op | count_
Chaque ligne : <op> | <count_>
(Si aucun événement ne correspond : afficher uniquement l'en-tête).

Entrée du programme
EVENT rg=rg-prod op=RestartVM status=Failed duration_ms=450
EVENT rg=rg-prod op=DeleteDisk status=Failed duration_ms=1200
EVENT rg=rg-prod op=RestartVM status=Failed duration_ms=300
EVENT rg=rg-dev op=RestartVM status=Success duration_ms=150
KQL where status == "Failed" | summarize count() by op | order by count_ desc | take 2
Sortie attendue
op | count_
RestartVM | 2
DeleteDisk | 1

Filtrage des événements en échec, agrégation par opération et sélection des 2 premières.

Deux indices, rédigés en mots
  1. Stocker les événements dans une liste de dictionnaires.
  2. Extraire le filtre status et la limite N depuis la ligne de commande KQL avec re ou split.
  3. Utiliser collections.Counter pour compter les opérations filtrées.

Exercice 2 — Gestionnaire d'alertes Azure Monitor et suivi budgétaire

Python Niveau 2 — Application

Objectif : Évaluer en temps réel des règles d’alerte sur métriques d’infrastructure (CPU) et surveiller les seuils d’engagement budgétaire Cost Management.

Azure Monitor déclenche des alertes métriques pour automatiser les remédiations, tandis qu'Azure Cost Management avertit les équipes lorsque les dépenses réelles ou prévisionnelles franchissent des pourcentages clés du budget mensuel.

Format d'entrée :
1. Définition du budget mensuel :
BUDGET amount=<float> currency=EUR
2. Déclaration des règles d'alerte :
- ALERT_RULE metric=CPU threshold=<int> severity=<Sev0..Sev4>
- ALERT_RULE metric=SPEND_ACTUAL threshold_pct=<int> severity=<Sev0..Sev4>
- ALERT_RULE metric=SPEND_FORECAST threshold_pct=<int> severity=<Sev0..Sev4>
3. Enregistrements télémétriques :
RECORD metric=<METRIC> value=<float>

Règles de déclenchement :
- Pour CPU :
- Si value >= threshold :
ALERT_FIRED: metric=CPU val=<value:.1f>% threshold=<threshold>% severity=<SevX> action=TRIGGER_ACTION_GROUP
- Sinon : ALERT_OK: metric=CPU val=<value:.1f>%
- Pour SPEND_ACTUAL :
Le seuil en euros vaut amount * (threshold_pct / 100).
- Si value >= seuil_euros :
ALERT_FIRED: metric=SPEND_ACTUAL val=<value:.2f>EUR threshold=<seuil_euros:.2f>EUR (pct=<threshold_pct>%) severity=<SevX> action=NOTIFY_FINOPS
- Sinon : ALERT_OK: metric=SPEND_ACTUAL val=<value:.2f>EUR
- Pour SPEND_FORECAST :
Le seuil en euros vaut amount * (threshold_pct / 100).
- Si value >= seuil_euros :
ALERT_FIRED: metric=SPEND_FORECAST val=<value:.2f>EUR threshold=<seuil_euros:.2f>EUR (pct=<threshold_pct>%) severity=<SevX> action=NOTIFY_FINOPS
- Sinon : ALERT_OK: metric=SPEND_FORECAST val=<value:.2f>EUR

Entrée du programme
BUDGET amount=1000 currency=EUR
ALERT_RULE metric=CPU threshold=80 severity=Sev1
ALERT_RULE metric=SPEND_ACTUAL threshold_pct=80 severity=Sev2
RECORD metric=CPU value=85.5
RECORD metric=SPEND_ACTUAL value=750.0
Sortie attendue
ALERT_FIRED: metric=CPU val=85.5% threshold=80% severity=Sev1 action=TRIGGER_ACTION_GROUP
ALERT_OK: metric=SPEND_ACTUAL val=750.00EUR

Alerte CPU déclenchée à 85.5% et dépense sous le seuil des 80% (800 EUR).

Deux indices, rédigés en mots
  1. Calculer les seuils budgétaires effectifs en multipliant le montant du budget par threshold_pct / 100.
  2. Associer chaque métrique à sa sévérité et formater rigoureusement les messages d'alerte.

Exercice 3 — Linter et ordonnanceur de gabarit Bicep / ARM

Python Niveau 3 — Raisonnement

Objectif : Vérifier la validité des déclarations et dépendances (dependsOn) d’un gabarit d’Infrastructure as Code Azure et ordonnancer les déploiements.

Dans les modèles Azure Resource Manager (ARM) ou Bicep, la propriété dependsOn garantit que les ressources prérequises (ex: réseau, sous-réseau, carte réseau) sont déployées avant les ressources dépendantes (ex: machine virtuelle).

Format d'entrée :
- Déclaration des paramètres :
PARAM name=<nom> type=<string|int|bool>
- Déclaration des ressources :
RESOURCE name=<nom> type=<type> dependsOn=[<dep1>,<dep2>] (ou dependsOn=[]).

Contrôles de cohérence :
1. Dépendance manquante : si une ressource mentionnée dans dependsOn n'est déclarée dans aucune ligne RESOURCE :
LINT_FAILED: Missing dependency '<nom_dep>' for resource '<nom_res>'
2. Dépendance circulaire : si le graphe des dépendances contient une boucle (ex: A dépend de B qui dépend de A) :
LINT_FAILED: Circular dependency detected involving '<nom_res>'
3. Si le gabarit est valide : déterminer l'ordre d'exécution (tri topologique déterministe où chaque ressource intervient après ses dépendances ; en cas d'indépendance mutuelle, tri alphabétique par nom de ressource) :
LINT_SUCCESS: resources_count=<N> params_count=<M> execution_order=[<res1>, <res2>, ...]

Entrée du programme
PARAM name=env type=string
RESOURCE name=vnet01 type=Microsoft.Network/virtualNetworks dependsOn=[]
RESOURCE name=nic01 type=Microsoft.Network/networkInterfaces dependsOn=[vnet01]
RESOURCE name=vm01 type=Microsoft.Compute/virtualMachines dependsOn=[nic01]
Sortie attendue
LINT_SUCCESS: resources_count=3 params_count=1 execution_order=[vnet01, nic01, vm01]

Gabarit valide déployant dans l'ordre vnet01 puis nic01 puis vm01.

Deux indices, rédigés en mots
  1. Construire le graphe des dépendances : chaque ressource possède une liste de prérequis.
  2. Utiliser l'algorithme de Kahn pour le tri topologique : extraire en priorité les ressources sans dépendances non satisfaites.
  3. Trier la file des ressources prêtes par ordre alphabétique pour assurer un résultat déterministe.

5. QCM — niveau examen

Quel opérateur KQL est utilisé pour filtrer les lignes d'une table de journaux selon une condition logique ?

En langage KQL (Kusto Query Language), l'opérateur where permet de filtrer les enregistrements d'une table selon un prédicat booléen (ex: where Status == "Failed").

Quel opérateur KQL permet d'agréger des résultats pour calculer le nombre d'occurrences d'un événement par catégorie (ex: par type d'opération) ?

L'opérateur summarize count() by regroupe les enregistrements par les valeurs distinctes de la colonne et calcule le total d'occurrences pour chaque groupe.

Quel outil de surveillance de la sécurité fournit le Secure Score pour évaluer la posture de conformité d'un tenant Azure ?

Microsoft Defender for Cloud (anciennement Azure Security Center) évalue en continu les configurations et calcule le Secure Score avec des recommandations prioritaires.

Dans Azure Monitor, quel composant regroupe la liste des destinataires (adresses email, numéros SMS, webhooks Teams/Slack) appelés lorsqu'une alerte se déclenche ?

Un Action Group regroupe l'ensemble des actions de notification et de remédiation automatisée à exécuter lors du déclenchement d'une règle d'alerte.

Quelle est la sévérité d'alerte Azure Monitor correspondant au niveau d'urgence le plus critique (panne majeure bloquante) ?

Les alertes Azure Monitor s'échelonnent de Sev0 (Critique absolue / panne totale) à Sev4 (Informationnelle / Audit).

Quel est l'avantage du langage déclaratif Bicep par rapport aux templates JSON Azure Resource Manager (ARM) traditionnels ?

Bicep est un DSL moderne conçu par Microsoft offrant une syntaxe modulaire et épurée tout en compilant directement en templates ARM standards de manière totalement transparente.

Dans un budget Azure Cost Management, quelle est la différence entre une alerte basée sur "Actual" et une alerte basée sur "Forecasted" ?

Une alerte "Actual" surveille la somme réellement consommée à l'instant T, tandis que "Forecasted" utilise l'analyse prédictive de consommation pour alerter dès que la trajectoire projetée dépasse le budget avant la fin du cycle mensuel.

Que se passe-t-il lors du déploiement d'un gabarit d'Infrastructure as Code ARM ou Bicep contenant une dépendance circulaire entre deux ressources ?

Le moteur d'orchestration ARM construit un graphe acyclique dirigé (DAG) avant tout déploiement. Si une boucle est détectée, la validation échoue immédiatement et aucune ressource n'est créée.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Rédiger des requêtes KQL sans filtre temporel (ago(1h) ou ago(24h)), forçant Log Analytics à scanner des mois de logs et dégradant les temps de réponse.
  • Configurer des alertes de sévérité Sev0 sans notification téléphonique ni astreinte, laissant des incidents critiques non traités.
  • Ne surveiller que les dépenses réelles et ignorer les prévisions (Forecast) : le budget peut être déjà dépassé avant que l'alerte sur le spend réel ne se déclenche.
  • Créer des dépendances circulaires dans un gabarit Bicep (ex: ressource A dépend de B qui dépend de A), provoquant l'échec immédiat de la validation ARM.

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Déploiement centralisé d'un Log Analytics Workspace : activer les paramètres de diagnostic (Diagnostic Settings) sur toutes les ressources pour acheminer automatiquement métriques et logs vers Log Analytics.
  2. Création des alertes métriques et des budgets d'avertissement FinOps : associer des Action Groups aux alertes CPU/RAM et fixer des seuils d'alerte budgétaire à 80% (réel) et 100% (prévisionnel).
  3. Optimisation du Secure Score dans Defender for Cloud : passer en revue les recommandations prioritaires et appliquer les remédiations (chiffrement, suppression d'IP publiques, MFA obligatoire).
  4. Automatisation des déploiements par templates Bicep : écrire l'infrastructure complète en code déclaratif Bicep, valider l'absence de dépendances circulaires et industrialiser dans une chaîne CI/CD.

8. Révision active

Résumé essentiel
  • Azure Monitor centralise les métriques (données numériques temps réel) et les logs (événements structurés) pour assurer l'observabilité totale.
  • Les Action Groups automatisent les notifications et les remédiations lors du déclenchement d'alertes de sévérité Sev0 à Sev4.
  • KQL (Kusto Query Language) offre un pipeline d'opérateurs hautement performant (where, summarize, project, order by, take) pour explorer les journaux.
  • Microsoft Defender for Cloud évalue la posture de sécurité globale via le Secure Score et détecte les menaces actives.
  • Azure Cost Management contrôle les budgets FinOps, tandis qu'Infrastructure as Code (Bicep / ARM) garantit des déploiements déclaratifs et idempotents.

Checklist de maîtrise

  • Connaissez-vous la différence d'utilisation entre les métriques Azure Monitor et les journaux Log Analytics ?
  • Savez-vous écrire une requête KQL filtrant les erreurs et regroupant par nom d'opération ?
  • Comprenez-vous le rôle du Secure Score dans l'évaluation de la sécurité d'un tenant Azure ?
  • Quelle est la différence entre une alerte budgétaire sur dépense réelle (Actual) et prévisionnelle (Forecasted) ?
  • Pourquoi l'Infrastructure as Code avec Bicep est-elle supérieure à l'administration manuelle par le portail web ?

Les 8 notions à connaître absolument

  1. Log Analytics Workspace : Environnement de stockage et d'indexation centralisé de télémétrie Azure où sont exécutées les requêtes d'analyse KQL.
  2. KQL (Kusto Query Language) : Langage de requête en pipeline utilisé dans Azure Monitor, Microsoft Sentinel et Azure Data Explorer pour le traitement de logs massifs.
  3. Action Group : Collection de récepteurs de notifications (emails, SMS, webhooks, fonctions) déclenchée lors de l'activation d'une règle d'alerte Azure Monitor.
  4. Secure Score : Indicateur chiffré en pourcentage mesurant la posture de sécurité d'un environnement Azure par rapport aux recommandations de Microsoft Defender.
  5. Bicep : Langage de programmation déclaratif spécifique à Azure (DSL) simplifiant l'écriture de gabarits d'Infrastructure as Code (IaC).
