Chapitre 3 — Conteneurisation Docker, Multi-Stage Builds & Infrastructure as Code (IaC)

Module 3 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Le célèbre syndrome « mais ça fonctionnait pourtant sur ma machine ! » traduit l’hétérogénéité chronique des environnements de développement, de test et de production. Pour éradiquer ces divergences et garantir une portabilité stricte, l’industrie s’est convertie à la conteneurisation et à l’Infrastructure as Code (IaC). Toutefois, de nombreux conteneurs déployés en entreprise s’avèrent pachydermiques (plusieurs gigaoctets), lents à construire en CI et truffés de vulnérabilités critiques car construits sans discernement sous privilèges root. L’ingénieur DevOps B3 doit maîtriser l’ingénierie fine des conteneurs Linux (namespaces, cgroups, OverlayFS), concevoir des Dockerfiles ultra-optimisés tirant parti du cache de couches et des builds multi-étapes (Multi-Stage Builds), et piloter ses parcs de serveurs par du code déclaratif idempotent.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. décortiquer les mécanismes d’isolation sous-jacents du noyau Linux : Namespaces, Control Groups (cgroups) et Chroot/Pivot_root ;
  2. différencier architecturalement la conteneurisation de la virtualisation lourde par hyperviseur ;
  3. ordonnancer méthodiquement les instructions d’un Dockerfile pour maximiser l’efficacité du cache de couches (Layer Caching) ;
  4. concevoir des Multi-Stage Builds pour diviser la taille d’image par dix et réduire la surface d’attaque CVE ;
  5. appliquer les règles de sécurité indispensables des conteneurs : exécution non-root, suppression d’outils de build et images minimales (Alpine, Distroless) ;
  6. modéliser et vérifier l’idempotence et la convergence d’état en Infrastructure as Code (IaC).

1. Conteneurisation vs Virtualisation Lourde : Les Primitives du Noyau Linux

Contrairement à une machine virtuelle (VM) qui embarque un système d’exploitation invité complet au-dessus d’un hyperviseur (Type 1 ou 2), un conteneur Linux n’est pas une machine virtuelle. C’est un processus standard du système d’exploitation hôte isolé par des fonctionnalités natives du noyau Linux (Linux Kernel) :

Namespaces (Isolation)

Cloisonnent la vue du système pour le processus : pid (arbre des processus), net (interfaces réseau, ports, tables de routage), mnt (points de montage disque), ipc (mémoire partagée), uts (nom d’hôte) et user (mappage des UID/GID).

Control Groups - cgroups (Plafonds)

Régulent et mesurent la consommation physique des ressources matérielles allouées au conteneur : plafonnement du temps CPU (quota), mémoire vive maximale (RAM limit / OOM killer) et débit d’entrées/sorties disque (I/O throttle).

Chroot & Pivot_root (Système de fichiers)

Isolent la racine du système de fichiers (/), empêchant le processus de naviguer hors de l’arborescence fournie par l’image de base du conteneur.

Puisqu’il partage directement le noyau du serveur hôte, le conteneur démarre en quelques millisecondes, ne consomme aucun overhead de virtualisation matérielle et offre des performances quasi-natives.

2. Le Système de Fichiers en Couches (OverlayFS) & Optimisation du Cache

Une image Docker est constituée d’un empilement de couches immuables en lecture seule (read-only layers) gérées par un système de fichiers d’union (typiquement OverlayFS sous Linux). Chaque instruction du Dockerfile (FROM, RUN, COPY, ADD) génère une nouvelle couche identifiée par une empreinte cryptographique (hash SHA-256).

Lors de la commande docker build, Docker compare le hash de chaque couche avec son cache local : si l’instruction et les fichiers injectés sont strictement identiques, la couche est réutilisée instantanément (Using cache). En revanche, dès qu’une couche est invalidée, toutes les couches suivantes sont obligatoirement reconstruites.

L’Erreur Classique d’Ordonnancement Dockerfile

Copier tout le projet avant d’installer les dépendances brise le cache à chaque modification du moindre fichier source :

# INEFFECTIF (invalide le cache des dépendances à chaque commit) :
COPY . .
RUN npm install

# OPTIMAL (le cache de npm install est conservé tant que package.json ne change pas) :
COPY package*.json ./
RUN npm ci --only=production
COPY . .

3. Multi-Stage Builds & Durcissement de Sécurité

Pour compiler une application (TypeScript, Go, Rust, Java), l’environnement nécessite des compilateurs, des SDKs et des paquets de développement lourds (plusieurs centaines de mégaoctets). Conserver ces outils dans l’image de production finale constitue une triple hérésie : image obèse, transfert réseau lent et vulnérabilités de sécurité critiques (surface d’attaque CVE démesurée).

Le Multi-Stage Build résout ce dilemme en scindant le Dockerfile en étapes distinctes :

Étape 1 : Builder (Compilation)

Image complète équipée de tous les outils nécessaires. Elle compile le binaire exécutable ou minifie les artéfacts web, puis est jetée.

FROM golang:1.21 AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /bin/api

Étape 2 : Runtime (Production Épurée)

Image minimale (Scratch, Alpine ou Distroless). On ne copie que l’artéfact final via COPY --from=builder. Aucun compilateur ni shell n’est conservé.

FROM alpine:3.19
RUN adduser -D appuser
USER appuser
COPY --from=builder /bin/api /bin/api
ENTRYPOINT ["/bin/api"]

Résultat : une image dont la taille passe de 1.1 Go à 15 Mo, sans vulnérabilité système résiduelle et s’exécutant sous un utilisateur non privilégié (USER appuser).

4. Infrastructure as Code (IaC) & Le Principe d’Idempotence

L’Infrastructure as Code (IaC) formalise l’infrastructure réseau et serveur sous forme de fichiers texte versionnés sur Git, éliminant les interventions manuelles sur console (ClickOps). Deux paradigmes s’opposent :

Approche Impérative (Scripts Bash, CLI)

Décrit comment exécuter une succession d’ordres (ex. aws ec2 create-instance ...). Si le script est relancé deux fois, il risque de dupliquer la ressource ou d’échouer brutalement.

Approche Déclarative (Terraform, CloudFormation)

Décrit l’état cible désiré (ex. « il doit exister exactement 3 VM avec tel tag »). Le moteur compare l’état réel et l’état désiré, calculant le delta strict nécessaire.

Idempotence & Détection de Dérive (Configuration Drift)

Une opération est dite idempotente si son application répétée $N$ fois produit exactement le même résultat que son application unique, sans effet secondaire imprévu :

$$f(f(x)) = f(x)$$

Si un opérateur modifie manuellement un groupe de sécurité en production, l’infrastructure entre en état de Drift (Dérive). Un moteur d’IaC moderne détecte ce désalignement lors du plan et restaure la configuration déclarée lors du apply pour garantir la convergence absolue vers l’état de référence.

Exercice 1 — Auditeur d’optimisation de Dockerfile (Layer Caching & Multi-Stage)

Étude de cas Niveau 1 — Acquisition

Objectif : Détecter les anti-patterns courants dans la rédaction d’un Dockerfile et calculer son score de conformité aux bonnes pratiques de conteneurisation.

Analysez les paramètres du problème pour chaque cas...) :

Règles d'audit (score de départ : 100 points) :
1. Image de base lourde (-20 pts) : si une instruction FROM utilise une image complète (contient python:, node:, golang:, ubuntu:) SANS contenir slim ou alpine -> alerte BASE_IMAGE_VOLUMINEUSE.
2. Invalidation prématurée du cache (-30 pts) : si une instruction COPY . . ou COPY . / apparaît chronologiquement avant une instruction d'installation de dépendances (contenant npm install ou pip install) -> alerte CACHE_DEPENDANCES_INVALIDE.
3. Absence de multi-stage pour le compilé (-30 pts) : si le Dockerfile contient une commande de compilation lourde (contenant go build ou cargo build) mais qu'il n'y a qu'une seule instruction FROM dans tout le fichier -> alerte MULTI_STAGE_REQUIS.
4. Exécution en compte root (-20 pts) : si aucune instruction USER n'apparaît dans tout le fichier -> alerte EXECUTION_ROOT_DECONSEILLEE.

Score minimal = 0.
Qualification du score :
- 100 : OPTIMAL
- $\ge 60$ : ACCEPTABLE
- $< 60$ : A_REFACTORISER

Afficher :
AUDIT_DOCKERFILE: SCORE=<score>/100 | NIVEAU=<NIVEAU> | ALERTES=[<alertes ou AUCUNE>]

Cas d’exemple
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
USER appuser
CMD ["python", "main.py"]
Résolution attendue
AUDIT_DOCKERFILE: SCORE=100/100 | NIVEAU=OPTIMAL | ALERTES=[AUCUN]

Image slim, dépendances copiées avant le code complet, compte non-root : Dockerfile parfait.

Deux indices, rédigés en mots
  1. Copier package.json ou requirements.txt avant COPY . . permet de réutiliser le cache Docker.
  2. Garder l’ordre officiel des 4 alertes ci-dessus.

Exercice 2 — Calculateur d’empreinte disque des couches d’images partagées

Étude de cas Niveau 2 — Application

Objectif : Quantifier l’économie d’espace disque permise par le système de couches immuables (layer sharing) du démon Docker sur un hôte.

Analysez les paramètres du problème pour chaque cas...>.
Chaque couche possède un identifiant de hachage et une taille en Mo (ex: L_base:120,L_node:80,L_app:15).

Pour chaque image :
- Calculer sa taille brute apparente = somme de ses couches.
- Afficher : IMAGE: <nom> -> TAILLE=<taille>Mo

Pour l’ensemble du parc :
- Brut_cumulé = somme des tailles de toutes les images.
- Réel_sur_hôte = somme des tailles des couches uniques (chaque hash n'est comptabilisé qu'une seule fois sur le disque hôte).
- Économie = $Brut\_cumulé - Réel\_sur\_hôte$
- Pourcentage = $(Économie / Brut\_cumulé) \times 100$

Afficher la synthèse :
SYNTHESE_DOCKER: BRUT_CUMULE=<brut>Mo | REEL_SUR_HOTE=<reel>Mo | ECONOMIE=<eco>Mo (-<pct:.1f>%)

Cas d’exemple
IMAGE nom=api_auth LAYERS=L_node:150,L_express:30,L_auth:10
IMAGE nom=api_users LAYERS=L_node:150,L_express:30,L_users:15
IMAGE nom=worker LAYERS=L_node:150,L_queues:40
Résolution attendue
IMAGE: api_auth -> TAILLE=190Mo
IMAGE: api_users -> TAILLE=195Mo
IMAGE: worker -> TAILLE=190Mo
SYNTHESE_DOCKER: BRUT_CUMULE=575Mo | REEL_SUR_HOTE=245Mo | ECONOMIE=330Mo (-57.4%)

La couche L_node (150 Mo) et L_express (30 Mo) sont mutualisées sur l’hôte physique.

Deux indices, rédigés en mots
  1. Utiliser un dictionnaire pour mémoriser la taille associée à chaque hash de couche unique.
  2. Le partage de couches de base (ex: Ubuntu ou Alpine) réduit drastiquement l’empreinte des flottes de microservices.

Exercice 3 — Résolveur d’ordre de démarrage de services Docker Compose (depends_on)

Étude de cas Niveau 3 — Raisonnement

Objectif : Calculer la séquence de démarrage topologique valide d’un fichier docker-compose.yml en résolvant les dépendances et en détectant les cycles bloquants.

Analysez les paramètres du problème pour chaque cas...|NONE>.

Règles :
- Un service ne peut démarrer que lorsque TOUS les services mentionnés dans sa directive depends_on ont déjà démarré.
- Si plusieurs services sont éligibles à démarrer au même moment, les ordonner par ordre alphabétique de leur nom pour garantir un résultat déterministe.
- Si un cycle de dépendance mutuelle rend le démarrage impossible (ex: A dépend de B et B dépend de A) :
DOCKER_COMPOSE: ERREUR=CYCLE_DE_DEPENDANCE_DETECTE
- Sinon, affichezzr la séquence ordonnée :
DOCKER_COMPOSE: ORDRE_DEMARRAGE=[<s1, s2, ...>]

Cas d’exemple
SERVICE nom=web depends_on=api
SERVICE nom=api depends_on=database,redis
SERVICE nom=database depends_on=NONE
SERVICE nom=redis depends_on=NONE
Résolution attendue
DOCKER_COMPOSE: ORDRE_DEMARRAGE=[database, redis, api, web]

database et redis démarrent en premier (alphabétiquement database puis redis), puis api, puis web.

Deux indices, rédigés en mots
  1. Utiliser l’algorithme de Kahn avec file de priorité ou sélection du minimum alphabétique parmi les degrés entrants nuls.
  2. Un service dépend de ses prérequis (ses prérequis doivent démarrer avant lui).

6. QCM — niveau examen

Quel mécanisme du noyau Linux permet d’isoler la table des processus (PID) et les interfaces réseau d’un conteneur ?

Les Namespaces Linux restreignent ce qu’un processus peut voir : les namespaces pid et net lui fournissent une table des processus et des interfaces réseau virtuelles dédiées.

Quelle composante du noyau Linux est responsable de limiter la mémoire vive (RAM) maximale consommée par un conteneur ?

Les cgroups (Control Groups) contrôlent et plafonnent la quantité de ressources physiques (mémoire vive, temps CPU, entrées/sorties) allouables à un groupe de processus.

Pourquoi est-il crucial de placer la commande « COPY package.json » avant « COPY . . » dans un Dockerfile Node.js ?

Si le code source change, la couche correspondante et toutes les suivantes sont invalidées. Isoler la copie des manifestes de dépendances permet de réutiliser le cache de téléchargement de paquets.

Quel est l’avantage architectural majeur d’un Dockerfile « Multi-Stage Build » ?

Le Multi-Stage Build isole les outils de build lourds dans un stage temporaire et ne transfère que le binaire final dans l’image de production, réduisant la taille et éliminant les CVE.

Pourquoi est-il formellement déconseillé de laisser un conteneur s’exécuter par défaut sous l’utilisateur « root » en production ?

En cas de vulnérabilité permettant d’échapper au conteneur, un processus tournant sous UID 0 (root) s’octroie un accès root direct sur le noyau de la machine hôte. Il faut toujours créer un utilisateur non privilégié.

En Infrastructure as Code (IaC), que signifie la propriété d’« Idempotence » ?

Une opération idempotente converge vers l’état cible : qu’elle soit exécutée une fois ou cent fois consécutives, l’infrastructure reste conforme sans altération non sollicitée.

Comment qualifie-t-on la situation où la réalité des ressources de production ne correspond plus au code source de configuration déclaré sur Git ?

Le Configuration Drift survient lorsque des modifications manuelles (ou des pannes non réconciliées) désalignent l’infrastructure réelle par rapport au code d’infrastructure versionné.

Parmi ces types d’images de base de conteneur, laquelle offre la surface d’attaque la plus restreinte pour héberger un binaire compilé en Go ou Rust ?

Les images Scratch ou Distroless ne contiennent ni shell (/bin/sh), ni gestionnaire de paquets, ni outils de diagnostic : un assaillant qui injecte du code ne dispose d’aucun binaire pour pivoter.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Placer l’instruction COPY . . avant l’installation des dépendances dans un Dockerfile, détruisant tout le cache de couches à chaque commit.
  • Conserver les compilateurs et SDKs dans l’image finale de production au lieu d’utiliser un Multi-Stage Build épuré.
  • Exécuter les conteneurs sous le compte utilisateur root en production, exposant l’hôte aux failles d’évasion de conteneur.
  • Écrire des scripts d’automatisation impératifs non idempotents qui échouent ou dupliquent les ressources lorsqu’ils sont exécutés une deuxième fois.

8. Méthodologie de résolution

Démarche d’Optimisation et de Sécurisation de Conteneurs Docker
  1. Sélectionner une image de base minimale, officielle et vérifiée (Alpine ou Distroless).
  2. Ordonnancer scrupuleusement les instructions Dockerfile de la moins volatile à la plus fréquemment modifiée.
  3. Isoler les manifestes de dépendances (package.json, requirements.txt) pour réutiliser le cache de téléchargement.
  4. Implémenter un Multi-Stage Build scindant l’environnement de compilation de l’image d’exécution finale.
  5. Créer et déclarer un utilisateur système dédié non privilégié (USER nonroot) pour l’exécution du processus.
  6. Vérifier l’idempotence et la convergence d’état de toute ressource d’Infrastructure as Code (IaC).

9. Révision active

Résumé essentiel
  • Les conteneurs Linux s’appuient sur les Namespaces (isolation) et les cgroups (quotas), partageant le noyau hôte.
  • Une image Docker est un empilement de couches immuables (OverlayFS) identifiées par hash cryptographique.
  • Toute modification d’une couche invalide toutes les couches suivantes : ordonner du statique vers le dynamique.
  • Le Multi-Stage Build réduit l’empreinte de plus de 80% et élimine les compilateurs et failles de l’image de prod.
  • Exécuter un conteneur sous root constitue un risque d’élévation de privilège critique sur la machine hôte.
  • L’IaC déclarative garantit l’idempotence et détecte la dérive de configuration (Drift) par rapport à Git.
