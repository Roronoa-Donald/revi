Chapitre 4 — Déploiement Continu (CD), Stratégies de Release & Feature Flags

Module 4 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Déployer une application en production le vendredi soir en coupant le service pendant deux heures pour « maintenance planifiée » appartient au passé de l’informatique d’entreprise. Dans une économie numérique mondialisée fonctionnant 24h/24, toute indisponibilité programmée entraîne des pertes directes de chiffre d’affaires et dégrade la réputation de l’organisation. Les équipes DevOps modernes doivent réaliser des mises en production continues en plein milieu de journée sans aucune interruption perceptible pour les utilisateurs (Zero-Downtime Deployment). Pour parvenir à ce niveau d’excellence, l’ingénieur B3 doit concevoir des stratégies de release avancées (Blue/Green, Canary progressive) avec coupe-circuit automatisé, et maîtriser le découplage entre le déploiement technique de code et la publication métier par le biais de Feature Flags.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. distinguer avec rigueur la Livraison Continue (Continuous Delivery) du Déploiement Continu (Continuous Deployment) ;
  2. concevoir une architecture de déploiement sans interruption (Zero Downtime) via Rolling Updates ;
  3. implémenter la stratégie Blue/Green et piloter la bascule instantanée de routeur réseau et le retour arrière (Rollback) ;
  4. paramétrer une Canary Release progressive avec monitoring d’erreurs HTTP 5xx et coupe-circuit automatisé ;
  5. découpler le déploiement de code de l’activation métier via des Feature Flags (Toggles) ;
  6. analyser et résoudre méthodologiquement des simulateurs de bascule Blue/Green, de routage Canary et d’évaluation de Feature Flags.

1. Continuous Delivery vs Continuous Deployment : La Frontière Décisionnelle

Bien que regroupés sous l’acronyme commun CD, la Livraison Continue et le Déploiement Continu désignent deux niveaux d’automatisation distincts de la chaîne logicielle :

Livraison Continue (Continuous Delivery)

Chaque modification franchissant avec succès le pipeline de CI produit un artéfact (image Docker, binaire) rigoureusement qualifié et prêt pour la production. Cependant, la mise en production finale requiert une décision humaine explicite (clic sur un bouton par le Release Manager ou approbation managériale).

Déploiement Continu (Continuous Deployment)

L’automatisation est intégrale : chaque commit validé par la suite de tests et les scanners de sécurité est automatiquement déployé en production sans aucune intervention humaine. C’est le modèle adopté par des géants comme Netflix, Amazon ou Spotify (des milliers de déploiements quotidiens).

2. Stratégies de Déploiement Sans Interruption (Zero-Downtime)

Pour renouveler un parc de serveurs ou de pods sans impacter les utilisateurs en session, trois architectures de référence coexistent :

Stratégie Fonctionnement technique Avantages & Contraintes
Rolling Update (Progressif) Remplacement séquentiel des instances anciennes par les nouvelles instances une par une (ou par petits lots maxSurge / maxUnavailable). Ne nécessite aucune surcapacité matérielle majeure. En revanche, les versions N et N+1 cohabitent temporairement en direct.
Blue/Green (Miroir) Deux environnements de production identiques : l’un est actif (Blue), l’autre reçoit la nouvelle version (Green). Une fois les tests de fumée validés sur Green, le routeur/équilibreur bascule 100% du trafic. Bascule instantanée et rollback immédiat en re-routant vers Blue. En contrepartie, double le coût d’infrastructure le temps du déploiement.
Canary Release (Canari) Acheminement d’une fraction infime du trafic réel (ex. 2% ou 5%) vers la version canari. Si les métriques télémétriques (taux d’erreur, latence) restent stables, la part de trafic est augmentée progressivement (25%, 50%, 100%). Détection immédiate des régressions sur trafic réel sans compromettre l’ensemble des utilisateurs. Nécessite un outillage de routage fin (Service Mesh, Ingress).
Le Piège des Schémas de Base de Données

Le déploiement sans interruption impose la règle de compatibilité bidirectionnelle de la base de données : la base de données doit supporter simultanément l’ancienne version (N) et la nouvelle version (N+1). On applique le patron Expand and Contract (Parallel Run) : ajouter d’abord la nouvelle colonne sans supprimer l’ancienne, déployer le code qui écrit dans les deux, migrer les données, et seulement plus tard supprimer l’ancienne colonne.

3. Feature Flags (Toggles) : Découpler Déploiement et Publication

L’un des axiomes les plus puissants du DevOps moderne affirme : « Deploy ≠ Release » (Déployer n’est pas Publier).

  • Le Déploiement (Deploy) : Est une opération purement technique d’acheminement de code sur les serveurs de production.
  • La Publication (Release) : Est une décision métier rendant une fonctionnalité visible et exploitable par les utilisateurs ciblés.

Les Feature Flags (ou basculeurs de fonctionnalités) insèrent des embranchements conditionnels dynamiques dans le code source contrôlés à chaud via une interface de pilotage centralisée (LaunchDarkly, Unleash, Flagsmith) sans recompiler ni re-déployer :

Release Flags (Gradual Rollout)

Activation d’une nouvelle fonctionnalité pour 5% des utilisateurs, puis 20%, puis 100%, avec analyse en temps réel de l’impact sur les performances et les ventes.

Targeting Flags (Ciblage)

Activation exclusive pour les collaborateurs internes de l’entreprise (Dogfooding), les testeurs bêta ou les clients premium ayant souscrit à une option payante.

Ops Flags (Kill Switch)

Disjoncteur d’urgence permettant de désactiver instantanément une sous-partie coûteuse de l’application (moteur de recommandation IA) si la charge serveur menace de faire s’effondrer le site.

Gouvernance & Dette Technique des Flags

Un Feature Flag temporaire doit avoir une durée de vie limitée. Une fois une fonctionnalité déployée à 100% et stabilisée, le code conditionnel doit être promptement nettoyé. Laisser des centaines de flags obsolètes crée un labyrinthe logique instable source de pannes graves (ex. faillite de Knight Capital en 2012 causée par la réactivation accidentelle d’un vieux drapeau mort).

Exercice 1 — Simulateur de bascule Blue-Green sans interruption de service

Étude de cas Niveau 1 — Acquisition

Objectif : Simuler le routage du trafic réseau entre deux environnements jumeaux et automatiser la bascule ou le rollback en cas de défaillance du test de santé.

Analysez les paramètres du problème pour chaque cas.

Règles :
- Si target == active : le déploiement sur l’environnement actif est prohibé.
BLUE_GREEN: ERREUR=DEPLOIEMENT_SUR_ENV_ACTIF_INTERDIT
- Si target != active :
- Si health_check == PASS : le routeur commute instantanément sur target.
BLUE_GREEN: STATUT=BASCULE_REUSSIE | ROUTER_ACTIF=<target> | VERSION_EN_LIGNE=<new_ver> | ANCIEN_ENV=<ancien> (IDLE)
- Si health_check == FAIL : bascule avortée, rollback de sécurité.
BLUE_GREEN: STATUT=ROLLBACK_ANOMALIE | ROUTER_ACTIF=<active> | VERSION_EN_LIGNE=<ver_active> | TARGET_ABANDONNEE=<target>

Cas d’exemple
ROUTER active=BLUE version=1.2.0
DEPLOY target=GREEN version=1.3.0 health_check=PASS
Résolution attendue
BLUE_GREEN: STATUT=BASCULE_REUSSIE | ROUTER_ACTIF=GREEN | VERSION_EN_LIGNE=1.3.0 | ANCIEN_ENV=BLUE (IDLE)

Le test est PASS : le trafic passe sur GREEN (1.3.0), BLUE devient inactif.

Deux indices, rédigés en mots
  1. Le déploiement Blue-Green garantit zéro interruption car la nouvelle version est validée avant la bascule du load balancer.
  2. En cas d’erreur, aucun utilisateur ne subit la version corrompue.

Exercice 2 — Gestionnaire de déploiement progressif en Canari (Canary Release)

Étude de cas Niveau 2 — Application

Objectif : Acheminer graduellement le trafic utilisateur vers une version canari tout en surveillant le taux d’erreur pour avorter automatiquement en cas de régression.

Analysez les paramètres du problème pour chaque cas...> error_rates=<e1,e2,...>.

Déroulement des paliers :
- À chaque palier steps[i], le taux d'erreur observé est error_rates[i].
- Si $error\_rates[i] > seuil\_max$ : le déploiement est immédiatement interrompu.
CANARY_DEPLOY: app=<nom> -> ARRET_ANOMALIE_ETAPE=<step>% (erreur=<e:.2f>%/seuil=<max:.2f>%) | STATUT=ROLLBACK_AUTOMATIQUE
- Si toutes les étapes sont validées jusqu'au dernier palier (100%) sans dépasser le seuil :
CANARY_DEPLOY: app=<nom> -> PROMOTION_100%_SUCCES | STATUT=DEPLOIEMENT_FINALISE | VERSION_ACTIVE=<ver>

Cas d’exemple
CANARY app=payment_svc version=2.4.0 seuil_max=1.00 steps=5,25,50,100 error_rates=0.20,0.35,0.40,0.45
CANARY app=reco_engine version=3.0.0 seuil_max=0.50 steps=10,30,70,100 error_rates=0.10,0.85,1.20,2.00
Résolution attendue
CANARY_DEPLOY: app=payment_svc -> PROMOTION_100%_SUCCES | STATUT=DEPLOIEMENT_FINALISE | VERSION_ACTIVE=2.4.0
CANARY_DEPLOY: app=reco_engine -> ARRET_ANOMALIE_ETAPE=30% (erreur=0.85%/seuil=0.50%) | STATUT=ROLLBACK_AUTOMATIQUE

payment_svc est promu à 100%. reco_engine est stoppé au palier 30% avec rollback.

Deux indices, rédigés en mots
  1. Le déploiement Canari réduit le rayon d’impact (blast radius) en exposant d’abord un petit échantillon d’utilisateurs (ex: 5%).
  2. Interrompre la boucle dès le premier dépassement de seuil.

Exercice 3 — Simulateur de mise à jour progressive Kubernetes (Rolling Update)

Étude de cas Niveau 3 — Raisonnement

Objectif : Simuler le déroulement pas à pas d’un Rolling Update Kubernetes en garantissant les contraintes de maxSurge et maxUnavailable.

Analysez les paramètres du problème pour chaque cas.

Paramètres :
- $N$ : nombre désiré de réplicas en régime stable.
- $S$ (maxSurge) : nombre maximal de pods supplémentaires autorisés au-delà de $N$ ($Total_{max} = N + S$).
- $U$ (maxUnavailable) : nombre maximal de pods indisponibles autorisés ($Dispo_{min} = N - U$).

Algorithme de déroulement par pas :
Initialement, $v1 = N, v2 = 0$.
À chaque pas :
1. On ajoute autant de pods $v2$ que possible sans dépasser $Total_{max} = N + S$ (soit $ajout = \min(S, N - v2)$ pour le premier pas ou pour compléter). Plus précisément : $v2_{cible} = \min(N, v2 + S)$.
2. Une fois les nouveaux $v2$ créés, on détruit des pods $v1$ pour ramener le total à $N$ (ou s'assurer que $v1 + v2 \ge N - U$), c’est-à-dire : supprimer des pods $v1$ jusqu’à ce que $v1 = N - v2$ (ou $v1 = 0$ quand $v2 = N$).
3. Répéter jusqu’à ce que $v1 = 0$ et $v2 = N$.

Afficher :
ROLLING_SPEC: REPLICAS=<N> | MAX_TOTAL=<N+S> | MIN_DISPO=<N-U>
Puis chaque pas :
PAS <k>: v1=<v1>, v2=<v2> (total=<v1+v2>)
Et la conclusion finale :
ETAT_FINAL: v1=0, v2=<N> | SUCCES_ROLLING_UPDATE

Cas d’exemple
ROLLING replicas=4 max_surge=1 max_unavail=0
Résolution attendue
ROLLING_SPEC: REPLICAS=4 | MAX_TOTAL=5 | MIN_DISPO=4
PAS 1: v1=3, v2=1 (total=4)
PAS 2: v1=2, v2=2 (total=4)
PAS 3: v1=1, v2=3 (total=4)
PAS 4: v1=0, v2=4 (total=4)
ETAT_FINAL: v1=0, v2=4 | SUCCES_ROLLING_UPDATE

Avec maxSurge=1 et maxUnavail=0, les pods se remplacent un par un sans interruption.

Deux indices, rédigés en mots
  1. À chaque itération, créer les pods v2 autorisés puis détruire les anciens pods v1 correspondants.
  2. Le nombre de pods disponibles ne doit jamais chuter sous N - U.

5. QCM — niveau examen

Quelle différence fondamentale sépare la Livraison Continue (Continuous Delivery) du Déploiement Continu (Continuous Deployment) ?

En Continuous Delivery, le paquet est prêt et testé, mais un humain déclenche le passage en production. En Continuous Deployment, l’ensemble de la chaîne est automatisé de bout en bout jusqu’à la prod.

Dans une stratégie de déploiement Blue/Green, comment s’effectue la bascule vers la nouvelle version du logiciel ?

L’environnement Green est déployé et vérifié à blanc à côté de l’environnement Blue actif. La bascule se fait en modifiant la cible du répartiteur de charge en une fraction de seconde.

Quel est l’intérêt majeur d’une « Canary Release » (déploiement canari) par rapport à un déploiement massif classique ?

À l’image des canaris autrefois descendus dans les mines de charbon pour détecter le coup de grisou, la Canary Release expose un échantillon d’utilisateurs réels pour tester la fiabilité sans exposer l’ensemble du public.

Pourquoi le patron de conception « Expand and Contract » est-il obligatoire pour faire du Zero-Downtime Deployment sur une base de données ?

Pendant un déploiement sans coupure, des instances de l’ancienne et de la nouvelle version tournent conjointement. Le schéma de base doit donc pouvoir être lu et écrit par les deux versions sans erreur.

Que signifie l’adage DevOps « Deploy is not Release » (Déployer n’est pas Publier) ?

On peut déployer du code en production de manière continue tout en maintenant la fonctionnalité éteinte derrière un Feature Flag jusqu’au moment commercial ou marketing opportun.

Qu’est-ce qu’un « Kill Switch » implémenté via un Feature Flag en exploitation ?

Un Kill Switch permet aux équipes d’astreinte de désactiver à chaud un composant causant une surcharge CPU ou un bogue critique par simple changement de configuration instantané.

Quel risque technique majeur engendre l’accumulation excessive de Feature Flags non nettoyés dans une base de code ?

Chaque drapeau ajoute des branches logiques if/else. Si les vieux flags ne sont pas élagués après généralisation, la combinatoire des tests devient ingérable et des comportements imprévus surviennent.

Dans une stratégie Rolling Update sous Kubernetes, que spécifie le paramètre « maxUnavailable » ?

maxUnavailable garantit qu’un pourcentage suffisant de répliques reste opérationnel en continu pour continuer à absorber le trafic usuel sans dégradation de service.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Effectuer une migration de base de données cassante en une seule passe lors d’un déploiement sans coupure, ignorant le patron Expand and Contract.
  • Confondre le déploiement technique (Deploy) avec la publication fonctionnelle (Release) pour les utilisateurs finaux.
  • Oublier d’implémenter un retour arrière automatique (Rollback) ou un coupe-circuit lors d’un déploiement Canary en cas d’explosion des erreurs HTTP 5xx.
  • Laisser des dizaines de Feature Flags obsolètes s’accumuler dans le code source sans jamais les décommissionner.

7. Méthodologie de résolution

Méthodologie de Déploiement Continu Sans Interruption (Zero Downtime)
  1. Valider la stratégie de packaging immuable et la traçabilité des artéfacts testés en staging.
  2. Concevoir le schéma de base de données selon le patron Expand and Contract pour assurer la compatibilité N / N+1.
  3. Sélectionner la stratégie d’aiguillage : Rolling Update pour l’économie de ressources, Blue/Green ou Canary pour la sécurité.
  4. Configurer l’observation télémétrique temps réel (taux d’erreurs HTTP 5xx, latence P99) sur la version canari.
  5. Programmer un disjoncteur automatique (Circuit Breaker) déclenchant le rollback immédiat en cas d’anomalie.
  6. Découpler le déploiement technique de la visibilité utilisateur via une plateforme centralisée de Feature Flags.

8. Révision active

Résumé essentiel
  • Continuous Delivery requiert une approbation humaine, tandis que Continuous Deployment automatise la prod de bout en bout.
  • Le déploiement sans interruption élimine les maintenances nocturnes en faisant cohabiter temporairement deux versions.
  • Le Blue/Green maintient deux environnements complets et bascule le routeur instantanément avec retour arrière direct.
  • La Canary Release expose un faible pourcentage de trafic réel pour valider le comportement sous charge.
  • Le patron Expand and Contract est indispensable pour faire évoluer une base de données sans bloquer le service.
  • Les Feature Flags séparent le déploiement technique de la publication métier (Deploy ≠ Release).

Checklist de maîtrise

  • Je sais distinguer formellement la Livraison Continue (Delivery) du Déploiement Continu (Deployment).
  • Je sais dimensionner une mise à jour Rolling Update avec maxSurge et maxUnavailable.
  • Je maîtrise l’architecture réseau d’un basculement Blue/Green et de son rollback.
  • Je sais orchestrer les paliers de routage progressif d’une Canary Release.
  • Je sais appliquer les phases du patron Expand and Contract sur une table de base de données relationnelle.
  • Je sais expliquer le fonctionnement d’un Feature Flag et d’un Kill Switch opérationnel.
