Chapitre 4 — Documentation d’API & Référence Technique (OpenAPI / Swagger)

Module 4 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans les architectures modernes orientées microservices et les écosystèmes d’intégration partenaires, l’API est le produit. Une API dépourvue de documentation claire, rigoureusement typée et à jour est vouée à l’abandon : les développeurs tiers perdent des journées entières à deviner la structure des payloads JSON, se heurtent à des erreurs HTTP 500 inexpliquées et multiplient les tickets de support technique. L’approche « API-First » impose de concevoir et valider la spécification OpenAPI 3.0 (Swagger) du contrat d’interface avant même d’écrire la moindre ligne de code back-end. L’ingénieur de Bachelor 3 doit maîtriser la syntaxe OpenAPI 3.0, respecter les conventions REST canoniques, documenter les docstrings de code et déployer des portails interactifs de référence.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. maîtriser la philosophie « API-First » et les avantages contractuels de la spécification d’interface en amont ;
  2. rédiger des spécifications OpenAPI 3.0 complètes : endpoints, méthodes HTTP, paramètres, corps de requêtes et schémas JSON ;
  3. appliquer la sémantique stricte des codes de statut HTTP REST (2xx succès, 4xx erreurs client, 5xx erreurs serveur) ;
  4. documenter le code source via des docstrings normalisées (formats Google, Sphinx, TypeDoc) ;
  5. générer des portails interactifs développeurs exploitant Swagger UI, Redoc et des serveurs de mocks (Prism) ;
  6. développer en Python 3 des validateurs de routes OpenAPI, des auditeurs de docstrings et des vérificateurs de schémas JSON.

1. L’Approche « API-First » & Le Contrat d’Interface Immuable

Historiquement, les développeurs programmaient les routes du serveur puis rédigeaient (ou omettaient de rédiger) la documentation a posteriori (« Code-First »). Cette méthode engendre des dérives majeures : documentation perpétuellement en retard sur le code et travail en silo séquentiel.

La Philosophie API-First

L’API est traitée comme un contrat officiel opposable conclu entre l’équipe fournisseuse et les consommateurs du service. La spécification OpenAPI (format YAML ou JSON) est rédigée, revue et validée collégialement avant toute écriture de code d’implémentation.

Bénéfices Opérationnels Majeurs

  • Développement Parallèle : Le front-end et le back-end avancent simultanément grâce à des serveurs de simulation (mocks) générés à partir du contrat.
  • Génération de Code & SDK : Les stubs de serveurs et les clients typés (TypeScript, Python, Java) sont générés automatiquement via OpenAPI Generator.
  • Zéro Dérive : Le contrat sert de suite de tests de conformité automatisée en intégration continue.

2. La Spécification OpenAPI 3.0 : Anatomie & Conventions REST

La norme OpenAPI 3.0 (maintenue par l’OpenAPI Initiative sous l’égide de la Linux Foundation) formalise la description des APIs REST. Elle s’articule autour de sections fondamentales :

1. En-tête : info & servers

Titre de l’API, version sémantique (ex. version: 1.2.0), description, conditions d’utilisation, contact technique et URLs des environnements cibles (dev, staging, prod).

2. Les Routes : paths

Déclaration des endpoints hiérarchisés au pluriel (ex. /api/v1/clients/{id}), verbes HTTP associés, résumés, tags de regroupement et identifiants uniques operationId.

3. Les Schémas : components

Dictionnaire centralisé des modèles de données réutilisables ($ref: "#/components/schemas/User"), prévenant la duplication et garantissant la cohérence du typage.

Sémantique Canonique des Réponses HTTP

Code HTTP Intitulé officiel Condition exacte d’émission en API REST
200 OK Succès nominal Requête GET, PUT ou PATCH traitée avec succès ; retourne la ressource demandée.
201 Created Création effectuée Requête POST ayant créé une ressource nouvelle ; inclut l’en-tête Location: /api/v1/items/42.
204 No Content Succès sans contenu Requête DELETE ou PUT exécutée sans corps de réponse retourné au client.
400 Bad Request Erreur de validation Corps de requête JSON syntaxiquement invalide ou violation de contraintes métier (champs obligatoires omis).
401 Unauthorized Non authentifié Absence ou expiration du jeton porteur d’authentification (Token JWT / clé d’API invalide).
403 Forbidden Droits insuffisants Client authentifié avec succès mais ne disposant pas du rôle requis (RBAC) pour cette ressource.
404 Not Found Ressource introuvable L’identifiant ciblé dans l’URI n’existe pas dans la base de données.
500 Server Error Panne interne Exception non interceptée côté serveur (crash base de données, bug inattendu) ; ne doit jamais fuiter la stack trace.

3. Documentation du Code Source & Docstrings Normalisées

openapi: 3.0.0\ninfo:\n  title: API Calcul de Remise Commerciale\n  version: 1.0.0\npaths:\n  /remise:\n    post:\n      summary: Calcule le montant net apres application d'un code promotionnel\n      parameters:\n        - name: montant_ht\n          in: query\n          required: true\n          schema:\n            type: number\n        - name: code_promo\n          in: query\n          required: true\n          schema:\n            type: string\n      responses:\n        '200':\n          description: Montant net calcule avec succes
Portails Développeurs Interactifs

Une spécification OpenAPI 3.0 bien rédigée permet d’instancier immédiatement des portails visuels de référence : Swagger UI (offrant un bouton interactif « Try it out » pour tester l’API en direct dans le navigateur) ou Redoc (interface responsive épurée à trois colonnes adoptée par Stripe et Docker). Les développeurs disposent d’une documentation vivante, auto-générée et interactive.

Exercice 1 — Validateur de spécification de route d’API REST (OpenAPI 3.0)

Étude de cas Niveau 1 — Acquisition

Objectif : Vérifier la complétude et la conformité REST d’une déclaration d’endpoint documentée.

Pour chaque cas d’application :
ROUTE_CHECK method=<v> path=<v> codes=<c1,c2,...>.

Règles de validation OpenAPI :
1. method : doit appartenir à GET, POST, PUT, DELETE, PATCH.
2. path : doit commencer par /api/ ou /v (ex. /v1/, /v2/).
3. codes : doit contenir au moins un code de succès (commençant par 2, ex. 200, 201, 204) ET au moins un code d'erreur client ou serveur (commençant par 4 ou 5, ex. 400, 404, 500).

Statut :
- Si tous les critères sont respectés : STATUT=ROUTE_OPENAPI_VALIDE
- Sinon : STATUT=NON_CONFORME (ERREURS=[<erreurs_ordonnees>])
(Ordre d'évaluation : METHODE_INVALIDE, PATH_NON_NORMALISE, CODES_INCOMPLETS).

Afficher :
OPENAPI_CHECK: <METHOD> <path> -> STATUT=<STATUT>

Cas d’exemple
ROUTE_CHECK method=GET path=/api/users codes=200,404,500
Résolution attendue
OPENAPI_CHECK: GET /api/users -> STATUT=ROUTE_OPENAPI_VALIDE

Méthode, chemin et codes 2xx/4xx valides.

Deux indices, rédigés en mots
  1. Vérifier que la liste des codes contient au moins un 2xx et au moins un 4xx/5xx.
  2. Tester la présence de /api/ ou /v au début du chemin.

Exercice 2 — Extracteur et auditeur de docstrings de code (Format Google / Sphinx)

Étude de cas Niveau 2 — Application

Objectif : Vérifier qu’une fonction de code possède une documentation complète de ses paramètres et de sa valeur de retour.

Pour chaque cas d’application des lignes au format :
DOCSTRING_AUDIT fn=<nom> params=<p1,p2,...> doc=<chaine_docstring>.

Règles d'évaluation de la docstring :
- Paramètres documentés : pour chaque paramètre $p_i$ présent dans la liste params, vérifier si le mot p_i: ou p_i ( apparaît dans doc.
- Section retour : le mot Returns: ou Return: ou return: doit apparaître dans doc.

Calculs :
- Paramètres manquants : liste ordonnée des paramètres déclarés dans params mais non trouvés dans la doc.
- Manque retour : si la section de retour est absente, ajouter RETURNS_MANQUANT à la liste des manques.

Qualité :
- Si aucun paramètre manquant et retour présent :
QUALITE=DOCSTRING_COMPLETE_VALIDE
- Sinon :
QUALITE=DOCSTRING_INCOMPLETE (MANQUES=[<manques>])

Afficher :
DOCSTRING_AUDIT: <fn> -> QUALITE=<QUALITE>

Cas d’exemple
DOCSTRING_AUDIT fn=calculer_tva params=montant_ht,taux doc=Calcul du montant. Args: montant_ht (float): base. taux (float): taux. Returns: float
Résolution attendue
DOCSTRING_AUDIT: calculer_tva -> QUALITE=DOCSTRING_COMPLETE_VALIDE

Tous les paramètres et Returns sont documentés.

Deux indices, rédigés en mots
  1. Découper les paramètres et vérifier leur présence dans le texte de la doc.
  2. Vérifier la présence de Returns: ou return:.

Exercice 3 — Validateur de contrat de schéma JSON (JSON Schema Contract)

Étude de cas Niveau 3 — Raisonnement

Objectif : Vérifier la conformité typée d’un payload JSON produit par un endpoint par rapport au schéma contractuel documenté.

Pour chaque cas d’application :
SCHEMA_CHECK endpoint=<path> requis=<c1:type,c2:type,...> payload=<json_string>.

Types supportés dans requis : str, int, bool, float.

Règles de validation :
- Analyser le payload (format JSON valide).
- Pour chaque champ champ:type_attendu déclaré dans requis :
1. Vérifier si champ existe dans l'objet JSON. Si absent :
erreur : CHAMP_MANQUANT:<champ>.
2. Si présent, vérifier la compatibilité du type :
- int : doit être un entier numérique (attention en Python : bool hérite de int, veiller à ce que isinstance(v, int) and not isinstance(v, bool)).
- float : doit être un nombre flottant ou entier.
- str : doit être une chaîne de caractères.
- bool : doit être un booléen (True ou False).
Si le type ne concorde pas : erreur TYPE_INCORRECT:<champ>(attendu=<type>,recu=<type_reel>).

Verdict :
- Si aucune erreur : VERDICT=CONTRAT_RESPECTE
- Sinon : VERDICT=VIOLATION_CONTRAT (ERREURS=[<erreurs>])

Afficher :
CONTRACT_VALIDATION: <endpoint> -> VERDICT=<VERDICT>

Cas d’exemple
SCHEMA_CHECK endpoint=/api/user requis=id:int,nom:str,actif:bool payload={"id": 10, "nom": "Alice", "actif": true}
Résolution attendue
CONTRACT_VALIDATION: /api/user -> VERDICT=CONTRAT_RESPECTE

Tous les champs sont présents avec les bons types.

Deux indices, rédigés en mots
  1. Utiliser json.loads pour parser le payload.
  2. Attention au piège Python : isinstance(True, int) vaut True, vérifier le type bool en priorité.

5. QCM — niveau examen

Quel est le bénéfice principal de l’approche « API-First » dans un projet logiciel moderne ?

API-First contractualise les interfaces en amont : les intégrateurs n’attendent plus la fin du back-end pour commencer à développer leurs applications clientes.

Quel code de statut HTTP une API REST conforme doit-elle retourner lors de la création réussie d’un nouvel utilisateur via une méthode POST ?

Le code 201 Created est le code standard désignant la création effective d’une ressource nouvelle, idéalement accompagné de l’en-tête Location précisant son URI.

Quelle convention de nommage d’URI respecte les bonnes pratiques de conception d’une API RESTful ?

En REST, les URIs désignent des ressources (noms au pluriel), et les verbes HTTP (GET, POST, PUT, DELETE) portent l’action à effectuer.

Dans la spécification OpenAPI 3.0, à quoi sert la section « components/schemas » ?

La section components/schemas est le dictionnaire des types de données : un même schéma (ex. User ou ErrorPayload) est référencé partout via `$ref`.

Quelle différence formelle sépare le code d’erreur HTTP 401 Unauthorized du code 403 Forbidden ?

401 est un problème d’authentification (« Qui êtes-vous ? »). 403 est un problème d’autorisation (« Je sais qui vous êtes, mais vous n’avez pas le droit »).

Pourquoi est-il considéré comme une faute majeure de renvoyer un code 200 OK pour une requête ayant échoué (ex: `{"status": 200, "error": "Compte introuvable"}`) ?

Les couches intermédiaires (API Gateways, clients HTTP) inspectent le code statut : masquer une erreur sous un 200 OK oblige à parser chaque corps JSON et neutralise la supervision.

Dans une docstring Python au format standard Google, quelles sont les trois sections fondamentales couramment attendues ?

Le format Google structure l’explication technique en documentant les arguments (Args), la valeur produite (Returns) et les erreurs potentielles (Raises).

Quel outil permet de transformer une spécification OpenAPI 3.0 en une interface web interactive avec formulaire de test « Try it out » ?

Swagger UI analyse le fichier OpenAPI YAML/JSON et génère dynamiquement une page web ergonomique permettant aux développeurs de tester les requêtes en temps réel.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Renvoyer un code HTTP 200 OK avec un corps JSON contenant `{"error": "User not found"}`, violant la norme REST.
  • Nommer les routes avec des verbes d’action (ex. `/api/getUser/10`) plutôt que des noms pluriels (`/api/users/10`).
  • Omettre de documenter les schémas d’erreur 400 et 404, laissant les développeurs dans l’ignorance des formats de rejet.
  • Laisser la documentation d’API dériver du code de production sans contrôle automatisé en intégration continue.

7. Méthodologie de résolution

Protocole de Conception et de Validation d’une API OpenAPI 3.0
  1. Concevoir le contrat d’interface en amont sur un modèle API-First avec les équipes consommatrices.
  2. Structurer l’arborescence des chemins selon la convention REST plurielle (ex. /api/v1/ressources).
  3. Définir rigoureusement les verbes HTTP appropriés et l’idempotence associée (GET, POST, PUT, DELETE).
  4. Documenter systématiquement les codes de retour nominaux (200, 201) et les codes d’erreur (400, 401, 403, 404, 500).
  5. Factoriser tous les modèles de données dans la section components/schemas pour éliminer la duplication.
  6. Intégrer un linter OpenAPI (Spectral) dans le pipeline CI pour bloquer toute route non documentée.

8. Révision active

Résumé essentiel
  • L’approche API-First garantit que la spécification contractuelle OpenAPI est approuvée avant le codage.
  • La norme OpenAPI 3.0 décrit de façon standardisée les routes, paramètres, requêtes et schémas JSON réutilisables.
  • La sémantique REST impose le respect strict des codes HTTP : 200/201 pour le succès, 400/401/403/404 pour les fautes client.
  • Les docstrings de code (format Google/Sphinx) documentent les arguments, le type de retour et les exceptions levées.
  • Swagger UI et Redoc transforment le contrat OpenAPI en portails de documentation interactive testables en direct.

  • Je sais rédiger une docstring normalisée au format Google.

  • Je sais déployer Swagger UI pour offrir un bac à sable interactif de test.
