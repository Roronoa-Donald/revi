Chapitre 5 — L’Approche Docs-as-Code, Markdown & Générateurs Statiques

Module 5 ≈ 3 h 00 de travail Réservé B3 et plus
Mise en situation

Pendant des décennies, la documentation technique d’entreprise est restée enfermée dans des suites bureautiques propriétaires (Word, PowerPoint) ou des wikis d’entreprise non versionnés (Confluence). Le résultat est universellement déplorable : documents désynchronisés du code de production, schémas vectoriels remplacés par des captures d’écran floues impossibles à modifier, conflits de versions insolubles et absence totale de revue collégiale. Le paradigme « Docs-as-Code » révolutionne la documentation technique en appliquant aux documents les mêmes outils, processus et exigences que pour le code source : fichiers textes bruts en Markdown, versionnement sous Git, schémas textuels déclaratifs avec Mermaid.js, compilation en sites web statiques ultra-rapides (MkDocs, Docusaurus) et déploiement automatisé via des pipelines CI/CD. L’ingénieur de Bachelor 3 doit maîtriser ce workflow moderne pour industrialiser la production documentaire.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. assimiler les fondements et avantages opérationnels de la démarche « Docs-as-Code » ;
  2. maîtriser la syntaxe Markdown avancée (CommonMark, GitHub Flavored Markdown) et l’organisation modulaire de dossiers ;
  3. concevoir des diagrammes d’architecture et de séquence as-code via la syntaxe textuelle Mermaid.js ;
  4. configurer et structurer un générateur de site statique documentaire (MkDocs avec le thème Material, Docusaurus, Sphinx) ;
  5. automatiser la compilation, la validation et la publication continue de la documentation dans une forge logicielle (GitHub Actions, GitLab CI) ;
  6. développer en Python 3 des linters de hiérarchie Markdown, des validateurs de connectivité Mermaid et des générateurs d’arborescence YAML.

1. Le Paradigme « Docs-as-Code » : Principes & Rupture Opérationnelle

L’approche Docs-as-Code consiste à traiter la documentation technique avec la même rigueur, les mêmes outils et les mêmes flux de travail que le code applicatif.

L’Ancien Monde : Fichiers Binaires & Wikis Isolés

  • Fichiers .docx ou .pdf stockés sur des répertoires partagés sans historique granulaire.
  • Différences illisibles : impossible de voir ce qui a changé entre deux versions d’un fichier binaire.
  • Déconnexion totale : le développeur modifie le code dans son IDE mais oublie de mettre à jour le wiki distant.
  • Goulots d’étranglement et perte de traçabilité des relectures.

Le Monde Moderne : Docs-as-Code

  • Format texte brut : Fichiers Markdown (.md) ou AsciiDoc (.adoc) légers et interopérables.
  • Dépôt Git unique : La documentation vit dans le même dépôt (monorepo ou dossier docs/) que le code.
  • Revue par Pull Request : Toute modification documentaire est soumise à une PR, commentée ligne par ligne et relue par les pairs.
  • Intégration continue (CI) : Tests de syntaxe, détection des liens cassés et déploiement automatisé à chaque commit.

2. Syntaxe Markdown Avancée (GFM) & Structuration Documentaire

Le format Markdown s’est imposé comme le standard de facto de la documentation textuelle. La variante GitHub Flavored Markdown (GFM) apporte des extensions indispensables à l’ingénierie logicielle.

Hiérarchie Stricte des Titres

Un seul titre de niveau 1 (# Titre Principal) par page. Les sous-sections s’enchaînent obligatoirement sans sauter de niveau (ex. ## Niveau 2 puis ### Niveau 3). Sauter d’un # à un ### est une erreur d’accessibilité et de linter.

Blocs de Code Typés

Tout extrait de code ou commande console doit être encapsulé dans un bloc clôturé par trois backticks avec indication explicite du langage (```python, ```bash, ```json), garantissant la coloration syntaxique et l’extraction automatisée.

Tableaux & Callouts

Tableaux alignés avec barres verticales (|) et tirets. Utilisation des blocs d’alerte standardisés (> [!NOTE], > [!WARNING], > [!IMPORTANT]) pour faire ressortir les consignes de sécurité ou d’exploitation.

3. Diagrammes-as-Code avec Mermaid.js : Clarté & Maintenabilité

Dans un projet Docs-as-Code, intégrer une image PNG ou JPEG d’un schéma réseau ou d’une architecture logicielle est un anti-patron critique. Dès que l’architecture évolue, l’image devient obsolète car personne ne retrouve le fichier source original du logiciel de dessin.

Mermaid.js résout ce problème en permettant d’écrire des diagrammes sous forme de code texte déclaratif, directement interprété et rendu par GitHub, GitLab et les générateurs statiques modernes.

Exemple : Graphe d’Architecture Réseau

```mermaid
graph TD
  Client[Navigateur Web] -->|HTTPS 443| LB[Reverse Proxy Nginx]
  LB -->|Port 8000| App1[Service API A]
  LB -->|Port 8000| App2[Service API B]
  App1 -->|TCP 5432| BDD[(Cluster PostgreSQL)]
  App2 -->|TCP 5432| BDD
```

Avantages Incomparables

  • Diff Git Parfait : Lorsqu’un nœud réseau ou un port est modifié, le diff Git montre exactement la ligne de texte modifiée dans la Pull Request.
  • Maintenance Pérenne : N’importe quel ingénieur de l’équipe peut mettre à jour le schéma en 30 secondes en modifiant le fichier texte.
  • Accessibilité & Recherche : Le texte des libellés du schéma est indexable par les moteurs de recherche interne.

4. Moteurs de Sites Statiques (SSG) : MkDocs, Material & Docusaurus

Les fichiers Markdown bruts stockés dans un dépôt Git sont compilés par un Générateur de Site Statique (Static Site Generator - SSG) pour produire un portail documentaire HTML/CSS/JS complet, réactif, indexé et consultable sur le web interne ou public.

MkDocs + Material for MkDocs

Le standard incontournable de l’écosystème Python et DevOps. Écrit en Python, il se configure via un fichier central mkdocs.yml. Le thème Material offre une recherche plein texte instantanée, le mode sombre/clair automatique, la coloration syntaxique et le support natif de Mermaid.

Docusaurus (Meta)

Basé sur Node.js et React. Idéal pour les portails développeurs hautement interactifs nécessitant des composants React dynamiques (MDX), le versionnement de documentation multi-releases et l’internationalisation (i18n).

Sphinx (Python / C++)

L’outil historique de référence pour documenter les bibliothèques et frameworks techniques. Supporte reStructuredText et Markdown (MyST), et extrait automatiquement les docstrings du code source pour générer les références de classes et méthodes.

Structure du fichier mkdocs.yml
Le fichier mkdocs.yml définit les métadonnées du site et son arborescence de navigation : 
site_name: Portail Documentation Infrastructure Cloud
theme:
  name: material
  features:
    - search.suggest
    - navigation.tabs
nav:
  - Accueil: index.md
  - Architecture: architecture.md
  - Guides d’Exploitation:
    - Sauvegardes: runbooks/backup.md
    - Procédure de Bascule: runbooks/failover.md

5. Industrialisation en Intégration Continue (CI/CD)

La puissance du Docs-as-Code réside dans son automatisation au sein des pipelines de la forge logicielle (GitHub Actions, GitLab CI/CD) :

1. Contrôles Automatisés (Linters)

À chaque Pull Request, le runner CI vérifie que le document respecte les standards avant toute fusion :

  • markdownlint : Validation de la syntaxe et de la hiérarchie des titres.
  • lychee / markdown-link-check : Détection immédiate des liens internes ou externes brisés.
  • Vale : Linter de style éditorial vérifiant la clarté et le respect de la charte de rédaction technique.

2. Déploiement & Hébergement Statique

Dès que la PR est approuvée et fusionnée sur la branche main :

  • La commande mkdocs build --strict compile les pages HTML statiques. En mode strict, le moindre avertissement fait échouer le pipeline.
  • Les fichiers générés sont automatiquement déployés sur GitHub Pages, GitLab Pages, AWS S3 / CloudFront ou un conteneur Nginx interne.
  • Zéro maintenance de serveur applicatif : performance et sécurité maximales.

6. Exercices de code

Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

Exercice 1 — Linter de hiérarchie des titres Markdown (Structure Docs-as-Code)

Python Niveau 1 — Acquisition

Objectif : Vérifier la rigueur structurelle d’un document Markdown : H1 unique, progression de niveau sans saut abrupt et absence de titre vide.

Le script lit sur l'entrée standard un en-tête suivi de lignes de titres Markdown :
MD_DOC nom=<nom> titres=<t1|t2|...>.
Chaque titre $t_i$ commence par un ou plusieurs # suivis du texte (ex. # Titre, ## Section).

Règles de validation :
1. Nombre de H1 : le document doit comporter exactement un titre de niveau 1 (# ). Si 0 ou > 1, ajouter l'anomalie H1_NON_UNIQUE.
2. Titres vides : aucun titre ne doit être vide après les # (ex. ## sans texte). Si détecté, ajouter TITRE_VIDE.
3. Sauts de niveau : le niveau d'un sous-titre ne doit jamais dépasser le niveau précédent de plus de 1 (ex. passer de # à ### est interdit car le niveau 2 est sauté). Si détecté, ajouter SAUT_DE_NIVEAU_INTERDIT.

Statut :
- Si aucune anomalie : STATUT=STRUCTURE_MARKDOWN_VALIDE
- Sinon : STATUT=NON_CONFORME (ANOMALIES=[<anomalies_uniques_ordonnees>])
(Ordre : H1_NON_UNIQUE, TITRE_VIDE, SAUT_DE_NIVEAU_INTERDIT).

Afficher :
MD_LINTER: <nom> -> STATUT=<STATUT>

Entrée du programme
MD_DOC nom=guide.md titres=# Guide d'installation|## Prérequis|### Système|## Configuration
Sortie attendue
MD_LINTER: guide.md -> STATUT=STRUCTURE_MARKDOWN_VALIDE

Un seul H1, pas de titre vide, progression 1 -> 2 -> 3 -> 2 valide.

Deux indices, rédigés en mots
  1. Compter les symboles # initiaux pour trouver le niveau du titre.
  2. Suivre le niveau précédent pour vérifier qu’il n’y a pas de saut de niveau supérieur à +1.

Exercice 2 — Validateur de diagramme textuel Mermaid (Docs-as-Code)

Python Niveau 2 — Application

Objectif : Vérifier la validité de l’en-tête d’un diagramme Mermaid et la connectivité globale de ses nœuds.

Le script lit sur l'entrée standard :
MERMAID_DIAG nom=<nom> type=<type> aretes=<a1-->b1,a2-->b2,...>.

Règles de validation :
- Types autorisés (insensible à la casse) : graph TD, graph LR, flowchart TD, flowchart LR.
Si le type est différent, VERDICT=TYPE_DIAGRAMME_INVALIDE.
- Extraire l'ensemble des nœuds distincts participants aux arêtes (format A-->B).
- Compter le nombre de nœuds uniques $N_{noeuds}$ et le nombre d'arêtes déclarées $N_{aretes}$.
- Vérification de connectivité : un graphe orienté cohérent possède au minimum $N_{aretes} \ge N_{noeuds} - 1$.
Si $N_{aretes} < N_{noeuds} - 1$ : VERDICT=GRAPHE_POTENTIELLEMENT_DISJOINT (NOEUDS=<N>, ARETES=<M>).
Sinon : VERDICT=DIAGRAMME_VALIDE (NOEUDS=<N>, ARETES=<M>).

Afficher :
MERMAID_AUDIT: <nom> -> VERDICT=<VERDICT>

Entrée du programme
MERMAID_DIAG nom=flux_auth type=flowchart TD aretes=Client-->Passerelle,Passerelle-->AuthService,AuthService-->BDD
Sortie attendue
MERMAID_AUDIT: flux_auth -> VERDICT=DIAGRAMME_VALIDE (NOEUDS=4, ARETES=3)

4 nœuds, 3 arêtes : arbre connexe valide.

Deux indices, rédigés en mots
  1. Extraire les nœuds de part et d’autre de "-->".
  2. Vérifier le type parmi les 4 valeurs autorisées.

Exercice 3 — Générateur d’arborescence de navigation MkDocs / Docusaurus (YAML Nav)

Python Niveau 3 — Raisonnement

Objectif : Convertir une liste de fichiers Markdown hiérarchisés en section de navigation conforme pour un générateur statique.

Le script lit sur l'entrée standard :
NAV_GEN module=<nom_module> pages=<p1.md,p2.md,...>.

Traitement :
- Trier la liste des fichiers pages par ordre alphabétique.
- Produire une structure d'arborescence de navigation au format conventionnel suivant :
NAV_OUTPUT: - <nom_module>: [<pages_triees_separees_par_virgule>] (TOTAL=<N>).

Exemple :
Si module=Architecture et pages=overview.md,infra.md,reseau.md :
Pages triées : infra.md, overview.md, reseau.md
Affichage :
NAV_OUTPUT: - Architecture: [infra.md, overview.md, reseau.md] (TOTAL=3)

Entrée du programme
NAV_GEN module=Guide pages=installation.md,demarrage.md,faq.md
Sortie attendue
NAV_OUTPUT: - Guide: [demarrage.md, faq.md, installation.md] (TOTAL=3)

Pages triées par ordre alphabétique strict.

Deux indices, rédigés en mots
  1. Trier les fichiers avec sorted().
  2. Afficher le total de pages entre parenthèses.

7. QCM — niveau examen

Quel est le principe directeur fondamental de l’approche « Docs-as-Code » ?

Docs-as-Code applique les pratiques logicielles éprouvées (Git, Pull Requests, linters, pipelines CI/CD) à la rédaction documentaire.

Pourquoi est-il considéré comme une faute de hiérarchie de faire suivre immédiatement un titre de niveau 1 (#) par un sous-titre de niveau 3 (###) en Markdown ?

Sauter un niveau hiérarchique (de h1 à h3 sans h2) crée un trou dans l’arborescence du document, violant les règles WCAG d’accessibilité et déclenchant des erreurs de linters.

Quel est l’avantage décisif d’un diagramme Mermaid.js par rapport à une image PNG intégrée dans une documentation technique ?

Un schéma texte Mermaid se versionne sous Git : un changement de topologie se relit ligne par ligne lors d’une Pull Request et se modifie directement dans l’éditeur.

Dans un projet utilisant MkDocs, quel fichier central définit les métadonnées du site, les extensions et l’arborescence de navigation ?

Le fichier `mkdocs.yml` est le fichier de configuration principal d’un projet MkDocs, contenant notamment la clé `nav` qui structure la navigation du site.

À quoi sert l’argument `--strict` lors de l’exécution de la commande de build `mkdocs build --strict` dans un pipeline d’intégration continue ?

L’option `--strict` transforme les avertissements (warnings) en erreurs bloquantes, garantissant qu’aucun lien brisé ou problème de configuration ne passe en production.

Parmi les propositions suivantes, laquelle décrit correctement le rôle d’un outil comme « Vale » dans une chaîne de CI/CD documentaire ?

Vale est un linter de prose (style linter) permettant d’appliquer automatiquement des guides de style rédactionnel (Google Style, Microsoft Style, règles personnalisées).

Quelle balise d’encadrement permet de déclarer un bloc de code Python avec coloration syntaxique en Markdown GFM ?

Trois backticks suivis de l’identifiant du langage (```python) forment la syntaxe standard pour les blocs de code clôturés avec coloration syntaxique.

Pourquoi est-il fortement recommandé d’héberger la documentation dans le même dépôt Git que le code de l’application (dossier docs/) plutôt que dans un wiki externe séparé ?

Conserver la documentation dans le même dépôt permet de coupler les commits de code et de documentation dans la même Pull Request, évitant la dérive documentaire.

8. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Insérer des captures d’écran d’architecture au lieu de diagrammes textuels Mermaid, rendant toute mise à jour ultérieure impossible.
  • Sauter des niveaux de titres Markdown (ex: passer d’un titre `#` directement à un sous-titre `###`), rompant l’accessibilité.
  • Conserver la documentation dans un wiki externe non synchronisé avec les branches de code du dépôt Git.
  • Ignorer les erreurs de compilation du générateur statique au lieu d’activer le mode strict (`--strict`) en intégration continue.

9. Méthodologie de résolution

Méthodologie de Déploiement d’un Projet Docs-as-Code
  1. 1. Initialiser l’arborescence documentaire : Créer un dossier `docs/` à la racine du dépôt Git du projet avec un fichier `index.md` servant de page d’accueil.
  2. 2. Rédiger en Markdown strict : Respecter la hiérarchie des niveaux de titres (# puis ## puis ###), typager chaque bloc de code et insérer les diagrammes Mermaid.js sous forme textuelle.
  3. 3. Structurer la navigation : Déclarer l’arborescence dans le fichier de configuration `mkdocs.yml` (ou `docusaurus.config.js`) en organisant les rubriques de manière logique pour l’utilisateur.
  4. 4. Tester localement : Lancer le serveur de développement en direct (`mkdocs serve`) avec rechargement à chaud (live-reload) pour valider le rendu visuel dans le navigateur.
  5. 5. Configurer la validation CI : Écrire un workflow GitHub Actions / GitLab CI exécutant un linter Markdown et un vérificateur de liens à chaque pull request.
  6. 6. Déployer en continu : Configurer le job de publication finale (`mkdocs gh-deploy` ou copie S3) lors de la fusion sur la branche principale.

10. Révision active

Résumé essentiel
  • Le Docs-as-Code traite la documentation avec les mêmes standards que le code : texte brut versionné sous Git, revues par Pull Requests et tests automatisés en CI/CD.
  • Le format Markdown (GFM) garantit la lisibilité native en texte brut tout en offrant des fonctionnalités riches (code typé, tableaux, alertes).
  • La hiérarchie des titres Markdown doit être rigoureuse : un seul titre h1 par page, sans saut de niveau (ex: passer directement de h1 à h3 est une erreur).
  • Mermaid.js permet de coder des diagrammes d’architecture et de séquence directement en texte, facilitant les revues de diffs Git et bannissant les captures d’écran obsolètes.
  • Les générateurs statiques comme MkDocs (thème Material) et Docusaurus compilent le Markdown en sites web rapides, ergonomiques, avec recherche plein texte instantanée.
  • L’intégration continue (CI) garantit la qualité pérenne : compilation en mode strict (`--strict`), validation de la syntaxe par linters et détection des liens rompus.

Checklist de maîtrise

  • La documentation réside-t-elle dans le même dépôt Git que le code dans un sous-dossier dédié (ex: `docs/`) ?
  • Chaque page Markdown comporte-t-elle un unique titre de niveau 1 (#) sans rupture hiérarchique ?
  • Tous les extraits de code et commandes sont-ils encadrés par des blocs typés avec leur langage ?
  • Les schémas d’architecture et diagrammes de flux sont-ils rédigés en syntaxe textuelle Mermaid.js ?
  • L’arborescence du site est-elle explicitement configurée dans le fichier `mkdocs.yml` sous la clé `nav` ?
  • Un pipeline CI/CD vérifie-t-il la compilation stricte et l’absence de liens cassés à chaque commit ?
