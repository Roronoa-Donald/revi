Examens Blancs & Épreuves Corrigées de Sécurité Réseau & Pare-feux B3

Deux épreuves d’évaluation complètes conformes aux exigences professionnelles et académiques de niveau Bachelor 3 / Licence 3 (Support Caleb Benaja).

Épreuve 1 : Contrôle Continu (CC) — Durée 1 h 30 (Barème sur 20 points)

Sujet du Contrôle Continu — Fondements, Suivi d’État TCP, Table conntrack & Politiques ACLs

Partie 1 : Fondements Théoriques & Évolution des Pare-feux (6 points)

  1. Distinguez précisément le filtrage de paquets sans état (Stateless / Génération 1) du filtrage avec suivi d’état (Stateful Inspection / Génération 2). Expliquez pourquoi un pare-feu stateless est incapable de bloquer une attaque par injection de paquets ACK forgés simulant une session déjà ouverte. (3 pts)
  2. Définissez les acronymes UTM (Unified Threat Management) et NGFW (Next-Generation Firewall). Précisez deux différences majeures entre une appliance UTM et un NGFW d’entreprise opérant en coupure de flux haute disponibilité. (3 pts)

Partie 2 : Mécanique de Suivi de Session TCP & Détection d’Anomalies (7 points)

  1. Détaillez la succession des paquets et des drapeaux (flags) lors de l’établissement d’une connexion TCP à 3 voies (3-Way Handshake) selon la RFC 793. Indiquez l’état attribué à chaque étape par le module netfilter conntrack (NEW, ESTABLISHED). (3 pts)
  2. Un analyseur réseau capte des paquets entrants avec les combinaisons de drapeaux suivantes :
    a) flags=FIN,PSH,URG
    b) flags=NONE (aucun drapeau)
    c) flags=SYN,FIN.
    Identifiez la nature exacte de chaque sonde/attaque, le logiciel offensif classiquement employé (ex: options de scan Nmap) et expliquez pourquoi le pare-feu doit obligatoirement les DROP avec le statut INVALID. (4 pts)

Partie 3 : Politiques de Sécurité, Ordonnancement d’ACLs & Rule Shadowing (7 points)

  1. Expliquez le principe d’évaluation First-Match-Wins et la règle de sécurité implicite Default DROP (ou White-listing). Pourquoi une règle permissive placée trop haut dans le jeu de règles représente-t-elle une faille critique ? (3 pts)
  2. Soit la politique de filtrage suivante ordonnée de haut en bas :
    - Règle 1 : DENY TCP src=ANY dst=10.0.0.0/24 dport=ANY
    - Règle 2 : PERMIT TCP src=192.168.1.50 dst=10.0.0.10 dport=443
    - Règle 3 : DENY TCP src=192.168.1.0/24 dst=10.0.0.10 dport=22
    Identifiez les anomalies de configuration dans ce jeu de règles (masquage de règle / Rule Shadowing et redondance). Proposez une réorganisation corrigée et optimale. (4 pts)

Corrigé Partie 1 (6 points)

  • Stateless vs Stateful (3 pts) : Le filtrage stateless examine chaque paquet de manière totalement isolée en couches 3 et 4 (IP source/dest, port source/dest) sans mémoire du contexte. Le filtrage stateful maintient une table d’état en mémoire (table conntrack) mémorisant l’historique des échanges. Un pirate peut facilement envoyer un paquet TCP avec le drapeau ACK activé (ACK scan) vers un pare-feu stateless : le pare-feu pensant qu’il s’agit du retour d’une connexion initiée de l’intérieur laisse passer le paquet. Le pare-feu stateful vérifie sa table : aucune entrée correspondante n’existant, le paquet orphelin est rejeté avec l’état INVALID.
  • UTM vs NGFW (3 pts) : L’UTM centralise sur une même boîte matérielle diverses briques hétérogènes (filtrage, antivirus, antispam, VPN) convenant idéalement aux PME mais avec des goulets d’étranglement de performances dès que tous les modules sont activés. Le NGFW (ex: Palo Alto Networks, Fortinet FortiGate haut débit) intègre de façon native et parallélisée un moteur d’inspection monocycle (Single-Pass Architecture), capable de décoder les applications de niveau 7 (App-ID), d’identifier les utilisateurs (User-ID) et d’analyser le contenu sans dégradation majeure de latence en cœur de réseau.

Corrigé Partie 2 (7 points)

  • Handshake 3-voies & conntrack (3 pts) :
    1. Client -> Serveur : paquet avec drapeau SYN. Conntrack alloue l’entrée avec l’état NEW (phase SYN_SENT).
    2. Serveur -> Client : réponse avec drapeaux SYN,ACK. Conntrack maintient NEW (phase SYN_RCVD).
    3. Client -> Serveur : confirmation avec drapeau ACK. Conntrack bascule la session à l’état ESTABLISHED. Tout paquet DATA ultérieur est alors admis sous l’état ESTABLISHED.
  • Identification des sondes furtives (4 pts) :
    a) FIN,PSH,URG : Xmas Tree Scan (Nmap option -sX). Fait clignoter le paquet comme un sapin de Noël pour forcer une réponse RST des ports fermés selon la RFC 793.
    b) flags=NONE : Null Scan (Nmap option -sN). Aucun drapeau actif, interdit en fonctionnement normal.
    c) SYN,FIN : SYN-FIN Anomaly. Combinaison paradoxale demandant d’ouvrir et de fermer la connexion simultanément, employée pour tromper les vieux moteurs d’inspection.
    Ces paquets doivent tous être rejetés (DROP) avec le statut INVALID car ils violent les règles élémentaires du protocole TCP et dénotent une tentative hostile de cartographie réseau.

Corrigé Partie 3 (7 points)

  • First-Match-Wins & Default DROP (3 pts) : Les règles sont lues séquentiellement de haut en bas ; la première correspondance met fin à l’évaluation. La politique Default DROP garantit que tout ce qui n’est pas explicitement autorisé est bloqué (principe du moindre privilège). Si une règle trop large (ex: PERMIT ANY) est placée en haut, aucune des restrictions placées plus bas ne s’appliquera, créant une faille béante.
  • Détection d’anomalies et correction (4 pts) :
    - La Règle 1 bloque tout trafic TCP vers le sous-réseau 10.0.0.0/24.
    - Par conséquent, la Règle 2 (PERMIT vers 10.0.0.10:443) est masquée (Shadowed) par la Règle 1 : elle ne sera jamais exécutée car tout paquet vers 10.0.0.10 sera déjà bloqué par la Règle 1.
    - La Règle 3 (DENY port 22) est redondante avec la Règle 1 car la Règle 1 bloque déjà tous les ports vers 10.0.0.0/24.
    Ordre corrigé et assaini :
    1. PERMIT TCP src=192.168.1.50 dst=10.0.0.10 dport=443 (Exception spécifique autorisée en premier)
    2. DENY TCP src=ANY dst=10.0.0.0/24 dport=ANY (Règle générale de blocage du sous-réseau)
    (La règle 3 est supprimée car superflue).

Épreuve 2 : Examen Terminal (ET) — Durée 2 h 00 (Barème sur 20 points)

Sujet de l’Examen Terminal — DMZ, Topologies Multi-Pare-feux, L7/DPI, Linux Netfilter & SIEM

Partie 1 : Architecture DMZ, Topologies & Matrice des Flux (7 points)

  1. Définissez le concept de Zone Démilitarisée (DMZ). Énoncez la règle d’or absolue concernant les flux initiés entre la DMZ et le réseau local interne LAN. Pourquoi cette règle est-elle vitale en cas de compromission d’un serveur web ? (3 pts)
  2. Comparez une architecture à pare-feu unique à trois interfaces (Triple-Homed Screened Subnet) et une architecture à double pare-feu en cascade (Back-to-Back). Justifiez l’intérêt de choisir deux constructeurs différents (hétérogénéité) pour le pare-feu frontal et le pare-feu interne. (4 pts)

Partie 2 : Filtrage Applicatif L7, Inspection SNI & Protection anti-DoS (6 points)

  1. Comment un pare-feu nouvelle génération inspecte-t-il les flux HTTPS chiffrés sans rupture de chiffrement (sans déchiffrement SSL man-in-the-middle) ? Expliquez le rôle du champ SNI (Server Name Indication) dans le handshake TLS. (3 pts)
  2. Expliquez le fonctionnement du Deep Packet Inspection (DPI) pour intercepter une attaque par injection SQL (SQLi) ou Cross-Site Scripting (XSS). Donnez deux exemples de motifs de signatures recherchés dans la charge utile HTTP. (3 pts)

Partie 3 : Déploiement Linux Netfilter (iptables/nftables) & Réponse SIEM (7 points)

  1. Écrivez les commandes complètes en syntaxe iptables pour :
    a) Définir la politique par défaut de la chaîne INPUT à DROP.
    b) Autoriser les connexions de retour déjà établies (état ESTABLISHED, RELATED).
    c) Autoriser le trafic web entrant HTTPS (port 443) sur l’interface eth0. (3 pts)
  2. Traduisez les mêmes règles de filtrage en syntaxe moderne nftables. (2 pts)
  3. Expliquez l’intégration d’un pare-feu avec un outil de type Fail2ban ou un orchestrateur SOAR relié à un SIEM pour contrer les attaques par force brute SSH. (2 pts)

Corrigé type & Barème détaillé de l’Examen Terminal

Corrigé Partie 1 (7 points)

  • DMZ & Règle d’or (3 pts) : La DMZ est une zone réseau tampon isolée hébergeant les serveurs accessibles depuis Internet (serveur web, relais messagerie, DNS public). La règle d’or absolue : aucune connexion ne doit jamais pouvoir être initiée depuis la DMZ vers le réseau interne LAN (seules les réponses aux requêtes initiées par le LAN vers la DMZ sont permises). Si un pirate exploite une faille zero-day sur le serveur web en DMZ et obtient un shell distant, il se retrouve bloqué dans la DMZ et ne peut pas rebondir vers les postes de travail ou les contrôleurs de domaine Active Directory du LAN.
  • Triple-Homed vs Back-to-Back hétérogène (4 pts) :
    - Triple-Homed : un seul boîtier avec 3 interfaces (LAN, WAN, DMZ). Économique et simple, mais présente un point unique de défaillance (SPOF) matériel et logiciel. Si le boîtier plante ou si une vulnérabilité critique touche son firmware, toute l’entreprise est compromise.
    - Back-to-Back : deux pare-feux distincts encadrant la DMZ. Le pare-feu frontal filtre le trafic Internet vers la DMZ ; le pare-feu interne filtre le trafic DMZ vers le LAN.
    - Intérêt de l’hétérogénéité : en choisissant deux fabricants différents (ex: Fortinet en frontal et Palo Alto ou Cisco en interne), si une vulnérabilité zero-day touche le premier équipement, elle n’affectera pas le second. Le pirate qui franchit le premier pare-feu doit trouver une seconde faille totalement différente pour atteindre le LAN (défense en profondeur maximale).

Corrigé Partie 2 (6 points)

  • Inspection SNI TLS (3 pts) : Lors de la négociation TLS (handshake), le client envoie un paquet en clair Client Hello avant que le canal chiffré ne soit établi. Ce paquet contient l’extension SNI (Server Name Indication) qui mentionne le nom de domaine complet (FQDN) du serveur distant visé (ex: banque-phishing.evil). Le NGFW lit cette information en clair, la confronte à sa base de données d’URL et de réputation catégorielle, et peut interrompre la connexion immédiatement (DROP ou TCP RST) avant même l’échange des clés de chiffrement.
  • Deep Packet Inspection L7 (3 pts) : Le moteur DPI réassemble les segments TCP pour analyser la charge utile applicative HTTP (URL, paramètres GET, corps POST). Il compare le flux avec une base de signatures d’attaques et d’expressions régulières :
    - Pour l’injection SQL : motifs UNION SELECT, ' OR '1'='1, SLEEP(, DROP TABLE.
    - Pour le XSS : balises <script>, gestionnaires d’événements onerror=, protocole javascript:.
    Dès qu’un motif suspect est identifié, la requête est rejetée avec un code HTTP 403 Forbidden et une alerte de sécurité est envoyée au SIEM.

Corrigé Partie 3 (7 points)

  • Commandes iptables (3 pts) :
    a) iptables -P INPUT DROP
    b) iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
    c) iptables -A INPUT -i eth0 -p tcp --dport 443 -j ACCEPT
  • Commandes nftables (2 pts) :
    nft add table inet filter
    nft add chain inet filter input { type filter hook input priority 0; policy drop; }
    nft add rule inet filter input ct state established,related accept
    nft add rule inet filter input iifname "eth0" tcp dport 443 accept
  • Intégration SIEM & Fail2ban (2 pts) : Les logs d’authentification (ex: /var/log/auth.log) sont analysés en temps réel. Lorsque Fail2ban détecte plus de 3 ou 5 échecs consécutifs depuis une même adresse IP dans une fenêtre de quelques minutes, il injecte dynamiquement une règle de bannissement dans netfilter (ex: nft add element inet filter blacklist { IP }). Le SIEM centralise ces événements pour corréler les attaques distribuées et ordonner le bannissement sur l’ensemble des pare-feux du parc informatique via des playbooks SOAR automatisés.
