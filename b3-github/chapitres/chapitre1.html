Chapitre 1 — Modèle Objet Git & Arborescence Interne

Module 1 ≈ 2 h 45 de travail Accès libre
Mise en situation

Pour la majorité des utilisateurs débutants, Git apparaît comme une boîte noire mystérieuse où s’enchaînent des commandes mnémotechniques sans compréhension des structures sous-jacentes. Pourtant, au niveau Bachelor 3, l’ingénieur logiciel doit appréhender Git pour ce qu’il est réellement : un système de fichiers adressable par contenu (Content-Addressable Storage) doublé d’une base de données orientée graphe (Directed Acyclic Graph - DAG). Chaque fichier, chaque dossier, chaque commit et chaque étiquette est sérialisé en un objet immuable indexé par son empreinte cryptographique. Face à un dépôt corrompu, une défaillance de synchronisation ou l’écriture d’outils d’automatisation CI/CD, la maîtrise des commandes de plomberie (plumbing commands) et de l’arborescence interne du répertoire .git est la clé qui sépare l’utilisateur passif de l’expert en ingénierie logicielle.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. analyser la structure détaillée et le rôle de chaque composant du répertoire interne .git (objects, refs, HEAD, index) ;
  2. comprendre le principe du stockage adressable par contenu et le calcul des identifiants cryptographiques SHA-1 et SHA-256 ;
  3. distinguer la structure, les métadonnées et le rôle des quatre types d’objets fondamentaux : blob, tree, commit et annotated tag ;
  4. démontrer le fonctionnement de l’arbre de Merkle et l’immuabilité cryptographique de l’historique de versions ;
  5. manipuler les commandes de plomberie de bas niveau (git hash-object, git cat-file, git ls-tree, git rev-parse) ;
  6. développer en Python 3 des parseurs de structures Git internes, des calculateurs de hashes conformes et des résolveurs de références.

1. Anatomie Interne du Dossier .git & Système Adressable par Contenu

Lors de l’initialisation d’un dépôt via git init, Git génère un répertoire masqué .git/ contenant l’intégralité de la base de données de versionnage. Contrairement aux systèmes centralisés (SVN, CVS) qui stockent des deltas successifs fichier par fichier sur un serveur distant, Git conserve des instantanés complets (snapshots) au sein d’une base de données clé-valeur locale.

Architecture du Dossier .git/

  • HEAD : Référence symbolique pointant vers la branche active courante (ex: ref: refs/heads/main).
  • objects/ : Magasin d’objets adressés par leur empreinte SHA-1/SHA-256. Organisé en sous-dossiers de 2 caractères hexadécimaux pour optimiser les performances des systèmes de fichiers.
  • refs/ : Pointeurs vers des commits (branches locales dans refs/heads/, branches distantes dans refs/remotes/, étiquettes dans refs/tags/).
  • index : Fichier binaire représentant la zone de transit (Staging Area), faisant le lien entre la copie de travail et la base d’objets.

Principe de l’Adressage par Contenu

Une clé dans la base d’objets est la valeur de hachage cryptographique du contenu de l’objet préfixé par son en-tête. La clé détermine l’emplacement physique :

Un objet de hash 3b18e512... sera sauvegardé dans le fichier .git/objects/3b/18e512... compressé avec l’algorithme DEFLATE (zlib).

Ce paradigme garantit une déduplication native : deux fichiers au contenu identique, quel que soit leur nom ou leur emplacement, partagent exactement la même entrée dans la base.

2. Les Quatre Types Fondamentaux d’Objets Git

La base de données Git ne gère que quatre types d’objets atomiques, chacun ayant une structure et une responsabilité précises dans la reconstruction du projet :

Type d’ObjetEn-tête & Format BrutContenu StockéComportement vis-à-vis des Métadonnées
blob blob <taille>\0<octets> Contenu brut du fichier (texte, image, binaire). Aucune métadonnée : ni nom de fichier, ni date, ni permissions d’accès Unix ne sont conservés dans un blob.
tree tree <taille>\0[entrées...] Liste ordonnée de références représentant un dossier. Chaque entrée contient le mode Unix (100644 pour standard, 100755 pour exécutable, 040000 pour sous-dossier), le type, le hash de l’objet cible et le nom du fichier.
commit commit <taille>\0[en-têtes + message] Instantané de projet avec traçabilité complète. Pointe vers l’arbre racine (tree), les commits parents (0 pour le commit initial, 1 pour standard, 2+ pour fusion), l’auteur, le committer et le message.
tag tag <taille>\0[cible + tagger + msg] Objet d’étiquette annotée immuable. Pointe vers un objet cible (généralement un commit), contient l’identifiant du signataire, un horodatage et optionnellement une signature cryptographique GPG.

3. Cryptographie du Graphe : Hachage SHA, Immuabilité & Arbre de Merkle

La rigueur de Git découle de son organisation sous forme d’arbre de Merkle (Merkle Tree). Toute modification d’un seul caractère dans un fichier modifie son hash de blob, ce qui modifie le hash du tree parent, qui modifie le hash du commit qui le référence, jusqu’à la tête du graphe.

Calcul Exact de l’Empreinte SHA-1 d’un Objet Git

Le hash affiché par Git n’est pas le simple hash du fichier : Git injecte un en-tête canonique avant le calcul cryptographique :

,
format_brut = f"{type_objet} {taille_en_octets}\0{contenu_du_fichier}"
sha1 = hashlib.sha1(format_brut).hexdigest()
,

Par exemple, pour un fichier contenant le mot test (5 octets) :

,
    ,
  • En-tête : blob 5\0
    • ,
  • Charge utile : test
    • ,
  • Total à hacher : blob 5\0test (12 octets au total)
    • ,
  • Empreinte SHA-1 résultante : 9daeafb9864cf43055ae93beb0afd6c7d144bfa4
    • ,

En 2017, la première collision pratique sur SHA-1 (attaque SHAttered par le CWI et Google) a démontré la vulnérabilité théorique de l’algorithme. Depuis la version 2.29, Git supporte une transition architecturale vers SHA-256 (hashes de 64 caractères hexadécimaux), renforçant la résilience cryptographique face aux ordinateurs modernes et attaques par collision ciblée.

4. Commandes de Plomberie vs Porcelaine : Contrôle de Bas Niveau

Dans la terminologie inventée par Linus Torvalds, Git distingue deux couches d’interfaces :

  • La porcelaine (Porcelain) : Commandes de haut niveau destinées à l’humain (git status, git commit, git log, git checkout). Elles masquent la complexité en orchestrant plusieurs actions de bas niveau.
  • La plomberie (Plumbing) : Commandes spécialisées conçues pour les scripts et les outils internes. Elles manipulent directement les objets bruts et les références de la base de données.
Commande de PlomberieSyntaxe OpérationnelleEffet Technique
git hash-object git hash-object -w fichier.txt Calcule le SHA et écrit (-w) l’objet compressé dans le magasin .git/objects/.
git cat-file git cat-file -p <hash> / -t <hash> Affiche le contenu formaté (-p pour pretty-print) ou le type de l’objet (-t).
git ls-tree git ls-tree -r HEAD Parcourt récursivement l’objet tree pour lister les blobs et sous-arbres avec leurs modes.
git rev-parse git rev-parse HEAD Résout une référence symbolique ou relative en son identifiant SHA canonique à 40 caractères.

Exercice 1 — Calculateur de hachage SHA-1 d’objet Git (Plomberie git hash-object)

Étude de cas Niveau 1 — Acquisition

Objectif : Calculer le hash SHA-1 exact d’un objet Git selon le formatage canonique interne du stockage objet.

En interne, Git stocke tous les contenus dans sa base de données orientée objets (.git/objects/) adressée par le contenu (Content-Addressable Storage).

Pour calculer l'empreinte SHA-1 d'un objet (équivalent de la commande de plomberie git hash-object), Git préfixe le contenu brut avec une chaîne d'en-tête standard suivie d'un octet nul \0 :
en-tete = f"{type_objet} {taille_octets}\0"
Puis il calcule le condensat SHA-1 (40 caractères hexadécimaux en minuscules) de la concaténation de l'en-tête et du contenu.

Analysez les paramètres du problème pour chaque cas.

Pour chaque ligne, afficher :
GIT_HASH type={type} size={taille} sha1={hash_hex}

Cas d’exemple
OBJECT type=blob content=hello world
Résolution attendue
GIT_HASH type=blob size=11 sha1=95d09f2b10159347eece71399a7e2e907ea3df4f

Blob Git contenant "hello world" (11 octets) dont le sha1 canonique avec en-tête est 95d09f2b...

Deux indices, rédigés en mots
  1. L’en-tête d’un objet Git se compose du type d’objet, d’un espace, de la taille en octets et d’un octet nul.
  2. L’empreinte SHA-1 de 40 caractères hexadécimaux est calculée sur la concaténation de l’en-tête et du contenu brut.

Exercice 2 — Parseur d’arbre Git et inspection de hiérarchie (git ls-tree)

Étude de cas Niveau 2 — Application

Objectif : Analyser les entrées d’un objet Tree Git et afficher l’inventaire des blobs et sous-arbres avec leur mode.

Un objet Tree dans Git modélise un répertoire. Il contient une suite ordonnée d'entrées représentant les fichiers (blobs) et les sous-répertoires (trees).

Chaque entrée comporte :
- Un mode UNIX à 6 chiffres :
- 100644 : fichier texte / données normal (non exécutable)
- 100755 : script / binaire exécutable
- 040000 : sous-répertoire (Tree)
- 120000 : lien symbolique (symlink)
- Le type de l'objet lié (blob pour les fichiers, tree pour les répertoires).
- L'identifiant SHA-1 de l'objet (40 caractères hexadécimaux).
- Le nom du fichier ou dossier.

Analysez les paramètres du problème pour chaque cas.

Indiquez pour chaque cas les entrées triées par ordre alphabétique du nom de fichier au format standard git ls-tree :
{mode} {type} {sha1}\t{name}
Puis un récapitulatif :
TREE_SUMMARY total={n} blobs={nb_blobs} subtrees={nb_trees} executables={nb_exec}

Cas d’exemple
ENTRY mode=100644 type=blob sha1=a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2 name=README.md
ENTRY mode=040000 type=tree sha1=b1c2d3e4f5a6b1c2d3e4f5a6b1c2d3e4f5a6b1c2 name=src
Résolution attendue
100644 blob a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2	README.md
040000 tree b1c2d3e4f5a6b1c2d3e4f5a6b1c2d3e4f5a6b1c2	src
TREE_SUMMARY total=2 blobs=1 subtrees=1 executables=0

Un fichier README et un sous-dossier src.

Deux indices, rédigés en mots
  1. Extraire chaque champ avec une regex ou découpage de chaîne.
  2. Trier la liste des entrées sur la clé name.
  3. Compter les exécutables dont le mode vaut 100755.

Exercice 3 — Résolveur de références symboliques & pointeur HEAD (git rev-parse)

Étude de cas Niveau 3 — Raisonnement

Objectif : Résoudre la chaîne de pointeurs de références de Git pour déterminer le commit actif pointé par HEAD.

Dans Git, HEAD est une référence symbolique qui pointe généralement vers une branche locale (ex: ref: refs/heads/main), qui elle-même contient le hash du dernier commit de cette branche.

Si un développeur effectue un checkout directement sur un commit ou un tag, HEAD contient directement le hash : le dépôt est alors en HEAD détachée (Detached HEAD).

Analysez les paramètres du problème pour chaque cas. Des définitions de références :
REF name=<nom> target=<hash|ref: autre_ref>.
2. Des requêtes de résolution :
RESOLVE name=<ref_a_resoudre>.

Pour chaque requête, le script suit la chaîne de déréférencement jusqu'au hash SHA-1 final (en détectant si HEAD pointe sur une branche ou est détachée) :
- Si la chaîne aboutit à un commit :
RESOLVED name={name} commit={hash} state={BRANCH_REF|DETACHED_HEAD} path={chaine_de_refs}
- Si la référence n'existe pas :
RESOLVED name={name} status=NOT_FOUND

Cas d’exemple
REF name=refs/heads/main target=c0ffee1234567890abcdef1234567890abcdef12
REF name=HEAD target=ref: refs/heads/main
RESOLVE name=HEAD
Résolution attendue
RESOLVED name=HEAD commit=c0ffee1234567890abcdef1234567890abcdef12 state=BRANCH_REF path=HEAD -> refs/heads/main

HEAD pointe sur la branche main qui pointe sur le commit.

Deux indices, rédigés en mots
  1. Stocker les refs dans un dictionnaire.
  2. Suivre les cibles commençant par "ref: " en boucle jusqu’à obtenir un hash.

6. QCM — niveau examen

Quelles informations sont réellement conservées à l’intérieur d’un objet Git de type « blob » ?

Un blob ne contient que le contenu brut en octets du fichier. Le nom du fichier et les droits d’accès (permissions Unix) sont exclusivement portés par l’objet tree parent.

Quelle formule correspond exactement à la chaîne d’octets hachée par Git pour un objet blob de 10 octets ?

Le standard Git injecte toujours le préambule : type + espace + taille_en_octets + octet_nul (\0) suivi du contenu brut avant d’appliquer la fonction de hachage cryptographique.

Dans quelle structure Git les permissions d’accès Unix d’un fichier (ex: 100644 ou 100755) sont-elles enregistrées ?

C’est l’objet tree qui référence chaque blob en lui associant son mode Unix (100644 pour un fichier normal, 100755 pour un exécutable, 120000 pour un lien symbolique) et son nom.

À quoi sert la commande de plomberie « git cat-file -t » ?

L’option -t (type) de git cat-file retourne le nom du type de l’objet correspondant au hash dans la base de données Git (blob, tree, commit ou tag).

Que contient le fichier spécial « .git/HEAD » dans un état normal sur la branche principale « main » ?

HEAD est une référence symbolique pointant vers la branche active. Son contenu est textuellement « ref: refs/heads/main » (sauf en état de tête détachée / detached HEAD où il contient un SHA-1 direct).

Quel est l’impact de la modification d’un seul octet dans un fichier sur l’arbre de Merkle du dépôt ?

L’arbre de Merkle garantit l’intégrité en cascade : changer le blob modifie le tree qui le contient, ce qui modifie le commit qui référence ce tree, garantissant l’immuabilité de l’historique.

Quelle commande de plomberie permet d’écrire directement un nouvel objet blob dans le magasin .git/objects/ ?

L’option -w (write) de git hash-object ordonne à Git de calculer le hash et d’enregistrer physiquement l’objet compressé dans le répertoire .git/objects/.

Combien de parents possède le tout premier commit (commit initial) créé dans un dépôt Git ?

Le commit initial (root commit) n’a aucun commit parent. Un commit standard en possède un, et un commit de fusion en possède au moins deux.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Croire que Git stocke des fichiers entiers sous leur nom réel dans .git/objects/ (ils sont compressés et renommés selon leur hash).
  • Penser qu’un blob conserve le nom du fichier (le nom est uniquement stocké dans l’objet tree parent).
  • Oublier l’octet nul (« \0 ») dans le calcul manuel du hash SHA-1 d’un objet Git.
  • Confondre les références symboliques (HEAD pointant vers refs/heads/main) et les hashes absolus de commits.

8. Méthodologie de résolution

Méthode d’Ingénierie : Inspection & Audit des Objets Internes Git
  1. Étape 1 : Localiser la référence courante en lisant le fichier .git/HEAD pour identifier la branche ou le commit actif.
  2. Étape 2 : Résoudre la référence symbolique via git rev-parse pour obtenir le hash SHA-1/SHA-256 complet du commit cible.
  3. Étape 3 : Inspecter la structure du commit via git cat-file -p pour extraire le hash de l’arbre racine (tree) et les parents.
  4. Étape 4 : Dérouler l’arborescence des répertoires et fichiers en explorant les entrées tree via git ls-tree.
  5. Étape 5 : Vérifier l’intégrité d’un fichier en recalculant son empreinte avec git hash-object et en la comparant au hash stocké.

9. Révision active

Résumé essentiel
  • Git est un système de fichiers adressable par contenu reposant sur un graphe orienté acyclique (DAG).
  • Le dossier .git/ contient toute la base de données : HEAD, objects/, refs/ et index.
  • Quatre types d’objets immuables : blob (contenu pur), tree (répertoire), commit (instantané tracé), tag (étiquette annotée).
  • Un blob ne stocke jamais son nom de fichier ni ses droits : ces métadonnées sont encapsulées dans les objets tree.
  • Le hachage Git injecte toujours un préambule normalisé : type taille\0contenu avant le calcul SHA-1 ou SHA-256.
  • L’architecture en arbre de Merkle garantit que la modification d’un seul bit invalide et propage de nouveaux hashes en cascade.
  • Les commandes de plomberie (hash-object, cat-file, ls-tree, rev-parse) permettent l’automatisation et le diagnostic précis.

Checklist de maîtrise

  • Je sais expliquer la structure et le contenu du dossier masqué .git.
  • Je connais la formule exacte du préambule injecté avant le hachage d’un objet Git.
  • Je sais pourquoi un objet blob ne contient ni son nom de fichier ni ses permissions d’accès Unix.
  • Je maîtrise la différence entre un objet tree et un objet commit dans le graphe DAG.
  • Je sais utiliser git cat-file (-p, -t) pour inspecter n’importe quel objet de la base.
  • Je suis capable de résoudre une référence symbolique vers un hash absolu avec git rev-parse.

Les 8 notions à connaître absolument

  1. Système de fichiers adressable par contenu (CAS)
  2. Graphe Orienté Acyclique (DAG)
  3. Arbre de Merkle (Merkle Tree)
  4. Objet Blob (Binary Large Object)
  5. Objet Tree & modes de permissions Unix
  6. Objet Commit & chaîne d’ancêtres parents
  7. Empreintes cryptographiques SHA-1 & SHA-256
  8. Commandes de plomberie (Plumbing vs Porcelain)
