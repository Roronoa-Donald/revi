Chapitre 2 — Stratégies de Fusion Avancées & Rebase Interactif

Module 2 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Lorsqu’une équipe d’ingénieurs collabore sur un projet d’envergure, la convergence des branches de travail devient l’opération la plus critique et la plus source d’erreurs. Les fusions naïves sans maîtrise topologique engendrent un « historique en plat de spaghettis », rendant la traçabilité des bogues et les retours en arrière quasiment impossibles. En Bachelor 3, l’ingénieur doit maîtriser la mécanique topologique des fusions tridirectionnelles (3-Way Merge), le calcul algorithmique de l’ancêtre commun le plus proche (Lowest Common Ancestor - LCA), les subtilités du rebase interactif pour assainir les commits locaux avant livraison, et les techniques formelles de résolution de conflits sans perte d’intégrité.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. comprendre la différence mathématique et topologique entre une fusion Fast-Forward et un 3-Way Merge ;
  2. analyser l’algorithme de recherche du Lowest Common Ancestor (LCA) au sein du graphe orienté acyclique (DAG) ;
  3. comparer les moteurs de fusion historiques de Git (recursive) et le moteur moderne par défaut (ORT - Ostensibly Recursive’s Twin) ;
  4. maîtriser le rebase interactif (git rebase -i) avec ses directives clés : pick, reword, edit, squash, fixup, drop ;
  5. appliquer rigoureusement la règle d’or du rebase pour préserver la cohérence des dépôts d’équipe distribués ;
  6. développer en Python 3 des classificateurs de stratégies de fusion, des simulateurs de rebase et des résolveurs de conflits tridirectionnels.

1. Topologie des Fusions : Fast-Forward vs 3-Way Merge & Lowest Common Ancestor

L’intégration de branches dans Git ne se fait pas à l’aveugle : Git analyse les chemins reliant les branches au sein du graphe orienté acyclique (DAG).

1. La Fusion Linéaire (Fast-Forward)

Une fusion Fast-Forward (avance rapide) est possible lorsque la branche courante (ex: main) n’a reçu aucun nouveau commit depuis le moment où la branche de fonctionnalité (ex: feature) a été créée.

Topologiquement, le pointeur de main est un ancêtre direct de feature. Git n’a aucun arbitrage à réaliser : il déplace simplement le pointeur de main pour l’aligner sur le commit de tête de feature. Aucun nouveau commit de fusion n’est créé.

Pour forcer la création d’un commit de traçabilité même si un Fast-Forward est possible, on emploie le drapeau : git merge --no-ff feature.

2. La Fusion Tridirectionnelle (3-Way Merge)

Dès lors que les deux branches ont divergé (chacune possédant des commits spécifiques), un Fast-Forward est physiquement impossible.

Git doit trouver le Lowest Common Ancestor (LCA), c’est-à-dire le dernier commit ancêtre commun le plus proche dans l’arbre. Git compare ensuite trois états :

  • L’état de l’ancêtre commun (Base / LCA)
  • L’état de la branche cible (Ours / HEAD)
  • L’état de la branche source (Theirs / Feature)

Le résultat génère un nouveau commit de fusion (merge commit) possédant exactement deux parents.

2. Les Moteurs de Fusion Git : De « recursive » à « ORT »

Historiquement, Git utilisait la stratégie de fusion recursive. Cependant, dans les topologies complexes où deux branches ont divergé et se sont croisées plusieurs fois (fusions croisées ou criss-cross merges), il peut exister plusieurs LCA concurrents. La stratégie recursive devait alors synthétiser récursivement un ancêtre virtuel intermédiaire.

La Révolution du Moteur ORT (Git 2.33+)

3. Le Rebase Interactif : Nettoyage d’Historique & la Règle d’Or

Alors que la fusion (merge) préserve fidèlement la vérité historique brute avec tous ses embranchements, le rebase (git rebase) réécrit l’histoire pour produire un historique parfaitement linéaire.

La commande git rebase -i HEAD~N ouvre un éditeur interactif permettant de réordonner, combiner ou épurer les commits avant de proposer une Pull Request :

ActionAbréviationRôle Technique & Comportement
pickpConserve le commit tel quel dans l’historique réécrit.
rewordrConserve le contenu du commit mais permet d’éditer son message.
editeMet en pause le rebase pour amender le contenu du commit (fichiers).
squashsFond le commit dans le commit précédent et concatène les messages.
fixupfFond le commit dans le précédent en éliminant silencieusement son message.
dropdSupprime purement et simplement le commit de l’historique.
La Règle d’Or Absolue du Rebase

« Ne rebasez JAMAIS une branche publique partagée avec d’autres développeurs. »

,

Puisque le rebase réapplique chaque commit sur une nouvelle base, le parent de chaque commit change : tous les identifiants SHA-1/SHA-256 sont irrémédiablement modifiés. Si la branche est déjà présente sur GitHub, cela obligera un git push --force qui écrasera le travail des collaborateurs et sèmera la confusion.

4. Résolution Formelle des Conflits de Fusion Tridirectionnelle

Un conflit survient lorsqu’une même ligne d’un même fichier a été modifiée de deux manières différentes dans la branche locale et dans la branche distante par rapport à l’ancêtre commun (LCA). Git suspend l’opération et insère des marqueurs de conflit :

<<<<<<< HEAD (Notre version locale)
const PORT = 8080;
=======
const PORT = 3000;
>>>>>>> feature/api-port (Version distante en cours de fusion)

L’ingénieur doit analyser le contexte, supprimer les marqueurs, conserver la valeur appropriée, indexer le fichier via git add puis finaliser la fusion via git commit (ou git rebase --continue).

Exercice 1 — Détecteur de stratégie de fusion : Fast-Forward vs 3-Way Merge

Python Niveau 1 — Acquisition

Objectif : Déterminer si une fusion de branches peut s’effectuer en Fast-Forward ou requiert un 3-Way Merge avec commit de fusion.

Dans le graphe orienté acyclique (DAG) des commits de Git :
- Si le commit de tête de la branche courante (base) est un ancêtre direct de la branche à intégrer (target), Git avance simplement le pointeur sans créer de nouveau commit : c'est un Fast-Forward (FF).
- Si les deux branches ont divergé depuis un ancêtre commun (Lowest Common Ancestor - LCA), un Three-Way Merge est nécessaire et un commit de fusion à 2 parents doit être généré.

Le script lit sur l'entrée standard :
1. La déclaration des commits et de leurs parents :
COMMIT id=<id> parents=<p1,p2...|NONE>.
2. La position des branches :
BRANCH name=<nom> commit=<id>.
3. Une demande de fusion :
MERGE_REQUEST current=<branche_base> incoming=<branche_target>.

Afficher :
MERGE_STRATEGY from={incoming} into={current} type={FAST_FORWARD|THREE_WAY_MERGE} lca={lca_id}

Entrée du programme
COMMIT id=C1 parents=NONE
COMMIT id=C2 parents=C1
COMMIT id=C3 parents=C2
BRANCH name=main commit=C1
BRANCH name=feature commit=C3
MERGE_REQUEST current=main incoming=feature
Sortie attendue
MERGE_STRATEGY from=feature into=main type=FAST_FORWARD lca=C1

C1 est un ancêtre direct de C3 : avance rapide du pointeur main vers C3.

Deux indices, rédigés en mots
  1. Construire la liste de tous les ancêtres de chaque commit en remontant les parents.
  2. Si base_commit fait partie des ancêtres de incoming_commit, la fusion est FAST_FORWARD.
  3. Sinon, trouver le plus proche ancêtre commun (LCA).

Exercice 2 — Simulateur de Rebase Interactif (git rebase -i)

Python Niveau 2 — Application

Objectif : Simuler l’exécution des instructions de réécriture d’historique git-rebase-todo (pick, squash, reword, drop).

Le rebase interactif (git rebase -i) permet de nettoyer un historique de commits avant de proposer une Pull Request.

Actions supportées :
- pick <id> <msg> : conserve le commit tel quel.
- reword <id> <nouveau_msg> : conserve les modifications mais remplace le message du commit.
- drop <id> : supprime purement et simplement le commit de l’historique.
- squash <id> <msg> : fusionne ce commit dans le commit précédent en concaténant les messages sous la forme {msg_precedent} + {msg_squashe}.

Le script lit les commandes ordonnées de haut en bas :
TODO action=<pick|reword|drop|squash> commit=<id> [msg=<message>].

À l’issue de la réécriture, afficher le nouvel historique résultant :
Pour chaque commit conservé :
REBASED_COMMIT id={id} msg="{message}"
Et la ligne finale :
REBASE_SUMMARY total_commits={n}

Entrée du programme
TODO action=pick commit=C1 msg=feat: ajout login
TODO action=squash commit=C2 msg=fix: correction typo
TODO action=reword commit=C3 msg=feat: ajout logout propre
Sortie attendue
REBASED_COMMIT id=C1 msg="feat: ajout login + fix: correction typo"
REBASED_COMMIT id=C3 msg="feat: ajout logout propre"
REBASE_SUMMARY total_commits=2

C2 a été écrasé (squashed) dans C1, C3 a son message réécrit.

Deux indices, rédigés en mots
  1. Gérer une liste de commits réécrits.
  2. Lors d’un squash, modifier le dernier commit ajouté dans la liste en combinant les messages.

Exercice 3 — Moteur de résolution de conflits à 3 voies (Base, Ours, Theirs)

Python Niveau 3 — Raisonnement

Objectif : Appliquer l’algorithme de fusion à 3 voies ligne à ligne pour détecter les modifications unilatérales et les conflits.

Lors d'un Three-Way Merge, Git compare chaque bloc de code par rapport à la version de l'ancêtre commun (base) :

Règles de décision pour chaque ligne :
1. Si ours == base et theirs == base : aucun changement -> conserver base (statut CLEAN).
2. Si ours != base et theirs == base : modification unilatérale par notre branche -> adopter ours (statut RESOLVED_OURS).
3. Si ours == base et theirs != base : modification unilatérale par la branche distante -> adopter theirs (statut RESOLVED_THEIRS).
4. Si ours == theirs : les deux branches ont fait exactement le même changement -> adopter ours (statut RESOLVED_SAME).
5. Si ours != theirs et les deux diffèrent de base : conflit de fusion réel (statut CONFLICT).

Le script lit sur l'entrée standard des comparaisons de lignes au format :
LINE idx=<n> base=<texte> ours=<texte> theirs=<texte>.

Afficher :
- Si pas de conflit : MERGE idx={n} status={CLEAN|RESOLVED_OURS|RESOLVED_THEIRS|RESOLVED_SAME} val="{val}"
- Si conflit : MERGE idx={n} status=CONFLICT ours="{ours}" theirs="{theirs}"

Entrée du programme
LINE idx=1 base=port = 80 ours=port = 443 theirs=port = 80
LINE idx=2 base=timeout = 30 ours=timeout = 60 theirs=timeout = 120
Sortie attendue
MERGE idx=1 status=RESOLVED_OURS val="port = 443"
MERGE idx=2 status=CONFLICT ours="timeout = 60" theirs="timeout = 120"

Ligne 1 résolue en faveur de ours, ligne 2 en conflit.

Deux indices, rédigés en mots
  1. Comparer les valeurs par rapport à base.
  2. Ne lever CONFLICT que si ours et theirs ont tous deux divergé de base avec des valeurs différentes.

6. QCM — niveau examen

Dans quelle situation topologique une fusion Fast-Forward est-elle possible ?

Le Fast-Forward n’est possible que si la branche réceptrice n’a pas divergé par rapport à l’ancêtre commun de la branche à intégrer. Git déplace simplement le pointeur vers l’amont.

Combien de parents possède un commit généré par une fusion tridirectionnelle classique (3-Way Merge) ?

Un commit de fusion standard à deux branches possède exactement deux parents : le commit HEAD courant et le commit de la branche intégrée.

Quel est le rôle du Lowest Common Ancestor (LCA) lors d’une fusion à 3 voies ?

Le LCA est le dernier ancêtre commun le plus proche dans le DAG. Git compare les modifications de la branche locale par rapport au LCA et de la branche distante par rapport au LCA pour identifier les vrais conflits.

Quelle directive de « git rebase -i » permet de fondre un commit dans le précédent en éliminant son message ?

La commande fixup fusionne les modifications dans le commit situé au-dessus de lui dans la liste tout en ignorant son message de commit, contrairement à squash qui ouvre un éditeur pour concaténer les messages.

Pourquoi est-il formellement interdit de rebaser une branche publique partagée sur GitHub ?

Chaque commit rebasé reçoit un nouveau parent, donc un nouvel identifiant SHA. Pour les autres membres de l’équipe qui se basaient sur les anciens commits, l’historique est brisé et entre en conflit violent.

Quel moteur de fusion est devenu le moteur officiel par défaut de Git depuis la version 2.33 ?

Le moteur ORT a succédé au moteur recursive historique. Il est infiniment plus rapide et gère de manière optimale les renommages de répertoires et fichiers.

Que symbolise la section comprise entre « <<<<<<< HEAD » et « ======= » dans un fichier en conflit ?

La partie supérieure (entre <<<<<<< HEAD et =======) représente la version du fichier présente sur la branche locale active (HEAD).

Quelle commande permet de forcer la création d’un commit de fusion même si un Fast-Forward est réalisable ?

L’option --no-ff désactive le comportement par défaut d’avance rapide et force Git à créer un commit de fusion dédié, préservant la trace explicite de l’existence d’une branche de fonctionnalité.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Faire un git push --force sur la branche main après un rebase local (catastrophe d’équipe).
  • Confondre squash (qui fusionne en conservant les messages) et fixup (qui élimine le message du commit fusionné).
  • Oublier de supprimer les marqueurs de conflit (« <<<<<<< ») avant de commiter un fichier résolu.
  • Penser que git merge modifie les hashes des commits fusionnés (seul git rebase réécrit les hashes).

8. Méthodologie de résolution

Méthode d’Ingénierie : Arbitrage & Nettoyage d’une Branche Avant PR
  1. Étape 1 : Mettre à jour la copie locale de la branche principale : git fetch origin main.
  2. Étape 2 : Lancer un rebase interactif local pour condenser les micro-commits de travail : git rebase -i HEAD~5.
  3. Étape 3 : Utiliser « fixup » sur les commits de corrections mineures (typos, lint) pour ne conserver que des commits atomiques.
  4. Étape 4 : Rebaser la branche de fonctionnalité sur la tête à jour de main : git rebase origin/main.
  5. Étape 5 : En cas de conflit, inspecter les deltas par rapport au LCA, éditer le code, git add puis git rebase --continue.
  6. Étape 6 : Vérifier la compilation et les tests unitaires avant de pousser la branche nettoyée sur GitHub.

9. Révision active

Résumé essentiel
  • Fast-Forward avance le pointeur de branche sans créer de commit si l’historique est strictement linéaire.
  • Le 3-Way Merge intervient dès qu’il y a divergence et crée un commit de fusion à 2 parents.
  • L’algorithme LCA (Lowest Common Ancestor) est le pivot mathématique de la fusion tridirectionnelle.
  • Le moteur ORT (Git 2.33+) remplace recursive : ultra-rapide et détection avancée des renommages.
  • Le rebase interactif (git rebase -i) permet d’assainir l’historique local : pick, squash, fixup, reword.
  • La règle d’or : ne jamais rebaser une branche publique déjà partagée avec l’équipe.
  • Les conflits tridirectionnels résultent de modifications contradictoires par rapport à la base LCA.
