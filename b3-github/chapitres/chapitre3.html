Chapitre 3 — Diagnostic, Reflog & Sauvetage de Données

Module 3 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans le cycle de vie d’un projet logiciel, l’erreur humaine est inévitable : une commande destructive exécutée par inadvertance (git reset --hard, suppression accidentelle d’une branche non fusionnée), ou l’apparition d’un bogue silencieux introduit il y a plusieurs mois parmi des centaines de commits. L’ingénieur de niveau Bachelor 3 ne panique pas face à ces incidents : il sait que Git ne détruit presque jamais immédiatement les données. Grâce au journal de références (git reflog) et aux outils d’inspection d’intégrité (git fsck), chaque état passé reste récupérable. De plus, la recherche dichotomique automatisée (git bisect) permet d’identifier le commit exact responsable d’une régression en un temps logarithmique O(log2 N). Maîtriser ces outils de sauvetage et de diagnostic fait la différence entre des journées de travail perdues et une remédiation en quelques secondes.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. comprendre le fonctionnement interne du journal de références local (git reflog) et son cycle de rétention ;
  2. restaurer des commits orphelins (dangling commits) et des branches supprimées par erreur après un reset destructif ;
  3. analyser l’intégrité du magasin d’objets avec la commande de bas niveau git fsck ;
  4. maîtriser la recherche dichotomique binaire de régressions avec git bisect en mode interactif et automatisé (git bisect run) ;
  5. manipuler la pile de remisage LIFO git stash (push, pop, apply, drop, list) et inspecter ses commits internes ;
  6. développer en Python 3 des analyseurs de reflog, des moteurs de bisect binaire et des gestionnaires de pile stash.

1. Le Journal de Références : git reflog & le Filet de Sécurité Ultime

Alors que git log parcourt l’arbre des commits accessibles depuis la référence active en suivant les liens parents, git reflog (Reference Log) consigne l’historique chronologique de tous les déplacements du pointeur HEAD et des références de branches sur la machine locale.

Fonctionnement & Localisation

Chaque fois que HEAD se déplace (création d’un commit, changement de branche, rebase, merge, reset), une entrée est inscrite dans .git/logs/HEAD.

La syntaxe de navigation temporelle est redoutable :

  • HEAD@{0} : Position actuelle de HEAD.
  • HEAD@{1} : Position de HEAD juste avant la dernière commande.
  • HEAD@{5} : Position il y a 5 opérations.
  • main@{yesterday} : État de la branche main hier.

Procédure de Sauvetage après « reset --hard »

Scénario critique : un développeur exécute par erreur git reset --hard HEAD~3.

  1. Exécuter git reflog show HEAD pour identifier l’entrée juste avant le reset (ex: HEAD@{1} avec son SHA).
  2. Restaurer immédiatement l’état :
    git checkout -b rescue HEAD@{1}
    ou remettre la branche courante à niveau :
    git reset --hard HEAD@{1}.

Le travail est intégralement restauré, sans aucune perte de code !

2. Objets Orphelins (Dangling) & Nettoyage Garbaged avec git fsck

Dans Git, lorsqu’une branche est supprimée ou qu’un commit est écrasé lors d’un reset, les objets commits et blobs ne sont pas effacés physiquement de .git/objects/. Ils deviennent simplement inaccessibles depuis les branches actives (objets orphelins ou dangling objects).

Cycle de Vie des Objets & Garbage Collector (git gc)

Git conserve les objets orphelins par défaut pendant un délai de grâce configurable :

,
    ,
  • Les entrées du reflog sont conservées pendant 90 jours pour les objets accessibles et 30 jours pour les objets inaccessibles (gc.reflogExpireUnreachable).
    • ,
  • Tant que ce délai n’est pas écoulé, le ramasse-miettes (git gc) ne supprime pas les données.
    • ,
  • La commande de plomberie git fsck --lost-found scanne la base d’objets, identifie tous les commits orphelins et les exporte dans .git/lost-found/commit/ pour inspection.

3. Isolation Dichotomique de Régressions : La Puissance de git bisect

Lorsqu’une régression apparaît en production dans une application composée de centaines de commits, inspecter manuellement chaque commit est fastidieux et inefficace. git bisect applique l’algorithme de recherche binaire (dichotomie) pour diviser l’espace de recherche par deux à chaque itération.

Complexité Algorithmique

Pour un historique de $N$ commits, le nombre maximal d’étapes d’évaluation nécessaires est borné par :

$\lceil \log_2(N) \rceil$

Exemple : pour 1 024 commits, 10 tests seulement suffisent pour désigner de façon certaine le commit fautif !

Workflow Interactif & Automatisé

# 1. Démarrer la session
git bisect start
git bisect bad HEAD        # Le bogue est présent ici
git bisect good v2.1.0      # Ici tout fonctionnait

# 2. Mode automatique avec script de test
git bisect run npm test

Si le script retourne le code de sortie 0, Git marque le commit comme good ; s’il retourne 1..127, il le marque bad. Dès l’isolation terminée, git bisect reset remet la copie de travail à son état initial.

4. Gestion Avancée de la Pile de Remisage : L’Anatomie de git stash

Le remisage (git stash) permet de mettre de côté des modifications non terminées dans la copie de travail et l’index pour basculer sur une urgence (hotfix) sans créer de commit provisoire « wip » polluant l’arbre.

CommandeRôle Technique & Comportement
git stash push -m "msg"Empile l’état actuel de l’index et de la copie de travail avec un libellé clair.
git stash listAffiche la pile LIFO des remises stockées (stash@{0}, stash@{1}, ...).
git stash apply stash@{N}Réapplique les modifications de la remise sans la supprimer de la pile.
git stash popRéapplique la remise la plus récente (stash@{0}) et la dépile immédiatement.
git stash drop stash@{N}Supprime définitivement une remise spécifique de la pile.

Exercice 1 — Explorateur de Reflog et récupération de commits orphelins (Dangling Commits)

Étude de cas Niveau 1 — Acquisition

Objectif : Analyser le journal des mouvements de têtes (reflog) pour identifier et sauver un commit devenu orphelin après un reset accidentel.

Lorsqu'un développeur exécute par erreur git reset --hard HEAD~3 ou supprime une branche locale avant d'avoir poussé, les commits semblent perdus.
En réalité, Git ne supprime jamais immédiatement les objets : ils restent référencés dans le Reflog (Reference Log) jusqu'à la collecte des déchets (Garbage Collection git gc).

Analysez les paramètres du problème pour chaque cas. La liste des commits actuellement accessibles par les branches actives :
ACTIVE_BRANCH name=<nom> tip=<hash> ancestors=<h1,h2...|NONE>.
2. Les entrées chronologiques du reflog de HEAD (du plus récent au plus ancien) :
REFLOG_ENTRY id=<HEAD@{n}> commit=<hash> action=<action> desc=<message>.

Un commit est considéré comme orphelin (Dangling) s'il figure dans le reflog mais n'apparaît ni comme tête (tip) ni comme ancêtre d'aucune branche active.

Pour chaque commit orphelin identifié dans le reflog (dans l'ordre d'apparition), afficher :
RESCUE_CANDIDATE reflog={id} commit={hash} action="{action}" desc="{desc}" status=DANGLING
Si aucun commit orphelin n'est trouvé :
RESCUE_SUMMARY: ALL_COMMITS_REFERENCED

Cas d’exemple
ACTIVE_BRANCH name=main tip=C1 ancestors=NONE
REFLOG_ENTRY id=HEAD@{0} commit=C1 action=reset desc=moving to C1
REFLOG_ENTRY id=HEAD@{1} commit=C3 action=commit desc=Feature perdue
Résolution attendue
RESCUE_CANDIDATE reflog=HEAD@{1} commit=C3 action="commit" desc="Feature perdue" status=DANGLING

C3 a été abandonné par le reset to C1 et n’est plus dans main.

Deux indices, rédigés en mots
  1. Constituer un ensemble (set) de tous les commits accessibles par les branches actives.
  2. Parcourir les entrées de reflog et vérifier l’appartenance au set.

Exercice 2 — Détecteur de régression dichotomique automatique (git bisect)

Étude de cas Niveau 2 — Application

Objectif : Simuler la recherche dichotomique de Git Bisect pour identifier le premier commit ayant introduit un bogue.

L'outil git bisect effectue une recherche binaire (dichotomie) dans l'historique des commits pour trouver la régression en un minimum de tests ($O(\log N)$).

Algorithme :
1. On dispose d'une liste ordonnée chronologiquement de $N$ commits : [c_0, c_1, ..., c_{N-1}].
Le commit initial $c_0$ est certifié GOOD (sain), et le commit final $c_{N-1}$ est BAD (défaillant).
2. Tant que l'intervalle [low, high] contient plus d'un commit suspect :
On choisit le commit médian : mid = (low + high) // 2.
On évalue l'état du commit mid (fourni par la table des statuts) :
- Si mid == BAD : la régression a eu lieu à mid ou avant -> high = mid.
- Si mid == GOOD : la régression a eu lieu après mid -> low = mid + 1.
On Indiquez chaque étape : BISECT_STEP step={k} testing={commit_id} verdict={GOOD|BAD} remaining={high - low + 1}.
3. Dès que low == high, le premier commit défaillant est identifié :
FIRST_BAD_COMMIT id={commit_id}.

Analysez les données fournies pour chaque cas...>
STATUSES <c_id>=<GOOD|BAD> ...

Cas d’exemple
HISTORY commits=C1,C2,C3,C4,C5
STATUSES C1=GOOD C2=GOOD C3=BAD C4=BAD C5=BAD
Résolution attendue
BISECT_STEP step=1 testing=C3 verdict=BAD remaining=3
BISECT_STEP step=2 testing=C2 verdict=GOOD remaining=1
FIRST_BAD_COMMIT id=C3

C3 est identifié comme le premier commit ayant introduit le bogue en 2 étapes.

Deux indices, rédigés en mots
  1. L’outil git bisect utilise la recherche dichotomique pour identifier le commit responsable d’une régression en log2(N) étapes.
  2. À chaque itération, examinez le commit médian situé à mi-chemin entre la bonne version connue et la mauvaise version.

Exercice 3 — Gestionnaire de pile de remisage (git stash LIFO stack)

Étude de cas Niveau 3 — Raisonnement

Objectif : Simuler le comportement en pile LIFO (Last-In, First-Out) des commandes git stash.

La commande git stash enregistre temporairement les modifications en cours sur une pile LIFO sans créer de commit formel.

Commandes à exécuter :
- push <message> : empile une nouvelle entrée au sommet stash@{0}. Les entrées existantes sont décalées : stash@{k} -> stash@{k+1}.
- pop : extrait et supprime l'entrée la plus récente stash@{0}.
- apply <idx> : applique l'entrée stash@{idx} sans la supprimer de la pile.
- drop <idx> : supprime l'entrée stash@{idx} de la pile (les entrées d'indice supérieur sont décrémentées d'une unité).

Analysez les données fournies pour chaque cas.

Pour chaque action, afficher :
STASH_OP action={action} result={OK|STACK_EMPTY|INDEX_OUT_OF_BOUNDS} current_size={taille} top="{msg_du_sommet|EMPTY}"

Cas d’exemple
STASH_CMD action=push arg=WIP sur formulaire
STASH_CMD action=pop
Résolution attendue
STASH_OP action=push result=OK current_size=1 top="WIP sur formulaire"
STASH_OP action=pop result=OK current_size=0 top="EMPTY"

Empilement puis dépilement immédiat de la réserve.

Deux indices, rédigés en mots
  1. Gérer une liste Python où l’indice 0 représente stash@{0}.
  2. Lors d’un push, insérer à l’indice 0 avec stack.insert(0, msg).

6. QCM — niveau examen

Quelle information capitale le journal « git reflog » enregistre-t-il que « git log » n’affiche pas ?

git log ne parcourt que les commits connectés à la branche courante. git reflog enregistre chronologiquement chaque déplacement de HEAD sur la machine locale, permettant de retrouver les commits détachés.

Où les entrées du reflog pour le pointeur HEAD sont-elles physiquement stockées sur le disque ?

Git écrit chaque transition dans des fichiers texte situés dans le sous-dossier masqué .git/logs/ (notamment .git/logs/HEAD et .git/logs/refs/heads/).

Combien d’étapes de test au maximum sont nécessaires avec « git bisect » pour localiser une régression parmi 500 commits ?

La recherche dichotomique a une complexité logarithmique en ceil(log2(500)) = ceil(8.96) = 9 étapes.

Quel code de sortie doit renvoyer un script de test exécuté par « git bisect run » pour indiquer que le commit actuel est sain (sans bogue) ?

Selon la convention Unix standard et la spécification de git bisect run, le code de sortie 0 signifie que le test réussit (commit « good ») ; un code entre 1 et 127 indique un échec (commit « bad »).

Par défaut, pendant combien de temps Git conserve-t-il les objets inaccessibles (unreachable/dangling) avant que « git gc » ne les purge définitivement ?

Par défaut, la directive gc.reflogExpireUnreachable conserve les objets orphelins pendant 30 jours, offrant une marge de sécurité confortable pour récupérer une fausse manipulation.

Quelle commande permet de restaurer la dernière remise enregistrée tout en la supprimant de la pile de remisage ?

git stash pop réapplique les modifications du stash supérieur (stash@{0}) et l’élimine immédiatement de la pile s’il n’y a pas eu de conflit lors de l’application.

À quoi sert la commande de plomberie « git fsck --lost-found » ?

git fsck (File System Check) contrôle la cohérence du magasin d’objets et l’option --lost-found extrait tous les objets orphelins inaccessibles pour permettre leur analyse.

Si vous avez exécuté par erreur « git reset --hard HEAD~2 », quelle commande permet de revenir immédiatement à l’état antérieur ?

HEAD@{1} correspond à la position de HEAD juste avant l’exécution du reset. Faire un git reset --hard HEAD@{1} réaligne instantanément la branche sur son état précédent.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Croire que git reflog est partagé sur GitHub (le reflog est strictement local à la machine du développeur).
  • Penser qu’un git reset --hard supprime immédiatement et définitivement les commits du disque.
  • Fournir un script pour git bisect run qui ne retourne pas 0 en cas de succès (cela fausserait tout l’aiguillage binaire).
  • Confondre git stash pop (qui supprime la remise) et git stash apply (qui la laisse dans la pile).

8. Méthodologie de résolution

Méthode d’Ingénierie : Traque d’un Bogue Fantôme via git bisect automatisé
  1. Étape 1 : Écrire un script de test unitaire déterministe (test.sh ou pytest) qui retourne 0 quand le code est sain et 1 en cas de bogue.
  2. Étape 2 : Identifier le dernier tag de version ou commit réputé 100% fonctionnel (ex: v1.0.0).
  3. Étape 3 : Initialiser bisect avec git bisect start HEAD v1.0.0 (HEAD étant défaillant et v1.0.0 fonctionnel).
  4. Étape 4 : Lancer l’automatisation : git bisect run bash ./test.sh.
  5. Étape 5 : Noter le SHA et l’auteur du premier commit fautif affiché par Git.
  6. Étape 6 : Clôturer la session de recherche avec git bisect reset et rédiger le correctif ciblé.

9. Révision active

Résumé essentiel
  • git reflog enregistre localement chaque mouvement de HEAD dans .git/logs/HEAD.
  • Après un reset --hard malencontreux, le reflog permet de restaurer le travail en quelques secondes.
  • Les objets orphelins (dangling) restent stockés sur disque pendant 30 à 90 jours avant purge par git gc.
  • git fsck inspecte l’intégrité du graphe et répertorie les commits détachés dans lost-found.
  • git bisect divise l’espace de recherche par 2 à chaque étape (complexité en O(log2 N)).
  • git bisect run automatise la détection grâce au code retour d’un script de test (0 = good, non-zéro = bad).
  • git stash gère une pile LIFO de remises pour mettre de côté le travail en cours sans commit prématuré.

Checklist de maîtrise

  • Je sais consulter et interpréter la sortie chronologique de git reflog show HEAD.
  • Je suis capable de récupérer une branche supprimée par erreur à l’aide du reflog.
  • Je comprends la différence de rétention entre objets accessibles et objets orphelins (dangling).
  • Je maîtrise la syntaxe et les arguments de git bisect (start, bad, good, reset).
  • Je sais automatiser git bisect avec un script de test retournant des codes de sortie standard.
  • Je sais manipuler la pile git stash (push, list, pop, apply, drop).
