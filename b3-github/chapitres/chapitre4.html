Chapitre 4 — Workflows d’Équipe, Gouvernance & Protection de Branches

Module 4 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans un contexte professionnel, la technique pure de Git ne suffit pas si elle n’est pas encadrée par une gouvernance d’équipe rigoureuse. La prolifération de branches orphelines, les fusions incontrôlées directement sur la branche principale en production et les messages de commits incompréhensibles constituent les causes majeures de régressions logicielles et de retards de livraison. L’ingénieur de niveau Bachelor 3 doit savoir choisir et formaliser la stratégie de branches appropriée (du modèle classique Git Flow jusqu’au Trunk-Based Development accéléré), configurer des règles d’accès strictes (Branch Protection Rules sur GitHub) exigeant approbations par les pairs et contrôles d’intégration continue, imposer la signature cryptographique des commits via GPG, et structurer les messages selon la norme Conventional Commits pour automatiser le versionnage sémantique (SemVer).

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. analyser et comparer de manière critique les flux de travail Git Flow, GitHub Flow et Trunk-Based Development ;
  2. concevoir une politique de gouvernance d’entreprise avec branches protégées, revues de code et historique linéaire ;
  3. configurer la signature cryptographique des commits avec GPG et clés SSH pour garantir l’authenticité des auteurs ;
  4. maîtriser la spécification formelle Conventional Commits 1.0.0 et son impact sur le calcul automatique de versions SemVer ;
  5. mettre en place des règles de protection de branche (Rulesets GitHub) empêchant les fusions sans statut CI valide ;
  6. développer en Python 3 des auditeurs de conformité de workflow, des évaluateurs de règles de fusion et des analyseurs sémantiques de messages.

1. Modèles de Collaboration en Équipe : Du Git Flow au Trunk-Based Development

Le choix d’un modèle de cycle de vie des branches (Branching Strategy) conditionne directement la cadence de déploiement et la stabilité des applications :

1. Le Modèle Git Flow (Historique & Cycles Longs)

Conçu par Vincent Driessen en 2010 pour les logiciels packagés à cycles de publication espacés :

  • main (ou master) : Reflète l’état exact de la production.
  • develop : Branche d’intégration courante des fonctionnalités.
  • Branches éphémères : feature/*, release/*, hotfix/*.

Limites : Modèle lourd, multiplication des fusions croisées et inadapté au déploiement continu moderne (CD).

2. Trunk-Based Development & GitHub Flow (Moderne & CI/CD)

Le standard des géants du web (Google, Meta, Netflix) et des équipes DevOps modernes :

  • Trunk-Based : Tous les développeurs intègrent leurs modifications sur une branche unique main (le tronc) au moins une fois par jour.
  • Branches de fonctionnalités (Feature Branches) ultra-courtes : durée de vie inférieure à 24-48 heures.
  • Utilisation systématique de Feature Flags (bascules de code) pour masquer en production les fonctionnalités en cours de développement.

2. Gouvernance de Dépôt & Règles de Protection de Branche (Branch Protection)

Sur GitHub, une branche de production ne doit jamais être modifiable par un git push direct, même par le créateur du dépôt. La mise en place de Branch Protection Rules (ou GitHub Repository Rulesets) impose des garde-fous formels :

Règle de ProtectionDescription TechniqueBénéfice de Sécurité & Qualité
Require pull request reviews Exige au minimum 1 ou 2 approbations de relecteurs pairs (Peer Review) et l’accord des CODEOWNERS. Empêche l’introduction de code unilatéral sans double regard critique.
Require status checks to pass La fusion est bloquée tant que les workflows CI (linter, tests unitaires, build) n’ont pas retourné un statut SUCCESS. Garantit que la branche principale ne compile jamais de code cassé (Zero Broken Trunk).
Require signed commits Rejette tout commit dont la signature cryptographique GPG/SSH n’est pas vérifiée par GitHub. Élimine totalement les attaques par usurpation d’identité d’auteur (Commit Spoofing).
Require linear history Interdit les commits de fusion à 2 parents (oblige Squash & Merge ou Rebase). Conserve un historique limpide, facilitant les audits et le fonctionnement de git bisect.

3. Signature Cryptographique : GPG & Clés SSH Signées

Par défaut, Git fait aveuglément confiance aux champs d’en-tête user.name et user.email d’un commit. N’importe qui peut commiter sous l’identité d’un administrateur sans mot de passe :

git config user.name "Linus Torvalds"
git config user.email "torvalds@linux-foundation.org"
Usurpation d’Identité & Badge « Verified » sur GitHub

Pour contrer cette vulnérabilité, la signature cryptographique associe la clé privée du développeur au hash du commit :

    ,
  • Création d’une clé GPG (ou utilisation d’une clé SSH moderne avec gpg.format = ssh).
    • ,
  • Signature automatique : git commit -S -m "commit certifie".
    • ,
  • GitHub vérifie la signature contre la clé publique enregistrée et appose le badge vert « Verified ». Tout commit forgé sans clé privée valide est rejeté ou marqué non vérifié.

4. Spécification Formelle Conventional Commits 1.0.0 & SemVer

La convention Conventional Commits 1.0.0 structure les messages de commit pour permettre le calcul automatisé des versions selon le Semantic Versioning (SemVer 2.0.0 - MAJOR.MINOR.PATCH) et la génération sans intervention humaine du journal des modifications (CHANGELOG) :

<type>[scope optionnel][!]: <description concise>

[corps detaille optionnel]

[pied de page : BREAKING CHANGE: ... ou Closes #42]

Types Autorisés & Sémantique

  • feat : Nouvelle fonctionnalité (incrémente MINOR).
  • fix : Correction de bogue (incrémente PATCH).
  • docs, chore, style, refactor, perf, test, ci : Modifications internes sans impact fonctionnel (aucun incrément).

Rupture de Compatibilité (Breaking Change)

Une rupture d’API publique incrémente immédiatement le chiffre MAJOR (ex: de v1.4.2 à v2.0.0). Elle se signale formellement de deux manières :

  • Par un point d’exclamation avant le deux-points : feat(auth)!: bascule vers OAuth2 strict.
  • Par la mention BREAKING CHANGE: dans le pied de page du commit.

Exercice 1 — Validateur de conformité de workflow de branches (Git Flow vs GitHub Flow)

Étude de cas Niveau 1 — Acquisition

Objectif : Auditer la création d’une branche et ses opérations selon les règles de gouvernance de Git Flow ou GitHub Flow.

En entreprise, la gestion des branches doit suivre des règles strictes pour garantir la stabilité de la production :

Règles du modèle GIT_FLOW :
- Les branches feature/* doivent obligatoirement être créées à partir de develop.
- Les branches release/* doivent partir de develop.
- Les branches hotfix/* doivent partir de main.
- Tout push direct (direct_push=OUI) sur main ou develop est formellement interdit (VIOLATION_DIRECT_PUSH_PROTECTED_BRANCH).

Règles du modèle GITHUB_FLOW :
- Toutes les branches de fonctionnalités/correctifs partent de main.
- Tout push direct sur main est interdit.

Analysez les paramètres du problème pour chaque cas.

Pour chaque ligne, afficher :
AUDIT branch={branch} status={CONFORME | motif_violation}

Cas d’exemple
BRANCH_EVENT wf=GIT_FLOW branch=feature/auth base=develop direct_push=NON
BRANCH_EVENT wf=GIT_FLOW branch=feature/auth base=main direct_push=NON
Résolution attendue
AUDIT branch=feature/auth status=CONFORME
AUDIT branch=feature/auth status=BRANCHE_BASE_INVALIDE_ATTENDU_DEVELOP

Dans Git Flow, une feature doit partir de develop, pas de main.

Deux indices, rédigés en mots
  1. Vérifier d’abord l’interdiction de push direct sur les branches protégées.
  2. Tester la conformité de la branche de départ (base) selon le préfixe du nom de branche.

Exercice 2 — Contrôleur de règles de protection de branches (Branch Protection Rules)

Étude de cas Niveau 2 — Application

Objectif : Appliquer les critères de fusion de Pull Request (approbations requises, statuts CI, signature GPG).

Sur GitHub Enterprise, les branches de production sont verrouillées par des Branch Protection Rules.

Critères nécessaires pour autoriser la fusion (Merge) dans main :
1. approvals >= min_approvals (nombre d'approbations de relecteurs humains requises, ex: 2).
2. ci_status == 'PASS' (les pipelines d'intégration continue doivent impérativement être au vert).
3. Si require_signed == 'OUI' : le commit doit obligatoirement être signé cryptographiquement (gpg_signed == 'OUI').
4. Si linear_history == 'OUI' : le type de merge demandé ne doit pas être MERGE_COMMIT (doit être SQUASH ou REBASE).

Analysez les données fournies pour chaque cas.

Pour chaque PR, afficher :
PR_MERGE pr={id} status={AUTHORIZED|BLOCKED} reason={OK|motif_du_premier_blocage}

Cas d’exemple
CONFIG min_approvals=2 require_signed=OUI linear_history=OUI
MERGE_REQ pr=42 approvals=2 ci_status=PASS gpg_signed=OUI merge_type=SQUASH
Résolution attendue
PR_MERGE pr=42 status=AUTHORIZED reason=OK

Tous les critères de protection sont satisfaits.

Deux indices, rédigés en mots
  1. Vérifier les critères dans l’ordre de la spécification : approvals, ci_status, signature, historique linéaire.
  2. Dès qu’un critère échoue, le statut est BLOCKED.

Exercice 3 — Analyseur sémantique de commits selon Conventional Commits

Étude de cas Niveau 3 — Raisonnement

Objectif : Vérifier la conformité des messages de commit selon la spécification formelle Conventional Commits 1.0.0.

La norme Conventional Commits structure les messages pour automatiser le versionnage sémantique (SemVer) et la génération de CHANGELOG.

Format standard :
<type>[scope optionnel][!]: <description>

Règles de validation :
1. type doit appartenir à la liste autorisée : feat, fix, docs, refactor, test, chore, perf, ci.
2. Le scope (si présent) doit être entouré de parenthèses : ex: feat(api): ....
3. Le caractère ! avant le deux-points ou la présence de BREAKING CHANGE dans le message indique une rupture de compatibilité (BREAKING=OUI).
4. Le séparateur obligatoire est deux-points suivi d'un espace ": ".
5. La description ne doit pas être vide.

Analysez les paramètres du problème pour chaque cas.

Pour chaque message, afficher :
- Si conforme : CONVENTIONAL_AUDIT id={id} valid=OUI type={type} scope={scope|NONE} breaking={OUI|NON}
- Si non conforme : CONVENTIONAL_AUDIT id={id} valid=NON error={TYPE_INCONNU|FORMAT_INVALIDE|DESCRIPTION_VIDE}

Cas d’exemple
COMMIT_MSG id=1 msg=feat(auth): ajout authentification JWT
COMMIT_MSG id=2 msg=fix!: correction faille critique
Résolution attendue
CONVENTIONAL_AUDIT id=1 valid=OUI type=feat scope=auth breaking=NON
CONVENTIONAL_AUDIT id=2 valid=OUI type=fix scope=NONE breaking=OUI

Validation du format avec et sans scope, détection de breaking change.

Deux indices, rédigés en mots
  1. Utiliser une regex : r"^([a-z]+)(?:\(([a-zA-Z0-9_-]+)\))?(!)?:s+(.+)$"
  2. Vérifier si le type extrait est dans les types autorisés.

6. QCM — niveau examen

Pourquoi les équipes adoptant la livraison continue (CI/CD) privilégient-elles Trunk-Based Development par rapport à Git Flow ?

Trunk-Based Development évite la divergence de code en incitant les développeurs à fusionner de petites modifications quotidiennement sur le tronc, supprimant les crises de fusions douloureuses de Git Flow.

Quel mécanisme logiciel permet de fusionner du code incomplet dans la branche principale sans impacter les utilisateurs finaux ?

Les Feature Flags permettent d’activer ou désactiver des morceaux de code via des variables de configuration, autorisant l’intégration continue du code inachevé sans risque pour la production.

Que se passe-t-il si un développeur tente de pusher un commit sans signature GPG sur une branche protégée par « Require signed commits » ?

La règle de protection vérifie les métadonnées cryptographiques : tout commit dépourvu d’une signature valide issue d’une clé publique enregistrée sur le profil de l’utilisateur est bloqué.

Dans la norme Conventional Commits 1.0.0, quel type de commit correspond à une nouvelle fonctionnalité ajoutée à l’application ?

Le type « feat » est réservé aux nouvelles fonctionnalités et entraîne automatiquement l’incrémentation du composant MINOR de la version sémantique SemVer.

Quel incrément SemVer (X.Y.Z) est déclenché par un commit rédigé « feat(api)!: suppression du support XML » ?

Le point d’exclamation « ! » signale une rupture de compatibilité ascendante (Breaking Change), ce qui déclenche obligatoirement l’incrémentation du chiffre majeur (MAJOR).

Quel est l’intérêt d’imposer la règle « Require linear history » sur la branche principale GitHub ?

Un historique linéaire ne contient aucun embranchement ni commit de fusion à plusieurs parents, ce qui facilite grandement la lecture chronologique, les audits de sécurité et le traçage bisect.

Où doit être placé le fichier déclarant formellement les propriétaires de répertoires de code pour les revues de Pull Requests sur GitHub ?

GitHub lit nativement le fichier .github/CODEOWNERS (ou CODEOWNERS à la racine) pour assigner automatiquement les relecteurs requis dès qu’une Pull Request touche les fichiers sous leur responsabilité.

Quelle information dans les en-têtes d’un commit Git peut être librement falsifiée sans clé de signature cryptographique ?

Git se fie aux variables d’environnement user.name et user.email configurées localement : sans signature GPG ou SSH, n’importe quel utilisateur peut prétendre être l’auteur d’un commit.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Conserver des branches de fonctionnalités ouvertes pendant des semaines (garantie de conflits inextricables).
  • Permettre aux administrateurs de contourner les règles de protection de branche en cochant « Do not apply to administrators ».
  • Oublier le deux-points suivi d’un espace (« : ») dans la syntaxe des messages Conventional Commits.
  • Pousser des commits non signés sur un dépôt imposant la vérification GPG (le push sera rejeté).

8. Méthodologie de résolution

Méthode d’Ingénierie : Mise en Place de la Gouvernance de Dépôt
  1. Étape 1 : Activer la protection de branche sur main (Settings -> Rules -> Rulesets) avec PR obligatoire et au moins 1 approbation.
  2. Étape 2 : Créer le fichier .github/CODEOWNERS pour assigner automatiquement les relecteurs référents selon les dossiers modifiés.
  3. Étape 3 : Rendre obligatoires les contrôles d’état CI (checks status) : le pipeline de validation doit réussir avant tout merge.
  4. Étape 4 : Activer l’exigence de signature des commits (Require signed commits) et configurer les clés GPG/SSH de l’équipe.
  5. Étape 5 : Installer un hook commit-msg validant la syntaxe Conventional Commits 1.0.0 sur les postes des développeurs.
  6. Étape 6 : Configurer un outil de release automatisé (semantic-release ou standard-version) sur GitHub Actions.

9. Révision active

Résumé essentiel
  • Git Flow est un modèle à branches longues lourd ; Trunk-Based Development privilégie des intégrations continues quotidiennes sur le tronc.
  • Les Feature Flags permettent de fusionner fréquemment sans exposer du code incomplet aux utilisateurs finaux.
  • Les Branch Protection Rules protègent la branche main : PR obligatoire, 1-2 approbations, CI au vert, historique linéaire.
  • N’importe qui peut forger l’auteur d’un commit sans mot de passe : la signature GPG/SSH est la seule preuve cryptographique d’authenticité.
  • La norme Conventional Commits (feat, fix, docs...) normalise les messages et pilote l’incrémentation automatique de SemVer.
  • Le caractère « ! » ou la mention BREAKING CHANGE déclenche immédiatement un saut de version majeure (MAJOR).

  • Je maîtrise la structure formelle de la spécification Conventional Commits 1.0.0.
