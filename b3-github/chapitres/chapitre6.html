Chapitre 6 — Administration Avancée, LFS, Hooks & Purge d’Historique

Module 6 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Au fur et à mesure que les projets d’entreprise grandissent, deux fléaux majeurs menacent la viabilité des dépôts : l’explosion de la taille du dossier .git due au stockage inapproprié de gros fichiers binaires (datasets, modèles d’IA, fichiers multimédias), et la fuite catastrophique d’identifiants de production (clés API, mots de passe, certificats SSL) commis par mégarde dans l’historique. Un ingénieur de niveau Bachelor 3 doit maîtriser l’administration de haut niveau d’un dépôt : déporter les binaires lourds via l’architecture de pointeurs Git LFS, automatiser les contrôles qualité et sécurité au plus près des postes de travail grâce aux hooks Git, et maîtriser les techniques de réécriture complète de graphe (DAG rewrite) avec l’outil moderne git-filter-repo pour purger définitivement les secrets compromis sans corrompre l’intégrité du projet.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. comprendre l’architecture de Git LFS (Large File Storage) et la spécification formelle de ses pointeurs textuels ;
  2. configurer le suivi de motifs de fichiers avec .gitattributes pour déporter les binaires volumineux vers un stockage d’objets dédié ;
  3. concevoir et déployer des hooks Git côté client (pre-commit, commit-msg) et côté serveur (pre-receive) ;
  4. analyser l’impact de l’empaquetage d’objets (.pack/.idx) et du garbage collector (git gc, git prune) sur les performances ;
  5. maîtriser l’utilisation de git-filter-repo pour expurger des secrets et supprimer des dossiers volumineux de l’historique complet ;
  6. développer en scripts Bash et commandes Git des générateurs de pointeurs LFS, des vérificateurs de hooks pre-commit et des moteurs de purge de secrets.

1. Gestion des Fichiers Volumineux : Architecture de Git LFS

Par conception, Git est conçu pour le code source textuel : il calcule des deltas compressés efficaces entre versions successives. En revanche, pour des fichiers binaires volumineux (vidéos, modèles de Deep Learning, fichiers audio, archives compressées), toute modification infime réécrit l’intégralité du fichier, provoquant une croissance exponentielle de la taille du dépôt lors du clonage.

Fonctionnement de Git LFS

Git LFS (Large File Storage) remplace le fichier lourd dans l’arborescence Git par un micro-pointeur textuel de quelques octets :

  • Le fichier binaire réel est téléversé séparément sur un serveur de stockage d’objets compatible LFS (ex: Amazon S3 ou stockage GitHub LFS).
  • Lors du git checkout, le client LFS télécharge uniquement les binaires nécessaires pour la version courante.
  • La configuration s’effectue dans le fichier tracé .gitattributes : *.bin filter=lfs diff=lfs merge=lfs -text.

Format Formel d’un Pointeur LFS (v1)

Un pointeur LFS est un fichier texte strict respectant la spécification suivante :

version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c9470e9b14...
size 12345678

Le champ oid contient l’identifiant d’objet calculé par la fonction de hachage SHA-256 sur le contenu brut du binaire, suivi de sa taille exacte en octets.

2. Automatisation Locale & Serveur : Les Hooks Git

Les hooks (crochets) sont des scripts exécutables situés dans le dossier .git/hooks/ (ou gérés via des frameworks modernes comme pre-commit) déclenchés automatiquement lors d’événements clés du cycle Git :

Nom du HookEmplacementMoment d’ExécutionCas d’Usage & Pouvoir de Blocage
pre-commit Client local Avant la création du commit (après git commit). Vérifie le formatage du code (Black, ESLint), détecte les clés d’API en clair ou les marqueurs de conflits non résolus. Si le script renvoie un code non-zéro, le commit est annulé.
commit-msg Client local Après saisie du message de commit. Valide le format du message selon la spécification Conventional Commits ou vérifie la présence d’un numéro de ticket JIRA.
pre-push Client local Avant l’envoi des commits vers le serveur distant. Exécute la suite de tests rapides pour éviter de pousser du code cassé sur le dépôt distant.
pre-receive Serveur distant À la réception d’un push, avant mise à jour des refs. Le garde-fou ultime d’entreprise : rejette tout push contenant des secrets, des commits non signés ou des branches non conformes à la politique PSSI.

3. Purge Radicale de Secrets & Réécriture du DAG avec git-filter-repo

L’incident de sécurité le plus redouté : un développeur commite par inadvertance un fichier .env contenant des clés privées AWS de production ou un token d’API Stripe dans un dépôt public.

Pourquoi « git rm » ne suffit pas face à une fuite

git rm .env prépare la suppression dans l’index et retire le fichier de l’arbre de travail par défaut ; --cached le conserve dans l’arbre de travail. La commande ne crée pas de commit : celui-ci est une opération distincte.

Le secret est toujours présent et intact dans les commits antérieurs de l’historique. N’importe quel utilisateur qui clone le projet ou consulte l’arborescence passée peut extraire la clé !

Après révocation du secret, une réécriture autorisée avec git-filter-repo peut retirer des données de références sélectionnées. Elle ne garantit pas leur disparition des copies, forks, caches ou autres références ; suivre la procédure du fournisseur et coordonner l’équipe.

Suppression d’un chemin dans l’historique réécrit

# Supprimer completement un fichier de tout l’historique
git-filter-repo --path .env --invert-paths

Cette opération réécrit les références traitées ; vérifier aussi les anciens noms et les copies restantes.

Remplacement de Secrets en Texte

# Remplacer une cle par un texte factice
echo "AKIAIOSFODNN7EXAMPLE==>REDACTED" > expressions.txt
git-filter-repo --replace-text expressions.txt

La réécriture ne supprime pas à elle seule les copies externes du secret.

4. Procédure Post-Purge en Production & Révocation d’Urgence

Une réécriture d’historique sur un dépôt d’entreprise requiert un protocole opérationnel millimétré :

  1. Révocation immédiate : Considérer le secret comme irrémédiablement compromis et le révoquer sur la plateforme cloud avant même de toucher à Git.
  2. Réécriture autorisée : Préparer une copie et suivre la procédure documentée du fournisseur pour les références concernées.
  3. Coordination : Planifier toute mise à jour forcée avec les responsables du dépôt et vérifier les références, forks et caches accessibles.
  4. Re-synchronisation : Prévenir les collaborateurs afin de limiter la réintroduction des anciens commits ; ne pas présumer que toutes les copies externes ont disparu.

Exercice 1 — Simulateur de Git LFS (Large File Storage) et génération de pointeurs

Bash Entraînement, non noté Niveau 1 — Acquisition

Objectif : Déterminer si un fichier doit être géré par Git LFS et générer le pointeur texte officiel.

La correction automatique de ce cours est temporairement suspendue pendant la vérification des exercices.

Git LFS remplace, dans le dépôt, le contenu d'un fichier suivi par un petit pointeur texte ; le contenu réel est stocké séparément. La configuration effective de suivi dépend notamment des motifs configurés. Pour cet exercice seulement, utilisez la politique suivante : un chemin terminé, avec respect de la casse, par .iso, .psd, .zip, .tar.gz ou .mp4, ou une taille size_bytes >= 104857600 octets, impose LFS. Ce seuil n'est pas une règle automatique universelle de Git LFS.

Chaque ligne est FILE path=<chemin> size_bytes=<taille> sha256=<64 chiffres hexadécimaux minuscules>. La taille est un entier décimal de 0 à 9 223 372 036 854 775 807, sans zéro initial sauf pour 0. Le chemin peut contenir des espaces mais ni guillemet double ni le délimiteur size_bytes=. Le SHA-256 est fourni : le contenu du fichier n'est pas disponible pour le recalculer.

Pour un fichier ordinaire, affichez LFS_DECISION file="{path}" mode=GIT_BLOB. Pour LFS, affichez LFS_DECISION file="{path}" mode=LFS_POINTER oid="{sha256}" size={size_bytes}, puis les trois lignes du pointeur v1 :
version https://git-lfs.github.com/spec/v1
oid sha256:{sha256}
size {size_bytes}.

Entrée du programme
FILE path=videos/intro.mp4 size_bytes=52428800 sha256=abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234567890
FILE path=src/main.py size_bytes=2048 sha256=00112233445566778899aabbccddeeff00112233445566778899aabbccddeeff
Sortie attendue
LFS_DECISION file="videos/intro.mp4" mode=LFS_POINTER oid="abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234567890" size=52428800
version https://git-lfs.github.com/spec/v1
oid sha256:abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234567890
size 52428800
LFS_DECISION file="src/main.py" mode=GIT_BLOB

Le fichier MP4 est suivi et son pointeur est produit ; le script Python reste un blob Git.

Deux indices, rédigés en mots
  1. Appliquez la politique du modèle : extension surveillée ou taille supérieure ou égale à 104857600.
  2. Reprenez le SHA-256 fourni et écrivez les trois lignes du pointeur v1 dans l’ordre.

Exercice 2 — Validateur de Hook Git pre-commit (Détection de secrets & conflits)

Bash Entraînement, non noté Niveau 2 — Application

Objectif : Simuler les contrôles d’un hook pre-commit sur quelques motifs de conflit et de secrets.

La correction automatique de ce cours est temporairement suspendue pendant la vérification des exercices.

Un hook Git pre-commit peut interrompre un commit en renvoyant un code non nul ; il peut aussi être contourné avec git commit --no-verify. Ici, vous ne créez pas de vrai hook : simulez uniquement ses décisions sur les lignes INSPECT_FILE file=<chemin> content=<contenu>. Les chemins peuvent contenir des espaces mais ni guillemet double ni le délimiteur content= ; le contenu tient sur une ligne et peut représenter des retours à la ligne par \n.

Vérifiez ces motifs dans l'ordre : les chaînes <<<<<<<, ======= ou >>>>>>> donnent MERGE_CONFLICT_MARKERS ; AKIA suivi d'au moins 16 lettres majuscules ASCII ou chiffres donne HARDCODED_AWS_KEY ; ghp_ suivi d'au moins 20 lettres ASCII ou chiffres donne HARDCODED_GITHUB_TOKEN ; sinon le résultat est CLEAN.

Affichez HOOK_RESULT file="{file}" verdict={COMMIT_ACCEPTED|COMMIT_REJECTED} reason={reason}. Ces motifs sont pédagogiques : une correspondance ne prouve pas qu'un identifiant soit actif, et leur absence ne garantit pas l'absence de secret.

Entrée du programme
INSPECT_FILE file=app.py content=AWS_KEY = "AKIAIOSFODNN7EXAMPLE123"
INSPECT_FILE file=main.py content=print("Hello World")
Sortie attendue
HOOK_RESULT file="app.py" verdict=COMMIT_REJECTED reason=HARDCODED_AWS_KEY
HOOK_RESULT file="main.py" verdict=COMMIT_ACCEPTED reason=CLEAN

La clé AWS bloque le commit, le code sain est accepté.

Deux indices, rédigés en mots
  1. Vérifiez les marqueurs de conflit avant les motifs d’identifiants.
  2. Utilisez les expressions régulières de Bash et testez les longueurs immédiatement inférieure et égale aux bornes.

Exercice 3 — Purge médico-légale de secrets dans l’historique (git-filter-repo)

Bash Entraînement, non noté Niveau 3 — Raisonnement

Objectif : Simuler la réécriture d’un historique Git pour expurger un fichier confidentiel commité par erreur.

La correction automatique de ce cours est temporairement suspendue pendant la vérification des exercices.

Retirer un fichier sensible d'un commit récent ne l'efface pas des anciens commits. GitHub recommande notamment git-filter-repo pour réécrire l'historique ; un secret compromis doit aussi être révoqué ou renouvelé. Cet exercice est une simulation : les identifiants r_{id} ne sont pas de vrais hachages et aucun dépôt n'est modifié.

Déclarez zéro ou plusieurs lignes COMMIT id=<id> files=<f1,f2,...> parents=<p1,p2,...|NONE>, puis PURGE_FILE target=<fichier>. Une liste de fichiers vide s'écrit files=. Les noms sont distincts au sein de chaque liste et, comme les identifiants, ne contiennent ni espaces ni virgule. Les commits sont distincts, acycliques et déclarés après tous leurs parents.

Retirez le fichier cible de chaque instantané. Un commit est réécrit s'il contenait le fichier ou si au moins un de ses parents a été réécrit ; son nouvel identifiant est r_{id}. Les autres restent inchangés. La tête simulée est le dernier commit déclaré, ou NONE si l'historique est vide.

Affichez PURGE_RESULT target="{fichier}" impacted_count={nombre_de_commits_réécrits} new_tip_hash="{id_de_tête}", puis pour chaque commit réécrit dans l'ordre d'entrée REWRITTEN_COMMIT old="{id}" new="r_{id}" remaining_files=[{fichiers}]. Conservez l'ordre des fichiers restants.

Entrée du programme
COMMIT id=C1 files=main.py,.env parents=NONE
COMMIT id=C2 files=main.py parents=C1
PURGE_FILE target=.env
Sortie attendue
PURGE_RESULT target=".env" impacted_count=2 new_tip_hash="r_C2"
REWRITTEN_COMMIT old="C1" new="r_C1" remaining_files=[main.py]
REWRITTEN_COMMIT old="C2" new="r_C2" remaining_files=[main.py]

C1 contenait .env donc il est réécrit en r_C1, et C2 ayant r_C1 pour parent est réécrit en r_C2.

Deux indices, rédigés en mots
  1. Parcourez les commits dans l’ordre où tous leurs parents sont déjà connus.
  2. Réécrivez un commit si le fichier est présent ou si au moins un parent a été réécrit.

6. QCM — niveau examen

Pourquoi le stockage direct de gros fichiers binaires dans Git classique pose-t-il un problème majeur de performance ?

Git télécharge l’historique complet lors du clone. Pour des fichiers binaires non compressibles par deltas, la taille du dossier .git enfle de plusieurs gigaoctets, saturant le réseau et les disques.

Que contient physiquement dans l’arbre Git un fichier suivi par Git LFS (Large File Storage) ?

Git LFS remplace le binaire par un micro-pointeur textuel contenant l’identifiant SHA-256 (oid) et la taille du fichier. Le binaire réel est déporté sur un serveur de stockage dédié.

Dans quel fichier de configuration les règles associant des extensions de fichiers au filtre LFS sont-elles déclarées et tracées ?

Le fichier .gitattributes versionné à la racine du dépôt définit les filtres appliqués aux fichiers lors des checkouts et commits (ex: *.psd filter=lfs diff=lfs merge=lfs -text).

Quel hook Git côté client permet d’interrompre automatiquement un commit si des marqueurs de conflit non résolus sont détectés ?

Le hook pre-commit s’exécute immédiatement après le lancement de git commit : s’il retourne un code de sortie non-zéro (suite à la détection de conflits ou erreurs de linter), Git interrompt la validation.

Où le hook d’entreprise « pre-receive » s’exécute-t-il et quel est son avantage stratégique pour la sécurité ?

pre-receive s’exécute sur le serveur Git distant. Il examine l’ensemble des commits reçus et peut bloquer définitivement le push s’il contient des secrets, du code mal formaté ou des violations de politiques.

Quelle commande permet de réécrire des références locales en retirant un chemin précis de leur historique ?

git-filter-repo peut réécrire les références traitées en excluant ce chemin ; les autres noms, références et copies externes nécessitent des vérifications distinctes.

Quelle est la première action vitale à accomplir immédiatement dès qu’une clé d’API sensible est découverte sur un dépôt Git public ?

Même si le dépôt est nettoyé quelques minutes plus tard, des robots scrappeurs automatisés surveillent en permanence GitHub pour voler les secrets publiés. La seule parade absolue est la révocation immédiate du secret.

Que doivent impérativement faire les membres de l’équipe de développement après une réécriture d’historique complète (purge de secrets) poussée sur le serveur ?

Puisque la réécriture a modifié tous les hashes SHA de l’historique, faire un git pull réintroduirait les anciens commits non purgés. Les collaborateurs doivent cloner une copie neuve et supprimer l’ancienne.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Penser qu’effacer un secret dans le commit le plus récent élimine la vulnérabilité (il reste dans l’historique antérieur).
  • Utiliser le vieil outil obsolète git filter-branch au lieu de git-filter-repo (trop lent et sujet à des corruptions).
  • Oublier de révoquer le secret chez le fournisseur de service en pensant que réécrire Git suffit.
  • Pousser de gros fichiers binaires dans Git sans LFS, ce qui fait exploser définitivement la taille du clone pour l’équipe.

8. Méthodologie de résolution

Méthode d’Ingénierie : Protocole d’Assainissement d’un Dépôt après Fuite de Secret
  1. Étape 1 : Révoquer et renouveler immédiatement le secret compromis auprès du fournisseur tiers (AWS, GitHub, Stripe, BDD).
  2. Étape 2 : Créer une sauvegarde bare de sécurité du dépôt dans un dossier isolé : git clone --bare mon-depot.git backup.git.
  3. Étape 3 : Sur un clone de travail dédié, exécuter git-filter-repo avec le motif de fichier ou l’expression de remplacement ciblée.
  4. Étape 4 : Vérifier avec git log -S "secret" que la chaîne compromise est devenue totalement introuvable dans tout l’historique.
  5. Étape 5 : Réassocier le remote distant et forcer la mise à jour : git push origin --force --all --tags.
  6. Étape 6 : Informer l’équipe technique et invalider les caches des serveurs d’intégration continue (runners CI).

9. Révision active

Résumé essentiel
  • Git gère mal les fichiers binaires lourds : Git LFS résout ce problème en utilisant des pointeurs textuels légers (SHA-256).
  • Le fichier .gitattributes spécifie les motifs de fichiers capturés par le filtre LFS (filter=lfs).
  • Les hooks Git permettent d’automatiser des vérifications qualité et sécurité avant commit (pre-commit) ou à la réception serveur (pre-receive).
  • Un git rm ne supprime pas un secret compromis des commits passés dans l’historique.
  • git-filter-repo réécrit l’intégralité du DAG pour expurger définitivement fichiers volumineux ou données sensibles.
  • Après une fuite de secret, la révocation immédiate de la clé auprès du service concerné est la priorité numéro un absolue.
  • Toute réécriture d’historique modifie les hashes et impose un re-clonage propre par l’ensemble des collaborateurs.

Checklist de maîtrise

  • Je comprends l’architecture de Git LFS et la structure d’un pointeur LFS v1.
  • Je sais configurer .gitattributes pour orienter des fichiers binaires vers Git LFS.
  • Je connais la différence entre un hook client (pre-commit) et un hook serveur (pre-receive).
  • Je sais expliquer pourquoi git rm est inefficace pour corriger la fuite d’un mot de passe dans l’historique.
  • Je maîtrise la commande git-filter-repo pour purger un fichier ou masquer un secret.
  • Je connais la procédure opérationnelle complète à suivre en cas de fuite de clé de production.

Les 8 notions à connaître absolument

  1. Git LFS (Large File Storage)
