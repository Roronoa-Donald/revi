Examens Blancs & Épreuves Corrigées — Git & GitHub B3

Deux épreuves d’évaluation complètes conformes aux exigences professionnelles et académiques de niveau Bachelor 3 en ingénierie de dépôts et CI/CD.

Épreuve 1 : Contrôle Continu (CC) — Durée 1 h 30 (Barème sur 20 points)

Sujet du Contrôle Continu — Modèle Objet Interne, Fusions Avancées & Diagnostic Reflog

Partie 1 : Modèle Objet Git & Adressage par Contenu (6 points)

  1. Détaillez la structure et le rôle des quatre types d’objets fondamentaux de la base Git (blobs, trees, commits, annotated tags). Expliquez pourquoi un blob ne contient ni son nom de fichier ni ses droits d’accès Unix. (3 pts)
  2. Décrivez la formule exacte du préambule injecté avant le hachage cryptographique SHA-1/SHA-256 d’un objet Git. Pourquoi le format Git garantit-il l’immuabilité absolue de l’historique ? (3 pts)

Partie 2 : Stratégies de Fusion & Réécriture d’Historique (7 points)

  1. Distinguez précisément une fusion Fast-Forward d’une fusion tridirectionnelle (3-Way Merge). Définissez le concept de Lowest Common Ancestor (LCA) et son rôle dans la résolution automatique des différences. (3 pts)
  2. Énoncez la règle d’or du git rebase. Pourquoi l’opération de rebase modifie-t-elle systématiquement les identifiants SHA de tous les commits rejoués, et quelles en sont les conséquences pour une équipe de développement ? (4 pts)

Partie 3 : Voyage dans le Temps, Reflog & Diagnostic de Régressions (7 points)

  1. Un développeur exécute par mégarde git reset --hard HEAD~3 puis ferme son terminal. La branche semble avoir perdu 3 commits cruciaux. Expliquez comment le git reflog permet de localiser et récupérer l’intégralité des données en toute sécurité. (3 pts)
  2. Présentez le fonctionnement de git bisect. Démontrez que sa complexité algorithmique est en O(log2 N) pour localiser une régression parmi N commits. Comment automatiser ce processus via un script shell de validation ? (4 pts)
Corrigé type & Barème détaillé du Contrôle Continu

Corrigé Partie 1 (6 points)

  • Modèle objet et séparation blob/tree (3 pts) : Le blob stocke uniquement la suite brute d’octets représentant le contenu d’un fichier. Le nom du fichier, ses permissions (ex: 100644 pour un fichier standard, 100755 pour un exécutable) et sa hiérarchie de répertoires sont portés par l’objet tree qui référence le hash du blob. Cette séparation permet la déduplication parfaite : deux fichiers identiques situés dans des dossiers différents ou renommés partagent le même blob sans duplication de stockage.
  • Formule de hachage et immuabilité (3 pts) : Le préambule Git est composé de : type taille\0contenu (ex: blob 14\0Bonjour monde!). Le hash SHA-1 (40 caractères hexadécimaux) ou SHA-256 (64 caractères) est calculé sur cette séquence complète. Comme chaque commit contient le hash de son arborescence racine (tree) et le hash de ses commits parents, toute modification même minime d’un seul octet ou d’une date propage un changement de hash en cascade jusqu’à la racine du DAG (Merkle Tree), garantissant une intégrité cryptographique absolue.

Corrigé Partie 2 (7 points)

  • Fast-Forward vs 3-Way Merge & LCA (3 pts) : Un Fast-Forward survient lorsque la branche cible n’a pas divergé depuis la création de la branche source : Git déplace simplement le pointeur de référence sans créer de commit de fusion. Un 3-Way Merge intervient en cas de divergence : Git calcule le Lowest Common Ancestor (LCA), c’est-à-dire le dernier ancêtre commun le plus proche dans le graphe DAG, et compare les modifications de la branche source par rapport au LCA et de la branche cible par rapport au LCA pour synthétiser un commit de fusion à deux parents.
  • Règle d’or du rebase (4 pts) : La règle d’or énonce : « Ne jamais rebaser une branche publique déjà partagée avec d’autres collaborateurs ». Le rebase déplace la base d’une branche en réappliquant chaque commit sous forme de patch sur la nouvelle base : comme le parent change, le hash de chaque commit est irrémédiablement recalculé. Si la branche a déjà été poussée sur GitHub, un rebase force un historique divergent pour tous les équipiers, obligeant des fusions enchevêtrées et brisant la synchronisation du dépôt.

Corrigé Partie 3 (7 points)

  • Sauvetage via git reflog (3 pts) : Le journal de références (reflog) consigne localement chaque déplacement du pointeur HEAD (commits, checkouts, resets, merges). Même après un reset hard, les objets commits existent toujours dans la base .git/objects/ et ne sont pas effacés immédiatement (ils attendent le garbage collector git gc après 30 jours par défaut). La commande git reflog show HEAD affiche l’historique des positions : il suffit de repérer l’entrée antérieure au reset (ex: HEAD@{1}) et d’exécuter git checkout -b branche-recup HEAD@{1} ou git reset --hard HEAD@{1} pour restaurer instantanément l’intégralité du travail.
  • Fonctionnement et automatisation de git bisect (4 pts) : git bisect effectue une recherche binaire (dichotomie) dans l’intervalle de commits compris entre un commit réputé fonctionnel (good) et un commit avec régression (bad). À chaque étape, Git extrait le commit médian. Avec N commits, l’algorithme isole le commit coupable en au plus ceil(log2(N)) étapes (ex: pour 1 000 commits, ~10 étapes suffisent). On peut l’automatiser complètement en fournissant un script de test retournant le code de sortie 0 (succès) ou 1 à 127 (échec) : git bisect run pytest tests/test_regression.py.

Épreuve 2 : Examen Terminal (ET) — Durée 2 h 00 (Barème sur 20 points)

Sujet de l’Examen Terminal — Gouvernance de Dépôt, CI/CD Actions & Sécurité des Dépôts

Partie 1 : Gouvernance de Dépôt, Branch Protection & Conventional Commits (7 points)

  1. Comparez les stratégies de branches Git Flow et Trunk-Based Development. Pour quelles raisons les équipes adoptant l’Intégration et le Déploiement Continus (CI/CD) privilégient-elles le Trunk-Based Development ? (3 pts)
  2. Détaillez les quatre règles de protection de branche (Branch Protection Rules) indispensables sur la branche principale main d’un dépôt d’entreprise. (2 pts)
  3. Analysez la norme Conventional Commits 1.0.0. Expliquez comment la structure des messages de commit (type(scope): description) s’articule avec le versionnage sémantique SemVer (MAJOR, MINOR, PATCH) et les ruptures de compatibilité ascendante. (2 pts)

Partie 2 : Orchestration CI/CD avec GitHub Actions & Durcissement Sécuritaire (7 points)

  1. Décrivez la structure hiérarchique d’un workflow GitHub Actions (Workflows, Events, Jobs, Runners, Steps, Actions). Comment fonctionne la directive strategy.matrix et quel est son intérêt pour une suite de tests multi-environnements ? (3 pts)
  2. Analysez la vulnérabilité critique d’injection de commande shell ci-dessous et proposez la remédiation sécurisée conforme aux bonnes pratiques GitHub Security :
    - name: Traiter titre PR
  run: echo "Titre recu : ${{ github.event.pull_request.title }}"
    (2 pts)
  3. Expliquez pourquoi le token par défaut GITHUB_TOKEN doit toujours être configuré selon le principe du moindre privilège via le bloc déclaratif permissions:. Donnez un exemple de configuration pour un workflow de simple audit statique. (2 pts)

Partie 3 : Hygiène de Dépôt, Git LFS & Purge d’Historique (6 points)

  1. Pourquoi Git est-il inefficace pour gérer de gros fichiers binaires (vidéos, modèles IA, bases SQLite) ? Expliquez le fonctionnement de Git LFS (pointeurs textuels légers et déport des objets volumineux). (3 pts)
  2. Un développeur a commité par inadvertance une clé privée AWS dans l’historique d’un dépôt public. Pourquoi la commande git rm cle.pem && git commit ne résout-elle absolument pas le problème ? Décrivez la procédure complète de remédiation en production avec git-filter-repo. (3 pts)
Corrigé type & Barème détaillé de l’Examen Terminal

Corrigé Partie 1 (7 points)

  • Git Flow vs Trunk-Based Development (3 pts) : Git Flow utilise des branches à longue durée de vie (develop, release, hotfix, feature), ce qui retarde l’intégration, favorise des « conflits d’enfer » (merge hell) et ralentit le déploiement. Trunk-Based Development rassemble tous les développeurs sur une unique branche principale main (le tronc), avec des branches de fonctionnalités très courtes (moins de 24 à 48 heures) fusionnées fréquemment via des Pull Requests légères et des feature flags. Ce modèle évite les dérives de code et permet le déploiement continu automatisé en production plusieurs fois par jour.
  • Règles de protection de branche (2 pts) :
    1. Requis d’une Pull Request avec au moins 1 ou 2 approbations de pairs avant fusion.
    2. Passage obligatoire de tous les contrôles d’état CI (tests unitaires, linter, analyse SonarQube).
    3. Signature cryptographique GPG obligatoire de tous les commits pour certifier l’identité des auteurs.
    4. Historique linéaire strict (interdiction des commits de fusion classiques via rebase ou squash & merge obligatoire).
  • Conventional Commits & SemVer (2 pts) : La norme formalise le message de commit :
    - Le type fix incrémente le PATCH (bogue résolu, ex: 1.0.1).
    - Le type feat incrémente le MINOR (nouvelle fonctionnalité compatible, ex: 1.1.0).
    - La présence de ! avant le deux-points (ex: feat!:) ou de la mention textuelle BREAKING CHANGE: dans le corps signale une rupture de compatibilité ascendante et incrémente le MAJOR (ex: 2.0.0). Des outils comme Semantic Release automatisent ainsi le changelog et la création des tags de version.

Corrigé Partie 2 (7 points)

  • Structure GitHub Actions & Matrix (3 pts) : Un workflow YAML réagit à des événements (push, pull_request, schedule). Il orchestre des jobs s’exécutant sur des machines virtuelles (runners). Chaque job contient une suite séquentielle d’étapes (steps) exécutant des scripts shell ou des actions réutilisables. strategy.matrix permet d’instancier dynamiquement un produit cartésien de configurations (ex: Python 3.10, 3.11, 3.12 sur Ubuntu, macOS et Windows), parallélisant les tests sur l’ensemble des matrices de support.
  • Injection de commande et remédiation (2 pts) : La syntaxe ${{ github.event.pull_request.title }} est évaluée avant l’exécution du shell : si un attaquant nomme sa PR "Test"; rm -rf /; echo "", le shell bash exécutera la commande arbitraire injectée, compromettant le runner et les secrets du dépôt. La remédiation obligatoire consiste à passer la valeur par une variable d’environnement intermédiaire :
    - name: Traiter titre PR de facon securisee
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}
  run: echo "Titre recu : $PR_TITLE"
  • Permissions GITHUB_TOKEN (2 pts) : Par défaut sur certains dépôts, le token dispose d’accès d’écriture complets. En cas de faille dans une dépendance ou une action tierce compromise, l’attaquant peut pousser du code malveillant sur le dépôt ou altérer les releases. Pour un audit statique, on restreint explicitement les droits au strict minimum :
    permissions:
  contents: read
  pull-requests: read

Corrigé Partie 3 (6 points)

  • Git LFS (3 pts) : Git standard conserve l’intégralité des versions de chaque fichier dans son historique sous forme compressée : modifier plusieurs fois un fichier de 500 Mo gonfle la taille du dossier .git de plusieurs gigaoctets, rendant chaque clone prohibitif pour l’équipe. Git LFS (Large File Storage) remplace le fichier volumineux dans l’arbre Git par un micro-pointeur textuel de quelques octets contenant son identifiant SHA-256 et sa taille. Le binaire réel est téléversé séparément sur un serveur de stockage d’objets dédié et n’est téléchargé en local que pour le commit actif au checkout.
  • Purge d’un secret avec git-filter-repo (3 pts) : Un git rm crée simplement un nouveau commit supprimant le fichier dans la version courante ; la clé reste présente dans tous les commits antérieurs de l’historique et est accessible à quiconque clone le dépôt. Pour éliminer définitivement le secret :
    1. Révoquer immédiatement la clé privée auprès d’AWS (première mesure d’urgence vitale !).
    2. Utiliser git-filter-repo --path cle.pem --invert-paths ou --replace-text pour réécrire l’intégralité du DAG en purgeant l’objet de tous les arbres et commits.
    3. Forcer la mise à jour des références distantes : git push origin --force --all --tags.
    4. Prévenir l’ensemble des collaborateurs de cloner une copie neuve du dépôt assaini.
