Chapitre 1 — Architecture Globale, Hiérarchie des Ressources & CLI gcloud

Mise en situation

Lorsqu'une entreprise amorce sa migration ou le déploiement de ses applications critiques sur Google Cloud Platform, une mauvaise structuration initiale des projets et des environnements engendre une perte de contrôle totale : autorisations IAM chaotiques, fuites budgétaires impossibles à isoler et dépassements imprévus de quotas d'infrastructure. En tant qu'architecte Cloud B3, vous devez concevoir dès le premier jour une hiérarchie organisationnelle rigoureuse conforme aux recommandations de Google, sélectionner les régions optimales en termes de latence et d'empreinte carbone, et automatiser l'administration quotidienne via le SDK gcloud CLI.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. comprendre l'infrastructure physique planétaire de Google Cloud : Régions, Zones de disponibilité et réseau mondial en fibre optique ;
  2. maîtriser la hiérarchie des ressources GCP : Organisation, Dossiers (Folders), Projets et Ressources ;
  3. différencier Project ID (RFC 1035), Project Name et Project Number et appliquer les conventions de nommage ;
  4. analyser le modèle de facturation, les comptes de facturation (Billing Accounts) et la gestion des quotas d'API ;
  5. maîtriser le SDK gcloud CLI : initialisation, gestion des configurations actives, commutation de contextes et Cloud Shell ;
  6. analyser et résoudre méthodologiquement des validateurs de Project ID, des sélecteurs de régions multi-zones et des parsers de configuration CLI.

1. Infrastructure Mondiale de Google Cloud : Régions, Zones & Réseau Edge

Google Cloud s'appuie sur la même infrastructure matérielle et réseau que celle qui alimente Google Search, YouTube et Gmail. Cette infrastructure est structurée selon un maillage mondial rigoureux :

Régions Géographiques

Une région est un emplacement géographique indépendant (ex: europe-west9 à Paris, europe-west1 en Belgique, us-central1 dans l'Iowa).

Les régions sont choisies selon la proximité des utilisateurs (faible latence), la conformité réglementaire (RGPD) et l'empreinte carbone (indicateur Low Carbon).

Zones de Disponibilité (AZ)

Chaque région comprend au moins 3 zones (ex: europe-west9-a, b, c). Certaines zones peuvent partager un centre de données : consultez la carte Google Cloud, consultée le 30 octobre 2026.

Les zones sont conçues comme des domaines de défaillance distincts. Répartir les composants et examiner leurs dépendances reste nécessaire : cette organisation ne supprime pas automatiquement tous les points uniques de défaillance (SPOF).

Réseau Mondial Privé (Edge)

Google possède l'un des plus grands réseaux privés en fibre optique au monde (câbles sous-marins transocéaniques).

Grâce à plus de 180 points de présence (Points of Presence - PoP), le trafic des utilisateurs entre dans le réseau Google au plus près de leur localisation via le routage Anycast.

Niveaux de Service Réseau : Premium vs Standard Tier

Google Cloud propose deux niveaux de transit réseau mondial :

  • Premium Tier (par défaut) : le trafic est injecté immédiatement dans le réseau privé en fibre de Google au PoP le plus proche de l'utilisateur, garantissant latence minimale et débit maximal.
  • Standard Tier : le trafic transite sur l'Internet public (FAI tiers) jusqu'à la région cible, offrant une alternative économique pour les charges tolérantes à la gigue.

2. Hiérarchie Organisationnelle des Ressources Google Cloud

Toutes les ressources créées dans Google Cloud s'inscrivent dans une arborescence stricte où les politiques de sécurité (IAM) et les règles d'organisation se propagent par héritage du haut vers le bas :

Les 4 Niveaux de la Hiérarchie

  1. Organisation (Niveau 0) : Racine absolue liée au nom de domaine de l'entreprise (ex: entreprise.com via Cloud Identity ou Google Workspace).
  2. Dossiers / Folders (Niveau 1) : Regroupements logiques hiérarchiques par département (ex: Finance, Ingenierie) ou environnement (Prod, Staging).
  3. Projets (Niveau 2) : Unité fondamentale de base. Toutes les ressources doivent être rattachées à un projet.
  4. Ressources (Niveau 3) : Instances Compute Engine, tables BigQuery, buckets Cloud Storage.

Les 3 Identifiants d'un Projet GCP

  • Project ID : Identifiant permanent et unique au monde choisi lors de la création (6 à 30 caractères, minuscules, chiffres, tirets). Immuable.
  • Project Name : Nom lisible par l'humain (ex: Plateforme Vente Prod). Modifiable à tout moment, non unique.
  • Project Number : Numéro entier généré automatiquement par Google (ex: 102938475612), utilisé par les comptes de service système.
Héritage des Politiques IAM dans la Hiérarchie

Une autorisation allow accordée sur un dossier est héritée par ses descendants : supprimer une liaison allow au niveau d'un projet ne retire pas le rôle accordé par le dossier. Toutefois, une politique IAM deny applicable, attachée à une organisation, un dossier ou un projet, peut refuser des permissions prises en charge pour le principal ciblé, même si un rôle hérité les accorde. Le refus ne supprime pas le rôle ; il prime sur les autorisations.

Une règle deny peut prévoir des exceptions de principaux ou de permissions ; une autre règle applicable reste évaluée. Sa condition porte sur les tags de ressource : si elle est vraie ou ne peut pas être évaluée, le refus s'applique. La propagation des changements n'est pas instantanée. Référence consultée le 30 octobre 2026 : politiques IAM deny.

3. Gestion des Quotas, Facturation & Comptes de Facturation

Pour protéger l'infrastructure contre les abus et éviter des factures catastrophiques, Google Cloud applique deux types de garde-fous :

Comptes de Facturation (Cloud Billing Accounts)

  • Un compte de facturation est lié à un moyen de paiement (carte bancaire, facturation mensuelle sur devis pour les grands comptes).
  • Un compte de facturation peut être associé à plusieurs projets. Un projet sans compte de facturation actif ne peut exécuter aucun service payant.
  • Rôles dédiés : Billing Account Administrator (gestion financière) et Billing Account User (liaison d'un projet au compte).

Quotas de Ressources & Limites de Débit

  • Quotas d'allocation : limitent le volume maximal d'une ressource dans une région (ex: 24 vCPUs de type N2 par région).
  • Quotas de taux (Rate limits) : limitent la fréquence d'appels à une API (ex: 1 000 requêtes de création par minute).
  • Les quotas préviennent les dérives de coûts imprévues et peuvent être augmentés sur demande justifiée via la console.

4. Administration avec le SDK gcloud CLI & Cloud Shell

L'interface graphique (Google Cloud Console) est idéale pour l'exploration, mais l'automatisation d'ingénierie repose sur les outils en ligne de commande :

Cloud Shell

  • Machine virtuelle Debian éphémère accessible directement dans le navigateur, gratuite avec 5 Go de stockage persistant dans $HOME.
  • SDK gcloud, kubectl, terraform, Python, Docker et Node.js préinstallés et pré-authentifiés avec le compte connecté.
  • Mode Boîte de boost (Boost mode) temporaire doublant la puissance CPU/RAM de la session.

Le SDK gcloud CLI

Outil unifié pour piloter tous les services Google Cloud :

# Initialisation et authentification
gcloud init
gcloud auth login

# Gestion des configurations
gcloud config set project mon-projet-prod
gcloud config set compute/region europe-west9
gcloud config list

Le SDK organise ses propriétés en sections : core/project, core/account, compute/region, compute/zone.

Exercice 1 — Validateur de Hiérarchie des Ressources et Nommage GCP

Étude de cas Formative Niveau 1 — Acquisition

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Valider la conformité d'un identifiant de projet Google Cloud (Project ID) selon la RFC 1035 et modéliser la hiérarchie des ressources.

Google Cloud organise les ressources selon une hiérarchie stricte :
ORGANIZATION (niveau 0) > FOLDER (niveau 1) > PROJECT (niveau 2) > RESOURCE (niveau 3).

Règles de validation d'un Project ID Google Cloud (RFC 1035) :
- Longueur comprise entre 6 et 30 caractères inclus.
- Composé uniquement de lettres minuscules (a-z), chiffres (0-9) et traits d'union (-).
- Doit obligatoirement commencer par une lettre minuscule.
- Ne doit pas se terminer par un trait d'union.

Opérations soumises à l’analyse :
1. VALIDATE_PROJECT_ID id=<str> :
- Si valide : PROJECT_ID: id=<id> status=VALID format=RFC1035
- Si trop court (< 6) : PROJECT_ID: id=<id> status=INVALID reason=TOO_SHORT
- Si trop long (> 30) : PROJECT_ID: id=<id> status=INVALID reason=TOO_LONG
- Si ne commence pas par une lettre : PROJECT_ID: id=<id> status=INVALID reason=MUST_START_WITH_LETTER
- Si se termine par '-' : PROJECT_ID: id=<id> status=INVALID reason=CANNOT_END_WITH_HYPHEN
- Si caractères non autorisés : PROJECT_ID: id=<id> status=INVALID reason=INVALID_CHARS
2. HIERARCHY_LEVEL type=<ORGANIZATION|FOLDER|PROJECT|RESOURCE> :
- HIERARCHY: type=<type> level=<L> parent=<parent>

Cas d’exemple
VALIDATE_PROJECT_ID id=tp-cloud-b3-prod
HIERARCHY_LEVEL type=PROJECT
Trois indices, rédigés en mots
  1. Vérifiez la longueur avant de tester les expressions régulières ou les caractères.
  2. Testez si id[0].isalpha() et id[0].islower() pour le premier caractère.
  3. Pour les niveaux : ORGANIZATION -> (0, NONE), FOLDER -> (1, ORGANIZATION), PROJECT -> (2, FOLDER), RESOURCE -> (3, PROJECT).

Exercice 2 — Sélecteur de Région et Répartition Multi-Zones GCP

Étude de cas Formative Niveau 2 — Application

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Répartir fictivement des instances entre zones et distinguer répartition et résilience démontrée.

Utilisez ce référentiel figé pour la grille : il ne constitue ni un inventaire officiel à jour ni une mesure actuelle de l’empreinte carbone.
- europe-west1 : Belgique, zones a, b, c, low_carbon=YES
- europe-west9 : Paris, zones a, b, c, low_carbon=YES
- us-central1 : Iowa, zones a, b, c, f, low_carbon=NO
- asia-east1 : Taïwan, zones a, b, c, low_carbon=NO

REGION_INFO region=<nom> retourne REGION: name=<nom> location=<lieu> zones_count=<N> low_carbon=<YES|NO>, ou REGION: name=<nom> status=UNKNOWN si elle est absente du référentiel.

MULTI_ZONE_DEPLOY region=<nom> instance_count=<N> simule une répartition dans une région connue. Si N est inférieur à 1, retourner DEPLOY: region=<nom> total=<N> status=INVALID_INSTANCE_COUNT.
Sinon, répartir les instances sur les zones dans l’ordre donné : division entière, puis reste attribué de gauche à droite. Afficher chaque zone, y compris celles qui reçoivent zéro instance, et le statut :
- SINGLE_ZONE_NO_REDUNDANCY si une seule zone reçoit des instances ;
- MULTI_ZONE_NO_GUARANTEE si plusieurs zones en reçoivent.
Format : DEPLOY: region=<nom> total=<N> allocation=<zone1:n1,zone2:n2,...> status=<statut>.

La répartition ne crée aucune ressource et ne démontre pas la haute disponibilité. Il faut notamment vérifier capacité et quotas, dépendances, contrôles de santé, charge et basculement. Voir les principes de conception pour la disponibilité.

Cas d’exemple
REGION_INFO region=europe-west9
MULTI_ZONE_DEPLOY region=europe-west9 instance_count=5
Deux indices, rédigés en mots
  1. Pour N instances et M zones, calculez le quotient et le reste ; les premières zones reçoivent une instance supplémentaire.
  2. Comptez les zones réellement occupées et ne déduisez jamais un basculement fonctionnel de la seule répartition.

Exercice 3 — Parser et Simulateur de Contexte CLI gcloud

Étude de cas Formative Niveau 3 — Raisonnement

Cette vérification est une aide à l’apprentissage : elle ne donne pas de note et ne valide pas les acquis.

Objectif : Simuler le gestionnaire de configurations gcloud CLI et gérer les contextes de projet, de zone et de compte.

Le SDK Google Cloud (CLI gcloud) gère des profils de configuration contenant les paramètres par défaut de l'opérateur.

Opérations soumises à l’analyse :
1. gcloud config set <section>/<propriete> <valeur> ou gcloud config set <propriete> <valeur> :
Met à jour la valeur et Indiquez UPDATED: <cle>=<valeur>.
(Si la clé est sans slash, par exemple project, elle est stockée sous core/project ; account sous core/account ; sinon sous sa forme complète compute/region, compute/zone).
2. gcloud config get <propriete> :
Indiquez GET: <cle>=<valeur> (ou GET: <cle>=(unset) si non définie).
3. gcloud config list :
Indiquez la liste triée alphabétiquement des propriétés définies sous la forme :
CONFIG: [<section>] <propriete>=<valeur>.

Cas d’exemple
gcloud config set project tp-module1-prod
gcloud config set compute/region europe-west9
gcloud config get project
gcloud config list
Trois indices, rédigés en mots
  1. Normalisez les clés simples : "project" -> ("core", "project"), "account" -> ("core", "account").
  2. Pour "compute/region" -> section "compute", propriété "region".
  3. Triez les sections et les propriétés pour la commande "config list".

6. QCM — niveau examen

Quel est l'ordre exact de la hiérarchie organisationnelle des ressources dans Google Cloud du niveau racine vers les ressources ?

La hiérarchie Google Cloud s'organise strictement du haut vers le bas : Organisation (niveau 0) > Dossiers (niveau 1) > Projets (niveau 2) > Ressources (niveau 3).

Laquelle de ces chaînes est un identifiant Project ID Google Cloud VALIDE selon la RFC 1035 ?

« mon-projet-cloud-2026 » est valide : entre 6 et 30 caractères, lettres minuscules, chiffres et tirets, commençant par une lettre et ne se terminant pas par un tiret.

Combien de zones de disponibilité au minimum une région Google Cloud contient-elle ?

Une région comprend au moins 3 zones. Leur présence ne garantit pas à elle seule la haute disponibilité : celle-ci dépend notamment de la redondance des composants et du basculement.

Quelle commande gcloud permet de définir le projet actif dans la configuration courante ?

La syntaxe standard du SDK gcloud pour définir le projet actif est « gcloud config set project [ID] » (ou « gcloud config set core/project [ID] »).

Que se passe-t-il si un utilisateur reçoit le rôle Viewer au niveau d'un dossier contenant 5 projets ?

La liaison allow est héritée par les projets descendants. Une règle deny applicable au principal et aux permissions prises en charge peut toutefois les refuser ; ses conditions et exceptions doivent être vérifiées, ainsi que les autres règles deny applicables.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Tenter de modifier le Project ID après la création d'un projet : le Project ID est strictement immuable, seul le Project Name peut être changé.
  • Attribuer des rôles IAM trop permissifs à l'Organisation en supposant qu'une modification allow au niveau d'un projet supprime le rôle hérité ; un deny applicable peut refuser certaines permissions, sous conditions.
  • Oublier de relier un projet à un compte de facturation actif : toutes les API de calcul, de stockage et de bases de données restent bloquées.
  • Travailler dans la mauvaise configuration gcloud CLI sans vérifier le projet actif, risquant de supprimer accidentellement des ressources de production.

8. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Conception de l'arbre organisationnel : définir l'arborescence de dossiers par direction et environnement (Dossier Production vs Hors-Production) sous l'Organisation racine.
  2. Gouvernance des projets et respect du standard RFC 1035 : nommer rigoureusement les identifiants Project ID selon la nomenclature d'entreprise en minuscules sans tiret terminal.
  3. Rattachement financier et monitoring budgétaire : associer chaque projet à son compte de facturation (Cloud Billing) et définir les budgets d'alerte dès l'initialisation.
  4. Automatisation via configurations gcloud CLI : créer des profils de configuration nommés (gcloud config configurations) pour isoler les contextes de travail Dev et Prod.

9. Révision active

Résumé essentiel
  • Google Cloud déploie ses services sur des Régions géographiques indépendantes comprenant chacune au moins 3 Zones de disponibilité reliées par un réseau en fibre privé.
  • La hiérarchie des ressources suit l'ordre Organisation > Dossiers > Projets > Ressources : les autorisations IAM allow sont héritées, mais une politique deny applicable peut refuser des permissions prises en charge.
  • Le Project ID est l'identifiant unique permanent mondial (6 à 30 caractères, conforme RFC 1035), tandis que le Project Name est modifiable et le Project Number est généré par Google.
  • Les comptes de facturation (Cloud Billing) alimentent les projets, et les quotas protègent l'infrastructure contre les emballements de consommation.
  • Le SDK gcloud CLI et Cloud Shell constituent les outils standards d'ingénierie pour piloter, configurer et automatiser les déploiements GCP.

Checklist de maîtrise

  3. Project ID : Identifiant permanent, unique au monde et immuable d'un projet Google Cloud respectant la norme RFC 1035.
  4. Cloud Shell : Environnement de terminal Linux Debian dans le navigateur avec 5 Go de stockage et les outils d'administration Cloud préconfigurés.
  5. SDK gcloud CLI : Outil officiel en ligne de commande permettant de gérer et automatiser les ressources et configurations Google Cloud.
  6. Google Cloud déploie ses services sur des Régions géographiques indépendantes comprenant chacune au moins 3 Zones de disponibilité reliées par un réseau en fibre privé.
