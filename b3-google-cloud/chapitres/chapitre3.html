Chapitre 3 — Calcul & Virtualisation (Compute Engine, GKE, Cloud Run & App Engine)

Module 3 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Le choix du moteur d'exécution de calcul dans Google Cloud conditionne directement la vitesse de livraison, l'efficacité opérationnelle et la facture mensuelle d'une organisation. Déployer de simples conteneurs web sur des VMs Compute Engine surdimensionnées gérées à la main entraîne des coûts astronomiques et une maintenance lourde (patchs d'OS). À l'inverse, tenter d'exécuter des calculs temps réel à état ou des protocoles personnalisés sur du Serverless pur peut conduire à des blocages techniques majeurs. En tant qu'architecte Cloud B3, vous devez maîtriser l'éventail complet des options de calcul GCP, dimensionner rigoureusement vos instances IaaS et orchestrer des déploiements conteneurisés élastiques avec GKE et Cloud Run.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. dimensionner et configurer les instances Google Compute Engine selon les séries de calcul (E2, N2, C2, Spot VMs) ;
  2. comprendre le calcul des SLA de disponibilité mono-zone (99.5%) et multi-zones (99.99%) ;
  3. concevoir des Groupes d'Instances Gérés (MIG) avec auto-scaling élastique et auto-healing supervisé par Health Checks ;
  4. comparer les modes opérationnels de Google Kubernetes Engine : GKE Standard versus GKE Autopilot managé ;
  5. maîtriser le déploiement Serverless conteneurisé sur Cloud Run : concurrence de requêtes, révisions immuables et Traffic Splitting ;
  6. développer en Python 3 des dimensionneurs de VM, des moteurs d'autoscaling MIG et des routeurs de trafic Cloud Run.

1. Google Compute Engine (GCE) : Familles de Machines & SLA

Google Compute Engine (GCE) est le service IaaS permettant d'exécuter des machines virtuelles sur l'infrastructure physique de Google. Les types de machines sont répartis en familles optimisées :

Familles de Machines Virtuelles

  • Série E2 (Économique / Partagée) : Processeurs x86 dynamiques (Intel/AMD) sans surcoût. Idéale pour les environnements de dev, les serveurs web modestes et les microservices peu consommateurs (ex: e2-micro, e2-medium).
  • Série N2 / N2D (Polyvalente) : Équilibre parfait entre vCPU et RAM (jusqu'à 128 vCPUs et 864 Go de RAM). Pour bases de données et progiciels métier.
  • Série C2 / C3 (Optimisée Calcul) : Hautes fréquences d'horloge fixes. Idéale pour le calcul scientifique, l'encodage vidéo et le gaming.
  • Série M2 / M3 (Optimisée Mémoire) : Jusqu'à 12 To de RAM pour SAP HANA et bases in-memory massives.
  • Instances Spot (ex-Préemptibles) : Capacité excédentaire vendue avec jusqu'à 91% de réduction, mais que Google peut interrompre avec un préavis de 30 secondes. Idéale pour les batchs et le rendu.

Engagements de Service (SLA) & Disques Persistants

Le taux de disponibilité mensuel contractuel de GCE dépend de l'architecture déployée :

  • VM Mono-zone avec Persistent Disk SSD : SLA de 99.5% (temps d'indisponibilité mensuelle max = 216 minutes).
  • Instances réparties Multi-zones (MIG) : SLA de 99.99% (temps d'arrêt mensuel max = 4.32 minutes).

Stockage bloc attaché :

  • Standard Persistent Disk (pd-standard) : disques magnétiques économiques pour sauvegardes.
  • Balanced Persistent Disk (pd-balanced) : compromis SSD performances/prix standard.
  • SSD Persistent Disk (pd-ssd) : haute performance IOPS pour bases relationnelles.
  • Local SSD : SSD NVMe physiquement rattachés à l'hôte (très haute vitesse, non persistant après arrêt de la VM).

2. Groupes d'Instances Gérés (MIG) : Auto-scaling & Auto-healing

Un groupe d'instances géré (Managed Instance Group - MIG) permet de piloter un ensemble de VMs identiques comme une seule entité homogène et élastique :

Instance Template & Déploiement

  • Le MIG instancie toutes ses machines à partir d'un modèle d'instance (Instance Template) immuable définissant l'OS, le type de machine, le disque et les scripts de démarrage (startup-script).
  • MIG Zonal : toutes les VMs sont dans la même zone.
  • MIG Régional : les VMs sont automatiquement réparties sur plusieurs zones de la région pour garantir la tolérance aux pannes zonales.

Auto-scaling & Auto-healing

  • Auto-scaling : adapte dynamiquement le nombre de VMs entre un minimum et un maximum pour maintenir une cible de métrique (ex: Target CPU = 60% ou débit de requêtes HTTP du Load Balancer).
  • Auto-healing (Auto-guérison) : une sonde de santé (Health Check) envoie des requêtes périodiques à l'application. Si l'application échoue au test de santé, le MIG recrée automatiquement la VM défaillante à neuf.
  • Rolling Updates : mise à jour progressive du parc de VMs avec contrôle de la surcapacité maximale (maxSurge) et de l'indisponibilité maximale (maxUnavailable).

3. Google Kubernetes Engine (GKE) : Standard vs Autopilot

Google est le créateur originel de Kubernetes (dérivé de son système interne Borg). GKE est la plateforme Kubernetes managée de référence sur le marché :

GKE Mode Standard

  • Google gère le plan de contrôle (Control Plane : API Server, etcd) avec SLA 99.95% à 99.99%.
  • L'administrateur configure et paie les nœuds workers (VMs Compute Engine sous-jacentes, pools de nœuds).
  • Contrôle total sur les versions de noyau, les démons système et les GPU spécifiques.

GKE Mode Autopilot (Recommandé)

  • Google prend entièrement en charge la gestion, le dimensionnement, la mise à l'échelle et le durcissement de sécurité de l'ensemble de l'infrastructure des nœuds.
  • Facturation uniquement basée sur les ressources réelles demandées par les Pods (vCPU, RAM, stockage), et non sur les VMs entières.
  • Application native des meilleures pratiques de sécurité CIS Kubernetes et mise à l'échelle automatique des nœuds intégrée sans configuration.

4. Serverless Moderne : Cloud Run vs Cloud Functions & App Engine

Google Cloud propose trois solutions sans serveur (Serverless) selon le niveau d'abstraction souhaité :

Cloud Run (PaaS Conteneurisé)

  • Exécute n'importe quel conteneur OCI (Docker) répondant sur un port HTTP ou gRPC.
  • Scale-to-Zero : aucun coût lorsqu'aucune requête n'est traitée.
  • Concurrence : un seul conteneur peut traiter jusqu'à 1 000 requêtes simultanées (extrême rentabilité).
  • Révisions immuables : support natif de Canary Release et de Traffic Splitting sans interruption.

Cloud Functions v2 (FaaS Événementiel)

  • Exécution de petits extraits de code (fonctions Python, Node.js, Go) sans gérer de conteneur.
  • Déclenchée par des événements Cloud Storage, Pub/Sub, Firestore ou Firestore via Eventarc.
  • Bâtie directement au-dessus de l'infrastructure Cloud Run en version 2.

App Engine (Historique)

  • Plateforme PaaS historique de Google lancée en 2008.
  • Environnement Standard (runtimes sandboxés très rapides) et Environnement Flexible (conteneurs Docker).
  • Aujourd'hui largement supplantée par la flexibilité et la modernité de Cloud Run pour les nouveaux projets.
Canary Deployment sur Cloud Run

Déployer une nouvelle version applicative sans risque : en déployant la révision v2 sans lui attribuer 100% du trafic, on utilise la commande gcloud run services update-traffic [SERVICE] --to-revisions=v1=80,v2=20 pour envoyer 20% des requêtes vers v2. En observant les métriques de latence et d'erreurs, on bascule à 100% ou on annule en une seconde.

Exercice 1 — Dimensionneur d'Instances Compute Engine et Calcul de SLA Composite

Étude de cas Niveau 1 — Acquisition

Objectif : Vérifier les caractéristiques des séries de VM Compute Engine et calculer le SLA de disponibilité.

Google Compute Engine (GCE) propose différentes familles de machines virtuelles :
Catalogue des séries standard :
- e2-micro : vcpu=2, ram_gb=1, family=COST_OPTIMIZED
- e2-medium : vcpu=2, ram_gb=4, family=COST_OPTIMIZED
- e2-standard-4 : vcpu=4, ram_gb=16, family=GENERAL_PURPOSE
- n2-standard-8 : vcpu=8, ram_gb=32, family=GENERAL_PURPOSE
- c2-standard-16 : vcpu=16, ram_gb=64, family=COMPUTE_OPTIMIZED

SLA de disponibilité mensuel Compute Engine :
- Déploiement mono-zone (Single-Zone VM) : sla=99.5% max_downtime_monthly=216m
- Déploiement multi-zones (Multi-Zone MIG / HA) : sla=99.99% max_downtime_monthly=4.32m

Commandes lues sur STDIN :
1. GCE_SIZE machine_type=<type> :
GCE: type=<type> vcpu=<v> ram_gb=<r> family=<fam> (ou GCE: type=<type> status=UNKNOWN).
2. GCE_SLA multi_zone=<true|false> :
GCE_SLA: multi_zone=<bool> sla=<sla> max_downtime=<time>

Cas d’exemple
GCE_SIZE machine_type=e2-standard-4
GCE_SLA multi_zone=true
Résolution attendue
GCE: type=e2-standard-4 vcpu=4 ram_gb=16 family=GENERAL_PURPOSE
GCE_SLA: multi_zone=true sla=99.99% max_downtime=4.32m

Machine polyvalente 4 vCPU et SLA haute disponibilité multi-zones.

Deux indices, rédigés en mots
  1. Structurez les machines dans un dictionnaire type -> (vcpu, ram, family).
  2. Branchez multi_zone == "true" vs "false" pour le calcul de SLA.

Exercice 2 — Moteur d'Auto-scaling pour Groupes d'Instances Gérés (MIG)

Étude de cas Niveau 2 — Application

Objectif : Calculer la taille cible d'un Managed Instance Group (MIG) selon la charge CPU cible et les limites d'échelle.

Un groupe d'instances géré (MIG) ajuste automatiquement le nombre d'instances selon la formule :
desired = math.ceil(current_instances * (current_cpu / target_cpu)).
La valeur calculée doit être bornée :
- Si desired > max_instances : desired = max_instances.
- Si desired < min_instances : desired = min_instances.

Actions :
- Si desired > current_instances : action=SCALE_UP
- Si desired < current_instances : action=SCALE_DOWN
- Si desired == current_instances : action=NO_CHANGE

Commande STDIN :
MIG_AUTOSCALE min=<min> max=<max> target_cpu=<t> current_instances=<c> current_cpu=<cur_cpu>.
Sortie :
MIG: current=<c> target_cpu=<t> current_cpu=<cur_cpu> desired=<d> action=<action>

Cas d’exemple
MIG_AUTOSCALE min=2 max=10 target_cpu=0.60 current_instances=3 current_cpu=0.85
Résolution attendue
MIG: current=3 target_cpu=0.60 current_cpu=0.85 desired=5 action=SCALE_UP

3 * (0.85 / 0.60) = 4.25 -> 5 instances, déclenchant un Scale-up.

Deux indices, rédigés en mots
  1. Convertissez target_cpu et current_cpu en float.
  2. Utilisez math.ceil(cur * (cur_cpu / target_cpu)) puis appliquez max(min_val, min(max_val, desired)).

Exercice 3 — Déployeur Serverless Cloud Run et Répartition de Trafic Multi-Révisions

Étude de cas Niveau 3 — Raisonnement

Objectif : Valider la répartition de trafic entre révisions Cloud Run et simuler le routage d'une requête client.

Google Cloud Run permet de répartir le trafic HTTP entre plusieurs révisions (Canary Release / Blue-Green) :

Commandes lues sur STDIN :
1. VALIDATE_SPLIT revs=<r1:p1,r2:p2,...> :
- Vérifie que la somme des pourcentages vaut exactement 100.
- Si valide : SPLIT: status=VALID revs_count=<N> allocation=<revs>
- Si somme != 100 : SPLIT: status=INVALID reason=SUM_MUST_BE_100 current_sum=<S>
2. ROUTE_REQUEST req_id=<id> revs=<r1:p1,r2:p2,...> :
- Calcule hash_val = sum(ord(c) for c in req_id) % 100.
- Parcourt les révisions dans l'ordre de gauche à droite. La requête est attribuée à la première révision dont le cumul des pourcentages dépasse strictement hash_val.
- ROUTE: req_id=<id> bucket=<hash_val> target_revision=<rev>

Cas d’exemple
VALIDATE_SPLIT revs=v1:80,v2:20
ROUTE_REQUEST req_id=REQ-1001 revs=v1:80,v2:20
Résolution attendue
SPLIT: status=VALID revs_count=2 allocation=v1:80,v2:20
ROUTE: req_id=REQ-1001 bucket=71 target_revision=v1

Routage déterministe avec Canary deployment 80/20.

Deux indices, rédigés en mots
  1. La répartition de trafic Cloud Run Traffic Split affecte des pourcentages stricts entre les différentes révisions du conteneur.
  2. Vérifiez que la somme des quotas de trafic alloués aux révisions déployées atteint exactement 100%.

6. QCM — niveau examen

Quel est le SLA de disponibilité mensuel garanti par Google pour des instances Compute Engine réparties sur plusieurs zones de disponibilité (MIG Régional) ?

Google garantit un SLA de 99.99% pour les déploiements multi-zones d'instances Compute Engine (contre 99.5% pour une VM isolée dans une seule zone).

Dans un groupe d'instances géré (MIG), quel mécanisme recrée automatiquement une VM dont l'application ne répond plus aux requêtes de la sonde de santé ?

L'Auto-healing supervise la santé applicative de chaque VM via un Health Check et déclenche automatiquement la recréation de l'instance si la sonde échoue.

Quelle est la principale différence de facturation entre GKE Standard et GKE Autopilot ?

En mode Autopilot, l'utilisateur ne paie pas pour la capacité inutilisée des nœuds workers, mais uniquement pour les ressources CPU et mémoire déclarées par ses Pods.

Quel service Google Cloud permet d'exécuter n'importe quel conteneur Docker répondant sur un port HTTP avec passage à l'échelle à zéro (Scale-to-Zero) sans gérer d'infrastructure ?

Cloud Run est la plateforme Serverless conteneurisée de référence de Google, capable de démarrer en quelques millisecondes et de passer à zéro instance en l'absence de requêtes.

Quel pourcentage maximal d'économie les instances Spot de Compute Engine peuvent-elles offrir par rapport au tarif à la demande standard ?

Les instances Spot (qui remplacent les anciennes VMs préemptibles) permettent d'obtenir jusqu'à 60% à 91% d'économie sur les tarifs de calcul Compute Engine.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Utiliser des instances Spot pour des bases de données relationnelles principales ou des applications à état sans réplication : la VM peut s'arrêter à tout moment.
  • Configurer un Health Check d'auto-healing sur un point d'accès dépendant d'une base de données externe en panne : le MIG redémarrera en boucle toutes les VMs saines sans résoudre le problème.
  • Déployer des microservices simples sur un cluster GKE Standard sous-utilisé : les nœuds minimaux facturés en permanence coûtent beaucoup plus cher qu'une exécution serverless sur Cloud Run.
  • Oublier de configurer le paramètre de concurrence sur Cloud Run (laisser à 1 par défaut pour des applications I/O bound), entraînant un surcoût d'instances inutiles.

8. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Choix du modèle de calcul approprié : privilégier Cloud Run pour les microservices HTTP sans état, GKE Autopilot pour les architectures microservices complexes, et Compute Engine pour les applications monolithiques ou legacy avec exigences d'OS spécifiques.
  2. Configuration de la résilience zonale Compute Engine : regrouper les VMs dans un MIG Régional distribué sur 3 zones pour bénéficier du SLA 99.99% et activer les Health Checks d'auto-guérison.
  3. Optimisation des coûts avec les instances Spot : réserver des pools de nœuds d'instances Spot pour les traitements par lots asynchrones ou les calculs de staging afin d'économiser jusqu'à 90%.
  4. Industrialisation des déploiements sans interruption : configurer le fractionnement de trafic (Traffic Splitting) progressif sur Cloud Run pour valider les nouvelles versions applicatives.

9. Révision active

Résumé essentiel
  • Google Compute Engine propose des séries adaptées (E2 économique, N2 équilibrée, C2 calcul) avec un SLA atteignant 99.99% en déploiement multi-zones.
  • Les Groupes d'Instances Gérés (MIG) garantissent l'élasticité automatique (Auto-scaling) et la tolérance aux pannes (Auto-healing) via des sondes de santé.
  • GKE Autopilot décharge l'équipe de la maintenance des nœuds Kubernetes et facture uniquement les ressources réellement allouées aux Pods.
  • Cloud Run représente le standard serverless moderne : exécution de conteneurs arbitraires, scale-to-zero, concurrence élevée et basculement de trafic instantané.
  • Cloud Functions v2 est idéal pour l'événementiel asynchrone (Eventarc/PubSub), tandis qu'App Engine est progressivement remplacé par Cloud Run.

Checklist de maîtrise

  • Savez-vous comparer les séries de machines Compute Engine E2, N2, C2 et les instances Spot ?
  • Connaissez-vous le calcul du SLA mono-zone (99.5%) vs multi-zones (99.99%) ?
  • Pouvez-vous expliquer le fonctionnement conjoint de l'auto-scaling et de l'auto-healing dans un MIG ?
  • Savez-vous expliquer pourquoi GKE Autopilot est plus simple et sécurisé que GKE Standard ?
  • Comprenez-vous le mécanisme de Traffic Splitting sur Cloud Run pour réaliser un déploiement Canary ?

Les 8 notions à connaître absolument

  1. Compute Engine (GCE) : Service IaaS de Google Cloud fournissant des machines virtuelles hautement configurables avec disques persistants.
  2. Managed Instance Group (MIG) : Groupe de machines virtuelles identiques gérées automatiquement avec fonctions d'auto-scaling, d'auto-healing et de mises à jour progressives.
  3. GKE Autopilot : Mode opérationnel de Kubernetes managé où Google gère intégralement l'infrastructure des nœuds et facture uniquement la consommation réelle des Pods.
  4. Cloud Run : Plateforme Serverless exécutant des conteneurs sans état avec passage à l'échelle automatique jusqu'à zéro et facturation à la milliseconde.
  5. Instances Spot (Préemptibles) : Instances Compute Engine à prix très réduit que Google peut récupérer avec un préavis de 30 secondes pour d'autres charges prioritaires.
