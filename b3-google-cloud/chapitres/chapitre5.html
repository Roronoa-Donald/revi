Chapitre 5 — Stockage Distribué, Bases de Données & Pipeline Big Data

Module 5 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans les applications d'entreprise modernes générant des téraoctets de données hétérogènes (fichiers multimédias, transactions bancaires, télémétrie IoT, analytics décisionnels), choisir le mauvais moteur de persistance conduit à des goulets d'étranglement catastrophiques ou à des factures de stockage disproportionnées. Utiliser Cloud SQL pour de l'analytique de masse sature rapidement la base, tandis que stocker des archives sur Cloud Storage Standard sans politique de cycle de vie génère des surcoûts considérables. En tant qu'architecte de données Cloud B3, vous devez maîtriser la matrice de sélection des bases Google Cloud, automatiser le cycle de vie des objets GCS et orchestrer des pipelines d'ingestion résilients avec Pub/Sub.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. maîtriser Google Cloud Storage (GCS) : nommage mondial unique, niveaux de redondance et 11 9s de durabilité ;
  2. configurer des règles d'Object Lifecycle Management pour migrer automatiquement les données vers Nearline, Coldline et Archive ;
  3. comparer Cloud SQL (MySQL, PostgreSQL, SQL Server) et Cloud Spanner (NewSQL mondial avec SLA 99.999% et horloges TrueTime) ;
  4. différencier les moteurs NoSQL managés : Firestore (documents temps réel) versus Cloud Bigtable (large-colonne sub-milliseconde) ;
  5. concevoir une architecture d'ingestion asynchrone découplée avec Cloud Pub/Sub (Topics, Subscriptions Pull/Push et Ack Deadlines) ;
  6. développer en Python 3 des moteurs de cycle de vie GCS, des matrices de sélection de bases de données et des simulateurs Pub/Sub.

1. Google Cloud Storage (GCS) : Classes d'Objets & Cycle de Vie

Google Cloud Storage (GCS) est le service de stockage d'objets non structurés (blobs) hautement résilient, offrant une durabilité annuelle de 99.999999999% (11 9s). Les fichiers sont organisés dans des conteneurs appelés Buckets dont le nom doit être unique au monde :

Les 4 Classes de Stockage

  • Standard Storage : Données actives fréquemment consultées (sites web, vidéos en streaming, données courantes). Pas de durée minimale de conservation.
  • Nearline Storage : Données consultées au maximum une fois par mois (sauvegardes mensuelles, rapports périodiques). Durée minimale de facturation : 30 jours.
  • Coldline Storage : Données consultées au plus une fois par trimestre (archivage intermédiaire, plans de reprise d'activité DRP). Durée minimale : 90 jours.
  • Archive Storage : Données froides rarement accédées (< 1 fois par an, conformité fiscale ou juridique). Coût au Go le plus bas du marché. Durée minimale : 365 jours.

Gestion Automatisée du Cycle de Vie (Lifecycle Rules)

Une politique de cycle de vie applique automatiquement des actions selon des conditions d'âge :

{
  "action": {"type": "SetStorageClass", "storageClass": "NEARLINE"},
  "condition": {"age": 30}
},
{
  "action": {"type": "SetStorageClass", "storageClass": "ARCHIVE"},
  "condition": {"age": 365}
}

Cette automatisation réduit la facture de stockage de plus de 80% sans modifier le moindre code applicatif.

Contrôle d'Accès : Uniform Bucket-Level Access vs Signed URLs

Par défaut, Google Cloud préconise Uniform Bucket-Level Access qui unifie le contrôle d'accès uniquement au niveau IAM (éliminant les ACLs complexes objet par objet). Pour permettre à un utilisateur externe de téléverser ou télécharger un fichier temporairement sans compte Google, on génère une URL signée (Signed URL) avec une durée de validité limitée (ex: 15 minutes).

2. Bases Relationnelles : Cloud SQL vs Cloud Spanner

Google Cloud propose deux approches relationnelles selon l'échelle et les contraintes géographiques :

Cloud SQL (Régional Managé)

  • Moteurs compatibles standards : MySQL, PostgreSQL et SQL Server.
  • Gestion automatique des sauvegardes, correctifs d'OS et réplicas de lecture (Read Replicas).
  • Haute Disponibilité (HA) : basculement automatique vers une instance standby synchrone dans une zone secondaire en cas de sinistre zonal (SLA 99.95%).
  • Limite : stockage plafonné à 64 To et montée en charge verticale (scale-up).

Cloud Spanner (NewSQL Mondial Distribué)

  • Base de données relationnelle distribuée à l'échelle de la planète avec montée en charge horizontale illimitée (scale-out).
  • Cohérence stricte ACID mondiale garantie par la technologie d'horloges matérielles synchronisées Google TrueTime (combinaison d'horloges atomiques et de récepteurs GPS dans chaque datacenter).
  • Disponibilité record de 99.999% (moins de 5 minutes d'indisponibilité par an). Moteur officiel de Google Play, Google Ads et des plus grandes banques mondiales.

3. Bases NoSQL : Firestore vs Cloud Bigtable

Pour les modèles de données non structurés ou semi-structurés ne nécessitant pas de schéma rigide :

Firestore (NoSQL Document Temps Réel)

  • Base de données NoSQL orientée documents (organisée en collections et documents JSON).
  • Synchronisation bidirectionnelle en temps réel des données avec les clients web et mobiles via SDK.
  • Support natif du mode hors-connexion (offline data persistence).
  • Idéale pour les applications mobiles, catalogues de produits, profils utilisateurs et jeux en ligne.

Cloud Bigtable (NoSQL Large-Colonne Analytique)

  • Le moteur originel créé par Google en 2006 pour indexer le Web et animer Google Maps.
  • Base NoSQL large-colonne (Wide-column / clé-valeur massivement distribuée) compatible API Apache HBase.
  • Latence de lecture et d'écriture sub-milliseconde sur des pétaoctets de données.
  • Idéale pour la télémétrie IoT, les séries temporelles financières, les logs publicitaires et l'entraînement de modèles IA.

4. Ingestion de Données Asynchrone : Cloud Pub/Sub & Écosystème Big Data

Dans une architecture distribuée, les composants ne doivent jamais communiquer par appels directs bloquants. Cloud Pub/Sub assure le découplage asynchrone mondial :

Fonctionnement de Cloud Pub/Sub

  • Topic (Sujet) : flux nommé où les producteurs (Publishers) envoient des messages sans connaître les destinataires.
  • Subscription (Abonnement) : file de réception dédiée rattachée à un topic. Chaque abonnement reçoit une copie de tous les messages publiés.
  • Mode Pull : le consommateur interroge activement Pub/Sub pour récupérer des lots de messages.
  • Mode Push : Pub/Sub envoie immédiatement une requête HTTP POST webhook à un endpoint (ex: service Cloud Run).
  • Ack Deadline : délai maximal accordé au consommateur pour acquitter le traitement (défaut 10s). Si le délai expire sans accusé de réception, Pub/Sub renvoie le message.

La Suite Analytique Google Cloud

  • BigQuery : entrepôt de données (Data Warehouse) Serverless permettant d'analyser des pétaoctets de données en SQL avec temps de réponse en secondes.
  • Cloud Dataflow : moteur de traitement distribué stream/batch unifié basé sur Apache Beam.
  • Cloud Dataproc : clusters managés pour exécuter des écosystèmes open-source Hadoop et Apache Spark.

Exercice 1 — Moteur de Transition de Cycle de Vie Cloud Storage (Lifecycle Management)

Python Niveau 1 — Acquisition

Objectif : Simuler les règles d'archivage et de transition automatique de classes d'objets dans Google Cloud Storage.

Google Cloud Storage propose 4 classes de stockage à coûts décroissants :
- STANDARD : accès chaud fréquent (durée minimale 0 jour)
- NEARLINE : consultation mensuelle (durée minimale 30 jours)
- COLDLINE : consultation trimestrielle (durée minimale 90 jours)
- ARCHIVE : archivage à long terme (durée minimale 365 jours)

Commande STDIN :
LIFECYCLE_EVAL current_class=<class> age_days=<N> target_class=<class> min_age=<M>.
Sorties :
- Si age_days >= min_age :
LIFECYCLE: current=<cur> target=<target> age=<N> action=TRANSITION_APPLIED status=SUCCESS
- Sinon :
LIFECYCLE: current=<cur> target=<target> age=<N> action=NONE status=CONDITION_NOT_MET

Entrée du programme
LIFECYCLE_EVAL current_class=STANDARD age_days=35 target_class=NEARLINE min_age=30
Sortie attendue
LIFECYCLE: current=STANDARD target=NEARLINE age=35 action=TRANSITION_APPLIED status=SUCCESS

Objet âgé de 35 jours dépassant le seuil de 30 jours pour transition vers Nearline.

Deux indices, rédigés en mots
  1. Comparez int(age_days) >= int(min_age).
  2. Affichez les sorties formatées avec statut SUCCESS ou CONDITION_NOT_MET.

Exercice 2 — Sélecteur d'Architecture de Données GCP (Decision Matrix)

Python Niveau 2 — Application

Objectif : Déterminer le service de stockage ou de base de données Google Cloud optimal selon le modèle de données, l'échelle et les contraintes de latence.

Google Cloud propose une vaste gamme de moteurs de persistance de données :
Matrice de décision :
- model=RELATIONAL scale=GLOBAL acid=STRICT -> service=Cloud_Spanner type=NEW_SQL sla=99.999%
- model=RELATIONAL scale=REGIONAL -> service=Cloud_SQL type=RDBMS sla=99.95%
- model=NOSQL_DOCUMENT -> service=Firestore type=DOCUMENT_DB latency=LOW
- model=NOSQL_WIDE_COLUMN latency=SUB_MILLISECOND -> service=Cloud_Bigtable type=WIDE_COLUMN usecase=IOT_ANALYTICS
- model=OBJECT_STORAGE -> service=Cloud_Storage type=BLOB_STORE scale=EXABYTE

Commande STDIN :
SELECT_DB model=<model> scale=<scale> latency=<lat> acid=<acid>.
Sortie :
RECOMMENDATION: service=<name> <attributs...> (ou RECOMMENDATION: status=UNKNOWN_COMBINATION).

Entrée du programme
SELECT_DB model=RELATIONAL scale=GLOBAL latency=STANDARD acid=STRICT
Sortie attendue
RECOMMENDATION: service=Cloud_Spanner type=NEW_SQL sla=99.999%

Base NewSQL mondiale avec cohérence stricte ACID et haute disponibilité.

Deux indices, rédigés en mots
  1. Vérifiez d abord si model == "RELATIONAL" : différenciez selon scale == "GLOBAL" et acid == "STRICT" vs scale == "REGIONAL".
  2. Testez ensuite "NOSQL_DOCUMENT", "NOSQL_WIDE_COLUMN" et "OBJECT_STORAGE".

Exercice 3 — Simulateur de Pipeline d'Ingestion Cloud Pub/Sub (Topics & Subscriptions)

Python Niveau 3 — Raisonnement

Objectif : Simuler le cycle de publication, de délivrance et d'acquittement de messages dans Google Cloud Pub/Sub.

Google Cloud Pub/Sub est le service d'ingestion et de messagerie asynchrone haute cadence mondial :

Commandes lues sur STDIN :
1. CREATE_SUB sub=<nom> ack_deadline=<sec> :
Enregistre un abonnement avec un délai maximal d'acquittement ack_deadline (ex: 10s).
Affiche SUB_READY: name=<nom> ack_deadline=<sec>s.
2. DELIVER_MSG sub=<nom> msg_id=<id> elapsed_time=<sec> :
- Si elapsed_time <= ack_deadline :
DELIVERY: sub=<nom> msg_id=<id> status=ACKNOWLEDGED action=REMOVED_FROM_QUEUE
- Si elapsed_time > ack_deadline :
DELIVERY: sub=<nom> msg_id=<id> status=DEADLINE_EXCEEDED action=REDELIVERED_TO_CONSUMER

Entrée du programme
CREATE_SUB sub=order-processor ack_deadline=10
DELIVER_MSG sub=order-processor msg_id=ORD-999 elapsed_time=6
DELIVER_MSG sub=order-processor msg_id=ORD-1000 elapsed_time=14
Sortie attendue
SUB_READY: name=order-processor ack_deadline=10s
DELIVERY: sub=order-processor msg_id=ORD-999 status=ACKNOWLEDGED action=REMOVED_FROM_QUEUE
DELIVERY: sub=order-processor msg_id=ORD-1000 status=DEADLINE_EXCEEDED action=REDELIVERED_TO_CONSUMER

Le message 999 est acquitté en 6s (conforme) ; le message 1000 dépasse la deadline (réexpédié).

Deux indices, rédigés en mots
  1. Stockez les abonnements dans un dictionnaire sub_name -> int(ack_deadline).
  2. Comparez int(elapsed_time) <= ack_deadline pour valider l acquittement.

6. QCM — niveau examen

Quelle est la durée minimale de conservation et de facturation associée à la classe de stockage Cloud Storage Nearline ?

Cloud Storage Nearline impose une durée minimale de facturation de 30 jours (Coldline impose 90 jours et Archive 365 jours).

Quelle technologie matérielle brevetée par Google permet à Cloud Spanner de garantir une cohérence transactionnelle stricte ACID à travers le monde entier ?

Google TrueTime synchronise les horloges de tous les datacenters de Google via des récepteurs GPS et des horloges atomiques, fournissant une incertitude temporelle bornée pour ordonner les transactions mondiales.

Quel service de base de données NoSQL Google Cloud est recommandé pour stocker des flux de télémétrie IoT massifs avec des latences de lecture/écriture inférieures à la milliseconde ?

Cloud Bigtable est le moteur NoSQL large-colonne conçu pour absorber des débits colossaux d'écriture et de lecture avec des temps de réponse sub-millisecondes constants.

Dans Cloud Pub/Sub, que se passe-t-il si un consommateur met 25 secondes à traiter un message alors que l'Ack Deadline est configurée à 10 secondes ?

Dès que l'Ack Deadline expire sans accusé de réception formel (ack), Pub/Sub remet immédiatement le message dans la file de distribution pour qu'il soit retraité.

Quelle méthode de contrôle d'accès Cloud Storage permet de donner à un utilisateur externe un accès temporaire en écriture ou lecture à un objet précis sans qu'il ne possède de compte Google ?

Une URL signée (Signed URL) fournit un lien sécurisé temporaire avec signature cryptographique permettant d'effectuer une opération HTTP (GET, PUT) pendant une durée définie sans authentification GCP.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Supprimer des objets dans Nearline ou Coldline avant leur durée minimale de conservation (30 ou 90 jours), déclenchant des frais de suppression anticipée (Early Deletion Fees).
  • Rendre un bucket public via allUsers pour distribuer un fichier temporaire au lieu de générer une URL signée (Signed URL) avec expiration courte.
  • Utiliser Cloud Spanner pour un petit projet d'application interne : le coût de démarrage d'un nœud Spanner est disproportionné face à une petite instance Cloud SQL.
  • Oublier d'acquitter un message Pub/Sub dans l'Ack Deadline impartie, provoquant des réexpéditions infinies et des doublons de traitement applicatif.

8. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Élaboration de la stratégie de stockage Cloud Storage : choisir l'emplacement (Multi-Region vs Region) et paramétrer les règles de cycle de vie pour basculer automatiquement les données vers les classes économiques.
  2. Sélection du moteur relationnel selon le SLA : déployer Cloud SQL pour les applications standards et migrer vers Cloud Spanner dès que les exigences de scalabilité horizontale et de cohérence mondiale stricte s'imposent.
  3. Dimensionnement des moteurs NoSQL : arbitrer entre Firestore pour les applications applicatives réactives et Cloud Bigtable pour l'ingestion massive de télémétrie en temps réel.
  4. Architecture de découplage avec Pub/Sub : dimensionner les délais d'acquittement (Ack Deadline) et implémenter des files de lettres mortes (Dead Letter Topics) pour traiter les messages en échec.

9. Révision active

Résumé essentiel
  • Cloud Storage offre 11 9s de durabilité avec 4 classes de stockage optimisées pour le coût (Standard, Nearline, Coldline, Archive).
  • L'Object Lifecycle Management migre automatiquement les objets sans intervention humaine selon des règles d'âge.
  • Cloud SQL gère MySQL, PostgreSQL et SQL Server en régional avec HA, tandis que Cloud Spanner fournit du NewSQL mondial à cohérence stricte avec 99.999% de SLA.
  • Firestore est optimisé pour les documents temps réel et mobiles, alors que Cloud Bigtable traite des téraoctets de données large-colonne avec latence sub-milliseconde.
  • Cloud Pub/Sub fournit une messagerie asynchrone mondiale scalable reliant les producteurs et les consommateurs en mode Pull ou Push.

Checklist de maîtrise

  • Connaissez-vous les durées minimales de facturation des classes GCS (30j Nearline, 90j Coldline, 365j Archive) ?
  • Savez-vous expliquer la différence entre Cloud SQL et Cloud Spanner (horloges TrueTime et NewSQL mondial) ?
  • Comprenez-vous pourquoi Cloud Bigtable est privilégié pour l'IoT et les séries temporelles face à Firestore ?
  • Pouvez-vous expliquer le fonctionnement des modes Pull et Push dans Cloud Pub/Sub ?
  • Savez-vous ce qu'est une Ack Deadline dans Pub/Sub et ce qui se produit si elle est dépassée ?

Les 8 notions à connaître absolument

  1. Cloud Storage (GCS) : Service de stockage d'objets non structurés mondialement résilient offrant 11 9s de durabilité et des classes tarifaires adaptées au cycle de vie.
  2. Cloud Spanner : Base de données relationnelle NewSQL distribuée mondialement combinant transactions ACID strictes, horloges TrueTime et SLA 99.999%.
  3. Cloud Bigtable : Base de données NoSQL large-colonne massivement distribuée fournissant une latence sub-milliseconde pour les très grands volumes de données.
  4. Firestore : Base de données NoSQL orientée documents offrant une synchronisation en temps réel et un support hors-ligne pour applications web et mobiles.
  5. Cloud Pub/Sub : Service de messagerie asynchrone mondial hautement scalable permettant le découplage fiable entre producteurs et consommateurs d'événements.
