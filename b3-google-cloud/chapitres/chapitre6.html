Chapitre 6 — Observabilité (Operations Suite), FinOps & Infrastructure as Code (Terraform)

Module 6 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Déployer des services dans le Cloud sans observabilité en temps réel ni gouvernance financière rigoureuse conduit inexorablement à deux désastres : l'incapacité à diagnostiquer les pannes de production (lenteurs invisibles, incidents non détectés) et l'explosion non maîtrisée des factures mensuelles (« bill shock »). De plus, gérer l'infrastructure manuellement via la console graphique empêche toute reproductibilité et multiplie les erreurs de configuration humaines. En tant qu'ingénieur DevOps & SRE B3, vous devez superviser la santé de vos systèmes avec Cloud Operations, optimiser les coûts avec les pratiques FinOps et automatiser l'intégralité des déploiements déclaratifs via Terraform.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. maîtriser la suite Google Cloud Operations : métriques, tableaux de bord et canaux d'alerte Cloud Monitoring ;
  2. exploiter Cloud Logging : syntaxe de filtrage des événements, journaux d'audit et export continu via Log Sinks ;
  3. diagnostiquer les goulets d'étranglement applicatifs avec Error Reporting, Cloud Trace et Cloud Profiler ;
  4. piloter la rentabilité financière FinOps : calcul des remises d'utilisation continue (SUD) et des engagements CUD (1 an et 3 ans) ;
  5. automatiser l'infrastructure avec Terraform : provider Google, gestion de l'état distant sécurisé sur GCS et bonnes pratiques HCL ;
  6. développer en Python 3 des parseurs de filtres de logs, des calculateurs de remises FinOps et des linters de manifestes Terraform.

1. Google Cloud Operations Suite : Monitoring, Alertes & Métriques

Google Cloud Operations Suite (anciennement Stackdriver) est la solution intégrée de supervision, de journalisation et d'analyse de performance de Google Cloud :

Cloud Monitoring

  • Collecte automatiquement les métriques d'infrastructure (CPU, mémoire, réseau, disque, requêtes HTTP, latence).
  • Support des métriques personnalisées via l'API ou l'agent OpenTelemetry.
  • Tableaux de bord (Dashboards) : visualisations graphiques en temps réel avec corrélation multi-projets.

Politiques d'Alerte (Alerting Policies)

  • Déclenchées lorsqu'une métrique franchit un seuil pendant une durée paramétrable (ex: CPU > 85% pendant plus de 5 minutes).
  • Canaux de notification : Email, Slack, Webhook, SMS, PagerDuty ou Pub/Sub.
  • Gestion des incidents avec accusé de réception et fermeture automatique lors du retour à la normale.

2. Cloud Logging & Export de Données (Log Sinks)

Cloud Logging centralise des pétaoctets d'événements générés par les services GCP, les VM et les applications :

Types de Journaux & Niveaux de Gravité

  • Admin Activity Audit Logs : tracent qui a créé, modifié ou supprimé une ressource (conservés gratuitement 400 jours).
  • Data Access Audit Logs : tracent les lectures et écritures de données sensibles (BigQuery, Cloud Storage).
  • System Event Logs : événements de maintenance ou d'auto-scaling de l'infrastructure Google.
  • Sévérités : DEBUG < INFO < NOTICE < WARNING < ERROR < CRITICAL.

Récepteurs de Journaux (Log Sinks)

Par défaut, les logs applicatifs sont conservés 30 jours. Pour un archivage pérenne ou une analyse analytique, on configure un Log Sink avec un filtre de sélection vers :

  • BigQuery : pour l'analyse SQL temps réel et les requêtes de conformité.
  • Cloud Storage : pour l'archivage à long terme à coût minimal (Archive class).
  • Cloud Pub/Sub : pour router les logs vers un SIEM externe (Splunk, Datadog).
Diagnostics de Performance : Trace, Profiler & Error Reporting

Au-delà des métriques et des logs, Google Cloud intègre des outils d'observabilité avancés :

3. Gouvernance Financière FinOps : Budgets, CUD & SUD

Le mouvement FinOps (Financial Operations) allie ingénierie et finance pour maximiser la valeur métier de chaque euro investi dans le Cloud :

Budgets & Alertes de Facturation

  • Définition d'un montant de budget mensuel cible par projet ou compte de facturation.
  • Alertes automatiques par seuil de consommation : 50%, 90% et 100% des dépenses prévisionnelles ou réelles.
  • Automatisation : publication des alertes vers un topic Pub/Sub déclenchant une Cloud Function pour désactiver temporairement les environnements de test hors-production.

Remises Tarifaires : SUD vs CUD

  • Sustained Use Discounts (SUD) : réduction automatique appliquée par Google sans aucun engagement si une instance Compute Engine tourne plus de 25% du mois (jusqu'à 20% à 30% de remise).
  • Committed Use Discounts (CUD) : engagement contractuel sur une capacité minimale de vCPU/RAM ou sur une dépense monétaire horaire (Flexible CUD) :
    - Engagement 1 an : environ 37% de remise.
    - Engagement 3 ans : environ 55% de remise.

4. Infrastructure as Code (IaC) avec Terraform sur GCP

Pour garantir la reproductibilité, l'auditabilité et le déploiement automatisé en CI/CD, l'infrastructure Google Cloud est déclarée sous forme de code avec HashiCorp Terraform :

Le Provider Google pour Terraform

terraform {
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.0"
    }
  }
  backend "gcs" {
    bucket = "mon-tfstate-prod"
    prefix = "terraform/state"
  }
}

provider "google" {
  project = "fintech-prod-2026"
  region  = "europe-west9"
}

Bonnes Pratiques de Sécurité HCL

  • Backend distant sur GCS : stocker le fichier d'état (terraform.tfstate) dans un bucket Cloud Storage sécurisé avec contrôle de version et verrouillage d'état automatique (State Locking).
  • Zéro secret en dur : ne jamais utiliser credentials = file(...) dans le code ! Terraform doit utiliser automatiquement Application Default Credentials (ADC) en local ou Workload Identity en CI/CD.
  • Audit de pare-feu : bannir les règles de pare-feu autorisant 0.0.0.0/0 sur les ports d'administration (SSH 22, RDP 3389).
Workflow de Déploiement Terraform

Le cycle de vie standard Terraform comprend 4 étapes : terraform init (téléchargement du provider et initialisation du backend GCS), terraform fmt -check (validation de la mise en forme), terraform plan (calcul différentiel sans modification de l'infrastructure) et terraform apply (application idempotente des changements sur Google Cloud).

Exercice 1 — Interpréteur de Filtres Cloud Logging et Détection d'Incidents

Étude de cas Niveau 1 — Acquisition

Objectif : Filtrer des flux d'événements Google Cloud Logging selon le type de ressource et le niveau de sévérité.

Google Cloud Logging structure les événements avec un type de ressource et un niveau de gravité :
Hiérarchie des sévérités :
DEBUG (0) < INFO (1) < NOTICE (2) < WARNING (3) < ERROR (4) < CRITICAL (5).

Format d'un log : resource_type:severity:message (ex: gce_instance:ERROR:Disk quota exceeded).

Commande STDIN :
LOG_QUERY target_resource=<res> min_severity=<sev> logs=<log1;log2;...>.
Sortie :
LOG_RESULTS: resource=<res> min_sev=<sev> total=<T> matched=<M> critical_count=<C>.

Cas d’exemple
LOG_QUERY target_resource=gce_instance min_severity=WARNING logs=gce_instance:INFO:Boot ok;gce_instance:ERROR:Disk full;cloud_run:ERROR:Timeout;gce_instance:CRITICAL:Kernel panic
Résolution attendue
LOG_RESULTS: resource=gce_instance min_sev=WARNING total=4 matched=2 critical_count=1

2 logs GCE correspondent avec sévérité >= WARNING dont 1 critique.

Deux indices, rédigés en mots
  1. Créez un dictionnaire associant chaque sévérité à son niveau numérique (DEBUG=0 ... CRITICAL=5).
  2. Un log correspond si log_resource == target_resource et log_sev_level >= min_sev_level.

Exercice 2 — Moteur d'Alertes Budgétaires et Optimisation FinOps (CUD & SUD)

Étude de cas Niveau 2 — Application

Objectif : Calculer le coût net remisé avec les remises d'engagement (CUD) et générer des alertes de budget GCP.

Google Cloud propose deux mécanismes majeurs de réduction tarifaire Compute Engine :
- CUD (Committed Use Discount) : engagement d'1 an (-37%) ou 3 ans (-55%).
- SUD (Sustained Use Discount) : réduction automatique jusqu'à -20% si exécuté 100% du mois sans engagement.

Règles de calcul (non cumulables, CUD prioritaire) :
- Si commit_years == 3 : discount = 0.55.
- Sinon si commit_years == 1 : discount = 0.37.
- Sinon (commit_years == 0) : si runtime_pct == 100 : discount = 0.20 ; sinon discount = 0.00.

Coût net : net_cost = base_cost * (1 - discount).
Alerte budgétaire face au seuil de référence :
- Si net_cost > budget : alert=BUDGET_EXCEEDED
- Si net_cost >= 0.90 * budget : alert=WARNING_90_PCT
- Sinon : alert=OK

Commande STDIN : FINOPS_EVAL base_cost=<cost> runtime_pct=<pct> commit_years=<0|1|3> budget=<budget>.
Sortie : FINOPS: base=<cost> discount_pct=<pct> net_cost=<net:.2f> budget=<budget> alert=<alert>.

Cas d’exemple
FINOPS_EVAL base_cost=1000 runtime_pct=100 commit_years=3 budget=600
Résolution attendue
FINOPS: base=1000 discount_pct=55 net_cost=450.00 budget=600 alert=OK

Engagement 3 ans apportant 55% de remise : coût net de 450$ sous le budget de 600$.

Deux indices, rédigés en mots
  1. Calculez discount_pct (55, 37, 20 ou 0).
  2. Calculez net_cost = base * (1.0 - discount_pct / 100.0).
  3. Vérifiez net_cost > budget, puis net_cost >= 0.90 * budget, sinon OK.

Exercice 3 — Linter et Validateur de Manifeste Terraform pour GCP

Étude de cas Niveau 3 — Raisonnement

Objectif : Auditer un extrait de code Terraform HCL pour Google Cloud et détecter les mauvaises pratiques de sécurité.

Terraform automatise le déploiement déclaratif de ressources Google Cloud.

Règles d'audit de sécurité et de conformité :
1. HARDCODED_SECRETS : le code ne doit jamais contenir credentials = file(...) ou de chaînes de clé privée (utiliser Application Default Credentials ou Workload Identity).
2. MISSING_PROJECT : toute ressource doit hériter d'un projet explicite ou du bloc provider.
3. OPEN_FIREWALL : une règle pare-feu autorisant 0.0.0.0/0 sur le port 22 (SSH) ou 3389 (RDP) doit être rejetée.

Commande STDIN : TF_LINT res_type=<type> res_name=<nom> props=<k1:v1,k2:v2,...>.
Sorties :
- Si valide : TF_AUDIT: resource=<type>.<name> status=VALID_HCL security=COMPLIANT
- Si secret en dur : TF_AUDIT: resource=<type>.<name> status=REJECTED reason=HARDCODED_SECRETS
- Si pare-feu trop ouvert : TF_AUDIT: resource=<type>.<name> status=REJECTED reason=OPEN_INGRESS_MANAGEMENT_PORT port=<p>

Cas d’exemple
TF_LINT res_type=google_compute_instance res_name=web_vm props=machine_type:e2-medium,zone:europe-west9-a
Résolution attendue
TF_AUDIT: resource=google_compute_instance.web_vm status=VALID_HCL security=COMPLIANT

Ressource Compute Engine Terraform valide et conforme.

Deux indices, rédigés en mots
  1. Analysez chaque couple cle:valeur dans props.
  2. Si cle == "credentials" ou "file(" dans valeur -> HARDCODED_SECRETS.
  3. Si source_ranges == "0.0.0.0/0" et port in ("22", "3389") -> OPEN_INGRESS_MANAGEMENT_PORT.

6. QCM — niveau examen

Quel composant de Cloud Logging permet de router et d'exporter automatiquement les journaux d'événements vers BigQuery pour analyse SQL à long terme ?

Un récepteur de journaux (Log Sink) configure un filtre logique et achemine en streaming continu les événements sélectionnés vers une destination comme BigQuery ou Cloud Storage.

Quel niveau de réduction approximatif un engagement d'utilisation continue (CUD) de 3 ans sur Compute Engine procure-t-il par rapport au tarif standard à la demande ?

Un engagement CUD de 3 ans permet d'obtenir environ 55% de réduction sur les ressources de calcul engagées (contre environ 37% pour 1 an).

Quel outil de la suite Google Cloud Operations permet de mesurer la latence de chaque appel RPC et requête réseau à travers une chaîne complexe de microservices ?

Cloud Trace est le système de traçabilité distribuée (Distributed Tracing) qui chronomètre la traversée des requêtes à travers l'ensemble des microservices.

Où le fichier d'état d'infrastructure Terraform (terraform.tfstate) doit-il être stocké en production pour garantir le travail collaboratif et le verrouillage d'état ?

Terraform recommande d'utiliser le backend « gcs » pour stocker son fichier d'état dans un bucket Google Cloud Storage sécurisé avec verrouillage automatique pour éviter les écritures concurrentes.

Quelle pratique de sécurité relative aux identifiants est formellement requise lors de l'écriture de code Terraform pour Google Cloud ?

Le code Terraform ne doit jamais contenir de fichier de clé de compte de service en dur ; il doit s'appuyer sur Application Default Credentials (ADC) en local ou Workload Identity Federation dans la CI/CD.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Laisser les logs applicatifs verbeux s'accumuler dans Cloud Logging sans filtre d'exclusion, générant une facture de stockage de logs imprévue.
  • Ne pas configurer d'alertes budgétaires lors du lancement d'un projet, découvrant les dérives de coûts uniquement lors de la réception de la facture mensuelle.
  • Stocker le fichier d'état Terraform (terraform.tfstate) sur un poste local au lieu d'un bucket GCS partagé, provoquant des conflits d'état et des désynchronisations d'infrastructure.
  • Inscrire des clés privées de service account en dur dans les fichiers Terraform (credentials = file(...)) au lieu d'utiliser Application Default Credentials.

8. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Mise en place de l'observabilité dès l'initialisation : configurer un espace de travail Cloud Monitoring, créer des tableaux de bord pour les métriques de saturation (Golden Signals) et définir des alertes à notification multi-canal.
  2. Exportation et rétention des journaux d'audit : créer un Log Sink filtrant les événements de sécurité critiques et les acheminer vers un dataset BigQuery partitionné pour les contrôles réglementaires.
  3. Optimisation proactive FinOps : analyser les recommandations de dimensionnement (Recommender API), activer les alertes de budget à 50%, 90% et 100%, et souscrire des engagements CUD sur la capacité de base stable.
  4. Automatisation déclarative avec Terraform : modulariser les déploiements GCP (modules VPC, GKE, Cloud Run), sécuriser le backend d'état sur un bucket Cloud Storage et intégrer un linter de conformité dans la pipeline CI/CD.

9. Révision active

Résumé essentiel
  • Cloud Monitoring supervise les métriques système et déclenche des alertes configurées vers Slack, PagerDuty ou Email.
  • Cloud Logging centralise tous les événements d'infrastructure et permet l'archivage à long terme via des Log Sinks vers BigQuery ou Cloud Storage.
  • Cloud Trace et Cloud Profiler identifient avec précision les goulots d'étranglement de latence et de mémoire dans le code applicatif.
  • Le FinOps optimise les dépenses via les remises automatiques d'usage continu (SUD) et les remises sur engagement d'utilisation (CUD 1 an et 3 ans).
  • Terraform automatise l'infrastructure déclarative avec le provider Google, un backend d'état distant GCS et une stricte interdiction de secrets en dur.

Checklist de maîtrise

  • Savez-vous configurer une alerte Cloud Monitoring avec seuil métrique et canal de notification ?
  • Comprenez-vous le rôle d'un Log Sink pour exporter des journaux d'audit vers BigQuery ?
  • Pouvez-vous expliquer la différence entre Cloud Trace (latence de requêtes) et Cloud Profiler (CPU/mémoire du code) ?
  • Connaissez-vous les pourcentages de remise des engagements CUD 1 an (~37%) et 3 ans (~55%) ?
  • Savez-vous configurer un backend GCS distant pour stocker l'état Terraform de façon collaborative et sécurisée ?

Les 8 notions à connaître absolument

  1. Cloud Operations Suite : Ensemble unifié d'outils d'observabilité Google Cloud regroupant Monitoring, Logging, Trace, Profiler et Error Reporting.
  2. Log Sink : Mécanisme de routage dans Cloud Logging qui filtre et exporte en continu des journaux d'événements vers BigQuery, Storage ou Pub/Sub.
  3. Committed Use Discount (CUD) : Remise contractuelle substantielle accordée par Google en échange d'un engagement d'utilisation continue de ressources sur 1 ou 3 ans.
  4. Sustained Use Discount (SUD) : Remise automatique sans engagement appliquée sur les VMs Compute Engine tournant une part significative du mois civil.
  5. Backend Terraform GCS : Configuration stockant le fichier d'état terraform.tfstate dans un bucket Google Cloud Storage avec gestion des versions et verrouillage automatique.
