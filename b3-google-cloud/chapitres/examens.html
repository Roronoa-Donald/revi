Examens Blancs & Épreuves Corrigées — Google Cloud Platform B3

Deux épreuves académiques complètes d’architecture et d’ingénierie Cloud conformes au cursus Bachelor 3 et aux certifications professionnelles Google Cloud (Associate Cloud Engineer & Professional Cloud Architect) : gouvernance, IAM, Compute Engine, VPC, Cloud Storage, Cloud Run, GKE, FinOps et Terraform.

Épreuve 1 : Contrôle Continu (CC) — Durée 1 h 30 (Barème sur 20 points)

Sujet du Contrôle Continu — Hiérarchie GCP, Gestion des Identités IAM & Calcul IaaS

Partie 1 : Hiérarchie des Ressources, Projets & Outils CLI (6 points)

  1. Décrivez les 4 niveaux de la hiérarchie organisationnelle de Google Cloud (Organisation, Dossiers, Projets, Ressources). Pourquoi est-il déconseillé de créer des ressources sans attachement à un projet ? (3 pts)
  2. Expliquez la différence fondamentale entre le Project ID, le Project Name et le Project Number sous Google Cloud. Quelles sont les règles RFC 1035 appliquées au Project ID ? (3 pts)

Partie 2 : Sécurité IAM, Rôles & Comptes de Service (7 points)

  1. Distinguez les rôles primitifs (Viewer, Editor, Owner) des rôles prédéfinis (Predefined Roles). Pourquoi les rôles primitifs doivent-ils être rigoureusement bannis des environnements de production ? (4 pts)
  2. Qu'est-ce qu'un compte de service (Service Account) ? Expliquez les risques associés au téléchargement de clés privées JSON de comptes de service et présentez la solution alternative recommandée par Google (Workload Identity Federation). (3 pts)

Partie 3 : Calcul & Élasticité avec Compute Engine (7 points)

  1. Qu'est-ce qu'un groupe d'instances géré (Managed Instance Group - MIG) ? Comment fonctionnent les mécanismes d'auto-scaling et d'auto-healing basés sur les sondes de santé (Health Checks) ? (4 pts)
  2. Comparez le SLA de disponibilité d'une instance Compute Engine mono-zone (99.5%) avec un déploiement de VM réparties sur plusieurs zones de disponibilité au sein d'une même région (99.99%). Calculez le temps d'indisponibilité mensuel maximal autorisé dans chaque cas. (3 pts)

Corrigé Partie 1 (6 points)

  • Hiérarchie des Ressources (3 pts) : 1. Organisation : Racine absolue représentant l'entreprise (liée à un domaine Google Workspace ou Cloud Identity). 2. Dossiers (Folders) : Regroupements logiques par départements, environnements (Prod, Dev) ou filiales. 3. Projets : Unités fondamentales d'allocation de ressources, d'activation d'API, de facturation et de délimitation de sécurité. 4. Ressources : Éléments terminaux (VMs, buckets, tables BigQuery). Toute ressource doit impérativement appartenir à un projet car les quotas, les autorisations IAM et la facturation y sont directement rattachés.
  • Identifiants de Projet & RFC 1035 (3 pts) : - Project Name : Nom lisible par l'humain, modifiable, non unique mondialement. - Project Number : Entier unique généré automatiquement par Google, utilisé en interne pour les comptes de service par défaut. - Project ID : Identifiant permanent, immuable et unique à l'échelle mondiale. Règles RFC 1035 : 6 à 30 caractères, lettres minuscules (a-z), chiffres (0-9) et tirets (-), doit commencer par une lettre et ne peut se terminer par un tiret.

Corrigé Partie 2 (7 points)

  • Rôles Primitifs vs Prédéfinis (4 pts) : Les rôles primitifs (Viewer, Editor, Owner) accordent des privilèges globaux excessifs sur l'intégralité des services du projet (par exemple, Editor permet de supprimer des bases de données et modifier le réseau). Ils violent le principe du moindre privilège (Least Privilege). En production, seuls les rôles prédéfinis (ex: roles/storage.objectViewer ou roles/compute.instanceAdmin.v1) ou des rôles personnalisés (Custom Roles) doivent être attribués.
  • Comptes de Service & Workload Identity (3 pts) : Un compte de service est une identité non humaine utilisée par des applications ou des VMs pour s'authentifier auprès des API Google Cloud. Télécharger des clés privées JSON pose un risque majeur de fuite de secret dans Git ou sur des postes de travail non sécurisés. Workload Identity Federation élimine totalement les clés de compte de service en permettant aux conteneurs GKE ou aux charges de travail externes (AWS, GitHub Actions) d'échanger des jetons OIDC éphémères contre des jetons d'accès Google Cloud temporaires.

Corrigé Partie 3 (7 points)

  • Groupes d'Instances Gérés (MIG) (4 pts) : Un MIG gère un parc de VMs identiques créées à partir d'un template d'instance. Auto-scaling : ajuste dynamiquement le nombre d'instances en fonction d'une métrique cible (ex: utilisation CPU à 60% ou requêtes HTTP). Auto-healing : interroge périodiquement chaque VM via un Health Check applicatif ; si une instance ne répond plus (timeout), elle est automatiquement recréée sans intervention humaine.
  • SLA Mono-Zone vs Multi-Zones (3 pts) : - Mono-Zone (SLA 99.5%) : 0.005 * 30 jours * 24 h * 60 min = 216 minutes d'indisponibilité mensuelle (3 h 36 min). - Multi-Zones (SLA 99.99%) : 0.0001 * 30 jours * 24 h * 60 min = 4.32 minutes d'indisponibilité mensuelle. Le déploiement multi-zones réduit le temps d'arrêt toléré de plus de 50 fois.

Épreuve 2 : Examen Terminal (ET) — Durée 2 h 00 (Barème sur 20 points)

Sujet de l'Examen Terminal — Conception d'une Architecture Globale d'Entreprise sur Google Cloud

Une entreprise fintech internationale souhaite déployer sa nouvelle plateforme bancaire sur Google Cloud. La solution doit gérer une API sécurisée à très faible latence mondiale, stocker des transactions financières sous conformité stricte et garantir une résilience totale aux pannes zonales.

Section A : Réseau Virtuel VPC, Sécurité & Load Balancing (5 points)

  1. Concevez l'architecture VPC en mode sous-réseaux personnalisés (Custom Subnet Mode). Quels sont les rôles des 4 adresses IP réservées par Google dans un sous-réseau /24 ? (2.5 pts)
  2. Présentez l'architecture d'un Global External HTTP(S) Load Balancer. Détaillez le rôle de l'IP Anycast, du Target HTTPS Proxy et de l'URL Map pour acheminer le trafic mondial. (2.5 pts)

Section B : Moteurs de Persistance & Stratégie de Données (5 points)

  1. Comparez Cloud SQL, Cloud Spanner et Cloud Bigtable. Quel moteur recommandez-vous pour le grand livre des transactions financières mondiales nécessitant une cohérence stricte ACID et un SLA 99.999% ? Justifiez votre choix. (3 pts)
  2. Définissez une politique de cycle de vie (Lifecycle Management) sur un bucket Cloud Storage pour optimiser les coûts des reçus de paiement : Standard les 30 premiers jours, Nearline jusqu'à 90 jours, Coldline jusqu'à 365 jours, puis Archive au-delà. (2 pts)

Section C : Conteneurs & Serverless (GKE vs Cloud Run) (5 points)

  1. Comparez les cas d'usage de Google Kubernetes Engine (GKE) en mode Autopilot avec Cloud Run. Quel service préconisez-vous pour des microservices HTTP sans état devant passer à l'échelle à zéro pendant les heures creuses ? (3 pts)
  2. Décrivez la mise en œuvre d'un déploiement progressif de type Canary Release (80% sur la révision stable, 20% sur la nouvelle révision) avec Cloud Run. (2 pts)

Section D : Observabilité, FinOps & Terraform (5 points)

  1. Expliquez comment superviser les erreurs applicatives avec Google Cloud Operations (Monitoring et Cloud Logging). Comment configurer un Log Sink pour archiver les journaux d'audit vers BigQuery ? (2.5 pts)
  2. En tant qu'ingénieur FinOps, comparez les remises d'utilisation soutenue (SUD) et les remises sur engagement d'utilisation (CUD 1 an et 3 ans). Pourquoi le code Terraform ne doit-il jamais contenir de clés de service account en dur ? (2.5 pts)

Corrigé type & Barème détaillé de l'Examen Terminal

Corrigé Section A (5 points)

  • VPC Custom & Adresses Réservées (2.5 pts) : Le mode personnalisé évite la création automatique de sous-réseaux par défaut dans toutes les régions et permet une segmentation stricte du plan d'adressage CIDR. Dans chaque sous-réseau, 4 adresses sont réservées : .0 (réseau), .1 (passerelle par défaut), .2 (DNS interne Google) et .255 (diffusion). Un sous-réseau 10.10.0.0/24 offre donc 252 adresses utilisables (256 - 4).
  • Global External HTTP(S) Load Balancer (2.5 pts) : Ce répartiteur de charge repose sur une adresse IP Anycast mondiale unique annoncée par BGP sur les 100+ points de présence (PoP) de Google. Le trafic client entre dans le réseau mondial Google au plus près de l'utilisateur. Le Target HTTPS Proxy termine la session TLS au PoP edge, et l'URL Map inspecte les en-têtes et chemins d'URL pour acheminer la requête via la dorsale privée en fibre optique de Google vers le backend régional le plus proche.

Corrigé Section B (5 points)

  • Sélection du Moteur de Données (3 pts) : - Cloud SQL : base relationnelle régionale (max 64 To), limitée en montée en charge horizontale. - Cloud Bigtable : NoSQL analytique ultra-rapide mais cohérence finale et absence de transactions relationnelles ACID multi-tables. - Cloud Spanner : recommandé sans équivoque pour le grand livre des transactions financières. Spanner est une base relationnelle NewSQL distribuée mondialement avec synchronisation d'horloges matérielles TrueTime (GPS et horloges atomiques), garantissant une cohérence stricte (external consistency) et un SLA exceptionnel de 99.999% (moins de 5 minutes d'arrêt par an).
  • Politique de Cycle de Vie Cloud Storage (2 pts) : Configuration JSON/XML de règles Lifecycle : Règle 1 : Action SetStorageClass: NEARLINE si age >= 30. Règle 2 : Action SetStorageClass: COLDLINE si age >= 90. Règle 3 : Action SetStorageClass: ARCHIVE si age >= 365. Permet d'économiser jusqu'à 90% sur la facture de stockage sans aucune intervention applicative.

Corrigé Section C (5 points)

  • GKE Autopilot vs Cloud Run (3 pts) : GKE Autopilot gère les clusters Kubernetes complets avec provisionnement automatique des nœuds, idéal pour des applications complexes avec microservices communicants, maillages de services (Istio) et protocoles non HTTP. Pour des microservices HTTP sans état avec besoin de mise à l'échelle à zéro (scale-to-zero), Cloud Run est supérieur : conteneurs serverless démarrant en moins d'une seconde, facturation exacte à la milliseconde de calcul consommé, zéro coût en l'absence de trafic.
  • Canary Release sur Cloud Run (2 pts) : Cloud Run génère une révision immuable à chaque déploiement (ex: v1 et v2). La commande gcloud run services update-traffic [SERVICE] --to-revisions=v1=80,v2=20 configure le répartiteur de charge interne pour router 20% du trafic vers la nouvelle version pour validation opérationnelle avant basculement à 100%.

Corrigé Section D (5 points)

  • Cloud Operations & Log Sink (2.5 pts) : Cloud Logging centralise les logs de toutes les ressources. Un Log Sink définit une requête de filtrage (ex: logName:"cloudaudit.googleapis.com") et exporte en streaming continu les journaux vers un jeu de données BigQuery pour analyse SQL et conformité réglementaire à long terme.
  • FinOps CUD/SUD & Sécurité Terraform (2.5 pts) : - SUD s'applique automatiquement sans engagement (jusqu'à 20% de remise si la VM tourne tout le mois). - CUD nécessite un engagement contractuel d'1 an (~37% de remise) ou 3 ans (~55% de remise) sur des capacités de vCPU et RAM. - Dans Terraform, inscrire des clés de service account en dur (credentials = file(...)) expose les identifiants au vol lors de commits dans Git. On utilise systématiquement Application Default Credentials (ADC) en local et Workload Identity Federation dans les pipelines CI/CD.
