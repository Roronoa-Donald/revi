Chapitre 5 — Réseau Avancé Linux : Namespaces, Bridges & Policy Routing

Module 5 ≈ 2 h 45 de travail Réservé B3 et plus
Mise en situation

Dans les architectures de serveurs modernes, l’environnement réseau dépasse largement une unique carte physique connectée à un switch local. L’hébergement de conteneurs, les passerelles VPN multi-fournisseurs (Multi-WAN) et les réseaux superposés (Overlay Networks VXLAN/Geneve) imposent une virtualisation complète de la pile réseau au cœur du noyau Linux. L’ingénieur de niveau Bachelor 3 doit savoir concevoir des topologies virtuelles complexes combinant ponts logiciels (Linux Bridges) et câbles virtuels (veth pairs), maîtriser la suite d’outils iproute2 (remplaçant les vieux outils obsolètes ifconfig et route), déployer du routage basé sur les politiques (Policy-Based Routing - PBR) via ip rule pour aiguiller le trafic selon la source ou le port applicatif, et comprendre l’ordre de résolution des noms d’hôtes dans /etc/nsswitch.conf.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. concevoir des architectures réseau virtuelles complètes interconnectant des namespaces isolés avec des paires veth et des ponts Linux ;
  2. maîtriser la suite d’administration réseau moderne iproute2 (ip link, ip addr, ip route, ip rule) ;
  3. comprendre le routage par politiques (Policy-Based Routing) et la gestion de tables de routage alternatives multiples ;
  4. configurer des règles d’aiguillage PBR basées sur l’adresse IP source, l’interface d’entrée ou le marquage pare-feu (fwmark) ;
  5. analyser la séquence de résolution de noms d’hôtes orchestrée par le commutateur de services de noms (NSSwitch) ;
  6. développer en Python 3 des validateurs de topologie réseau, des moteurs d’évaluation PBR et des simulateurs de résolution nsswitch.conf.

1. Interfaces Virtuelles & Interconnexion de Namespaces (veth & bridge)

Dans un environnement virtualisé ou conteneurisé sous Linux, le réseau est bâti avec des briques logicielles émulées par le noyau :

1. Les Paires veth (Virtual Ethernet)

Une paire veth est un câble réseau virtuel bidirectionnel doté de deux interfaces terminales (ex: veth_host et veth_cnt).

Tout paquet injecté par une extrémité émerge instantanément par l’autre. En déplaçant l’une des interfaces dans le namespace réseau d’un conteneur via ip link set veth_cnt netns <PID>, on établit la passerelle de communication avec l’hôte physique.

2. Le Pont Logiciel Linux (Bridge)

Un pont Linux (bridge) opère comme un commutateur Ethernet de niveau 2 émulé dans le noyau (similaire à un switch matériel). Il apprend les adresses MAC et commute les trames entre toutes les interfaces esclaves qui lui sont rattachées.

La commande de création standard est :
ip link add name br0 type bridge && ip link set br0 up.

2. La Suite iproute2 : L’Outillage Moderne du Réseau Linux

Depuis plus d’une décennie, les commandes historiques ifconfig, route et arp (issues du paquet net-tools) sont officiellement obsolètes et incapables de gérer les namespaces ou les tables multiples. La suite iproute2 dialogue directement avec le noyau via l’interface de socket Netlink :

3. Routage par Politiques (PBR) & Tables de Routage Multiples

Le routage IP standard est strictement déterminé par l’adresse de destination (Destination Routing). Dans un serveur hébergeant plusieurs connexions Internet (Multi-WAN) ou des tunnels VPN, on doit acheminer les paquets selon l’adresse IP source ou le type de service : c’est le Policy-Based Routing (PBR).

Architecture de la Routing Policy Database (RPDB)

Linux consulte la base RPDB gérée via la commande ip rule par ordre de priorité croissante (de 0 à 32767). Dès qu’une règle correspond, le noyau utilise la table de routage indiquée :

,
# 1. Creer une regle aiguillant une IP source vers une table dediee
ip rule add from 192.168.10.50 table 100 priority 100

# 2. Definir la passerelle par defaut de cette table 100
ip route add default via 10.0.0.1 dev tun0 table 100

# 3. Rafraichir le cache de routage du noyau
ip route flush cache
,

Les tables de routage peuvent être nommées de façon lisible dans le fichier /etc/iproute2/rt_tables (ex: 100 vpn_traffic).

4. Architecture de Résolution de Noms : NSSwitch (/etc/nsswitch.conf)

Lorsqu’une application appelle getaddrinfo() ou gethostbyname(), la bibliothèque glibc consulte le fichier de configuration /etc/nsswitch.conf pour déterminer l’ordre des sources :

Ordre Standard de Résolution

# /etc/nsswitch.conf
hosts: files dns myhostname
  • files : Lit en priorité le fichier statique local /etc/hosts.
  • dns : Interroge les serveurs DNS distants spécifiés dans /etc/resolv.conf (ou systemd-resolved).
  • myhostname : Résout automatiquement le nom d’hôte local de la machine.

Critères de Continuité d’Évaluation

Chaque source retourne un statut (SUCCESS, NOTFOUND, UNAVAIL, TRYAGAIN).

Par défaut, l’évaluation s’arrête dès le premier SUCCESS. Si une source répond NOTFOUND, glibc passe automatiquement à la source suivante de la liste.

Exercice 1 — Validateur de topologie réseau virtuelle (veth pairs & Linux Bridge)

Python Niveau 1 — Acquisition

Objectif : Vérifier la cohérence de configuration des interfaces réseau virtuelles (veth) et des ponts sous Linux.

Sous Linux, la communication inter-conteneurs repose sur des paires d'interfaces virtuelles (veth pairs, sorte de câble réseau virtuel) connectées à un pont logiciel (Linux Bridge).

Règles de validation :
1. Un pont (type=bridge) ne peut pas être lui-même esclave d'un autre équipement (master doit valoir NONE). Sinon, erreur BRIDGE_CANNOT_HAVE_MASTER.
2. Une interface doit avoir son état activé (state=UP). Si state=DOWN, erreur INTERFACE_DOWN.
3. Une interface veth doit soit être rattachée à un pont maître (master != NONE), soit posséder une adresse IP (ip != NONE). Si les deux sont à NONE, erreur VETH_UNATTACHED.

Le script lit sur l'entrée standard des définitions au format :
NET_IFACE name=<nom> type=<bridge|veth|physical> master=<nom|NONE> ip=<cidr|NONE> state=<UP|DOWN>.

Pour chaque interface, afficher :
NET_AUDIT iface={name} valid={OUI|NON} error={OK|motif}

Entrée du programme
NET_IFACE name=br0 type=bridge master=NONE ip=10.0.0.1/24 state=UP
Sortie attendue
NET_AUDIT iface=br0 valid=OUI error=OK

Pont logiciel actif avec IP et sans maître : configuration conforme.

Deux indices, rédigés en mots
  1. Tester les règles dans l’ordre : état UP, bridge sans master, veth avec master ou IP.
  2. Dès qu’une règle échoue, valid=NON avec l’erreur correspondante.

Exercice 2 — Moteur d’évaluation de Policy-Based Routing (ip rule & multi-tables)

Python Niveau 2 — Application

Objectif : Aiguiller les paquets réseau vers la bonne table de routage selon les règles de politique PBR (Policy Routing).

Sous Linux, la commande ip rule permet de router le trafic non seulement d'après l'adresse de destination (routage classique), mais également en fonction de l'adresse source ou du port applicatif vers des tables de routage indépendantes (Policy-Based Routing).

Le script lit d'abord les règles de politique ordonnées par priorité :
RULE prio=<prio> src=<ip|ANY> dport=<port|ANY> table=<nom_table>.

Puis il lit des paquets à router :
PACKET id=<id> src=<ip> dport=<port>.

Principe First-Match-Wins : le paquet est évalué séquentiellement contre chaque règle dans l'ordre de priorité croissante. Dès qu'une règle correspond (adresse source identique ou ANY, et port identique ou ANY), le routage s'arrête et la table associée est retournée.

Pour chaque paquet, afficher :
ROUTE_MATCH packet={id} matched_prio={prio} table={nom_table}

Entrée du programme
RULE prio=100 src=192.168.1.50 dport=ANY table=vpn_tunnel
RULE prio=32766 src=ANY dport=ANY table=main
PACKET id=1 src=192.168.1.50 dport=443
Sortie attendue
ROUTE_MATCH packet=1 matched_prio=100 table=vpn_tunnel

Le paquet provient de l’IP 192.168.1.50 et correspond à la règle 100 routant vers vpn_tunnel.

Deux indices, rédigés en mots
  1. Stocker les règles ordonnées par leur priorité numérique (prio).
  2. Tester chaque paquet contre les règles et stopper dès la première correspondance.

Exercice 3 — Parseur et simulateur de résolution NSSwitch (/etc/nsswitch.conf)

Python Niveau 3 — Raisonnement

Objectif : Simuler la séquence de résolution de noms d’hôtes selon la politique déclarative de nsswitch.conf.

Le fichier /etc/nsswitch.conf (Name Service Switch) régit l'ordre dans lequel la bibliothèque C (glibc) consulte les bases de données système (fichiers locaux files comme /etc/hosts, résolveur DNS dns, mDNS mdns4).

Le script lit d'abord la configuration de la base hosts :
CONF_NSSWITCH order=<sources_separees_par_virgule>.

Puis il lit des requêtes de résolution :
QUERY_HOST name=<fqdn> in_files=<OUI|NON> in_dns=<OUI|NON> in_mdns=<OUI|NON>.

Règles :
- Les sources déclarées dans order sont interrogées successivement de gauche à droite.
- Dès qu'une source répond OUI, la résolution s'arrête immédiatement : resolved_by={source} status=SUCCESS.
- Si aucune source ne répond OUI : resolved_by=NONE status=NOT_FOUND.

Pour chaque requête, afficher :
RESOLV_RESULT host={name} resolved_by={source} status={SUCCESS|NOT_FOUND}

Entrée du programme
CONF_NSSWITCH order=files,dns
QUERY_HOST name=localhost in_files=OUI in_dns=NON in_mdns=NON
Sortie attendue
RESOLV_RESULT host=localhost resolved_by=files status=SUCCESS

Présent dans /etc/hosts (files) : résolu en priorité par files.

Deux indices, rédigés en mots
  1. Découper la chaîne order avec split(",") pour obtenir la liste ordonnée des sources.
  2. Parcourir les sources dans l’ordre et vérifier si la présence est OUI.

6. QCM — niveau examen

Quel composant réseau virtuel Linux fonctionne comme un câble Ethernet virtuel reliant deux namespaces ?

Une paire veth est constituée de deux interfaces liées : tout paquet entrant par une extrémité ressort instantanément par l’autre, reliant physiquement deux namespaces distincts.

Quelle commande moderne de la suite iproute2 remplace la commande obsolète « ifconfig eth0 192.168.1.10 netmask 255.255.255.0 » ?

ip addr add dev est la syntaxe standard et universelle de la suite iproute2 pour configurer une adresse IP.

Quelle est la différence fondamentale entre le routage IP classique et le Policy-Based Routing (PBR) ?

Le Policy-Based Routing (PBR) permet de choisir la table de routage et la passerelle en fonction de critères multiples (adresse source, port, protocole), surpassant le routage traditionnel basé sur la seule destination.

Quelle commande permet de consulter les règles de politiques de routage ordonnées par priorité sous Linux ?

ip rule show (ou ip rule list) affiche la table RPDB avec les priorités numériques et les tables de routage associées.

Dans quel fichier système l’ordre de résolution des noms d’hôtes (files vs dns) est-il formellement déclaré ?

/etc/nsswitch.conf (Name Service Switch) spécifie l’ordre dans lequel la glibc consulte les différentes sources (ex: hosts: files dns).

À quelle couche du modèle OSI un pont logiciel Linux (Linux Bridge) opère-t-il ?

Un pont Linux fonctionne comme un switch Ethernet en couche 2 (Liaison) : il commute les trames d’après leur adresse MAC.

Pourquoi est-il nécessaire d’exécuter « ip route flush cache » après avoir modifié des règles de routage sous Linux ?

Le noyau met en cache les décisions de routage pour accélérer le débit. Purger le cache garantit que les nouveaux flux empruntent immédiatement les règles modifiées.

Comment déplacer une interface réseau virtuelle « veth1 » dans le namespace réseau d’un processus ayant le PID 4200 ?

ip link set netns transfère immédiatement l’interface dans le namespace réseau du processus spécifié.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Utiliser ifconfig ou route dans des scripts d’automatisation modernes (ils ignorent les tables multiples et namespaces).
  • Oublier d’activer le pont avec ip link set br0 up (les interfaces esclaves ne recevront aucun paquet).
  • Oublier de purger le cache de routage après une modification de politique via ip route flush cache.
  • Créer des règles ip rule de même priorité avec des critères contradictoires (ordre d’évaluation indéterminé).

8. Méthodologie de résolution

Méthode d’Ingénierie : Mise en Place d’un Réseau Isolé pour Conteneur avec Bridge
  1. Étape 1 : Créer le pont virtuel Linux : ip link add name br0 type bridge && ip link set br0 up.
  2. Étape 2 : Assigner une passerelle IP au pont : ip addr add 172.20.0.1/24 dev br0.
  3. Étape 3 : Créer la paire d’interfaces veth : ip link add veth_host type veth peer name veth_cnt.
  4. Étape 4 : Rapprocher une extrémité sur le pont : ip link set veth_host master br0 && ip link set veth_host up.
  5. Étape 5 : Injecter l’autre extrémité dans le namespace du conteneur : ip link set veth_cnt netns .
  6. Étape 6 : Dans le conteneur, renommer l’interface en eth0, attribuer l’IP (172.20.0.10/24) et ajouter la route par défaut via 172.20.0.1.

9. Révision active

Résumé essentiel
  • Une paire veth agit comme un câble Ethernet virtuel reliant deux espaces ou namespaces distincts.
  • Un pont Linux (bridge) émule un switch de niveau 2 commutant les trames entre interfaces virtuelles esclaves.
  • La suite iproute2 remplace totalement les vieux outils net-tools obsolètes (ifconfig, route, arp).
  • Le routage classique ne tient compte que de la destination ; le Policy-Based Routing (PBR) aiguille selon la source ou le port.
  • ip rule gère la base RPDB par ordre de priorité croissante pour sélectionner des tables de routage indépendantes.
  • /etc/nsswitch.conf orchestre l’ordre de consultation des bases de noms (files /etc/hosts puis serveurs DNS).
  • L’interconnexion de conteneurs sous Linux repose sur l’assemblage élégant de ces primitives noyau fondamentales.
