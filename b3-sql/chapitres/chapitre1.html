Chapitre 1 — Transactions ACID, Journalisation WAL & Niveaux d’Isolation ANSI

Module 1 ≈ 2 h 45 de travail Accès libre
Mise en situation

Dans un système d’information moderne gérant des millions de transactions bancaires, de commandes e-commerce ou de dossiers médicaux, plusieurs milliers d’utilisateurs et de services accèdent simultanément aux mêmes tables. Sans garanties strictes de concurrence, des conflits destructeurs se produisent : débits bancaires partiels sur panne réseau, lectures de soldes non validés (Dirty Read), ou pertes irrémédiables de mises à jour (Lost Update). L’ingénieur de données de niveau Bachelor 3 doit maîtriser les fondements mathématiques et architecturaux des transactions ACID, comprendre le rôle vital du journal de réécriture en amont (Write-Ahead Logging - WAL) lors des récupérations après crash, configurer les 4 niveaux d’isolation ANSI SQL selon les compromis de performance, et analyser les graphes d’attente de verrous (Wait-For Graph) pour éradiquer les interblocages (deadlocks).

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. comprendre les quatre piliers fondamentaux ACID et leur implémentation physique dans le moteur SGBD ;
  2. analyser la cinématique du journal Write-Ahead Logging (WAL) et la récupération après panne (Crash Recovery) ;
  3. comparer les 4 niveaux d’isolation ANSI SQL et leurs protections contre les anomalies de concurrence ;
  4. maîtriser la matrice de compatibilité des verrous à deux phases (2PL) partagés (S) et exclusifs (X) ;
  5. détecter et résoudre les cycles d’interblocage (Deadlocks) par exploration de graphes orientés ;
  6. développer en Python 3 des simulateurs de niveaux d’isolation, des gestionnaires de verrous S/X et des détecteurs de cycles de transactions.

1. Les Fondations ACID & Le Mécanisme de Journalisation WAL (Write-Ahead Logging)

Une transaction est une unité logique de traitement composée d’une ou plusieurs instructions SQL exécutées de manière atomique (entre BEGIN et COMMIT ou ROLLBACK). Le standard relationnel repose sur quatre propriétés incontournables :

Les Quatre Propriétés ACID

  • Atomicité (Atomicity) : Tout ou rien. Soit l’intégralité des opérations réussit, soit la base est restaurée dans son état initial sans effet de bord en cas d’erreur.
  • Cohérence (Consistency) : La transaction fait passer la base d’un état intègre à un autre état intègre en respectant toutes les contraintes (clés étrangères, NOT NULL, CHECK, triggers).
  • Isolation : Les opérations intermédiaires d’une transaction en cours sont invisibles aux transactions concurrentes selon le niveau d’isolation choisi.
  • Durabilité (Durability) : Une fois le COMMIT acquitté au client, les modifications sont définitivement pérennisées sur disque, survivant à toute panne matérielle ultérieure.

Le Principe du Write-Ahead Logging (WAL)

Écrire directement chaque page de données modifiée (8 Ko) de manière synchrone sur disque serait prohibitif pour les performances (accès I/O aléatoires dispersés). Les moteurs modernes (PostgreSQL, InnoDB) appliquent le protocole ARIES / WAL :

  1. Les modifications sont enregistrées séquentiellement dans des fichiers de journaux circulaires pg_wal (fichiers de 16 Mo).
  2. Règle d’or du WAL : Aucun bloc de données en mémoire tampon (Buffer Pool) n’est écrit sur disque avant que l’enregistrement WAL correspondant n’ait été synchronisé par un fsync().
  3. Lors d’un crash, le moteur exécute une passe REDO (rejoue les commits) puis une passe UNDO (annule les transactions inachevées).

2. Niveaux d’Isolation ANSI SQL & Anomalies de Concurrence

Pour concilier intégrité stricte et parallélisme élevé, le standard ANSI SQL définit quatre niveaux d’isolation hiérarchiques caractérisés par les anomalies qu’ils autorisent ou préviennent :

Lecture Sale (Dirty Read)

La transaction T2 lit des données modifiées par T1 qui n’ont pas encore été validées par un COMMIT. Si T1 effectue ensuite un ROLLBACK, T2 aura basé ses calculs sur des données fantaisistes.

Lecture Non Répétable (Non-Repeatable Read)

La transaction T1 lit une ligne, puis T2 modifie ou supprime cette ligne et valide. Lorsque T1 relit la même ligne au sein de la même transaction, les valeurs ont changé.

Lecture Fantôme (Phantom Read)

La transaction T1 exécute une requête à plage (ex: WHERE solde > 1000). T2 insère une nouvelle ligne répondant à ce critère et valide. Lorsque T1 réexécute sa requête, de nouvelles lignes apparaissent.

3. Verrouillage 2PL, Détection d’Interblocages (Deadlocks) & MVCC

Pour arbitrer les accès concurrents, les SGBD exploitent le protocole de verrouillage à deux phases (Two-Phase Locking - 2PL) combiné au contrôle de concurrence multiversion (MVCC) :

Matrice des Verrous Partagés (S) & Exclusifs (X)

Les verrous protègent les données contre les écritures conflictuelles :

  • Verrou Partagé (S - Shared) : Posé par une lecture explicite (SELECT ... FOR SHARE). Plusieurs transactions peuvent détenir un verrou S simultanément sur la même ressource.
  • Verrou Exclusif (X - Exclusive) : Posé par toute écriture (UPDATE, DELETE, SELECT ... FOR UPDATE). Incompatible avec tout autre verrou (S ou X).
  • Protocole 2PL Strict : Tous les verrous acquis au cours d’une transaction sont conservés jusqu’à la fin définitive (COMMIT ou ROLLBACK) pour garantir la recouvrabilité.

Interblocages (Deadlocks) & Graphe d'Attente (Wait-For Graph)

Un interblocage survient lorsque deux transactions ou plus se bloquent mutuellement (ex: T1 détient ressource A et attend ressource B détenue par T2, qui attend ressource A) :

  • Le SGBD maintient un graphe orienté Wait-For Graph où chaque arc représente une attente.
  • Un démon en tâche de fond (deadlock_timeout, par défaut 1 seconde dans PostgreSQL) recherche les cycles orientés dans ce graphe.
  • Dès qu’un cycle est détecté, le moteur sélectionne une transaction victime (généralement la plus récente) et l’annule par un ROLLBACK avec code d’erreur 40P01.

Exercice 1 — Détecteur d’anomalies de concurrence selon le niveau d’isolation ANSI SQL

Python Niveau 1 — Acquisition

Objectif : Déterminer si une anomalie de concurrence (Dirty Read, Non-Repeatable Read, Phantom Read) est possible sous un niveau d’isolation ANSI SQL donné.

Dans un système de gestion de bases de données relationnelles (SGBDR), les 4 niveaux d’isolation standard ANSI SQL offrent des compromis distincts entre cohérence et performance : - READ UNCOMMITTED : autorise Dirty Read, Non-Repeatable Read et Phantom Read. - READ COMMITTED : empêche Dirty Read ; autorise Non-Repeatable Read et Phantom Read. - REPEATABLE READ : empêche Dirty Read et Non-Repeatable Read ; autorise Phantom Read. - SERIALIZABLE : empêche toutes les anomalies de concurrence (Dirty Read, Non-Repeatable Read, Phantom Read). Entrée : - Une ligne `ISOLATION ` - Des lignes `CHECK anomaly=` Sortie : - Pour chaque vérification : `ANOMALY name= allowed= state=` - Une ligne de bilan : `SUMMARY isolation= total= allowed= prevented=`
Entrée du programme
ISOLATION READ_COMMITTED
CHECK anomaly=DIRTY_READ
CHECK anomaly=NON_REPEATABLE_READ
CHECK anomaly=PHANTOM_READ
Sortie attendue
ANOMALY name=DIRTY_READ allowed=FALSE state=PREVENTED
ANOMALY name=NON_REPEATABLE_READ allowed=TRUE state=PERMISSIBLE
ANOMALY name=PHANTOM_READ allowed=TRUE state=PERMISSIBLE
SUMMARY isolation=READ_COMMITTED total=3 allowed=2 prevented=1

Sous READ COMMITTED, seule la lecture sale est prévenue.

Deux indices, rédigés en mots
  1. Stocker la matrice d’admissibilité ANSI dans un dictionnaire associant chaque niveau à l’ensemble des anomalies permises.
  2. Parcourir les lignes commençant par CHECK et extraire la clé anomaly.
  3. Afficher TRUE/PERMISSIBLE si l’anomalie est possible, FALSE/PREVENTED sinon.

Exercice 2 — Simulateur de verrous partagés et exclusifs (S/X Locks) et détection de conflit

Python Niveau 2 — Application

Objectif : Simuler l’octroi et les conflits de verrous partagés (S) et exclusifs (X) sur des ressources de base de données.

Dans un moteur transactionnel 2PL (Two-Phase Locking) : - Un verrou partagé `S` (Shared, lecture) est compatible avec d’autres verrous `S` sur la même ressource, mais incompatible avec un verrou `X`. - Un verrou exclusif `X` (Exclusive, écriture) est incompatible avec tout autre verrou (`S` ou `X`) sur la même ressource détenu par une autre transaction. - Si une demande est incompatible avec les verrous actuels, elle est mise en attente (`WAITING`). - Lorsqu’une transaction libère (`RELEASE`) ses verrous sur une ressource, les requêtes en attente peuvent être octroyées. Entrée : - `ACQUIRE tx= res= mode=` - `RELEASE tx= res=` Sortie : - Pour chaque ACQUIRE : `LOCK tx= res= mode= status=` - Pour chaque RELEASE : `UNLOCKED tx= res= count_released=` et si une attente est débloquée : `PROMOTED tx= res= mode=` - Bilan : `LOCK_REPORT granted_active= waiting_active=`
Entrée du programme
ACQUIRE tx=T1 res=table_users mode=S
ACQUIRE tx=T2 res=table_users mode=S
ACQUIRE tx=T3 res=table_users mode=X
RELEASE tx=T1 res=table_users
Sortie attendue
LOCK tx=T1 res=table_users mode=S status=GRANTED
LOCK tx=T2 res=table_users mode=S status=GRANTED
LOCK tx=T3 res=table_users mode=X status=WAITING
UNLOCKED tx=T1 res=table_users count_released=1
LOCK_REPORT granted_active=1 waiting_active=1

T3 attend car T2 détient toujours un verrou S sur table_users.

Deux indices, rédigés en mots
  1. Maintenir pour chaque ressource la liste des verrous actifs : {res: [(tx, mode), ...]} et la file d’attente : {res: deque([(tx, mode), ...])}.
  2. Un mode S est accordé si aucun verrou X d’une autre tx n’est actif.
  3. Un mode X est accordé si aucun verrou (S ou X) d’une autre tx n’est actif.

Exercice 3 — Détecteur d’interblocage de transactions (Deadlock Graph Cycle Finder)

Python Niveau 3 — Raisonnement

Objectif : Construire le graphe d’attente des transactions (Wait-For Graph) et détecter les cycles d’interblocage avec désignation de la victime à avorter.

Dans un système de gestion de bases de données, un interblocage (Deadlock) survient lorsqu’un ensemble de transactions forment un cycle d’attente mutuel circulaire (ex: T1 attend T2, et T2 attend T1). Le SGBD construit un graphe d’attente orienté $G = (V, E)$ où un arc $T_A \to T_B$ signifie que la transaction $T_A$ attend la libération d’une ressource détenue par $T_B$. Pour résoudre le deadlock, le moteur détecte le premier cycle orienté et sélectionne la transaction « victime » ayant le timestamp de démarrage le plus récent (ou identifiant alphabétique le plus grand en cas d’égalité) pour la terminer par un ROLLBACK forcé. Entrée : - Des déclarations de transactions : `TX id= start=` - Des dépendances d’attente : `WAIT tx= waits_for=` Sortie : - Si un cycle est détecté : `DEADLOCK_DETECTED cycle=T2->...->T1>` - Victime désignée : `VICTIM_SELECTED tx= action=ROLLBACK reason=YOUNGEST_TRANSACTION` - Si aucun cycle : `NO_DEADLOCK status=SAFE edges=`
Entrée du programme
TX id=T1 start=100
TX id=T2 start=200
WAIT tx=T1 waits_for=T2
WAIT tx=T2 waits_for=T1
Sortie attendue
DEADLOCK_DETECTED cycle=T1->T2->T1
VICTIM_SELECTED tx=T2 action=ROLLBACK reason=YOUNGEST_TRANSACTION

T1 et T2 forment un cycle. T2 est plus jeune (start=200 > 100) et est avortée.

Deux indices, rédigés en mots
  1. Construire une liste d’adjacence adj[u] = [v, ...] représentant u -> v (u attend v).
  2. Utiliser un algorithme DFS avec détection d’arcs retour (Back-edges) à l’aide des états VISITING / VISITED.
  3. Reconstituer le chemin du cycle dès qu’un arc retour est trouvé.
  4. Parmi les transactions appartenant au cycle, sélectionner celle ayant la valeur start la plus grande.

5. QCM — niveau examen

Quel principe fondamental régit le mécanisme de Write-Ahead Logging (WAL) dans un moteur SGBD relationnel ?

La règle d’or du WAL garantit qu’aucun bloc de données de table n’est écrit sur disque avant que l’enregistrement de journal WAL associé n’ait été persisté.

Quelle anomalie de concurrence se produit lorsqu’une transaction lit des modifications effectuées par une autre transaction qui n’a pas encore commité ?

Le Dirty Read désigne la lecture de données non validées susceptibles d’être annulées par un ROLLBACK ultérieur.

Quel est le niveau d’isolation par défaut de PostgreSQL pour chaque nouvelle session transactionnelle ?

PostgreSQL utilise par défaut READ COMMITTED, empêchant toute lecture sale grâce à des instantanés (snapshots) de requêtes.

Dans la matrice de compatibilité des verrous 2PL, quelle affirmation est rigoureusement exacte ?

Les verrous partagés (S) sont conçus pour les lectures concurrentes : ils sont compatibles entre eux, mais bloquent toute demande de verrou exclusif (X).

Comment le moteur de base de données modélise-t-il les blocages mutuels pour détecter un interblocage (Deadlock) ?

Le Wait-For Graph relie les transactions en attente de ressources. Un cycle orienté (ex: T1 attend T2 qui attend T1) signe un deadlock irréversible.

Quel niveau d’isolation ANSI SQL garantit l’absence totale de toute anomalie de concurrence au prix d’échecs de sérialisation possibles ?

Le niveau SERIALIZABLE émule une exécution séquentielle stricte des transactions sans aucune anomalie de concurrence.

Quelle instruction SQL permet d’acquérir un verrou exclusif pessimiste sur des lignes sélectionnées dès la lecture ?

La clause FOR UPDATE verrouille les lignes lues en mode exclusif (X), empêchant toute autre transaction de les modifier ou de poser un verrou concurrent.

Que signifie l’acronyme MVCC dans les moteurs transactionnels comme PostgreSQL ?

MVCC maintient plusieurs versions physiques d’un même enregistrement, permettant aux lectures de consulter des instantanés passés sans jamais bloquer les écritures.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Configurer le niveau d’isolation SERIALIZABLE sans implémenter de logique de retry applicatif en cas d’erreur de sérialisation 40001.
  • Garder des transactions ouvertes inutilement longtemps (ex: attendre un appel API réseau externe dans une transaction), provoquant l’accumulation de deadlocks.
  • Acquérir des verrous exclusifs dans des ordres différents selon les requêtes (ex: T1 verrouille A puis B, T2 verrouille B puis A), causant des deadlocks systématiques.
  • Confondre un verrou logique au niveau ligne avec un verrou de table complet bloquant l’ensemble des utilisateurs.

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Étape 1 : Analyser la criticité métier des flux pour choisir le niveau d’isolation minimal requis (Read Committed par défaut, Serializable pour la facturation).
  2. Étape 2 : Encadrer systématiquement les modifications multi-tables dans un bloc transactionnel explicite BEGIN ... COMMIT.
  3. Étape 3 : Poser des verrous pessimistes explicites (SELECT ... FOR UPDATE) lors des calculs conditionnels de stock ou de débit bancaire.
  4. Étape 4 : Ordonner les acquisitions de verrous dans le même ordre sur toutes les procédures applicatives pour prévenir les deadlocks.
  5. Étape 5 : Configurer le paramètre deadlock_timeout (ex: 1000ms) et surveiller les métriques de conflits via pg_stat_database.
  6. Étape 6 : Prévoir dans la couche applicative une stratégie de réessai automatique (Retry with Exponential Backoff) sur code d’erreur 40P01 / 40001.

8. Révision active

Résumé essentiel
  • Les propriétés ACID garantissent l’atomicité, la cohérence, l’isolation et la durabilité des opérations sur la base.
  • Le Write-Ahead Logging (WAL) sécurise les modifications de données de manière séquentielle avant toute écriture sur les tables.
  • Les 4 niveaux d’isolation ANSI définissent les seuils de tolérance aux lectures sales, lectures non répétables et lectures fantômes.
  • PostgreSQL combine l’isolation avec le mécanisme MVCC où les lectures ne bloquent jamais les écritures.
  • Les verrous partagés (S) sont compatibles entre eux mais incompatibles avec les verrous exclusifs (X).
  • Le moteur résout les interblocages (deadlocks) en détectant les cycles dans le graphe d’attente et en avortant une transaction victime.
