Chapitre 5 — Procédures Stockées PL/pgSQL, Déclencheurs (Triggers) & Row-Level Security (RLS)

Module 5 ≈ 3 h 00 de travail Réservé B1 et plus
Mise en situation

Dans les architectures d’entreprise modernes et les environnements multi-tenants (SaaS), la sécurité et l’intégrité des données ne peuvent reposer uniquement sur la couche applicative backend. Si une faille d’injection SQL ou un bug de code survient, la base de données doit constituer le rempart ultime. PostgreSQL offre un moteur d’exécution procédurale puissant (PL/pgSQL) permettant d’exécuter des règles métier complexes directement au plus près des données. Les déclencheurs (Triggers) garantissent une traçabilité d’audit infalsifiable en interceptant chaque mutation physique via les pseudo-enregistrements NEW et OLD. Enfin, le mécanisme de Row-Level Security (RLS) applique un cloisonnement cryptographique et logique strict, garantissant qu’un utilisateur ne puisse jamais lire ou modifier les données d’une autre organisation.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. maîtriser la syntaxe et la structure des blocs procéduraux PL/pgSQL (DECLARE, BEGIN, EXCEPTION, END) ;
  2. concevoir et déployer des fonctions déclencheurs (TRIGGER) associées aux événements BEFORE et AFTER ;
  3. exploiter rigoureusement les pseudo-enregistrements NEW et OLD pour journaliser les modifications d’attributs ;
  4. activer et configurer la sécurité au niveau de la ligne (Row-Level Security) avec CREATE POLICY ;
  5. différencier les clauses de politique RLS : USING (filtrage en lecture) et WITH CHECK (validation en écriture) ;
  6. développer en Python 3 des simulateurs de déclencheurs d’audit, des moteurs d’évaluation RLS et des détecteurs d’injections SQL.

1. Le Langage Procédural PL/pgSQL & Les Fonctions Déclencheurs

PL/pgSQL est un langage procédural structuré par blocs intégré au moteur PostgreSQL. Il permet de combiner des requêtes relationnelles avec des variables typées, des boucles (LOOP, WHILE, FOR) et des structures conditionnelles (IF/THEN/ELSE) :

Structure d’une Fonction PL/pgSQL

CREATE OR REPLACE FUNCTION virer_fonds(
    compte_src INT, compte_dest INT, montant NUMERIC
) RETURNS VOID AS $$
DECLARE
    solde_dispo NUMERIC;
BEGIN
    SELECT solde INTO solde_dispo FROM comptes WHERE id = compte_src FOR UPDATE;
    IF solde_dispo < montant THEN
        RAISE EXCEPTION 'Fonds insuffisants : disponible %', solde_dispo;
    END IF;
    UPDATE comptes SET solde = solde - montant WHERE id = compte_src;
    UPDATE comptes SET solde = solde + montant WHERE id = compte_dest;
EXCEPTION
    WHEN OTHERS THEN
        RAISE NOTICE 'Erreur transactionnelle : %', SQLERRM;
        RAISE;
END;
$$ LANGUAGE plpgsql;

Cycle de Vie et Types de Triggers

Un déclencheur intercepte une mutation (INSERT, UPDATE, DELETE, TRUNCATE) :

  • BEFORE : Déclenché avant l’écriture sur disque. Permet de modifier ou normaliser les données arrivantes, ou d’avorter l’opération (RETURN NULL ou RAISE EXCEPTION).
  • AFTER : Déclenché après la validation physique. Idéal pour propager des actions secondaires ou alimenter un journal d’audit infalsifiable.
  • FOR EACH ROW vs FOR EACH STATEMENT : S’exécute soit pour chaque ligne altérée individuellement, soit une seule fois pour toute la commande SQL.

2. Pseudo-Enregistrements NEW / OLD & Tables d’Audit Immuables

Au sein d’un déclencheur s’exécutant au niveau de la ligne (FOR EACH ROW), le moteur PostgreSQL met à disposition deux variables d’enregistrement spéciales :

Les Variables Spéciales de Trigger

OpérationOLDNEW
INSERTNULLNouvelle ligne insérée
UPDATELigne avant modificationLigne après modification
DELETELigne suppriméeNULL

La variable TG_OP contient le type d’opération ('INSERT', 'UPDATE', 'DELETE').

Patron de Conception : Table d’Audit Infalsifiable

CREATE OR REPLACE FUNCTION audit_employes_trigger()
RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'UPDATE') THEN
        INSERT INTO audit_log (table_name, op, row_id, old_val, new_val, modifie_par, modifie_le)
        VALUES ('employes', 'UPDATE', OLD.id, row_to_json(OLD), row_to_json(NEW), current_user, clock_timestamp());
        RETURN NEW;
    ELSIF (TG_OP = 'DELETE') THEN
        INSERT INTO audit_log (table_name, op, row_id, old_val, new_val, modifie_par, modifie_le)
        VALUES ('employes', 'DELETE', OLD.id, row_to_json(OLD), NULL, current_user, clock_timestamp());
        RETURN OLD;
    END IF;
    RETURN NEW;
END; $$ LANGUAGE plpgsql;
Règle d’or des Triggers AFTER : Les triggers d’audit doivent toujours être de type AFTER ... FOR EACH ROW pour s’assurer que les données ont passé toutes les contraintes d’intégrité (clés étrangères, check, unicités) avant d’être enregistrées dans le journal.

3. Sécurité au Niveau de la Ligne (Row-Level Security - RLS) & Prévention SQLi

La Row-Level Security (RLS) est une fonctionnalité de sécurité avancée intégrée dans le noyau du SGBD. Elle filtre de manière invisible les lignes accessibles par chaque utilisateur de base de données :

Configuration RLS dans PostgreSQL

-- 1. Activer RLS sur la table cible
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

-- 2. Définir une politique de cloisonnement multi-tenant
CREATE POLICY rls_documents_tenant ON documents
    FOR ALL
    TO role_applicatif
    USING (tenant_id = current_setting('app.current_tenant_id')::INT)
    WITH CHECK (tenant_id = current_setting('app.current_tenant_id')::INT);
  • USING : Condition booléenne appliquée aux requêtes de lecture (SELECT, UPDATE, DELETE). Les lignes hors condition sont invisibles.
  • WITH CHECK : Condition validée sur les nouvelles écritures (INSERT, UPDATE). Bloque toute tentative d’écriture illégitime.

Défense en Profondeur contre l’Injection SQL (SQLi)

L’injection SQL survient lorsque des entrées utilisateur non assainies sont concaténées dans des requêtes dynamiques :

-- VULNÉRABLE (Concaténation textuelle) :
EXECUTE 'SELECT * FROM users WHERE nom = ''' || entree || '''';

-- SÉCURISÉ (Requête paramétrée avec USING) :
EXECUTE 'SELECT * FROM users WHERE nom = $1' USING entree;

En PL/pgSQL dynamique, l’utilisation de la clause USING et des fonctions quote_ident() (pour les noms de tables/colonnes) et quote_literal() est indispensable pour neutraliser toute injection.

Les super-utilisateurs contournent RLS par défaut : Dans PostgreSQL, l’utilisateur postgres (superuser) ainsi que le propriétaire de la table ignorent les politiques RLS sauf si la table est explicitement configurée avec ALTER TABLE table_name FORCE ROW LEVEL SECURITY;. Dans une architecture applicative sécurisée, l’application doit toujours se connecter avec un rôle sans privilèges superuser.

5. QCM — niveau examen

Que vaut la variable OLD dans une fonction déclencheur interceptant un INSERT ?

Lors d’un INSERT, aucune ligne préalable n’existait dans la table : la variable OLD vaut donc strictement NULL.

Quel type de déclencheur est recommandé pour modifier ou normaliser les données d’une ligne avant son écriture sur disque ?

Un trigger BEFORE FOR EACH ROW s’exécute avant l’écriture disque et permet de modifier les attributs du tuple NEW avant persistance.

Si une fonction déclencheur BEFORE INSERT retourne NULL, que se passe-t-il pour la ligne en cours d’insertion ?

Retourner NULL dans un trigger BEFORE interrompt immédiatement l’opération pour le tuple courant, l’ignorant sans lever d’exception.

Dans une politique PostgreSQL Row-Level Security, quel est le rôle de la clause WITH CHECK ?

La clause WITH CHECK valide les données en entrée lors d’un INSERT ou UPDATE, rejetant toute ligne violant la condition.

Par défaut, pourquoi le super-utilisateur postgres n’est-il pas filtré par les politiques Row-Level Security ?

Dans la conception PostgreSQL, les super-utilisateurs ignorent les politiques de sécurité sauf si la directive FORCE ROW LEVEL SECURITY est appliquée.

Quelle instruction PL/pgSQL permet d’exécuter une requête dynamique sécurisée contre les injections SQL ?

L’utilisation de la clause USING avec des paramètres de substitution typés ($1) empêche toute interprétation de code malveillant.

Que contient la variable spéciale TG_OP dans un trigger PL/pgSQL ?

TG_OP contient sous forme de chaîne de caractères l’événement SQL ayant déclenché l’exécution (INSERT, UPDATE, DELETE ou TRUNCATE).

Pour garantir qu’un journal d’audit ne conserve que les transactions ayant réellement réussi, quel trigger privilégier ?

Un trigger AFTER ... FOR EACH ROW garantit que la modification a passé toutes les contraintes de table avant d’écrire l’audit.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Utiliser un trigger BEFORE au lieu d’un AFTER pour alimenter une table d’audit, risquant de journaliser une transaction qui va ensuite échouer.
  • Oublier de retourner NEW dans une fonction trigger BEFORE INSERT/UPDATE, ce qui supprime silencieusement la ligne.
  • Tester la Row-Level Security en se connectant en tant que superuser postgres, masquant ainsi l’inactivité des règles.
  • Concaténer des entrées utilisateur dans un bloc EXECUTE en PL/pgSQL, ouvrant une faille critique d’injection SQL.

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. 1. Déterminer si la règle métier doit être garantie dans la base (PL/pgSQL/Trigger) ou dans l’application cliente.
  2. 2. Choisir le moment du trigger : BEFORE pour nettoyer/valider des données, AFTER pour journaliser ou synchroniser.
  3. 3. Isoler le code procédural dans des blocs BEGIN...EXCEPTION pour garantir des rollbacks propres en cas d’anomalie.
  4. 4. Mettre en place une table d’audit immuable avec stockage JSON des états OLD et NEW.
  5. 5. Activer systématiquement ENABLE ROW LEVEL SECURITY sur toutes les tables contenant des données multi-tenants ou confidentielles.
  6. 6. Bannir toute concaténation de chaînes dans les requêtes dynamiques au profit de requêtes préparées avec clause USING.

8. Révision active

Résumé essentiel
  • PL/pgSQL apporte la puissance procédurale au moteur relationnel avec une gestion fine des exceptions et des curseurs.
  • Les triggers interceptent les opérations INSERT, UPDATE et DELETE soit avant validation physique (BEFORE), soit après (AFTER).
  • NEW représente l’état résultant d’une modification, OLD l’état antérieur ; NEW est NULL lors d’un DELETE, OLD est NULL lors d’un INSERT.
  • Row-Level Security (RLS) applique un filtrage transparent et imperméable au niveau des tuples sans modifier le code SQL applicatif.
  • La clause USING d’une politique RLS filtre les lignes visibles en lecture ; la clause WITH CHECK valide les insertions et modifications.
  • La prévention absolue contre les injections SQL exige des requêtes paramétrées avec substitution typée ($1, $2).

Checklist de maîtrise

  • Le trigger est-il déclaré FOR EACH ROW pour inspecter chaque tuple individuellement ?
  • La fonction trigger retourne-t-elle NEW pour les insertions/mises à jour valides et OLD pour les suppressions ?
  • La table d’audit enregistre-t-elle l’utilisateur système (current_user) et un horodatage précis (clock_timestamp()) ?
  • La politique RLS utilise-t-elle à la fois USING (lecture) et WITH CHECK (écriture) ?
  • L’application se connecte-t-elle avec un rôle dédié non-superuser pour que la politique RLS s’applique réellement ?
  • Toutes les requêtes dynamiques utilisent-elles des paramètres typés ($1, USING) plutôt que des concaténations ?

Les 8 notions à connaître absolument

  1. Langage PL/pgSQL (DECLARE, BEGIN, EXCEPTION)
  2. Déclencheurs (Triggers) BEFORE vs AFTER
  3. Pseudo-enregistrements NEW & OLD
  4. Opération TG_OP & variable TG_TABLE_NAME
  5. Tables d’audit immuables (Audit Logging)
  6. Row-Level Security (RLS) & ALTER TABLE ... ENABLE RLS
  7. Politiques de sécurité (CREATE POLICY ... USING / WITH CHECK)
  8. Prévention des injections SQL & requêtes paramétrées (USING)
