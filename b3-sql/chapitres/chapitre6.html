Chapitre 6 — Partitionnement Déclaratif, Réplication WAL & Haute Disponibilité (HA)

Module 6 ≈ 3 h 00 de travail Réservé B1 et plus
Mise en situation

Lorsqu’une table de base de données dépasse plusieurs dizaines ou centaines de millions de lignes et plusieurs téraoctets de données, les opérations d’indexation, de maintenance VACUUM et les scans séquentiels deviennent prohibitivement lents. En parallèle, les exigences de production imposent une disponibilité continue (99.99 %) et une tolérance totale aux pannes matérielles. Pour relever ce défi, PostgreSQL combine le partitionnement horizontal déclaratif — permettant de découper une table mère logique en partitions physiques autonomes et d’ignorer les segments non pertinents grâce au Partition Pruning — et le mécanisme de réplication physique en streaming basé sur le journal des transactions WAL (Write-Ahead Log). L’ingénieur de données doit maîtriser les stratégies de partitionnement (Range, List, Hash), le monitoring précis du lag LSN entre primaire et standby, et les compromis de consistance ACID en réplication synchrone versus asynchrone.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. concevoir une architecture de partitionnement déclaratif horizontal (RANGE, LIST, HASH) avec table mère et sous-partitions ;
  2. comprendre et activer l’élagage de partitions (Partition Pruning) au niveau de l’optimiseur CBO et au runtime ;
  3. analyser la mécanique interne du journal des transactions WAL (Write-Ahead Logging) et le rôle des Checkpoints ;
  4. différencier la réplication physique en streaming asynchrone (performance) et synchrone (zéro perte RPO=0) ;
  5. calculer et auditer le retard de réplication (Replication Lag) à partir des Log Sequence Numbers (LSN en base 16) ;
  6. développer en Python 3 des routeurs de partitionnement, des optimiseurs de pruning et des calculateurs de décalage WAL LSN.

1. Partitionnement Déclaratif Horizontal & Partition Pruning

Depuis PostgreSQL 10+, le partitionnement déclaratif permet de diviser une table volumineuse en fragments physiques distincts tout en conservant une interface relationnelle unifiée pour les requêtes applicatives :

Les Trois Stratégies de Partitionnement

  • RANGE (Intervalles) : Découpage par plages de valeurs continues (ex: par mois ou par an pour des données temporelles horodatées).
  • LIST (Listes discrètes) : Découpage selon des valeurs discrètes explicites (ex: par pays ou par code devise).
  • HASH (Hachage distribué) : Répartition pseudo-aléatoire et équilibrée à travers N compartiments selon une clé de hachage.

Syntaxe Déclarative Canonique

-- 1. Table mère partitionnée
CREATE TABLE mesures_capteurs (
    id BIGSERIAL,
    date_mesure TIMESTAMPTZ NOT NULL,
    valeur DOUBLE PRECISION
) PARTITION BY RANGE (date_mesure);

-- 2. Partitions filles physiques
CREATE TABLE mesures_2024_01 PARTITION OF mesures_capteurs
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE mesures_2024_02 PARTITION OF mesures_capteurs
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
CREATE TABLE mesures_defaut PARTITION OF mesures_capteurs DEFAULT;

Le Graal de la Performance : Le Partition Pruning

Lorsqu’une requête SQL contient une clause WHERE filtrant sur la clé de partitionnement (ex: WHERE date_mesure >= '2024-02-01' AND date_mesure < '2024-02-15'), le moteur PostgreSQL active le Partition Pruning. L’optimiseur élimine immédiatement toutes les partitions non concernées dès la compilation du plan, sans jamais lire leurs index ni leurs blocs sur disque. Cela divise le temps d’I/O par le nombre de partitions ignorées !

2. Architecture Write-Ahead Logging (WAL) & Checkpoints

Pour garantir la durabilité (le D de ACID) tout en maximisant le débit d’écriture, PostgreSQL utilise le principe fondamental du Write-Ahead Logging (WAL) :

Le Principe Fondamental du WAL

  1. Toute modification physique d’un tuple est d’abord consignée séquentiellement dans le journal WAL avant d’être répercutée dans les pages de données du buffer pool.
  2. L’écriture dans le WAL est strictement séquentielle (débit disque maximal, append-only).
  3. Lors d’un COMMIT, seul le segment WAL nécessaire est synchronisé sur disque (fsync). Les blocs de données de table restent temporairement en mémoire (pages dites « sales » ou dirty buffers).

Checkpoints & Reprise sur Panne (Crash Recovery)

À intervalles réguliers (déclenchés par checkpoint_timeout ou max_wal_size), le processus d’arrière-plan Checkpointer synchronise l’intégralité des blocs sales de la RAM vers les fichiers de table sur disque.

En cas de coupure de courant ou de crash serveur, le moteur redémarre au dernier checkpoint réussi et rejoue (REDO log) les enregistrements WAL postérieurs pour restaurer une consistance parfaite en quelques secondes.

3. Réplication en Streaming, Décalage LSN & Haute Disponibilité

La Streaming Replication physique permet de maintenir une ou plusieurs répliques miroirs (nœuds Standby) en transférant en continu les segments WAL émis par le nœud primaire :

Réplication Asynchrone vs Synchrone

  • Asynchrone : Le primaire valide le commit dès que le WAL local est écrit. Débit maximal, mais risque de perte de données en cas de crash brutal du primaire (RPO > 0).
  • Synchrone : Le primaire attend la confirmation qu’au moins une réplique standby a reçu et écrit le WAL (synchronous_commit = on). Zéro perte de données (RPO = 0), mais latence réseau accrue sur chaque commit.

Log Sequence Number (LSN) & Lag de Réplication

Chaque position dans le flux WAL est identifiée de manière unique par un entier 64-bit représenté en hexadécimal, le LSN (ex: 0/16B3800). Deux métriques clés mesurent la santé du cluster :

  • Lag d’écriture (Write Lag) : pg_wal_lsn_diff(pg_current_wal_lsn(), write_lsn) (en octets).
  • Lag d’application (Replay Lag) : pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) mesurant les données reçues mais pas encore rejouées par la standby.
Orchestration Haute Disponibilité : En production, la gestion automatique du basculement (Failover) et de l’élection d’un nouveau primaire est déléguée à des orchestrateurs spécialisés comme Patroni (utilisant un consensus distribué Raft/Etcd) ou repmgr, garantissant une reprise de service sous 10 à 30 secondes.

Exercice 1 — Routeur de partitionnement déclaratif de table (Range & List)

Étude de cas Niveau 1 — Acquisition

Objectif : Acheminer les insertions de données vers la partition physique appropriée selon la stratégie de partitionnement déclarative.

Dans PostgreSQL (à partir de la version 10), le partitionnement déclaratif horizontal divise une grande table logique en sous-tables physiques indépendantes : - `RANGE` : la partition héberge un intervalle semi-ouvert $[\text{from}, \text{to}[$ (valeur $\ge \text{from}$ et $< \text{to}$). - `LIST` : la partition accepte un ensemble fini de valeurs littérales (ex: codes régions ou statuts). - Si aucune partition ne correspond et qu’aucune partition par défaut n’existe : l’insertion échoue avec `NO_PARTITION_FOUND`. Entrée : - Définition de la stratégie : `STRATEGY type= col=` - Déclaration des partitions : Pour RANGE : `PARTITION name= from= to=` Pour LIST : `PARTITION name= values=` - Insertions : `INSERT id= =` Sortie : - Pour chaque insertion : `ROUTED row_id= val= partition= status=` - Bilan : `ROUTER_SUMMARY total= routed= unrouted=`
Cas d’exemple
STRATEGY type=RANGE col=annee
PARTITION name=p_2023 from=2023 to=2024
PARTITION name=p_2024 from=2024 to=2025
PARTITION name=p_2025 from=2025 to=2026
INSERT id=1 annee=2024
INSERT id=2 annee=2025
INSERT id=3 annee=2020
Résolution attendue
ROUTED row_id=1 val=2024 partition=p_2024 status=SUCCESS
ROUTED row_id=2 val=2025 partition=p_2025 status=SUCCESS
ROUTED row_id=3 val=2020 partition=NONE status=ERROR_NO_PARTITION
ROUTER_SUMMARY total=3 routed=2 unrouted=1

2024 va dans p_2024 ; 2020 ne correspond à aucune partition déclarée.

Deux indices, rédigés en mots
  1. Pour RANGE : convertir les bornes et valeurs en entiers pour la comparaison from <= val < to.
  2. Pour LIST : vérifier si str(val) est dans la liste values.
  3. Afficher ERROR_NO_PARTITION si aucun match n’est trouvé.

Exercice 2 — Simulateur d’élagage de partitions (Partition Pruning Optimizer)

Étude de cas Niveau 2 — Application

Objectif : Calculer les partitions éliminées (pruned) et le gain d’I/O lors de l’exécution d’une requête filtrée.

L’élagage de partitions (Partition Pruning) permet à l’optimiseur de ne scanner que les partitions physiques dont les bornes chevauchent le filtre WHERE, éliminant totalement les autres tables du plan d’exécution. L’efficacité de l’élagage est mesurée par : $$\text{Efficacité} = \frac{\text{Partitions Élaguées}}{\text{Total des Partitions}} \times 100$$ Entrée : - `PARTITIONS list=` - `QUERY id= op= val1= [val2=]` Sortie : - Pour chaque requête : `PRUNING_EVAL query_id= scanned= pruned= efficiency=%` - Bilan : `PRUNING_REPORT queries= avg_efficiency=%`
Cas d’exemple
PARTITIONS list=p_2023:2023-2024,p_2024:2024-2025,p_2025:2025-2026
QUERY id=1 op=eq val1=2024
QUERY id=2 op=gte val1=2024
Résolution attendue
PRUNING_EVAL query_id=1 scanned=p_2024 pruned=p_2023,p_2025 efficiency=66.7%
PRUNING_EVAL query_id=2 scanned=p_2024,p_2025 pruned=p_2023 efficiency=33.3%
PRUNING_REPORT queries=2 avg_efficiency=50.0%

La requête 1 élimine 2 partitions sur 3 (66.7% d’efficacité).

Deux indices, rédigés en mots
  1. Pour chaque partition [pfrom, pto[, tester l’intersection avec l’intervalle défini par le filtre.
  2. Pour eq val1 : tester pfrom <= val1 < pto.
  3. Pour gte val1 : tester pto > val1.
  4. Pour lte val1 : tester pfrom <= val1.
  5. Pour between val1 et val2 : tester (pfrom <= val2 et pto > val1).

Exercice 3 — Calculateur de lag de réplication WAL (Streaming Replication Lag)

Étude de cas Niveau 3 — Raisonnement

Objectif : Calculer le décalage de réplication en octets et en Ko entre le primaire et ses nœuds secondaires à partir de nombres LSN (Log Sequence Number).

Dans la réplication physique PostgreSQL (Streaming Replication), l’avancement des écritures dans le journal WAL est repéré par un `LSN` (Log Sequence Number) hexadécimal à deux composantes (ex: `16/B3C840`). Conversion d’un LSN en entier 64 bits d’octets : $$\text{LSN\_Bytes} = \text{int}(X, 16) \times 2^{32} + \text{int}(Y, 16)$$ Le retard de réplication (Lag) est calculé par : $$\text{Lag\_Bytes} = \text{Primary\_LSN} - \text{Replica\_LSN}$$ $$\text{Lag\_Ko} = \frac{\text{Lag\_Bytes}}{1024.0}$$ Évaluation de la santé : - Si `Lag_Bytes == 0` : `SYNCED` (parfaite synchronisation). - Si `0 < Lag_Ko <= 64` : `HEALTHY_LAG` (retard opérationnel normal en réplication asynchrone). - Si `Lag_Ko > 64` : `CRITICAL_LAG` (danger de perte de données en cas de failover, violation de RPO). Entrée : `REPLICA node= mode= primary_lsn= replay_lsn=` Sortie : `LAG_STATUS node= mode= lag_bytes= lag_kb= health=` `CLUSTER_STATUS total_nodes= max_lag_kb=`
Cas d’exemple
REPLICA node=standby_1 mode=async primary_lsn=0/16B3C840 replay_lsn=0/16B3A000
REPLICA node=standby_2 mode=sync primary_lsn=0/16B3C840 replay_lsn=0/16B3C840
Résolution attendue
LAG_STATUS node=standby_1 mode=async lag_bytes=10304 lag_kb=10.06 health=HEALTHY_LAG
LAG_STATUS node=standby_2 mode=sync lag_bytes=0 lag_kb=0.00 health=SYNCED
CLUSTER_STATUS total_nodes=2 max_lag_kb=10.06

standby_1 a un léger retard de 10 Ko (sain), standby_2 est parfaitement synchronisé.

Deux indices, rédigés en mots
  1. Découper le LSN sur le caractère "/" : high, low = lsn.split("/").
  2. Calculer lsn_val = int(high, 16) * (2**32) + int(low, 16).
  3. Calculer lag_bytes = primary_bytes - replay_bytes.
  4. Comparer lag_kb aux seuils 0 et 64 Ko.

5. QCM — niveau examen

Quelle stratégie de partitionnement convient le mieux à une table de transactions bancaires conservant 10 ans d’historique ?

Le partitionnement par intervalle (RANGE) sur la date permet un élagage massif sur les requêtes temporelles et un archivage facile des vieux mois.

Qu’est-ce que le Partition Pruning dans PostgreSQL ?

Le Partition Pruning ignore les partitions dont les contraintes contredisent les critères de la clause WHERE de la requête.

Pourquoi PostgreSQL écrit-il dans le WAL avant d’écrire dans les pages de table sur disque ?

Le WAL garantit la persistance immédiate par écriture séquentielle append-only, permettant de repousser les écritures aléatoires au Checkpoint.

Que se passe-t-il lors d’un Checkpoint dans PostgreSQL ?

Le Checkpoint synchronise toutes les données modifiées en RAM avec les fichiers disque, bornant la durée de récupération en cas de crash.

Quelle fonction PostgreSQL permet de calculer l’écart en octets entre deux Log Sequence Numbers (LSN) ?

pg_wal_lsn_diff() calcule la différence numérique exacte en octets entre deux positions LSN fournies au format hexadécimal.

En réplication en streaming synchrone (synchronous_commit = on), quand le primaire valide-t-il un COMMIT ?

Le mode synchrone garantit un RPO de 0 en attendant l’acquittement physique de la réplique avant de confirmer la transaction au client.

Quel risque majeur présente un physical replication slot laissé actif alors que le serveur standby associé est éteint ?

Un replication slot orphelin empêche le primaire de nettoyer ses WAL, saturant l’espace disque jusqu’au blocage total de la base.

Quel outil open source de haute disponibilité utilise un magasin de consensus distribué (comme Etcd) pour orchestrer le basculement automatique ?

Patroni est la solution de référence pour la haute disponibilité PostgreSQL, utilisant Etcd ou Consul pour le consensus et le failover sécurisé.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Oublier de créer les partitions futures sur une table partitionnée par RANGE, provoquant l’échec des insertions au changement de mois.
  • Filtrer avec une fonction non-immutable dans le WHERE, ce qui empêche le Partition Pruning à la compilation.
  • Ne pas surveiller l’espace disque du WAL en présence d’un replication slot inactif, menant à la saturation complète du disque primaire.
  • Confondre le lag de réception WAL (write_lsn) et le lag d’application des données (replay_lsn) sur la standby.

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. 1. Évaluer la volumétrie prévisionnelle : envisager le partitionnement dès qu’une table dépasse 20 à 50 millions de lignes.
  2. 2. Déterminer la clé de partitionnement : date chronologique pour RANGE, dimension géographique ou statut pour LIST.
  3. 3. Créer systématiquement une partition DEFAULT pour intercepter et alerter sur les valeurs hors bornes.
  4. 4. Vérifier avec EXPLAIN que le Partition Pruning élimine bien les partitions physiques sur les requêtes types.
  5. 5. Configurer la réplication en streaming avec des Replication Slots pour éviter la suppression prématurée des segments WAL.
  6. 6. Monitorer en continu le décalage LSN (replication lag) via pg_stat_replication et déclencher des alertes au-delà d’un seuil critique.

8. Révision active

Résumé essentiel
  • Le partitionnement déclaratif découpe physiquement une table logique en fragments autonomes sans altérer le code SQL.
  • Le Partition Pruning permet à l’optimiseur d’ignorer totalement la lecture des partitions dont les bornes ne satisfont pas la clause WHERE.
  • Le Write-Ahead Log (WAL) garantit la durabilité ACID et la vitesse d’écriture en journalisant séquentiellement chaque mutation.
  • Les Checkpoints vident régulièrement les pages modifiées de la mémoire vers le stockage de données définitif.
  • La réplication physique transmet le flux WAL du primaire vers les standbys en mode asynchrone ou synchrone.
  • Le lag de réplication se mesure par la différence numérique entre le LSN courant du primaire et le LSN rejoué par la standby.

Checklist de maîtrise

  • La table volumineuse est-elle partitionnée par RANGE (temporel) ou LIST (catégoriel) selon son profil d’accès ?
  • La partition DEFAULT est-elle déclarée pour éviter les erreurs d’insertion de clés inattendues ?
  • Le plan d’exécution EXPLAIN confirme-t-il l’activité de Partition Pruning sur les requêtes filtrées ?
  • Le paramètre max_wal_size et checkpoint_timeout sont-ils ajustés pour lisser les I/O du serveur ?
  • Les répliques standby utilisent-elles un physical replication slot pour sécuriser la rétention des WAL ?
  • Le décalage LSN en octets et le replay lag en secondes font-ils l’objet d’un monitoring Prometheus/Grafana dédié ?
