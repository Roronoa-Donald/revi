Chapitre 3 — Supervision des Systèmes & Réseaux avec Zabbix & Nagios Core

Module 3 ≈ 2 h 45 Réservé B3 et plus
Mise en situation

Votre entreprise dispose d'un parc hétérogène comprenant à la fois des serveurs Linux Debian/CentOS, des serveurs Windows Active Directory et des commutateurs infogérés. Vous êtes chargé d'orchestrer la supervision opérationnelle avec les deux outils piliers du marché open source : auditer et déployer les plugins Nagios avec traitement des métriques de performance (Perfdata), configurer Zabbix en mode agent actif et passif avec des templates personnalisés, concevoir des déclencheurs booléens prédictifs et instaurer une politique d'escalade automatique suspendant les alertes dès l'acquittement par l'ingénieur d'astreinte.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. Comprendre l'architecture de Nagios Core et développer/analyser des sondes de supervision respectant les 4 codes retour et le format Perfdata.
  2. Déployer et configurer Zabbix (Server, Frontend Web, Agent passif port 10050, Agent actif port 10051 et Zabbix Proxy).
  3. Concevoir des templates modulaires Zabbix articulant Items, Applications, Déclencheurs (Triggers) et Macros contextuelles.
  4. Programmer des déclencheurs avancés (fonctions avg, last, min, max) et structurer un moteur d'escalade d'incidents avec gestion des acquittements.

1. Nagios Core : Architecture, Plugins & Données de Performance (Perfdata)

Pionnier historique de la supervision open source, Nagios Core repose sur une architecture modulaire ultra-légère basée sur l'exécution périodique de binaires ou de scripts autonomes appelés plugins :

Exécution Distante via NRPE & NSClient++

  • Sondes locales vs distantes : Nagios vérifie les services réseau (HTTP, Ping) directement depuis le serveur maître. Pour les métriques internes (disque, RAM), il s'appuie sur un agent distant.
  • NRPE (Nagios Remote Plugin Executor) : Démon écoutant sur le port 5666/TCP des machines Linux. Le serveur ordonne l'exécution locale d'une commande (ex: check_disk) et récupère le code de retour.
  • NSClient++ : Agent équivalent pour les environnements Microsoft Windows permettant la collecte WMI et compteurs de performance.

Spécification Standard des Plugins Nagios

Chaque sonde communique avec le moteur Nagios selon deux règles strictes :

  1. Code de sortie processus :
    0 = OK (nominal), 1 = WARNING (seuil d'alerte), 2 = CRITICAL (panne), 3 = UNKNOWN (erreur d'exécution).
  2. Format de sortie textuelle :
    TEXT MESSAGE | PERFDATA
    Où la section Perfdata (après |) respecte la syntaxe :
    'label'=valeur[uom];[warn];[crit];[min];[max]

2. Zabbix Enterprise : Architecture, Agents Passifs/Actifs & Templates

Plateforme de supervision tout-en-un moderne, Zabbix intègre nativement la collecte, le stockage relationnel/NoSQL, la détection complexe et la visualisation graphique :

Composants Zabbix

  • Zabbix Server : Cœur du système qui planifie la collecte, évalue les triggers et déclenche les alertes.
  • Base de Données : Stockage des configurations et de l'historique des métriques (PostgreSQL / MySQL / TimescaleDB).
  • Zabbix Frontend : Interface web moderne d'administration et de tableaux de bord.
  • Zabbix Proxy : Relais pour environnements distribués et DMZ.

Agent Passif vs Actif

  • Mode Passif (port 10050/TCP) : Le serveur Zabbix contacte l'agent sur la machine cible et lui demande la valeur d'un item (modèle Polling traditionnel).
  • Mode Actif (port 10051/TCP) : L'agent contacte le serveur, télécharge sa liste d'items à mesurer, puis pousse les données collectées périodiquement. Idéal pour les pare-feux stricts et les machines derrière NAT.

Hiérarchie des Objets

  • Host : Équipement ou serveur physique/virtuel surveillé.
  • Item : Métrique unitaire brute (ex: system.cpu.util).
  • Trigger : Condition logique d'alerte.
  • Template : Modèle réutilisable agrégeant items, triggers, graphiques et règles de découverte (LLD).

3. Déclencheurs Avancés (Triggers) & Politiques d'Escalade d'Incidents

Pour éviter les faux positifs et garantir la résolution rapide des pannes, Zabbix propose un moteur d'expressions puissant et une gestion stricte des escalades :

Fonctions Temporelles de Déclenchement

Un trigger évalue l'historique des valeurs sur une fenêtre glissante :

  • last() : Dernière valeur reçue.
  • avg(5m) : Moyenne arithmétique sur 5 minutes (lisse les pics éphémères).
  • max(10m) / min(10m) : Valeur extrême sur la période.
  • nodata(5m) : Détecte l'absence de télémétrie (panne de l'agent ou de la sonde).

Exemple de trigger robuste :
avg(/srv-db/system.cpu.load,5m) > 80 and last(/srv-db/system.cpu.load) > 90

Paliers d'Escalade & Acquittement (ACK)

Lorsqu'un problème est détecté, le système ordonnance les notifications par échelons temporels :

  1. Échelon 1 (immédiat) : Notification email / chat à l'équipe d'exploitation N1.
  2. Échelon 2 (après 15 min sans ACK) : Alerte SMS / appel automatique à l'ingénieur d'astreinte N2.
  3. Échelon 3 (après 30 min sans ACK) : Escalade hiérarchique au responsable des opérations (Manager).

Dès qu'un exploitant acquitte (Acknowledge) l'incident dans la console, l'escalade est immédiatement gelée.

Exercice 1 — Analyseur de Sortie Plugin Nagios et Métriques Perfdata

Étude de cas Niveau 1 — Acquisition

Objectif : Interpréter le code de retour d'un plugin Nagios et extraire les données de performance (perfdata) normalisées.

L'architecture de supervision Nagios/Centreon standardise la communication des plugins :

1. Code de retour :
- 0 : OK
- 1 : WARNING
- 2 : CRITICAL
- 3 : UNKNOWN

2. Structure de la sortie :
MESSAGE_TEXT | PERFDATA (le caractère tube sépare le message humain des métriques machine).
Dans la section Perfdata, chaque métrique suit le format : label=valeur[uom];[warn];[crit];[min];[max].

Entrée STDIN : NAGIOS_PLUGIN CODE=<0..3> OUTPUT=<texte|perfdata>.
Sortie : NAGIOS: status=<OK|WARNING|CRITICAL|UNKNOWN> message=<msg> metrics=<label1=valeur1,label2=valeur2...|NONE>.

Cas d’exemple
NAGIOS_PLUGIN CODE=1 OUTPUT=DISK WARNING - free space: / 15% (15GB/100GB)|/=85GB;80;90;0;100 /var=40GB;70;85;0;100
Résolution attendue
NAGIOS: status=WARNING message=DISK WARNING - free space: / 15% (15GB/100GB) metrics=/=85GB,/var=40GB

Statut WARNING et extraction de deux partitions disques.

Deux indices, rédigés en mots
  1. Isolez la section message et la section perfdata autour du caractère '|'.
  2. Pour chaque élément perfdata, extrayez la partie label=valeur (avant le premier point-virgule).

Exercice 2 — Moteur d’Évaluation des Déclencheurs Zabbix (Triggers)

Étude de cas Niveau 2 — Application

Objectif : Évaluer une fonction temporelle de trigger Zabbix (avg, last, min, max) et calculer l'état d'alarme et son niveau de sévérité.

Dans Zabbix, un déclencheur calcule dynamiquement l'état d'un équipement à partir d'une suite de valeurs collectées :

Fonctions supportées :
- avg : Moyenne arithmétique de la liste.
- last : Dernière valeur observée (dernier élément de la liste).
- min : Valeur minimale observée.
- max : Valeur maximale observée.

Opérateurs : GT (>), GTE (>=), LT (<), LTE (<=), EQ (==).

Sévérité :
- Si l'alarme se déclenche (fired=YES) :
- Si computed >= 90.0 : DISASTER
- Sinon si computed >= 75.0 : HIGH
- Sinon : WARNING
- Si l'alarme ne se déclenche pas : fired=NO et severity=OK.

Entrée STDIN : ZABBIX_TRIGGER ITEM=<clef> FN=<avg|last|min|max> OP=<GT|GTE|LT|LTE|EQ> THRESHOLD=<seuil> VALUES=<v1,v2,...>.
Sortie : ZABBIX: item=<ITEM> computed=<val:.2f> fired=<YES|NO> severity=<DISASTER|HIGH|WARNING|OK>.

Cas d’exemple
ZABBIX_TRIGGER ITEM=system.cpu.load FN=avg OP=GT THRESHOLD=75.0 VALUES=65.0,72.5,80.0,85.5,92.0
Résolution attendue
ZABBIX: item=system.cpu.load computed=79.00 fired=YES severity=HIGH

Moyenne égale à 79.00 > 75.0 déclenche une alerte HIGH.

Deux indices, rédigés en mots
  1. Convertissez les valeurs d'historique en liste de floats.
  2. Calculez la métrique selon la fonction demandée puis appliquez l'opérateur de comparaison.

Exercice 3 — Moteur d’Escalade et Traitement des Acquittements d’Incidents

Étude de cas Niveau 3 — Raisonnement

Objectif : Ordonnancer les paliers d'escalade de notifications selon le temps d'indisponibilité non acquitté.

Pour garantir la prise en charge rapide des pannes, les systèmes de supervision automatisent l'escalade :

Règles temporelles d'escalade (si ACK=NO) :
- DURATION_MIN >= 30 : STAGE=3 CHANNEL=SMS TARGET=manager-on-call.
- DURATION_MIN >= 15 : STAGE=2 CHANNEL=SLACK TARGET=#astreinte-infra.
- Sinon (DURATION_MIN < 15) : STAGE=1 CHANNEL=EMAIL TARGET=noc-team@corp.local.
- Dans ces cas, le statut vaut ESCALATING.

Si l'incident est acquitté (ACK=YES) :
- Les notifications automatiques sont immédiatement suspendues : STAGE=0 CHANNEL=NONE TARGET=NONE status=PAUSED_ACKNOWLEDGED.

Entrée STDIN : ALERT_ESCALATE INCIDENT=<id> DURATION_MIN=<min> ACK=<YES|NO>.
Sortie : ESCALATION: incident=<id> stage=<STAGE> channel=<CHANNEL> target=<TARGET> status=<ESCALATING|PAUSED_ACKNOWLEDGED>.

Cas d’exemple
ALERT_ESCALATE INCIDENT=INC-8902 DURATION_MIN=20 ACK=NO
Résolution attendue
ESCALATION: incident=INC-8902 stage=2 channel=SLACK target=#astreinte-infra status=ESCALATING

20 minutes non acquitté déclenche l'échelon 2 sur Slack.

Deux indices, rédigés en mots
  1. Vérifiez d'abord si l'incident est acquitté (ACK=YES).
  2. Si non acquitté, testez les seuils de 30 minutes, puis 15 minutes, puis le palier initial.

5. QCM — niveau examen

Quel code de sortie un plugin Nagios doit-il renvoyer pour signaler un état CRITICAL au moteur de supervision ?

Selon la spécification officielle Nagios : 0=OK, 1=WARNING, 2=CRITICAL, et 3=UNKNOWN.

Quel caractère sépare le message lisible par l'opérateur des métriques Perfdata dans la sortie d'un plugin Nagios ?

Le caractère tube "|" sépare la ligne de texte humain des données de performance Perfdata destinées au traçage de graphiques.

Sur quel port TCP un agent Zabbix configuré en mode passif écoute-t-il les requêtes du serveur Zabbix ?

En mode passif, le Zabbix Agent écoute sur le port 10050/TCP. En mode actif, c'est l'agent qui initie la connexion vers le serveur sur le port 10051/TCP.

Dans Zabbix, quelle fonction de trigger permet de calculer la moyenne des mesures sur une fenêtre de 5 minutes ?

La fonction avg(5m) calcule la moyenne arithmétique de la métrique sur les 5 dernières minutes, ce qui permet de lisser les pics temporaires.

Quel est l'effet immédiat de l'action « Acquitter » (Acknowledge) d'un incident par un exploitant dans la console de supervision ?

L'acquittement signale au système qu'un opérateur humain a pris en charge le problème, ce qui stoppe les paliers d'escalade vers les échelons supérieurs.

Quel démon permet au serveur Nagios d'exécuter des plugins locaux sur des serveurs distants Linux ?

NRPE écoute sur le port 5666/TCP des hôtes Linux et exécute les plugins de supervision locaux à la demande du serveur Nagios.

Pourquoi le mode agent actif de Zabbix est-il particulièrement avantageux pour surveiller des postes nomades ou des serveurs en cloud privé ?

En mode actif, l'agent initie une connexion sortante standard vers le port 10051 du Zabbix Server, ce qui traverse sans difficulté les passerelles NAT et pare-feux.

Dans la syntaxe Perfdata « disk_free=15GB;20;10;0;100 », que représente la valeur 20 ?

Dans la structure label=value;warn;crit;min;max, le premier paramètre après la valeur mesurée est le seuil de WARNING (ici 20).

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Définir des triggers Zabbix basés uniquement sur la fonction last() pour la charge CPU : cela génère une avalanche de faux positifs à chaque micro-pic applicatif.
  • Oublier de configurer le pare-feu pour le port 5666/TCP (NRPE) ou 10050/TCP (Zabbix Agent passif).
  • Ne pas inclure de données Perfdata dans les scripts de sondes personnalisés : impossibilité totale de tracer des graphiques de métrologie dans Nagios/Centreon.
  • Ne pas activer la détection de flapping sur les services oscillants, saturant les canaux de notification de l'astreinte.

7. Méthodologie de résolution

Démarche d’Exploitation : Nagios, Centreon & Zabbix
  1. Développer des sondes conformes aux standards Nagios : respecter scrupuleusement les codes de sortie 0=OK, 1=WARNING, 2=CRITICAL, 3=UNKNOWN et formater la chaîne perfdata standardisée.
  2. Déployer et sécuriser les agents distants : installer NRPE ou Zabbix Agent avec filtrage d'adresses IP autorisées et certificats TLS.
  3. Composer des déclencheurs (triggers) intelligents : combiner les fonctions temporelles avg() et last() pour filtrer les faux positifs et absorber le bruit transitoire.
  4. Configurer les politiques d'escalade et d'acquittement : définir des règles d'acheminement N1/N2/N3 temporisées et conditionnées à l'absence d'ACK dans la console.

8. Révision active

Résumé essentiel
  • L'écosystème Nagios repose sur une architecture modulaire de plugins vérifiant ponctuellement l'état des services et machines.
  • Le format Perfdata (ex: metric=val;warn;crit;min;max) permet l'historisation et le rendu graphique au sein de solutions comme Centreon ou Graphite.
  • Zabbix offre une solution intégrée tout-en-un avec base de données dédiée, templates réutilisables et agent de collecte haut débit.
  • Les triggers Zabbix évaluent des expressions booléennes complexes sur des fenêtres temporelles glissantes (avg, min, max, nodata).
  • L'acquittement d'incident (ACK) est la pierre angulaire de la coordination des équipes d'astreinte, gelant immédiatement le processus d'escalade.

Checklist de maîtrise

  • Connaissez-vous les 4 codes de sortie obligatoires d'un plugin Nagios (0, 1, 2, 3) ?
  • Savez-vous formater une ligne de sortie avec métriques Perfdata conformes à la spécification Nagios ?
  • Quelle est la différence fondamentale entre le mode actif et le mode passif de l'agent Zabbix ?
  • Savez-vous écrire un trigger Zabbix combinant une moyenne sur 5 minutes et un seuil critique instantané ?
  • Comment fonctionne le cycle d'escalade et quel est l'effet immédiat d'un acquittement (ACK) par l'opérateur ?

Les 8 notions à connaître absolument

  1. Nagios Core : Moteur de supervision modulaire exécutant des plugins autonomes vérifiant l'état des services et des hôtes.
  2. NRPE : Nagios Remote Plugin Executor : démon d'écoute sur le port 5666/TCP permettant d'exécuter des sondes locales sur un hôte distant.
  3. Perfdata : Données de performance normalisées retournées par une sonde après le séparateur | pour tracer des graphiques.
  4. Zabbix Agent : Agent de collecte ultra-performant fonctionnant en mode passif (10050/TCP) ou actif (10051/TCP).
  5. Trigger Zabbix : Expression logique booléenne calculée à partir de fonctions temporelles pour qualifier l'état d'un service.
  6. Escalade d'Alerte : Mécanisme d'augmentation progressive des canaux et cibles de notification tant qu'une alerte n'est pas acquittée.
