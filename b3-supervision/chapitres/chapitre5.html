Chapitre 5 — Gestion des Journaux & Logs Centralisés, Détection d'Anomalies & SIEM (ELK/EFK)

Module 5 ≈ 2 h 45 Réservé B3 et plus
Mise en situation

L'équipe sécurité (SOC) et les exploitants système constatent des difficultés à identifier l'origine des incidents complexes sur les 50 serveurs de l'entreprise : les journaux sont dispersés sur chaque machine, formatés de manière hétérogène et écrasés par la rotation locale des fichiers. Vous êtes mandaté pour déployer un pipeline centralisé d'ingestion et d'analyse de logs : configurer des agents légers Filebeat, concevoir des filtres Logstash pour normaliser les logs applicatifs et web en JSON structuré, surveiller en temps réel le débit d'événements (EPS) pour repérer les pannes silencieuses ou les inondations, et corréler les traces multi-équipements pour isoler et mettre en quarantaine les comportements hostiles.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. Concevoir et déployer un pipeline complet de collecte de logs avec la suite Elastic (Filebeat, Logstash, Elasticsearch, Kibana) ou OpenSearch.
  2. Analyser et structurer des journaux texte bruts (Apache, Nginx, Syslog) en documents JSON normalisés via des filtres et motifs grok.
  3. Surveiller la métrologie des flux de logs en calculant le taux d'événements par seconde (EPS) pour détecter les anomalies de type Spike et Drop.
  4. Corréler des événements multi-sources (pare-feu, reverse proxy, serveur d'authentification) pour reconstituer la chronologie d'un incident de sécurité.

1. L'Architecture de Centralisation des Journaux : Filebeat, Logstash & Elasticsearch

La centralisation des logs répond à trois impératifs : conformité légale de rétention, audit de sécurité après compromission et diagnostic rapide en production :

1. Collecte : Filebeat

Agent de transport ultra-léger développé en Go, déployé sur chaque nœud pour lire les fichiers journaux locaux sur disque (/var/log/*).

Filebeat intègre la gestion de contre-pression (backpressure) : si le serveur central est saturé, Filebeat ralentit sa lecture sans saturer la mémoire.

2. Traitement : Logstash

Moteur d'ingestion et de transformation lourde fonctionnant en pipeline à 3 étapes :

  • Inputs : Écoute Beats (port 5044/TCP), Syslog (514), Kafka.
  • Filters : Découpage grok, parsing JSON, normalisation de dates et enrichissement GeoIP.
  • Outputs : Indexation vers Elasticsearch (port 9200/TCP).

3. Indexation : Elasticsearch

Moteur d'indexation inversée distribué basé sur Apache Lucene :

Organise les documents en index découpés en fragments (shards) répliqués sur un cluster pour garantir tolérance aux pannes et recherche textuelle instantanée.

Visualisation via l'interface Kibana (port 5601/TCP).

2. Normalisation des Logs & Parsing Grok

Un log texte non structuré est inexploitable pour les agrégations statistiques et les requêtes analytiques :

Du Texte Brut au Document JSON

Soit une ligne de log web au format Apache/Nginx Combined :

192.168.1.10 - - [11/Oct/2026:14:32:10 +0000] "GET /api/v1/users HTTP/1.1" 500 2314 "-" "curl/7.88.1"

Après application du filtre grok, elle devient un document structuré indexé avec des types de données stricts :

  • client_ip : type ip pour géolocalisation et filtrage CIDR.
  • status_code : type integer permettant de calculer le taux d'erreurs HTTP 4xx et 5xx.
  • response_bytes : type long pour mesurer la bande passante consommée.

Standardisation ECS (Elastic Common Schema)

Pour corréler des logs provenant de serveurs Windows, d'équipements Cisco et de conteneurs Linux, il est impératif d'unifier le nommage des champs grâce au schéma standard ECS :

  • source.ip pour l'adresse IP cliente.
  • http.response.status_code pour le code HTTP.
  • event.dataset pour classifier la source applicative.
  • @timestamp normalisé en UTC selon la norme ISO 8601.

3. Métrologie des Flux de Logs (EPS) & Détection d'Incidents SIEM

La télémétrie du volume d'événements est une sonde de surveillance opérationnelle majeure :

Analyse de Débit EPS (Events Per Second)

Surveiller l'EPS moyen par rapport à une base de référence (Baseline) permet de détecter deux types de crises majeures :

  • Log Flood (Spike, > +200%) : Inondation anormale de journaux provoquée par une attaque par déni de service, une boucle infinie de code générant des exceptions en cascade ou un brute-force massif.
  • Log Drop (Chute, < -80%) : Silence anormal signalant qu'un équipement critique a crashé, qu'un agent Filebeat est bloqué ou qu'un lien réseau est interrompu.

Corrélation Multi-Sources d'Incidents

Un attaquant ou une panne transverse laisse des empreintes dispersées dans plusieurs journaux :

  1. Le pare-feu enregistre des scans de ports depuis l'IP suspecte.
  2. Le reverse proxy Nginx enregistre des dizaines de requêtes 401 Unauthorized sur /auth/login.
  3. Le démon SSH consigne de multiples échecs de connexion root.

En corrélant ces événements par adresse IP sur une fenêtre temporelle restreinte, le SIEM isole automatiquement la menace et applique une règle de quarantaine dynamique.

Exercice 1 — Parseur et Normalisateur de Logs Web Nginx / Apache

Python Niveau 1 — Acquisition

Objectif : Extraire les champs structurés d'une ligne de journal HTTP Combined Log et classifier la réponse par catégorie.

Dans une chaîne Logstash / Fluentd, le parsing grok décompose la ligne de log :

Format standard Combined Log :
<client_ip> - - [<timestamp>] "<method> <uri> <http_version>" <status_code> <response_bytes> "<referrer>" "<user_agent>"

Catégories de statut :
- 200..299 : SUCCESS
- 400..499 : CLIENT_ERROR
- 500..599 : SERVER_ERROR
- Autre : OTHER

Entrée STDIN : LOG_PARSE <combined_log_line>.
Sortie : WEB_LOG: ip=<client_ip> method=<method> uri=<uri> status=<status_code> bytes=<bytes> category=<category>.

Entrée du programme
LOG_PARSE 192.168.1.10 - - [11/Oct/2026:14:32:10 +0000] "GET /api/v1/users HTTP/1.1" 500 2314 "-" "curl/7.88.1"
Sortie attendue
WEB_LOG: ip=192.168.1.10 method=GET uri=/api/v1/users status=500 bytes=2314 category=SERVER_ERROR

Erreur serveur 500 sur une requête GET.

Deux indices, rédigés en mots
  1. Isolez l'adresse IP, la requête entre guillemets et le code de statut HTTP.
  2. Gérez le cas où les octets sont représentés par un tiret '-' en affectant 0.

Exercice 2 — Détecteur d’Anomalies de Débit de Logs (Spike & Drop)

Python Niveau 2 — Application

Objectif : Surveiller les variations d'Events Per Second (EPS) et détecter les pics anormaux (inondation) ou chutes brutales (panne de collecte).

La télémétrie des flux de logs permet de repérer des anomalies opérationnelles majeures :

Calcul de déviation sur le dernier échantillon de débit mesuré current :
deviation_pct = ((current - BASELINE) / BASELINE) * 100.0.

Règles d'alerte :
- Si deviation_pct >= MAX_SPIKE : alert=LOG_FLOOD action=REQUIRED.
- Sinon si deviation_pct <= -MIN_DROP : alert=LOG_DROP action=REQUIRED.
- Sinon : alert=NORMAL action=NONE.

Entrée STDIN : EPS_CHECK BASELINE=<base> MIN_DROP=<drop_pct> MAX_SPIKE=<spike_pct> SAMPLES=<s1,s2,...>.
Sortie : EPS_ALERT: current=<curr:.1f> deviation=<dev_pct:+.1f>% alert=<LOG_FLOOD|LOG_DROP|NORMAL> action=<REQUIRED|NONE>.

Entrée du programme
EPS_CHECK BASELINE=500.0 MIN_DROP=80.0 MAX_SPIKE=200.0 SAMPLES=480.0,510.0,520.0,1600.0
Sortie attendue
EPS_ALERT: current=1600.0 deviation=+220.0% alert=LOG_FLOOD action=REQUIRED

Pic de débit de +220% dépassant le seuil de 200% : LOG_FLOOD.

Deux indices, rédigés en mots
  1. Extrayez la dernière valeur de la liste SAMPLES.
  2. Formatez la déviation avec un signe explicite (+ ou -) via :+.1f.

Exercice 3 — Corrélateur Multi-Sources de Logs d’Incidents de Sécurité

Python Niveau 3 — Raisonnement

Objectif : Regrouper et corréler les traces d'une adresse IP suspecte à travers des équipements hétérogènes.

En analyse SOC / SIEM, les traces laissées sur différents serveurs sont corrélées :

Critères de décision :
- Un événement est considéré suspect si sa sévérité est WARN, ALERT ou DENY.
- La mise en quarantaine (quarantine=YES) est décidée si l'adresse IP cible cumule >= 3 événements suspects OU si au moins un événement porte la sévérité bloquante DENY.
- Sinon, quarantine=NO.

Entrée STDIN : CORRELATE TARGET_IP=<ip> LOGS=<src1:ip1:act1:sev1|src2:ip2:act2:sev2|...>.
Sortie : CORRELATION: ip=<TARGET_IP> events=<total_matches> suspicious=<n_suspects> quarantine=<YES|NO>.

Entrée du programme
CORRELATE TARGET_IP=198.51.100.42 LOGS=firewall:198.51.100.42:PortScan:WARN|proxy:198.51.100.42:AuthFailed:WARN|proxy:10.0.0.5:HomeView:INFO|auth:198.51.100.42:BruteForce:ALERT
Sortie attendue
CORRELATION: ip=198.51.100.42 events=3 suspicious=3 quarantine=YES

3 événements suspects cumulés entraînent une mise en quarantaine.

Deux indices, rédigés en mots
  1. Isolez les événements correspondant à TARGET_IP.
  2. Vérifiez si le nombre d'événements suspects est >= 3 ou si la sévérité DENY apparaît.

5. QCM — niveau examen

Quel est l'avantage principal de Filebeat par rapport à Logstash pour la collecte de journaux sur les serveurs applicatifs ?

Filebeat a été spécialement conçu pour être un expéditeur ultra-léger (Go) qui n'impacte pas les performances des serveurs hébergeant les applications métiers.

Sur quel port TCP par défaut l'API REST d'Elasticsearch écoute-t-elle les requêtes d'indexation et de recherche ?

Elasticsearch écoute sur le port 9200/TCP pour son API REST HTTP. Le port 5601 est Kibana, le 5044 le port d'écoute Beats de Logstash.

Dans la terminologie Logstash, que désigne un filtre « grok » ?

Grok permet d'associer des motifs regex réutilisables (ex: %{IP:client_ip}) pour transformer facilement des lignes de logs brutes en documents JSON.

Si un cluster de logs fonctionnant habituellement à 500 EPS subit une chute brutale à 10 EPS sur un service critique, comment qualifie-t-on cette anomalie ?

Une chute massive de débit sous la baseline normale est un Log Drop, indiquant fréquemment un arrêt inopiné du service émetteur ou une rupture de connectivité.

Quel port TCP Kibana utilise-t-il par défaut pour son interface web d'administration et de tableaux de bord ?

Kibana est accessible sur le port 5601/TCP par défaut.

Que signifie le concept de « backpressure » implémenté dans Filebeat ?

Le contrôle de contre-pression permet à Filebeat d'adapter son rythme d'émission à la capacité d'ingestion en aval sans perdre d'événements.

Pourquoi est-il nécessaire d'utiliser un schéma commun comme l'ECS (Elastic Common Schema) lors de l'ingestion de logs provenant de sources hétérogènes ?

Si chaque équipement nomme différemment l'adresse IP source (src_ip, client, host_ip, remote_addr), il est impossible d'exécuter une requête corrélée unique.

Dans un SIEM, quel critère permet de relier chronologiquement une attaque par injection SQL sur un serveur web à une création suspecte de compte administrateur sur une machine Linux ?

La corrélation spatio-temporelle repose sur des identifiants partagés (adresse IP, trace_id, identifiant utilisateur) et une synchronisation d'horloge rigoureuse (NTP).

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Déployer Logstash directement sur tous les serveurs clients à la place de Filebeat : Logstash consomme une JVM lourde et monopolise les ressources applicatives.
  • Ne pas indexer les timestamps dans un format UTC normalisé (ISO 8601), ce qui rend impossible la corrélation chronologique entre serveurs situés sur des fuseaux différents.
  • Négliger la rotation et la purge des index anciens dans Elasticsearch, conduisant à la saturation complète des disques et au gel du cluster.
  • Ignorer les chutes brutales d'EPS (Log Drop) : un silence radio dans les logs est souvent le signe d'une panne majeure non détectée.

7. Méthodologie de résolution

Démarche d’Ingénierie : Centralisation & Analyse de Logs (ELK)
  1. Déployer des expéditeurs légers (Beats) : installer Filebeat sur les serveurs cibles avec contrôle de débit (backpressure) et acheminement chiffré vers Logstash ou Elasticsearch.
  2. Structurer et enrichir les journaux : construire des filtres Logstash ou Ingest Node avec motifs grok, conversions de types, géolocalisation IP et normalisation UTC.
  3. Dimensionner le stockage et l'indexation Elasticsearch : configurer les Index Lifecycle Management (ILM) avec politiques de rétention, rollovers et tiers chauds/froids.
  4. Implémenter la détection d'anomalies et la corrélation SIEM : surveiller les débits EPS (spikes et drops) et croiser les sources (Nginx, SSH, pare-feu) pour neutraliser les cyberattaques.

8. Révision active

Résumé essentiel
  • La stack Elastic (Elasticsearch, Logstash, Kibana, Beats) constitue le standard de l'industrie pour la centralisation, le parsing et l'analyse de logs massifs.
  • Filebeat assure une collecte locale économe en ressources avec maintien d'un registre d'offset disque pour garantir l'absence de perte de données.
  • Le parsing grok transforme les flux de texte brut (ex: format Combined Nginx/Apache) en documents JSON typés et interrogeables en quasi temps réel.
  • La volumétrie EPS (Events Per Second) reflète la dynamique opérationnelle : un pic signale une attaque ou une boucle d'erreurs, une chute indique une panne réseau ou le crash d'un service.
  • La corrélation multi-sources est l'atout maître du SIEM pour regrouper les indices faibles disséminés entre pare-feux, serveurs web et systèmes d'authentification.

Checklist de maîtrise

  • Savez-vous justifier le découplage entre l'agent léger Filebeat et le moteur de transformation Logstash ?
  • Pouvez-vous écrire une expression régulière grok pour extraire IP, verbe, URL et statut HTTP d'une ligne de log ?
  • Comprenez-vous pourquoi une chute brutale du débit EPS (Log Drop) est aussi critique qu'un pic d'erreurs ?
  • Comment fonctionne la corrélation multi-sources par adresse IP ou identifiant de session au sein d'un SIEM ?
  • Quelles sont les bonnes pratiques de cycle de vie (ILM) pour éviter la saturation disque d'un cluster Elasticsearch ?

Les 8 notions à connaître absolument

  1. Filebeat : Agent léger en langage Go dédié à la lecture des fichiers de logs sur disque et à leur transmission sécurisée.
  2. Logstash : Moteur d'ingestion et de transformation de données exécutant des pipelines de filtrage, parsing grok et enrichissement.
  3. Elasticsearch : Moteur de recherche et d'indexation distribué de documents JSON structurés basé sur Apache Lucene.
  4. Kibana : Interface utilisateur graphique pour explorer, requêter et visualiser les données stockées dans Elasticsearch.
  5. EPS : Events Per Second : débit volumétrique mesurant le nombre de lignes d'événements ingérées par seconde.
  6. SIEM : Security Information and Event Management : système de centralisation et corrélation temps réel des événements de sécurité.
