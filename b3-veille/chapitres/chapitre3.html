Chapitre 3 — Outils & Protocoles d’Acquisition : Mécanismes Push/Pull, RSS & Déduplication

Module 3 ≈ 2 h 45 de travail Réservé B1 et plus
Mise en situation

Automatiser la collecte de données sur le web est une compétence clé de l’ingénieur système et data. Cependant, agréger des dizaines de flux d’actualités expose à deux écueils majeurs : l’aspiration de contenus redondants sous des URLs de tracking différentes et le blocage d’adresses IP par les serveurs distants pour abus de requêtes (HTTP 429 Too Many Requests). L’ingénieur de niveau B3 doit comprendre les protocoles de transport et de syndication (RSS, Atom, Webhooks), concevoir des parseurs XML robustes capables d’extraire les métadonnées normées, appliquer des algorithmes de nettoyage d’URL et de déduplication lexicale par similarité de Jaccard, et orchestrer la charge de requêtes via des ordonnanceurs respectant les quotas d’appels API.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. comprendre les mécanismes d’échange et protocoles de syndication Push et Pull ;
  2. analyser la structure XML d’un flux RSS 2.0 (channel, item, title, link, guid, pubDate) et Atom ;
  3. configurer des agrégateurs et des collecteurs automatisés d’ingénierie ;
  4. nettoyer les paramètres de pistage d’URL (UTM analytics, balises ref et tracking) ;
  5. implémenter l’algorithme de similarité de Jaccard pour éliminer les quasi-doublons de titres ;
  6. développer en Python 3 des parseurs de flux RSS/Atom, des déduplicateurs de flux et des ordonnanceurs avec Rate Limiter.

1. Mécanismes Push vs Pull & Formats de Syndication (RSS 2.0 / Atom)

L’acquisition automatisée de données repose sur deux paradigmes de communication client-serveur aux propriétés complémentaires :

Comparatif Push vs Pull en Veille

  • Mécanisme Pull (Tirage) : Le client interroge périodiquement le serveur distant (polling). Utilisé pour le moissonnage web (scraping) ou la lecture d’API REST. Risque de requêtes inutiles et de décalage temporel si la période est trop longue.
  • Mécanisme Push (Poussée) : Le serveur émetteur notifie immédiatement le client dès qu’un nouvel événement survient (Webhooks, alertes e-mail, WebSockets). Latence quasi-nulle, zéro requête polling côté client.

Anatomie d’un Flux RSS 2.0

Le format RSS (Really Simple Syndication) est un document XML standardisé permettant la diffusion rapide de nouveautés :

<rss version="2.0">
  <channel>
    <title>ANSSI Alertes de Sécurité</title>
    <item>
      <guid>cve-2025-1044</guid>
      <title>Vulnérabilité critique OpenSSH</title>
      <link>https://cert.ssi.gouv.fr/avis/1044/</link>
      <pubDate>2025-10-15</pubDate>
    </item>
  </channel>
</rss>

2. Nettoyage des URLs & Déduplication par Similarité de Jaccard

Lorsqu’un robot de veille agrège de multiples sources, une même information est souvent relayée sous des URLs différentes ou avec des titres légèrement reformulés :

1. Normalisation et Nettoyage d’URLs (UTM Strip)

Les liens promotionnels et newsletters contiennent des paramètres de tracking analytics :

https://site.com/post?utm_source=twitter&utm_medium=social&ref=rss

Un collecteur rigoureux extrait l’URL canonique en supprimant tous les arguments utm_*, ref et source. Si l’URL nettoyée est déjà enregistrée en base, l’article est rejeté comme DOUBLON_URL.

2. Détection de Quasi-Doublons (Indice de Jaccard)

Deux communiqués de presse distincts traitent souvent du même fait avec des titres voisins :

Titre A : "Sortie officielle de Linux 6.12"
Titre B : "Sortie officielle et annonce de Linux 6.12"

L’indice de Jaccard compare les ensembles de mots des deux titres :

J(A, B) = |A ∩ B| / |A ∪ B|

Pour un seuil critique $J \ge 0.60$, l’article est automatiquement identifié comme DOUBLON_TITRE.

3. Ordonnancement de Collecte & Régulation de Débit (Rate Limiting)

Interroger des centaines de sites web sans régulation expose le robot à des bannissements IP immédiats :

Le Défi du Rate Limiting (HTTP 429)

Les serveurs web modernes et plateformes de partage de code (GitHub, GitLab, ArXiv) imposent des quotas stricts d’appels (ex: 60 requêtes par heure pour les accès non authentifiés). Dépasser ce quota entraîne une réponse HTTP 429 Too Many Requests et un blocage temporaire ou définitif de l’adresse IP de veille.

Algorithme de Régulation par Token Bucket

L’ordonnanceur de collecte associe à chaque source un réservoir de jetons (Token Bucket) caractérisé par :

  • La fréquence d’interrogation minimale autorisée (periode_sec).
  • Le plafond de requêtes par minute (rpm).
  • Si la demande dépasse le quota disponible sur la fenêtre de temps, l’appel est retardé ou le statut est marqué THROTTLED pour protéger le dispositif.
Éthique et Déontologie du Web Scraping : Avant de concevoir un robot de collecte par scraping HTML, l’ingénieur doit impérativement consulter le fichier robots.txt du domaine cible, respecter la directive Crawl-delay et renseigner un en-tête User-Agent explicite mentionnant l’organisme de recherche.

Exercice 1 — Parseur de flux de syndication RSS 2.0 / Atom

Étude de cas Niveau 1 — Acquisition

Objectif : Extraire et structurer les métadonnées techniques (titre, lien, date, identifiant GUID) d’un flux XML de veille.

Dans la collecte automatisée en mode Push/Pull, les flux RSS 2.0 et Atom constituent le standard d’interopérabilité pour agréger les nouveautés sans polluer les serveurs cibles. Chaque élément `` contient les balises : - `` : titre de la dépêche ou publication - `<link>` : URL canonique de la source - `<pubDate>` : date de publication au format RFC 822 ou ISO (ex: `2025-10-15`) - `<guid>` : identifiant unique de l’élément Entrée : Lignes contenant des balises XML au format standardisé : `<item><guid>G</guid><title>TLD` Sortie : - Pour chaque article : `ARTICLE id= title= link= date=` - Bilan : `SUMMARY total_articles= latest_date=`
Cas d’exemple
<item><guid>art-101</guid><title>Sortie de Python 3.14</title><link>https://python.org/news/101</link><pubDate>2025-10-01</pubDate></item>
<item><guid>art-102</guid><title>Vulnérabilité OpenSSL critique</title><link>https://cve.mitre.org/2025-02</link><pubDate>2025-10-14</pubDate></item>
Résolution attendue
ARTICLE id=art-101 title=Sortie de Python 3.14 link=https://python.org/news/101 date=2025-10-01
ARTICLE id=art-102 title=Vulnérabilité OpenSSL critique link=https://cve.mitre.org/2025-02 date=2025-10-14
SUMMARY total_articles=2 latest_date=2025-10-14

Le parseur extrait les 4 champs et repère la date la plus récente (2025-10-14).

Deux indices, rédigés en mots
  1. Utiliser des expressions régulières (re.search) ou un découpage pour extraire le contenu entre balises <tag> et </tag>.
  2. Identifier la date la plus récente au format lexicographique YYYY-MM-DD.
  3. Gérer les espaces superflus autour du titre et des liens.

Exercice 2 — Moteur de déduplication multi-sources et nettoyage de liens UTM

Étude de cas Niveau 2 — Application

Objectif : Éliminer les doublons stricts et quasi-doublons de flux via normalisation d’URL et similarité lexicale de Jaccard.

Lorsqu’un veilleur agrège des dizaines de flux RSS et lettres d’information, une même actualité apparaît sous plusieurs URLs avec des paramètres de pistage (UTM) ou des titres légèrement reformulés. Règles de traitement séquentiel pour chaque article entrant : 1. **Nettoyage d’URL** : Supprimer tous les paramètres commençant par `utm_` ainsi que `ref` et `source` de la chaîne de requête (séparateurs `?` et `&`). Si l’URL canonique nettoyée a déjà été vue : marquer `DOUBLON_URL` et rejeter. 2. **Similarité de Jaccard sur les titres** : Comparer l’ensemble des mots minuscules du titre avec les titres des articles *déjà conservés* : $$J(A, B) = \frac{|A \cap B|}{|A \cup B|}$$ Si pour un article conservé $J(A, B) \ge 0.60$ : marquer `DOUBLON_TITRE` et rejeter. 3. Sinon : marquer `CONSERVE` et enregistrer l’article. Entrée : `ITEM id= url= title=` Sortie : - Pour chaque élément : `STATUS id= action=` - Bilan : `SUMMARY recus= conserves= doublons=`
Cas d’exemple
ITEM id=1 url=https://tech.com/news?utm_source=twitter&utm_medium=social title=Sortie officielle de Linux 6.12
ITEM id=2 url=https://tech.com/news?utm_source=newsletter title=Autre actu
ITEM id=3 url=https://autre.com/linux title=Sortie officielle et annonce de Linux 6.12
Résolution attendue
STATUS id=1 action=CONSERVE
STATUS id=2 action=DOUBLON_URL
STATUS id=3 action=DOUBLON_TITRE
SUMMARY recus=3 conserves=1 doublons=2

L’item 2 a la même URL nettoyée (https://tech.com/news). L’item 3 a un Jaccard de 5/7 = 0.71 avec l’item 1.

Deux indices, rédigés en mots
  1. Normalisez les URLs collectées en supprimant les paramètres de traçage superflus et les ancres.
  2. L’indice de similarité de Jaccard mesure la proximité sémantique de deux sources par le quotient de l’intersection des mots par leur union.

Exercice 3 — Simulateur d’ordonnanceur de collecte hybride Push/Pull avec Rate Limiter

Étude de cas Niveau 3 — Raisonnement

Objectif : Simuler la charge de collecte sur un parc hétérogène de sources en appliquant les quotas de limitation de requêtes.

Un robot de veille doit équilibrer ses requêtes sortantes pour respecter la bande passante et éviter d’être banni par les serveurs distants (Rate Limiting HTTP 429) : - `PUSH_WEBHOOK` : l’information est poussée par le serveur distant vers notre API. Le collecteur local émet 0 requête sortante (`requetes_emises = 0`, `statut = OPTIMAL`). - `PULL_RSS` ou `PULL_SCRAPING` : le collecteur interroge la source toutes les `periode_sec` secondes. Sur une durée de simulation $S$ secondes : - Nombre de requêtes sollicitées : $R_{\text{sollicitees}} = \lfloor S / \text{periode_sec} \rfloor$ - Quota maximal alloué par la limite : $Q_{\text{max}} = \lfloor \text{rpm} \times (S / 60) \rfloor$ - Requêtes effectives émises : $R_{\text{emises}} = \min(R_{\text{sollicitees}}, Q_{\text{max}})$ - Si $R_{\text{sollicitees}} > Q_{\text{max}}$ : `statut = THROTTLED` (bridé par le rate limiter) - Sinon : `statut = OPTIMAL` Entrée : `DUREE_SIMU sec=` `FLUX id= type= periode_sec=

rpm=` Sortie : - Pour chaque flux : `COLLECT_JOB id= requetes_emises= statut=` - Bilan : `SUMMARY total_flux= total_requetes= flux_throttled=`

Cas d’exemple
DUREE_SIMU sec=3600
FLUX id=cert_webhook type=PUSH_WEBHOOK periode_sec=0 rpm=100
FLUX id=rss_github type=PULL_RSS periode_sec=600 rpm=10
FLUX id=scrape_forum type=PULL_SCRAPING periode_sec=30 rpm=1
Résolution attendue
COLLECT_JOB id=cert_webhook requetes_emises=0 statut=OPTIMAL
COLLECT_JOB id=rss_github requetes_emises=6 statut=OPTIMAL
COLLECT_JOB id=scrape_forum requetes_emises=60 statut=THROTTLED
SUMMARY total_flux=3 total_requetes=66 flux_throttled=1

Le scrape_forum voulait 3600/30 = 120 requêtes, mais le RPM de 1 le bride à 60 requêtes (THROTTLED).

Deux indices, rédigés en mots
  1. Lire d’abord la ligne DUREE_SIMU pour connaître le temps de simulation S.
  2. Pour les flux Push, les requêtes émises sont nulles.
  3. Comparer les requêtes théoriques avec le quota autorisé calculé sur S.
