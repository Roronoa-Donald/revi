Chapitre 6 — Sauvegarde Avancée (CBT), Sécurité & Virtualisation du Poste de Travail (VDI)

Module 6 ≈ 2 h 45 Réservé B3 et plus
Mise en situation

Vous devez finaliser le schéma directeur de virtualisation d'une organisation de 1 000 collaborateurs en sécurisant les hyperviseurs et les données d'entreprise. Vous concevez la stratégie de sauvegarde incrémentielle basée sur le Changed Block Tracking (CBT) pour respecter une fenêtre de sauvegarde nocturne de 4 heures, appliquez le durcissement de sécurité de l'hyperviseur ESXi (Lockdown mode strict, attestation TPM 2.0 et chiffrement de machines virtuelles), et dimensionnez l'infrastructure de postes virtuels VDI (VMware Horizon et Citrix Desktops) pour garantir une expérience utilisateur fluide tout en absorbant les pics d'I/O du Boot Storm matinal.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. Maîtriser le fonctionnement de Changed Block Tracking (CBT) et des APIs VADP pour orchestrer des sauvegardes incrémentielles sans agent à haute performance.
  2. Intégrer le quiescing applicatif via Microsoft VSS pour garantir la cohérence transactionnelle des bases de données lors des clichés de sauvegarde.
  3. Appliquer la matrice de durcissement sécuritaire des serveurs ESXi (désactivation SSH, Lockdown mode, puce TPM 2.0 et VM Encryption).
  4. Concevoir et dimensionner une infrastructure de postes virtuels VDI (pools persistants vs instant clones non-persistants, protocoles Blast/PCoIP/HDX et calcul d'IOPS Boot Storm).

1. Sauvegarde d'Infrastructure Moderne : Changed Block Tracking (CBT) & APIs VADP

Dans les centres de données virtualisés, l'ancienne méthode consistant à installer un agent de sauvegarde dans chaque système d'exploitation invité est abandonnée au profit de sauvegardes centralisées au niveau hyperviseur (Agentless) via les APIs VADP (vStorage APIs for Data Protection) :

Mécanisme du Changed Block Tracking (CBT)

  • Suivi des blocs modifiés : Le VMkernel enregistre en continu dans un fichier bitmap compact (-ctk.vmdk) la liste des blocs disques qui ont subi une écriture depuis le dernier snapshot.
  • Sauvegarde incrémentielle ultra-rapide : Le serveur de sauvegarde (Veeam, Commvault) interroge l'API vSphere pour obtenir uniquement l'index des blocs modifiés, sans jamais relire le disque complet.
  • Réduction d'E/S : Une VM de 500 Go n'ayant modifié que 5 Go de données est sauvegardée en quelques minutes au lieu de plusieurs heures.

Cohérence Applicative & Quiescing VSS

  • Crash-Consistent : Le snapshot capture le disque tel quel, équivalent à une coupure de courant. Les bases de données doivent rejouer leurs journaux au redémarrage.
  • Application-Consistent (VSS) : L'hyperviseur interagit avec le service Microsoft VSS (Volume Shadow Copy Service) via les VMware Tools pour forcer les bases de données (SQL Server, Exchange) à vider leurs caches en mémoire sur disque avant de figer le cliché.

2. Sécurité & Durcissement des Hyperviseurs : Lockdown Mode, TPM 2.0 & VM Encryption

L'hyperviseur est le point névralgique de l'infrastructure : sa compromission livre l'accès immédiat à l'ensemble des machines virtuelles et des données hébergées. Les guides de durcissement (CIS Benchmarks, VMware Hardening Guides) imposent des contrôles stricts :

Mesure de DurcissementMécanisme TechniqueObjectif de Sécurité / Conformité
Désactivation Shell / SSHServices ESXi Shell et SSH arrêtés par défaut sur le démon hostd.Supprimez les risques d'attaques par force brute sur le compte root local via le réseau.
Mode Lockdown (Normal)L'hôte ESXi ne peut être administré que via vCenter Server ; la console locale DCUI reste accessible aux administrateurs autorisés.Empêche toute modification de configuration hors du contrôle d'audit centralisé de vCenter.
Mode Lockdown (Strict)La console locale DCUI est elle-même désactivée. L'hôte est 100% dépendant de vCenter Server.Sécurisation maximale des serveurs situés dans des datacenters distants ou des colocalisations non surveillées.
Puce TPM 2.0 & Secure BootValidation cryptographique de l'intégrité des composants de boot du VMkernel au démarrage de l'hôte.Garantit qu'aucun rootkit ou chargeur de démarrage modifié n'a infecté le serveur (Host Attestation).
Chiffrement VM (VM Encryption)Chiffrement XTS-AES-256 des fichiers VMDK et VMX opéré par le VMkernel et géré par un serveur de clés KMS.Rend les disques virtuels illisibles s'ils sont dérobés ou copiés hors du stockage sécurisé.

3. Virtualisation du Poste de Travail (VDI) : Architectures & Protocoles d'Affichage

Le VDI (Virtual Desktop Infrastructure) héberge les environnements de travail des utilisateurs (Windows 10/11 ou Linux) sous forme de machines virtuelles exécutées dans le Datacenter et accessibles à distance :

Pools de Postes Virtuels

  • Pools Persistants (Dedicated) : Chaque utilisateur possède sa propre VM dédiée. Ses personnalisations et applications installées sont conservées d'une session à l'autre. Coût de stockage élevé.
  • Pools Non-Persistants (Floating / Instant Clones) : Les VM sont créées instantanément à partir d'une image maîtresse (Golden Master) par clonage mémoire direct. À la déconnexion, la VM est détruite et recréée propre. Les profils utilisateurs sont déportés (FSLogix, DEM).

Protocoles d'Affichage Haute Performance

  • VMware Blast Extreme : Protocole optimisé pour le Cloud utilisant les codecs vidéo H.264/H.265 avec transport adaptatif UDP/TCP (port 8443/22443).
  • Teradici PCoIP : Protocole historique propriétaire basé sur UDP (port 4172), compressant l'image par encodage sans perte de texte.
  • Citrix HDX / ICA : Suite de technologies d'accélération multimédia et de redirection de périphériques USB (port 1494/2598).

4. Dimensionnement du Stockage VDI & Absorption du Boot Storm

Contrairement aux serveurs classiques qui ont une consommation d'E/S prévisible, les infrastructures VDI sont soumises au phénomène critique du Boot Storm (tempête de démarrages) et du Logon Storm le matin lors de l'arrivée massive des collaborateurs :

Profils d'Utilisateurs & Besoins en IOPS

  • Profil Bureautique (Task Worker) : 10 à 15 IOPS par utilisateur en vitesse de croisière (navigation, messagerie, saisie).
  • Profil Connaissances (Knowledge Worker) : 25 à 35 IOPS par utilisateur (tableurs lourds, ERP, visioconférence).
  • Profil Développeur / Power User : 40 à 60 IOPS par utilisateur (compilations, conteneurs, IDEs multiples).

Prise en Compte du Boot Storm

Lors d'un démarrage simultané de 500 ou 1 000 postes entre 8h15 et 8h45, la demande d'IOPS en lecture explose de 50% à 100% au-dessus de la consommation nominale :

IOPS_Pic = Somme(Utilisateurs * IOPS_Profil) * (1.0 + Marge_Boot_Storm)

Pour absorber ce pic sans figer les sessions, l'utilisation de stockage Full Flash NVMe et de technologies de clonage mémoire instantané (vSphere Instant Clones) est indispensable.

Exercice 1 — Parseur de Métadonnées XenServer / Citrix Hypervisor & Rôles Dom0 / DomU

Étude de cas Niveau 1 — Acquisition

Objectif : Analyser les métadonnées d'un domaine XenServer (Citrix Hypervisor), qualifier les rôles Dom0/DomU et le mode de virtualisation.

L'architecture micro-noyau Xen distingue le domaine de contrôle (Dom0) des machines invitées (DomU) :

1. Règles architecturales :
- Si DOMAIN_TYPE == "DOM0" : Rôle CONTROL_DOMAIN, mode imposé NATIVE (accès matériel direct).
- Si DOMAIN_TYPE == "DOMU" : Rôle GUEST_VM, modes supportés : PV (paravirtualisation sans émulation) ou HVM (virtualisation assistée matériellement).
- Si une combinaison est incohérente (ex: Dom0 en mode PV/HVM ou DomU en mode NATIVE) : Statut INVALID_XEN_TOPOLOGY.

2. Identifiant UUID :
Afficher uniquement les 8 premiers caractères de l'UUID (préfixe court).

Format d'entrée (les données d’entrée) :
Lignes : UUID=<uuid> NAME=<nom> DOMAIN_TYPE=<DOM0|DOMU> VIRT_MODE=<NATIVE|PV|HVM> MEMORY_MB=<nb> VCPUS=<nb>.

Format de sortie :
VM:<nom> | UUID:<uuid[:8]> | TYPE:<DOM0|DOMU> | MODE:<mode> | ROLE:<role> | RAM:<MEMORY_MB>MB | VCPUS:<VCPUS>
(ou ERROR:INVALID_XEN_TOPOLOGY en cas d'incohérence).

Cas d’exemple
UUID=a84f32c1-829d-43cb-b09e-128492049182 NAME=Control-Domain DOMAIN_TYPE=DOM0 VIRT_MODE=NATIVE MEMORY_MB=4096 VCPUS=4
UUID=b95e41a2-918c-42ba-c18f-993849182931 NAME=Linux-Web01 DOMAIN_TYPE=DOMU VIRT_MODE=PV MEMORY_MB=8192 VCPUS=2
UUID=c12a93e3-718a-41aa-d09a-449182930192 NAME=Win-Desktop DOMAIN_TYPE=DOMU VIRT_MODE=HVM MEMORY_MB=16384 VCPUS=8
Résolution attendue
VM:Control-Domain | UUID:a84f32c1 | TYPE:DOM0 | MODE:NATIVE | ROLE:CONTROL_DOMAIN | RAM:4096MB | VCPUS:4
VM:Linux-Web01 | UUID:b95e41a2 | TYPE:DOMU | MODE:PV | ROLE:GUEST_VM | RAM:8192MB | VCPUS:2
VM:Win-Desktop | UUID:c12a93e3 | TYPE:DOMU | MODE:HVM | ROLE:GUEST_VM | RAM:16384MB | VCPUS:8

Domaine de contrôle Dom0, invité Linux paravirtualisé PV et invité Windows HVM.

Deux indices, rédigés en mots
  1. Dom0 a obligatoirement le rôle CONTROL_DOMAIN et le mode NATIVE.
  2. DomU a obligatoirement le rôle GUEST_VM et le mode PV ou HVM.

Exercice 2 — Dimensionneur de Catalogue VDI (Postes Virtuels, IOPS par Utilisateur, RAM & Stockage)

Étude de cas Niveau 2 — Application

Objectif : Dimensionner les ressources matérielles nécessaires (vCPUs, RAM, IOPS, Stockage) pour un catalogue de postes virtuels VDI.

Le dimensionnement d'un parc de bureaux virtuels (VDI Citrix Virtual Desktops ou VMware Horizon) s'appuie sur des profils types d'utilisateurs :

1. Profils de postes de travail :
- TASK_WORKER : 2 vCPUs, 4 Go RAM, 10 IOPS, disque clone lié 20 Go.
- KNOWLEDGE_WORKER : 4 vCPUs, 8 Go RAM, 25 IOPS, disque 40 Go.
- POWER_USER : 8 vCPUs, 16 Go RAM, 60 IOPS, disque 80 Go.

2. Calcul de simultanéité :
Utilisateurs actifs simultanés :
active_users = int(USERS * (CONCURRENT_PCT / 100.0)).

3. Besoins calculés :
- total_vcpus = active_users * profil.vcpus.
- total_ram_gb = active_users * profil.ram.
- total_iops = active_users * profil.iops.
- total_storage_gb = USERS * profil.disk (le stockage est réservé pour la totalité des utilisateurs inscrits).

Format d'entrée (les données d’entrée) :
Lignes : CATALOG=<nom> PROFILE=<nom_profil> USERS=<nb> CONCURRENT_PCT=<pct>.

Format de sortie :
CATALOG:<nom> | ACTIVE:<active_users> | VCPUS:<total_vcpus> | RAM:<total_ram_gb>GB | IOPS:<total_iops> | STORAGE:<total_storage_gb>GB

Cas d’exemple
CATALOG=CallCenter PROFILE=TASK_WORKER USERS=100 CONCURRENT_PCT=80.0
CATALOG=Engineering PROFILE=POWER_USER USERS=20 CONCURRENT_PCT=100.0
CATALOG=Sales PROFILE=KNOWLEDGE_WORKER USERS=50 CONCURRENT_PCT=60.0
Résolution attendue
CATALOG:CallCenter | ACTIVE:80 | VCPUS:160 | RAM:320GB | IOPS:800 | STORAGE:2000GB
CATALOG:Engineering | ACTIVE:20 | VCPUS:160 | RAM:320GB | IOPS:1200 | STORAGE:1600GB
CATALOG:Sales | ACTIVE:30 | VCPUS:120 | RAM:240GB | IOPS:750 | STORAGE:2000GB

Catalogue centre d'appels, ingénierie avancée et équipe commerciale.

Deux indices, rédigés en mots
  1. Associez à chaque profil ses caractéristiques (vcpus, ram, iops, disk).
  2. Le CPU, la RAM et les IOPS sont basés sur active_users, tandis que le stockage est calculé sur USERS total.

Exercice 3 — Calculateur de RPO/RTO & Volumétrie Sauvegarde Incrémentielle CBT (Changed Block Tracking)

Étude de cas Niveau 3 — Raisonnement

Objectif : Calculer la volumétrie d'une chaîne de sauvegarde CBT (Full + Incréments) et estimer le temps de restauration (RTO).

Les solutions de sauvegarde pour machines virtuelles exploitent l'API Changed Block Tracking (CBT) pour minimiser la volumétrie :

1. Taille de sauvegarde dédupliquée/compressée :
- Sauvegarde complète (Full) :
full_gb = SIZE_GB / DEDUP_RATIO.
- Incrément quotidien CBT (Changed Blocks) :
inc_gb = (SIZE_GB * (DAILY_CHANGE_PCT / 100.0)) / DEDUP_RATIO.

2. Volume total de la chaîne de sauvegarde :
Pour une durée de rétention de RETENTION_DAYS jours (1 Full initial + RETENTION_DAYS - 1 incréments) :
total_chain_gb = full_gb + (RETENTION_DAYS - 1) * inc_gb.

3. Temps de restauration complète (RTO) :
Le volume brut à réécrire sur le stockage est SIZE_GB * 1024 Mo.
À une vitesse de restauration RESTORE_MBPS (en Mo/s) :
rto_minutes = ((SIZE_GB * 1024) / RESTORE_MBPS) / 60.0.

Format d'entrée (les données d’entrée) :
Lignes : VM=<nom> SIZE_GB=<n> DAILY_CHANGE_PCT=<pct> RETENTION_DAYS=<nb> DEDUP_RATIO=<nb> RESTORE_MBPS=<nb>.

Format de sortie :
VM:<nom> | FULL:<full_gb:.1f>GB | INC:<inc_gb:.1f>GB | TOTAL_CHAIN:<total_chain_gb:.1f>GB | RTO:<rto_minutes:.1f>min

Cas d’exemple
VM=vm-database SIZE_GB=500 DAILY_CHANGE_PCT=5.0 RETENTION_DAYS=7 DEDUP_RATIO=2.0 RESTORE_MBPS=150
VM=vm-app-server SIZE_GB=100 DAILY_CHANGE_PCT=2.0 RETENTION_DAYS=14 DEDUP_RATIO=2.5 RESTORE_MBPS=100
Résolution attendue
VM:vm-database | FULL:250.0GB | INC:12.5GB | TOTAL_CHAIN:325.0GB | RTO:56.9min
VM:vm-app-server | FULL:40.0GB | INC:0.8GB | TOTAL_CHAIN:50.4GB | RTO:17.1min

Base de données 500 Go sur 7 jours avec 5% de modifications quotidiennes vs serveur applicatif 100 Go sur 14 jours.

Deux indices, rédigés en mots
  1. Appliquez le ratio de déduplication au Full et à chaque incrément CBT.
  2. Calculez le RTO en minutes à partir du volume brut en Mo et de la vitesse RESTORE_MBPS.

6. QCM — niveau examen

Quel fichier stocké sur le datastore contient la carte bitmap des blocs modifiés exploitée par le Changed Block Tracking (CBT) ?

Lorsqu'une VM active le CBT, le VMkernel crée un fichier compagnon `-ctk.vmdk` qui maintient la cartographie bitmap des blocs ayant fait l'objet d'écritures depuis le dernier point de référence.

Pourquoi une sauvegarde au niveau hyperviseur avec quiescing VSS est-elle supérieure à une simple sauvegarde crash-consistent ?

Le quiescing applicatif coordonné par Microsoft VSS force les applications et bases de données transactionnelles à finaliser leurs écritures en attente avant la prise du snapshot, garantissant une restauration sans corruption.

Que bloque le mode de sécurité vSphere Lockdown Mode en configuration "Normal" ?

Le mode Lockdown Normal empêche toute connexion directe par navigateur ou API à l'adresse IP de l'hôte ESXi pour centraliser toutes les actions dans les journaux d'audit de vCenter, tout en conservant l'accès d'urgence DCUI physique.

Quel composant matériel permet de valider l'intégrité cryptographique du chargeur et des binaires du noyau VMkernel lors du démarrage (Host Attestation) ?

La puce TPM 2.0 enregistre et valide cryptographiquement les empreintes de hachage de chaque composant du chargeur de démarrage UEFI et du noyau VMkernel, attestant qu'aucun code malveillant n'a altéré l'hyperviseur.

Quelle est la particularité d'un pool de postes virtuels VDI non-persistants (Floating / Instant Clones) ?

Dans un pool non-persistant, les postes sont éphémères : chaque utilisateur reçoit une machine vierge dérivée de l'image de référence (Golden Master). À la fermeture de session, la machine est détruite et reconstruite instantanément.

Quel protocole d'affichage distant propriétaire VMware s'appuie sur les codecs vidéo H.264/H.265 avec transport réseau adaptatif UDP/TCP ?

VMware Blast Extreme est le protocole d'affichage moderne de VMware Horizon utilisant l'accélération matérielle H.264/H.265 et un transport UDP/TCP adaptatif optimisé pour les réseaux WAN et Internet.

Qu'appelle-t-on le phénomène de "Boot Storm" dans une infrastructure de postes de travail virtuels VDI ?

Le Boot Storm désigne le pic massif d'entrées/sorties de lecture disque produit lorsque des centaines d'utilisateurs allument et initialisent leurs sessions Windows simultanément à leur arrivée au travail le matin.

Pour un parc de 200 postes VDI générant 20 IOPS moyens par utilisateur et une marge de sécurité de 50% pour absorber le Boot Storm, combien d'IOPS globaux la baie doit-elle délivrer ?

IOPS nominaux = 200 * 20 = 4 000 IOPS. Avec la surcapacité de 50% pour le Boot Storm : 4 000 * 1.50 = 6 000 IOPS requis au minimum en heure de pointe.

8. Méthodologie de résolution

Méthodologie d'Ingénierie : Audit de Sauvegarde, Durcissement & Dimensionnement VDI
  1. Activer Changed Block Tracking (CBT) sur les machines virtuelles et programmer des fenêtres de sauvegarde incrémentielle compatibles avec les débits de stockage.
  2. Intégrer le quiescing VSS pour toutes les VM hébergeant des bases de données relationnelles ou des annuaires d'entreprise.
  3. Auditer le durcissement des hôtes ESXi : désactiver les services SSH/Shell, basculer en Lockdown Mode et activer Secure Boot avec puce TPM 2.0.
  4. Calculer la volumétrie et la puissance d'IOPS globale d'un parc VDI en incluant une surcapacité de 50% à 80% pour encaisser le pic matinal de Boot Storm.

9. Révision active

Résumé essentiel
  • Changed Block Tracking (CBT) optimise radicalement les sauvegardes en ne lisant que les blocs disques modifiés consignés dans le fichier -ctk.vmdk.
  • Le quiescing VSS garantit la cohérence transactionnelle des bases de données en vidant leurs tampons avant la prise du cliché de sauvegarde.
  • Le durcissement de l'hyperviseur ESXi repose sur le Lockdown Mode, la désactivation des accès directs SSH et l'attestation cryptographique TPM 2.0.
  • Les architectures VDI à Instant Clones créent des postes de travail non-persistants à la volée avec une empreinte disque et mémoire ultra-réduite.
  • Le dimensionnement du stockage VDI impose de surdimensionner les IOPS de 50% à 80% pour absorber l'avalanche de lectures du Boot Storm matinal.

Checklist de maîtrise

  • Le paramètre `ctkEnabled = TRUE` est-il configuré dans le fichier .vmx de chaque VM pour activer le Changed Block Tracking ?
  • Les sauvegardes nocturnes utilisent-elles l'API vSphere VADP sans nécessiter d'agents résidents dans les systèmes invités ?
  • Le service SSH est-il arrêté sur tous les hyperviseurs ESXi de production et le mode Lockdown est-il activé ?
  • La baie de stockage VDI est-elle dimensionnée pour supporter le pic d'IOPS du Boot Storm calculé avec sa marge de sécurité ?
  • Les profils utilisateurs des postes VDI non-persistants sont-ils déportés et synchronisés via des conteneurs de profil (FSLogix) ?

Les 8 notions à connaître absolument

  1. Changed Block Tracking (CBT) : Fonctionnalité VMware retraçant les blocs disques modifiés pour n'exporter que les deltas lors des sauvegardes incrémentielles.
  2. VADP (vStorage APIs for Data Protection) : Ensemble d'APIs permettant aux logiciels tiers d'effectuer des sauvegardes sans agent au niveau de l'hyperviseur.
  3. Quiescing VSS : Synchronisation avec le service Microsoft Volume Shadow Copy pour geler temporairement les écritures applicatives et garantir la cohérence des données.
  4. Lockdown Mode : Mode de sécurité vSphere interdisant la connexion directe aux hyperviseurs ESXi pour imposer une administration exclusive via vCenter.
  5. TPM 2.0 & Secure Boot : Composant matériel cryptographique validant l'intégrité des modules du VMkernel lors du démarrage de l'hôte physique.
  6. VDI (Virtual Desktop Infrastructure) : Architecture hébergeant des environnements de travail utilisateurs sous forme de machines virtuelles dans le Datacenter.
  7. Instant Clone : Technologie VMware créant un poste virtuel en quelques secondes par duplication de la mémoire vive d'une VM parent en cours d'exécution.
  8. Boot Storm : Phénomène de surcharge massive des entrées/sorties disque lors du démarrage simultané de centaines de postes de travail virtuels en début de journée.
