Chapitre 3 — Stratégies de Groupe (GPO), Modèle LSDOU & Gouvernance de Parc

Module 3 ≈ 2 h 45 de travail Réservé B1 et plus
Mise en situation

Les stratégies de groupe (GPO - Group Policy Objects) représentent le levier d’automatisation et de sécurité le plus puissant d’un domaine Windows Server : elles permettent de déployer de manière centralisée des configurations système, des restrictions logicielles et des politiques de durcissement sur des milliers de postes clients et serveurs en quelques secondes. Cependant, une mauvaise maîtrise de la cinématique d’évaluation GPO entraîne des ralentissements majeurs à l’ouverture de session, des conflits de stratégies inexplicables et des failles d’application critiques. Pour un ingénieur système de niveau Bachelor 3, la gouvernance de parc impose une rigueur absolue : comprendre la dissociation physique entre le conteneur logique (GPC) et les fichiers de modèles (GPT dans SYSVOL), appliquer la règle de précédence LSDOU (Local -> Site -> Domain -> OU), maîtriser les mécanismes d’exception (Enforced et Block Inheritance), et exploiter les filtres WMI pour cibler chirurgicalement les déploiements selon le matériel et la version d’OS.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. maîtriser l’architecture interne des GPOs : synchronisation entre le Group Policy Container (GPC) et le Group Policy Template (GPT dans SYSVOL) ;
  2. appliquer l’ordre séquentiel strict de traitement LSDOU (Local, Site, Domaine, OU) et déterminer la stratégie gagnante en cas de conflit ;
  3. résoudre les cas complexes d’héritage de stratégies avec les options Enforced (application forcée) et Block Inheritance (blocage de l’héritage) ;
  4. configurer un filtrage de sécurité (Security Filtering) par groupes d’ordinateurs et restreindre l’application via le droit Apply Group Policy ;
  5. concevoir des filtres dynamiques WMI en langage WQL pour conditionner l’application d’une GPO aux spécifications matérielles et d’OS ;
  6. implémenter en Python 3 des calculateurs de précédence LSDOU, des moteurs d’arbitrage Enforced/Block et des évaluateurs de filtres WMI.

1. Architecture Interne et Composants d’une GPO (GPC vs GPT)

Une stratégie de groupe n’est pas un fichier monolithique : elle est constituée de deux composants distincts physiquement synchronisés par les contrôleurs de domaine :

Le Conteneur GPC (Group Policy Container)

  • Emplacement : stocké directement dans la base de données Active Directory (CN=Policies,CN=System,DC=domaine,DC=lan).
  • Contenu : métadonnées de la GPO, identifiant unique GUID (ex. {31B2F340-016D-11D2-945F-00C04FB984F9} pour la Default Domain Policy), numéro de version, statut (activée, désactivée, composants utilisateur/ordinateur désactivés) et listes de contrôle d’accès (ACL).
  • Réplication : répliqué par le moteur standard multi-maîtres d’Active Directory.

Le Modèle GPT (Group Policy Template)

  • Emplacement : stocké dans le système de fichiers partagé sur tous les contrôleurs : \\domaine\SYSVOL\domaine\Policies\{GUID}.
  • Contenu : fichiers de configuration réels, scripts de démarrage/ouverture de session, paramètres de registre (Registry.pol), modèles de sécurité et fichiers gpt.ini contenant le numéro de version.
  • Réplication : répliqué entre contrôleurs de domaine par le service de réplication DFS (DFSR - Distributed File System Replication).

2. Cycle d’Évaluation et Ordre de Précédence LSDOU

Lors du démarrage de l’ordinateur ou de l’ouverture de session d’un utilisateur, le moteur Group Policy traite les stratégies dans une séquence chronologique immuable :

La Règle Séquentielle L - S - D - O - U

  1. 1. Local (L) : Stratégie de sécurité locale définie sur le poste de travail individuel (niveau le plus faible).
  2. 2. Site (S) : Stratégies liées au site Active Directory auquel appartient le sous-réseau IP de la machine.
  3. 3. Domaine (D) : Stratégies liées à la racine du domaine (ex. Default Domain Policy).
  4. 4. Unité Organisationnelle (OU) : Stratégies liées aux OUs parentes puis aux OUs enfants les plus imbriquées.

Principe du « Dernier Écrivain Gagne » : Les niveaux s’exécutent dans l’ordre $1 \to 2 \to 3 \to 4$. En cas de conflit sur un même paramètre, la stratégie appliquée en dernier (le niveau le plus profond) écrase les valeurs précédentes.

Ordre de Liaison (Link Order)

Lorsque plusieurs GPOs sont liées au même conteneur (ex. sur la même OU) :

  • Chaque lien possède un numéro d’ordre : 1, 2, 3...
  • Le lien d’ordre le plus élevé est traité en premier, et le Link Order 1 est exécuté en dernier.
  • Par conséquent, la GPO avec Link Order = 1 a la précédence la plus haute au sein de ce conteneur.

3. Arbitrage Avancé : Enforced, Block Inheritance & Filtres WMI

Pour adapter le déploiement aux contraintes métier complexes, Windows Server fournit des mécanismes d’exception et de ciblage conditionnel :

Blocage d’Héritage vs Application Forcée (Enforced)

  • Bloquer l’héritage (Block Inheritance) : option activée au niveau d’une OU. Empêche l’application de toutes les GPOs héritées des niveaux supérieurs (Site, Domaine, OUs parentes). Les stratégies de l’OU s’appliquent seules.
  • Appliquée / Forcée (Enforced - ancien No Override) : option configurée sur un lien de GPO. Une GPO Enforced traverse obligatoirement tous les blocages d’héritage et ne peut être écrasée par aucune stratégie fille. C’est l’arme absolue de la sécurité régalienne.

Filtrage de Sécurité & Requêtes WMI

  • Filtrage de Sécurité (Security Filtering) : retire le groupe par défaut Utilisateurs authentifiés des ACLs de la GPO pour le remplacer par un groupe de sécurité spécifique (ex. GG_Postes_Compta) avec le droit Appliquer la stratégie de groupe (Apply Group Policy).
  • Filtres WMI (WQL) : évaluent dynamiquement les caractéristiques matérielles du poste avant d’exécuter la GPO. Exemple : SELECT * FROM Win32_OperatingSystem WHERE Version LIKE "10.0%" AND ProductType = "1" (cible uniquement les postes clients Windows 10/11 et exclut les serveurs).

Exercice 1 — Calculateur de précédence de stratégies de groupe (Modèle LSDOU)

Python Niveau 1 — Acquisition

Objectif : Calculer la valeur effective d’un paramètre selon l’ordre strict de traitement LSDOU (Local -> Site -> Domaine -> OU) et les liens de liaison.

Le moteur Group Policy applique les stratégies selon la hiérarchie stricte LSDOU : - `LOCAL` (Priorité niveau 1) - `SITE` (Priorité niveau 2) - `DOMAIN` (Priorité niveau 3) - `OU` (Priorité niveau 4) Règles de précédence : 1. Les niveaux s’appliquent dans l’ordre 1 -> 2 -> 3 -> 4. Un niveau supérieur (ex: OU) écrase toujours les niveaux inférieurs (ex: DOMAIN). 2. Au sein d’un même niveau, les GPOs ont un numéro de liaison `link_order=1, 2, ...` : le link_order 1 est le plus prioritaire (il est traité en dernier dans le niveau et gagne face au link_order 2). Entrée : `GPO name= level= link_order= param=

value=` Sortie : - Pour chaque paramètre unique (trié par nom alphabétique) : `EFFECTIVE_SETTING param=

value= source_gpo= level=` - Bilan : `SUMMARY params_evalues=

gpos_total=`

Entrée du programme
GPO name=DefaultDomainPolicy level=DOMAIN link_order=1 param=MaxPasswordAge value=42
GPO name=LocalSecurity level=LOCAL link_order=1 param=MaxPasswordAge value=90
GPO name=OUPolicy level=OU link_order=1 param=MaxPasswordAge value=30
Sortie attendue
EFFECTIVE_SETTING param=MaxPasswordAge value=30 source_gpo=OUPolicy level=OU
SUMMARY params_evalues=1 gpos_total=3

La GPO liée à l’OU a la plus forte précédence (niveau OU > DOMAIN > LOCAL) : 30 jours s’appliquent.

Deux indices, rédigés en mots
  1. Attribuer un poids numérique à chaque niveau (LOCAL:1, SITE:2, DOMAIN:3, OU:4).
  2. Pour le link_order, un ordre plus petit (1) doit avoir une priorité plus élevée que 2 (ex: utiliser -link_order).
  3. Trier par (poids_niveau, -link_order) pour déterminer la GPO gagnante.

Exercice 2 — Moteur d’arbitrage GPO : Enforced (No Override) vs Block Inheritance

Python Niveau 2 — Application

Objectif : Résoudre les conflits d’héritage entre une Unité Organisationnelle avec blocage et des GPOs parentes forcées (Enforced).

Dans Active Directory, les règles avancées d’héritage de stratégies modifient le flux LSDOU : - `OU_SETTING ou= block_inheritance=` : si ENABLED, toutes les GPOs des niveaux parents (Site, Domaine) sont bloquées. - `GPO name= level= enforced= param=

value=` Règle d’or Microsoft : 1. Si une GPO parente (DOMAIN) a `enforced=ENABLED`, elle traverse TOUS les blocages d’héritage et NE PEUT PAS être écrasée par une GPO de l’OU enfant (sa valeur prévaut sur tout). 2. Si `block_inheritance=ENABLED` sur l’OU, toutes les GPOs DOMAIN avec `enforced=DISABLED` sont purement et simplement IGNORÉES. 3. Si `block_inheritance=DISABLED`, les GPOs DOMAIN (enforced=DISABLED) s’appliquent mais peuvent être écrasées par les GPOs de l’OU. Sortie : - Pour chaque paramètre (trié par nom alphabétique) : `EFFECTIVE_SETTING param=

value= source_gpo=` - Bilan : `SUMMARY block_applied= enforced_count= params_count=

`

Entrée du programme
OU_SETTING ou=OU_Finance block_inheritance=ENABLED
GPO name=GPO_Securite level=DOMAIN enforced=ENABLED param=MinPasswordLength value=14
GPO name=GPO_Domaine level=DOMAIN enforced=DISABLED param=ScreenTimeout value=15
GPO name=GPO_Finance level=OU enforced=DISABLED param=MinPasswordLength value=8
GPO name=GPO_Finance level=OU enforced=DISABLED param=ScreenTimeout value=60
Sortie attendue
EFFECTIVE_SETTING param=MinPasswordLength value=14 source_gpo=GPO_Securite
EFFECTIVE_SETTING param=ScreenTimeout value=60 source_gpo=GPO_Finance
SUMMARY block_applied=TRUE enforced_count=1 params_count=2

MinPasswordLength est Enforced par le Domaine : il bat la tentative de réduction à 8 de l’OU. ScreenTimeout du Domaine est bloqué par l’OU, donc la valeur 60 de l’OU s’applique.

Deux indices, rédigés en mots
  1. Garder la valeur Enforced en priorité absolue (indétrônable).
  2. Si block_inheritance=ENABLED, éliminer les GPOs DOMAIN non forcées.
  3. Les GPOs de niveau OU s’appliquent ensuite si aucun Enforced ne verrouille le paramètre.

Exercice 3 — Évaluateur de filtres WMI et filtrage de sécurité (Security Filtering)

Python Niveau 3 — Raisonnement

Objectif : Vérifier si une GPO est applicable à un poste client en évaluant l’appartenance aux groupes de sécurité et les critères matériels/OS du filtre WMI.

Une stratégie de groupe n’est traitée par un ordinateur client que si elle satisfait deux filtres simultanés : 1. Filtrage de sécurité : l’ordinateur doit appartenir à au moins un des groupes listés dans `security_groups`. 2. Filtre WMI : les spécifications de l’ordinateur doivent vérifier tous les critères techniques : - `min_os_build` : `client.os_build >= gpo.min_os_build` - `arch` : `gpo.arch == ANY` ou `client.arch == gpo.arch` - `min_ram_gb` : `client.ram_gb >= gpo.min_ram_gb` Entrée : `CLIENT name= os_build= arch=<64BIT|32BIT> ram_gb= groups=` `GPO name= security_groups= min_os_build= arch=<64BIT|32BIT|ANY> min_ram_gb=` (1 ou plusieurs) Sortie : - Pour chaque GPO (triée par nom alphabétique) : `GPO_EVAL gpo= statut= motif=` (Priorité de motif : si la sécurité échoue -> `REFUS_SECURITE` ; si la sécurité passe mais WMI échoue -> `REFUS_WMI` ; si tout passe -> `OK`). - Bilan : `SUMMARY total_gpos= appliquees= ignorees=`
Entrée du programme
CLIENT name=PC-DEV-01 os_build=19045 arch=64BIT ram_gb=16 groups=Domain_Computers,DevWorkstations
GPO name=GPO_BitLocker security_groups=Domain_Computers min_os_build=19041 arch=ANY min_ram_gb=4
GPO name=GPO_CADSoftware security_groups=Engineers min_os_build=19041 arch=64BIT min_ram_gb=32
Sortie attendue
GPO_EVAL gpo=GPO_BitLocker statut=APPLIQUE motif=OK
GPO_EVAL gpo=GPO_CADSoftware statut=IGNORE motif=REFUS_SECURITE
SUMMARY total_gpos=2 appliquees=1 ignorees=1

GPO_BitLocker satisfait la sécurité et WMI (16 >= 4, build OK). GPO_CADSoftware est rejetée pour sécurité car le client n’est pas dans Engineers.

Deux indices, rédigés en mots
  1. Comparer les ensembles de groupes avec set.intersection().
  2. Vérifier os_build, arch et ram_gb si la sécurité est validée.
  3. Classer le motif en REFUS_SECURITE, REFUS_WMI ou OK.

5. QCM — niveau examen

Dans quel ordre séquentiel les stratégies de groupe sont-elles évaluées par le client Windows ?

L’ordre officiel est LSDOU : Local, puis Site, puis Domaine, et enfin Unité Organisationnelle (le dernier niveau appliqué l’emporte).

Où sont physiquement stockés les fichiers de modèles de stratégie GPT (Registry.pol, scripts) ?

Le Group Policy Template (GPT) est stocké dans le partage réseau répliqué \\domaine\SYSVOL\domaine\Policies\{GUID}.

Si une GPO de niveau Domaine est marquée « Enforced » et qu’une OU enfant active « Bloquer l’héritage », que se passe-t-il ?

L’option Enforced surpasse impérativement le blocage d’héritage : la GPO de domaine s’applique sans exception.

Au sein d’une même Unité Organisationnelle avec trois GPOs liées, laquelle a la priorité la plus élevée ?

Le Link Order 1 est évalué en dernier au sein du conteneur : il écrase donc les ordres supérieurs (2, 3...) et gagne.

Quel droit d’accès d’ACL est obligatoire pour qu’une GPO soit exécutée sur un groupe de machines ciblées ?

Pour que le moteur GPO applique la stratégie, la cible doit détenir à la fois les droits Read et Apply Group Policy.

À quoi sert un filtre WMI sur une stratégie de groupe ?

Un filtre WMI (requête WQL) vérifie des propriétés du poste (RAM, processeur, version de build d’OS) avant d’autoriser l’application de la GPO.

Où est déployé le Central Store permettant de centraliser les modèles de stratégies ADMX ?

Le Central Store se place dans \\domaine\SYSVOL\domaine\Policies\PolicyDefinitions pour être partagé par tous les contrôleurs.

Quelle commande permet de générer un diagnostic complet en HTML des stratégies appliquées sur un poste ?

La commande gpresult /h rapport.html génère un rapport visuel exhaustif détaillant toutes les GPOs appliquées et rejetées.

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Éviter de surcharger la Default Domain Policy : réserver cette GPO uniquement aux paramètres transverses minimaux (politique de compte, mots de passe).
  2. Créer des GPOs modulaires dédiées à une seule fonction (ex. GPO-BitLocker, GPO-PareFeu, GPO-ConfigProxy) pour faciliter le diagnostic.
  3. Utiliser le Magasin Central (Central Store) dans SYSVOL pour centraliser les modèles d’administration ADMX/ADML et éviter les divergences de versions.
  4. Vérifier la cohérence de version entre le conteneur GPC dans AD et le modèle GPT dans SYSVOL à l’aide de l’outil d’analyse de réplication.
  5. Appliquer l’option Enforced avec une extrême parcimonie et uniquement sur des impératifs légaux ou sécuritaires non négociables.
  6. Tester l’application effective des stratégies sur les postes clients via la commande gpresult /h rapport.html.

8. Révision active

Résumé essentiel
  • Une GPO est composée de métadonnées dans l’annuaire AD (GPC) et de fichiers de configuration dans le partage réseau SYSVOL (GPT).
  • L’ordre d’application chronologique strict est LSDOU : Local -> Site -> Domaine -> Unité Organisationnelle (le niveau le plus profond gagne).
  • Au sein d’une même OU, la GPO avec le Link Order 1 possède la précédence la plus élevée face aux ordres supérieurs.
  • L’option Enforced (application forcée) prévaut absolument sur le blocage d’héritage (Block Inheritance) et interdit tout écrasement descendant.
  • Le filtrage de sécurité restreint l’exécution d’une GPO aux membres d’un groupe détenant le droit d’accès « Appliquer la stratégie ».
  • Les filtres WMI permettent d’interroger les propriétés matérielles et l’OS (WQL) pour conditionner dynamiquement le traitement de la stratégie.

Checklist de maîtrise

  • Le Central Store des fichiers ADMX/ADML est-il déployé dans SYSVOL pour harmoniser les consoles d’administration ?
  • La Default Domain Policy contient-elle exclusivement les politiques globales de compte et de mot de passe ?
  • L’ordre de liaison (Link Order) a-t-il été contrôlé sur chaque conteneur regroupant plusieurs GPOs actives ?
  • L’activation de Block Inheritance sur une OU a-t-elle été validée pour ne pas couper des accès ou des configurations vitales ?
  • Les requêtes de filtre WMI ont-elles été testées avec wmic ou Get-CimInstance pour éviter les temps d’attente excessifs à l’ouverture de session ?
  • Un rapport gpresult /h a-t-il été généré sur un poste cible pour vérifier la liste exacte des GPOs gagnantes et rejetées ?

Les 8 notions à connaître absolument

  1. : Séquence chronologique officielle d’application des stratégies de groupe : Local, Site, Domaine, Unité Organisationnelle.
  2. : Répertoire unique situé dans SYSVOL hébergeant les modèles d’administration ADMX/ADML pour tous les contrôleurs de domaine.
  3. : Paramètre de liaison de GPO forçant son application prioritaire à travers tous les blocages d’héritage sans possibilité d’écrasement.
  4. : Option d’une Unité Organisationnelle empêchant l’héritage des stratégies de groupe configurées sur les conteneurs parents.
  5. : Mécanisme d’ACL restreignant l’exécution d’une GPO aux seuls objets ayant le droit « Appliquer la stratégie de groupe ».
  6. : Requête d’interrogation de la base de gestion Windows conditionnant l’application d’une GPO aux caractéristiques matérielles du poste.
  7. : Composant logique d’une GPO stocké dans Active Directory contenant les métadonnées, le GUID, la version et les ACLs.
  8. : Composant physique d’une GPO stocké dans SYSVOL contenant les fichiers de registre, scripts et modèles de configuration.
