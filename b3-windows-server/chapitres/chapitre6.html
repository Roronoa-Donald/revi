Chapitre 6 — Administration Avancée PowerShell, Sauvegardes VSS & Tolérance aux Pannes

Module 6 ≈ 2 h 45 de travail Réservé B1 et plus
Mise en situation

Dans une infrastructure d’entreprise mature, l’administration manuelle via des interfaces graphiques est proscrite au profit de l’automatisation par scripts et de la haute disponibilité. Un administrateur système en Bachelor 3 doit être capable de piloter des centaines de serveurs à distance via PowerShell Remoting sans jamais ouvrir de session RDP interactive, de garantir la continuité d’activité grâce à des politiques de sauvegarde bare-metal imperméables aux ransomwares via les clichés instantanés VSS, et d’orchestrer des clusters de basculement (Failover Clustering) garantissant un taux de disponibilité supérieur à 99,99 %. Si la formule de quorum n’est pas maîtrisée, une panne de réseau local peut scinder le cluster et provoquer le phénomène catastrophique de Split-Brain (corruption irrémédiable des données par écritures concurrentes). Ce module final scelle l’expertise opérationnelle de l’ingénieur système sous Windows Server.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. maîtriser le pipeline et les cmdlets avancées des modules ActiveDirectory, Hyper-V et NetTCPIP sous PowerShell 5.1/7 ;
  2. configurer et auditer l’administration à distance via PowerShell Remoting (protocole WS-Management, ports WinRM 5985/5986, Invoke-Command) ;
  3. concevoir une politique de sauvegarde bare-metal d’entreprise avec Windows Server Backup (wbadmin) et dimensionner le stockage de rétention ;
  4. disséquer le fonctionnement tripartite de l’architecture VSS (Volume Shadow Copy Service : Requestor, Writer et Provider) ;
  5. calculer mathématiquement le quorum d’un cluster de basculement (WSFC) et arbitrer le choix du témoin (Disk, File Share, Cloud Witness) ;
  6. analyser et résoudre méthodologiquement des parseurs de syntaxe PowerShell, des calculateurs de quorum de cluster et des planificateurs de volumétrie de sauvegarde.

1. Automatisation Système et Administration à Distance (WinRM)

PowerShell est l’outil régalien de l’ingénieur système pour automatiser le cycle de vie de l’infrastructure et administrer le parc à grande échelle :

Architecture de PowerShell Remoting (WinRM)

Basé sur le protocole standardisé WS-Management (WS-Man) et le service Windows Remote Management (WinRM) :

  • Ports d’écoute : port TCP 5985 en HTTP chiffré par Kerberos en environnement de domaine, et port TCP 5986 en HTTPS avec certificat SSL/TLS.
  • Session interactive 1:1 : Enter-PSSession -ComputerName srv01 ouvre un shell distant équivalent à SSH.
  • Exécution distribuée 1:N : Invoke-Command -ComputerName (Get-ADComputer -Filter *).Name -ScriptBlock { Get-Service wuauserv } exécute une commande en parallèle sur des centaines de serveurs.

2. Sauvegardes d’Entreprise et Architecture VSS (Volume Shadow Copy)

La protection contre les ransomwares et les pannes matérielles repose sur la coordination du service Volume Shadow Copy (VSS) :

Le Modèle Tripartite de VSS

  1. VSS Requestor (Le Demandeur) : logiciel de sauvegarde (ex. wbadmin.exe, Veeam Backup) qui initie la requête de cliché instantané.
  2. VSS Writer (Le Rédacteur) : composant intégré à chaque application (Active Directory NTDS Writer, Microsoft Exchange Writer, SQL Server Writer). Il vide les caches mémoire sur disque et gèle temporairement les transactions pendant quelques millisecondes.
  3. VSS Provider (Le Fournisseur) : composant de stockage (logiciel dans NTFS ou matériel dans une baie SAN) qui capture le cliché différentiel instantané (Copy-on-Write) sur le volume.

Ce mécanisme permet de sauvegarder des bases de données en production sans jamais interrompre le travail des utilisateurs ni subir d’incohérence.

Types de Sauvegardes & Stratégie Bare-Metal

  • Sauvegarde de l’état du système (System State) : sauvegarde la base Active Directory (ntds.dit), le registre, SYSVOL et la base de données COM+.
  • Sauvegarde Bare-Metal (BMR) : inclut l’ensemble des volumes requis pour reconstruire le serveur à partir de zéro sur une machine physique neuve.
  • Dimensionnement de rétention : une politique combinant une sauvegarde complète (Full) hebdomadaire et des sauvegardes incrémentales (Incremental) quotidiennes avec une réserve d’overhead VSS de 15 % garantit un RPO et RTO conformes aux SLAs d’entreprise.

3. Clustering de Basculement (WSFC) & Formules de Quorum

Pour garantir la haute disponibilité sans point unique de défaillance (SPOF), le rôle Failover Clustering regroupe plusieurs serveurs physiques :

Modèle Mathématique du Quorum

Le quorum détermine si le cluster détient la légitimité pour rester en ligne en cas de défaillance :

  • Chaque nœud actif dispose de 1 voix ($V_{\text{node}} = 1$).
  • Un témoin de quorum (Witness) apporte 1 voix de départage ($V_{\text{witness}} = 1$).
  • Nombre total de voix : $N_{\text{total}} = \sum V_{\text{nodes}} + V_{\text{witness}}$.
  • Majorité absolue requise : $\text{Quorum} = \lfloor N_{\text{total}} / 2 \rfloor + 1$.
  • Si les voix actives sont $\ge \text{Quorum}$, le cluster reste en ligne (QUORUM_OK). Sinon, il s’arrête immédiatement pour protéger les données.

Prévention du Split-Brain & Choix du Témoin

  • Phénomène de Split-Brain : si le réseau de communication inter-nœuds (Heartbeat) se rompt sans quorum, deux sous-groupes de serveurs croiraient l’autre mort et tenteraient d’écrire simultanément sur le stockage partagé, corrompant irrémédiablement les données.
  • Témoin de disque (Disk Witness) : LUN partagée sur baie SAN/iSCSI réservée au cluster.
  • Témoin de partage de fichiers (File Share Witness) : partage SMB distant sur un serveur tiers.
  • Témoin Cloud (Cloud Witness) : stockage Blob Azure, éliminant tout besoin de troisième site physique.

Exercice 1 — Analyseur syntaxique de commandes PowerShell d’administration Active Directory

Étude de cas Niveau 1 — Acquisition

Objectif : Valider la présence des paramètres obligatoires dans les commandes PowerShell d’administration d’annuaire AD DS.

L’administration automatisée d’un contrôleur de domaine s’appuie sur les cmdlets officielles du module ActiveDirectory : - `New-ADUser` : paramètres obligatoires = `-Name`, `-SamAccountName`. - `Set-ADUser` : paramètre obligatoire = `-Identity`. - `New-ADGroup` : paramètres obligatoires = `-GroupCategory`, `-GroupScope`, `-Name`. Règles de validation : 1. Si la commande commence par l’une de ces 3 cmdlets, vérifier que tous les paramètres obligatoires sont présents. 2. Si tous les paramètres obligatoires sont présents : `CMD_STATUS cmdlet= result=VALIDE params_count=` (où N = nombre total de paramètres préfixés par `-`). 3. Si au moins un paramètre obligatoire est absent : `CMD_STATUS cmdlet= result=INVALIDE manquant=` (le premier paramètre obligatoire manquant dans l’ordre alphabétique). Entrée : `POWERSHELL - - ...` (1 ou plusieurs) Résultat d’analyse attendu : - Pour chaque ligne : `CMD_STATUS cmdlet= result= ...` - Bilan : `SUMMARY total_cmds= valides= invalides=`
Cas d’exemple
POWERSHELL New-ADUser -Name "Alice Smith" -SamAccountName asmith -Enabled $true
POWERSHELL Set-ADUser -Department "Finance"
Résolution attendue
CMD_STATUS cmdlet=New-ADUser result=VALIDE params_count=3
CMD_STATUS cmdlet=Set-ADUser result=INVALIDE manquant=-Identity
SUMMARY total_cmds=2 valides=1 invalides=1

New-ADUser a -Name et -SamAccountName (VALIDE). Set-ADUser omet son paramètre obligatoire -Identity (INVALIDE).

Trois indices, rédigés en mots
  1. Créer un dictionnaire listant les paramètres obligatoires pour chaque cmdlet.
  2. Extraire tous les jetons commençant par un tiret (-) pour former la liste des paramètres fournis.
  3. Comparer les ensembles de paramètres et ordonner les manquants par ordre alphabétique.

Exercice 2 — Calculateur de quorum de cluster de basculement (Failover Clustering)

Étude de cas Niveau 2 — Application

Objectif : Calculer la majorité absolue des voix et vérifier le maintien du quorum dans un cluster Windows Server en cas de panne de nœuds.

Dans un cluster de basculement (WSFC - Windows Server Failover Clustering), le modèle de Quorum garantit la cohérence du cluster : - `NODE id= vote=<0|1> status=` : chaque nœud ayant `vote=1` détient 1 voix. - `WITNESS type= status=` : si `type != NONE`, le témoin apporte 1 voix de départage. Règles de Quorum officielles Microsoft : 1. Total des voix configurées : `total_votes = sum(votes des nœuds) + (1 si witness != NONE sinon 0)`. 2. Majorité absolue requise : `required_majority = (total_votes // 2) + 1`. 3. Voix actives : `active_votes = sum(voix des nœuds avec vote=1 et status=ONLINE) + (1 si witness != NONE et status=ONLINE sinon 0)`. 4. État du cluster : si `active_votes >= required_majority` -> `QUORUM_OK` ; sinon -> `PERTE_QUORUM`. Entrée : `NODE id= vote=<0|1> status=` (1 ou plusieurs) `WITNESS type= status=` Résultat d’analyse attendu : - Ligne d’analyse du quorum : `QUORUM_ANALYSIS total_votes= required_majority= active_votes= cluster_status=` - Bilan de disponibilité : `SUMMARY nodes_online= nodes_offline= witness_status=`
Cas d’exemple
NODE id=NODE-01 vote=1 status=ONLINE
NODE id=NODE-02 vote=1 status=ONLINE
NODE id=NODE-03 vote=1 status=OFFLINE
WITNESS type=CLOUD status=ONLINE
Résolution attendue
QUORUM_ANALYSIS total_votes=4 required_majority=3 active_votes=3 cluster_status=QUORUM_OK
SUMMARY nodes_online=2 nodes_offline=1 witness_status=ONLINE

4 voix configurées (3 nœuds + 1 témoin). Majorité requise = 4//2 + 1 = 3 voix. 3 voix actives (2 nœuds + témoin) : le quorum est maintenu.

Trois indices, rédigés en mots
  1. Compter les voix configurées (nœuds avec vote=1 + 1 si witness présent).
  2. Calculer la majorité avec total_votes // 2 + 1.
  3. Additionner les voix en ligne et comparer au seuil de majorité.

Exercice 3 — Planificateur de sauvegardes Windows Server Backup (VSS Full vs Incremental)

Étude de cas Niveau 3 — Raisonnement

Objectif : Calculer la capacité de stockage cible pour un cycle de sauvegarde hebdomadaire (VSS Full + Incrémentales) avec overhead de 15%.

Dans l’outil de sauvegarde Windows Server Backup (wbadmin), la volumétrie s’articule autour de clichés instantanés VSS : - Volume source : `SOURCE_VOL letter= size_gb= daily_change_gb=` - Période de rétention : `POLICY retention_weeks=` Formules de dimensionnement du stockage de sauvegarde : 1. Cycle hebdomadaire (1 sauvegarde complète le jour 1 + 6 sauvegardes incrémentales) : `cycle_hebdo_gb = size_gb + (6 * daily_change_gb)` 2. Données brutes sur $W$ semaines de rétention : `raw_backup_gb = W * cycle_hebdo_gb` 3. Réserve de surcharge VSS (Overhead de +15%) : `vss_overhead_15pct = round(raw_backup_gb * 0.15, 1)` 4. Capacité cible recommandée finale : `final_target_gb = round(raw_backup_gb * 1.15, 1)` Entrée : `SOURCE_VOL letter= size_gb= daily_change_gb=` `POLICY retention_weeks=` Résultat d’analyse attendu : - Profil du cycle hebdomadaire : `VOL_PLAN letter= full_backup_gb= week_inc_gb=<6*C> cycle_hebdo_gb=` - Dimensionnement de la cible de stockage : `TARGET_STORAGE weeks= raw_backup_gb= vss_overhead_15pct= final_target_gb=` - Bilan : `SUMMARY retention_days=<7*W> storage_recommande_gb=`
Cas d’exemple
SOURCE_VOL letter=D size_gb=500 daily_change_gb=20
POLICY retention_weeks=4
Résolution attendue
VOL_PLAN letter=D full_backup_gb=500 week_inc_gb=120 cycle_hebdo_gb=620
TARGET_STORAGE weeks=4 raw_backup_gb=2480 vss_overhead_15pct=372.0 final_target_gb=2852.0
SUMMARY retention_days=28 storage_recommande_gb=2852.0

1 semaine = 500 Go Full + 120 Go Incrémentales = 620 Go. 4 semaines = 2480 Go bruts. Avec 15% VSS = 2852.0 Go.

Trois indices, rédigés en mots
  1. Calculer week_inc = 6 * daily_change_gb.
  2. Calculer cycle = size_gb + week_inc, puis multiplier par retention_weeks.
  3. Appliquer l’overhead de 15% et arrondir à 1 décimale.

5. QCM — niveau examen

Quel protocole réseau sous-jacent est utilisé par PowerShell Remoting pour la communication distante ?

PowerShell Remoting repose sur le protocole standardisé WS-Management implémenté par le service système WinRM.

Quel est le port TCP d’écoute par défaut de WinRM en environnement de domaine Active Directory (HTTP avec chiffrement Kerberos) ?

Le port TCP 5985 est le port standard de WinRM HTTP (le port 5986 étant réservé à HTTPS avec certificat SSL dédié).

Dans l’architecture VSS, quel rôle remplit le composant « VSS Writer » ?

Le VSS Writer appartient à l’application (AD DS, SQL Server) et prépare celle-ci en figeant temporairement les écritures pendant la création du cliché.

Dans un cluster à 3 nœuds physiques sans témoin, combien de voix composent le quorum et quelle est la majorité requise ?

Chaque nœud a 1 voix (total = 3). La majorité absolue est égale à $\lfloor 3 / 2 \rfloor + 1 = 2$ voix.

Quel risque critique le mécanisme de quorum empêche-t-il formellement dans un cluster de basculement ?

Le quorum évite qu’une partition réseau n’entraîne l’exécution concurrente de deux instances du même service écrivant sur le même disque (Split-Brain).

Quel type de témoin de quorum est recommandé pour un cluster sans baie SAN partagée ou réparti sur plusieurs sites géographiques ?

Le Cloud Witness exploite un compte Azure Blob léger et économique comme arbitre tiers, idéal pour les clusters multi-sites ou sans SAN.

Quelle commande PowerShell permet d’exécuter un bloc de script en parallèle sur une liste de serveurs distants ?

Invoke-Command permet l’exécution distribuée 1:N en envoyant le ScriptBlock à travers des sessions WinRM parallèles.

Quelle commande en ligne permet de vérifier l’état de santé de tous les VSS Writers sur un serveur Windows ?

La commande vssadmin list writers affiche l’état de chaque composant de sauvegarde VSS (vérifier que l’état est [1] Stable).

7. Méthodologie de résolution

Démarche d’ingénierie pas à pas
  1. Activer WinRM sur tous les serveurs et vérifier la connectivité via Test-WSMan avant tout déploiement de scripts distribués.
  2. Utiliser Invoke-Command avec des blocs de scripts (ScriptBlock) pour paralléliser les audits sans saturer les files d’attente séquentielles.
  3. Vérifier l’état de santé des VSS Writers à l’aide de la commande vssadmin list writers avant d’exécuter une tâche de sauvegarde critique.
  4. Configurer un plan de sauvegarde hybride (Full hebdomadaire + Incremental quotidien) et tester périodiquement la procédure de restauration Bare Metal.
  5. Déterminer le nombre total de voix de cluster et choisir le témoin Witness adapté (Cloud Witness pour les clusters multi-sites).
  6. Auditer le calcul du quorum après chaque opération de maintenance ou d’éviction de nœud pour garantir la tolérance aux pannes.

8. Révision active

Résumé essentiel
  • PowerShell Remoting exploite WinRM (ports 5985/5986) pour administrer les serveurs à grande échelle via Enter-PSSession et Invoke-Command.
  • L’architecture VSS coordonne le Requestor (wbadmin), les Writers applicatifs (AD, SQL) et le Provider de stockage pour des instantanés cohérents.
  • Les sauvegardes de l’état du système (System State) et Bare Metal Recovery (BMR) constituent les garanties ultimes contre les ransomwares.
  • Le Failover Clustering (WSFC) élimine les SPOFs et maintient les services critiques en production (Hyper-V, SQL Server, serveurs de fichiers).
  • La règle du quorum impose une majorité absolue stricte : $\lfloor N / 2 \rfloor + 1$ voix actives pour maintenir le cluster en ligne.
  • Le mécanisme de quorum empêche le Split-Brain, protégeant le stockage partagé contre toute écriture concurrente destructrice.

Checklist de maîtrise

  • Le service WinRM est-il démarré et autorisé dans le pare-feu Windows pour autoriser l’administration distante ?
  • Les commandes PowerShell critiques utilisent-elles des paramètres obligatoires validés sans ambiguïté ?
  • Tous les VSS Writers affichent-ils un statut stable sans erreur (State: [1] Stable) sous vssadmin list writers ?
  • L’espace de stockage cible de la sauvegarde intègre-t-il la réserve d’overhead VSS de 15 % recommandée ?
  • Le cluster de basculement dispose-t-il d’un nombre impair total de voix grâce à un témoin Witness approprié ?
  • La procédure de reprise après sinistre (Disaster Recovery Plan) a-t-elle été validée par un test réel de basculement de nœud ?

Les 8 notions à connaître absolument

  1. : Technologie d’administration à distance s’appuyant sur le protocole WS-Management et WinRM pour exécuter des scripts sur des machines distantes.
  2. : Service Windows implémentant la norme WS-Man sur les ports TCP 5985 (HTTP/Kerberos) et 5986 (HTTPS).
  3. : Cadre architectural de Windows coordonnant la création de clichés instantanés différentiels sans interruption de service applicatif.
  4. : Composant logiciel applicatif spécialisé (AD, SQL, Exchange) garantissant que les données en mémoire sont gelées proprement lors du cliché.
  5. : Rôle de haute disponibilité regroupant des serveurs physiques indépendants pour assurer le basculement transparent de charges applicatives.
  6. : Nombre minimal de voix actives requis pour qu’un cluster de basculement soit autorisé à rester opérationnel et à gérer les ressources.
  7. : Scénario critique où deux sous-groupes d’un cluster coupé tentent d’accéder simultanément au même stockage, risquant la corruption irréversible.
  8. : Type de témoin de quorum utilisant un compte de stockage Azure Blob comme tiers de confiance arbitre dans un cluster Windows Server.
