# Lot 1 — intégrité technique : état partiel

**30 octobre 2026 — branche `corrections-lot-1` — dossier local uniquement. Porte du lot 1 non validée ; ne pas publier ni passer au lot 2 sur la base de ce rapport.**

## Périmètre et décisions

Le registre `corrections/suivi.csv` contient 227 identifiants uniques. Pour les 62 constats rattachés au lot 1 : **49 corrigés, 12 nuancés, aucun refusé et un reporté** (F171). Les 165 autres constats restent reportés à leurs lots respectifs ; le total du registre est donc de 166 reportés. Ces statuts sont individuels : ils ne signifient pas que les portes transversales du lot sont franchies.

Le registre distingue la source héritée de l’audit et la source effectivement consultée au lot 1 : 46 constats traités comportent une URL et une date UTC, et 15 indiquent explicitement qu’aucune source web vérifiée n’y est renseignée. Ces derniers peuvent reposer sur une preuve locale ou une source héritée ; cette mention ne valide pas une source externe. La vérification de ses 12 colonnes, de ses 227 identifiants et du refus d’écraser un registre existant est conservée dans `resultats/suivi-lot1-validation.txt` ; les identifiants, statuts et preuves des constats traités ont été revérifiés dans `resultats/reprise-suivi-reprise.txt`.

Les corrections ont été effectuées dans les sources et les générateurs, puis les pages correspondantes ont été régénérées. Aucun déploiement n’a été réalisé. Les résultats bruts, les codes de retour et les limites des sondes sont dans `corrections/resultats/`. Les contrôles qui restent rouges conservent leur code d’échec : un candidat automatique n’est toutefois pas nécessairement un défaut confirmé.

## Changements principaux

1. **HTML et formules.** Avant, des chevrons étaient interprétés comme balises et des paramètres de code comme formules : cartes ou textes disparaissaient. Après, le contenu est échappé ou balisé individuellement comme code ; le DOM et les sources des cartes/QCM sont comparés, et Chromium vérifie les cas ciblés.
2. **Correcteur.** Une réponse numérique suivie de texte pouvait être acceptée et la casse de données JSON structurées était perdue. La chaîne numérique est désormais entièrement contrôlée ; le JSON conserve la casse et compare les nombres sans perte des grands entiers. Une fraction non réduite est aussi refusée pour l'exercice qui exige ce format ; ses bornes 0 et 1 sont ajoutées. Les 18 attendus où deux lignes étaient fusionnées sont séparés.
3. **Corrigés et cas limites.** Les 72 corrigés mémorisés des quatre catalogues signalés ont été remplacés par des algorithmes ; des bornes et variantes ciblées ont été ajoutées. Leur notation reste suspendue, car les vérifications générales et les fournisseurs distants ne sont pas entièrement validés.
4. **Exécution.** Aucun échec de fournisseur ne déclenche l’exécution locale de Python, JavaScript, Bash, C# ou SQL côté serveur. Le SQL du navigateur utilise un worker interrompable et des limites de mémoire SQLite et de sortie. L’isolation des fournisseurs réels n’a pas été démontrée.
5. **SQL B1.** Le cours et son simulateur utilisent le parc de référence `Marque`, `Voiture`, `Equipement`, `VoitureEquipement` : 12 marques et 23 voitures dans le jeu initial. Les exemples et ateliers ciblés ont été réalignés ; les syntaxes MySQL restent distinguées de SQLite. La correction distante des trois cours SQL reste suspendue.
6. **Études de cas.** Le bouton de validation échouait avant l’appel au serveur parce qu’un bouton d’exécution inexistant était manipulé. Les réponses multilignes sont désormais saisissables directement, les brouillons et lignes réservées sont conservés, et une grille brute mal formée ne peut pas être soumise ni fermée silencieusement. Les cas affichés restent des évaluations formatives sur données visibles ; un avertissement le précise dans les 276 pages concernées.
7. **Retour de correction et confidentialité.** L’API renvoyait auparavant l’entrée, l’attendu et les messages du premier test caché en échec. Elle ne transmet plus ces données ni les libellés internes : l’élève voit le numéro du cas, son état et une piste générale. Pour les grilles, sa propre réponse reste visible mais l’attendu n’est plus renvoyé. Le tuteur reçoit le type d’échec autorisé sans recevoir le diagnostic caché ; il lui est demandé de ne pas inventer la cause. Les résultats successifs restent une information utilisable par essais, et le fournisseur d’exécution reçoit nécessairement les entrées qu’il doit exécuter : ce changement ne démontre pas une confidentialité absolue.
8. **Deux évaluations à domaine fini.** `ws2-c4-e3` et `fl2-c4-e1` utilisent légitimement une table d’associations imposée par leur énoncé ; les deux anciens signalements automatiques n’étaient donc pas, à eux seuls, des preuves de mémorisation. Trois tests d’origine sont conservés et quatre cas ajoutés pour chaque exercice. Deux variantes encore acceptées échouaient sur l’exemple affiché : celui-ci est maintenant évalué après les sept tests cachés, sans être compté comme un test caché. Une soumission qui atteint la fin consomme ainsi huit appels pour chacun de ces deux exercices ; le quota reste appliqué à chaque appel.

La relecture novice a également conduit à préciser `n ≥ 1` pour un maximum Linux, à distinguer les états simultanément indexé et modifié dans la simulation Git B1 et à rétablir deux énoncés pfSense. Un dépôt Git temporaire, des bornes et des variantes incorrectes ont servi de contre-vérification. Les deux exercices SQL de création demandent désormais une insertion pertinente en plus de la création : le schéma enseigné reste complet, mais les corrigés complets ne sont plus reproduits tels quels sur la page. Un modèle `UPDATE` non exécutable a été séparé de son exemple réel ; son contrôle passe de l'échec à 16 tests réussis.

## Relecture et sécurité

La relecture par IA sous angle novice, distincte d’un essai auprès d’étudiants, est détaillée dans `corrections/relecture-novice-lot1.md` : graine `20261029`, cinq pages tirées parmi les chapitres modifiés. Elle a aussi relevé des candidats qui ne sont pas tous corrigés ni attribués artificiellement à un constat F ; ils figurent dans `corrections/nouveaux-candidats.md`.

La politique suspend **126 soumissions** : 72 exercices C#, Docker, Linux B3 et GitHub B3, et 54 exercices SQL B1/B2/B3. Les ateliers et la pratique locale restent disponibles quand leur moteur le permet. Le script SQLite Piston examiné ne reprend pas le jeu d’initialisation fourni en entrée standard : cela ne démontre pas le comportement d’autres versions ni d’Oanor.

Les sondes d’exécution, la suite et la construction utilisent `bubblewrap`, sans réseau hôte ni répertoire personnel, et excluent fichiers d’environnement, clés et anciens résultats de l’instantané. Le parcours de pages Chromium utilise un serveur local temporaire et bloque les requêtes externes. Les valeurs après `IDENTIFIED BY` sont masquées dans les journaux SQL, sans modifier les requêtes exécutées. Le plafond SQLite du navigateur n’est pas un plafond de mémoire global de Chromium ; une interruption du simulateur réinitialise sa base.

Le test navigateur ciblé couvre les deux exercices pfSense, la saisie multiligne, le clavier, la persistance, les en-têtes mal formés, l’authentification, la suspension et le nouveau retour (`resultats/reprise-exemple-navigateur-apres.txt`). La région de résultat possède désormais un nom accessible, mais aucun essai avec lecteur d’écran n’a été réalisé. Une ancienne grille dont le nombre de cas a changé est conservée en mode texte ; les étapes de récupération sont précisées dans `corrections/README.md`.

Sous Node 26.10.0, un sous-test isolé du worker SQL échoue avant SQLite : V8 ne démarre pas avec sa limite de données fixée à 512 Mio. Sous Node 22.23.2 il réussit ; l'essai avec une limite supérieure a été écarté, faute de preuve d'une protection équivalente. Les sorties avant et après restauration sont conservées dans `resultats/sql-worker-node22-avant.txt`, `resultats/sql-worker-node26-avant.txt`, `resultats/sql-worker-node22-restaure.txt` et `resultats/sql-worker-node26-restaure.txt`. Cela ne démontre pas une incompatibilité générale du produit avec Node 26.
