Chapitre 3 — Héritage, Polymorphisme & Interfaces

Module 3 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Une suite logicielle d’édition graphique souffre de régressions majeures lors de l’ajout de nouveaux formats d’exportation. Des méthodes spécialisées écrasent silencieusement le comportement parent à cause d’une confusion entre "override" et "new", tandis que des conflits de noms de méthodes entre interfaces multiples paralysent l’intégration de modules tiers. L’équipe doit restructurer son modèle orienté objet : clarifier la répartition entre héritage d’implémentation et contrats d’interfaces, maîtriser le dispatch dynamique via la table des méthodes virtuelles (vtable), résoudre les collisions grâce à l’implémentation explicite d’interface et appliquer le patron Template Method sur des classes abstraites. Ce chapitre approfondit les mécanismes avancés du polymorphisme en C#.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. maîtriser la dérivation de classes avec le mot-clé base pour appeler les constructeurs et méthodes parents ;
  2. distinguer rigoureusement le polymorphisme dynamique (virtual/override) du masquage de membre statique (new) ;
  3. concevoir des classes abstraites (abstract) imposant des contrats d’implémentation avec le patron Template Method ;
  4. déclarer et implémenter des interfaces pour découpler les modules applicatifs (Inversion de Dépendance) ;
  5. résoudre les collisions d’homonymie de méthodes d’interfaces multiples via l’implémentation explicite.

1. Polymorphisme Dynamique (virtual / override) vs Masquage (new)

En C#, le polymorphisme n’est pas activé par défaut comme en Java : une méthode est non virtuelle sauf mention explicite du mot-clé virtual. Cette distinction change radicalement la façon dont la CLR résout les appels :

1. Polymorphisme dynamique (override)

La classe parente déclare virtual et la classe dérivée déclare override. La CLR met à jour la table des méthodes virtuelles (vtable). L’appel résout dynamiquement vers la classe dérivée, même si la référence est typée avec la classe de base.

class Base {
    public virtual void Saluer() => Console.WriteLine("Base");
}
class Deriv : Base {
    public override void Saluer() => Console.WriteLine("Deriv");
}
Base b = new Deriv();
b.Saluer(); // Affiche "Deriv" (dispatch dynamique)

2. Masquage statique (new)

La classe dérivée utilise le mot-clé new pour masquer une méthode parente. La vtable n’est pas modifiée : l’appel est résolu statiquement à la compilation selon le type déclaré de la variable.

class Base {
    public void Info() => Console.WriteLine("Base");
}
class Deriv : Base {
    public new void Info() => Console.WriteLine("Deriv");
}
Base b = new Deriv();
b.Info(); // Affiche "Base" ! (liaison statique précoce)

2. Classes Abstraites & Patron Template Method

Une classe abstraite (abstract class) ne peut pas être instanciée directement. Elle sert de modèle architectural en combinant des méthodes concrètes communes et des méthodes abstraites obligatoires :

public abstract class GenerateurRapport {
    // Template Method : squelette immuable de l'algorithme
    public void Generer() {
        Console.WriteLine("[1] Connexion à la base...");
        ChargerDonnees(); // Appel abstrait spécialisé
        Formater();       // Appel abstrait spécialisé
        Console.WriteLine("[4] Rapport archivé avec succès.");
    }

    protected abstract void ChargerDonnees();
    protected abstract void Formater();
}

public class RapportPdf : GenerateurRapport {
    protected override void ChargerDonnees() => Console.WriteLine("[2] Chargement SQL...");
    protected override void Formater() => Console.WriteLine("[3] Compilation du flux PDF...");
}
Avantage architectural du patron Template Method

Le patron Template Method garantit l’ordonnancement strict des étapes d’un processus métier tout en déléguant les variantes d’implémentation aux sous-classes, prévenant les omissions critiques (ex: oublier de clore une transaction ou d’archiver un fichier).

3. Interfaces Multiples & Implémentation Explicite

Contrairement à l’héritage de classes qui est strictement simple en C#, une classe peut implémenter un nombre illimité d’interfaces. Lorsqu’un conflit de noms survient entre deux interfaces, C# propose l’implémentation explicite d’interface :

public interface IExportable {
    void Traiter();
}
public interface IAuditable {
    void Traiter();
}

public class Document : IExportable, IAuditable {
    // Implémentation explicite : sans modificateur public !
    void IExportable.Traiter() => Console.WriteLine("Export JSON du document.");
    void IAuditable.Traiter()   => Console.WriteLine("Audit de conformité inscrit.");
}

var doc = new Document();
// doc.Traiter(); // ERREUR CS1061 : méthode inaccessible directement !
((IExportable)doc).Traiter(); // Affiche "Export JSON..."
((IAuditable)doc).Traiter();  // Affiche "Audit de conformité..."

Cette séparation étanche offre deux bénéfices majeurs :

  • Élimination totale des ambiguïtés lors de la coexistence de contrats fonctionnels homonymes ;
  • Protection de l’API publique de la classe en ne polluant pas l’autocomplétion (IntelliSense) avec des méthodes purement techniques d’interfaces spécialisées.

Exercice 1 — Polymorphisme dynamique (virtual/override) vs masquage (new)

C# Niveau 1 — Acquisition

Objectif : Démontrer la différence d'appel entre une méthode polymorphique virtual/override et un masquage statique new.

En C#, une classe Base expose une méthode polymorphique virtual void Afficher() et une méthode non virtuelle void Identifier().
Une classe dérivée Derived surcharge la première avec override void Afficher() et masque la seconde avec new void Identifier().
Votre programme C# lit les données sur l’entrée standard (Console.In).
Il doit déterminer quelle implémentation est exécutée selon la table des méthodes virtuelles (vtable dispatch) ou la liaison statique du compilateur.

Format de sortie :
<TypeReference>-><TypeInstance>: <NomMethode>() => <ClasseExecutant>.<NomMethode> <Tag>

Entrée du programme
REF Base OBJ Derived CALL Afficher
REF Base OBJ Derived CALL Identifier
REF Derived OBJ Derived CALL Afficher
REF Derived OBJ Derived CALL Identifier
Sortie attendue
Base->Derived: Afficher() => Derived.Afficher [virtual/override dynamique]
Base->Derived: Identifier() => Base.Identifier [new masqueur statique]
Derived->Derived: Afficher() => Derived.Afficher [override]
Derived->Derived: Identifier() => Derived.Identifier [new]

Afficher() résout vers Derived via vtable, tandis que Identifier() résout vers Base à cause du type de référence.

Trois indices, rédigés en mots
  1. Avec virtual/override, la méthode appelée dépend du type réel de l'objet à l'exécution (TypeInstance).
  2. Avec new (masquage statique), la méthode appelée dépend du type de la référence au moment de la compilation (TypeReference).
  3. Ajoutez le tag [virtual/override dynamique] ou [new masqueur statique] lorsque la référence est différente de l'instance.

Exercice 2 — Implémentation explicite d'interfaces multiples homonymes

C# Niveau 2 — Application

Objectif : Gérer la collision de noms de méthodes d'interfaces via l'implémentation explicite en C#.

Une classe C# implémente deux interfaces IExportable et IAuditable, qui définissent toutes deux une méthode void Traiter().
Elle utilise l'implémentation explicite :
- void IExportable.Traiter() génère un export de données JSON ;
- void IAuditable.Traiter() inscrit un enregistrement d'audit de sécurité.
Votre programme C# lit les données sur l’entrée standard (Console.In).
Le script doit simuler l'exécution et détecter l'erreur de compilation CS1061 en cas d'accès direct sans cast.

Format de sortie :
<Interface>.Traiter => <MessageSucces>
DIRECT Traiter => ERREUR_COMPILATION CS1061 (Implementation explicite requiert un cast)

Entrée du programme
CAST IExportable CALL Traiter
CAST IAuditable CALL Traiter
DIRECT CALL Traiter
Sortie attendue
IExportable.Traiter => Export JSON genere avec succes
IAuditable.Traiter => Audit journalise dans le registre de conformite
DIRECT Traiter => ERREUR_COMPILATION CS1061 (Implementation explicite requiert un cast)

L'accès direct échoue car les méthodes explicites ne sont accessibles que par référence d'interface.

Trois indices, rédigés en mots
  1. En C#, les méthodes d'interface implémentées explicitement ne sont pas publiques dans la classe : elles sont invisibles sans cast.
  2. Un cast vers IExportable déclenche le traitement d'export JSON.
  3. Un cast vers IAuditable déclenche le journal d'audit de conformité.

Exercice 3 — Classes abstraites et patron de conception Template Method

C# Niveau 3 — Raisonnement

Objectif : Implémenter un patron Template Method en C# avec étapes communes fixes et étapes abstraites spécialisées.

Une classe abstraite PipelineTraitement orchestre le traitement séquentiel d'une opération métier :
1. Étape abstraite Valider() (spécifique au type métier) ;
2. Étape abstraite Executer() (spécifique au type métier) ;
3. Étape concrète Journaliser() (partagée par tous les pipelines : [3. Notification globale envoyee]).
Votre programme C# lit les données sur l’entrée standard (Console.In).
Types supportés :
- Virement : [1. Valider IBAN et solde] -> [2. Debiter compte et crediter tiers] -> [3. Notification globale envoyee] ;
- Facture : [1. Valider TVA et lignes] -> [2. Calculer totaux et generer PDF] -> [3. Notification globale envoyee] ;
- Inscription : [1. Valider unicite email] -> [2. Creer compte utilisateur en base] -> [3. Notification globale envoyee].

Format de sortie :
Pipeline <Type>: <Etape1> -> <Etape2> -> <Etape3>

Entrée du programme
PIPELINE Virement
PIPELINE Facture
PIPELINE Inscription
Sortie attendue
Pipeline Virement: [1. Valider IBAN et solde] -> [2. Debiter compte et crediter tiers] -> [3. Notification globale envoyee]
Pipeline Facture: [1. Valider TVA et lignes] -> [2. Calculer totaux et generer PDF] -> [3. Notification globale envoyee]
Pipeline Inscription: [1. Valider unicite email] -> [2. Creer compte utilisateur en base] -> [3. Notification globale envoyee]

Chaque sous-classe spécialise les deux premières étapes abstraites, l'étape 3 étant héritée de la classe abstraite.

Trois indices, rédigés en mots
  1. La méthode Template Method définit le squelette de l'algorithme dans la classe de base.
  2. Les classes dérivées redéfinissent obligatoirement les étapes marquées abstract.
  3. Respecte la syntaxe exacte des étapes pour chaque type d'opération.

5. QCM — niveau examen

Soit Base b = new Deriv(); où Deriv redéfinit une méthode Afficher() présente dans Base. Quelle condition doit être remplie pour que Deriv.Afficher soit appelée ?

Pour obtenir un dispatch dynamique (polymorphisme réel à l’exécution), la méthode doit être déclarée virtual dans la classe de base et override dans la classe dérivée.

Quel est le résultat d’un appel b.Identifier() si b est de type Base mais référence une instance de Deriv qui utilise "new void Identifier()" ?

Le mot-clé new masque le membre sans mettre à jour la table des méthodes virtuelles (vtable). L’appel via une référence du type Base résout statiquement vers Base.Identifier().

Pourquoi une méthode implémentant explicitement une interface (ex: void ILogger.Log()) ne peut-elle pas comporter le mot-clé public ?

Les membres d’implémentation explicite d’interface ne font pas partie de la surface d’API publique directe de la classe et ne peuvent être consommés qu’en référençant explicitement l’interface.

Quel principe de conception logicielle est appliqué lorsqu’on programme contre une interface plutôt qu’une classe concrète ?

Le principe d’inversion des dépendances (le D de SOLID) préconise que les modules de haut niveau dépendent d’abstractions (interfaces) et non d’implémentations concrètes.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Oublier le mot-clé virtual sur une méthode de la classe de base, rendant impossible son polymorphisme avec override (avertissement ou masquage new involontaire).
  • Utiliser le mot-clé new en pensant surcharger une méthode : l’appel via une variable du type de la classe de base exécutera toujours la méthode parente.
  • Mettre le modificateur public sur une méthode implémentant explicitement une interface (erreur de compilation CS0106 : les méthodes explicites ne tolèrent aucun modificateur d’accès).
  • Instancier directement une classe abstraite avec new (erreur de compilation CS0144).

7. Méthodologie de résolution

Protocole en 4 étapes pour bâtir une hiérarchie polymorphique C#
  1. Déterminer si la relation relève d’un héritage d’implémentation (est un) ou d’un contrat (implémente).
  2. Marquer virtual les méthodes de base destinées à être redéfinies et override dans les classes dérivées.
  3. Ne jamais utiliser le mot-clé new par inadvertance pour tenter de surcharger une méthode.
  4. Isoler les méthodes homonymes d’interfaces multiples grâce à l’implémentation explicite d’interface sans mot-clé public.

8. Révision active

Résumé essentiel
  • En C#, les méthodes sont non virtuelles par défaut ; virtual et override activent le dispatch dynamique via la vtable.
  • Le mot-clé new masque un membre parent par liaison statique précoce sans altérer la vtable.
  • Une classe abstraite ne peut être instanciée et structure des processus communs avec le patron Template Method.
  • Une classe C# peut implémenter un nombre arbitraire d’interfaces, découplant le code selon le principe DIP.
  • L’implémentation explicite d’interface résout les collisions de noms et s’invoque obligatoirement par cast.
