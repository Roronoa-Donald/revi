Chapitre 6 — Programmation Asynchrone (TAP) & Gestion des Ressources

Module 6 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Un service de traitement de documents dématérialisés subit des ralentissements catastrophiques et des pannes régulières sous forte charge : des appels bloquants .Result et .Wait() sur des tâches asynchrones provoquent des interblocages (deadlocks) massifs de threads, tandis que des descripteurs de fichiers et connexions réseau restent ouverts indéfiniment parce que le Garbage Collector tarde à passer. L’architecte logiciel ordonne une refonte immédiate : bannir tout blocage de thread en adoptant le modèle Task-based Asynchronous Pattern (TAP) avec async et await de bout en bout, orchestrer la concurrence propre avec Task.WhenAll et la capture structurée des AggregateException, et garantir la libération immédiate et déterministe des ressources non managées via l’instruction using et le patron IDisposable. Ce dernier module parachève la formation en bâtissant des applications hautement scalables et exemptes de fuites de ressources.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. comprendre le fonctionnement interne de async/await et la transformation en machine à états générée par Roslyn ;
  2. éliminer les anti-patterns bloquants (.Result, .Wait()) responsables des deadlocks de ThreadPool ;
  3. exécuter des flux concurrents en parallèle avec Task.WhenAll et extraire la totalité des causes d’échec via AggregateException ;
  4. appliquer le modèle d’annulation coopérative grâce à CancellationToken et CancellationTokenSource ;
  5. implémenter rigoureusement le patron de conception IDisposable et maîtriser la syntaxe modernisée de l’instruction using.

1. Le Modèle Asynchrone TAP & La Machine à États Roslyn

En C#, la programmation asynchrone repose sur le Task-based Asynchronous Pattern (TAP) et les types Task et Task<TResult>. Contrairement au multi-threading classique qui bloque un thread lourd du système d’exploitation en attente d’I/O, le mot-clé await libère le thread courant pour qu’il traite d’autres requêtes :

public async Task<DonneesClient> ObtenirProfilAsync(int idClient)
{
    // Le thread appelant est libéré pendant l’attente réseau du SGBD
    string json = await _clientHttp.GetStringAsync($"https://api.interne/clients/{idClient}");
    
    // À la fin de l’I/O, un thread disponible de la ThreadPool reprend l’exécution
    return JsonSerializer.Deserialize<DonneesClient>(json)!;
}

En coulisses : la Machine à États Roslyn

À la compilation, Roslyn transforme la méthode async en une structure implémentant IAsyncStateMachine. Chaque await représente un point de suspension : un continuateur (callback) est enregistré et l’état courant de la méthode est sauvegardé sans bloquer le système.

Règle fondamentale : "Async all the way"

L’asynchronisme doit se propager sur l’intégralité de la chaîne d’appels, du contrôleur API jusqu’à l’accès disque ou base de données. Ne convertissez jamais du code asynchrone en synchrone avec .Result ou .Wait() au risque de provoquer un interblocage (deadlock).

2. Concurrence avec Task.WhenAll & Gestion des AggregateException

Pour exécuter plusieurs tâches indépendantes en parallèle sans attendre qu’elles se terminent séquentiellement, C# propose Task.WhenAll :

Task<RapportVentes> taskVentes = ChargerVentesAsync();
Task<RapportStock> taskStock = ChargerStockAsync();
Task<RapportClients> taskClients = ChargerClientsAsync();

try {
    // Attend la complétion simultanée des trois tâches
    await Task.WhenAll(taskVentes, taskStock, taskClients);
} catch (Exception ex) {
    // Attention : await ne propage que la première exception rencontrée !
    // Pour inspecter toutes les erreurs simultanées, examiner task.Exception
}
Le piège de la perte d’erreurs dans Task.WhenAll

Lorsqu’on utilise await Task.WhenAll(...), si plusieurs tâches échouent, le mot-clé await ne relance que la première exception survenue.
Pour capturer la totalité des erreurs survenues, il faut stocker la tâche combinée et examiner sa propriété Exception qui contient une instance de AggregateException avec la collection InnerExceptions :

Task allTasks = Task.WhenAll(t1, t2, t3);
try {
    await allTasks;
} catch {
    foreach (var err in allTasks.Exception!.InnerExceptions) {
        Console.WriteLine($"Erreur interceptée : {err.Message}");
    }
}

3. Libération Déterministe des Ressources : IDisposable & using

Le Garbage Collector de .NET gère remarquablement la mémoire managée (Gen 0, Gen 1, Gen 2). Cependant, il ignore quand libérer les ressources non managées du système d’exploitation : descripteurs de fichiers natifs, connexions TCP, verrous d’OS ou contextes GPU.
Pour ces ressources, .NET impose l’interface IDisposable et son unique méthode void Dispose().

Syntaxe de déclaration using moderne (C# 8+)

public void TraiterFichier(string chemin)
{
    // Libération garantie à la sortie du bloc de méthode
    using var stream = new FileStream(chemin, FileMode.Open);
    using var reader = new StreamReader(stream);
    
    string contenu = reader.ReadToEnd();
    Console.WriteLine($"Taille : {contenu.Length}");
} // stream.Dispose() et reader.Dispose() appelés automatiquement ici !

Code équivalent généré par le compilateur

FileStream stream = new FileStream(chemin, FileMode.Open);
try {
    // Corps du traitement
} finally {
    if (stream != null) {
        ((IDisposable)stream).Dispose();
    }
}
Garantie absolue du bloc finally

Même si une exception non gérée survient à l’intérieur du bloc d’utilisation (par exemple une rupture de connexion ou une mémoire saturée), la méthode Dispose() est inconditionnellement appelée grâce au bloc finally généré par Roslyn, bannissant tout risque de verrou orphelin sur les fichiers ou sockets.

Exercice 1 — Simulateur de Machine à États Async/Await (TAP Pattern)

C# Niveau 1 — Acquisition

Objectif : Tracer l'exécution d'un workflow asynchrone C# modélisé par la machine à états de Roslyn.

En C#, les méthodes asynchrones (async Task) sont compilées en machines à états qui libèrent le thread appelant lors d'un await et reprennent leur exécution au signal de fin de tâche I/O.
Votre programme C# lit les données sur l’entrée standard (Console.In).
Il doit simuler la progression temporelle à partir de T=0ms, tracer chaque démarrage avec suspension (Await), chaque reprise de contexte (Reprise contexte), et afficher la durée totale cumulée.

Format de sortie :
[T=<T>ms] Demarrage <Nom> -> Await (suspension thread)
[T=<T>ms] Reprise contexte -> Demarrage <NomSuivant> -> Await
...
[T=<Total>ms] Tache completee avec succes. Duree totale=<Total>ms

Entrée du programme
TASK TelechargerFichier Duree=30ms
TASK TraiterDonnees Duree=20ms
TASK SauvegarderBD Duree=15ms
Sortie attendue
[T=0ms] Demarrage TelechargerFichier -> Await (suspension thread)
[T=30ms] Reprise contexte -> Demarrage TraiterDonnees -> Await
[T=50ms] Reprise contexte -> Demarrage SauvegarderBD -> Await
[T=65ms] Tache completee avec succes. Duree totale=65ms

Tracé temporel précis des suspensions et reprises de la machine à états C#.

Trois indices, rédigés en mots
  1. La première tâche démarre à T=0ms.
  2. Chaque reprise de contexte se produit au temps T cumulé des tâches précédentes.
  3. La durée totale est la somme exacte des durées de chaque étape.

Exercice 2 — Orchestrateur concurrent avec Task.WhenAll et AggregateException

C# Niveau 2 — Application

Objectif : Simuler la synchronisation de tâches concurrentes via Task.WhenAll et la capture d'erreurs groupées.

En C#, await Task.WhenAll(t1, t2, ...) attend l'achèvement simultané de plusieurs tâches.
Si au moins une tâche échoue avec une exception, le runtime regroupe toutes les exceptions survenues dans une AggregateException (contrairement au premier échec qui masquerait les autres).
Votre programme C# lit les données sur l’entrée standard (Console.In).
Il doit compter les succès et échecs, puis formater l'éventuelle AggregateException avec la liste ordonnée des erreurs.

Format de sortie :
WHENALL: <NbreSucces> succes, <NbreEchecs> echecs
Si échecs > 0 :
AggregateException levee (<N> erreurs):
- Erreur 1: <Message>
...
Sinon :
Execution terminee sans exception

Entrée du programme
TASK T1 Status=OK
TASK T2 Status=FAIL Error="SocketException: Connexion refusee"
TASK T3 Status=OK
TASK T4 Status=FAIL Error="SqlException: Timeout expire"
Sortie attendue
WHENALL: 2 succes, 2 echecs
AggregateException levee (2 erreurs):
- Erreur 1: SocketException: Connexion refusee
- Erreur 2: SqlException: Timeout expire

Task.WhenAll agrège les deux exceptions sans perdre la seconde.

Trois indices, rédigés en mots
  1. Compte les statuts OK et extrait les messages d'erreur des statuts FAIL.
  2. Si le nombre d'échecs est supérieur à zéro, affiche le bloc AggregateException.
  3. Numérote les erreurs de 1 à N dans l'ordre de lecture.

Exercice 3 — Gestion déterministe des ressources non managées (IDisposable et using)

C# Niveau 3 — Raisonnement

Objectif : Simuler le pattern IDisposable et l'instruction using C# garantissant la libération des ressources en toutes circonstances.

En C#, l'instruction using (var res = new Ressource()) { ... } se traduit par un bloc try / finally où res.Dispose() est obligatoirement exécuté pour libérer les handles natifs (fichiers, sockets, curseurs BD), même en cas de crash non géré.
Votre programme C# lit les données sur l’entrée standard (Console.In).
Le script doit tracer les étapes et garantir l'appel inconditionnel de [DISPOSE] à la fin.

Format de sortie :
[ALLOC] <Nom> alloue (Handle=<Handle>)
[EXEC] Op <NomOp> <Params>
[CRASH] Exception <Type> interceptee (si applicable)
[DISPOSE] <Nom> libere via IDisposable

Entrée du programme
RESOURCE FichierLogs ALLOCATE=Handle0x10A
OP EcritureLigne "Demarrage"
THROW DiskFullException
Sortie attendue
[ALLOC] FichierLogs alloue (Handle=Handle0x10A)
[EXEC] Op EcritureLigne "Demarrage"
[CRASH] Exception DiskFullException intercepte
[DISPOSE] FichierLogs libere via IDisposable

Malgré le crash DiskFullException, la ressource est immédiatement libérée via le finally de using.

Trois indices, rédigés en mots
  1. Gardez une référence vers la ressource allouée au début.
  2. Affichez chaque opération OP exécutée.
  3. Si une exception THROW survient, intercepte-la et appelle quand même le bloc finally [DISPOSE].

5. QCM — niveau examen

Quel est l’effet de l’opérateur await sur le thread appelant lors d’une opération d’E/S asynchrone ?

L’opérateur await suspend l’exécution logique de la méthode asynchrone et libère immédiatement le thread d’exécution appelant, maximisant le débit et la scalabilité du système sans saturer la ThreadPool.

Pourquoi la signature "async void" est-elle formellement déconseillée en dehors des gestionnaires d’événements d’interface graphique ?

Une méthode async void est du type "fire-and-forget" : elle ne renvoie aucun objet Task. L’appelant ne peut ni l’attendre ni capturer ses exceptions, lesquelles sont envoyées directement au SynchronizationContext et provoquent l’arrêt brutal du processus applicatif.

Lorsqu’on attend plusieurs tâches avec Task.WhenAll(t1, t2), si t1 et t2 échouent toutes les deux, où sont conservées les deux exceptions ?

Task.WhenAll rassemble toutes les erreurs survenues dans une AggregateException accessible via la propriété Exception de la tâche combinée, garantissant qu’aucune cause de défaillance ne soit perdue.

Quel code de bas niveau le compilateur Roslyn génère-t-il automatiquement lorsqu’on utilise l’instruction "using var res = new MonObjet();" ?

L’instruction using est un sucre syntaxique traduisant le code en une structure try / finally où res.Dispose() est invoqué dans le bloc finally, assurant la libération déterministe même en cas de crash dans le try.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Bloquer un thread avec .Result ou .Wait() au lieu d’utiliser await, créant des risques majeurs d’interblocage (deadlock) de ThreadPool.
  • Utiliser async void au lieu de async Task pour une méthode asynchrone (les exceptions levées dans async void ne peuvent pas être interceptées et font crasher le processus entier ; exception réservée uniquement aux gestionnaires d’événements d’interface graphique).
  • Oublier de capturer AggregateException lors d’échecs multiples avec Task.WhenAll, masquant des pannes critiques survenues sur les tâches secondaires.
  • Ne pas utiliser l’instruction using sur un objet implémentant IDisposable, provoquant l’épuisement des handles de fichiers sous charge soutenue.

7. Méthodologie de résolution

Protocole en 4 étapes pour orchestrer l’asynchronisme et la libération mémoire
  1. Propager async/await de bout en bout ("async all the way") sans jamais bloquer avec .Result ou .Wait().
  2. Utiliser async Task plutôt que async void pour permettre l’attente et la capture des exceptions.
  3. Orchestrer les traitements parallèles indépendants avec Task.WhenAll et inspecter allTasks.Exception.
  4. Envelopper toute ressource non managée (fichiers, sockets) dans une instruction using ou implémenter IDisposable.

8. Révision active

Résumé essentiel
  • Le modèle TAP s’appuie sur Task et libère le thread appelant pendant les opérations d’E/S via await.
  • Roslyn décompose toute méthode async en une machine à états managée (IAsyncStateMachine).
  • Task.WhenAll exécute des tâches en concurrence et rassemble toutes les erreurs dans une AggregateException.
  • CancellationToken propage l’annulation coopérative propre à travers les tâches asynchrones.
  • IDisposable et using garantissent la libération déterministe des ressources natives via un bloc finally sous-jacent.

Checklist de maîtrise

  • Je ne bloque jamais de thread avec .Result ou .Wait().
  • Je n’écris jamais async void sauf pour les événements graphiques.
  • Je sais exécuter plusieurs tâches en parallèle avec Task.WhenAll.
  • Je sais inspecter toutes les erreurs d’une AggregateException.
  • Je libère systématiquement mes objets IDisposable avec l’instruction using.
