Chapitre 1 — Fondements des Conteneurs, Isolation Linux & Architecture Docker

Module 1 ≈ 2 h 45 de travail Accès libre
Mise en situation

Pendant des décennies, le déploiement d’applications en entreprise souffrait du syndrome classique « mais pourtant ça marchait sur ma machine ! ». Deux approches coexistaient : le déploiement direct sur serveur physique (générant des conflits inextricables de versions de bibliothèques et de dépendances) ou la virtualisation lourde par hyperviseur (VMware, VirtualBox), où chaque instance duplique un système d’exploitation complet de plusieurs gigaoctets avec son propre noyau et des minutes de temps de démarrage. L’avènement de Docker en 2013 a révolutionné cette industrie en démocratisant les fonctionnalités d’isolation natives du noyau Linux. Ce premier module pose les fondations théoriques et architecturales indispensables : comprendre comment le système d’exploitation isole les processus sans hyperviseur et comment s’articulent les briques internes de la pile Docker moderne conforme aux standards ouverts OCI.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. comprendre l’évolution historique de l’hébergement applicatif (bare-metal, VM, conteneurs) ;
  2. comparer avec précision les architectures et coûts de ressources entre machine virtuelle et conteneur ;
  3. maîtriser le fonctionnement des 6 Namespaces fondamentaux du noyau Linux (PID, NET, MNT, IPC, UTS, USER) ;
  4. comprendre le rôle des Control Groups (cgroups v1 et v2) dans la régulation CPU, mémoire et E/S ;
  5. décortiquer l’architecture modulaire de Docker : du client CLI jusqu’au runtime OCI runc via containerd ;
  6. exécuter et inspecter ses premiers conteneurs en ligne de commande de manière méthodique.

1. De la Machine Virtuelle au Conteneur Léger

Pour comprendre la valeur ajoutée de Docker, il est essentiel d’opposer la virtualisation système à la virtualisation au niveau du système d’exploitation :

Machine Virtuelle (Virtualisation Lourde)

  • Hyperviseur : Type 1 (KVM, ESXi) ou Type 2 (VirtualBox) qui émule du matériel virtuel (CPU, RAM, contrôleurs disques).
  • Guest OS complet : Chaque VM embarque son propre noyau Linux ou Windows, ses démons systèmes (systemd, udev), et ses pilotes.
  • Empreinte : Plusieurs gigaoctets par instance, démarrage en plusieurs dizaines de secondes, overhead CPU/RAM de 10 à 25 %.

Conteneur Docker (Isolation Noyau Légère)

  • Moteur de conteneurisation : Pas d’émulation matérielle ni d’hyperviseur.
  • Partage du noyau : Tous les conteneurs s’exécutent directement sur le noyau de la machine hôte.
  • Empreinte : Quelques mégaoctets, démarrage quasi instantané en quelques millisecondes, performances quasi natives (overhead < 1 %).
Un conteneur est un processus Linux isolé

Contrairement à une idée reçue tenace, un conteneur n’est pas une « petite machine virtuelle ». Sur le serveur hôte, un conteneur n’est rien d’autre qu’un processus Linux standard auquel le noyau a appliqué des filtres de visibilité (Namespaces) et des plafonds de ressources (Cgroups).

2. Les Primitives du Noyau Linux : Namespaces & Cgroups

Docker ne réinvente pas l’isolation : il orchestre avec élégance des fonctionnalités intégrées au noyau Linux depuis les années 2000 :

Primitive Noyau Type Fonction & Espace Isolé
PID Namespace Isolation Isole l’arborescence des processus. Le processus principal du conteneur se voit comme PID 1 (processus initial), alors qu’il possède un PID standard (ex: 28412) sur l’hôte.
NET Namespace Isolation Fournit au conteneur sa propre pile réseau : interface de boucle locale lo, interface virtuelle eth0, table de routage et ports TCP/UDP dédiés.
MNT Namespace Isolation Isole les points de montage du système de fichiers. Combiné à pivot_root, le conteneur ne voit que son propre système de fichiers racine sans accéder à l’arborescence de l’hôte.
IPC Namespace Isolation Isole les mécanismes de communication inter-processus (mémoire partagée POSIX, sémaphores, files de messages).
UTS Namespace Isolation Permet au conteneur de définir son propre nom d’hôte (hostname) et nom de domaine indépendant de la machine physique.
USER Namespace Isolation Mappe les UID/GID : permet d’être root (UID 0) à l’intérieur du conteneur tout en étant un simple utilisateur non-privilégié (ex: UID 100000) sur la machine hôte.
Cgroups (Control Groups) Régulation Contrôle et plafonne l’utilisation des ressources matérielles : limitation de mémoire vive (RAM), quotas de temps processeur (CPU) et débits disques (I/O).

3. Architecture Interne du Moteur Docker et Standards OCI

À l’origine, Docker était un démon monolithique écrit en Go. Pour favoriser la standardisation industrielle, l’architecture a été scindée en briques modulaires sous l’égide de l’Open Container Initiative (OCI) :

1. Client CLI & Docker Daemon

Le client docker transmet les ordres utilisateur via l’API REST (par défaut via la socket UNIX /var/run/docker.sock). Le démon dockerd gère les images, les volumes de stockage, les réseaux virtuels et l’authentification.

2. containerd & containerd-shim

containerd est le superviseur industriel de conteneurs. Il gère le cycle de vie et le téléchargement des images. Pour chaque conteneur actif, un processus léger containerd-shim reste actif pour gérer les entrées/sorties et préserver le conteneur si le démon Docker doit redémarrer (Live Restore).

3. runc (OCI Runtime)

runc est l’implémentation de référence universelle du standard OCI. Écrit en Go, il dialogue directement avec les appels système du noyau Linux pour configurer les namespaces, appliquer les cgroups et exécuter le binaire de l’application.

La Socket Docker et Risque de Sécurité

Le fichier /var/run/docker.sock est le point d’accès direct à l’API Docker. Tout utilisateur ayant un accès en écriture sur cette socket (ou membre du groupe système docker) peut instantanément s’octroyer les privilèges superutilisateur root sur l’hôte physique en lançant un conteneur privilégié qui monte la racine du système (-v /:/host). Ne montez JAMAIS la socket Docker dans des conteneurs non fiables.

4. Premières Manipulations et Commandes de Base

Pour démarrer avec le client Docker, quatre commandes fondamentales constituent le socle du quotidien :

  • docker run --rm hello-world : télécharge une image minimale, crée le conteneur, l’exécute et le détruit automatiquement après affichage.
  • docker ps -a : liste l’intégralité des conteneurs (actifs et arrêtés) avec leur identifiant (CONTAINER ID), leur statut et leurs ports.
  • docker images : affiche les images locales stockées dans le cache du démon avec leurs tags et leur taille.
  • docker inspect <id_conteneur> : inspecte l’objet conteneur et renvoie l’intégralité de sa configuration bas niveau au format JSON.

Python Niveau 1 — Acquisition

Objectif : Distinguer les primitives du noyau Linux sous-jacentes à Docker : Namespaces (vue isolée) et Cgroups (limitation des ressources).

Le script lit sur l'entrée standard des noms de mécanismes d'isolation du noyau Linux (un par ligne).
Selon les fondements de la conteneurisation :
- Namespaces (Isolation de l'espace de visibilité) :
* PID -> Arborescence des processus isolée (le conteneur voit son propre PID 1)
* NET -> Interfaces reseau, tables de routage et ports isoles

<MECANISME> -> INCONNU

Exercice 2 — Comparateur d’empreinte mémoire et stockage : VM vs Conteneur

Python Niveau 2 — Application

Objectif : Quantifier l’overhead de virtualisation lourde (Hyperviseur + Guest OS complet) face à la conteneurisation légère.

Le script lit sur l'entrée standard :
- Première ligne : <NbInstances> <TailleAppMo> <RamAppMo> (ressources nécessaires à l'application seule).
- Deuxième ligne : <TailleGuestOsMo> <RamGuestOsMo> (ressources consommées par l'OS invité dans une machine virtuelle).
Dans une architecture de conteneurs Docker, le kernel de l'hôte est partagé (0 Mo d'overhead Guest OS par conteneur).
Calculer :
1. VM :
- Disque total VM = NbInstances * (TailleAppMo + TailleGuestOsMo)
- RAM totale VM = NbInstances * (RamAppMo + RamGuestOsMo)
2. DOCKER :
- Disque total Docker = NbInstances * TailleAppMo
- RAM totale Docker = NbInstances * RamAppMo
3. GAINS :
- Gain disque = Disque VM - Disque Docker
- Gain RAM = RAM VM - RAM Docker
Afficher :

ARCHITECTURE DOCKER: Disque <Ddoc> Mo | RAM <Rdoc> Mo
ECONOMIE DOCKER: Disque -<GainD> Mo | RAM -<GainR> Mo

6. QCM — niveau examen

Quelle est la différence architecturale majeure entre une Machine Virtuelle et un Conteneur Docker ?

Une VM duplique un OS invité complet avec son propre noyau au-dessus d’un hyperviseur. Le conteneur s’exécute directement sur l’OS hôte et partage son noyau.

Quel mécanisme du noyau Linux permet d’attribuer au processus principal d’un conteneur l’identifiant PID 1 tout en conservant son vrai PID sur la machine hôte ?

Le PID Namespace crée une arborescence de processus cloisonnée et indépendante où le premier processus lancé reçoit le PID 1 à l’intérieur du conteneur.

À quoi servent les Control Groups (Cgroups) dans l’infrastructure de conteneurs Linux ?

Alors que les namespaces isolent la visibilité des ressources, les cgroups régulent quantitativement l’allocation des ressources physiques (plafond de RAM, part de CPU).

Quel composant logiciel bas niveau conforme aux spécifications de l’OCI (Open Container Initiative) est responsable de la création effective des namespaces et du démarrage du processus conteneurisé ?

runc est le runtime OCI de référence : il interagit directement avec les primitives du noyau Linux pour instancier le conteneur selon la spécification OCI.

Pourquoi le processus « containerd-shim » reste-t-il actif pour chaque conteneur en cours d’exécution ?

containerd-shim découple le conteneur du démon dockerd : si dockerd plante ou est mis à jour, les conteneurs continuent de tourner sans interruption.

Que se passe-t-il si un utilisateur non-root a un accès complet en écriture au fichier socket « /var/run/docker.sock » ?

Contrôler la socket Docker permet de lancer un conteneur privilégié montant le disque hôte (-v /:/host) et modifiant le fichier /etc/shadow pour prendre le contrôle total de l’hôte.

Quel Namespace Linux permet au conteneur de disposer de sa propre table de routage et de ses propres ports TCP/UDP indépendants ?

Le NET Namespace fournit une pile réseau complètement étanche, incluant ses propres interfaces réseau, règles de filtrage et ports d’écoute.

Quelle commande CLI Docker permet d’afficher la configuration bas niveau d’un conteneur au format JSON (adresses IP, points de montage, statut) ?

docker inspect retourne l’état complet, la configuration réseau, les montages et les limites de ressources du conteneur au format JSON structuré.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Penser qu’un conteneur est une VM : un conteneur ne peut pas faire tourner un noyau différent de l’hôte (ex: pas de noyau Windows natif sur hôte Linux).
  • Oublier le flag --rm lors de tests rapides en ligne de commande, ce qui accumule des conteneurs arrêtés inutiles sur le disque.
  • Donner les droits sudo ou l’accès au groupe docker à des utilisateurs non sécurisés sans mesurer l’impact d’élévation de privilèges.
  • Confondre le rôle de dockerd (orchestrateur haut niveau) et runc (exécuteur bas niveau de conteneurs).

8. Méthodologie de résolution

Protocole de Démarrage et d’Inspection d’un Conteneur Docker
  1. Étape 1 — Vérifier le statut du service Docker : S’assurer que le démon dockerd est actif avec la commande « systemctl status docker » ou « docker info ».
  2. Étape 2 — Télécharger une image officielle : Rapatrier l’image minimale Alpine Linux avec « docker pull alpine:3.18 ».
  3. Étape 3 — Lancer un conteneur interactif : Exécuter « docker run -it --name mon_test alpine:3.18 /bin/sh » pour obtenir une invite de commande isolée.
  4. Étape 4 — Observer l’isolation des processus : Taper « ps aux » à l’intérieur du conteneur et constater que seul le shell /bin/sh s’exécute avec le PID 1.
  5. Étape 5 — Observer l’isolation depuis l’hôte : Ouvrir un second terminal sur la machine hôte et chercher le processus avec « pgrep -a sh » pour voir son vrai PID système.
  6. Étape 6 — Nettoyer les ressources : Quitter le conteneur avec « exit » et détruire le conteneur arrêté avec « docker rm mon_test ».

9. Révision active

Résumé essentiel
  • Un conteneur Docker est un processus Linux isolé partageant le noyau hôte, sans couche d’émulation matérielle ni Guest OS.
  • Les Namespaces créent des cloisons virtuelles d’espace de noms (PID, NET, MNT, IPC, UTS, USER).
  • Les Cgroups (Control Groups) plafonnent et mesurent la consommation matérielle (CPU, RAM, débits E/S).
  • L’architecture moderne découple le client CLI, le démon dockerd, le superviseur containerd et le runtime OCI runc.
  • Le composant containerd-shim permet aux conteneurs de continuer à tourner sans interruption même si le démon Docker redémarre.
  • L’accès en écriture à /var/run/docker.sock équivaut à un accès root complet sur le système hôte.
