Chapitre 2 — Images, Layers & Registres Docker

Module 2 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Une entreprise déploie 80 conteneurs sur un serveur de production dont le disque dur s’est soudainement saturé. En examinant le stockage, l’administrateur découvre que chaque développeur a packagé une image de 1,2 Go basée sur une distribution Linux lourde sans mutualisation, consommant près de 100 Go de disque inutilement. Pire encore : un déploiement récent utilisant le tag flottant « :latest » a brisé l’application en production car l’image distante avait été mise à jour à l’insu de l’équipe. Pour maîtriser le stockage, la reproductibilité et la sécurité des déploiements, les ingénieurs doivent comprendre intimement comment fonctionne le système de fichiers en couches OverlayFS, comment les couches sont dédupliquées sur l’hôte et comment épingler rigoureusement les images par leurs digests cryptographiques SHA256.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. comprendre la structure interne d’une image Docker (empilement de couches immuables Read-Only) ;
  2. analyser le fonctionnement du pilote de stockage Overlay2 (dossiers lowerdir, upperdir, merged) ;
  3. maîtriser le principe de Copy-On-Write (CoW) lors des opérations d’écriture et de suppression (Whiteout) ;
  4. calculer les gains d’espace disque réels issus de la déduplication des couches partagées ;
  5. décomposer une référence d’image selon la norme OCI (registre, namespace, repository, tag, digest) ;
  6. comprendre pourquoi l’usage du tag « latest » en production est un anti-pattern dangereux.

1. Anatomie d’une Image et Empilement de Couches (Layers)

Une image Docker n’est pas un fichier monolithique, mais une pile ordonnée de couches immuables (tarballs d’arborescences de fichiers) identifiées par un hachage cryptographique SHA256 :

Couches d’Image (Image Layers — Read-Only)

  • Chaque instruction d’un Dockerfile (FROM, RUN, COPY) crée une nouvelle couche sur le disque.
  • Ces couches sont strictement en lecture seule (immuables) : une fois forgées, elles ne peuvent jamais être altérées.
  • Elles sont partagées universellement entre toutes les images et conteneurs du serveur qui s’appuient dessus.

Couche Conteneur (Container Layer — Read-Write)

  • Lorsqu’un conteneur est instancié à partir d’une image, Docker ajoute une couche mince en lecture-écriture au sommet de la pile.
  • Toutes les modifications du conteneur (création de fichiers temporaires, journaux, base de données locale) sont consignées dans cette couche.
  • Elle est détruite automatiquement lors de la suppression du conteneur (docker rm).

2. Le Pilote de Stockage Overlay2 et la Mécanique Copy-On-Write (CoW)

Le pilote de stockage standard sous Linux est OverlayFS (overlay2). Il fusionne virtuellement plusieurs répertoires en un point de montage unifié sans dupliquer les fichiers :

Composant OverlayFS Nature & Rôle Équivalent Docker
lowerdir Ensemble des répertoires inférieurs en lecture seule. Les couches immuables de l’image Docker.
upperdir Répertoire supérieur unique en lecture-écriture. La couche volatile du conteneur (Container Writable Layer).
workdir Répertoire interne de préparation pour les opérations atomiques. Espace de travail interne géré par le noyau Linux.
merged Point de montage résultant visible par le conteneur. La racine du conteneur (ce que le processus voit dans son arborescence).
Comment Fonctionne le Copy-On-Write (CoW) ?

Tant qu’un conteneur lit un fichier existant dans l’image, il accède directement à la couche inférieure sans aucune copie mémoire ni disque. Dès que le conteneur tente de modifier ce fichier, le noyau le copie d’abord instantanément dans le répertoire supérieur (upperdir) avant d’y appliquer les modifications. Si un conteneur tente de supprimer un fichier d’image, le noyau ne peut pas toucher à la couche Read-Only : il crée alors un fichier spécial nommé whiteout (nœud de périphérique avec majeur/mineur 0/0) dans l’upperdir, masquant le fichier aux yeux du conteneur.

3. Registres d’Images, Tags Flottants vs Digests SHA256

Les images sont hébergées sur des registres distants (Docker Hub, GitHub Container Registry ghcr.io, Quay.io, ou registries privées auto-hébergées comme Harbor). Une référence d’image complète répond à la nomenclature formelle suivante :

[REGISTRE/][NAMESPACE/]REPOSITORY[:TAG][@sha256:DIGEST]\n\nExemples :\n- nginx                                 -> docker.io/library/nginx:latest\n- monorg/backend:v1.2.0                  -> docker.io/monorg/backend:v1.2.0\n- ghcr.io/equipe/service:2.1.0           -> ghcr.io/equipe/service:2.1.0\n- redis@sha256:4b912a...                -> Version cryptographiquement immuable
Le Piège Mortel du Tag « :latest » en Production

Le tag latest n’offre aucune garantie de stabilité : il s’agit d’un simple pointeur symbolique flottant qui est réassigné chaque fois qu’une nouvelle image est poussée sans tag spécifique. En production, l’usage de :latest expose à des pannes imprévisibles, à l’impossibilité de reproduire un bogue, et à des attaques par empoisonnement de dépendance (Supply Chain Attack). Exigence de production : toujours utiliser un tag sémantique explicite (ex: node:18.19.0-alpine) ou mieux encore, le digest SHA256 complet de l’image.

4. Commandes de Gestion et Distribution d’Images

Pour manipuler efficacement les images dans son flux de travail quotidien :

  • docker pull <image>:<tag> : télécharge l’image depuis le registre distant couche par couche (en ignorant les couches déjà présentes en cache local).
  • docker tag <source> <cible> : crée un alias symbolique vers une image existante sans dupliquer les couches.
  • docker push <image> : publie une image forgée localement vers un registre distant après authentification (docker login).
  • docker history <image> : inspecte l’historique des couches de l’image, affichant la taille et la commande Dockerfile à l’origine de chaque layer.
  • docker rmi <image> : supprime la référence locale et libère les couches de stockage si aucun autre conteneur ni tag ne les utilise.

Exercice 1 — Calculateur de taille d’image et déduplication des Layers (OverlayFS)

Python Niveau 1 — Acquisition

Objectif : Calculer le stockage réel consommé sur le démon Docker grâce au partage de couches en lecture seule (UnionFS).

Le script lit sur l'entrée standard des lignes au format <NomImage> : <Layer1>:<TailleMo> , <Layer2>:<TailleMo> , ....
Dans le pilote de stockage Overlay2, chaque couche en lecture seule (identifiée par son ID unique) n'est stockée qu'une seule fois sur le disque hôte, quel que soit le nombre d'images qui s'appuient dessus.
Calculer :
1. La taille apparente de chaque image (somme de ses couches).
2. La taille brute totale cumulée (somme naïve sans partage).
3. La taille réelle stockée sur l'hôte (somme des couches uniques sans doublon).
4. L'économie d'espace réalisée (TailleBrute - TailleReelle).
Afficher :
IMAGE: <NomImage> -> TAILLE_APPARENTE: <T> Mo
... puis en fin d'exécution :
TOTAL_BRUT: <Tb> Mo | TOTAL_REEL: <Tr> Mo | ECONOMIE_DEDUPLICATION: -<Gain> Mo

Entrée du programme
NodeApp : base_os:100 , node_runtime:80 , app_code:20
PythonApp : base_os:100 , python_runtime:70 , app_code_py:15
Sortie attendue
IMAGE: NodeApp -> TAILLE_APPARENTE: 200 Mo
IMAGE: PythonApp -> TAILLE_APPARENTE: 185 Mo
TOTAL_BRUT: 385 Mo | TOTAL_REEL: 285 Mo | ECONOMIE_DEDUPLICATION: -100 Mo

La couche commune base_os (100 Mo) n’est stockée qu’une seule fois.

Deux indices, rédigés en mots
  1. Garder un dictionnaire des couches uniques (id_couche -> taille) pour la taille réelle.
  2. Faire attention aux espaces autour des deux-points et des virgules.

Exercice 2 — Parseur canonique de références d’images et de tags

Python Niveau 2 — Application

Objectif : Décomposer une référence d’image Docker en ses composantes normalisées : registre, namespace/nom, tag et digest SHA256.

Le script lit sur l'entrée standard des références d'images (une par ligne).
Règles de normalisation canonique :
1. Digest : si la référence contient @sha256:..., l'extraire (sinon NONE).
2. Tag : si la référence contient :<tag> (hors du digest), l'extraire (sinon valeur par défaut latest).
3. Registre & Nom :
- Si l'image contient un nom de domaine avec point (ex: ghcr.io/org/app ou docker.elastic.co/...), le registre est le premier segment avant le slash.
- Si l'image est officielle sans slash (ex: nginx, ubuntu), le registre est docker.io/library et le nom est l'image.
- Si l'image a un namespace simple (ex: monorg/monapp), le registre est docker.io et le nom est monorg/monapp.
Pour chaque référence, afficher :
REF: <entree> -> REGISTRE: <reg> | IMAGE: <nom> | TAG: <tag> | DIGEST: <digest>

Entrée du programme
nginx
ubuntu:22.04
myorg/backend:v1.0
ghcr.io/dev/api:latest@sha256:abcd1234ef
Sortie attendue
REF: nginx -> REGISTRE: docker.io/library | IMAGE: nginx | TAG: latest | DIGEST: NONE
REF: ubuntu:22.04 -> REGISTRE: docker.io/library | IMAGE: ubuntu | TAG: 22.04 | DIGEST: NONE
REF: myorg/backend:v1.0 -> REGISTRE: docker.io | IMAGE: myorg/backend | TAG: v1.0 | DIGEST: NONE
REF: ghcr.io/dev/api:latest@sha256:abcd1234ef -> REGISTRE: ghcr.io | IMAGE: dev/api | TAG: latest | DIGEST: sha256:abcd1234ef

Normalisation canonique conforme à la spécification Docker distribution.

Deux indices, rédigés en mots
  1. Traiter en premier l’éventuel digest après @.
  2. Extraire ensuite le tag après le dernier deux-points.
  3. Déterminer le registre selon la présence d’un point ou d’un slash.

Exercice 3 — Simulateur de stratégie Copy-On-Write (CoW) et couche conteneur

Python Niveau 3 — Raisonnement

Objectif : Simuler le fonctionnement du pilote de stockage OverlayFS lors des opérations de lecture, écriture et suppression.

Le script lit sur l'entrée standard :
- Première ligne : liste des fichiers existants dans l'image de base (séparés par des virgules).
- Lignes suivantes : opérations au format <ACTION> <CheminFichier> où ACTION vaut READ, WRITE, CREATE ou DELETE.
Comportement OverlayFS :
- READ :
* Si le fichier a déjà été modifié dans le conteneur : ACCES: Container Layer (Version modifiee)
* Sinon s'il est dans l'image : ACCES: Image Layer (Lecture directe RO sans duplication)
* Sinon ou s'il est marqué supprimé : ERREUR: Fichier introuvable (404 ENOENT)
- WRITE :
* S'il est dans l'image et pas encore copié : MECANISME: Copy-On-Write (Copie du fichier vers la Container Layer puis ecriture)
* S'il est déjà dans la Container Layer : MECANISME: Ecriture directe dans Container Layer
* Sinon : ERREUR: Fichier introuvable pour modification
- CREATE : MECANISME: Creation directe dans Container Layer (le fichier devient actif dans la couche conteneur).
- DELETE :
* S'il était dans l'image : MECANISME: Whiteout (Creation d'un fichier masque dans Container Layer sans toucher a l'image RO)
* S'il a été créé uniquement dans le conteneur : MECANISME: Suppression directe de Container Layer
Afficher :
<ACTION> <Chemin> -> <RESULTAT>

Entrée du programme
/etc/app.conf, /usr/bin/python, /var/log/old.log
READ /etc/app.conf
WRITE /etc/app.conf
READ /etc/app.conf
DELETE /var/log/old.log
READ /var/log/old.log
Sortie attendue
READ /etc/app.conf -> ACCES: Image Layer (Lecture directe RO sans duplication)
WRITE /etc/app.conf -> MECANISME: Copy-On-Write (Copie du fichier vers la Container Layer puis ecriture)
READ /etc/app.conf -> ACCES: Container Layer (Version modifiee)
DELETE /var/log/old.log -> MECANISME: Whiteout (Creation d'un fichier masque dans Container Layer sans toucher a l'image RO)
READ /var/log/old.log -> ERREUR: Fichier introuvable (404 ENOENT)

Démonstration complète de la mécanique Copy-On-Write et du masquage Whiteout.

Deux indices, rédigés en mots
  1. Gérer trois ensembles : fichiers dans l’image, fichiers copiés/créés dans le conteneur, fichiers supprimés (whiteout).
  2. Un fichier supprimé dans le conteneur ne peut plus être lu.

6. QCM — niveau examen

Que se passe-t-il au niveau du stockage lorsque deux images distinctes s’appuient toutes les deux sur la même image de base « alpine:3.18 » (7 Mo) ?

Chaque couche possède un identifiant de contenu SHA256 unique : si une couche existe déjà dans le cache du démon, elle est réutilisée sans duplication disque.

Dans l’architecture du pilote de stockage Overlay2, à quoi correspond le répertoire « upperdir » ?

upperdir est la couche supérieure inscriptible du conteneur où sont enregistrées toutes les écritures et modifications de fichiers.

Comment le système de fichiers OverlayFS gère-t-il la suppression par un conteneur d’un fichier appartenant à une couche d’image inférieure en lecture seule ?

Les couches inférieures sont immuables : OverlayFS crée un fichier spécial (whiteout) dans la couche supérieure pour cacher le fichier d’image sans l’effacer physiquement.

Pourquoi est-il fortement déconseillé d’utiliser le tag « :latest » pour les images de conteneurs déployées en production ?

latest est un simple pointeur mutable : il ne garantit aucune version précise et peut introduire des régressions ou des failles de sécurité lors d’un redémarrage de conteneur.

Quel est le moyen le plus sûr et le plus immuable pour référencer une image Docker de manière infalsifiable ?

Le digest SHA256 est calculé sur le manifeste exact de l’image : il garantit à 100 % que l’image exécutée correspond au binaire exact audité, sans risque de falsification.

Si une instruction RUN dans un Dockerfile crée un fichier de 500 Mo puis que l’instruction RUN suivante le supprime avec « rm », quel est l’impact sur la taille finale de l’image ?

Chaque ligne RUN crée une couche immuable scellée : supprimer un fichier dans une couche postérieure ne retire pas la donnée de la couche précédente dans l’historique.

Quelle commande Docker permet d’inspecter les couches successives d’une image et la taille ajoutée par chaque instruction ?

docker history liste l’empilement complet des layers de l’image avec la taille de chaque couche et l’instruction correspondante.

Où se situe le registre par défaut lorsque l’on télécharge une image officielle simple comme « redis » sans préfixe de domaine ?

Les images sans préfixe de registre sont automatiquement résolues vers le registre officiel Docker Hub sous l’espace officiel docker.io/library/.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Utiliser le tag :latest en production, entraînant des déploiements non déterministes et des pannes silencieuses.
  • Penser que supprimer un fichier dans une commande RUN ultérieure allège l’image : le fichier reste figé dans la couche précédente.
  • Confondre la taille apparente cumulée (docker images) et la taille physique réelle stockée sur le disque après déduplication.
  • Écrire des gigaoctets de logs directement dans la couche conteneur sans volume, saturant le disque système de l’hôte.

8. Méthodologie de résolution

Protocole d’Audit et d’Optimisation du Stockage d’Images Docker
  1. Étape 1 — Inventorier l’espace disque consommé : Exécuter la commande « docker system df » pour visualiser l’espace pris par les images, conteneurs et volumes.
  2. Étape 2 — Inspecter les couches d’une image : Lancer « docker history --no-trunc <image> » pour identifier les couches volumineuses et suspectes.
  3. Étape 3 — Rapatrier uniquement par version sémantique : Remplacer systématiquement tous les tags « latest » par des versions précises dans les manifestes.
  4. Étape 4 — Vérifier la déduplication Overlay2 : Constater dans « /var/lib/docker/overlay2/ » que les couches communes ne sont pas dupliquées.
  5. Étape 5 — Épingler les digests critiques : Récupérer le digest cryptographique SHA256 avec « docker inspect --format="{{index .RepoDigests 0}}" <image> ».
  6. Étape 6 — Purger les couches orphelines : Nettoyer les images non référencées et sans conteneur actif avec « docker image prune -a ».

9. Révision active

Résumé essentiel
  • Une image Docker est un assemblage immuable de couches en lecture seule (Image Layers) superposées.
  • Le pilote Overlay2 fusionne les lowerdir (couches d’images) et l’upperdir (couche Writable du conteneur) dans merged.
  • La stratégie Copy-On-Write (CoW) copie un fichier dans la couche conteneur uniquement lors de sa première tentative de modification.
  • La suppression d’un fichier de l’image de base crée un fichier masquant (whiteout) dans la couche conteneur sans effacer la donnée de l’image.
  • Les couches communes partagent le même hash SHA256 et ne sont stockées qu’une seule fois sur la machine hôte.
  • Le tag « latest » est flottant et imprévisible : les déploiements de production doivent privilégier des tags sémantiques ou des digests SHA256.

  • Je sais pourquoi le tag latest est formellement banni en environnement de production.
