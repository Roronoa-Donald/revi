Chapitre 3 — Dockerfile, Directives & Optimisation Multi-Stage

Module 3 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Une équipe de développeurs livre une image Docker pour une application écrite en Go. L’image pèse 1,4 Go en production et intègre le compilateur Go complet, l’historique git, les outils de build gcc et les codes sources complets. Un audit de sécurité automatisé (scanner Trivy) relève plus de 180 vulnérabilités critiques liées aux utilitaires système embarqués inutilement dans l’image de production. De plus, chaque modification d’une seule ligne de code oblige Docker à réinstaller l’intégralité des dépendances pendant 15 minutes faute d’un ordre de couches réfléchi. Ce module forme les étudiants à écrire des Dockerfiles professionnels, ultra-rapides à compiler grâce au cache, et à diviser par cinquante la taille et la surface de vulnérabilité de leurs images grâce au pattern Multi-Stage Build.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. maîtriser la syntaxe et les directives fondamentales du Dockerfile (FROM, WORKDIR, COPY, RUN, ENV, ARG, EXPOSE, USER) ;
  2. comprendre l’invalidation du cache de build et ordonner les couches du moins changeant au plus changeant ;
  3. filtrer rigoureusement les fichiers sensibles et temporaires grâce au fichier .dockerignore ;
  4. distinguer rigoureusement la forme exec (JSON) de la forme shell pour CMD et ENTRYPOINT ;
  5. garantir la bonne transmission des signaux d’arrêt UNIX (SIGTERM) au processus conteneurisé ;
  6. concevoir une architecture de build Multi-Stage séparant l’environnement de compilation du runtime de production.

1. Directives Clés du Dockerfile et Bonnes Pratiques

Le Dockerfile est la recette déclarative d’assemblage d’une image Docker. Chaque directive doit être choisie avec rigueur technique :

Directive Rôle Bonne pratique recommandée
FROM Définit l’image de départ (Base Image). Toujours spécifier une version explicite (ex: node:20-alpine) plutôt qu’un tag flottant.
WORKDIR Définit le répertoire de travail pour les commandes suivantes. Toujours utiliser un chemin absolu (ex: WORKDIR /app). Ne jamais enchaîner de cd manuels.
COPY Copie des fichiers ou dossiers depuis la machine hôte vers l’image. Préférer COPY à ADD pour les fichiers locaux afin d’éviter les effets de bord d’extraction automatique.
ADD Copie avec décompression automatique d’archives tar locales ou téléchargement d’URL. À réserver exclusivement pour décompresser une archive tar locale directement dans l’image.
RUN Exécutez une commande shell lors de la construction et scelle une couche. Chaîner les commandes avec && et nettoyer les caches de paquets dans la même instruction.
ENV vs ARG Variables de configuration. ARG existe uniquement pendant le build ; ENV persiste dans l’image et au runtime du conteneur.
EXPOSE Documentation du port d’écoute. Purement informatif pour les développeurs, ne publie aucun port sur l’hôte (contrairement à -p).

2. Optimisation du Build Cache et Fichier .dockerignore

Lors de l’exécution de docker build, Docker réutilise les couches déjà compilées si aucun fichier ni paramètre n’a changé en amont. Dès qu’une couche est invalidée, toutes les couches suivantes doivent être entièrement recalculées :

Anti-pattern : Invalidation Permanente du Cache

FROM node:18-alpine
WORKDIR /app
COPY . .  # <-- Erreur ! Modifie a chaque commit
RUN npm install # Se relance a chaque modification du code !

Le développeur modifie une ligne de commentaire dans son code source : COPY . . change, le cache est brisé, et npm install doit retélécharger 800 Mo de dépendances à chaque fois.

Pattern Optimal : Isolation des Dépendances

FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production  # En cache si package.json inchange
COPY . .
CMD ["node", "server.js"]

npm ci reste parfaitement en cache tant que les dépendances n’ont pas été modifiées. Le build ne prend alors que 2 secondes !

Le Fichier .dockerignore

Tout comme .gitignore, le fichier .dockerignore empêche l’envoi de fichiers indésirables dans le contexte de build envoyé au démon Docker : excluez systématiquement les dossiers .git, les dépendances locales node_modules ou venv, les fichiers secrets .env et les journaux de logs.

3. CMD vs ENTRYPOINT : Forme Exec (JSON) vs Forme Shell

L’une des erreurs les plus fréquentes concerne le lancement du processus conteneurisé. Deux formes de syntaxe coexistent :

Syntaxe Exemple Comportement du Système Transmission des Signaux UNIX
Forme Exec (Recommandée) CMD ["node", "app.js"] Exécutez directement le binaire node qui devient le PID 1 du conteneur. Parfaite : Reçoit directement les signaux SIGTERM émis par docker stop pour s’arrêter proprement.
Forme Shell (Anti-pattern) CMD node app.js Enveloppe la commande dans un sous-shell : /bin/sh -c "node app.js". Défaillante : Le shell est PID 1 et ne transmet pas SIGTERM au processus fils. Le conteneur se fige pendant 10s avant d’être tué brutalement par SIGKILL.

Combinaison ENTRYPOINT + CMD :

# ENTRYPOINT fixe le binaire de base inaltérable :
ENTRYPOINT ["python", "main.py"]
# CMD fournit les arguments par défaut substituables :
CMD ["--port", "8080"]

# Un "docker run monapp" executera : python main.py --port 8080
# Un "docker run monapp --debug" executera : python main.py --debug

4. Le Pattern Révolutionnaire du Multi-Stage Build

Introduit dans Docker 17.05, le Multi-Stage Build permet d’utiliser plusieurs instructions FROM dans un même Dockerfile afin d’isoler hermétiquement l’environnement de compilation de l’image finale de production :

# --- Étape 1 : Environnement de compilation lourd (Build Stage) ---
FROM golang:1.21-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /bin/monapp .

# --- Étape 2 : Image minimale de production (Final Stage) ---
FROM alpine:3.18
RUN adduser -D -u 10001 appuser
WORKDIR /app
# On copie UNIQUEMENT le binaire final depuis l'étape builder :
COPY --from=builder /bin/monapp /app/monapp
USER appuser
EXPOSE 8080
CMD ["/app/monapp"]
Bénéfice Stratégique du Multi-Stage

Le compilateur Go, le code source brut, les outils git et les fichiers intermédiaires sont tous abandonnés dans l’étape 1. L’image finale ne contient que le binaire statique de 15 Mo sur une base Alpine de 7 Mo, soit 22 Mo au lieu de 900 Mo. Les pirates ne trouvent ni compilateur ni outils de débogage dans le conteneur en cas d’intrusion.

Exercice 1 — Validateur et linter de bonnes pratiques Dockerfile

Bash Niveau 1 — Acquisition

Objectif : Analyser statiquement les instructions d’un Dockerfile et détecter les anti-patterns courants.

Le script Bash lit les paramètres sur l’entrée standard (stdin).
Règles d'audit et de conformité :
1. Première instruction non-commentaire : DOIT être FROM (ou ARG). Si absent : ERREUR_CRITIQUE: Dockerfile doit debuter par FROM.
2. Anti-pattern ADD : si une ligne commence par ADD avec un fichier local simple (.txt, .js, .py, etc. sans .tar/.gz/.zip ni URL http) : afficher AVERTISSEMENT [Ligne N]: Preferer COPY a ADD pour les fichiers locaux.
3. Anti-pattern Cache Apt : si RUN apt-get update est présent seul sans apt-get install sur la même instruction chaînée : afficher AVERTISSEMENT [Ligne N]: RUN apt-get update isole (fusionner avec install et rm -rf /var/lib/apt/lists/*).
4. Si aucun problème n'est détecté : afficher AUDIT_DOCKERFILE: CONFORME (Aucun anti-pattern detecte).
Sinon, affichezzr AUDIT_DOCKERFILE: NON_CONFORME (<K> avertissement(s)).

Entrée du programme
# Mon Dockerfile de production
FROM node:18-alpine
ADD package.json .
RUN npm install
COPY . .
CMD ["node", "server.js"]
Sortie attendue
AVERTISSEMENT [Ligne 3]: Preferer COPY a ADD pour les fichiers locaux
AUDIT_DOCKERFILE: NON_CONFORME (1 avertissement(s))

ADD est déconseillé pour copier de simples fichiers locaux.

Deux indices, rédigés en mots
  1. Ignorer les lignes commençant par # (commentaires).
  2. Identifier les chaînes locales dans ADD (absence de http/tar/gz).

Exercice 2 — Distributeur de commandes CMD vs ENTRYPOINT

Bash Niveau 2 — Application

Objectif : Calculer la ligne de commande finale exacte exécutée dans le conteneur selon la présence de ENTRYPOINT, CMD et arguments CLI.

Le script Bash lit les paramètres sur l’entrée standard (stdin). ENTRYPOINT: <liste d'arguments séparés par des virgules ou NONE>
2. CMD: <liste d'arguments séparés par des virgules ou NONE>
3. CLI_ARGS: <arguments passés à docker run séparés par des virgules ou NONE>
Règles d'évaluation du runtime Docker :
- Si CLI_ARGS n'est pas NONE, il écrase complètement CMD.
- Si ENTRYPOINT n'est pas NONE : la commande finale est la concaténation de ENTRYPOINT + (CLI_ARGS s'il existe, sinon CMD si présent).
- Si ENTRYPOINT est NONE : la commande finale est CLI_ARGS (s'il existe) sinon CMD.
Afficher la commande résultante (arguments joints par des espaces) :
COMMANDE_FINALE: <cmd1> <cmd2> ...

Entrée du programme
ENTRYPOINT: python, app.py
CMD: --port, 8080
CLI_ARGS: NONE
Sortie attendue
COMMANDE_FINALE: python app.py --port 8080

ENTRYPOINT et CMD sont combinés par défaut.

Deux indices, rédigés en mots
  1. Traiter la valeur spéciale NONE comme une liste vide.
  2. Les arguments passés en ligne de commande remplacent systématiquement l’instruction CMD.

Exercice 3 — Optimiseur de cache et build Multi-Stage

Bash Niveau 3 — Raisonnement

Objectif : Quantifier l’allègement drastique d’image obtenu par le pattern Multi-Stage Build face à une construction monolithique.

Le script Bash lit les paramètres sur l’entrée standard (stdin).
- Ligne 2 : STAGE_BUILD: <NomBaseBuild> <TailleTotalBuildMo> -> EXPORT: <BinaireProduitMo>.
- Ligne 3 : STAGE_FINAL: <NomBaseLegere> <TailleBaseLegereMo> + IMPORT: <BinaireProduitMo>.
Calculer :
1. Taille totale de l'image monolithique = TailleBaseMo + OutilsDevMo + CodeMo + BinaireProduitMo.
2. Taille de l'image finale issue du multi-stage = TailleBaseLegereMo + BinaireProduitMo.
3. Réduction brute = TailleMono - TailleMulti (en Mo).
4. Pourcentage d'économie = (Reduction / TailleMono) * 100 (arrondi à 1 décimale).
Afficher :
IMAGE_MONOLITHIQUE: <Tmono> Mo
IMAGE_MULTI_STAGE: <Tmulti> Mo
GAIN_SECURITE_ET_TAILLE: -<Red> Mo (<Pct:.1f>% economises)

Entrée du programme
MONOLITHIC: golang:1.21 800 + 150 + 10 + 20
STAGE_BUILD: golang:1.21 980 -> EXPORT: 20
STAGE_FINAL: alpine:3.18 7 + IMPORT: 20
Sortie attendue
IMAGE_MONOLITHIQUE: 980 Mo
IMAGE_MULTI_STAGE: 27 Mo
GAIN_SECURITE_ET_TAILLE: -953 Mo (97.2% economises)

Une application Go compilée passe de près de 1 Go à 27 Mo.

Deux indices, rédigés en mots
  1. Seule la dernière étape (STAGE_FINAL) est embarquée dans l’image finale distribuée.
  2. Les compilateurs et codes sources de build sont jetés.

6. QCM — niveau examen

Pourquoi est-il crucial de copier le fichier « package.json » et de lancer « npm install » AVANT de copier le reste du code source applicatif ?

Si vous copiez tout le code en premier, la moindre retouche de code invalide le cache et force une réinstallation lente des paquets npm à chaque build.

Quelle est la conséquence critique de l’utilisation de la forme shell « CMD node server.js » par rapport à la forme exec « CMD ["node", "server.js"] » ?

En forme shell, /bin/sh est le PID 1 et n’achemine pas les signaux système à ses processus fils, empêchant l’application de fermer proprement ses connexions et fichiers.

À quoi sert le pattern du Multi-Stage Build dans un Dockerfile moderne ?

Le Multi-Stage Build isole les outils de build volumineux (compilateurs, SDK) dans un stage temporaire et ne conserve que le résultat compilé dans l’image finale de production.

Quelle directive Dockerfile doit-on privilégier pour copier un fichier simple du disque hôte vers le conteneur sans comportement magique inattendu ?

COPY est explicite, transparente et sans surprise. ADD réalise des décompressions automatiques d’archives tar et accepte des URL distantes, ce qui est souvent source d’erreurs.

Quelle instruction permet de définir l’utilisateur sous lequel toutes les commandes suivantes du Dockerfile et le conteneur lui-même s’exécuteront ?

L’instruction USER spécifie le nom d’utilisateur (ou l’UID) pour l’exécution des instructions RUN, CMD et ENTRYPOINT restantes.

Quelle est la différence fondamentale entre les instructions ARG et ENV dans un Dockerfile ?

ARG définit des variables d’étape de build non transmises au conteneur au runtime. ENV inscrit des variables d’environnement persistantes dans l’image.

Quel fichier permet d’exclure le dossier « .git » et les fichiers secrets de l’envoi au contexte de build du démon Docker ?

Le fichier .dockerignore à la racine du projet fonctionne comme .gitignore et évite d’envoyer des fichiers volumineux ou sensibles au démon lors du build.

Si un Dockerfile définit ENTRYPOINT ["nginx"] et CMD ["-g", "daemon off;"], que se passe-t-il si l’utilisateur exécute « docker run mon-nginx -v » ?

ENTRYPOINT reste le préfixe fixe de la commande, et tout argument fourni en CLI vient écraser les arguments de CMD.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Copier l’intégralité des sources avant d’installer les dépendances (ex: COPY . . avant npm install), brisant le cache à chaque modification.
  • Utiliser la forme shell pour CMD (ex: CMD python app.py) : le conteneur ne répond pas au signal SIGTERM de docker stop.
  • Laisser traîner des clés SSH, des jetons API ou des fichiers .env dans les couches de l’image.
  • Oublier de nettoyer les caches de paquets apt ou pip dans la même instruction RUN que l’installation.
  • Livrer un compilateur lourd (Go, JDK, Rust) dans l’image de production au lieu d’utiliser un Multi-Stage Build.

8. Méthodologie de résolution

Protocole de Conception d’un Dockerfile Optimisé et Sécurisé
  1. Étape 1 — Créer le fichier .dockerignore : Écarter immédiatement les répertoires .git, tests, .env et caches locaux.
  2. Étape 2 — Choisir une image de base minimale : Opter pour une variante Alpine Linux (musl) ou Debian-Slim selon les contraintes de glibc.
  3. Étape 3 — Structurer l’ordre des couches de dépendances : Copier les manifestes de paquets (package.json, requirements.txt, go.mod) et installer les dépendances avant de copier le reste du code.
  4. Étape 4 — Chaîner et nettoyer les commandes RUN : Fusionner les étapes d’installation système avec la purge immédiate des listes de paquets temporaires.
  5. Étape 5 — Créer et basculer sur un utilisateur non-root : Déclarer un utilisateur dédié avec l’instruction « USER » pour abandonner les privilèges d’administration.
  6. Étape 6 — Adopter la forme JSON exec pour le point d’entrée : Spécifier la commande de lancement sous forme de tableau JSON strict pour intercepter les signaux SIGTERM.

9. Révision active

Résumé essentiel
  • Le Dockerfile assemble une image de façon déclarative à travers une suite d’instructions ordonnées.
  • Les couches doivent être ordonnées du moins changeant au plus changeant pour maximiser l’efficacité du Build Cache.
  • Le fichier .dockerignore préserve le contexte de build en filtrant les fichiers secrets, volumineux ou inutiles.
  • Toujours utiliser la forme Exec (JSON) pour CMD et ENTRYPOINT pour que le processus reçoive les signaux UNIX (SIGTERM).
  • La directive ADD ne doit être utilisée que pour l’extraction automatique d’archives tar locales ; préférer COPY dans tous les autres cas.
  • Le Multi-Stage Build isole les compilateurs dans une étape transitoire et garantit une image finale ultralégère et sécurisée.

Checklist de maîtrise

  • Je comprends la différence fondamentale entre la directive COPY et la directive ADD.
  • Je sais pourquoi le cache est invalidé dès qu’un fichier copié est modifié.
  • J’ai configuré un fichier .dockerignore pour exclure .git et les dépendances locales.
  • Je sais pourquoi CMD ["node", "app.js"] est infiniment supérieur à CMD node app.js.
  • Je sais combiner ENTRYPOINT pour fixer l’exécutable et CMD pour fournir des arguments modifiables.
  • Je maîtrise l’instruction COPY --from=builder pour extraire des binaires compilés dans une étape finale légère.
