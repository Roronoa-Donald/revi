Chapitre 4 — Cycle de Vie des Conteneurs, Réseau & Stockage

Module 4 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Un développeur junior configure une base de données PostgreSQL dans un conteneur pour une application critique. Au bout de trois semaines de saisie de données par les utilisateurs, le serveur hôte redémarre et l’administrateur exécute la commande « docker rm -f postgres » pour mettre à niveau l’image. Catastrophe absolue : la totalité des données clients est anéantie instantanément car les fichiers résidaient dans la couche Writable volatile du conteneur sans aucun montage de volume persistant ! Au même moment, les autres services de l’entreprise ne parviennent plus à communiquer avec l’API car celle-ci a changé d’adresse IP privée lors du redémarrage sur le bridge par défaut non routé. Ce module forme les étudiants à maîtriser rigoureusement le cycle de vie d’un conteneur, à configurer des réseaux virtuels sécurisés avec découverte automatique par nom d’hôte, et à garantir la persistance intégrale des données d’entreprise à travers les volumes managés.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. modéliser la machine à états finis du cycle de vie d’un conteneur (Created, Running, Paused, Stopped, Removed) ;
  2. maîtriser les commandes de pilotage opérationnel (run, exec, stop, kill, restart, logs, inspect, rm) ;
  3. comprendre le fonctionnement de la publication de ports via les tables de translation NAT iptables ;
  4. distinguer les modes réseau Docker (Bridge, Host, None) et exploiter le DNS interne (127.0.0.11) ;
  5. comparer et choisir judicieusement entre Volumes Docker nommés, Bind Mounts et montages Tmpfs ;
  6. sécuriser les montages de fichiers sensibles à l’aide du mode lecture seule (:ro).

1. Machine à États Finis et Commandes du Cycle de Vie

Un conteneur Docker traverse des états strictement définis au cours de son existence :

État Description système Commandes déclenchantes
Created Le conteneur est instancié avec ses couches, son réseau et ses cgroups réservés, mais le processus applicatif n’est pas encore lancé. docker create
Running Le processus principal (PID 1) s’exécute activement dans ses namespaces. docker run, docker start, docker unpause
Paused Tous les processus du conteneur sont gelés au niveau du cgroup freezer (consommation CPU = 0). docker pause
Stopped (Exited) Le processus principal a terminé son exécution ou a été arrêté via un signal. Le système de fichiers est préservé. docker stop, docker kill
Dead / Removed Le conteneur et sa couche Writable ont été effacés du système de fichiers de l’hôte. docker rm
Différence Cruciale entre docker stop et docker kill

docker stop envoie d’abord le signal d’arrêt propre SIGTERM (15) au processus PID 1, lui laissant un délai de grâce de 10 secondes pour fermer les connexions de base de données et vider ses buffers. Ce n’est qu’après ce délai que Docker envoie SIGKILL (9). À l’inverse, docker kill abat immédiatement le processus par SIGKILL sans aucun préavis, au risque de corrompre des fichiers en cours d’écriture.

2. Réseaux Docker, Port Mapping et DNS Intégré

Par défaut, Docker isole le conteneur dans son propre NET Namespace. Pour communiquer avec le monde extérieur et avec d’autres conteneurs, plusieurs modes existent :

Bridge Network (Par Défaut)

Créez une interface pont virtuelle (comme docker0) et attribue une adresse IP privée (ex: 172.17.0.X) à chaque conteneur. L’accès extérieur s’effectue par translation d’adresses NAT.

Host Network (--network=host)

Désactive l’isolation réseau : le conteneur partage directement la pile réseau et les ports de la machine hôte. Performances maximales mais suppression du cloisonnement de sécurité.

None Network (--network=none)

Isole totalement le conteneur du réseau : seule l’interface de boucle locale lo est disponible. Idéal pour des calculs ultra-sécurisés ou des traitements batch fermés.

La Règle d’Or du Réseau Bridge Personnalisé

Sur le réseau bridge par défaut historique (docker0), les conteneurs ne peuvent pas se joindre par leur nom d’hôte : il faut obligatoirement connaître leur adresse IP changeante. À l’inverse, dès que vous créez un réseau bridge personnalisé (docker network create mon-reseau), Docker active son serveur DNS interne intégré (127.0.0.11) : les conteneurs connectés à ce réseau peuvent alors communiquer simplement en utilisant leur nom de conteneur comme nom d’hôte (ex: curl http://api-service:8080).

3. Persistance des Données : Volumes Nommés vs Bind Mounts vs Tmpfs

Tout fichier créé à l’intérieur d’un conteneur sans configuration de montage est stocké dans la couche Writable volatile et disparaît définitivement lors de la destruction du conteneur. Docker propose trois architectures de persistance :

Type de Montage Syntaxe CLI Emplacement Physique Cas d’Usage Idéal
Volume Nommé -v pgdata:/var/lib/postgresql/data Géré entièrement par le démon Docker dans /var/lib/docker/volumes/ sur l’hôte. Production & Bases de Données : Performance optimale, isolation du système hôte, sauvegardes facilitées, survit à la destruction du conteneur.
Bind Mount -v /home/user/app:/app Lié directement à un fichier ou répertoire arbitraire existant sur la machine hôte. Développement : Partage du code source hôte pour rechargement à chaud (Hot Reloading) ou injection de fichiers de configuration hôte.
Tmpfs Mount --tmpfs /tmp Alloué exclusivement dans la mémoire vive RAM de la machine hôte. Sécurité & Données Temporaires : Fichiers éphémères, jetons secrets qui ne doivent jamais toucher le disque dur physique.

4. Commandes d’Exécution et Diagnostic en Production

Pour diagnostiquer et manipuler les conteneurs actifs :

  • docker exec -it mon_conteneur /bin/bash : entre dans un conteneur en cours d’exécution sans interrompre son service.
  • docker logs -f --tail 50 mon_conteneur : suit en direct les journaux émis sur les flux stdout et stderr.
  • docker top mon_conteneur : liste les processus actifs à l’intérieur du conteneur avec leur PID hôte.
  • docker stats : moniteur de performances en temps réel affichant la consommation CPU, RAM, réseau et E/S de tous les conteneurs.

Exercice 1 — Gestionnaire d’états du cycle de vie d’un conteneur

Bash Niveau 1 — Acquisition

Objectif : Simuler la machine à états finis du cycle de vie d’un conteneur Docker et valider les transitions de commandes.

Le script Bash lit les paramètres sur l’entrée standard (stdin).
États possibles : ABSENT, CREATED, RUNNING, PAUSED, STOPPED.
Règles de transition :
- Depuis ABSENT : create -> CREATED, run -> RUNNING.
- Depuis CREATED : start -> RUNNING, rm -> ABSENT.
- Depuis RUNNING : pause -> PAUSED, stop -> STOPPED, restart -> RUNNING, kill -> STOPPED.
- Depuis PAUSED : unpause -> RUNNING.
- Depuis STOPPED : start -> RUNNING, rm -> ABSENT.
- Si une commande rm est tentée sur RUNNING ou PAUSED sans option force : afficher TRANSITION_INVALIDE: Impossible de supprimer un conteneur actif sans --force (Etat: <ETAT>).
- Pour toute autre action invalide : afficher TRANSITION_INVALIDE: Action <cmd> impossible depuis l'etat <ETAT>.
- Si la transition est valide, afficher :
<CMD> -> NOUVEL_ETAT: <NOUVEL_ETAT>

Entrée du programme
create
start
pause
unpause
stop
rm
Sortie attendue
create -> NOUVEL_ETAT: CREATED
start -> NOUVEL_ETAT: RUNNING
pause -> NOUVEL_ETAT: PAUSED
unpause -> NOUVEL_ETAT: RUNNING
stop -> NOUVEL_ETAT: STOPPED
rm -> NOUVEL_ETAT: ABSENT

Cycle de vie complet et nominal d’un conteneur.

Deux indices, rédigés en mots
  1. Initialiser l’état à ABSENT.
  2. Gérer scrupuleusement les conditions de rejet.

Exercice 2 — Simulateur de redirection de ports (Port Mapping NAT) et conflits

Bash Niveau 2 — Application

Objectif : Simuler la table de translation d’adresses NAT et détecter les collisions de ports hôte.

Le script Bash lit les paramètres sur l’entrée standard (stdin).
Formulats de publication :
- HotePort:ConteneurPort -> IP par défaut 0.0.0.0.
- IP:HotePort:ConteneurPort.
Règles de validation :
- Une paire (IP_Hote, HotePort) ne peut être allouée qu'à un seul conteneur. (L'IP 0.0.0.0 entre en conflit avec n'importe quelle IP spécifique sur le même port).
- Si le port est libre : enregistrer la règle et afficher :
PUBLICATION: <Conteneur> -> NAT: <IP>:<HotePort> => <ConteneurPort>/tcp (SUCCES)
- S'il y a conflit de port sur l'hôte : afficher :
CONFLIT_PORT: <Conteneur> -> Port hote <HotePort> deja reserve par <ConteneurPrecedent> (ECHEC)

Entrée du programme
web_nginx 8080:80
api_node 3000:3000
autre_nginx 8080:80
Sortie attendue
PUBLICATION: web_nginx -> NAT: 0.0.0.0:8080 => 80/tcp (SUCCES)
PUBLICATION: api_node -> NAT: 0.0.0.0:3000 => 3000/tcp (SUCCES)
CONFLIT_PORT: autre_nginx -> Port hote 8080 deja reserve par web_nginx (ECHEC)

Le port 8080 est déjà réservé par le premier conteneur.

Deux indices, rédigés en mots
  1. Gérer un dictionnaire associant (port) ou (ip, port) au conteneur propriétaire.
  2. 0.0.0.0 écoute sur toutes les interfaces.

Exercice 3 — Audit de persistance des données : Volumes nommés vs Bind Mounts vs Tmpfs

Bash Niveau 3 — Raisonnement

Objectif : Qualifier la nature, la persistance et les droits d’accès des options de stockage Docker (-v, --mount, --tmpfs).

Le script Bash lit les paramètres sur l’entrée standard (stdin).
Règles d'analyse :
1. --tmpfs <cible> :
- Type : TMPFS
- Localisation : Memoire vive RAM de l'hote
- Persistance : VOLATILE (detruit a l'arret du conteneur)
- Droits : LECTURE_ECRITURE
2. -v <source>:<cible>[:<opt>] :
- Si source commence par /, ./ ou ../ : Type BIND_MOUNT, Localisation Repertoire specifique de la machine hote.
- Sinon : Type VOLUME_NOMME, Localisation Espace reserve du daemon (/var/lib/docker/volumes/).
- Persistance : PERSISTANT (survit a docker rm).
- Droits : LECTURE_SEULE si :ro est spécifié, sinon LECTURE_ECRITURE.
Afficher :
STOCKAGE: <entree> -> TYPE: <TYPE> | <LOCALISATION> | <PERSISTANCE> | <DROITS>

Entrée du programme
-v db_data:/var/lib/mysql
-v /etc/nginx/nginx.conf:/etc/nginx/nginx.conf:ro
--tmpfs /tmp
Sortie attendue
STOCKAGE: -v db_data:/var/lib/mysql -> TYPE: VOLUME_NOMME | Espace reserve du daemon (/var/lib/docker/volumes/) | PERSISTANT (survit a docker rm) | LECTURE_ECRITURE
STOCKAGE: -v /etc/nginx/nginx.conf:/etc/nginx/nginx.conf:ro -> TYPE: BIND_MOUNT | Repertoire specifique de la machine hote | PERSISTANT (survit a docker rm) | LECTURE_SEULE
STOCKAGE: --tmpfs /tmp -> TYPE: TMPFS | Memoire vive RAM de l'hote | VOLATILE (detruit a l'arret du conteneur) | LECTURE_ECRITURE

Distinction formelle des 3 mécanismes de stockage sous Docker.

Deux indices, rédigés en mots
  1. Un chemin absolu ou relatif indique un Bind Mount.
  2. Un identifiant sans slash indique un volume Docker nommé.

6. QCM — niveau examen

Quel signal UNIX la commande « docker stop » envoie-t-elle initialement au processus principal du conteneur pour demander un arrêt propre ?

docker stop envoie SIGTERM (signal 15). Si le conteneur ne s’arrête pas dans le délai de grâce (10 secondes par défaut), Docker émet alors un SIGKILL (signal 9).

Pourquoi est-il fortement recommandé de créer un réseau bridge personnalisé (docker network create) plutôt que d’utiliser le bridge par défaut « docker0 » ?

Sur un réseau bridge personnalisé, Docker active un serveur DNS embarqué (127.0.0.11) qui résout automatiquement les noms de conteneurs en adresses IP.

Où sont physiquement stockées les données d’un Volume Nommé Docker (ex: « docker volume create mon_vol ») sur un système Linux ?

Docker isole les volumes nommés sous /var/lib/docker/volumes/<nom_volume>/_data, préservant ainsi les données en toute sécurité même si les conteneurs sont supprimés.

Quelle option de la commande « docker run » permet de mapper le port 8080 de la machine hôte vers le port 80 à l’intérieur du conteneur ?

L’option -p 8080:80 (ou --publish) ordonne à Docker de configurer les règles iptables pour transférer les paquets arrivant sur le port 8080 de l’hôte vers le port 80 du conteneur.

Quelle commande permet d’ouvrir un terminal interactif dans un conteneur déjà en cours d’exécution sans l’arrêter ni le redémarrer ?

docker exec lance un nouveau processus fils dans les namespaces du conteneur existant, ce qui est idéal pour inspecter l’environnement en direct.

Que caractérise un montage de type « Tmpfs » (--tmpfs /tmp) sous Docker ?

Tmpfs crée un point de montage en RAM pure : les écritures sont ultra-rapides et aucune trace n’est conservée sur le disque physique lors de l’extinction du conteneur.

Comment rendre un point de montage Bind Mount strictement en lecture seule afin que le conteneur ne puisse pas modifier les fichiers hôtes ?

L’option :ro (read-only) indique au noyau Linux de monter le répertoire avec l’attribut de lecture seule, empêchant tout conteneur compromis d’altérer les fichiers de l’hôte.

Quelle commande permet de visualiser en direct les flux stdout et stderr émis par une application conteneurisée ?

docker logs affiche la journalisation capturée par le driver de logs de Docker, et le drapeau -f (follow) permet de suivre le flux continu en temps réel.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Oublier de créer un volume pour une base de données : toutes les données sont perdues au prochain docker rm.
  • Utiliser le bridge par défaut et tenter de contacter un conteneur par son nom : la résolution DNS échoue silencieusement.
  • Utiliser -p 80:80 sur plusieurs conteneurs simultanément, provoquant un conflit de port hôte bloquant.
  • Donner un accès Bind Mount en lecture-écriture à la racine de l’hôte physique (ex: -v /:/host:rw).
  • Faire un docker kill systématique au lieu de docker stop, corrompant les transactions de base de données en cours.

8. Méthodologie de résolution

Protocole de Déploiement d’un Service avec Réseau et Volume Sécurisé
  1. Étape 1 — Créer un réseau bridge dédié : Isoler le trafic en exécutant « docker network create app-network ».
  2. Étape 2 — Créer un volume de stockage persistant : Déclarer un volume managé indépendant avec « docker volume create db-data ».
  3. Étape 3 — Instancier le conteneur de base de données : Lancer le conteneur sur le réseau privé avec « docker run -d --name database --network app-network -v db-data:/var/lib/postgresql/data -e POSTGRES_PASSWORD=secret postgres:15-alpine ».
  4. Étape 4 — Instancier l’application cliente : Lancer l’API sur le même réseau « docker run -d --name api --network app-network -p 8080:8080 -e DB_HOST=database mon-api:v1 ».
  5. Étape 5 — Valider la résolution DNS et l’accès réseau : Tester la liaison avec « docker exec -it api ping -c 2 database ».
  6. Étape 6 — Tester la résilience des données : Supprimer puis recréer le conteneur de base de données et constater que l’intégralité des données est intacte grâce au volume db-data.

9. Révision active

Résumé essentiel
  • Un conteneur transite entre les états Created, Running, Paused, Stopped et Removed.
  • docker stop envoie un SIGTERM avec 10s de délai de grâce ; docker kill foudroie immédiatement le processus par SIGKILL.
  • La publication de ports (-p Host:Conteneur) configure les tables NAT iptables de la machine hôte.
  • Les réseaux bridge personnalisés activent un serveur DNS interne à 127.0.0.11 permettant la résolution automatique par nom.
  • Les volumes nommés sont gérés par Docker et garantissent la persistance des bases de données lors des mises à niveau.
  • Les Bind Mounts exposent directement le système de fichiers de l’hôte, idéaux en développement mais risqués en production.

Checklist de maîtrise

  • Je comprends pourquoi supprimer un conteneur non persistant efface toutes ses données locales.
  • Je sais expliquer la différence entre SIGTERM (15) et SIGKILL (9).
  • Je sais comment fonctionne la translation d’adresse NAT lors de l’usage du flag -p.
  • Je sais pourquoi un réseau bridge personnalisé est indispensable pour que deux conteneurs communiquent par leur nom.
  • Je sais différencier les 3 solutions de stockage : Volume nommé, Bind Mount et Tmpfs.
  • Je sais entrer dans un conteneur en cours d’exécution avec docker exec -it.

Les 8 notions à connaître absolument

  1. Cycle de vie (Created, Running, Paused, Stopped)
  2. Signaux UNIX SIGTERM (15) vs SIGKILL (9)
  3. Publication de ports et redirection NAT iptables
  4. Réseau Bridge par défaut vs personnalisé
  5. Serveur DNS interne Docker (127.0.0.11)
  6. Volumes nommés gérés (/var/lib/docker/volumes)
  7. Bind Mounts et mode lecture seule (:ro)
  8. Stockage éphémère en mémoire vive Tmpfs
