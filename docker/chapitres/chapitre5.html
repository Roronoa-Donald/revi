Chapitre 5 — Orchestration avec Docker Compose

Module 5 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Dans une start-up en pleine expansion, le déploiement de l’application sur la machine de test nécessite d’exécuter à la main un script shell complexe contenant 14 commandes « docker run » consécutives avec des dizaines de variables d’environnement, des ports et des volumes en ligne de commande. Régulièrement, un développeur oublie un argument ou lance l’API avant la base de données, provoquant des crashs en cascade. De plus, nettoyer l’environnement demande d’arrêter et supprimer chaque conteneur un par un. Pour professionnaliser ce flux de travail, l’équipe décide de standardiser l’ensemble de la pile sous Docker Compose. Ce module forme les étudiants à modéliser des architectures multi-services déclaratives, à orchestrer le cycle de vie applicatif d’une seule commande (« docker compose up -d »), et à fiabiliser les dépendances de démarrage à l’aide de sondes de santé (Healthchecks).

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. comprendre l’apport de l’approche déclarative (Infrastructure as Code) face aux scripts impératifs docker run ;
  2. structurer un fichier docker-compose.yml complet (sections services, networks, volumes) ;
  3. configurer des services avec directives build, image, ports, environment, env_file et restart ;
  4. analyser les limites de la directive depends_on et la compléter avec des sondes de santé (Healthchecks) ;
  5. maîtriser l’interpolation de variables d’environnement et les fichiers .env dans Compose ;
  6. piloter des piles applicatives complètes avec les commandes CLI (up, down, ps, logs, exec).

1. Du Script Impératif à la Déclaration d’Infrastructure as Code

Lancer plusieurs conteneurs interconnectés par des commandes CLI brutes est fastidieux, fragile et non reproductible :

Approche Impérative (Scripts Shell)

Le développeur écrit un script start.sh rempli de commandes :

docker network create mynet
docker volume create dbdata
docker run -d --net mynet -v dbdata:/var/lib/postgresql/data postgres
docker run -d --net mynet -p 8080:8080 myapi

Aucune gestion de l’état désiré, pas de mécanisme de nettoyage automatique, et code difficile à maintenir.

Approche Déclarative (Docker Compose)

L’architecture complète est déclarée dans un fichier docker-compose.yml :

services:
  db:
    image: postgres:15-alpine
    volumes: [pgdata:/var/lib/postgresql/data]
  api:
    build: ./api
    ports: ["8080:8080"]

Une seule commande docker compose up -d crée les réseaux, volumes et conteneurs nécessaires.

2. Structure Complète du Fichier docker-compose.yml

La spécification moderne de Docker Compose (spécification Compose unifiée) articule la configuration en trois grands blocs de niveau racine :

Bloc Racine Rôle Éléments configurables clés
services: Définit chaque conteneur applicatif de la pile. image ou build, ports, environment, volumes, depends_on, restart.
networks: Définit les réseaux virtuels partagés entre les services. Driver (bridge par défaut), sous-réseau IPAM, isolation réseau entre tiers.
volumes: Définit les volumes managés persistants créés automatiquement. Driver de stockage, options de montage pour persister les données.
Création Automatique du Réseau par Défaut

Lorsque vous exécutez docker compose up dans un dossier nommé projet, Compose crée automatiquement un réseau bridge isolé nommé projet_default. Tous les services déclarés dans le fichier rejoignent ce réseau et peuvent immédiatement communiquer entre eux par leur nom de service (ex: http://db:5432 ou http://redis:6379) sans avoir besoin de déclarer manuellement de réseau personnalisé.

3. Dépendances depends_on vs Sondes de Santé (Healthchecks)

L’un des pièges les plus célèbres de Docker Compose réside dans la directive depends_on :

Le Piège de depends_on Classique

Écrire simplement depends_on: [db] indique à Docker de démarrer le conteneur db avant le conteneur api. Cependant, pour Docker, un conteneur est « démarré » dès que son processus est spawné ! Or, une base de données PostgreSQL ou MySQL prend 5 à 15 secondes pour initialiser ses tables et écouter sur le port TCP. L’API démarre, tente de se connecter immédiatement, échoue et s’arrête en erreur (CrashLoop).

La Solution Professionnelle : Healthcheck

On définit une sonde de santé sur la base de données et on attend qu’elle soit saine :

services:
  db:
    image: postgres:15-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy

4. Gestion des Variables d’Environnement et Fichiers .env

Docker Compose lit automatiquement le fichier .env présent dans le même répertoire et remplace les variables selon des syntaxes d’interpolation normalisées :

  • ${VARIABLE} : insère la valeur définie dans .env. Si la variable n’existe pas, renvoie une chaîne vide.
  • ${VARIABLE:-valeur_par_defaut} : utilise la variable si elle existe et n’est pas vide, sinon applique valeur_par_defaut.
  • ${VARIABLE:?message_erreur} : bloque immédiatement le lancement avec une erreur si la variable obligatoire est manquante.
Règle de Sécurité des Fichiers .env

Le fichier .env contient généralement des secrets de configuration (mots de passe de base de données, clés API privées, tokens de signature JWT). Il doit impérativement figurer dans votre fichier .gitignore et ne jamais être commité dans le dépôt git. Fournissez à la place un fichier modèle .env.example contenant des valeurs fictives documentées.

Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

Exercice 1 — Parseur et validateur de services Docker Compose

Python Niveau 1 — Acquisition

Objectif : Valider la structure des déclarations de services dans une spécification Docker Compose.

Le script lit sur l'entrée standard des déclarations de services au format plat service: <Nom> | image: <Img> | ports: <P> | restart: <R>.
Règles de validation :
1. Chaque service DOIT comporter au moins une directive image OU build.
2. La directive restart, si présente, doit être parmi : no, always, unless-stopped, on-failure. (Sinon no par défaut).
Pour chaque service :
- Si valide : SERVICE: <Nom> -> VALIDE [Origine: <ImageOuBuild> | Ports: <PortsOuAucun> | Restart: <Restart>]
- Si ni image ni build n'est défini : SERVICE: <Nom> -> INVALIDE (Directive image ou build obligatoire)

Entrée du programme
service: frontend | image: nginx:alpine | ports: 80:80 | restart: always
service: cache | image: redis:7 | restart: unless-stopped
service: orphelin | restart: always
Sortie attendue
SERVICE: frontend -> VALIDE [Origine: image:nginx:alpine | Ports: 80:80 | Restart: always]
SERVICE: cache -> VALIDE [Origine: image:redis:7 | Ports: aucun | Restart: unless-stopped]
SERVICE: orphelin -> INVALIDE (Directive image ou build obligatoire)

Validation des directives requises de la spécification Compose.

Deux indices, rédigés en mots
  1. Découper chaque ligne par le caractère pipe |.
  2. Extraire les paires cle: valeur.

Exercice 2 — Résolveur d’ordre de démarrage par graphe de dépendances (depends_on)

Python Niveau 2 — Application

Objectif : Calculer l’ordre d’instanciation séquentiel des conteneurs via un tri topologique sans cycle.

Le script lit sur l'entrée standard des déclarations de dépendances Compose au format <Service> -> <Dep1, Dep2, ... ou NONE>.
Par exemple : web -> api signifie que web dépend de api (donc api doit démarrer avant web).
Règles :
- Effectuer un tri topologique des services.
- En cas d'égalité de niveau de dépendance, trier par ordre alphabétique des noms de service.
- Si une boucle de dépendance mutuelle est détectée, afficher : ERREUR_COMPOSE: Dependance cyclique detectee.
- Sinon, afficher l'ordre strict de démarrage :
ORDRE_DEMARRAGE: <S1> -> <S2> -> ...

Entrée du programme
web -> api
api -> db, redis
db -> NONE
redis -> NONE
Sortie attendue
ORDRE_DEMARRAGE: db -> redis -> api -> web

db et redis démarrent en premier, puis api, puis web.

Deux indices, rédigés en mots
  1. Construire la liste d’adjacence et les degrés entrants.
  2. Un service avec 0 dépendance restante peut démarrer immédiatement.

Exercice 3 — Interprète de variables d’environnement et fichiers .env dans Compose

Python Niveau 3 — Raisonnement

Objectif : Résoudre les syntaxes d’interpolation ${VAR} et ${VAR:-default} dans les fichiers de configuration Compose.

Le script lit sur l'entrée standard :
- Bloc 1 (jusqu'à la ligne contenant ---) : paires CLE=VALEUR définies dans le fichier .env.
- Bloc 2 (après ---) : chaînes de configuration Compose à évaluer (une par ligne).
Règles d'interpolation :
- ${VAR} : remplacé par la valeur de VAR si elle existe, sinon chaîne vide.
- ${VAR:-default} : remplacé par la valeur de VAR si non vide, sinon par default.
Pour chaque chaîne du bloc 2, afficher :
RESOLU: <ChaineApresInterpolation>

Entrée du programme
PORT=8080
DB_USER=admin
---
image: nginx:${TAG:-latest}
ports: ${PORT}:80
user: ${DB_USER}
db_pass: ${DB_PASS:-secret123}
Sortie attendue
RESOLU: image: nginx:latest
RESOLU: ports: 8080:80
RESOLU: user: admin
RESOLU: db_pass: secret123

TAG prend la valeur latest par défaut, PORT et DB_USER sont interpolés.

Deux indices, rédigés en mots
  1. Gérer les expressions régulières ou le parcours caractère par caractère pour repérer ${...}.
  2. Séparer proprement le bloc .env du bloc Compose via le délimiteur ---.

6. QCM — niveau examen

Quel est l’avantage fondamental de Docker Compose par rapport à des scripts de déploiement composés de commandes « docker run » ?

Docker Compose centralise l’architecture (services, volumes, réseaux, configurations) dans un fichier YAML déclaratif garantissant des déploiements reproductibles et unifiés.

Pourquoi une directive « depends_on: [database] » classique est-elle souvent insuffisante pour empêcher un conteneur d’API de crasher au démarrage ?

Démarré ne signifie pas prêt : la base a besoin de quelques secondes pour charger ses fichiers et démarrer son écoute. Sans sonde healthcheck, l’API tente une connexion immédiate et plante.

Quelle configuration Compose moderne permet d’attendre qu’un service de base de données soit pleinement opérationnel avant de lancer l’API ?

L’option condition: service_healthy suspend le démarrage du service consommateur jusqu’à ce que le test de santé (healthcheck) du service requis réussisse avec succès.

Que fait Docker Compose par défaut concernant le réseau lorsque l’on exécute « docker compose up » dans un projet sans déclaration explicite de bloc networks ?

Compose instancie un réseau par défaut (projet_default) sur lequel tous les conteneurs sont automatiquement branchés et peuvent se joindre directement par leur nom de service.

Que produit la syntaxe d’interpolation « ${DB_PORT:-5432} » dans un fichier docker-compose.yml si la variable DB_PORT n’est pas définie dans l’environnement ni dans le fichier .env ?

La syntaxe ${VAR:-defaut} permet de fournir une valeur de repli robuste lorsque la variable d’environnement n’est pas renseignée.

Pourquoi est-il impératif d’ajouter le fichier « .env » dans le fichier « .gitignore » du projet ?

Le fichier .env renferme les secrets et identifiants sensibles de la configuration locale : il ne doit jamais être commité ni poussé sur un dépôt partagé (GitHub, GitLab).

Quelle commande Docker Compose permet d’arrêter tous les conteneurs de la pile ET de supprimer définitivement tous les volumes de données persistants associés ?

docker compose down éteint les conteneurs et supprime le réseau. L’adjonction du drapeau -v (ou --volumes) détruit en plus les volumes nommés déclarés dans le fichier.

Quelle politique de redémarrage (restart) permet à un conteneur Compose de redémarrer automatiquement en cas de crash ou de redémarrage de l’hôte, SAUF si l’administrateur l’a explicitement arrêté ?

unless-stopped relance automatiquement le conteneur dans tous les cas, sauf si une commande manuelle docker stop ou docker compose stop a été explicitement exécutée.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Croire que depends_on attend que PostgreSQL ou MySQL soit prêt à accepter des requêtes SQL.
  • Commiter le fichier .env contenant des mots de passe en clair dans un dépôt git public.
  • Oublier les guillemets autour des ports dans YAML (ex: ports: - 80:80 au lieu de "80:80"), pouvant être interprété comme un nombre sexagésimal.
  • Utiliser docker compose down -v en pensant simplement arrêter la pile : le flag -v détruit irréversiblement tous les volumes de données associés.

8. Méthodologie de résolution

Protocole de Déploiement et de Gestion d’une Pile Docker Compose
  1. Étape 1 — Rédiger le fichier docker-compose.yml : Définir les services, volumes et dépendances d’état de santé.
  2. Étape 2 — Préparer le fichier de variables d’environnement : Créer un fichier .env local avec les identifiants et clés de chiffrement.
  3. Étape 3 — Lancer la pile en arrière-plan : Exécuter « docker compose up -d » pour télécharger les images, compiler les services et instancier les conteneurs.
  4. Étape 4 — Vérifier l’état de santé des services : Lancer « docker compose ps » et constater que les conteneurs affichent le statut « healthy ».
  5. Étape 5 — Suivre les journaux consolidés : Observer les flux d’interaction entre conteneurs avec « docker compose logs -f ».
  6. Étape 6 — Arrêter et nettoyer la pile proprement : Éteindre les conteneurs avec « docker compose down » ou « docker compose down -v » pour purger les volumes de données.

9. Révision active

Résumé essentiel
  • Docker Compose fournit un format déclaratif (Infrastructure as Code) unifiant la gestion multi-conteneurs.
  • Par défaut, Compose crée un réseau bridge privé dédié et connecte tous les services déclarés avec résolution DNS interne.
  • depends_on seul ne garantit que le lancement du conteneur cible, pas sa disponibilité applicative interne.
  • L’association de healthcheck avec condition: service_healthy garantit un ordre de démarrage parfaitement fiable.
  • Le fichier .env permet de paramétrer la pile par interpolation sans coder de valeurs sensibles en dur.
  • La commande docker compose down arrête les conteneurs et supprime le réseau virtuel associé en une seule opération.

Checklist de maîtrise

  • Je comprends l’intérêt de l’approche déclarative par rapport à une suite de commandes docker run.
  • Je sais structurer les trois grands blocs : services, networks et volumes.
  • Je sais pourquoi depends_on classique peut conduire à un plantage d’application au démarrage.
  • Je sais configurer une directive healthcheck avec interval, timeout et retries.
  • Je maîtrise la syntaxe d’interpolation ${VAR:-default} dans les fichiers YAML Compose.
  • Je sais pourquoi le fichier .env ne doit jamais être versionné dans git.
