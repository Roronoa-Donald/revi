Chapitre 6 — Sécurité, Production & Optimisation

Module 6 ≈ 3 h 00 de travail Réservé B2 et plus
Mise en situation

Un serveur de production hébergeant une dizaine d’applications conteneurisées est victime d’une intrusion majeure : un pirate a exploité une faille de type Remote Code Execution (RCE) dans une bibliothèque vulnérable d’un conteneur web. Comme le conteneur tournait avec l’utilisateur root par défaut et sans aucune restriction de capabilities Linux, l’attaquant a réussi à charger un module noyau malveillant, à s’évader du conteneur (Container Escape) et à compromettre l’intégralité de l’infrastructure physique de l’entreprise. Dans le même temps, un second conteneur victime d’une fuite mémoire a provoqué l’intervention brutale de l’OOM-Killer qui a fauché le processus de base de données principal, faute de quotas mémoire configurés. Ce dernier module d’expertise forme les ingénieurs à verrouiller intégralement leurs conteneurs en production : bannir les privilèges root, filtrer les capabilities du noyau, poser des garde-fous stricts de CPU/mémoire et intégrer l’audit continu de sécurité dans la chaîne d’intégration continue (DevSecOps).

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. appliquer les recommandations essentielles du standard de sécurité CIS Docker Benchmark ;
  2. bannir l’exécution en utilisateur root et configurer des utilisateurs dédiés non-privilégiés (USER) ;
  3. restreindre les privilèges du noyau Linux avec la gestion fine des Capabilities (--cap-drop / --cap-add) ;
  4. comprendre les dangers critiques du flag --privileged et les vecteurs d’évasion de conteneur ;
  5. configurer des quotas stricts de ressources cgroups (--memory, --cpus, --pids-limit) pour immuniser l’hôte ;
  6. automatiser la rotation des journaux de logs (logging drivers) pour empêcher la saturation du disque.

1. Le Principe du Moindre Privilège : Bannir l’Utilisateur Root

Par défaut, si aucune directive USER n’est spécifiée dans le Dockerfile, le processus s’exécute sous le compte root (UID 0). Bien que cloisonné par les namespaces, un attaquant qui parvient à exécuter du code arbitraire en tant que root dispose d’un pouvoir bien supérieur pour tenter une évasion de conteneur :

Anti-pattern : Exécution Root

FROM node:18-alpine
WORKDIR /app
COPY . .
CMD ["node", "server.js"]  # S'execute en UID 0 (root) !

Si l’application présente une faille de téléversement de fichier ou d’injection de commande, le pirate peut modifier les fichiers système du conteneur, manipuler les interfaces réseau et chercher une faille de noyau pour s’évader sur l’hôte.

Bonne Pratique : Utilisateur Dédié Non-Root

FROM node:18-alpine
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
WORKDIR /app
COPY --chown=appuser:appgroup . .
USER appuser  # Bascule en utilisateur sans privileges
CMD ["node", "server.js"]

Même en cas de compromission totale de l’application, le pirate est confiné dans un compte sans aucun droit d’administration, bloquant net la quasi-totalité des attaques d’évasion.

2. Linux Capabilities et Dangers Mortels de --privileged

Sous Linux, les super-pouvoirs du compte root sont découpés en privilèges granulaires appelés Capabilities. Docker active par défaut un sous-ensemble restreint (comme CAP_CHOWN, CAP_NET_BIND_SERVICE) et désactive les plus dangereuses (comme CAP_SYS_ADMIN ou CAP_SYS_MODULE) :

Option Docker CLI Action de Sécurité Niveau de Risque / Recommandation
--cap-drop=ALL Retire l’intégralité des privilèges noyau accordés au conteneur. Excellence sécuritaire : À appliquer par défaut sur toutes les applications de production.
--cap-add=NET_BIND_SERVICE Accorde uniquement le droit d’écouter sur un port inférieur à 1024 (ex: port 80/443). Recommandé : n’ajouter que le strict minimum de capabilities indispensables.
--privileged Désactive TOUTES les barrières : accorde toutes les capabilities et l’accès direct à /dev. DANGER MORTEL : Équivaut à donner l’accès root physique sur l’hôte. Formellement interdit en production.
--read-only Monte la racine du conteneur en lecture seule intégrale. Empêche tout attaquant de déposer un script malveillant sur le système de fichiers.

3. Quotas de Ressources Cgroups : Prévenir le Déni de Service (DoS)

Sans limites explicites de ressources, un seul conteneur victime d’une boucle infinie ou d’une fuite de mémoire peut consommer 100 % du processeur et de la RAM de la machine physique, paralysant l’ensemble des autres services hébergés :

  • --memory="512m" : plafonne la mémoire vive allouée. Si le conteneur dépasse ce seuil, le gestionnaire OOM (Out Of Memory) de son cgroup le termine immédiatement sans affecter les autres conteneurs.
  • --memory-swap="1g" : limite la mémoire totale cumulée (RAM + espace de swap). Si égal à --memory, le conteneur n’a pas le droit d’utiliser de swap sur disque.
  • --cpus="1.5" : garantit que le conteneur ne peut pas consommer plus de 150 % de temps de calcul processeur (soit l’équivalent d’un cœur et demi sur une période CFS de 100 ms).
  • --pids-limit=100 : plafonne le nombre total de processus simultanés dans le conteneur, immunisant l’hôte contre les attaques de type Fork Bomb.

4. Scans de Vulnérabilités et Rotation des Logs en Production

Deux mesures opérationnelles indispensables complètent le durcissement en environnement de production :

Scans de Vulnérabilités (Trivy / Docker Scout)

Avant tout déploiement dans le registre, l’image doit être scannée par un outil de sécurité automatisé :

trivy image --severity HIGH,CRITICAL mon-image:v1.0

L’analyse compare les versions des bibliothèques système et paquets applicatifs contre les bases nationales de CVE et bloque automatiquement le pipeline CI/CD si une faille critique est détectée.

Rotation des Logs (Logging Drivers)

Par défaut, Docker stocke les journaux dans des fichiers JSON non limités qui peuvent saturer le disque en quelques semaines. Configurez une rotation dans /etc/docker/daemon.json :

{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}

Les journaux sont ainsi bornés à 3 fichiers de 10 Mo maximum par conteneur.

Exercice 1 — Auditeur de privilèges root et directive USER

Python Niveau 1 — Acquisition

Objectif : Vérifier la conformité de sécurité d’une image Docker en s’assurant qu’elle ne s’exécute pas sous le superutilisateur root.

Le script lit sur l'entrée standard les instructions d'un Dockerfile (une par ligne).
Règles de sécurité CIS Docker Benchmark :
- Par défaut dans Docker, l'utilisateur actif est root (UID 0).
- Si une instruction USER <nom_ou_uid> est rencontrée, elle modifie l'utilisateur actif pour les étapes suivantes et le runtime final.
- À la fin du fichier :
* Si le dernier utilisateur actif est root ou 0 ou si aucune directive USER n'a été définie :
afficher AUDIT_SECURITE: CRITIQUE (Le conteneur s'execute avec les privileges root - UID 0)
* Si le dernier utilisateur actif est non-root (ex: node, appuser, 1001) :
afficher AUDIT_SECURITE: CONFORME (Execution sous utilisateur non-privilegie: <USER>)

Entrée du programme
FROM python:3.11-slim
WORKDIR /app
COPY . .
USER appuser
CMD ["python", "main.py"]
Sortie attendue
AUDIT_SECURITE: CONFORME (Execution sous utilisateur non-privilegie: appuser)

Image conforme exécutée sous utilisateur non-privilégié.

Deux indices, rédigés en mots
  1. Parcourir le fichier et mettre à jour la variable utilisateur_courant à chaque instruction USER.
  2. Ignorer les commentaires débutant par #.

Exercice 2 — Calculateur de quotas cgroups (CPU & Mémoire)

Python Niveau 2 — Application

Objectif : Convertir les paramètres de contrainte de ressources Docker en métriques de contrôle noyau cgroups.

Le script lit sur l'entrée standard des déclarations de limites au format MEM=<valeur> SWAP=<valeur> CPUS=<valeur>.
Exemple : MEM=512m SWAP=1g CPUS=1.5.
Unités mémoire : m (Mo = 1024 Ko) ou g (Go = 1024 Mo).
Règles cgroups v2 :
- RAM_MAX_MO : valeur convertie en Mo entiers.
- Dans Docker, l'option --memory-swap représente la mémoire totale (RAM + SWAP cumulés).
Le swap additionnel effectif est donc : SWAP_EFFECTIF_MO = max(0, SWAP_TOTAL_MO - RAM_MAX_MO).
- Période CPU CFS standard = 100000 microsecondes.
Le quota alloué par période est : CPU_QUOTA_US = int(CPUS * 100000).
Afficher :
CGROUPS: RAM: <RAM_MAX_MO> Mo | SWAP_ADDITIONNEL: <SWAP_EFFECTIF_MO> Mo | CPU_QUOTA: <CPU_QUOTA_US> us / 100000 us (<CPUS> cœurs)

Entrée du programme
MEM=512m SWAP=1g CPUS=1.5
MEM=256m SWAP=256m CPUS=0.5
Sortie attendue
CGROUPS: RAM: 512 Mo | SWAP_ADDITIONNEL: 512 Mo | CPU_QUOTA: 150000 us / 100000 us (1.5 cœurs)
CGROUPS: RAM: 256 Mo | SWAP_ADDITIONNEL: 0 Mo | CPU_QUOTA: 50000 us / 100000 us (0.5 cœurs)

Si SWAP == MEM, aucun swap supplémentaire n’est autorisé.

Deux indices, rédigés en mots
  1. Convertir 1g en 1024 Mo.
  2. Se rappeler que l’argument swap de Docker est la somme de la RAM et du swap.

Exercice 3 — Simulateur de politique de redémarrage (Restart Policy)

Python Niveau 3 — Raisonnement

Objectif : Déterminer si le démon Docker redémarre ou non un conteneur arrêté selon sa politique et son code de sortie.

Le script lit sur l'entrée standard des événements d'arrêt au format POLITIQUE=<pol> EXIT_CODE=<code> MANUEL=<OUI|NON>.
Règles du démon Docker :
1. Si MANUEL=OUI (ex: docker stop déclenché par l'admin) :
- DECISION: ARRET_DEFINITIF (Arret volontaire par l'administrateur)
2. Sinon :
- POLITIQUE=no : DECISION: ARRET_DEFINITIF (Politique "no")
- POLITIQUE=always ou POLITIQUE=unless-stopped :
DECISION: REDEMARRER (Relance automatique du conteneur)
- POLITIQUE=on-failure :
* Si EXIT_CODE == 0 : DECISION: ARRET_DEFINITIF (Code sortie normal 0)
* Si EXIT_CODE != 0 : DECISION: REDEMARRER (Echec detecte: code <code>)
Afficher :
EVENEMENT: <entree> -> <DECISION>

Entrée du programme
POLITIQUE=always EXIT_CODE=1 MANUEL=NON
POLITIQUE=always EXIT_CODE=0 MANUEL=OUI
POLITIQUE=on-failure EXIT_CODE=0 MANUEL=NON
POLITIQUE=on-failure EXIT_CODE=137 MANUEL=NON
Sortie attendue
EVENEMENT: POLITIQUE=always EXIT_CODE=1 MANUEL=NON -> DECISION: REDEMARRER (Relance automatique du conteneur)
EVENEMENT: POLITIQUE=always EXIT_CODE=0 MANUEL=OUI -> DECISION: ARRET_DEFINITIF (Arret volontaire par l'administrateur)
EVENEMENT: POLITIQUE=on-failure EXIT_CODE=0 MANUEL=NON -> DECISION: ARRET_DEFINITIF (Code sortie normal 0)
EVENEMENT: POLITIQUE=on-failure EXIT_CODE=137 MANUEL=NON -> DECISION: REDEMARRER (Echec detecte: code 137)

Simulation exacte des 4 comportements clés de redémarrage.

Deux indices, rédigés en mots
  1. Un arrêt volontaire manuel bloque tout redémarrage automatique.
  2. on-failure ne relance le conteneur que si le code de sortie est non nul.

6. QCM — niveau examen

Pourquoi est-il impératif de déclarer un utilisateur non-root avec la directive « USER » dans un Dockerfile de production ?

S’exécuter en tant qu’utilisateur non-privilégié neutralise la plupart des attaques d’évasion de conteneur et restreint drastiquement le rayon d’action d’un pirate.

Que produit l’utilisation du drapeau « --privileged » lors du lancement d’un conteneur avec « docker run » ?

--privileged retire toutes les protections de sécurité : un processus dans le conteneur peut charger des modules noyau et prendre le contrôle total du serveur physique en quelques secondes.

Quelle option CLI permet d’immuniser un serveur hôte contre une attaque de type « Fork Bomb » (création infinie de processus fils) lancée depuis un conteneur ?

--pids-limit plafonne le nombre de threads et processus simultanés que le conteneur peut créer, empêchant la saturation de la table des processus du noyau Linux.

Quelle combinaison d’options permet d’appliquer la stratégie de sécurité maximale concernant les Linux Capabilities d’un conteneur ?

Retirer toutes les capabilities par défaut (--cap-drop=ALL) puis réactiver uniquement le privilège indispensable applique le principe de défense en profondeur le plus strict.

Que se passe-t-il sur un serveur hôte si un conteneur sans limite de mémoire spécifiée subit une fuite de mémoire RAM massive ?

Sans plafond cgroup (--memory), le conteneur engloutit la RAM de l’hôte physique, provoquant un arrêt d’urgence par l’OOM-Killer qui peut tuer les processus de l’OS ou d’autres conteneurs sains.

À quoi sert l’option « --read-only » lors de l’exécution d’un conteneur Docker ?

Un système de fichiers en lecture seule (--read-only) rend le conteneur immuable à l’exécution, bloquant le dépôt de tout binaire ou script pirate sur son arborescence.

Quel outil open source de sécurité est couramment intégré dans les chaînes CI/CD pour scanner les images Docker à la recherche de CVE connues ?

Trivy (Aqua Security) est un scanner de vulnérabilités de référence pour conteneurs, capable de détecter les failles dans les paquets OS et les dépendances applicatives.

Pourquoi est-il crucial de configurer les options « max-size » et « max-file » dans le pilote de journalisation de Docker ?

Par défaut, Docker ne purge pas les logs : une application bavarde peut générer des dizaines de gigaoctets de logs et bloquer totalement le serveur hôte par saturation disque.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Utiliser le drapeau --privileged en production pour résoudre un problème de droits de fichiers au lieu d’ajuster les permissions.
  • Ne pas fixer de limite mémoire (--memory), permettant à un conteneur défaillant de saturer la RAM et de déclencher l’OOM-Killer sur l’hôte.
  • Laisser le conteneur s’exécuter en root par défaut sans directive USER dans le Dockerfile.
  • Oublier de configurer la rotation des logs, aboutissant au blocage complet du serveur par saturation de la partition /var.
  • Ignorer les alertes de sécurité des scanners de vulnérabilités CVE dans les pipelines CI/CD.

8. Méthodologie de résolution

Protocole de Durcissement et Déploiement Sécurisé en Production
  1. Étape 1 — Scannage statique des vulnérabilités : Passer l’image au crible avec Trivy ou Docker Scout pour éliminer les failles HIGH et CRITICAL.
  2. Étape 2 — Forcer un utilisateur non-root : Vérifier que le Dockerfile comporte une directive USER non nulle et sans droits sudo.
  3. Étape 3 — Restreindre les Linux Capabilities : Lancer le conteneur avec « --cap-drop=ALL » et ne réactiver que les permissions indispensables.
  4. Étape 4 — Poser des plafonds de ressources stricts : Configurer obligatoirement --memory, --cpus et --pids-limit pour prévenir tout déni de service.
  5. Étape 5 — Activer le système de fichiers en lecture seule : Appliquer « --read-only » avec un volume tmpfs temporaire uniquement pour les répertoires d’écriture nécessaires (/tmp).
  6. Étape 6 — Configurer la politique de redémarrage et la rotation des logs : Définir restart: unless-stopped et vérifier la rotation des fichiers de journalisation.

9. Révision active

Résumé essentiel
  • Le principe du moindre privilège impose d’exécuter les conteneurs sous un utilisateur non-root dédié (directive USER).
  • Le flag --privileged désactive toutes les protections d’isolation et doit être formellement banni en production.
  • La stratégie --cap-drop=ALL retire l’intégralité des privilèges noyau pour ne conserver que le strict minimum.
  • Les quotas cgroups (--memory, --cpus, --pids-limit) protègent l’hôte contre les fuites de mémoire et les fork-bombs.
  • L’option --read-only fige le système de fichiers du conteneur et empêche l’injection de scripts malveillants persistants.
  • La rotation des logs (max-size et max-file) prévient la saturation accidentelle de l’espace disque de la machine hôte.

Checklist de maîtrise

  • Je comprends pourquoi exécuter un conteneur en root est un risque de sécurité majeur.
  • Je sais comment créer et déclarer un utilisateur non-privilégié dans un Dockerfile.
  • Je sais expliquer pourquoi le drapeau --privileged est dangereux pour l’hôte physique.
  • Je maîtrise l’usage de --cap-drop=ALL combiné à --cap-add ciblé.
  • Je sais configurer des plafonds de mémoire RAM et de processeur CPU avec les cgroups.
  • Je sais configurer la rotation automatique des logs pour éviter la saturation du disque.
