Examens Blancs & Épreuves Corrigées Docker B2

Deux épreuves d’évaluation complètes conformes aux exigences académiques universitaires de niveau Bachelor 2 / Licence 2 en administration système et conteneurisation DevOps.

Épreuve 1 : Contrôle Continu (CC) — Durée 1 h 30 (Barème sur 20 points)

Sujet du Contrôle Continu — Isolation Noyau, Images & Dockerfile

Partie 1 : Fondements de la Conteneurisation (6 points)

  1. Expliquez la différence fondamentale d’architecture entre une machine virtuelle de type 2 (VirtualBox) et un conteneur Docker. Quels composants matériels ou logiciels sont virtualisés ou partagés dans chaque cas ? (3 pts)
  2. Détaillez le rôle respectif des Namespaces Linux et des Control Groups (cgroups) dans la création d’un conteneur. Citez au moins 4 types de namespaces distincts. (3 pts)

Partie 2 : Système de Fichiers en Couches & OverlayFS (6 points)

Un serveur Docker héberge trois applications web basées sur l’image parente node:18-alpine (150 Mo). Chaque application ajoute 30 Mo de code source spécifique.

  1. Expliquez le mécanisme d’Union File System (OverlayFS) et le principe de Copy-On-Write (CoW). Quel est l’espace disque physique total réellement consommé par ces trois images sur l’hôte ? (3 pts)
  2. Que se passe-t-il exactement sur le disque si l’un des conteneurs supprime le fichier /etc/hosts appartenant à l’image parente en lecture seule ? (3 pts)

Partie 3 : Rédaction et Optimisation de Dockerfile (8 points)

Soit le Dockerfile suivant pour une application Node.js :

FROM ubuntu:22.04\nRUN apt-get update\nRUN apt-get install -y nodejs npm\nCOPY . /app\nWORKDIR /app\nRUN npm install\nCMD node server.js
  1. Identifiez au moins 4 anti-patterns critiques dans ce Dockerfile (taille d’image, invalidation de cache, sécurité, signaux UNIX). (4 pts)
  2. Rédigez le Dockerfile corrigé et optimisé respectant les meilleures pratiques de production (image de base légère, ordre des couches de cache, utilisateur non-root, forme exec de CMD). (4 pts)
Corrigé type & Barème détaillé du Contrôle Continu

Corrigé Partie 1 (6 points)

  • VM vs Conteneur (3 pts) : La VM virtualise le matériel complet via un hyperviseur et embarque son propre système d’exploitation invité (Guest OS avec noyau, pilotes et services système). Le conteneur Docker s’exécute directement sur l’OS hôte, partage son noyau Linux unique et n’embarque que les binaires et bibliothèques utilisateurs de l’application.
  • Namespaces et Cgroups (3 pts) : Les Namespaces créent une bulle d’illusion spatiale en isolant la vue des ressources système (PID pour les processus, NET pour le réseau, MNT pour les points de montage, IPC pour la mémoire partagée, UTS pour le nom d’hôte, USER pour les identifiants). Les Cgroups contrôlent et limitent la consommation quantitative des ressources matérielles (plafond CPU, quota mémoire RAM, E/S disque).

Corrigé Partie 2 (6 points)

  • OverlayFS & Stockage (3 pts) : OverlayFS superpose des couches en lecture seule (Image Layers) et une couche supérieure en lecture-écriture (Container Writable Layer). La couche de base node:18-alpine (150 Mo) n’est stockée qu’une seule fois. Espace réel = 150 Mo + (3 * 30 Mo) = 240 Mo (au lieu de 540 Mo sans déduplication).
  • Suppression et Whiteout (3 pts) : La couche d’image inférieure étant strictement immuable (Read-Only), le fichier d’origine n’est pas effacé. Le pilote OverlayFS crée un fichier spécial de masquage (whiteout file) dans la couche Container Layer, rendant le fichier invisible au conteneur sans modifier l’image partagée.

Corrigé Partie 3 (8 points)

  • Anti-patterns identifiés (4 pts) :
    1. Image de base lourde (Ubuntu 22.04 > 80 Mo) avec installation inutile d’outils système complets.
    2. RUN apt-get update isolé brisant le cache et absence de nettoyage de /var/lib/apt/lists/*.
    3. COPY . /app placé AVANT npm install : tout changement d’un fichier source invalide le cache des dépendances node_modules.
    4. Exécution par défaut en utilisateur superadministrateur root.
    5. CMD node server.js en forme shell qui lance un sous-shell /bin/sh -c bloquant la réception des signaux SIGTERM.
  • Dockerfile corrigé (4 pts) :
    FROM node:18-alpine\n WORKDIR /app\n COPY package*.json ./\n RUN npm ci --only=production\n COPY . .\n USER node\n EXPOSE 3000\n CMD ["node", "server.js"]

Épreuve 2 : Examen Terminal (ET) — Durée 2 h 00 (Barème sur 20 points)

Sujet de l’Examen Terminal — Réseaux, Multi-Stage, Docker Compose & Sécurité

Partie 1 : Architecture Docker Engine & Spécification OCI (5 points)

  1. Détaillez le rôle de dockerd, containerd, containerd-shim et runc lors du démarrage d’un conteneur avec la commande docker run. (3 pts)
  2. Quel est l’intérêt architectural d’avoir découplé le démon Docker de l’exécuteur de conteneur containerd-shim ? (2 pts)

Partie 2 : Réseau et Résolution DNS Interne (5 points)

  1. Quelle est la différence fondamentale de comportement entre le réseau bridge par défaut (docker0) et un réseau bridge personnalisé créé via docker network create ? (2.5 pts)
  2. Comment un conteneur api peut-il communiquer avec un conteneur database situé sur le même réseau bridge personnalisé ? Expliquez le fonctionnement du serveur DNS intégré de Docker. (2.5 pts)

Partie 3 : Déploiement Multi-Services avec Docker Compose (6 points)

On souhaite déployer une architecture à trois niveaux : une interface web Nginx (port 80), une API Python Flask (port 5000) et une base de données PostgreSQL (port 5432).

  1. Rédigez le fichier docker-compose.yml complet avec déclaration des services, des volumes de données persistants pour PostgreSQL, et d’un réseau privé interne. (4 pts)
  2. Pourquoi la directive depends_on seule ne suffit-elle pas pour garantir que l’API ne crashe pas au démarrage en tentant de se connecter à PostgreSQL ? Comment sécuriser cette initialisation ? (2 pts)

Partie 4 : Durcissement et Sécurité en Production (4 points)

  1. Expliquez les risques liés à l’utilisation de conteneurs privilégiés (flag --privileged). Pourquoi ce flag doit-il être formellement banni en production ? (2 pts)
  2. Comment contraindre la mémoire maximale (OOM) et le temps de calcul CPU d’un conteneur à l’aide des commandes CLI Docker ? (2 pts)
Corrigé type & Barème détaillé de l’Examen Terminal

Corrigé Partie 1 (5 points)

  • Pile logicielle Docker (3 pts) : Le client CLI envoie la requête HTTP au démon dockerd via la socket Unix. dockerd gère les images et le réseau puis délègue l’exécution à containerd. containerd appelle le runtime de bas niveau runc (conforme OCI) pour configurer les namespaces/cgroups et lancer le processus conteneurisé. runc s’arrête une fois le processus lancé et laisse containerd-shim superviser le conteneur.
  • Avantage de containerd-shim (2 pts) : containerd-shim maintient les descripteurs de fichiers (stdin/stdout/stderr) et l’état du conteneur sans dépendre du démon dockerd. Cela permet de redémarrer ou mettre à jour le démon Docker sans interrompre l’exécution des conteneurs actifs (Live Restore).

Corrigé Partie 2 (5 points)

  • Réseau bridge par défaut vs personnalisé (2.5 pts) : Sur le bridge par défaut, les conteneurs ne peuvent communiquer entre eux que par adresse IP ou liens historiques dépréciés --link. Sur un réseau bridge personnalisé, Docker active automatiquement un serveur DNS interne à l’adresse 127.0.0.11 permettant la résolution automatique des noms d’hôtes par nom de conteneur.
  • Communication et DNS interne (2.5 pts) : Le conteneur api contacte l’hôte database:5432. Le resolver DNS intégré intercepte la requête, résout le nom database en son adresse IP interne privée sur le sous-réseau bridge et achemine les paquets TCP sans exposer le port 5432 sur la machine hôte physique.

Corrigé Partie 3 (6 points)

  • Fichier docker-compose.yml (4 pts) :
    services:\n  web:\n    image: nginx:alpine\n    ports:\n      - "80:80"\n    depends_on:\n      - api\n    networks:\n      - app-net\n\n  api:\n    build: ./api\n    environment:\n      - DB_HOST=db\n    depends_on:\n      db:\n        condition: service_healthy\n    networks:\n      - app-net\n\n  db:\n    image: postgres:15-alpine\n    environment:\n      POSTGRES_PASSWORD: secret\n    volumes:\n      - pgdata:/var/lib/postgresql/data\n    healthcheck:\n      test: ["CMD-SHELL", "pg_isready -U postgres"]\n      interval: 5s\n      retries: 5\n    networks:\n      - app-net\n\nvolumes:\n  pgdata:\n\nnetworks:\n  app-net:
  • Sécurisation de depends_on (2 pts) : depends_on garantit uniquement que le conteneur cible est démarré au sens du système, pas que le démon de base de données PostgreSQL a terminé son initialisation et accepte les connexions TCP. La solution consiste à associer une directive healthcheck sur PostgreSQL et utiliser condition: service_healthy dans l’API.

Corrigé Partie 4 (4 points)

  • Risques de --privileged (2 pts) : Le flag --privileged désactive l’ensemble de l’isolation de sécurité (accès direct à tous les périphériques /dev de l’hôte, toutes les Linux Capabilities activées, désactivation des profils AppArmor/Seccomp). Une faille applicative permet une évasion immédiate du conteneur et la prise de contrôle totale de l’OS hôte physique.
  • Quotas de ressources (2 pts) : En ligne de commande : docker run --memory="512m" --cpus="1.5" .... Cela configure directement les contrôleurs mémoire et CPU CFS des cgroups noyau, empêchant un conteneur en fuite de mémoire ou en boucle infinie de paralyser le serveur hôte.
