Chapitre 3 — Intégration du SI & Architectures

Module 3 ≈ 3 h 00 de travail Réservé B2 et plus
Mise en situation

L’ERP ne vit jamais seul : il doit dialoguer avec les banques, les sites e-commerce, les applications logistiques des transporteurs et les logiciels RH. Concevoir ces passerelles de façon anarchique mène à une « architecture spaghetti » indémêlable. Les architectures EAI et ESB structurent cette intégration.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. comparer les topologies d’intégration (Point-à-Point, Hub & Spoke, ESB, iPaaS) ;
  2. comprendre le rôle et les fonctions d’un Enterprise Service Bus (ESB) ;
  3. maîtriser le concept de format pivot pour la transformation des messages (EDI, XML, JSON) ;
  4. différencier les processus d’intégration par lots (ETL/ELT) des flux temps réel ;
  5. garantir la qualité et la déduplication des données dans le Master Data Management (MDM).

1. Topologies d’intégration : Du Spaghetti au Bus de services

Lorsque le Système d’Information comporte plusieurs dizaines d’applications, la méthode retenue pour les interconnecter conditionne la maintenabilité globale :

  • Intégration Point-à-Point (« Architecture Spaghetti ») : chaque application développe une interface sur mesure vers chaque partenaire. Pour N applications, cela engendre jusqu’à N * (N - 1) / 2 connecteurs. Toute mise à jour d’une application casse potentiellement toutes ses interfaces.
  • Modèle Hub & Spoke (EAI classique) : un serveur centralisateur (Hub) reçoit tous les flux et les redistribue. Le nombre d’interfaces passe à N, mais le Hub devient un goulet d’étranglement et un point unique de défaillance (SPOF).
  • Bus de services d’entreprise (ESB) : architecture distribuée orientée services (SOA) où chaque application se connecte à une dorsale commune via des adaptateurs normalisés.
  • iPaaS (Integration Platform as a Service) : version cloud moderne de l’ESB (ex. MuleSoft, Boomi, Workato) facilitant la connexion entre progiciels SaaS et SI interne.
La métaphore de la prise électrique universelle

L’ESB agit comme le réseau électrique domestique : chaque appareil (application) dispose d’une prise standard sans avoir besoin de tirer un câble spécifique vers chaque centrale électrique.

2. Fonctions clés de l’ESB et du Middleware

Un middleware d’intégration (ESB) assure quatre missions fondamentales lors du transit d’un message :

  1. Routage : déterminer le ou les destinataires du message en fonction de son contenu ou de règles déclaratives (Content-Based Routing).
  2. Transformation : convertir les données du format propriétaire émetteur vers le format attendu par le destinataire (ex. JSON vers XML ou EDIFACT).
  3. Médiation de protocoles : faire dialoguer un système émettant en SFTP avec un ERP recevant en Web Service REST HTTPS.
  4. Garantie de livraison et file d’attente : stocker temporairement les messages (via des brokers comme RabbitMQ ou Kafka) si l’application cible est momentanément indisponible.
Le modèle du Format Pivot (Canonical Data Model)

Plutôt que d’écrire une transformation pour chaque couple d’applications, l’entreprise définit un format pivot unique (modèle de données canonique). Chaque système ne traduit son format que vers et depuis ce pivot, réduisant drastiquement les coûts de maintenance.

3. Formats d’échange : EDI, XML et JSON

Les données transitent à travers le SI sous différents standards selon les partenaires :

FormatContexte d’utilisation typeAvantages & Limites
EDI (EDIFACT / ANSI X12)Grande distribution, automobile, logistique internationale.Très compact, normé par l’ONU, mais rigide et coûteux à mettre en œuvre.
XMLÉchanges bancaires (SEPA), facturation électronique obligatoire, SOAP.Structure arborescente rigoureuse validée par schéma (XSD), mais verbeux.
JSONAPI REST modernes, intégrations SaaS Cloud, applications web/mobiles.Léger, rapide à parser nativement dans tous les langages modernes.

4. Pipelines de données : ETL vs ELT

Pour alimenter l’ERP ou consolider les données vers un entrepôt décisionnel (Data Warehouse), on utilise des pipelines de traitement par lots :

  • ETL (Extract - Transform - Load) : les données brutes sont extraites des bases sources, transformées et nettoyées sur un serveur dédié, puis chargées dans la cible. Idéal lorsque la qualité de données exige un assainissement préalable rigoureux.
  • ELT (Extract - Load - Transform) : les données sont chargées directement dans l’entrepôt cible moderne (BigQuery, Snowflake), qui utilise sa puissance de calcul parallèle pour exécuter les transformations.

Exercice 1 — Point-à-Point vs Hub d’intégration EAI

Python Niveau 1 — Acquisition

Objectif : Calculer la complexité d’interconnexion entre N applications d’entreprise.

Dans une intégration Point-à-Point (spaghetti), relier N applications deux à deux requiert N * (N - 1) / 2 interfaces spécifiques. À l’inverse, une architecture orientée Hub EAI ou ESB ne nécessite qu’un connecteur par application vers le bus central, soit exactement N interfaces.

Lit le nombre entier d’applications N sur l’entrée standard (N >= 2).
Calcule le nombre d’interfaces nécessaires dans les deux modèles ainsi que le gain d’interfaces apporté par le Hub.
Affiche le résultat sous la forme :
Point-a-Point: <X> | Hub ESB: <Y> | Gain: <Z> interfaces.

Entrée du programme
6
Sortie attendue
Point-a-Point: 15 | Hub ESB: 6 | Gain: 9 interfaces

Pour 6 applications : 15 interfaces spécifiques contre 6 avec un bus.

Deux indices, rédigés en mots
  1. Point-à-point = n * (n - 1) // 2.
  2. Hub ESB = n.
  3. Gain = point_a_point - hub_esb.

Exercice 2 — Mappage de message pivot EDI / JSON

Python Niveau 2 — Application

Objectif : Transformer un message reçu d’un partenaire vers le format canonique de l’ERP.

Un middleware EAI reçoit des messages hétérogènes et les mappe vers le format pivot interne de l’ERP.

Lit un objet JSON représentant une commande externe au format partenaire :
{"ref_ext": "CMD-88", "partenaire": "FOURN_12", "lignes": [{"article": "A1", "qte": 10, "prix": 15.0}, ...]}.
Transforme ce payload en objet pivot ERP canonique contenant :
- "order_id": valeur de ref_ext
- "vendor_id": valeur de partenaire
- "items_count": nombre total d’articles physiques (somme des qte)
- "total_ht": montant total calculé round(somme(qte * prix), 2)
Affiche le dictionnaire pivot sérialisé en JSON compact trié (json.dumps(..., sort_keys=True)).

Entrée du programme
{"lignes": [{"article": "A1", "prix": 15.0, "qte": 10}], "partenaire": "FOURN_12", "ref_ext": "CMD-88"}
Sortie attendue
{"items_count": 10, "order_id": "CMD-88", "total_ht": 150.0, "vendor_id": "FOURN_12"}

Mapping pivot avec calculs de somme.

Deux indices, rédigés en mots
  1. Itère sur message.get("lignes", []).
  2. total_ht = round(sum(ligne["qte"] * ligne["prix"] for ligne in lignes), 2).
  3. items_count = sum(ligne["qte"] for ligne in lignes).

Exercice 3 — Pipeline ETL : Déduplication de flux

Python Niveau 3 — Raisonnement

Objectif : Filtrer et dédupliquer une liste de contacts importés dans l’ERP en conservant l’enregistrement le plus récent.

Une étape clé d’un processus ETL (Extract-Transform-Load) lors de l’alimentation de l’ERP consiste à éliminer les doublons tout en conservant les données les plus à jour (Master Data Management).

Lit une liste JSON de contacts sur l’entrée standard. Chaque fiche contient :
{"email": "...", "nom": "...", "version": int}.
1. Si un même email apparaît plusieurs fois (insensible à la casse), conserve uniquement la fiche ayant le plus grand numéro de version.
2. Passe la valeur du champ nom en majuscules (.upper()).
3. Normalise l’email en minuscules (.lower()).
Affiche la liste finale dédupliquée, triée par ordre alphabétique de l’email, avec json.dumps(..., sort_keys=True).

Entrée du programme
[{"email": "ALICE@site.fr", "nom": "Alice", "version": 1}, {"email": "alice@site.fr", "nom": "Alice Martin", "version": 2}]
Sortie attendue
[{"email": "alice@site.fr", "nom": "ALICE MARTIN", "version": 2}]

La version 2 a écrasé la version 1.

Deux indices, rédigés en mots
  1. Utilise un dictionnaire indexé par email.lower().
  2. Si un email existe déjà, compare les numéros de version.
  3. Extrais les valeurs et trie la liste résultante avec sorted(..., key=lambda c: c["email"]).

6. QCM — niveau examen

Pourquoi l’architecture d’intégration « Point-à-Point » devient-elle ingérable ?

Chaque nouvelle application impose de recoder des connecteurs vers toutes les autres.

Que signifie l’acronyme ESB dans une architecture de SI ?

L’Enterprise Service Bus est la dorsale de communication commune du SI.

À quoi sert le concept de « Format Pivot » (Canonical Data Model) ?

Le format pivot évite la multiplication exponentielle des convertisseurs spécifiques.

Quel format d’échange est historiquement incontournable dans la grande distribution et l’automobile ?

L’EDI régit les échanges automatisés inter-entreprises (commandes, expéditions, factures).

Quelle fonction d’un middleware garantit que les messages ne sont pas perdus si l’ERP est temporairement indisponible ?

Les files de messages temporisent les requêtes jusqu’au rétablissement de la cible.

Que signifie iPaaS ?

L’iPaaS désigne une plateforme d’intégration hébergée dans le Cloud (ex. MuleSoft, Boomi).

Quelle est la différence fondamentale entre ETL et ELT ?

L’ELT tire parti de la puissance de calcul des entrepôts de données cloud pour transformer sur place.

Que permet le routage basé sur le contenu (Content-Based Routing) dans un ESB ?

L’ESB lit le message et décide de la destination selon les règles métiers configurées.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Créer des flux point-à-point directs en pensant gagner du temps à court terme.
  • Négliger la normalisation d’un format pivot, obligeant à maintenir des dizaines de scripts de conversion ad hoc.
  • Confondre un bus de messages asynchrone (Kafka/RabbitMQ) avec une base de données de stockage permanent.
  • Oublier de monitorer les rejets d’intégration (messages non délivrés en file morte / Dead Letter Queue).
  • Transférer des données en production sans valider leur conformité avec un schéma de contrat (XSD ou JSON Schema).

8. Méthodologie de résolution

Concevoir l’intégration d’une nouvelle application au SI
  1. Identifier les besoins d’échange : recenser les données à synchroniser, les fréquences et la tolérance à la latence.
  2. Définir le contrat d’interface : choisir le format (JSON / XML) et le protocole (REST, SFTP, Webhook).
  3. Raccorder au bus ESB ou iPaaS : configurer l’adaptateur sans contact direct point-à-point.
  4. Mapper vers le format pivot : implémenter la transformation aller-retour vers le modèle d’entreprise.
  5. Mettre en place la surveillance : superviser les files d’attente, les alertes et la Dead Letter Queue.

9. Révision active

Résumé essentiel
  • L’intégration point-à-point engendre une dette technique massive en architecture spaghetti.
  • L’ESB (Enterprise Service Bus) normalise le routage, la médiation et la transformation des flux.
  • Le format pivot évite la démultiplication des connecteurs en instaurant un standard commun.
  • L’EDI, le XML et le JSON répondent à des contextes d’intégration inter et intra-entreprises variés.
  • Les plateformes iPaaS permettent d’interconnecter de façon agile l’ERP interne aux applications SaaS Cloud.
