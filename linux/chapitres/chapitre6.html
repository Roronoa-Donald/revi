Chapitre 6 — Services, processus et planification

Module 6 ≈ 2 h 30 de travail Réservé B2 et plus
Mise en situation

Un serveur passe sa vie à exécuter des services. L’administrateur doit savoir lequel tourne, lequel est tombé, quel processus consomme tout, et programmer les tâches récurrentes — sans oublier de surveiller ce qui se passe dans les journaux.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. lire et changer l’état d’un service systemd ;
  2. interpréter les états d’un processus et repérer un zombie ;
  3. programmer une tâche récurrente avec cron ;
  4. consulter les journaux pour diagnostiquer.

1. systemctl : piloter un service

Sous Debian moderne, les services sont gérés par systemd via systemctl. Un service est active, inactive ou failed. Selon l’état, l’action diffère : démarrer, redémarrer ou ne rien faire.

systemctl status nginx        # état détaillé
systemctl start nginx         # démarrer (inactive)
systemctl restart nginx       # redémarrer (failed)
systemctl enable nginx        # activer au démarrage
État vers action

active → rien à faire ; inactive → start ; failed → restart. Le choix de l’action selon l’état est exactement ce que code l’exercice 1 de ce chapitre.

2. Processus et zombies

ps et top listent les processus. Un processus running s’exécute, sleeping attend, zombie est terminé mais non récupéré par son parent : il ne consomme plus de ressources mais occupe une entrée de la table des processus.

ps aux            # tous les processus
top               # tri par consommation, en direct
kill PID          # demander l’arrêt d’un processus
kill -9 PID       # forcer (dernier recours)
Piège — kill -9 en premier recours

kill envoie un signal d’arrêt propre ; kill -9 ne laisse aucune chance au processus de fermer ses fichiers. On le réserve au processus réellement bloqué.

3. Planifier avec cron

cron exécute des commandes à heure fixe. Une entrée crontab a cinq champs — minute, heure, jour du mois, mois, jour de la semaine — suivis de la commande.

crontab -e                     # éditer ses tâches
# minute heure jour mois jour-semaine  commande
  0      6     *    *    *             /root/backup.sh
 30     23     *    *    *             /root/nettoyage.sh
Classer une tâche

On distingue les tâches du matin (heure < 12) de celles de l’après-midi. Cette règle simple structure l’exercice 3 : lire heure, minute et nom de tâche, classer, puis compter.

4. Lire les journaux

Tout service écrit dans le journal de systemd, consultable avec journalctl. On filtre par service, par priorité ou par heure.

journalctl -u nginx        # journal d’un service
journalctl -p err -b       # erreurs depuis le dernier démarrage
tail -f /var/log/syslog    # suivre un fichier en direct
Diagnostiquer dans l’ordre

Un service ne répond plus ? 1) systemctl status ; 2) journalctl -u ; 3) ps pour vérifier le processus ; 4) décider de l’action. Le réflexe d’ordre évite de redémarrer à l’aveugle.

5. Exercices de code

Ces trois exercices se font dans la page. L’éditeur du navigateur exécute votre code sur un service distant, puis la validation fait tourner des tests que vous ne voyez pas : réussir l’exemple affiché ne suffit donc pas, il faut traiter le cas général.

En cas d’erreur, le bouton Expliquer mon erreur interroge le tuteur : il décrit ce qui s’est passé et par où chercher, sans jamais écrire de code à votre place — c’est le principe de l’exercice.

Exercice 1 — Superviser un service

Bash Niveau 2 — Application

Objectif : Décider de l’action à mener selon l’état d’un service systemd.

Le script lit n lignes « service etat » où etat vaut active, inactive ou failed. Il affiche pour chacun service : rien a faire (active), service : demarrer (inactive) ou service : redemarrer (failed). Il termine par alertes : X, le nombre de services non actifs.

Entrée du programme
3
ssh active
nginx inactive
mysql failed
Sortie attendue
ssh : rien a faire
nginx : demarrer
mysql : redemarrer
alertes : 2
Deux indices, rédigés en mots
  1. Trois cas : active, inactive (démarrer), failed (redémarrer).
  2. Une alerte est comptée pour tout service qui n’est pas active.

Exercice 2 — Détecter un processus anormal

Bash Niveau 2 — Application

Objectif : Repérer les processus zombies et dresser la liste des actifs.

Le script lit n lignes « pid etat » où etat vaut running, sleeping ou zombie. Il affiche pid : actif, pid : en attente ou pid : a nettoyer, puis termine par zombies : X.

Entrée du programme
3
101 running
205 sleeping
309 zombie
Sortie attendue
101 : actif
205 : en attente
309 : a nettoyer
zombies : 1
Deux indices, rédigés en mots
  1. Trois états possibles : running, sleeping, zombie.
  2. Seuls les zombies alimentent le compteur final.

Exercice 3 — Vérifier une tâche planifiée

Bash Niveau 3 — Raisonnement

Objectif : Classer les tâches cron selon qu’elles s’exécutent le matin ou l’après-midi.

Le script lit n lignes « heure minute tache ». Une tâche dont heure est strictement inférieure à 12 s’exécute le matin ; sinon elle s’exécute l’après-midi. Il affiche tache : matin ou tache : apres-midi, puis termine par matin : X.

Entrée du programme
2
6 30 sauvegarde
23 0 nettoyage
Sortie attendue
sauvegarde : matin
nettoyage : apres-midi
matin : 1
Deux indices, rédigés en mots
  1. La comparaison se fait sur l’heure seule : [ "$heure" -lt 12 ].
  2. Midi (12) et au-delà sont considérés comme l’après-midi.

6. QCM — niveau examen

Que fait systemctl restart nginx ?

restart relance le service, utile quand son état est failed.

État d’un service arrêté mais installé ?

inactive signifie arrêté ; failed signifie en échec après une tentative.

Un processus zombie…

Il est fini mais son parent n’a pas récupéré son code de retour.

Que fait kill -9 ?

-9 envoie SIGKILL : arrêt forcé, sans nettoyage, en dernier recours.

Combien de champs dans une entrée crontab ?

Cinq champs de temps, puis la commande.

0 6 * * * s’exécute…

minute 0, heure 6, tous les jours : chaque matin à 6 h.

Quelle commande lit le journal d’un service ?

journalctl -u filtre le journal par unité de service.

Quelle action pour un service failed ?

Un service en échec se redémarre (restart) ; inactive se démarre (start).

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Redémarrer un service « à l’aveugle » sans avoir lu son status ni son journal.
  • Utiliser kill -9 en premier recours au lieu de kill.
  • Confondre start (inactive) et restart (failed).
  • Écrire une entrée crontab avec le mauvais nombre de champs.
  • Oublier d’activer le service au démarrage (enable).

8. Méthodologie de résolution

Diagnostiquer puis agir
  1. Constater l’état avec systemctl status.
  2. Lire le journal du service avant toute action.
  3. Choisir l’action : rien, start ou restart, selon l’état.
  4. Vérifier les processus avec ps et repérer les zombies.
  5. Automatiser le contrôle récurrent avec une tâche cron.

9. Révision active

Résumé essentiel
  • systemd gère les services : active, inactive, failed → rien, start, restart.
  • ps et top listent les processus ; un zombie est terminé mais non récupéré.
  • kill demande un arrêt propre ; kill -9 force, en dernier recours.
  • cron planifie : cinq champs de temps puis la commande.
  • journalctl -u lit le journal d’un service, journalctl -p err les erreurs.

Checklist de maîtrise

  • Je lis l’état d’un service et en déduis l’action.
  • Je repère un processus zombie dans une liste.
  • J’écris une entrée crontab correcte.
  • Je consulte le journal d’un service avant d’agir.
