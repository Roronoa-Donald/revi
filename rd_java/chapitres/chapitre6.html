Chapitre 6 — Exceptions et robustesse

Module 6 ≈ 2 h 30 de travail Réservé B2 et plus
Mise en situation

Une division par zéro, une saisie non numérique, un solde négatif : les erreurs surgissent. Java les représente par des exceptions. Bien traitées, elles transforment un plantage en message clair — ou en décision métier.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. intercepter une exception avec try/catch ;
  2. reconnaître les exceptions standard (ArithmeticException, NumberFormatException) ;
  3. écrire et lancer une exception personnalisée ;
  4. déclarer qu’une méthode peut lever une exception avec throws.

1. try, catch, finally

Le bloc try contient le code risqué ; le bloc catch traite l’erreur ; le bloc finally s’exécute dans tous les cas (nettoyage).

try {
    System.out.println(a / b);
} catch (ArithmeticException e) {
    System.out.println("division par zéro");
} finally {
    System.out.println("terminé");
}

Sans capture, l’exception remonte et le programme s’arrête en affichant une trace d’appel. Attraper un type précis vaut mieux qu’attraper Exception partout.

2. Exceptions standard

Deux erreurs très fréquentes ont chacune leur exception : ArithmeticException pour la division entière par zéro, NumberFormatException pour une conversion Integer.parseInt qui échoue.

try {
    int valeur = Integer.parseInt(saisie);
} catch (NumberFormatException e) {
    System.out.println("saisie invalide");
}
Vérifié ou non vérifié

Les exceptions héritant de RuntimeException ne sont pas obligatoires à déclarer : c’est le cas d’ArithmeticException et de NumberFormatException. Les autres (héritant directement d’Exception) doivent être déclarées avec throws ou capturées.

3. Exception personnalisée

Pour un problème métier — un solde insuffisant, une date impossible — on crée une classe d’exception dédiée. Elle étend Exception et transmet son message au constructeur parent.

class SoldeInsuffisant extends Exception {
    SoldeInsuffisant(String message) {
        super(message);
    }
}

void retirer(int montant) throws SoldeInsuffisant {
    if (montant > solde) {
        throw new SoldeInsuffisant("solde insuffisant");
    }
    solde -= montant;
}

Intercepter un type précis (catch (SoldeInsuffisant e)) distingue une erreur métier d’un bug technique.

4. Écrire du code robuste

Le bon réflexe : anticiper les cas limites (b == 0, saisie vide, montant négatif) et laisser l’exception signaler ce qui ne peut pas être traité. Le message doit être explicite et le traitement cohérent.

if (montant < 0) {
    throw new IllegalArgumentException("montant négatif");
}
if (montant > solde) {
    throw new SoldeInsuffisant("solde insuffisant");
}
Une erreur est une information

Une exception mal traitée est avalée et disparaît : le bug devient invisible. Une exception précise, avec un message clair, transforme un plantage en piste. C’est l’objet le plus utile d’un programme qui dure.

Exercice 1 — Division protégée

Java Niveau 2 — Application

Objectif : Intercepter une exception d’exécution.

Le programme reçoit deux entiers a et b. Affichez resultat : X où X est le quotient entier a / b. Si b vaut 0, interceptez l’exception et affichez erreur : division par zéro.

Entrée du programme
10
2
Sortie attendue
resultat : 5

10 divisé par 2.

Deux indices, rédigés en mots
  1. En Java, la division entière par zéro lève une ArithmeticException, pas un résultat infini.
  2. Place l’affichage du quotient dans le try, et le message d’erreur dans le catch.

Exercice 2 — Conversion d’une saisie

Java Niveau 2 — Application

Objectif : Intercepter une erreur de format.

Le programme reçoit une saisie (un mot). Essayez de la convertir en entier avec Integer.parseInt. Si la conversion réussit, affichez valeur : X ; sinon affichez saisie invalide.

Entrée du programme
42
Sortie attendue
valeur : 42

Un entier valide.

Deux indices, rédigés en mots
  1. Integer.parseInt("42") renvoie 42, mais lance une NumberFormatException sur un texte non numérique.
  2. Le catch (NumberFormatException e) affiche "saisie invalide".

Exercice 3 — Exception personnalisée

Java Niveau 3 — Raisonnement

Objectif : Déclarer et lancer une exception métier, puis l’intercepter.

Le programme reçoit un solde puis un montant (deux entiers). Écrivez une exception SoldeInsuffisant et une classe Compte dont retirer() la lance quand le montant dépasse le solde. Affichez reste : X si le retrait passe, sinon erreur : solde insuffisant.

Entrée du programme
100
30
Sortie attendue
reste : 70

Un retrait de 30 sur 100.

Deux indices, rédigés en mots
  1. Une exception personnalisée étend Exception et transmet le message à super().
  2. La méthode retirer déclare throws SoldeInsuffisant ; l’appel est encadré d’un try / catch de ce type.

6. QCM — niveau examen

Quel bloc contient le code risqué ?

Le try encadre le code susceptible de lever une exception.

Quel bloc s’exécute dans tous les cas ?

finally s’exécute après le try, avec ou sans erreur.

Quelle exception pour une division entière par zéro ?

La division par zéro lève une ArithmeticException.

Quelle exception pour parseInt invalide ?

Une chaîne non numérique provoque NumberFormatException.

Comment créer une exception métier ?

On crée une classe qui extends Exception.

Que fait throw ?

throw déclenche l’exception choisie.

Que déclare throws ?

throws prévient l’appelant du risque, qui doit capturer ou propager.

Pourquoi capturer un type précis ?

Un catch précis sépare les erreurs attendues des bugs inattendus.

7. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Avale une exception avec un catch vide.
  • Attraper Exception partout au lieu du type concerné.
  • Oublier throws sur une méthode qui lève une exception vérifiée.
  • Confondre throw (lancer) et throws (déclarer).
  • Laisser un message d’erreur trop vague.

8. Méthodologie de résolution

Traiter une erreur proprement
  1. Repérer les opérations risquées (division, conversion, bornes).
  2. Choisir l’exception adaptée : standard ou personnalisée.
  3. Encadrer l’appel d’un try/catch sur le bon type.
  4. Déclarer throws quand la méthode laisse remonter.
  5. Rédiger un message clair pour l’utilisateur ou le développeur.

9. Révision active

Résumé essentiel
  • try encadre le code risqué, catch traite, finally s’exécute toujours.
  • ArithmeticException (division par zéro) et NumberFormatException (conversion) sont courantes.
  • Une exception personnalisée étend Exception et transmet un message.
  • throw lance ; throws déclare qu’une méthode peut lever.
  • Une erreur bien signalée vaut mieux qu’un plantage silencieux.

Checklist de maîtrise

  • J’encadre le code risqué d’un try/catch.
  • Je capture le type précis de l’exception.
  • Je crée une exception métier quand le cas le justifie.
  • Je rédige des messages d’erreur explicites.
