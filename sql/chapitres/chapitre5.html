Chapitre 5 — Transactions ACID, Concurrence & Niveaux d’Isolation

Module 5 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Lors d’une vente flash de billets de concert, deux utilisateurs cliquent simultanément sur le dernier siège disponible. Dans un système mal isolé, les deux requêtes lisent l’état « libre », débitent les comptes respectifs et attribuent la même place deux fois : c’est une anomalie de concurrence classique de mise à jour perdue (Lost Update). À l’inverse, des verrous trop agressifs risquent de figer la base de données dans un interblocage total (Deadlock) où les transactions s’attendent indéfiniment. Comment garantir l’atomicité intégrale d’une série d’opérations avec BEGIN, COMMIT et ROLLBACK ? Quel niveau d’isolation choisir entre Read Committed, Repeatable Read et Serializable pour équilibrer rigueur et débit ? Comment le SGBD résout-il les deadlocks grâce aux graphes d’attente ? Ce module étudie les mécanismes vitaux de la cohérence transactionnelle.

Objectifs pédagogiques

À la fin de ce chapitre, tu seras capable de :

  1. définir rigoureusement les quatre propriétés ACID (Atomicité, Cohérence, Isolation, Durabilité) d’un SGBD relationnel ;
  2. manipuler les instructions de contrôle de transaction : BEGIN, COMMIT, ROLLBACK, SAVEPOINT et ROLLBACK TO SAVEPOINT ;
  3. identifier et caractériser les 3 anomalies de concurrence majeures : Dirty Read, Non-Repeatable Read et Phantom Read ;
  4. comparer les 4 niveaux d’isolation du standard ANSI/ISO SQL et leurs compromis entre consistance et performances ;
  5. analyser les mécanismes de verrous partagés (S) et exclusifs (X) et détecter les cycles d’interblocage (Deadlocks).

1. Le Modèle ACID & Contrôle Transactionnel (TCL)

Une transaction est une unité logique de travail regroupant une ou plusieurs instructions SQL. Le moteur relationnel garantit que cette séquence respecte le contrat ACID :

Les 4 Piliers ACID

  • A - Atomicité (Tout ou rien) : Soit toutes les opérations de la transaction sont enregistrées, soit aucune ne l’est. En cas d’erreur au milieu, le SGBD annule tout (ROLLBACK).
  • C - Cohérence (Consistency) : La transaction fait passer la base d’un état valide à un autre état valide, en respectant l’intégralité des contraintes d’intégrité (clés, CHECK, triggers).
  • I - Isolation : Les transactions concurrentes s’exécutent sans interférences mutuelles néfastes, comme si elles étaient séquentielles.
  • D - Durabilité : Une fois le COMMIT confirmé, les modifications sont écrites de façon permanente dans le journal non volatil (WAL), résistant même à une coupure électrique immédiate.

Commandes de Contrôle (TCL)

BEGIN TRANSACTION; UPDATE Comptes SET solde = solde - 500 WHERE id = 12; SAVEPOINT etape1; UPDATE Comptes SET solde = solde + 500 WHERE id = 88; -- Si incident sur la 2e opération : -- ROLLBACK TO SAVEPOINT etape1; COMMIT;

2. Anomalies de Concurrence & Les 4 Niveaux d’Isolation ANSI

Lorsque des centaines d’utilisateurs lisent et écrivent simultanément sur les mêmes tables, des phénomènes parasites peuvent fausser les calculs :

  • Lecture sale (Dirty Read) : La transaction T1 lit une donnée modifiée par T2 qui n’a pas encore fait de COMMIT. Si T2 fait un ROLLBACK, T1 aura travaillé sur des données fantaisistes qui n’ont jamais existé.
  • Lecture non répétable (Non-Repeatable Read) : T1 lit une ligne, puis T2 modifie cette ligne et fait un COMMIT. Si T1 relit la même ligne au cours de sa transaction, elle observe une valeur différente.
  • Lecture fantôme (Phantom Read) : T1 exécute une requête avec un filtre de plage (ex: WHERE age > 18). T2 insère une nouvelle ligne respectant ce critère et valide son COMMIT. Si T1 relance la même requête, de nouvelles lignes « fantômes » sont apparues.

READ UNCOMMITTEDOuiOuiOui
READ COMMITTED (Défaut PostgreSQL/Oracle)NonOuiOui

3. Verrouillage Concurrente & Interblocages (Deadlocks)

Pour isoler les transactions, les SGBD s’appuient sur des verrous posés en mémoire :

Types de verrous

  • Verrou Partagé (Shared Lock - S) : Posé en lecture (SELECT ... FOR SHARE). Plusieurs transactions peuvent lire la même ressource en parallèle.
  • Verrou Exclusif (Exclusive Lock - X) : Posé en écriture (UPDATE, DELETE, SELECT ... FOR UPDATE). Une seule transaction peut détenir ce verrou ; tout autre accès est suspendu.

L’Interblocage (Deadlock)

Survient lorsque deux transactions s’attendent mutuellement dans une boucle fermée :

T1 verrouille A et attend B • T2 verrouille B et attend A.

Le moteur détecte le cycle dans son graphe d’attente (Wait-For Graph), choisit une transaction « victime », annule ses opérations par un ROLLBACK forcé et lève une exception Deadlock detected.

  • Ordonnancement strict : Toujours verrouiller ou modifier les tables et les lignes dans le même ordre déterministe au sein de toutes les fonctions applicatives (ex: toujours par id croissant).
  • Transactions courtes : Réduire la durée de vie des transactions au strict nécessaire : jamais d’appel API externe ou de traitement lourd à l’intérieur d’un bloc BEGIN ... COMMIT.

Exercice 1 — Simulateur de transaction atomique bancaire (COMMIT vs ROLLBACK)

Python Niveau 1 — Acquisition

Objectif : Appliquer l’atomicité (A de ACID) : si un virement échoue (fonds insuffisants), la transaction entière est annulée.

Une transaction bancaire transfère des fonds entre comptes : TRANSFERT source destination montant. Pour chaque transfert, le compte source doit exister et disposer d’au moins le montant demandé (pas de découvert). Le compte destination doit également exister. Si toutes les opérations réussissent, la transaction fait COMMIT. Si la moindre opération échoue, la transaction fait ROLLBACK et restaure l’état exact de départ.

Entrée : - Ligne 1 : Soldes initiaux compte:solde séparés par des virgules (ex: A:1000,B:500,C:200). - Lignes suivantes : Opérations TRANSFERT source destination montant. Sortie : - Si succès : Statut: COMMIT | Soldes: <compte:solde triés> - Si échec : Statut: ROLLBACK | Erreur: <Raison> | Soldes: <soldes initiaux inchangés>

Entrée du programme
A:1000,B:500,C:200
TRANSFERT A B 300
TRANSFERT B C 150
Sortie attendue
Statut: COMMIT | Soldes: A:700,B:650,C:350

Tous les virements sont valides, la transaction est validée (COMMIT).

Deux indices, rédigés en mots
  1. Garde une copie indépendante des soldes initiaux pour le ROLLBACK.
  2. Vérifie que les comptes source et destination existent.
  3. Vérifie que le solde de la source est suffisant (>= montant).
  4. Si une erreur survient, interromps les virements et restaure la copie de départ.

Exercice 2 — Gestionnaire de points de sauvegarde SAVEPOINT & ROLLBACK TO

Python Niveau 2 — Application

Objectif : Gérer des états intermédiaires dans une transaction avec les points de reprise SAVEPOINT.

Dans une longue transaction SQL, l’instruction SAVEPOINT nom_point sauvegarde l’état courant de la base. En cas d’erreur survenue ultérieurement, la commande ROLLBACK TO nom_point annule uniquement les opérations effectuées après ce point de sauvegarde sans compromettre le reste de la transaction.

Entrée : Une suite de commandes sur chaque ligne : - AJOUT cle valeur - SAVEPOINT nom - ROLLBACK TO nom - COMMIT Sortie : Etat_Final: <cle:valeur triées>.

Entrée du programme
AJOUT A 10
SAVEPOINT sp1
AJOUT B 20
ROLLBACK TO sp1
AJOUT C 30
COMMIT
Sortie attendue
Etat_Final: A:10,C:30

L'ajout de B est annulé par le ROLLBACK TO sp1, mais A:10 est conservé.

Deux indices, rédigés en mots
  1. Maintiens un dictionnaire représentant l état de la base.
  2. Pour chaque SAVEPOINT nom, sauvegarde une copie superficielle ou profonde du dictionnaire dans un historique {nom: copie}.
  3. Lors de ROLLBACK TO nom, restaure la copie correspondante.

Exercice 3 — Détecteur d’interblocage (Deadlock) par graphe d’attente (Wait-For Graph)

Python Niveau 3 — Raisonnement

Objectif : Construire le graphe orienté de dépendance des transactions et détecter la présence d’un cycle d’interblocage.

Un interblocage (Deadlock) survient lorsque deux ou plusieurs transactions s’attendent mutuellement pour libérer des verrous exclusifs. Si la transaction T1 détient la ressource R1 et attend R2, alors que T2 détient R2 et attend R1, il y a une dépendance circulaire T1 -> T2 -> T1.

Entrée : Chaque ligne décrit une transaction : T_ID DETIENT ressource_tenue ATTEND ressource_attendue (ou ATTEND AUCUNE s’il n’y a pas d’attente). Sortie : - S’il existe un cycle : DEADLOCK DETECTE: cycle <T_A -> T_B -> ... -> T_A> - Si le graphe est acyclique : AUCUN DEADLOCK: execution possible.

Entrée du programme
T1 DETIENT R1 ATTEND R2
T2 DETIENT R2 ATTEND R1
Sortie attendue
DEADLOCK DETECTE: cycle T1 -> T2 -> T1

T1 attend T2 qui attend T1 : cycle d'interblocage.

Deux indices, rédigés en mots
  1. Établis qui détient chaque ressource : detenteurs[ressource] = transaction.
  2. Pour chaque transaction qui attend une ressource, crée une arête orientée : T_demandeur -> detenteurs[ressource].
  3. Applique un parcours en profondeur (DFS) pour détecter si un cycle existe.

5. QCM — niveau examen

Que signifie la propriété d’Atomicité (A) dans le contrat ACID d’une base de données relationnelle ?

L’atomicité garantit que l’ensemble des instructions d’une transaction forme un bloc indivisible : en cas d’échec partiel, le SGBD annule l’intégralité des modifications préalables pour restaurer l’état d’origine (ROLLBACK).

Quelle anomalie de concurrence se produit lorsqu’une transaction lit des modifications apportées par une autre transaction qui n’a PAS encore été validée par un COMMIT ?

La lecture sale (Dirty Read) consiste à lire des données non validées en mémoire qui risquent d’être annulées par un ROLLBACK ultérieur de la transaction concurrente.

Quel est le niveau d’isolation minimal requis pour empêcher totalement les lectures sales (Dirty Reads) ?

Le niveau Read Committed garantit qu’une transaction ne peut lire que les données dont le COMMIT a été définitivement enregistré par d’autres transactions, neutralisant ainsi les lectures sales.

À quoi sert l’instruction SAVEPOINT dans une transaction SQL ?

SAVEPOINT nom_point crée un point de jalonnement dans la transaction en cours. En cas d’erreur sur une étape ultérieure, la commande ROLLBACK TO SAVEPOINT nom_point rétablit l’état à ce point précis sans perdre le travail antérieur.

Comment le SGBD résout-il un interblocage (Deadlock) entre deux transactions ?

Le gestionnaire de verrous du SGBD surveille son graphe d’attente (Wait-For Graph). Dès qu’un cycle est détecté, il interrompt l’une des transactions (la victime), annule ses actions par ROLLBACK et renvoie une erreur applicative pour que le programme puisse retenter l’opération.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Laisser une transaction ouverte (BEGIN sans COMMIT ni ROLLBACK) dans une application web, ce qui maintient indéfiniment des verrous et paralyse la base.
  • Effectuer des appels réseau externes lents (ex: API de paiement par carte) à l’intérieur d’une transaction SQL active.
  • Modifier des ressources dans un ordre aléatoire (ex: T1 verrouille client puis facture, T2 verrouille facture puis client), provoquant des interblocages fréquents.
  • Utiliser le niveau SERIALIZABLE partout en pensant que c’est toujours « plus sûr », sans anticiper les erreurs d’interblocage et la chute drastique du débit applicatif.
  • Croire que la durabilité (D de ACID) dispense de mettre en place des sauvegardes régulières et une réplication externe hors-site.

7. Méthodologie de résolution

Protocole en 4 étapes pour sécuriser les transactions concurrentes en production
  1. Garder les blocs transactionnels les plus courts et atomiques possible : préparer toutes les données en mémoire avant de lancer le BEGIN.
  2. Imposer un ordre universel d’accès aux tables et aux lignes (ex: toujours trier les IDs par ordre croissant avant de poser un SELECT FOR UPDATE).
  3. Sélectionner le niveau d’isolation adapté au besoin métier (Read Committed pour les opérations courantes, Repeatable Read ou Serializable pour les clôtures comptables).
  4. Intercepter systématiquement les erreurs de deadlock et de sérialisation au niveau du code applicatif pour réexécuter la transaction (Retry Pattern avec backoff exponentiel).

8. Révision active

Résumé essentiel
  • Le contrat ACID garantit l’intégrité absolue des bases de données relationnelles face aux pannes et aux accès concurrents.
  • Les commandes TCL (BEGIN, COMMIT, ROLLBACK, SAVEPOINT) définissent et contrôlent le périmètre de la transaction.
  • Les trois anomalies de concurrence sont la lecture sale, la lecture non répétable et la lecture fantôme.
  • Les 4 niveaux d’isolation ANSI (Read Uncommitted, Read Committed, Repeatable Read, Serializable) offrent un compromis entre consistance et performances.
  • Les deadlocks sont prévenus par un ordonnancement déterministe des verrous et résolus automatiquement par le SGBD via l’annulation d’une transaction victime.
