Chapitre 6 — Vues, Procédures Stockées, Déclencheurs (Triggers) & Optimisation

Module 6 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Une application de gestion commerciale subit de graves ralentissements lors des heures de pointe : certaines requêtes SELECT mettent plus de 15 secondes à répondre en scannant séquentiellement une table de 10 millions de factures, et la logique d’audit des modifications de prix est dupliquée maladroitement dans trois microservices différents en Node.js, Python et Java. Pour résoudre ces goulets d’étranglement, l’ingénieur base de données doit centraliser les règles métier au plus près des données grâce aux déclencheurs (triggers) et procédures stockées, simplifier les accès aux données agrégées avec des vues matérialisées, et diagnostiquer les coûts d’exécution grâce à la commande EXPLAIN ANALYZE afin d’implanter les index B-Tree pertinents. Ce dernier module couronne le cursus SQL B2 par la maîtrise de la performance et de l’architecture serveur.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. concevoir des vues relationnelles standard et exploiter les vues matérialisées pour précalculer des agrégations lourdes ;
  2. comprendre le rôle des procédures stockées et fonctions serveur pour encapsuler la logique métier critique ;
  3. écrire des déclencheurs (Triggers) BEFORE et AFTER manipulant les pseudo-enregistrements NEW et OLD à des fins de validation et d’audit ;
  4. analyser la structure interne des index B-Tree et leurs cas d’usage (index simples, composites, partiels) ;
  5. déchiffrer un plan d’exécution SQL (EXPLAIN / EXPLAIN ANALYZE) pour traquer les parcours séquentiels (Seq Scan) pénalisants.

1. Vues Relationnelles & Vues Matérialisées

Une vue (VIEW) est une table virtuelle définie par une requête SELECT stockée dans le dictionnaire du SGBD. Elle ne stocke aucune donnée physique par défaut : à chaque consultation, la requête sous-jacente est exécutée.

1. Vues Standard (Sécurité & Abstraction)

Permet de masquer la complexité des jointures et de restreindre l’accès aux colonnes confidentielles (ex: masquer le mot de passe) :

CREATE VIEW v_clients_actifs AS SELECT id, nom, email, ville FROM Clients WHERE actif = TRUE;

2. Vues Matérialisées (Performance Analytique)

Stocke physiquement le résultat sur disque. Idéal pour des tableaux de bord analytiques complexes réactualisés périodiquement :

CREATE MATERIALIZED VIEW mv_ca_mensuel AS SELECT date_trunc('month', date_cmd) AS mois, SUM(total) AS ca FROM Commandes GROUP BY 1; -- Rafraîchissement manuel ou planifié : REFRESH MATERIALIZED VIEW mv_ca_mensuel;

2. Déclencheurs (Triggers) : Automatisation & Tables d’Audit

Un déclencheur (Trigger) est une procédure automatiquement exécutée par le moteur du SGBD lorsqu’un événement spécifique survient sur une table (INSERT, UPDATE, DELETE).

BEFORE vs AFTER

  • BEFORE : S’exécute avant la modification physique. Utilisé pour valider des données, forcer des valeurs par défaut ou lever une erreur bloquante.
  • AFTER : S’exécute après la validation de l’opération. Utilisé pour alimenter des tables de traçabilité (audit logs) ou synchroniser d’autres tables.

Les variables NEW et OLD

  • NEW : Représente le nouvel enregistrement proposé (disponible lors de INSERT et UPDATE).
  • OLD : Représente l’état existant avant modification (disponible lors de UPDATE et DELETE).
CREATE TRIGGER trg_audit_prix AFTER UPDATE ON Produits FOR EACH ROW BEGIN IF OLD.prix != NEW.prix THEN INSERT INTO HistoriquePrix (produit_id, ancien_prix, nouveau_prix, modifie_le) VALUES (OLD.id, OLD.prix, NEW.prix, CURRENT_TIMESTAMP); END IF; END;

3. Optimisation Physique, Index B-Tree & Plans d’Exécution EXPLAIN

Par défaut, pour trouver une ligne dans une table sans index, le SGBD doit inspecter chaque bloc de données du disque : c’est le parcours séquentiel (Sequential Scan / Table Scan), dont le coût est proportionnel à la taille O(N).

L’Index B-Tree (Arbre Équilibré)

Structure d’arbre hiérarchique triée stockant les clés et les pointeurs vers les blocs physiques. Permet de localiser n’importe quel enregistrement en un nombre d’accès constant et minuscule O(log N) :

CREATE INDEX idx_clients_email ON Clients(email); -- Index composite (respecter la règle du préfixe à gauche) : CREATE INDEX idx_cmd_date_client ON Commandes(date_cmd, client_id);

L’Analyse avec EXPLAIN

La commande EXPLAIN dévoile la stratégie choisie par le planificateur de requêtes :

  • Index Scan : Parcours ultra-rapide via l’arbre d’index.
  • Seq Scan : Parcours intégral de la table. Si une requête filtrée sur une colonne fait un Seq Scan, il manque un index !

Si vous écrivez WHERE UPPER(nom) = 'DUPONT', un index ordinaire sur nom est totalement ignoré par le SGBD car la fonction UPPER() est appliquée à chaque ligne lors de l’évaluation ! Pour optimiser cette requête, il faut créer un index fonctionnel dédié :

CREATE INDEX idx_clients_nom_upper ON Clients(UPPER(nom));

5. QCM — niveau examen

Quelle est la différence fondamentale entre une vue standard (CREATE VIEW) et une vue matérialisée (CREATE MATERIALIZED VIEW) ?

Une vue standard est une simple définition de requête qui n’occupe aucun espace de stockage. Une vue matérialisée enregistre physiquement les données calculées sur disque pour accélérer les consultations massives au prix d’un rafraîchissement (REFRESH) périodique.

Dans un déclencheur SQL de type BEFORE INSERT, que représente la pseudo-variable NEW ?

Dans un trigger BEFORE/AFTER INSERT ou UPDATE, NEW contient les données de la ligne candidate. En mode BEFORE, le trigger peut valider ou même rectifier directement les attributs de NEW (ex: forcer un stock négatif à 0) avant l’écriture sur disque.

Pourquoi une condition telle que WHERE YEAR(date_commande) = 2026 peut-elle transformer un Index Scan rapide en un Seq Scan très lent sur une table de 5 millions de lignes ?

Enveloppe la colonne dans une fonction (YEAR(col)) oblige le SGBD à évaluer la fonction pour chaque ligne de la table au lieu de naviguer dans l’arbre d’index. Il vaut mieux écrire 'WHERE date_commande >= '2026-01-01' AND date_commande < '2027-01-01'' pour préserver l’index.

Quel type de structure d’indexation est utilisé par défaut dans la grande majorité des SGBD relationnels (PostgreSQL, MySQL InnoDB, Oracle) pour les clés primaires et colonnes uniques ?

L’arbre B-Tree équilibré est le standard universel des bases relationnelles car il optimise à la fois les recherches d’égalité stricte (=) et les requêtes par plage de valeurs (<, >, BETWEEN).

Dans un plan d’exécution obtenu par la commande EXPLAIN ANALYZE, quelle information supplémentaire essentielle est fournie par rapport à un simple EXPLAIN ?

EXPLAIN ne fait qu’estimer les coûts selon les statistiques du catalogue. EXPLAIN ANALYZE exécute réellement la requête et compare les estimations du planificateur avec la réalité des temps et volumes d’exécution réels.

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Ajouter des index sur toutes les colonnes d’une table sans discernement : chaque index accélère la lecture mais pénalise lourdement toutes les opérations d’écriture (INSERT, UPDATE, DELETE).
  • Créer un index composite (colA, colB) et espérer qu’il accélère une requête filtrant uniquement sur colB (règle du préfixe le plus à gauche non respectée).
  • Utiliser des déclencheurs (triggers) pour exécuter des calculs lourds ou des appels réseau externes, ce qui paralyse les transactions utilisatrices.
  • Négliger le rafraîchissement (REFRESH MATERIALIZED VIEW) d’une vue matérialisée, servant alors des données obsolètes depuis plusieurs semaines.
  • Ne pas analyser les plans d’exécution avec EXPLAIN avant la mise en production de requêtes critiques à fort volume.

7. Méthodologie de résolution

Protocole en 4 étapes pour auditer et optimiser les performances d’une requête lente
  1. Préfixer la requête lente avec EXPLAIN (ANALYZE, BUFFERS) pour inspecter les nœuds du plan d’exécution et repérer les Seq Scan sur les grosses tables.
  2. Vérifier les clauses WHERE et JOIN : identifier les colonnes filtrées sans index ou les expressions neutralisant un index existant (ex: UPPER(col) ou DATE(col)).
  3. Créer l’index approprié (B-Tree simple sur colonne sélective, composite en plaçant la colonne d’égalité en premier, ou partiel avec WHERE actif = TRUE).
  4. Réexécuter EXPLAIN ANALYZE pour confirmer le passage à un Index Scan et mesurer le gain réel de latence (passage de secondes à quelques millisecondes).

8. Révision active

Résumé essentiel
  • Les vues simplifient les requêtes et restreignent les accès ; les vues matérialisées stockent physiquement les agrégats lourds.
  • Les déclencheurs (BEFORE/AFTER) automatisent les contrôles de cohérence et l’audit sans modifier le code applicatif client.
  • Les pseudo-variables NEW et OLD permettent d’intercepter et de comparer les états avant et après modification.
  • Les index B-Tree réduisent le coût de recherche de O(N) à O(log N) mais consomment du stockage et ralentissent les écritures.
  • La commande EXPLAIN ANALYZE est l’outil de référence absolu pour diagnostiquer les plans d’exécution et neutraliser les parcours séquentiels indésirables.

Checklist de maîtrise

  • Je sais quand créer une vue standard et quand opter pour une vue matérialisée.
  • Je maîtrise l’usage des variables NEW et OLD dans un trigger d’audit.
  • Je comprends pourquoi envelopper une colonne dans une fonction dans WHERE neutralise l’index classique.
  • Je sais interpréter un plan d’exécution EXPLAIN (Seq Scan vs Index Scan).
  • Je sais concevoir un index composite en respectant la règle du préfixe à gauche.
