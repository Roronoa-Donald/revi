1 1. Les types numériques

Le standard SQL distingue rigoureusement les entiers, les nombres décimaux exacts (à virgule fixe) et les flottants approchés. Le choix d'un type a un impact direct sur la volumétrie de stockage sur disque et la validité des calculs arithmétiques.

Tableau 1 — Synthèse comparative des types numériques SQL Standard
Type Plage (signé) Usage typique
TINYINT -128 à +127 Âge humain, mois de l'année, statut binaire étendu
SMALLINT -32 768 à +32 767 Nombre de pages, petites quantités en stock
INT / INTEGER ≈ -2,14 milliards à +2,14 milliards Identifiants primaires standards (clés ID), compteurs globaux
BIGINT ≈ -9,22 × 10¹⁸ à +9,22 × 10¹⁸ Horodatages microsecondes, ID réseaux sociaux mondiaux
DECIMAL(p,s) Exacte selon précision (p) et échelle (s) Comptabilité, montants financiers (ex: DECIMAL(10,2))
FLOAT / REAL Virgule flottante IEEE 754 (approchée) Coordonnées GPS, mesures scientifiques physiques
verified Règle d'or : Pourquoi le DECIMAL est incontournable pour la monnaie

En machine, FLOAT code les valeurs en base 2. La fraction 0.10 ne possède pas de représentation binaire finie exacte, créant de minuscules résidus d'imprécision (ex: 0.10000000000000002). À l'inverse, DECIMAL(10, 2) stocke 10 chiffres significatifs avec exactement 2 décimales fixes garanties au centime près.

2 2. CHAR et VARCHAR

Pour stocker des chaînes textuelles, deux types coexistent : CHAR(n) (taille fixe) et VARCHAR(n) (taille variable). L'erreur courante consiste à utiliser VARCHAR sans distinction, au détriment des performances d'indexation sur des codes formatés.

Tableau 2 — Comparaison du stockage en mémoire Longueur définie : n = 5
Valeur entrée Stockage dans CHAR(5) Stockage dans VARCHAR(5)
'SQL' 'SQL  ' (3 caractères + 2 espaces) 'SQL' (3 caractères + 1 octet de longueur)
'PARIS' 'PARIS' (5 octets) 'PARIS' (5 octets + 1 octet de longueur)
'FR' 'FR   ' (complété à droite) 'FR' (longueur dynamique)
check Cas où CHAR(n) gagne

Longueur invariante stricte : Codes ISO pays (CHAR(2)), plaques d'immatriculation, codes postaux, hash MD5/SHA.

check Cas où VARCHAR(n) gagne

Longueur variable : Nom, prénom, adresse e-mail, libellé produit, commentaires. Évite le gaspillage d'espace disque.

3 3. Les types temporels

Le SQL standard impose la norme universelle ISO 8601. Le piège récurrent pour les développeurs francophones réside dans l'utilisation instinctive de dates au format JJ/MM/AAAA, catégoriquement rejetées par les analyseurs SQL ou interprétées de façon ambiguë.

Tableau 3 — Types temporels et littéraux standards Norme ISO 8601
Type Contenu Format littéral SQL valide
DATE Date calendaire (Année, Mois, Jour) '2025-03-30' (YYYY-MM-DD)
TIME Heure du jour (Heure, Minute, Seconde) '14:30:00' (HH:MM:SS)
DATETIME / TIMESTAMP Instantané complet (date + horaire exact) '2025-03-30 14:30:00'
error
Piège d'examen critique

Ne jamais écrire '21/11/2014' dans une clause WHERE ou VALUES. SQL attend strictement '2014-11-21', délimité par des guillemets simples (').

4 4. CREATE TABLE et INSERT

La commande de définition des données (DDL) CREATE TABLE permet d'allouer la table, de définir le type de chaque colonne et d'attacher des contraintes déclaratives qui garantissent la cohérence des insertions.

schema_definition.sql
DDL SQL 
CREATE TABLE IF NOT EXISTS Marque (
    codemarque   INTEGER PRIMARY KEY,
    nommarque    VARCHAR(50) NOT NULL UNIQUE,
    paysmarque   CHAR(2) DEFAULT 'FR'
);

CREATE TABLE IF NOT EXISTS Equipement (
    idequipement INTEGER PRIMARY KEY,
    nomequipement VARCHAR(100) NOT NULL,
    prix         DECIMAL(8,2) DEFAULT 0.00,
    codemarque   INTEGER REFERENCES Marque(codemarque)
);

Insertion de tuples avec INSERT INTO

Lorsqu'on omet une colonne dans la liste d'insertion, SQL injecte automatiquement sa valeur définie par DEFAULT. Si aucun DEFAULT n'est spécifié, il insère NULL (sauf si NOT NULL est actif, ce qui produit un rejet immédiat).

INSERT INTO Marque (codemarque, nommarque)
VALUES (1, 'Logitech'); -- Le champ 'paysmarque' recevra automatiquement 'FR' via la clause DEFAULT.

5 5. Ajouter une colonne avant de s’exercer

L'évolution d'un schéma en production ne nécessite pas de supprimer puis recréer la table. On utilise ALTER TABLE ... ADD COLUMN.

ALTER TABLE Equipement
ADD COLUMN garantie_mois INTEGER DEFAULT 24;

Remarque : Les lignes déjà présentes dans la table recevront instantanément la valeur 24 pour la nouvelle colonne.

8 8. Erreurs classiques — récapitulatif

1

Utilisation de FLOAT pour les montants financiers

Conséquence : Perte de centimes lors des additions de TVA ou des cumuls d'écritures. Solution : Toujours déclarer DECIMAL(12,2) ou NUMERIC.

2

Oubli des guillemets simples autour des chaînes et dates ISO

Conséquence : Écrire 2025-01-01 sans apostrophes est interprété par le compilateur SQL comme une soustraction arithmétique (2025 - 1 - 1 = 2023), entraînant des données corrompues.

3

Insertion partielle sur colonne NOT NULL sans valeur DEFAULT

Conséquence : Échec immédiat de la transaction : NOT NULL constraint failed. Toute colonne non alimentée doit posséder un DEFAULT ou tolérer NULL.

9 9. Méthodologie de résolution

route Protocole en 4 étapes pour concevoir une table relationnelle robuste
1

Identification de l'entité et de sa clé

Désignez le concept modélisé au singulier et isolez la clé primaire naturelle ou technique (id INTEGER PRIMARY KEY).

2

Choix strict des types & longueurs

Fixe = CHAR(n), Variable = VARCHAR(n), Monnaie = DECIMAL(p,s), Dates = DATE/DATETIME.

3

Déclaration des contraintes d'intégrité

Systématisez NOT NULL pour les attributs obligatoires, UNIQUE pour les identifiants métier alternatifs, et DEFAULT pour les valeurs par défaut prévisibles.

4

Validation par insertion de cas tests

Injectez immédiatement un tuple nominal complet, puis vérifiez que les cas d'erreur attendus (violation de contrainte NOT NULL ou de clé dupliquée) sont bien rejetés.
