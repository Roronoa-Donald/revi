Chapitre 4 — Diagramme de Séquence, Lignes de Vie & Fragments Combinés

Module 4 ≈ 2 h 45 de travail Réservé B2 et plus
Mise en situation

Au sein d’une architecture microservices de paiement instantané, des clients subissent des blocages inexpliqués : des transactions restent suspendues indéfiniment lors des pics de charge, provoquant des dépassements de délai et des pertes de paniers d’achat. L’investigation révèle que les services s’appellent mutuellement de manière synchrone en formant des dépendances circulaires masquées. Pour cartographier la dynamique temporelle, valider le parallélisme et prouver l’absence d’interblocage (deadlock), l’équipe recourt au diagramme de séquence UML 2.5. Ce module forme les étudiants à modéliser la chronologie exacte des échanges, à maîtriser la typologie des flèches de messages et à structurer la logique conditionnelle via les fragments combinés normalisés.

Objectifs pédagogiques

À la fin de ce chapitre, vous serez capable de :

  1. définir une ligne de vie (lifeline) avec sa syntaxe normalisée (nomInstance : TypeClassificateur) ;
  2. représenter les périodes d’activité d’un objet via les barres d’activation (execution specifications) ;
  3. distinguer et tracer les 4 types de flèches de messages (synchrone plein, asynchrone ouvert, retour tireté, création) ;
  4. modéliser la création dynamique d’un objet et sa destruction explicite avec la croix de terminaison (X) ;
  5. structurer les flux conditionnels et répétitifs à l’aide des fragments combinés alt, opt, loop et par ;
  6. analyser une séquence temporelle pour détecter les boucles de rétro-appel bloquantes et prévenir les deadlocks.

1. Lignes de Vie, Barres d’Activation et Chronologie

Le diagramme de séquence capture les interactions temporelles entre objets au cours d’un scénario précis. Le temps s’écoule conventionnellement de haut en bas :

  • Ligne de vie (Lifeline) : Rectangle supérieur représentant l’objet ou le rôle, prolongé vers le bas par une ligne pointillée verticale. La syntaxe officielle est nomInstance : Classe (ou :Classe si l’instance est anonyme).
  • Barre d’activation (Execution Specification) : Rectangle étroit superposé à la ligne de vie indiquant la période pendant laquelle l’objet exécute une action ou attend la réponse d’un appel synchrone.
  • Création d’objet : Un message horizontal pointant directement sur le rectangle d’en-tête de la ligne de vie de l’objet nouvellement créé (annoté «create»).
  • Destruction d’objet : Une grande croix X à l’extrémité de la ligne pointillée signifiant que l’objet a été libéré de la mémoire.

2. Typologie des Messages et Conventions Graphiques OMG

Chaque type d’interaction possède une notation graphique rigoureuse dans la spécification UML 2.5 :

Type de message Notation graphique Sémantique temporelle Exemple concret
Synchrone Trait plein avec triangle noir plein fermé (→) L’émetteur bloque son exécution et attend que le destinataire ait terminé le traitement. Appel de méthode classique bloquant (ex: calculerMontant()).
Asynchrone Trait plein avec flèche simple ouverte (→) L’émetteur envoie le message et poursuit immédiatement son travail sans bloquer. Message MQ, événement Kafka, notification (ex: notifierEmail()).
Message de retour Trait tireté avec flèche simple ouverte (‐‐>) Retour de valeur de la méthode vers l’appelant, libérant la barre d’activation. Renvoi du résultat calculé (ex: solde = 250.00 €).
Message réflexif Flèche en boucle sur la même ligne de vie Un objet invoque une méthode privée sur lui-même (auto-appel). Traitement interne (ex: validerFormatDate()).

3. Fragments Combinés d’Interaction (Combined Fragments)

Depuis UML 2.0, les organigrammes et conditions algorithmiques sont formalisés au sein de cadres rectangulaires appelés fragments combinés, identifiés par un opérateur d’interaction dans le coin supérieur gauche :

alt (Alternatives exclusives)

Équivalent du if ... else if ... else. Le cadre est divisé en sous-compartiments horizontaux par des traits pointillés. Chaque compartiment est précédé d’une garde entre crochets [condition]. Seul le compartiment dont la garde s’évalue à vrai est exécuté.

opt (Comportement optionnel)

Équivalent d’un if simple sans clause else. Comporte un seul compartiment avec une garde [condition]. Si la condition est fausse, le flux poursuit directement en aval sans rien exécuter dans le cadre.

loop (Boucle d’itération)

Répétition d’une séquence. La syntaxe permet de fixer des bornes loop(min, max) ou une condition booléenne d’arrêt [tant que articlesRestants > 0].

par (Exécution parallèle)

Exécution concurrente. Les sous-compartiments séparés par des pointillés s’exécutent en parallèle sans ordre séquentiel prédéfini entre leurs messages respectifs.

2. À la fin de la séquence, toutes les activations doivent être fermées (pile vide).

Exercice 2 — Évaluateur de fragments combinés (alt, opt, loop)

Étude de cas Niveau 2 — Application

Objectif : Interpréter les fragments d'interaction UML (alt pour alternative exclusive, opt pour optionnel, loop pour itération).

Le script simule l'exécution d'un fragment combiné UML en fonction d'un contexte de variables initiales :
- Première ligne : variables d'état au format VAR k=v ... (ex: VAR solde=150 age=20).
- Lignes suivantes : blocs de séquence balisés :
* ALT [garde] ... ELSE ... END_ALT
* OPT [garde] ... END_OPT
* LOOP [N] ... END_LOOP (répète N fois le bloc)
* Messages simples : A -> B : msg
Le script évalue les gardes booléennes simples (ex: solde >= 100). Si la condition est vraie, les messages internes sont exécutés et affichés au format :
[EXEC] <Source> -> <Cible> : <msg>.
Si la garde est fausse, le bloc est ignoré (ou la branche ELSE est empruntée).
À la fin, afficher le nombre total de messages émis : MESSAGES TRANSMIS: <N>.

Cas d’exemple
VAR solde=200
ALT [solde >= 100]
  Client -> Distributeur : delivrerBillets
ELSE
  Client -> Distributeur : refuserRetrait
END_ALT
Résolution attendue
[EXEC] Client -> Distributeur : delivrerBillets
MESSAGES TRANSMIS: 1

La garde solde >= 100 est vraie (200 >= 100), la branche ALT est exécutée.

Deux indices, rédigés en mots
  1. Stocker les variables dans un dictionnaire pour évaluer les expressions de garde.
  2. Pour le bloc LOOP [N], exécuter le corps N fois.

Exercice 3 — Analyseur de synchronisme et concurrence de messages

Étude de cas Niveau 3 — Raisonnement

Objectif : Distinguer les messages synchrones (flèche pleine, appel bloquant) des messages asynchrones (flèche ouverte, non bloquant) et détecter les risques de blocage.

Analysez les données fournies pour chaque cas. Si un émetteur A tente un appel (synchrone ou asynchrone) alors qu'il est lui-même déjà bloqué en attente d'une réponse synchrone : [BLOCAGE] <A> ne peut pas emettre (bloque en attente de reponse).
2. Si un appel synchrone est circulaire direct (A attend B et B attend A) : [DEADLOCK] Interblocage mutuel detecte entre <A> et <B>.
3. Sinon, affichezzr : [OK] <TYPE> de <A> vers <B> (Statut <A>: <BLOQUE|LIBRE>).

Cas d’exemple
SYNC Client ->> Serveur : getData
ASYNC Serveur -> Logger : logEvent
REPLY Serveur --> Client
SYNC Client ->> Autre : check
Résolution attendue
[OK] SYNC de Client vers Serveur (Statut Client: BLOQUE)
[OK] ASYNC de Serveur vers Logger (Statut Serveur: LIBRE)
[OK] REPLY de Serveur vers Client (Statut Client: LIBRE)
[OK] SYNC de Client vers Autre (Statut Client: BLOQUE)

Le client se bloque sur l'appel synchrone, le serveur émet en asynchrone sans bloquer, puis le client est débloqué.

Deux indices, rédigés en mots
  1. Maintenir l'état de chaque lifeline : bloquée (avec le nom de l'acteur attendu) ou libre.
  2. Un message asynchrone n'altère pas la disponibilité de l'émetteur.

5. QCM — niveau examen

Comment est représenté graphiquement un appel de méthode synchrone (bloquant pour l’émetteur) en UML 2.5 ?

En UML 2.5, le message synchrone est impérativement représenté par un trait plein terminé par une tête de flèche triangulaire noire pleine fermée.

Quelle flèche est utilisée pour représenter le retour d’une valeur de fonction (message de réponse) ?

Le message de retour (reply message) s’illustre formellement par un trait tireté muni d’une flèche ouverte simple pointant vers l’émetteur initial.

Quel opérateur de fragment combiné correspond à une structure conditionnelle exclusive à plusieurs branches (if / else if / else) ?

L’opérateur «alt» (alternatives) divise un cadre en compartiments exclusifs séparés par des pointillés, chacun surveillé par une condition de garde.

Quelle est la différence fondamentale entre les opérateurs de fragments «alt» et «opt» ?

L’opérateur «opt» (option) contient un unique sous-bloc exécuté seulement si sa garde est vraie ; «alt» définit plusieurs branches alternatives exclusives.

Comment note-t-on graphiquement la destruction définitive d’un objet à la fin de sa ligne de vie ?

La fin de vie d’un objet et sa libération mémoire sont formellement symbolisées par une croix «X» sur sa ligne de vie (destruction occurrence).

Quel opérateur de fragment combiné permet de spécifier que plusieurs groupes de messages s’exécutent de façon concurrente en parallèle ?

L’opérateur «par» (parallel) modélise la concurrence : les sous-compartiments s’exécutent en parallèle, les messages s’entremêlant de manière non déterministe.

Dans quelle direction s’écoule conventionnellement le temps dans un diagramme de séquence UML ?

L’axe vertical d’un diagramme de séquence représente la flèche du temps : la chronologie progresse strictement de haut en bas.

Que désigne le phénomène d’«interblocage» (deadlock) observable dans les mauvaises modélisations de séquences ?

Un deadlock survient lorsque le service A attend la réponse synchrone de B, tandis que B attend la réponse synchrone de A (attente circulaire bloquante).

6. Erreurs classiques — récapitulatif

À reconnaître en examen
  • Dessiner une flèche pleine fermée pour un message asynchrone : cela induit en erreur sur le caractère bloquant de l’appel.
  • Oublier les conditions de garde entre crochets [condition] dans les compartiments d’un fragment alt.
  • Faire remonter le temps : dans un diagramme de séquence, le temps s’écoule strictement du haut vers le bas.
  • Créer des dépendances synchrones circulaires (A appelle synchrone B qui rappelle synchrone A) : risque majeur de deadlock.
  • Invoquer des messages qui n’existent pas dans les opérations de la classe réceptrice.

7. Méthodologie de résolution

Méthodologie de Conception d’un Diagramme de Séquence Robuste
  1. Étape 1 — Délimiter le scénario : Choisir un cas d’utilisation ou une branche précise (ex: scénario nominal de paiement par carte).
  2. Étape 2 — Aligner les lignes de vie : Positionner les objets de gauche à droite dans l’ordre naturel d’interaction (Acteur → IHM → Contrôleur → Métier → BDD/Tiers).
  3. Étape 3 — Choisir le bon type de message : Utiliser des flèches fermées pleines pour les appels de fonctions synchrones et des flèches ouvertes pour les événements asynchrones.
  4. Étape 4 — Matérialiser les retours et activations : Faire figurer les barres d’activation pour visualiser la durée de blocage et tracer les retours tiretés lorsque des valeurs sont produites.
  5. Étape 5 — Encadrer la logique avec les fragments normalisés : Utiliser alt pour les cas de succès/erreur, opt pour les options, et loop pour les traitements en lot.
  6. Étape 6 — Auditer la cohérence avec le modèle de classes : S’assurer que chaque message correspond exactement au nom d’une méthode publique déclarée dans la classe destinataire.

8. Révision active

Résumé essentiel
  • Le diagramme de séquence modélise l’ordre chronologique des échanges de messages entre lignes de vie.
  • Une ligne de vie représente un participant individuel (nom:Type) avec sa barre d’activation verticale.
  • Les messages synchrones (flèche pleine fermée) bloquent l’émetteur, contrairement aux messages asynchrones (flèche ouverte simple).
  • Les messages de retour utilisent un trait tireté avec flèche ouverte pour transmettre le résultat calculé.
  • Les fragments combinés (alt, opt, loop, par) structurent la logique conditionnelle et concurrente directement sur le diagramme.
  • La cohérence transversale exige que chaque message d’une séquence corresponde à une méthode définie dans le diagramme de classes.

Checklist de maîtrise

  • Je sais tracer une ligne de vie avec la syntaxe normalisée nom:Type.
  • Je distingue visuellement une flèche de message synchrone d’une flèche asynchrone.
  • Je trace les messages de retour avec un trait tireté.
  • Je sais découper un fragment alt en sous-compartiments avec leurs gardes entre crochets [condition].
  • Je comprends l’usage d’un fragment opt pour une action conditionnelle sans alternative else.
  • Je sais identifier un risque d’interblocage (deadlock) dans une suite d’appels synchrones croisés.

Les 8 notions à connaître absolument

  1. Lignes de vie (Lifelines)
  2. Barres d’activation (Execution Specifications)
  3. Messages synchrones (flèche pleine fermée)
  4. Messages asynchrones (flèche ouverte)
  5. Messages de retour (trait tireté)
  6. Fragment combiné alt (alternatives)
  7. Fragment combiné opt (optionnel)
  8. Fragment combiné loop & par
